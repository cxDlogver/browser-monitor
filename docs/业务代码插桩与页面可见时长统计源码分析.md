# 业务代码插桩与页面可见时长统计源码分析

本文分析 **业务方如何决定记录什么、在什么生命周期产生记录、怎样调用浏览器监控 SDK**。以通用网站访问、页面停留和关键操作为问题起点，再对应已核验的 `browser-monitor` SDK 源码；其中 `official-network` 展示 SDK 的真实接入方式，但属于**另一个业务项目**，不能将它的路由和计时器代码误认为监控 SDK 的内置功能。

本专题只分析**浏览器内业务埋点的设计与产生记录的过程**，不展开记录上报后的服务端计算、存储和展示。SDK 内部从 Envelope 到 Processing、Transport 的真实机制，见[监控 SDK 执行链路源码分析](./监控SDK业务插桩与TraceSpan执行链路源码分析.md)。与项目无关的通用机制见[监控 SDK 插桩与 Trace/Span 工程体系](https://github.com/cxDlogver/cx-learn-notes/blob/main/Full-Stack-AI-NOTES/J-%E7%9B%91%E6%8E%A7SDK%E6%8F%92%E6%A1%A9%E4%B8%8ETraceSpan%E5%B7%A5%E7%A8%8B%E4%BD%93%E7%B3%BB.md)。

## 1. 业务目标先决定记录对象，再选择 Event、Span 或 Trace

### 【页面统计实际上包含三类不同的事实】

以不依赖特定网站的访问过程为例：

~~~text
用户进入网站
    ↓ 访问首页，浏览一段时间
点击产品入口
    ↓ 导航到产品详情
切换标签页，过一段时间返回
    ↓ 继续浏览并点击咨询按钮
离开网站
~~~

业务方可能需要三个不同答案：

1. **行为计数**：点击了哪个按钮、提交表单成功几次？事实发生在某一时刻，适合 Event。
2. **业务计算结果**：产品页有效可见多少毫秒？由业务计时器累计，完成时生成一条带 `visibleMs` 的 Event 就够了。
3. **完整过程关系**：一次访问经历了几个页面，各阶段什么时候开始、什么时候结束、关键行为落在哪个阶段？这时 Trace（一次访问）+ Span（一次页面停留）+ Event（点击）的组合才有附加价值。

~~~text
最小化统计：
进入页 → 计时器累计可见时间 → 离开页 → track("page.stay.completed", visibleMs)

需要还原访问轨迹：
访问 Trace
    ├─ 首页停留 Span ── Event（产品点击）
    ├─ 产品停留 Span ── Event（联系按钮）
    └─ 联系页停留 Span
~~~

不要把“使用 Span 记录了一段持续时间”误认为“已经完成有效可见时长统计”。这两个问题相互独立。

### 【何时不需要 Span，何时必须保留它的时间区间语义】

| 要回答的业务问题 | 最小插桩 | 附加能力与代价 |
| --- | --- | --- |
| 按钮点击次数、表单成功次数 | `monitor.track()` | 不要求额外管理起止状态 |
| 单个页面访问完成后的有效可见时长 | `VisibleTimer + monitor.track()` | 单条完成记录足够；需保证原始页面身份 |
| 一次请求从发起到完成的状态、耗时和异常 | `Span.start/end` | 有明确时间区间，可关联错误与子调用 |
| 一次访问多个页面与按钮动作的完整时间轴 | `Trace + 页面 Span + Event` | 需要管理 Trace/Span 生命周期与父子关联 |
| 点击后用户是否真正提交成功 | `attempt / success / failure` 等业务 Event | 不能将点击等同于业务成功 |

**结论：先定义分析问题和时间口径，再按信息需求选择最小的数据模型。** 所有业务事实不需要都包装成 Span；全部使用 Span 反而会增加管理成本。

## 2. 当前 SDK 的对外接口与父子关联怎样工作

### 【实际 API 并不是通用 OTel 的 tracer.startActiveSpan】

源码：[sdk/src/core/monitor.ts](../sdk/src/core/monitor.ts)、[sdk/src/collectors/event/custom/index.ts](../sdk/src/collectors/event/custom/index.ts)。

当前对外接口包含：

~~~ts
interface Monitor {
  track(name: string, data?: CustomSignalInput): void;
  startTrace(name: string, data?: CustomSignalInput): TraceHandle;
  trace<T>(name: string, callback: (trace: TraceHandle) => T, data?: CustomSignalInput): T;
}
interface TraceHandle {
  readonly traceId: string;
  startSpan(name: string, data?: CustomSignalInput): SpanHandle;
  addEvent(name: string, data?: CustomSignalInput): void;
  end(options?: CustomSignalEndInput): void;
}
interface SpanHandle {
  readonly traceId: string;
  readonly spanId: string;
  startSpan(name: string, data?: CustomSignalInput): SpanHandle;
  addEvent(name: string, data?: CustomSignalInput): void;
  end(options?: CustomSignalEndInput): void;
}
~~~

代码片段省略了 `span()`、`setAttribute()`、`setMetric()` 等成员，**接口形态和方法名与源文件一致**。`CustomSignalInput` 包含 `attributes` 与 `metrics`，后者数据格式为 `{value, unit}`。

当前 SDK 的 `monitor.track()` 创建一条独立业务 Event；`trace.addEvent()` 创建带 Trace ID 的 Event；`span.addEvent()` 创建同时带 Trace ID、Span ID 和可选父 Span ID 的 Event。**如果希望点击事件能归属当前停留 Span，业务层需要调用当时的 Span Handle，普通 `monitor.track()` 并不会自动查找活动 Span。**

### 【Span 在开始时确定归属，但不等于必须上传对象树】

真实实现中的关键状态与数据关联：

~~~ts
class TraceHandleImpl extends TimedHandle implements TraceHandle {
  readonly traceId = createId('trace');
  readonly children = new Set<SpanHandleImpl>();
  // ...
  startSpan(name: string, data?: CustomSignalInput): SpanHandle {
    if (this.ended || !this.owner) return new SpanHandleImpl(undefined, this, undefined, name);
    const span = new SpanHandleImpl(this.owner, this, undefined, requiredName(name), data);
    this.children.add(span);
    return span;
  }
}
~~~

~~~ts
private correlation(): CorrelationContext {
  return {
    traceId: this.traceId,
    spanId: this.spanId,
    ...(this.parent ? { parentSpanId: this.parent.spanId } : {}),
  };
}
~~~

当前设计**在运行时用父对象和 `children` 集合管理开放句柄**，并在生成记录时用独立 ID 表达关联。父级 `end()` 会递归取消尚未结束的子级，这是当前 SDK 的本地取消策略，不是通用分布式追踪的必须语义。

当前 `ContextManager` 负责 App、Session、View 等业务环境快照，**不是通过 AsyncLocalStorage 或浏览器隐式活动上下文自动绑定父 Span**。因此业务接入层必须保存当前 `visitTrace` 和 `routeSpan` 的引用，主动选择 `trace.startSpan()` 或 `span.addEvent()`。

## 3. 有效可见时长为什么必须由业务计时器单独计算

### 【Span 持续时间与页面可见时间不能混为一谈】

假设打开页面后先浏览 20 秒，切到后台 30 秒，再回来浏览 10 秒，最后跳转：

~~~text
页面开始 ── 可见20s ── hidden30s ── 可见10s ── 页面结束
    └──────────── Span duration = 60s ─────────────┘

业务需要的有效可见时长 visibleMs = 20s + 10s = 30s
~~~

浏览器 Page Visibility API 里的 `document.visibilityState` 用来判断**整个文档是否在可见状态**，而不是判断特定模块是否进入屏幕视口；后者需要单独引入 IntersectionObserver。

因而若只关心最终时长，可暂停计时器 + Event 即可；若还关心这段停留在访问时间线上的起止与其他步骤的关系，可以同时保存 Span 和 `visibleMs`。

### 【当前业务计时器如何保存累计值】

业务实现：[official-network/app/utils/monitor/visible-stopwatch.ts](https://github.com/cxDlogver/official-network/blob/main/app/utils/monitor/visible-stopwatch.ts)。

源码核心状态：

~~~ts
const now = options.now ?? defaultNow;
let accumulated = 0;
let runningSince: number | null = now();
let disposed = false;
~~~

它不是每秒启动一次加法定时器，而是在可见区间开始时记录单调时钟起点，到隐藏/结束时按时间差累加：

~~~ts
elapsed() {
  if (disposed || runningSince === null) return roundMs(accumulated);
  return roundMs(accumulated + Math.max(0, now() - runningSince));
},
pause() {
  if (disposed || runningSince === null) return;
  accumulated += Math.max(0, now() - runningSince);
  runningSince = null;
},
resume() {
  if (disposed || runningSince !== null) return;
  runningSince = now();
},
~~~

这三段是真实实现中的关键逻辑。`pause` 通过将 `runningSince` 置为 `null` 停止累计；`resume` 切换到新的区间起点；`elapsed` 在计时期间返回“累计值 + 本次区间尚未结算的时间”。`dispose()` 最终冻结读数。默认时钟为 `performance.now()`，避免系统墙钟调整直接影响区间差值。

该计时器只负责计量，不知道 Trace、Span、路由或者平台；用独立单元测试核验它的数学行为，比把所有计时状态写进 Nuxt 插件更容易维护。

## 4. 业务接入层如何映射网站生命周期

### 【插件只连接依赖，业务管理器负责行为】

真实业务接入：[official-network/app/plugins/monitor.client.ts](https://github.com/cxDlogver/official-network/blob/main/app/plugins/monitor.client.ts)。客户端插件核心调用顺序：

~~~ts
const stayTracker = createStayTracker(monitor, { router: useRouter() });

monitor.start();
stayTracker.begin();
~~~

`createMonitor()` 在这两行之前初始化 SDK。插件文件使用 `.client.ts`，防止服务端渲染时访问浏览器专有 API。**此处业务插件与计时器位于 official-network，而不是 browser-monitor SDK 自动推断页面时长。**

先创建 `stayTracker` 的原因是该函数会提前注册 DOM 监听；后续 `monitor.start()` 才安装 SDK 自身的生命周期处理。对 `pagehide` 来说，期望先由业务结算末段时长，然后 SDK 处理打开的 Trace/Span 并尝试冲刷。该顺序是具体接入条件，未来若 SDK 调整其生命周期钩子，不应默认仍成立。

### 【一次网站访问和一次页面停留分别管理】

业务编排：[official-network/app/utils/monitor/stay-tracking.ts](https://github.com/cxDlogver/official-network/blob/main/app/utils/monitor/stay-tracking.ts)。

~~~ts
let visitTrace: TraceHandle | null = null;
let visitStopwatch: VisibleStopwatch | null = null;
let routeSpan: SpanHandle | null = null;
let routeStopwatch: VisibleStopwatch | null = null;
let currentSection: SectionName | null = null;
~~~

- **访问级**：`visitTrace` + `visitStopwatch` 表示当前文档一次进站，统计整次访问有效可见时长。
- **页面级**：`routeSpan` + `routeStopwatch` 表示当前一级路由的一段停留，统计该板块有效可见时长。
- **业务归一化**：`currentSection` 表示板块而非每个 URL。实际 `/product/a` 与 `/product/b` 都归于 `/product`，在当前策略下不会分成两个 Span。

创建时的真实调用：

~~~ts
visitTrace = monitor.startTrace(VISIT_TRACE_NAME, {
  attributes: { entrySection: section, entryPath: currentPathname() },
});
openRouteSpan(section, currentPathname());
~~~

~~~ts
routeStopwatch = createVisibleStopwatch();
if (isHidden()) routeStopwatch.pause();

routeSpan = visitTrace?.startSpan(ROUTE_SPAN_NAME, {
  attributes: { section, path: pathname },
});
currentSection = section;
~~~

这段代码表明：计时器与 Span 由业务层同时创建，但两者职责不同。Span 在创建时冻结所属页面的 Context，所以稍后路由已切换再调用 `span.end()`，仍归属旧页面；若改为仅使用 Event，业务层必须显式保留**原页面身份**，不能无条件依赖提交 Event 时的当前 View。

### 【路由变化时先结算上一段，再开始下一段】

当前使用 `router.afterEach(handleRouteChange)` 监听已完成路由切换，并比较一级路由：

~~~ts
if (section === currentSection) {
  routeSpan?.setAttribute('path', pathname);
  return;
}

closeRouteSpan();
openRouteSpan(section, pathname);
~~~

`closeRouteSpan()` 读取旧计时器的 `elapsed()`，再调用：

~~~ts
span.end({ metrics: metricPatch(elapsed) });
~~~

**两个统计口径必须说清楚**：当前只有一级路由板块级时长；同一板块的不同子路径不会单独产生 Span。若需要逐 URL 的独立停留时长，应改变拆分策略，不能将原记录直接解释为子页面数据。

### 【切后台暂停，页面离开结算，BFCache 恢复重新开始】

原业务代码实际注册：

~~~ts
document.addEventListener('visibilitychange', onVisibilityChange);
window.addEventListener('pagehide', onPageHide);
window.addEventListener('pageshow', onPageShow);
~~~

对应行为：

~~~ts
const onVisibilityChange = () => {
  if (isHidden()) {
    visitStopwatch?.pause();
    routeStopwatch?.pause();
    return;
  }
  visitStopwatch?.resume();
  routeStopwatch?.resume();
};
const onPageHide = () => {
  finishVisit();
};
const onPageShow = (event: PageTransitionEvent) => {
  if (event.persisted) begin();
};
~~~

**隐藏与退出是两种不同状态**：切后台仅停止有效可见时间累计，Trace/Span 仍保持开放；`pagehide` 会结束当前停留 Span、结束访问 Trace，并把计算值写入 `visibleMs`。如从 BFCache 恢复，业务会重新开始一次进站区间，而不是继续已结束的 Span。

页面进程直接被关闭或崩溃时，`pagehide` 不是必然事件；若产品要求更强的最终时长可靠性，应另设可幂等的周期快照方案，不能声称已有本地实现可以覆盖所有异常退出。

### 【生命周期设计不能遗漏重复结算与初始隐藏状态】

`begin()` 使用 `if (visitTrace) return` 防止重复开始；`finishVisit()` 使用 `if (!visitTrace) return` 防止重复结束；`closeRouteSpan()` 清理计时器和 Span 引用后结束当前句柄。

创建计时器时默认运行，而 `begin()` 与 `openRouteSpan()` 会检测 `isHidden()` 并立即暂停，避免后台打开页面后继续累积可见时间。

这里应优先验证：路由快速连续切换、同一路由内动态路径变化、重复 `visibilitychange`、多次结束、隐藏后 `pagehide`、BFCache 往返、初始后台打开。

## 5. 关键按钮 Event 的插桩位置与当前实现边界

### 【关键动作的事实位置必须选在业务确认处】

真实官网首页的“立即开启”仍在按钮上直接执行 `navigateTo('/contact')`；联系页的 `handleSubmit` 主要执行表单验证、POST 请求及成功/失败状态更新。当前审查到的源码中**尚未发现这些关键按钮统一调用 `monitor.track()` 或 `routeSpan.addEvent()`**。因此这部分必须标为**建议扩展**。

按钮点击：

~~~ts
// 建议方案，非当前已实现的官网代码
function onClickCTA() {
  tracker.recordAction('site.cta.click', {
    buttonId: 'home.start',
    target: '/contact',
  });
  return navigateTo('/contact');
}
~~~

表单成功与失败应在业务结果被确认的分支分别上报，而不是把 `submit` 点击当成提交成功：

~~~ts
// 建议方案：使用业务语义，属性禁止包含姓名、手机号、邮箱或原始留言
tracker.recordAction('site.contact.submit_attempt', { formId: 'contact' });
try {
  await submitContact();
  tracker.recordAction('site.contact.submit_success', { formId: 'contact' });
} catch (error) {
  tracker.recordAction('site.contact.submit_failure', { formId: 'contact', reason: 'request_failed' });
  throw error; // 保持业务错误传播，不让埋点吞掉异常
}
~~~

### 【关键事件如何挂在当前页面的执行轨迹】

按当前 SDK 实际接口，建议由业务插桩层持有当前 `routeSpan`，不让每个页面组件直接管理底层 Span 对象：

~~~ts
// 建议加入业务 tracker 的方法（并非当前 stay-tracking.ts 已有）
function recordAction(name: string, attributes: Record<string, unknown>) {
  if (routeSpan) {
    routeSpan.addEvent(name, { attributes });
  } else {
    monitor.track(name, { attributes });
  }
}
~~~

`span.addEvent()` 会通过当前 Span 的 `correlation()` 生成关联字段；`monitor.track()` 默认不自动继承活动 Span，所以 fallback Event 在没有 Span Handle 时不保证关联到同一 Trace。若只做业务统计而不需要轨迹，所有操作都可以用 `monitor.track()`；**不要为了给一条 Event 带父 Span 而引入不必要的 Span 生命周期。**

## 6. 当前实现的代码证据、覆盖范围与工程取舍

### 【已实现、未实现及不能推出的结论】

| 观察点 | 可由现有代码证明的事实 | 不能推出的结论 |
| --- | --- | --- |
| SDK 自定义事件 | `monitor.track()` 接受 attributes/metrics | 点击事件自动有业务名称或关联父 Span |
| Trace / Span | 手动 `startTrace/startSpan`，结束产生独立记录 | Trace 不会丢失任何子 Span；父结束不影响子级 |
| 业务计时器 | `pause/resume/elapsed/dispose` 累计可见区间 | 用户真的在阅读或某元素一直在视口内 |
| 官网业务接入 | Client Plugin、Router Hook、Visibility、BFCache 路径 | 任意刷新/异常退出都会获得完整最终停留 |
| 关键按钮 | 找到按钮与表单的业务处理函数 | 已实现完整 CTA/表单 Event 上报 |
| 完整线上统计 | SDK 与业务接入代码具备数据生成能力 | 生产采集服务已经成功接收并入库 |

特别注意，当前官网插件中 DSN 仍采用本机 `localhost` 地址，**项目有接入代码，并不等于已证明公网部署的生产监控数据有效**。涉及服务端与 Transport 的可靠性问题，详见[SDK 执行链路分析](./监控SDK业务插桩与TraceSpan执行链路源码分析.md)。

### 【现有测试与补充验收方向】

已核对[tests/monitor-stay.test.ts](https://github.com/cxDlogver/official-network/blob/main/tests/monitor-stay.test.ts)：测试了路由归一、可见计时器累加、重复 pause/resume、终态冻结、非负和四舍五入行为。**现有这些单元测试没有证明 Nuxt 插件与 SDK 的端到端生命周期行为**。

建议后续针对业务插桩补齐：模拟 router.afterEach 时旧 Span 先结束；初始文档 hidden 时无累计；pagehide 与 SDK 清理的先后顺序；BFCache 恢复产生新 Trace；连续点击产生独立 Event；表单结果 Event 只在对应成功/失败分支发出。此处是**改进建议**，不计入已完成测试。

### 【业务插桩最值得复述的设计判断】

业务埋点设计应沿“问题与口径 → 最小观测事实 → 生命周期触发 → SDK API → 校验”逐步展开。

- **只要数值结果**：业务计时器计算 `visibleMs`，在约定完成时刻生成 Event。
- **还要操作过程**：Span 表达起止边界，必要时挂载 Event；Trace 关联多个阶段。
- **框架生命周期负责触发时机**：路由决定开始/结束，可见性决定暂停/恢复，页面离开决定最后结算。
- **管理边界独立**：插件注入依赖，业务 Tracker 管理语义与状态，VisibleStopwatch 只计算时间，SDK 负责记录机制与关联 ID。

Trace/Span 不是完成停留统计的前置要求；只有当产品确实需要访问轨迹和阶段间关系时，它们才比“一条带 visibleMs 的 Event”产生额外价值。
