# Browser Monitor 服务端可靠性体系源码学习从可靠接收到故障恢复建立完整控制链

> **文档定位**：本文是 Browser Monitor 服务端 Reliability（可靠性）的项目总入口。它不替代数据库、Redis、异步 Worker、Docker 等专项文档，而是从“系统发生故障以后怎样保护事实、限制影响、恢复工作并证明恢复成功”的横向视角，把这些专项重新连接起来。
>
> **事实边界**：当前实现结论以 browser-monitor main 分支源码、配置和已有项目文档为准；尚未实现的 Timeout Policy、Circuit Breaker、Worker Heartbeat、Redis / PostgreSQL 高可用等内容只作为演进建议，不写成现状。
>
> **通用知识入口**：[Full-Stack-AI-NOTES · 服务端可靠性体系](https://github.com/cxDlogver/cx-learn-notes/blob/main/Full-Stack-AI-NOTES/F-%E6%9C%8D%E5%8A%A1%E7%AB%AF%E5%8F%AF%E9%9D%A0%E6%80%A7%E4%BD%93%E7%B3%BB.md)。本文只负责回答：这些通用可靠性问题在 Browser Monitor 当前源码中具体怎样落地。

Browser Monitor 的服务端可靠性不能只看 Outbox Worker。一次遥测数据真正成为看板结果，需要跨过多个独立失败边界：

~~~text
Browser SDK
   ↓
Public Ingestion API
   ↓
Validation / Origin / Rate Limit
   ↓
PostgreSQL Transaction
   ├── telemetry_events
   └── outbox_tasks
   ↓
202 Accepted
   ↓
Outbox Worker
   ↓
Claim / Lease / Retry / Dead Letter
   ↓
Projection Transaction
   ↓
TimescaleDB / PostgreSQL
   ↓
Analytics API
   ↓
Redis Cache
   ↓
Web Dashboard
~~~

任何一层都可能失败，而且不同失败需要不同机制。因此项目可靠性应该从七个连续问题建立：

~~~text
1. 请求是否应该进入核心系统？
        ↓
2. 已经接受的事实能否原子保存？
        ↓
3. 离开 Request 的任务能否最终完成？
        ↓
4. Database / Redis 等依赖失败时影响边界在哪里？
        ↓
5. 流量大于处理能力时系统是否仍然受控？
        ↓
6. Process / Container 退出后能否安全恢复？
        ↓
7. 怎样证明数据链路没有静默丢失或长期积压？
~~~

## 1. 项目可靠性目标围绕可靠接收、状态正确、任务终结和运行可证明建立

### 【可靠性边界首先从 HTTP 202 的真实含义开始】

采集 Controller 返回 202 Accepted，但当前项目并不把 202 定义成“指标已经进入看板”。

真实时间线是：

~~~text
T0
SDK 发起采集

T1
Ingestion Service 完成校验

T2
PostgreSQL Transaction COMMIT
telemetry_events + outbox_tasks 持久化

T3
HTTP 202 Accepted

T4
Worker Claim Task

T5
Projection Transaction COMMIT

T6
outbox_tasks = completed

T7
Analytics Query / Cache 可读取新结果
~~~

因此项目至少存在三个不同完成语义：

| 完成阶段 | 当前可以承诺什么 | 不能承诺什么 |
| --- | --- | --- |
| 202 Accepted | 原始事件与对应后台任务已经成功进入数据库事务结果 | Worker 已经完成投影 |
| Worker Completed | 对应 Projection 已成功处理，Outbox 进入 completed | 所有缓存客户端已经看到最新结果 |
| Dashboard Visible | 查询路径已经能够返回结果 | 不代表所有历史聚合都已即时刷新 |

这也是可靠性分析的起点：**先把成功定义清楚，再讨论每一段如何防故障。**

项目全链路背景继续阅读 [浏览器监控平台 · 服务端全链路](./浏览器监控平台-服务端全链路.md)。

### 【当前可靠性目标更接近单集群内的故障恢复而不是完整高可用】

当前 Docker Compose 中：

~~~text
1 × TimescaleDB / PostgreSQL
1 × Redis
1 × API
1 × Worker
1 × Audit Worker
~~~

虽然 Database、Redis、API、Worker 都有持久化、Health 或 Restart 等保护，但当前配置没有 PostgreSQL Replica、Redis Sentinel / Cluster、多 API Replica 或跨节点 Failover。

因此目前可以确认的是：

~~~text
Process Crash Recovery
Task Retry / Reclaim
Database Transaction Safety
Redis AOF + Volume
Container Restart
Health-based Startup Dependency
~~~

不能直接表述为：

~~~text
Database High Availability
Redis High Availability
Multi-node Failover
Zero Downtime Architecture
~~~

这些属于后续部署规模扩大后的演进方向。

## 2. 请求接收可靠性在写库之前完成校验、去重和过载保护

### 【采集链路先阻止不合法数据进入持久化边界】

核心源码：

- [ingestion.service.ts](../platform/apps/api/src/ingestion/ingestion.service.ts)
- [rate-limiter.service.ts](../platform/apps/api/src/ingestion/rate-limiter.service.ts)

当前 Ingestion Service 的顺序可以概括为：

~~~text
Decode Body
   ↓
Protocol Version
   ↓
Batch Schema
   ↓
Resolve Project
   ↓
Origin
   ↓
Rate Limit
   ↓
Event Schema / app.name / occurredAt
   ↓
In-request Dedup
   ↓
Database Transaction
~~~

这条顺序的可靠性意义是：

> 越靠前发现无效输入，越少让它继续占用数据库连接、Row Lock、Worker 和长期存储。

例如协议版本不兼容、批次结构不正确、项目 Key 无效、Origin 不允许、事件时间越界，都在写 telemetry_events 之前结束。

### 【Redis Token Bucket 把容量预算转成明确的准入结果】

IngestionRateLimiter 使用 Redis Lua Script 原子执行 Token Bucket（令牌桶），同时限制：

~~~text
Project Budget
      +
Project + IP Budget
~~~

只有两个 Bucket 都允许才继续处理。

这不是单纯的“接口防刷”，而是可靠性保护：

~~~text
无限进入
   ↓
Database Connection / Lock / Storage / Worker 全部承压

变成

有限准入
   ↓
超过容量时明确 429
   ↓
保护核心处理链
~~~

当前 Lua Script 把 Bucket 更新放在 Redis 内完成，避免“读 Token → 应用计算 → 再写 Token”之间产生竞争窗口。

### 【采集统计失败被主动隔离在 Durable Commit 之后】

Ingestion Service 有一个非常值得保留的可靠性边界。

数据库事务 COMMIT 以后，服务还会把 accepted / duplicate / rejected 等运行统计写入 Redis：

~~~text
PostgreSQL COMMIT
      ↓
Redis Statistics
~~~

但统计写入最后使用：

~~~text
.exec()
.catch(() => undefined)
~~~

源码注释明确说明：

~~~text
A statistics failure must not turn
a successfully committed ingestion request
into a retryable SDK error.
~~~

这体现出当前项目对失败进行了分级：

~~~text
Core Business Fact
telemetry_events + outbox_tasks
        ↓
必须成功

Operational Statistics
Redis ingestion stats
        ↓
失败可以降级
不能反过来否定已经 COMMIT 的采集结果
~~~

这是“可靠性不是所有步骤都必须同时成功”的典型工程例子。

### 【当前请求依赖还没有形成统一 Timeout / Circuit Breaker 策略】

从当前源码可以确认 Database、Redis 调用以及主要内部依赖存在明确错误传播，但项目还没有建立统一的：

~~~text
Dependency Deadline
Per-call Timeout Policy
Retry Budget
Circuit Breaker
~~~

不能因为 Redis Client 本身有重试能力，就把它等同于完整的依赖可靠性策略。

因此这一点应标记为**当前可靠性缺口**：后续若出现依赖慢调用拖长 API、连接池耗尽或级联超时，再统一设计 Dependency Timeout / Retry / Circuit Breaker，而不是现在假设已经存在。

## 3. 状态与数据可靠性通过事务、幂等和 Outbox 保证已接受事实不处于半提交状态

### 【采集事务同时解决原始事实、重复事件和后台任务产生】

Ingestion Service 获取 PostgreSQL Connection 后执行：

~~~text
BEGIN
   ↓
按 eventId 获取 Transaction Advisory Lock
   ↓
查询 telemetry_events 中已有 eventId
   ↓
过滤 Duplicate
   ↓
INSERT telemetry_events
   ↓
同一 CTE
INSERT outbox_tasks
   ↓
UPDATE ingestion_keys.last_used_at
   ↓
COMMIT
~~~

这里包含三个相邻可靠性问题。

第一，eventId 幂等不能只靠当前 Request 内的 Set，因为两个并发请求仍可能携带相同 eventId。当前实现通过按确定顺序申请 PostgreSQL Transaction Advisory Lock，再检查已有事件，避免并发批次在同一逻辑事件上发生竞争。

第二，telemetry_events 和 outbox_tasks 通过同一个 SQL CTE + 同一事务写入：

~~~text
Raw Event 成功
+
Outbox Task 成功
        ↓
一起 COMMIT
~~~

避免：

~~~text
Raw Event 已经提交
↓
Process Crash
↓
Task 没产生
~~~

也就是 Dual Write Problem。

第三，接口只有在事务 COMMIT 完成后才返回 accepted，所以 202 的基础是 Durable Acceptance，而不是内存中“已经准备处理”。

数据库 Transaction、Concurrency Control、Advisory Lock 与 Outbox 的更细源码证据继续阅读 [服务端数据管理源码学习-2](./服务端数据管理源码学习-2.md)。

### 【Projection 事务把领域结果和 processed_at 绑定成同一状态变化】

Worker 的 EventProcessor：

[processor.ts](../platform/apps/worker/src/processor.ts)

处理每个事件时重新开启独立事务：

~~~text
BEGIN
   ↓
Performance / View / Custom Projection
   ↓
UPDATE telemetry_events.processed_at
   ↓
COMMIT
~~~

如果 Projection 中途失败：

~~~text
ROLLBACK
~~~

这样不会出现：

~~~text
Projection 只写了一半
但 telemetry_events 已经被标成 processed
~~~

这说明数据可靠性不是只有 Ingestion Transaction；**不同业务阶段有各自的 Transaction Boundary。**

### 【重复执行由数据库约束、Advisory Lock 和 Sequence 共同吸收】

当前 Worker 不是 Exactly Once Processing。

Projection COMMIT 与后续 outbox_tasks = completed 属于两个数据库操作阶段，因此存在 Crash Window：

~~~text
Projection COMMIT 成功
        ↓
Worker Crash
        ↓
Outbox 还没有 completed
        ↓
任务之后被重新 Claim
        ↓
Projection 再次执行
~~~

所以当前系统接受 At-least-once 风格的重复处理风险，再由 Consumer 幂等保护结果：

- Custom Signal 使用 Unique Constraint / ON CONFLICT DO NOTHING；
- Performance / View 使用 Advisory Lock 串行化关键状态；
- Performance Revision 结合 sequence 判断新旧修订；
- processed_at 与 Projection 同事务更新。

因此正确表述应该是：

> **当前可靠性目标不是阻止 Task 永远重复，而是让重复处理不会破坏最终业务结果。**

## 4. 后台任务可靠性通过持久任务、Claim、Lease、Retry、Dead Letter 和 Replay 建立完整终态

这一部分是可靠性体系中的 Async Task 子系统，详细实现继续阅读 [异步任务与 Worker 可靠消费体系源码学习](./异步任务与Worker可靠消费体系源码学习.md)。本文只保留它在整个服务端可靠性中的位置。

### 【Outbox Task 让任务生命周期独立于 API Process】

当前 Worker 不消费 API 内存队列，而是消费 PostgreSQL outbox_tasks：

~~~text
API Process
   ↓
COMMIT outbox_tasks
   ↓
API 可以结束 Request / 甚至退出

Worker Process
   ↓
之后继续 Claim
~~~

因此 Process 生命周期与 Task 生命周期分离。

### 【FOR UPDATE SKIP LOCKED 让多个 Worker 安全竞争任务】

核心代码：

[outbox-worker.ts](../platform/apps/worker/src/outbox-worker.ts)

Claim 条件：

~~~text
pending
AND available_at <= now()

OR

processing
AND locked_at < now() - 5 minutes
~~~

候选 Row 使用：

~~~text
FOR UPDATE SKIP LOCKED
~~~

然后原子更新：

~~~text
status = processing
locked_at = now()
locked_by = workerId
attempts = attempts + 1
~~~

这形成：

~~~text
发现任务
   ↓
Claim
   ↓
明确当前 Owner
   ↓
Processing
~~~

多个 Worker 竞争时，已经被一个 Worker 锁住的 Row 会被其他 Worker 跳过，不需要中央 Scheduler 决定“谁最空闲”。

### 【Stale Reclaim 让 Worker Crash 后任务重新获得处理机会】

如果 Worker 领取任务后进程退出：

~~~text
status = processing
locked_at = old timestamp
~~~

任务不会永久卡住。

5 分钟以后：

~~~text
processing
+
locked_at < now() - 5 minutes
        ↓
重新进入 Claim Candidate
~~~

这相当于固定 Lease Timeout。

当前优点是实现简单；当前边界是：如果未来单个 Task 可能合法执行超过 5 分钟，就需要考虑 Heartbeat / Lease Renewal，否则长任务可能被误判为 stale。

### 【Retry 把瞬态失败转成受控重新执行】

单 Task 失败时：

~~~text
attempts < 8
   ↓
status = pending
   ↓
available_at = now() + backoff
~~~

当前 Backoff：

~~~text
min(300, 2 ^ attempts)
~~~

即 2 / 4 / 8 / ... / 256 / 300 秒封顶。

它已经避免立即重试，但目前没有 Jitter，也没有按 Error Type 区分：

~~~text
Retryable Error
Non-retryable Error
~~~

因此当前所有 Worker Error 共用统一 Retry Policy。这是后续值得优先优化的地方之一。

### 【Dead Letter 让永久失败拥有明确终态而不是无限循环】

attempts >= 8 后，Worker 开启一个新事务：

~~~text
BEGIN
   ↓
INSERT / UPDATE dead_letter_tasks
   ↓
UPDATE outbox_tasks = failed
   ↓
COMMIT
~~~

“死信记录”和“Outbox Failed”原子提交，避免其中一个成功另一个失败。

项目 Owner 还可以通过 ProjectsService.retryDeadLetter()：

~~~text
DELETE dead_letter_tasks
        +
reset outbox_tasks → pending
        ↓
重新进入 Worker 链
~~~

所以当前任务恢复闭环不是：

~~~text
Retry → 永远 Retry
~~~

而是：

~~~text
Retry
  ↓
Retry Exhausted
  ↓
Dead Letter
  ↓
人工修复 / 判断
  ↓
Manual Replay
~~~

## 5. 依赖与容量可靠性通过关键依赖分级、缓存边界和有限并发控制故障传播

### 【Database 与 Redis 在当前 API Readiness 中都属于关键依赖】

Health Controller：

[health.controller.ts](../platform/apps/api/src/health/health.controller.ts)

区分：

~~~text
GET /health/live
→ Process 存活即可返回 ok

GET /health/ready
→ PostgreSQL SELECT 1
+
Redis PING
→ 两者都成功才 ready
~~~

因此当前架构实际上把：

~~~text
PostgreSQL
Redis
~~~

都视为 API 对外服务的 Readiness Dependency。

这与前面“采集统计 Redis 失败可以降级”并不冲突，因为 Redis 在不同功能中的重要性不同：

~~~text
Redis for ingestion statistics
→ 非核心统计，可 fail-soft

Redis for rate limit / session / analytics
→ 当前代码路径中的关键运行依赖
~~~

可靠性分析不能只按“某个技术重要不重要”判断，而要看：

> **这个依赖在当前业务路径承担什么职责，它失败后是否还能给出正确结果。**

### 【Analytics Cache 通过 Version Key + TTL 控制陈旧数据窗口】

Analytics Service 的缓存模型：

~~~text
analytics:version:<projectId>
        ↓
拼入 Cache Key
        ↓
查询 Redis Cache
        ↓
Miss → Database Query
        ↓
SET EX 15s
~~~

Worker 完成 Projection 后递增 version，使旧 Key 自然失效；即使 Version Invalidation 没有长期保留，Cache Entry 也只有 15 秒 TTL。

这属于：

~~~text
Versioned Invalidation
+
Short TTL
~~~

两层保护。

但是当前 OutboxWorker.handle() 把：

~~~text
Projection
↓
Outbox completed
↓
Redis version incr
~~~

放在同一个 try 中。

因此存在一个值得继续评估的边界：

~~~text
Projection 已成功
Outbox 也已 completed
但是 Redis incr 失败
        ↓
进入 fail()
        ↓
Task 可能重新执行
~~~

由于 Cache 本身只有 15 秒 TTL，未来可以讨论：**Cache Invalidation 是否真的应该属于 Task Success Boundary**。这是演进建议，不是当前已修改行为。

### 【Redis 自身当前具备 AOF 与 Volume，但仍是单实例】

docker-compose.yml 中 Redis 使用：

~~~text
redis-server --appendonly yes
+
Volume /data
+
healthcheck
+
restart: unless-stopped
~~~

这些机制提高单实例重启后的数据恢复能力，但当前没有 Sentinel / Cluster / Replica。

完整 Redis 项目分析继续阅读 [Redis 体系源码学习](./Redis体系源码学习.md)。

### 【Worker 用 Batch Size 和固定并发限制单进程压力】

Worker 主循环：

~~~text
Claim 最多 WORKER_BATCH_SIZE
默认 100
        ↓
每 10 条切一组
        ↓
Promise.all
        ↓
下一组
~~~

而 Config Schema 还限制：

~~~text
WORKER_BATCH_SIZE <= 1000
~~~

这说明当前并没有“拿到多少任务就全部并发执行”。

有限并发主要保护：

~~~text
Database Connection
Row / Advisory Lock
CPU
Redis
~~~

但它仍然不能保证系统永不积压。

只要：

~~~text
Arrival Rate > Processing Rate
~~~

pending 就会持续增长。

所以 Queue 是缓冲层，不是无限容量。

## 6. 运行与部署可靠性通过配置校验、启动依赖、健康检查、重启和优雅关闭恢复服务实例

### 【Config Schema 在进程启动阶段 Fail Fast】

[config.ts](../platform/packages/shared/src/config.ts) 使用 Zod 验证：

~~~text
DATABASE_URL
REDIS_URL
Secret Length
Encryption Key Length
Port
Worker Poll Interval
Worker Batch Size
...
~~~

无效配置会在 Application 启动时直接失败，而不是让程序带着错误配置继续运行到业务请求阶段。

这是典型的：

~~~text
Bad Configuration
      ↓
Fail Fast at Startup
~~~

比运行一段时间以后随机报错更容易定位和恢复。

### 【Compose 用健康状态和一次性 Migration 建立启动顺序】

[docker-compose.yml](../platform/infra/docker-compose.yml) 当前关系：

~~~text
TimescaleDB healthy
      ↓
Migration completed successfully
      ↓
API / Worker 可以启动

Redis healthy
      ↓
API / Worker 可以启动

API ready
      ↓
Web 可以启动
~~~

Migration 使用：

~~~text
restart: no
~~~

属于一次性任务。

API / Worker / Database / Redis 等长期服务使用：

~~~text
restart: unless-stopped
~~~

这说明当前部署把：

~~~text
Initialization Job
≠
Long-running Service
~~~

分开处理。

### 【Liveness 与 Readiness 没有混成同一个状态】

当前 API：

~~~text
/health/live
→ 只证明 Process 能响应

/health/ready
→ Database + Redis 均可用
~~~

Compose 的 API healthcheck 访问 ready，因此下游 Web 依赖的不是单纯“容器已启动”，而是“API 已能使用关键依赖”。

这是当前项目运行可靠性中一个明确且正确的边界。

### 【Worker Graceful Shutdown 尽量把正在处理的 Batch 收束到稳定状态】

Worker main.ts：

[main.ts](../platform/apps/worker/src/main.ts)

接收：

~~~text
SIGINT / SIGTERM
~~~

以后：

~~~text
worker.stop()
↓
停止继续主循环
↓
clearInterval
↓
await runPromise
↓
让当前已 Claim Batch 尽量完成
↓
database.close()
redis.quit()
~~~

这可以降低部署时主动制造 Stale Task 的概率。

如果进程不是正常退出而是直接 Crash，前面的 Stale Reclaim 则负责兜底。

所以两层机制关系是：

~~~text
Normal Shutdown
→ Graceful Drain

Unexpected Crash
→ Lease Timeout + Reclaim
~~~

### 【当前 Worker 缺少独立业务 Health / Heartbeat】

Compose 为 API、Database、Redis 配置了 Health Check，但 Worker 当前只有：

~~~text
restart: unless-stopped
~~~

没有独立 Worker Health Endpoint / Heartbeat。

因此 Worker 是否“业务健康”，当前主要通过：

~~~text
Container Process
+
pending / processing
+
processedLastMinute
+
failed / deadLetters
~~~

间接判断。

如果以后进入 Kubernetes、多 Worker Replica 或自动扩容，增加 Worker Heartbeat / Active Worker Metric 会更容易区分：

~~~text
没有任务
≠
Worker 不工作
≠
Worker 卡死
~~~

## 7. 可观测性与容量验证证明数据链路可靠而不是只证明 API 进程存活

### 【Service Status 已经把接收问题和加工问题分开】

AnalyticsService.serviceStatus() 汇总：

~~~text
pending
processing
failed
processedLastMinute
acceptedLastMinute
deadLetters
accepted
duplicate
rejected
recentDeadLetters
~~~

因此可以按数据流排障：

~~~text
acceptedLastMinute = 0
↓
先查 SDK / Key / Origin / Rate Limit / Ingestion

accepted 正常增长
但 pending 持续增长
↓
查 Worker Throughput / Database

failed / deadLetters 增长
↓
查 Projection / Dependency / Bad Task

Worker 正常
但 Dashboard 结果不更新
↓
查 Analytics / Redis Cache / Query Filter
~~~

这比只看：

~~~text
API Process = running
~~~

更接近真正的业务可靠性。

### 【Prometheus 当前已经覆盖接收和 Queue State】

MetricsService 当前暴露：

~~~text
browser_monitor_ingestion_events_total
browser_monitor_ingestion_duration_seconds
browser_monitor_outbox_tasks{status}
browser_monitor_dead_letter_tasks
~~~

它们已经能回答：

~~~text
采集有没有成功
采集延迟是否变高
Queue 是否积压
Dead Letter 是否增长
~~~

但是还缺少直接衡量任务等待和恢复速度的关键指标：

~~~text
oldest_pending_age
queue_wait_duration
processing_duration
retry_rate
attempts_distribution
stale_reclaim_count
active_worker_count
~~~

因此当前更准确的评价是：

> **已经具备 Queue State Visibility，但还没有形成完整的 Worker SLO / Queue Lag Observability。**

### 【Queue Age 比单独 pending Count 更接近用户实际等待时间】

例如：

~~~text
Case A
pending = 10000
oldest = 2s

Case B
pending = 300
oldest = 20min
~~~

单看 Queue Depth 会认为 A 更严重，但如果业务目标要求分钟级可见，B 已经明显违反可靠性目标。

所以后续指标优先级建议是：

~~~text
P0
oldest_pending_age
queue_wait_duration
processing_duration

P1
retry_rate
stale_reclaim_count
attempts_distribution

P2
active_worker_count
per-worker throughput
~~~

### 【可靠性验收应沿端到端数量和状态做 Reconciliation】

项目已有 k6 ingestion 压测能力。可靠性验收不能只看：

~~~text
HTTP Request Success
~~~

更完整的核对链应该是：

~~~text
SDK Sent
   ↓
API accepted / duplicate / rejected
   ↓
telemetry_events
   ↓
outbox_tasks
   ↓
Worker completed / failed
   ↓
Projection Samples
   ↓
Analytics Result
~~~

一次容量或故障测试结束后，需要比较这些阶段之间的数量和终态，而不是仅证明入口没有 5xx。

这也是监控平台自身最重要的“监控自己”。

## 8. 当前可靠性边界应按风险优先级继续演进而不是一次性增加所有组件

### 【当前已经形成一套完整但仍偏单节点的可靠性闭环】

当前已经实现：

| 可靠性问题 | 当前实现 |
| --- | --- |
| 非法输入 | Protocol / Schema / Origin / Event Validation |
| 重复采集 | Request 内 Set + Advisory Lock + Existing Event Check |
| 过量流量 | Redis Token Bucket |
| 原始数据与任务双写 | PostgreSQL Transaction + Outbox |
| Worker 并发 Claim | FOR UPDATE SKIP LOCKED |
| Worker Crash | 5 分钟 Stale Reclaim |
| 重复消费 | Unique / ON CONFLICT / Advisory Lock / sequence |
| 瞬态执行失败 | Retry + Exponential Backoff |
| 永久失败 | Dead Letter |
| 人工恢复 | Dead Letter Manual Replay |
| 进程退出 | Docker Restart |
| 正常停止 | SIGINT / SIGTERM Graceful Shutdown |
| API 业务可用性 | live / ready |
| Queue 运行状态 | Service Status + Prometheus Gauge |
| Redis 数据恢复基础 | AOF + Volume |

这张表比“用了 PostgreSQL、Redis、Docker”更能说明项目可靠性，因为每一个机制都对应一个明确失败模型。

### 【后续演进优先补可靠性证据和恢复边界，再考虑基础设施复杂化】

根据当前实现，建议按以下顺序推进。

| 优先级 | 当前边界 | 建议 | 原因 |
| --- | --- | --- | --- |
| P0 | Queue 主要看 Count | 增加 Oldest Pending Age、Wait / Processing Duration、Retry Rate | 先能够证明任务是否按目标完成 |
| P0 | 所有 Worker Error 共用 Retry | 区分 Retryable / Non-retryable | 永久错误不应等待 8 次后才终止 |
| P0 | Backoff 无 Jitter | 增加 Jitter | 降低同源故障后的同步重试 |
| P1 | 固定 5 分钟 Lease | 长任务出现后再增加 Heartbeat / Renewal | 防止合法长任务被错误 Reclaim |
| P1 | Worker 无独立 Health | 增加 Heartbeat / Worker Runtime Metric | 支持多实例、自动扩容和故障定位 |
| P1 | 依赖无统一 Deadline | 为外部依赖建立 Timeout / Retry Budget | 防止慢依赖占用资源 |
| P1 | Cache Invalidation 属于 Task try | 重新评估 Redis Version Failure 是否应让已完成 Projection Retry | 明确 Core Result 与 Cache Freshness 边界 |
| P2 | PostgreSQL / Redis 单实例 | 真实生产 SLA 需要时再引入 Replica / Sentinel / Managed HA | 不在尚无容量与可用性需求时提前复杂化 |

这里最重要的取舍是：

> **可靠性升级不等于不断增加中间件。先把失败边界、恢复语义和指标补完整，只有当前单实例或 Database-backed Queue 成为真实瓶颈时，才值得引入更重的 HA、Broker 或多节点架构。**

### 【当前 Database-backed Outbox 不需要因为“可靠性”自动升级成 Kafka】

现在主要是：

~~~text
Telemetry Event
   ↓
一次 Projection Task
   ↓
Worker
~~~

PostgreSQL 已同时提供：

~~~text
Transaction
Durable Task
Row Lock
Retry State
Dead Letter State
~~~

因此它与当前问题匹配。

只有需求真正演进到：

~~~text
大量独立 Consumer Group
Event Retention / Replay
Partition-level Scaling
高吞吐 Streaming
Database Queue 成为热点
~~~

才需要重新评估 Kafka / RabbitMQ / SQS 等基础设施。

这属于容量与消费模型演进，不是“可靠性越高越应该用 Kafka”。

## 10. 面试与答辩应该沿失败链连续追问而不是背机制名称

### 【核心回答先说明项目可靠性不是某一个组件提供的】

可以先回答：

> Browser Monitor 的服务端可靠性是按数据生命周期分层建立的：入口先通过校验、幂等和限流保护系统；接受数据时用 PostgreSQL Transaction 把 Raw Event 和 Outbox Task 原子提交；后台通过 Claim、Lease、幂等 Projection、Retry、Dead Letter 保证任务最终进入明确状态；运行层再用 Health、Restart 和 Graceful Shutdown 恢复进程；最后通过 Service Status 和 Prometheus 判断有没有积压、失败和静默丢失。它不是 Exactly Once，也还不是多副本高可用架构，当前重点是单集群内的数据正确和故障恢复。

然后继续追问：

**1. 为什么 HTTP 202 不能表示处理完成？**

因为 202 只发生在 telemetry_events + outbox_tasks COMMIT 以后，Worker Projection 仍是后续独立生命周期。

**2. 为什么 Raw Event 和 Outbox Task 必须一起写？**

为了避免 Raw Event 已提交而 Process 在创建 Task 前 Crash 的 Dual Write Window。

**3. Worker Crash 怎么恢复？**

processing Task 的 locked_at 超过 5 分钟会被重新 Claim；正常部署则优先通过 Graceful Shutdown 把当前 Batch 处理完。

**4. 这样是不是 Exactly Once？**

不是。Projection COMMIT 与 Outbox completed 之间存在 Crash Window，所以允许重复处理；靠 Consumer Idempotency 保护结果。

**5. Redis 挂了以后哪些功能受影响？**

当前 /health/ready 同时检查 Redis 与 Database，因此 API 会被视为 not ready；Rate Limit、Session、Analytics Cache 等路径依赖 Redis。但 Ingestion 在 PostgreSQL 已 COMMIT 后写 Redis 统计失败会被吞掉，不会把已经成功接收的数据重新变成 SDK 可重试错误。

**6. 为什么 Retry 不能无限做？**

因为永久错误不会因为次数增加而恢复，而且 Retry 会持续消耗 Database / CPU / Queue 资源；当前 8 次后进入 Dead Letter。

**7. 现在最大的可靠性短板是什么？**

优先不是“没有 Kafka”，而是 Queue Lag / Processing Duration / Retry Rate 等可靠性证据还不完整，Worker Error 还没有 Retryable 分类和 Jitter，Worker 也没有独立 Heartbeat。

**8. 什么时候才需要进一步做高可用？**

当生产 SLA、故障历史或容量证明单 PostgreSQL / Redis / API / Worker 已经成为不可接受的单点时，再引入 Replica、Managed HA、多实例和自动 Failover。
