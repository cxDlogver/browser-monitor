## 1. 先弄清：这个项目"后半段"在解决什么问题

整个监控系统被拆成三段，平台只负责**后两段**：

```text
① 业务页面（SDK）      —— 在浏览器里"采集事实"，生成协议事件
② 平台接入层（API）    —— 在服务端"可靠接收"，原文落库
③ 平台加工层（Worker）—— 在服务端"可靠计算"，投影指标
④ 平台查询层（API）    —— 对外"可查询"
⑤ 可视化（Web）        —— 给人看
```

平台要同时交付 **4 类能力**（记住这 4 条，"为什么有这些代码"就都有答案了）：

1. **身份与权限**：账号注册/验证/登录、项目、成员角色（owner / member）、Origin 白名单、写入键。
2. **可靠接收与留存**：接收批次、校验、脱敏、幂等、原始留存。
3. **异步加工与聚合**：投影明细、计算服务端评级、时间聚合。
4. **查询与运营**：看板查询、服务状态、失败任务恢复。

### 关键设计取舍：为什么 API 和 Worker 要拆成两个进程

这是全项目最重要的一个架构决策，先记住结论，第 06 篇（异步任务与 Worker）会展开：

> **API 只需回答"这批数据平台收不收"，必须快且确定；
> 投影和聚合要访问更多表、可能因单条脏数据失败，绝不能拖慢采集。**

所以 API 只在一个数据库事务里写"原始事件 + 待处理任务（Outbox）"，真正的计算交给独立的 Worker。这也解释了两条硬规则：

- 接口返回成功 ≠ 指标已经算好（中间有异步延迟）；
- Worker 崩了不影响采集，但会积压任务（需要"服务状态"页去看）。

## 2. 一张图看懂后端：四层结构

后端（服务端）本质只有四层，看任何后端项目都用这个框架去套：

```text
┌──────────────────────────────────────────────────────────┐
│ ① 接入层  HTTP 服务：接收请求、鉴权、校验、限流、返回响应      │
│           = api（NestJS + Fastify）                       │
├──────────────────────────────────────────────────────────┤
│ ② 业务层  业务规则：项目、成员、阈值、审计、指标口径          │
│           = api/src/{projects,auth,lab-audits}            │
│             packages/shared（配置、加密、脱敏、阈值）        │
├──────────────────────────────────────────────────────────┤
│ ③ 数据层  持久化与计算：PostgreSQL/TimescaleDB + Redis       │
│           = packages/database（Drizzle 模型 + SQL 迁移）    │
├──────────────────────────────────────────────────────────┤
│ ④ 加工层  异步任务：消费、投影、聚合、重试、死信              │
│           = worker（独立进程）                             │
└──────────────────────────────────────────────────────────┘
```

再叠加"运行环境"这一层：Docker Compose 把上面的东西和它的外部依赖（数据库、Redis、邮件、反向代理）编排到一起跑。

对应到 SDK 视角，完整链路是：

```text
Monitor SDK
  → 公开 DSN（写入键）
  → Ingestion API（接入层）
  → telemetry_events + outbox_tasks（数据层，同事务）
  → Worker（加工层，异步）
  → TimescaleDB 聚合（数据层）
  → Analytics API（接入层，查询）
  → React 看板（可视化）
```

## 3. 平台由"五个进程 + 一批共享包"构成

新手最需要先破除的误解：**一个后端项目不等于一个进程。** Platform 是一个 pnpm workspace（多包仓库），同时产出多个可独立部署的运行单元。

| 单元 | 包名 / 位置 | 技术 | 职责 | 启动入口 |
| --- | --- | --- | --- | --- |
| **API** | `@browser-monitor/api` / `apps/api` | NestJS + Fastify | HTTP 接口：采集、认证、项目管理、分析查询、实验室任务 | `apps/api/src/main.ts` |
| **Worker** | `@browser-monitor/worker` / `apps/worker` | 纯 Node.js | 消费 Outbox，投影明细、算评级、聚合 | `apps/worker/src/main.ts` |
| **Audit Worker** | `@browser-monitor/audit-worker` / `apps/audit-worker` | Node.js + Chrome + Lighthouse | 独立跑主动实验室测试（不碰 RUM 数据） | `apps/audit-worker/src/main.ts` |
| **Web** | `@browser-monitor/web` / `apps/web` | React + Vite + Ant Design + ECharts | 管理后台与看板 | `apps/web/src/main.tsx` |
| **Migrate** | `@browser-monitor/database` | Node.js 脚本 | 建表、Hypertable、连续聚合、保留策略 | `packages/database/src/migrate.ts` |
| 共享包 | `@browser-monitor/{shared,database,protocol}` | TypeScript | 被上面多个单元复用 | — |

两个值得注意的对比：

- **API 用框架，Worker 不用框架。** API 要处理路由、鉴权、校验、依赖注入，框架能省事；Worker 只是"取任务 → 处理 → 写回"的死循环，用裸 Node 更直接。
- **Worker 和 Audit Worker 必须是两个进程。** 前者是数据管道的核心，必须稳定、轻量；后者要跑 Chrome，吃内存、可能崩，还带安全风险（`read_only: true`、`cap_drop: ALL`）。

### 依赖方向（为什么要拆包，而不是全写在一起）

```text
        protocol（协议契约）
        ↓        ↓        ↓
      SDK      API     Worker
                 ↑
        database + shared
```

- **`protocol` 是唯一的数据契约来源**：SDK、API、Worker 共用同一套 Schema，避免"端上发 A 字段、服务端读 B 字段"。
- **`shared` 放跨单元的业务能力**：环境变量校验、ID 散列、敏感信息脱敏、阈值计算。
- **`database` 放模型与迁移**：API 需要写、Worker 需要读写、迁移脚本需要建表，三处共用一份定义。
- 反过来，**SDK 不依赖 Platform 的实现代码，Protocol 不依赖任何人**——单向依赖，才不会牵一发动全身。

## 5. 一次上报的完整旅程（端到端）

这一节是全篇最重要的一段，建议对照代码读一遍。它把第 2 节的"四层"串成一条时间线。

### ① 请求进来：一个地址、一个批次

- **整批失败**：身份、协议版本、Origin 错 → 直接抛 `4xx`，整批不收；
- **单条失败**：某个事件字段非法 → 只丢这一条，把下标和原因放进响应。

一条 SQL 里完成"插入原始事件 **且** 插入待处理任务"，两条写入在同一事务里，于是：

- 不会"接口说成功但没有任何后续任务"；
- 也不会"Worker 拿到任务但原始事件还没提交"。

这就是 **Transactional Outbox（事务性发件箱）**，第 05 篇（采集链路的可靠性设计）会专门讲它解决什么问题。

## 6. 三类入口，三种身份——绝不能混用

后端安全的第一原则是"分清谁在跟谁说话"。Platform 有三类入口：

| 入口 | 谁在用 | 靠什么证明身份 | 代码 |
| --- | --- | --- | --- |
| 公开采集 `/api/v3/ingest/*` | 业务浏览器里的 SDK | **DSN 写入键**（非凭据，配合 Origin 白名单 + 限流） | `ingestion.service.ts` |
| 管理/查询 `/api/v1/*` | 平台登录用户 | **Session Cookie + CSRF + 项目成员关系** | `session.guard.ts`、`csrf.guard.ts` |
| 内部运维 `/internal/*` | 运维/Prometheus | **只允许私网 IP** | `Caddyfile` |

三个细节值得记住：

**① Session 存在于 Redis，Cookie 只带一个随机 token，且库里存的是哈希。**

```28:37:platform/apps/api/src/auth/session.guard.ts
    const request = context.switchToHttp().getRequest<FastifyRequest>();

    if (!session) throw new UnauthorizedException({ code: 'session_expired' });

**② 写操作必须带 CSRF Token，读操作放行。**

```

再补一条贯穿全项目的原则：**分析接口挂在 `/api/v1/projects/:projectId` 之下，每次都要重新校验"当前用户是否属于这个项目"**——绝不允许"登录了就能看别人的项目"。

## 7. 本地把它跑起来（最小可运行路径）

1. 仓库根目录执行 `pnpm install`；
2. 复制 `platform/.env.example` 为 `platform/.env`（生产必须替换密钥）；
3. 启动：

```bash
docker compose --env-file platform/.env --profile dev -f platform/infra/docker-compose.yml up --build
```

启动顺序由 Compose 的 `depends_on` 决定：数据库健康 → 迁移跑完 → API 就绪 → Web 才能起来。**"迁移先于应用"是后端部署的一条铁律**（表结构没建好，应用起来也是报错）。

| 地址 | 内容 |
| --- | --- |
| `http://localhost:8080` | Web + API（经 Caddy） |
| `http://localhost:8025` | Mailpit（开发环境收验证邮件） |
| `http://localhost:5432` | TimescaleDB |
| `http://localhost:6379` | Redis |

接入顺序：注册 → 验证邮箱 → 创建项目 → 填 Origin 白名单 → 复制 DSN → 传进 SDK 的 `transport.dsn`。
注意 `app.name` 必须与建项目时填的应用标识**完全一致**（`ingestion.service.ts` 会逐条校验）。
