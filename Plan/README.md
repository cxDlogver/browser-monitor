## 文档职责与编写规范

需求文档说明要解决什么问题、为什么需要功能、使用者如何操作、应获得什么结果，以及哪些边界不能隐藏。每个功能需要完整展开，不用简短表格替代行为说明；需求文档不承载接口字段和代码实现细节。

技术文档说明如何实现需求，包括模块职责、数据与接口契约、命令参数、状态规则、错误、可靠性与验证。每个需求功能都需要同编号的设计方案，不能只提供通用架构和规范。表格用于字段或代码映射，配合解释和示例，不代替方案论证。

需求流程图使用 Mermaid，按人 / AI、CLI、监控平台 / 数据库划分参与方。图与文字应表达同一逻辑，正常路径、重要分支和结束结果都要可核对。

实施计划说明阶段、依赖、交付物及检查方式。未实现的能力应写成目标契约，不作为已存在能力描述。

验收计划按 AC 编号独立记录，每条结果核对点都需要预期、实际观察、判定和具体证据。计划中的待执行状态不能当作验收完成；勾选通过前必须补齐观察与产物。执行证据按批次和用例保存在 Plan/验收记录，并记录版本、数据时刻和来源。

所有文档应独立可读，不把当前源码、内部文件路径、调研记录或聊天过程作为读者理解的前提。需求改变时同步更新相关技术契约。

## 业务事件接入与验收规范

接入说明必须把业务动作与监控事件对应起来：说明触发条件、名称与类型、路由、必要属性或指标、结束/上报时机和可用关联身份。页面技术信号按 SDK 的采集规则说明；自定义业务含义由业务埋点明确定义。读者应能据此知道做什么操作、预计看到哪类记录，以及何时开始查询。

CLI 正常链路优先使用已有真实业务事件。探针是可选的受控辅助输入，不要求业务项目新增探针才能接入、查询或完成 CLI 验收。只验证探针不能代表 CLI 已能够读取已定义的真实业务事件。异常与边界可以使用控制夹具，但必须标明来源和基准。

证据按“业务动作与预期定义 → 实际采集身份 → 数据库记录 → CLI 观察”关联。测试 runId 只标识产物批次，普通业务事件不强制包含该属性。查询按项目、事件名称/类型、环境、版本、路由、时间和实际会话/视图等身份定位；多个候选必须补充关联依据，不能按名称猜选。

验收只核对 CLI 功能及其返回事实。业务页面用于产生输入，页面内容、地图功能与业务算法精度不增加为 CLI 验收项；业务事件应有的字段、单位、身份和上报时机仍需要说明并核对。发送、入库与处理完成分别取证，证据不足保持未知，输入无法准备记录阻塞。

需求、技术设计、实施、验收和固定输入变更时必须同步上述规则。保留全部 47 个 AC 编号与 94 条结果核对点，每项分别记录预期、观察、判定和具体证据。本轮基线为需求 1.3、技术设计 1.2、实施计划 1.2、验收计划 1.2、固定输入 schemaVersion=2；执行记录引用实际基线版本。
