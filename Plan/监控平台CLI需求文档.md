# 监控平台 CLI 需求文档

文档版本：1.3。编写日期：2026-10-13。状态：需求详细稿。

本文说明产品要解决的问题，以及每个功能的业务逻辑、参与对象、操作流程、结果和异常。配套的[技术设计文档](监控平台CLI技术设计文档.md)按相同的 FR 编号给出实现方案。

## 1. 需求概述

这套 CLI 的核心目标是：让人和 AI 在需要时取得监控平台中已经写入数据库的数据，并通过明确的操作完成平台管理和读写。使用者不必依次打开 Web 页面、寻找按钮、复制配置和切换项目，也能在终端、AI 工具调用或自动化脚本中完成接入与排障。

完整使用过程是：连接本地平台并登录，创建或选择项目，设置业务页面来源，导出 SDK 接入配置与示例；业务代码接入并产生事件后，再查询实际入库记录、当前数据数量、任务积压和指定事件的处理阶段。已有项目可以直接进入查询与诊断，不需要重新创建。

这里有三组需要贯穿所有功能的对象。第一组是平台、账号和项目：平台地址确定访问哪个服务，账号决定操作权限，项目 ID 确定数据范围。项目显示名称用于识别，应用标识用于 SDK 接入，两者不能代替明确的项目身份。第二组是接入配置：采集地址 DSN 用于 SDK 写入，业务 Origin 表示允许上报页面的协议、主机和端口，环境和版本来自真实业务参数。管理登录身份与 SDK 写入身份必须分开。第三组是事件和任务：原始记录表示数据库当前保留的接收数据，领域记录表示后续加工结果，异步任务表示处理工作。它们可能处于不同阶段，也可能具有不同保留期限。

首版的管理写操作包括创建项目和更新业务来源；监控事件由业务 SDK 正常上报写入。读取包括项目与接入信息、原始事件、当前原始数据概况、任务状态及单事件诊断。成功写入必须有平台确认和可回查对象；读取必须说明项目、范围、查询时刻和证据限制。任意 SQL、覆盖历史事件或批量删除需要另外定义需求。

“及时获取”要求每次调用取得本次查询结果，并说明它对应的数据时刻。它不要求异步处理瞬间结束，也不把缓存时刻、客户端发起时间和数据库快照时间混为一谈。记录缺失可能表示尚未出现、已清理或已删除，证据不足时应返回未知；查询失败则表示没有取得有效结果，两者必须区分。

接入者应说明业务动作与监控事件的对应关系：由哪个动作触发、采用什么事件名称与类型、携带哪些业务信息，以及何时上报。页面等技术信号可以由 SDK 按采集规则自动产生，业务语义明确的埋点由业务代码定义。CLI 提供查询和诊断事实，人和 AI 据此核对实际记录是否符合这份定义；不需要先添加测试探针才能识别业务数据。

人、AI 和脚本使用同一套已实现功能及平台权限。人需要易读的结果；AI 和脚本需要稳定、可解析的结果，能够区分成功、空数据、后续分页、写入未知和部分成功。首版在本地运行，使用已有账号会话，在仓库内提供独立 CLI 包。

以下流程图按参与方划分区域：**人 / AI** 表示发起操作和使用结果，**CLI** 表示参数、流程和本地文件处理，**监控平台 / 数据库** 表示权限校验、业务写入与数据读取。图中的分支表示不同操作或判断结果；文字同时说明图中省略的边界情况。

## 2. 功能需求

每个功能保留固定编号。阅读时可以先看目标与业务规则，再沿编号步骤和流程图理解操作，最后检查结果及异常；技术文档中可以按同一编号查找设计方案。

### 2.1 FR-01：选择平台并管理项目上下文

**功能目标。** 使用者在每次操作时都能知道正在访问哪个监控平台、哪个项目。多人、多个业务应用或多个本地平台同时存在时，工具不能依靠猜测选择目标。

**涉及对象与前置条件。** 参与对象包括调用者、平台地址、业务目录中的项目上下文和平台项目权限。所有后续命令都使用本功能解析的目标；账号操作、健康检查、项目列表和项目创建不要求默认项目，操作已有项目时需要明确项目 ID。

**业务逻辑。**

使用者可以显式指定平台地址，也可以把平台地址和默认项目关联到业务工作目录。进入该目录后，人和 AI 可以使用同一份项目上下文继续操作。首版默认连接本地平台，平台地址仍可明确覆盖。

保存上下文时，工具应验证项目是否可访问。业务目录只保存非敏感的连接与项目信息，不保存密码或管理会话。工具的结果应表明实际使用的平台与项目，使调用者能够检查是否选错。

当调用者显式切换到另一个平台时，原平台保存的默认项目不能自动跟过去。缺少项目或项目不可访问时，应要求补足明确身份，不能因某个平台恰好只返回一个项目就自动选择。

**操作流程。**

1. 调用者显式指定平台和项目，或者在已经保存上下文的业务目录中运行命令。需要更换上下文目录时，应明确指定。

2. CLI 先确定实际平台，再确定该平台下的项目。显式参数可以覆盖默认值；切换平台后不能继承原平台项目。

3. 当前命令需要项目但没有明确身份时，流程结束并提示补足项目；不能自动挑选列表中的唯一项目或同名项目。

4. 需要保存默认项目时，平台先检查当前身份能否访问该项目。检查成功后，CLI 只把平台地址和项目 ID 写入业务目录。

5. 后续结果携带实际目标。调用者可以核对目标并继续创建、配置或查询流程。

### 2.2 FR-02：登录、检查身份与退出

**功能目标。** 使用者能够建立并复用平台管理身份，知道当前会话是否有效，并在需要时退出。数据访问和写操作应当始终受平台授权约束。

**涉及对象与前置条件。** 参与对象包括已有账号、CLI 会话存储和平台认证服务。账号注册与验证在首版中由 Web 完成；CLI 不持久保存密码。

**业务逻辑。**

首版使用已经注册并完成验证的账号登录。人可以在交互终端中提供密码；自动化调用可以通过受控输入提供凭据。登录成功后，工具保存会话，后续命令可以复用，不要求每次重新输入密码。

身份检查应展示当前账号、访问的平台及会话是否有效。平台提供明确到期时间时可以展示；无法确定时应如实说明，不能根据一个固定时长猜测会话还剩多久。

会话过期时，工具需要明确提示重新登录。普通非交互调用不能转入登录提示并等待人工输入。退出应说明本地身份是否清除、平台是否确认会话已撤销；远端没有确认时不能仅凭本地删除就宣称彻底退出。

**操作流程。**

1. 调用者选择登录、检查身份或退出。登录时提供已有账号；人可以隐藏输入密码，非交互调用必须提供受控凭据输入。

2. CLI 向指定平台提交登录信息。平台验证成功后建立会话，CLI 按平台分别保存必要管理凭据，返回当前账号与可知的有效期。

3. 后续命令复用该会话。身份检查需要向平台核实有效性，而不是只看本地是否存在一个文件。

4. 平台确认会话过期时，工具返回明确的登录失效结果。普通查询不自动进入密码提示，AI 或脚本可以据此停止或另行登录。

5. 退出时，CLI 尝试让平台撤销会话，并清除本地使用记录。结果分别说明本地清除和远端撤销是否得到确认。

### 2.3 FR-03：查询、创建并选择项目

**功能目标。** 使用者能够通过 CLI 管理接入所需要的项目身份，完成项目从创建到后续回查的过程。

**涉及对象与前置条件。** 参与对象包括平台账号、项目记录和项目接入信息。项目列表、详情、创建和选择是同一功能中的四种操作；项目选择结果由 FR-01 保存。

**业务逻辑。**

查询项目列表时，工具应提供可访问项目的身份、名称、应用标识、启用状态及账号角色。使用者能够根据这些信息选择项目，但最终选择应保存明确项目 ID，而不是模糊名称。

查询项目详情时，应获得项目接入所需的配置，包括业务来源、写入键及采集地址等。工具应让调用者确认这些信息所属的项目，并区分项目管理身份与 SDK 写入身份。

创建项目时，调用者提供显示名称和应用标识。平台完成写入后，工具返回新项目 ID、最终保存的名称与标识以及可继续取得的接入信息。随后可以回查项目详情，也可以把该项目设置为业务目录默认项目。

如果平台允许重复的名称或应用标识，工具不能将它们视为可靠的唯一键。创建请求失去响应时，项目可能已经写入数据库。工具必须将结果说明为无法确定，并给出核查已有项目的方向，不自动重复创建。

**操作流程。**

1. 调用者先查看可访问项目列表，或直接提供已知项目 ID 查询详情。列表用于识别，详情用于核对项目状态和接入信息。

2. 需要新项目时，调用者提供显示名称和应用标识。CLI 校验输入，再提交给平台创建。

3. 平台验证身份、保存项目及必要接入对象，返回明确项目 ID 和最终保存值。CLI 以这个确认作为创建结果。

4. 调用者使用返回 ID 回查项目，或将其设为业务目录默认项目，继续来源设置和配置导出。创建本身不悄悄替换已有目录上下文。

5. 如果创建响应丢失，工具说明结果未知。调用者核查可访问项目或已取得的对象身份，工具不自动再次创建。

### 2.4 FR-04：查看并设置业务来源

**功能目标。** 让项目允许实际业务页面上报，并让人和 AI 能够通过 CLI 查看和更新这项平台配置。

**涉及对象与前置条件。** 参与对象包括目标项目、项目管理员和允许的业务来源集合。查看来源属于读取；设置来源会整体改变平台保存的配置。

**业务逻辑。**

使用者首先应能读取项目当前允许的业务来源，判断其中是否包含业务实际运行的协议、主机和端口。监控平台地址和业务页面地址不能被自动当作同一个来源。

设置来源时，使用者提供完整的允许集合。工具应明确这是整体替换，并返回平台实际保存的归一化集合。重复来源可以合并，但不能在调用者不知道的情况下保留或添加另一批来源。

该操作会修改平台保存的配置，需要管理员权限。权限不足时应说明操作未获授权；参数不合法时应说明哪项来源需要修正。请求结果未知时，应提示回查实际保存集合，不能用本地输入代替服务端结果。

**操作流程。**

1. 调用者读取项目当前来源，并确认业务页面实际运行的协议、主机和端口。

2. 调用者准备完整允许集合。设置操作表示整体替换，不能把一个新增来源误当成在旧集合上追加。

3. CLI 校验并归一化来源，向平台提交完整集合。平台校验项目管理员权限，再原子保存。

4. CLI 返回平台确认保存的集合。调用者可以再次读取来源核对，并用对应页面继续 SDK 上报。

5. 若权限不足或来源不合法，返回明确失败；响应丢失时，返回未知并提示读取实际集合。

### 2.5 FR-05：导出 SDK 配置 JSON 与接入示例

**功能目标。** 创建或选择项目后，使用者能得到业务代码可以读取的接入产物，并清楚知道怎样使用它。

**涉及对象与前置条件。** 参与对象包括目标项目、有效写入键、业务环境与版本、SDK JSON 和接入示例。该功能读取平台接入信息并生成文件，不直接修改业务源代码。

**业务逻辑。**

导出配置时，工具从平台取得应用标识和有效采集地址，使用者显式提供应用版本和环境。工具不能用示例版本代替真实版本，也不能把本地开发环境当作所有业务的默认环境。

生成的 JSON 应只包含 SDK 可以读取的配置数据。项目管理信息、成员列表、管理凭据和函数不能混入该文件。导出结果还应说明配置来自哪个项目、使用哪个写入键，以及该键是否存在到期限制。

如果项目被禁用、没有可用写入键或出现多个无法唯一选择的当前写入键，工具需要返回明确结果，并允许调用者显式选择有效键。不能只取列表第一个地址后声称它一定适合接入。

接入示例需要解释如何读取 JSON、初始化监控 SDK、启动采集，以及在业务代码中补充路由解析等函数。示例是独立参考产物，实际业务入口的修改由人或 AI 在业务代码中完成。

已有文件需要保护。工具应允许明确覆盖，但不能默认替换业务目录中已经维护的配置。若 JSON 已写入而示例写入失败，应列出已完成产物，便于调用者补齐。

**操作流程。**

1. 调用者明确项目、业务环境和应用版本，选择输出位置；需要指定写入键或覆盖文件时明确表达。

2. CLI 从平台读取项目启用状态、应用标识及写入键，判断是否存在唯一可用选择。项目禁用、键不可用或选择不唯一时先返回问题。

3. CLI 将平台返回的采集地址与真实业务参数组合成 SDK 配置。函数类选项只在示例中解释，不塞入 JSON。

4. CLI 检查目标路径和覆盖意图，再生成纯 JSON 及独立示例；未指定文件时返回配置内容和接入说明。

5. 人或 AI 按示例在业务代码中加载配置、补充必要函数并启动 SDK。这个步骤由业务接入者执行，随后用 FR-06 至 FR-10 核查数据。

6. 生成过程中若部分文件成功，工具保留并报告成功产物及失败位置，允许继续补齐。

### 2.6 FR-06：检索数据库中的原始事件

**功能目标。** 使用者能够取得平台实际保留的监控事件，回答“哪些数据已经写入”“最近出现了什么”“指定环境或页面有没有对应事件”。

**涉及对象与前置条件。** 参与对象包括指定项目的原始事件、查询条件和分页位置。读取的是平台当前保留记录，结果可以包含摘要或受权限保护的脱敏内容。

**业务逻辑。**

查询应支持时间、事件类型、名称、环境、版本、页面、会话以及事件 ID 等条件。工具需要说明每个条件的作用，例如事件发生时间与接收时间不能在展示中混为同一概念。

普通查询默认聚焦最近一天，并按页返回数据。使用者可以明确改变范围或继续读取下一页。工具需要保留初次查询的时间条件，避免续页时默认时间窗口不断变化，造成重复或遗漏。

核查真实业务接入时，调用者先依据事件定义选择项目、名称、类型、环境、版本、路由和操作时间范围，再利用会话、视图及可用关联身份确认本次动作。名称相同的多条记录可能属于不同访问，不能只凭事件名取第一条，也不能要求所有真实业务事件携带测试批次属性。身份不足时应保留候选并补充依据，不能把猜测作为本次动作已入库的证明。

每条结果应能辨认其事件身份、发生与接收时间、应用环境及相关页面或会话。需要查看事件内容时，应有明确入口获取平台允许查看的脱敏数据，而不是只能看到一行摘要。

没有结果时，应说明本次查询成功但当前范围内没有记录。范围超出平台支持能力或游标不合法时，应明确报错，不静默修改条件或从第一页重来。仅取得一页数据时，不能将它称为全部数据库数据。

**操作流程。**

1. 调用者依据业务事件定义或一般检索目的指定筛选条件；核查一次操作时同时记录该操作及可用关联身份。没有明确时间时，工具以本次查询时间确定最近一天的范围，并说明使用的是事件发生时间。

2. CLI 固定时间和筛选条件，向平台请求一页记录。平台校验项目访问，在当前保留数据中执行查询。

3. CLI 返回事件身份、发生与接收时间、相关业务信息，以及当前范围和是否还有下一页。

4. 调用者需要后续数据时，提交续页位置。CLI 恢复初次查询条件，不能把时间窗口滚动成新的最近一天。

5. 需要核查单条内容时，调用者显式请求内容，或使用事件身份进入 FR-08 诊断。

6. 无记录是有效空结果；非法游标、不支持的范围及服务故障分别返回错误，不能裁剪条件后假装原查询成功。

### 2.7 FR-07：查看原始数据的当前概况

**功能目标。** 使用者无需逐页遍历事件，就能知道项目数据库当前保留了多少原始记录，以及最近是否持续收到新数据。

**涉及对象与前置条件。** 参与对象包括指定项目的全部当前保留原始记录、最近接收时间和保留策略。概况不继承普通列表的最近一天范围。

**业务逻辑。**

数据概况应包含当前保留的原始事件数量、当前记录中的最近接收时间、统计对应时刻和适用的保留策略。统计应基于原始数据记录，不以接收累计统计代替。

例如，平台历史上接收过两千条事件，当前数据库保留一千条，这两个数字并不能直接说明丢失了一千条。保留策略、查询时间和统计来源都可能不同，工具应帮助使用者理解当前数量，而不是替使用者作出错误判断。

新项目没有事件时，结果应为有效的零记录概况，最近接收时间明确为空。工具仍应显示项目与查询时刻，让使用者知道确实查询了目标项目。

**操作流程。**

1. 调用者选择项目并请求数据概况，不需要遍历事件列表。

2. 平台在同一查询时刻统计当前保留原始记录，并读取其中最近接收时间和实际保留策略。

3. CLI 返回数量、最近接收时间、服务端数据时刻和统计来源。

4. 调用者再次执行时取得新结果，可以观察数量和接收活动变化；不能用旧缓存结果代替新查询。

5. 没有记录时返回零与空最近时间；查询失败时返回失败，不能伪造零记录。

### 2.8 FR-08：诊断单条事件的完整处理情况

**功能目标。** 对于具体事件，使用者能够了解平台当前保留的处理证据，找到它处于哪一步，而不是只得到一个“成功”或“失败”。

**涉及对象与前置条件。** 参与对象包括事件身份、当前原始记录、处理提交证据、异步任务和对应领域实体。所有阶段独立展示，不用一个总状态遮住差异。

**业务逻辑。**

调用者提供项目和事件 ID。该查询应覆盖全部当前保留记录，避免较早事件被普通列表的默认时间范围遮挡。若同一事件 ID 对应多个候选，应要求进一步提供发生时间，并说明候选情况。

诊断首先应说明原始记录是否存在，以及平台何时接收它。接着应说明有没有领域处理提交证据，当前异步任务是否存在、处于何种状态、尝试了多少次、何时可继续执行，以及是否记录了失败原因。

对于性能样本、页面访问等领域记录，工具应说明当前是否可以查询对应实体，并解释同一实体可能被多次事件修订。事件被正常去重或旧修订被忽略，也可能属于正常处理，不能因没有新增一行记录就认定处理失败。

各阶段证据可能同时成立而表面上不同。例如，领域处理已经提交，后续任务仍因另一阶段失败而待重试。工具应保留这种情况，而不是为了简化结果把其中一个状态隐藏。

原始事件和完成任务的保留期限可能不同。如果原始事件仍存在且有处理证据，但任务记录已经不在，工具可以说明已完成的领域处理和当前任务证据缺失，不能凭缺失推断任务过去一定成功或失败。

**操作流程。**

1. 调用者提供项目和事件 ID。平台先在全部保留记录中定位事件；出现多个候选时，返回候选并要求补足发生时间。

2. 对于明确事件，平台读取原始记录和处理提交证据，再关联任务、尝试次数、可执行时间、错误及领域实体。

3. CLI 分别解释每阶段当前存在的事实。例如，领域处理已提交，但任务仍待重试，两项事实应同时保留。

4. 领域记录不存在时，结合处理规则解释是否可能正常去重、旧修订或无对应领域产物；没有证据时只返回未知。

5. 历史任务缺失时，返回记录缺失及保留限制，不推断它过去完成。查询结束后，调用者可以进入等待或根据关联身份排障。

### 2.9 FR-09：查看当前任务数量与队列状态

**功能目标。** 回答使用者最直接的问题：当前到底有多少待执行任务，哪些现在能执行，哪些正在等待，哪些已经失败。

**涉及对象与前置条件。** 参与对象包括项目遥测任务、任务执行时间、锁信息、失败任务与死信。其他种类任务或非数据库采集计数需要独立标注。

**业务逻辑。**

工具应同时提供待处理总量和当前已到执行时间的数量。退避重试的任务虽然仍属于待处理，但不能被列为“现在可执行”。例如，待处理一百二十条，其中二十条到期、一百条等待重试时间时，结果应使这种区别清晰可见。

已被领取的任务需要区分锁未超时、锁已超时和缺少有效锁信息。锁尚未超时只能说明当前记录满足锁定条件，不能证明处理进程此刻一定仍在运行。

待处理任务缺少有效计划执行时间时，应单独展示无法分类的数量并说明异常，不能把这类记录算成“现在可执行”或直接漏出总数。

工具还应返回停止自动处理的任务数、死信数量、近期完成情况及最近失败信息。失败任务与死信可能重叠，近期失败列表也可能有数量限制，这些限制必须说明。

队列状态与采集累计计数可以一起用于观察平台，但需要标明来源。普通遥测任务与实验室测试等其他任务不能混成一个没有解释的“待执行总数”。

**操作流程。**

1. 调用者请求指定项目的当前队列状态。

2. 平台用同一数据时刻统计待处理任务，区分已到执行时间、退避等待和计划时间异常；总量保留所有记录。

3. 平台统计正在处理任务，并按锁时限区分锁正常、锁超时及缺少锁信息。

4. 平台同时读取终止处理数量、死信、近期完成和有限的最近失败记录。

5. CLI 返回各类数量及统计口径，说明失败与死信是否重叠、最近失败是否只展示一部分，以及非数据库计数来源。

6. 调用者根据可执行积压、超时锁或失败身份进一步排障；不能仅凭锁未超时或队列为零宣称处理进程健康。

### 2.10 FR-10：在有限时间内等待指定事件处理完成

**功能目标。** 业务刚产生事件时，使用者可以让工具等待其后续处理，得到明确的结束结果，避免反复手工查询。

**涉及对象与前置条件。** 参与对象包括指定事件、FR-08 诊断结果、总等待时限和轮询间隔。等待只编排观察，不执行任务、不触发失败重试。

**业务逻辑。**

等待针对指定项目和事件进行。调用者可以设置总等待时间及轮询间隔，工具应在截止之前定期取得新证据。等待过程需要有界，所有请求、重试与间隔都应计入总时限。

首版的完成条件是：已经取得处理事务提交证据，且对应任务在同一诊断结果中为完成状态。正常去重或旧修订被忽略可以满足处理完成，不要求一定新增领域记录。

如果任务停止自动处理，应立即返回失败情况和已完成阶段。如果历史任务记录不足，应说明不能确认完整条件。如果截止仍未达到条件，应返回超时及最后一次诊断，使用者可以据此决定继续观察还是排查。

连接失败与事件尚未入库必须分开。工具无法取得新查询结果时，不得用旧结果宣称事件当前仍未出现。等待完成也不承诺分析缓存或所有聚合已刷新。

**操作流程。**

1. 调用者提供明确事件身份和可选等待参数。CLI 确定总截止时间并开始诊断。

2. 每次取得新诊断后，先判断是否存在处理提交证据，以及同一结果中的任务是否已完成；两者都满足才结束为完成。

3. 任务停止自动处理时立即结束为处理失败；已提交但缺少任务历史时结束为证据不足。事件身份歧义要求补足身份。

4. 仍在等待入库、到期或处理时，在剩余预算内按间隔继续诊断。

5. 时限耗尽后结束为等待超时。读取故障导致无法继续时返回查询故障和最后有效观察，不把旧观察当作当前状态。

6. 所有结束情况返回原因、观察次数、耗时和最后有效证据，调用者据此继续排障或重新观察。

### 2.11 FR-11：提供人和 AI 都能理解的结果与错误

**功能目标。** 每个功能都能被人使用，也能被 AI 或脚本可靠调用，避免因输出形式不稳定而误判平台状态。

**涉及对象与前置条件。** 参与对象包括每个功能的正式结果、日志、退出状态以及人和 AI 的消费方式。该能力贯穿所有命令，不改变底层业务事实。

**业务逻辑。**

默认输出为结构化结果，人可以选择易读的表格展示。两种形式必须表达同一事实，不因展示模式不同而隐藏关键状态、分页信息或未知原因。

结果应说明操作目标、实际查询范围、所使用的项目、数据时刻、数据来源以及完整性限制。成功、空结果、局部成功、写入结果未知和证据不足都有明确表达，不能只依赖一段自由文本让 AI 猜测。

错误既需要便于人理解的说明，也需要稳定的机器标识和退出状态。日志、进度与交互提示应与正式结果分离，使脚本能够直接解析结果。非交互调用缺少参数或会话时，应立即结束并说明如何补足。

输出过大时，工具应给出缩小查询或分批获取的方向，不能悄悄截断记录再返回一个跳过部分数据的续页位置。原始事件内容和失败原因沿用平台的数据权限与脱敏规则。

**操作流程。**

1. 调用者选择默认结构化模式，或选择人工阅读展示。

2. 业务命令取得成功、错误或部分成功事实，连同项目、时间、范围、来源和后续分页交给结果处理。

3. CLI 保留空值、未知原因和已完成步骤，给错误附加稳定标识与退出状态；不把空数据当故障。

4. CLI 检查结果大小。正常时输出完整结果；过大时返回缩小范围的明确错误，不隐式裁掉记录。

5. 正式结果与日志、进度和提示分开输出。人阅读结果；AI 或脚本解析后决定查询下一页、继续步骤或结束。

### 2.12 FR-12：检查平台连接与基础可用性

**功能目标。** 使用者在接入前或查询失败时，可以检查当前平台是否可连接、管理 API 是否工作、关键依赖是否就绪。

**涉及对象与前置条件。** 参与对象包括目标平台、管理 API、服务存活状态和关键依赖。此功能不要求选择项目，也不以健康接口代替异步处理证据。

**业务逻辑。**

检查应分别展示连接结果、服务存活和依赖就绪情况。地址错误或服务不可达时，应说明无法取得平台状态；服务可连接但依赖未就绪时，应说明尚未具备完整工作条件。

健康检查需要说明自己的覆盖范围。管理 API 正常响应，不表示后台处理进程一定正常工作。是否持续处理数据，仍需要结合任务记录、完成情况以及后续可提供的进程状态证据判断。

**操作流程。**

1. 调用者指定或使用当前平台地址，发起健康检查。

2. CLI 尝试连接平台。无法连接时报告网络或地址问题，并标记其他状态未取得。

3. 连接可用时，分别取得管理 API 可响应情况、服务存活与关键依赖就绪结果，不用一个总成功遮住局部故障。

4. CLI 返回检查时间、各项结果及检查覆盖范围。缺少某项检查能力时说明未知，不补成健康。

5. 平台可用但项目没有事件时，调用者进入数据查询；怀疑后台处理异常时，进入队列及单事件诊断。

## 3. 写操作的结果与恢复要求

### 3.1 写入成功应当能继续核对

项目创建和来源设置必须通过平台业务接口执行，平台确认写入后返回保存的对象身份或最终配置。调用者应能够继续回查该对象，核对数据库所反映的实际状态。

工具不能仅根据自己准备的请求内容拼出成功结果。例如，来源设置结果应以平台确认保存的集合为依据；项目创建结果应以平台提供的身份为依据。

如果某个平台的读取具有延迟，应说明写入确认与回查可见性之间的差异。没有实际回查时，也不能宣称已经核对过数据库结果。

### 3.2 结果未知不等于未写入

写请求发出后连接中断，平台可能已经完成操作。工具应保存能够确定的事实，并明确表示本次结果无法确认。

对于项目创建，不能自动再次提交同一创建请求。调用者需要依据项目列表或其他可靠证据核查，重复名称不能作为本次操作的唯一证明。后续增加幂等能力时，应单独约定其行为。

### 3.3 多步骤允许部分成功，但必须能继续

项目创建、来源设置、配置导出和业务代码接入是不同步骤。前一步成功、后一步失败时，工具应返回已完成步骤、已创建对象或已生成文件，并给出继续修正的位置。

例如，项目已创建而来源更新失败，调用者应当修改已有项目来源，不需要重新创建项目。配置 JSON 已生成但接入示例未生成，也应能补齐示例，而不是丢失已经完成的产物。

### 3.4 写入权限和对象范围应明确

每个管理写操作都需要明确目标项目、将改变的对象及平台账号权限。首版中，项目创建由可登录账号发起，来源更新要求项目管理员权限。

人和 AI 可以执行相同的已实现写操作。首版没有提供的密钥轮换、任务重试或历史记录修改不能通过一个模糊的“管理数据库”命令替代。

## 4. 查询及时性、可靠性与使用体验

### 4.1 查询时刻必须清楚

每次数据查询应重新获取所请求的事实，不默认把上一次本地结果当作本次结果。返回中应说明服务端数据时刻，调用者能够判断结果是何时取得的。

如果平台使用缓存、聚合或异步查询模型，应说明来源和新鲜度边界。工具没有收到服务端数据时刻时，只能说明客户端请求时间，不能把它包装成数据库快照时间。

### 4.2 查询范围和保留策略必须可理解

普通事件列表的时间范围、数据概况的当前保留范围和单事件诊断的全部保留范围是不同概念。工具应在相应结果中说明，不要求使用者从内部实现猜测。

超过保留范围的查询没有结果时，不应自动解释为数据丢失。平台应公布保留策略，诊断中保留无法区分的历史可能性。

### 4.3 查询与等待必须按时结束

普通请求、一次命令和持续等待都需要明确时间预算。读取可以有限重试，写入结果未知时不自动重试。调用者需要能辨认网络请求超时和等待某条事件未完成这两种不同情况。

默认时限和可配置参数由技术文档规定。产品要求是：任何自动化调用都不会因无限请求或无限提示而卡住，截止时仍能取得清楚的结束原因和可用证据。

### 4.4 数据与凭据应受到正确保护

管理会话与 SDK 接入配置分开保存。密码不进入业务文件或普通输出。不同平台的管理身份不能混用，数据访问始终遵循平台账号的项目权限。

原始事件可能包含业务属性，失败原因可能包含内部信息。工具应返回平台允许查看并经过适当处理的数据，不因 CLI 输出或 AI 调用绕过数据边界。

### 4.5 帮助信息应支持独立使用

使用者无需阅读平台源码，就应能够了解每个功能的目的、必需输入、结果含义、权限要求、是否改变数据及常见错误。

帮助说明和接入示例应包含完整使用路径。新用户应知道怎样连接、登录、选项目、准备配置、产生事件和取得诊断结果，而不是只看到一份参数名称清单。

## 5. 首版边界与后续扩展

首版实现上述十二类功能，管理写入覆盖项目创建和业务来源更新；业务事件通过接入后的 SDK 正常写入。数据读取覆盖项目、接入信息、原始事件、原始数据概况和处理状态。

完整性能与页面趋势、自定义指标分析、各领域数据总量和实验室测试需要各自的查询口径。它们可以在后续接入 CLI，但不能在首版以没有说明的混合统计代替。

密钥轮换、成员管理、阈值修改和失败任务重试属于后续管理写入。新增这些功能时，应说明具体改变哪些对象、需要什么权限、失败后如何核查，以及 AI 如何使用。此前确定的“AI 可执行管理操作”同样适用于后续已实现的功能。

平台全局运维、任意 SQL、批量删除或修改历史监控记录需要单独定义产品场景。本首版不以这些能力作为普通项目接入与诊断的前提。

长期自动化凭据、全局安装和发布也在后续阶段处理。首版以本地监控平台、可登录账号、独立本地 CLI 包和可接入 SDK 的业务应用作为完整使用环境。

## 6. 验收场景与完成标准

### 6.1 新项目接入形成真实读写闭环

在一个可访问的本地平台中，开发者通过工具登录、创建项目、设置实际业务来源并导出配置。创建与来源更新都能够回查到保存结果，导出文件可以被业务代码读取。

业务接入 SDK 后，按照已定义的真实业务动作产生可追踪事件。执行前记录预期名称、类型、触发与结束时机及必要内容；执行后把操作记录、实际采集身份、数据库原始记录与 CLI 返回对齐，再展示概况、诊断或等待结果。页面事件与结束时才上报的耗时事件采用各自的触发规则，不能要求页面刚打开就出现尚未结束的记录。

这个场景验证 CLI 的管理写入、配置产物、业务事件读取及处理诊断。业务项目只提供真实输入，不扩大为整个业务的功能验收。探针可以辅助构造指定内容，但不作为 CLI 使用、业务数据识别或验收完成的必需条件；只有探针成功时，仍不能代替已定义真实业务事件的查询证据。

### 6.2 已有项目的数据查询完整可解释

使用者选择已有项目，查询指定时间与环境的数据，再继续读取后续页。每页都保留同一查询条件，明确是否仍有后续数据，不把一页结果称为全量。

无事件项目、范围内无事件、游标错误、范围不支持和访问失败均有不同结果。工具应让使用者知道自己取得了什么，以及没有取得什么。

### 6.3 数据统计能够反映真实保留情况

项目中存在事件时，数据概况返回当前保留数量与最近接收时间。改变查询列表范围不应改变概况对全部当前保留记录的定义。

平台接收累计数与保留数不相等时，工具仍分别标明来源，不将差异直接报告为丢失。新项目零数据时，概况仍是成功结果。

### 6.4 单事件诊断能解释正常处理与历史不足

准备尚未处理、已经处理、任务失败、重复或旧修订、领域记录不存在以及任务记录被清理等情况。工具应分别展示原始记录、处理证据、任务状态和领域可见性。

合法忽略的事件不因没有新增记录而被误判为失败；任务记录缺失不被自动断言为过去完成；查询不到原始记录不被自动断言为从未接收。

### 6.5 队列状态能够回答“现在可执行多少”

项目中同时存在已到期、退避等待、锁未超时、锁超时和终止处理的任务。结果能够清楚区分这些类别，总数与各子类可核对。

失败任务与死信重叠、最近失败列表不完整、普通遥测与其他任务类型不同等情况都能被明确说明，使用者不会据此重复计数或判断处理进程必然健康。

### 6.6 等待能在明确条件下结束

对指定事件分别验证处理完成、终止处理、历史证据不足、截止仍未完成以及等待期间网络故障。工具必须按相应情况结束，保留最后有效证据与观察过程信息。

完成判断允许合法去重，不要求新增领域行，不额外承诺分析缓存可见。截止后不能继续无期限轮询。

### 6.7 写入异常可以核查并恢复

模拟项目创建响应丢失、来源更新失败、配置文件冲突及部分产物生成成功。工具不得自动重复创建、默认覆盖已有文件或隐藏已成功步骤。

调用者能够根据返回的项目身份、保存状态、已生成文件和核查方向继续完成流程，而不是重新执行所有写操作。

### 6.8 人、AI 与脚本使用同一套可靠能力

人工终端可以登录并阅读结果，AI 或脚本可以非交互完成同样的查询和授权写入。标准结果可直接解析，日志不会混入正式输出。

会话过期、权限不足、参数缺失、输出过大和等待超时都能被稳定识别。切换平台不会误用旧项目或身份，未获授权的项目数据不可读取。

### 6.9 基础排障能够辨认真实故障范围

验证平台不可达、管理服务可连接但依赖未就绪、平台可用且项目无数据等情况。工具应给出清晰不同的结果。

健康检查通过后，仍不因缺少处理进程证据就宣称所有异步任务正常。使用者可以继续通过队列和事件诊断核查业务数据链路。

## 7. 需求文档与技术文档的使用关系

本文作为产品需求依据，用于评审功能是否完整、目标是否清楚、结果是否符合人和 AI 的实际工作过程。

配套技术文档将这些需求转换成模块、命令、接口、数据状态、输出格式、存储规则和验证方案。技术实现可以适配不同平台，但不能改变本文定义的数据含义、写入范围和未知状态处理。

两份文档统一保存在 Plan 目录。调整功能范围或数据含义时，应先更新需求，再同步技术契约，避免工具实现与使用者预期分离。
