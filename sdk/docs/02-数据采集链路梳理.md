# 02 · 数据采集链路梳理（Instrumentation）

> 本文只覆盖**数据采集**这一段：从 `createMonitor()` 触发开始，到 Instrumentation 把浏览器事实发布成 Raw Signal 为止。
> Collector 只在「谁在订阅这个信号」处做一句对照，不展开其内部逻辑。

---

## 一、监控平台的完整链路

一个监控平台要拿到线上数据，整体可以拆成三段。Browser Monitor SDK 的目录结构正是按这三段切开的：

```text
① 数据采集              ② 数据处理与度量计算          ③ 上报
浏览器里发生了什么   →    这条事实意味着什么      →    如何安全、可靠地送出去
instrumentation/         collectors/ + processing/      transport/
（原始事实 / Raw Signal）（领域解释 + 统一治理）      （队列、批处理、重试、发送）
```

| 环节 | 要回答的问题 | 承担目录 | 产物 |
| --- | --- | --- | --- |
| ① 数据采集 | 浏览器里刚刚发生了什么 | `src/instrumentation/` | Raw Signal（内部短暂事实） |
| ② 处理与计算 | 这条事实对监控意味着什么；要不要发、要不要脱敏 | `src/collectors/` + `src/processing/` | TelemetryEnvelope（标准上报体） |
| ③ 上报 | 怎么送出去且不丢、不炸、不拖慢页面 | `src/transport/` | HTTP 请求打到采集端点 |

三段的边界非常关键：**采集端不理解业务，计算端不触碰浏览器 API，上报端不认识具体指标。**
任何一段越界，都会让「同一份事实」在不同模块里被解释出不同含义。例如 LoAF 的「耗时阈值过滤」与「每个 View 最多上报几条」属于监控语义，必须留在 Collector；如果放进 Instrumentation，那么同一份 LoAF 数据换一个业务场景就无法复用了。

本文聚焦第 ① 段，以及支撑它的生命周期与信号体系。

## 二、SDK 的生命周期

### 2.1 模块契约：五个动作

所有参与生命周期的内部模块（Instrumentation、Collector、Transport 都算）实现同一个契约：

```ts
// src/core/module-registry.ts（第 21–28 行）
export interface MonitorModule {
  readonly name: string;
  install(): void;
  start(): void;
  stop(): void;
  destroy(): void;
}
```

`install` 与 `start` 被刻意拆开，是因为二者的性质完全不同：

| 动作 | 性质 | 典型工作 |
| --- | --- | --- |
| `install()` | 有副作用、一生一次 | 建立信号订阅关系、改写全局方法 |
| `start()` | 可反复执行 | 挂事件监听、创建 Observer、启动采样 |
| `stop()` | 与 start 严格对称 | 摘监听、断开 Observer、关闭数据出口 |
| `destroy()` | 终态 | 释放句柄、退订信号、清空引用 |

### 2.2 状态机

`src/core/lifecycle.ts` 用一台显式状态机把关，避免每个模块各自推断「现在能不能启动」：

```text
created ──install──> installed ──start──> running
                         ^                   │
                         └──────stop─────────┘
              （stopped 可以再次 start 回到 running）

destroyed 是终态：任何状态都能被 destroy，但进去之后再也出不来
```

```ts
// src/core/lifecycle.ts（第 33–56 行）
markInstalled(): void { if (this.state === 'created') this.state = 'installed'; }
markRunning(): void   { if (this.state === 'installed' || this.state === 'stopped') this.state = 'running'; }
markStopped(): void   { if (this.state === 'running') this.state = 'stopped'; }
markDestroyed(): void { this.state = 'destroyed'; }

canStart(): boolean {
  return this.state === 'created' || this.state === 'installed' || this.state === 'stopped';
}
```

`canStart()` 是「能否启动」的唯一判定入口：`created` 允许首次启动、`stopped` 允许恢复、`running` 让重复 start 变成幂等空操作、`destroyed` 被永久排除。

### 2.3 注册表：正序安装，逆序释放

`src/core/module-registry.ts` 用**数组**保存模块（而非 Set），因为注册顺序本身就是语义：

```ts
// src/core/module-registry.ts（第 30–78 行）
export class ModuleRegistry {
  private readonly modules: MonitorModule[] = [];
  private installed = false;

  register(module: MonitorModule): void {
    if (this.installed) throw new Error('Cannot register modules after installation.');
    this.modules.push(module);
  }

  install(): void {
    if (this.installed) return;                                   // install 的幂等闸门
    for (const module of this.modules) this.invoke(module, 'install');
    this.installed = true;
  }

  start(): void {
    for (const module of this.modules) this.invoke(module, 'start');
  }

  stop(): void {
    for (const module of [...this.modules].reverse()) this.invoke(module, 'stop');
  }

  destroy(): void {
    for (const module of [...this.modules].reverse()) this.invoke(module, 'destroy');
    this.modules.length = 0;
  }

  private invoke(module: MonitorModule, operation): void {
    try {
      module[operation]();
    } catch {
      // 单个监控模块失败不能破坏宿主应用，也不能阻断其他模块的生命周期。
    }
  }
}
```

注意 `stop()` / `destroy()` 里的 `[...this.modules].reverse()`：**先复制再反转**，避免就地反转污染 `modules` 自身的顺序（否则 stop 之后再 start，顺序就反了）。

`invoke()` 是统一的错误边界，这条规则是所有模块的共同底线：**任何一个模块出事，只影响它自己，绝不冒泡到宿主页面。**

### 2.4 注册顺序：为什么必须是这个次序

```ts
// src/core/monitor.ts（第 136–145 行）
this.registry.register(this.transport);          // 1  出口
this.registry.register(viewCollector);           // 2  消费者
this.registry.register(webVitalsCollector);
this.registry.register(loafCollector);
this.registry.register(fpsCollector);
this.registry.register(pageLifecycle);           // 6  数据源（公共事实）
this.registry.register(history);                 // 7  数据源
this.registry.register(webVitals);               // 8  数据源
this.registry.register(performanceObserver);     // 9  数据源（依赖 page.lifecycle）
this.registry.register(animationFrame);          // 10 数据源（依赖 page.lifecycle）
```

| 编号 | 模块 | 角色 | 为什么排在这里 |
| --- | --- | --- | --- |
| 1 | `transport` | 出口 | 必须最先就绪，否则最早的一批数据没人接管 |
| 2–5 | 四个 Collector | 消费者 | 它们的 `install()` 里订阅信号，必须先于数据源完成订阅 |
| 6 | `page-lifecycle` | 数据源 | 它发布的 `page.lifecycle` 被 9、10 订阅，因此必须先于它们注册 |
| 7–8 | `history`、`web-vitals` | 数据源 | 无内部依赖，位置自由 |
| 9–10 | `performance-observer`、`animation-frame` | 数据源 | 依赖 `page.lifecycle`，排在最后 |

两条方向相反的原则合在一起：

- **正序安装/启动**：消费者先就绪，数据源后启动 → 启动瞬间产生的事实不会「无人消费」；数据源订阅时，它依赖的那个发布者也已经存在。
- **逆序停止/销毁**：数据源先停，消费者后释放 → 不会出现「还在产生数据，但下游已被拆掉」的悬空状态。

## 三、Instrumentation 总览

### 3.1 定位与边界

Instrumentation 是 SDK 与浏览器 API 直接接触的唯一边界。它只回答「**浏览器刚刚发生了什么**」，不回答「这件事对监控平台意味着什么」。

- 不生成最终数据：同一份事实可能有多种解释，解释权归 Collector；
- 不携带上下文：session、view、user 由 Context 在 Pipeline 阶段注入；
- 不做决策：阈值过滤、上报次数限制一律留给下游；
- 依赖单向：只通过注入的 `SignalPublisher` 发事实，不直接导入 Core，也不直接调用 Collector。

### 3.2 每个模块的三步框架

```text
(a) 订阅它的依赖  →  (b) 监听浏览器并采集  →  (c) 发布自身的输出
      install()            start()                publisher.publish()
```

| 步骤 | 落点 | 说明 |
| --- | --- | --- |
| (a) 订阅依赖 | `install()` | 只做一次。例如 LoAF、FPS 都要先订阅 `page.lifecycle`，才能感知页面进入后台 |
| (b) 采集数据 | `start()` | 挂监听 / 建 Observer / 改写全局方法，可随 stop 反复挂卸 |
| (c) 发布输出 | 采集回调里 | 把浏览器原始字段安全地提取出来，按本模块的信号结构发布 |

**「为了保证订阅的依赖能够存在」，注册必须有顺序** —— 这正是 2.4 节那张表的由来。

### 3.3 模块清单

| 模块 | 采集手段 | 监听的浏览器能力 | 发布的信号类型 |
| --- | --- | --- | --- |
| `page-lifecycle` | 原生事件 | `visibilitychange` / `pagehide` / `pageshow` | `page.lifecycle` |
| `history` | 改写全局方法 + 事件 | `history.pushState/replaceState`、`popstate`、`hashchange` | `view.route-change` |
| `web-vitals` | 第三方库 | `web-vitals` 的 `onLCP/onFCP/onINP/onCLS` | `performance.web-vital` |
| `performance-observer` | 浏览器 API | `PerformanceObserver`（`long-animation-frame`） | `performance.loaf` |
| `animation-frame` | 浏览器 API | `requestAnimationFrame` + `setTimeout` | `performance.frame-window` |

## 四、模块化信号体系

这是整个采集段的组织方式：**模块、信号类型、负载结构三者一一对应，统一由 SignalHub 收发。**

```text
模块（Module）          信号类型（Signal Type）        负载结构（Payload Type）
performance-observer  →  'performance.loaf'         →  LoAFSignal
web-vitals            →  'performance.web-vital'    →  WebVitalSignal
animation-frame       →  'performance.frame-window' →  FrameWindowSignal
page-lifecycle        →  'page.lifecycle'           →  PageLifecycleSignal
history               →  'view.route-change'        →  RouteChangeSignal
        │                        │                            │
        └──── 发布 publish(type, payload) ──── SignalHub ──── 订阅 subscribe(type, listener) ────┘
```

### 4.1 信号类型总表：SignalMap

所有信号类型集中登记在一张映射表里，它是类型安全的唯一来源：

```ts
// src/signals/index.ts（SignalMap）
/**
 * 信号类型 → 负载类型的总映射表，是类型安全的唯一来源。
 * key 命名遵循「领域.事实」两段式，避免出现无归类的扁平常量。
 */
export interface SignalMap {
  'performance.web-vital': WebVitalSignal;
  'performance.loaf': LoAFSignal;
  'performance.frame-window': FrameWindowSignal;
  'page.lifecycle': PageLifecycleSignal;
  'view.route-change': RouteChangeSignal;
}
```

**新增一种事实 = 在这里加一行映射**，发布端与订阅端的类型安全随之自动获得：写错类型名会编译报错，监听器里拿到的负载类型也是自动推导的，不需要手写泛型参数。

### 4.2 每种信号自己的负载结构

每个模块都有**专属的负载结构**，按「自己采集到了什么」定义，互不干扰：

```ts
// src/signals/performance.ts
export interface WebVitalSignal {
  name: Extract<PerformanceMetricName, 'LCP' | 'FCP' | 'INP' | 'CLS'>;
  metricId: string;
  value: number;
  delta: number;
  rating: PerformanceMetricRating;
  navigationType: PerformanceNavigationType;
  navigationId: number;
  timestamp: number;
}

export interface LoAFSignal {
  timestamp: number;        // 绝对时间（timeOrigin + startTime）
  startTime: number;        // 相对 timeOrigin 的起点
  duration: number;         // 长动画帧总时长
  blockingDuration: number; // 主线程被阻塞的时长
  renderStart: number;
  styleAndLayoutStart: number;
  scriptCount: number;      // 归因脚本数量
}

export interface FrameWindowSignal {
  timestamp: number;
  frameCount: number;       // 采样窗口内的帧数
  sampleDurationMs: number; // 窗口实际时长
}
```

```ts
// src/signals/view.ts
export interface PageLifecycleSignal {
  type: 'visible' | 'hidden' | 'pagehide' | 'pageshow';
  timestamp: number;
  persisted: boolean;       // 是否来自 BFCache
}

export interface RouteChangeSignal {
  timestamp: number;
  url: string;
  source: 'initial' | 'history' | 'popstate' | 'hashchange' | 'bfcache';
}
```

共同点：**都带 `timestamp`，都不带 session / user / view**。前者用于按发生时间归属 View，后者由 Context 在 Pipeline 阶段注入 —— 采集层不关心数据最终属于谁。

### 4.3 SignalHub：统一的收发中枢

一个容易误解的点：**不是每个模块各自维护一份监听器数组**，而是所有模块共享同一个 `SignalHub` 实例；Hub 内部按信号类型分桶，每桶一个 `Set`：

```ts
// src/core/signal-hub.ts（第 31–76 行）
export class SignalHub implements SignalPublisher, SignalSubscriber {
  // 按信号类型分桶，每桶一个 Set：天然去重，避免同一个监听器被重复登记导致重复消费。
  private readonly listeners = new Map<keyof SignalMap, Set<AnySignalListener>>();

  publish<K extends keyof SignalMap>(type: K, signal: SignalMap[K]): void {
    const current = this.listeners.get(type);
    if (!current) return;

    // 同步分发且不缓存 Raw Signal；复制集合可以避免监听器在回调中退订时影响本轮遍历。
    for (const listener of [...current]) {
      try {
        listener(signal);
      } catch {
        // 一个订阅者的异常不应回传给数据源或宿主页面。
      }
    }
  }

  subscribe<K extends keyof SignalMap>(
    type: K,
    listener: (signal: SignalMap[K]) => void,
  ): () => void {
    const current = this.listeners.get(type) ?? new Set<AnySignalListener>();
    this.listeners.set(type, current);
    const stored = listener as unknown as AnySignalListener;
    current.add(stored);

    return () => {
      current.delete(stored);
      if (current.size === 0) this.listeners.delete(type);
    };
  }

  clear(): void {
    this.listeners.clear();
  }
}
```

运行时的内部结构长这样：

```text
listeners: Map {
  'page.lifecycle'        => Set { performanceObserver 的回调, animationFrame 的回调, ... },
  'performance.loaf'      => Set { loafCollector 的回调 },
  'view.route-change'     => Set { viewCollector 的回调, loafCollector 的回调 },
  ...
}
```

三个实现细节：

| 细节 | 代码 | 原因 |
| --- | --- | --- |
| 类型擦除 | `AnySignalListener` 用联合类型存，泛型在接口层补回 | `Map` 无法为每个 key 保存各自的具体负载类型 |
| 遍历副本 | `for (const listener of [...current])` | 允许监听器在回调里退订而不影响本轮遍历 |
| 逐个兜错 | 循环体内 `try/catch` | 一个订阅者抛错不能影响其他订阅者，更不能冒泡到宿主页面 |

三条硬性边界：

1. **同步分发、不缓存、不重放** —— Signal 只表达「刚刚发生」的事实；
2. **不属于上报协议** —— 既不入发送队列，也不作为最终 payload；
3. **不是业务事件总线** —— 不承担重试与持久化，`Monitor.destroy()` 里一句 `signals.clear()` 清空全部订阅。

### 4.4 发布端与订阅端：两个受限视图

同一个 Hub 对外只暴露两种能力，用两个接口切开：

```ts
// src/signals/index.ts（Publisher / Subscriber）
export interface SignalPublisher {
  publish<K extends keyof SignalMap>(type: K, signal: SignalMap[K]): void;
}

export interface SignalSubscriber {
  subscribe<K extends keyof SignalMap>(
    type: K,
    listener: (signal: SignalMap[K]) => void,
  ): () => void;
}
```

于是**依赖方向在类型层面就被固定住了**：

| 模块类型 | 注入的视图 | 能做的事 |
| --- | --- | --- |
| 纯数据源（history、web-vitals、page-lifecycle） | `SignalPublisher` | 只能发 |
| 纯消费者（各 Collector） | `SignalSubscriber` | 只能订 |
| 既订又发（performance-observer、animation-frame） | 两者都要 | 订阅 `page.lifecycle`，发布自己的指标 |

既订又发的模块在 `monitor.ts` 里表现为把同一个 Hub 实例传两次：

```ts
// src/core/monitor.ts（第 119–131 行）
const performanceObserver = new PerformanceObserverInstrumentation(
  this.signals,   // 作为 SignalPublisher
  this.signals,   // 作为 SignalSubscriber
  enabledMetrics.LoAF,
);
```

同一份对象、两个类型视角 —— 这就是「一个模块既是生产者又是消费者」但依赖方向依然单向的实现方式。

### 4.5 这样组织带来什么

| 收益 | 说明 |
| --- | --- |
| 解耦 | 发布者不知道谁在听，订阅者不知道谁在发，双方只依赖 `SignalMap` 里的类型 |
| 多方复用 | 一份事实可以被任意多个模块订阅（如 `view.route-change` 同时被 View、LoAF Collector 使用） |
| 类型安全 | 类型名、负载结构都在 `SignalMap` 里定义，写错即编译报错 |
| 可独立测试 | 用内存 Hub 即可单测某个模块，不需要真实浏览器事件 |
| 易扩展 | 新增能力 = 加一个模块 + 加一行 `SignalMap` + 加一个负载结构 |

## 五、LoAF 全链路详解

以 `PerformanceObserverInstrumentation` 为完整样例，把 (a) 订阅依赖 → (b) 监听采集 → (c) 发布输出 三步逐行拆开。

```text
page-lifecycle ──publish('page.lifecycle')──┐
                                            ↓  (a) install 里订阅
                              PerformanceObserverInstrumentation
                                            │
浏览器 PerformanceObserver ──条目推送──────→ │  (b) start 里 observe
                                            ↓
                              publishLoAF() 提取字段
                                            ↓  (c) publish('performance.loaf', LoAFSignal)
                                        SignalHub
                                            ↓
                                     LoAFCollector（订阅者）
```

### 5.1 它的状态字段

```ts
// src/instrumentation/performance-observer/index.ts（第 83–103 行）
export class PerformanceObserverInstrumentation implements MonitorModule {
  readonly name = 'performance-observer-instrumentation';
  private active = false;                                // 采集态闸门
  private everStarted = false;                           // 保证 buffered 只补一次
  private disconnect: (() => void) | undefined;          // Observer 卸载句柄，兼作「已挂载」标志
  private unsubscribeLifecycle: (() => void) | undefined;// 信号退订句柄

  constructor(
    private readonly publisher: SignalPublisher,         // 只用来发
    private readonly signals: SignalSubscriber,          // 只用来订
    private readonly loafEnabled: boolean,               // 功能开关
  ) {}
}
```

### 5.2 (a) 订阅依赖：`install()`

```ts
// src/instrumentation/performance-observer/index.ts（第 105–114 行）
install(): void {
  if (this.unsubscribeLifecycle) return;                 // install 幂等
  this.unsubscribeLifecycle = this.signals.subscribe('page.lifecycle', (signal) => {
    if (!this.active) return;                            // 不在采集态就不响应
    // 后台页面不继续持有 Observer；恢复时只观察新条目，防止重复读取 buffered 数据。
    if (signal.type === 'hidden' || signal.type === 'pagehide') this.disconnectObserver();
    if (signal.type === 'visible' || signal.type === 'pageshow') this.observe(false);
  });
}
```

要点：

- 订阅放在 `install()` 而非 `start()`：订阅关系与「是否正在采集」无关，一生只需建立一次，避免 stop/start 反复退订重订；
- 回调里第一件事是 `if (!this.active) return`：stop 之后即使信号还在发，也不做任何动作；
- 恢复时传 `false`：只观察新条目，绝不再次回放 `buffered` 历史数据。

**这就是「注册顺序」存在的意义**：它订阅的 `page.lifecycle` 由 `page-lifecycle` 模块发布，后者必须已经注册并处于可发布状态。

### 5.3 (b) 监听采集：`start()` → `observe()`

```ts
// src/instrumentation/performance-observer/index.ts（第 116–151 行）
start(): void {
  if (this.active) return;
  this.active = true;
  // buffered 仅用于首次启动补齐启动前条目，stop/start 后不能再次回放历史数据。
  this.observe(!this.everStarted);
  this.everStarted = true;
}

private observe(buffered: boolean): void {
  if (!this.active || !this.loafEnabled || !this.supportsLoAF() || this.disconnect) return;
  this.disconnect = observePerformanceEntries(
    'long-animation-frame',
    (entry) => this.publishLoAF(entry as LongAnimationFrameEntry),
    buffered,
  );
}
```

`observe()` 的四重前置校验：

| 校验 | 作用 |
| --- | --- |
| `this.active` | 采集态闸门，stop 后一律不挂载 |
| `this.loafEnabled` | 功能开关，关闭时零开销 |
| `this.supportsLoAF()` | 能力检测，不支持的浏览器静默降级 |
| `this.disconnect` | 已挂载则跳过，保证重复调用幂等（后台恢复可能连续触发两次 pageshow） |

底层的 Observer 封装：

```ts
// src/instrumentation/performance-observer/index.ts（第 32–57 行）
export function supportsPerformanceEntry(type: string): boolean {
  if (typeof PerformanceObserver === 'undefined') return false;
  const supportedEntryTypes = PerformanceObserver.supportedEntryTypes;
  return Array.isArray(supportedEntryTypes) && supportedEntryTypes.includes(type);
}

export function observePerformanceEntries(
  type: string,
  handler: PerformanceEntryHandler,
  buffered: boolean,
): () => void {
  if (!supportsPerformanceEntry(type)) return () => undefined;   // 不支持 → 返回空卸载函数

  try {
    const observer = new PerformanceObserver((list) => {
      for (const entry of list.getEntries()) handler(entry);     // 批量推来的条目逐条分发
    });
    observer.observe({ type, buffered });
    return () => observer.disconnect();                          // 必须保存卸载句柄
  } catch {
    return () => undefined;                                      // 声明支持但实际抛错也要兜住
  }
}
```

两个关键设计：能力检测先行（LoAF 并非全平台可用）；**即使失败也返回一个合法的空函数**，让调用方可以无差别地保存并调用卸载逻辑，不需要到处写判空。

### 5.4 (c) 发布输出：`publishLoAF()`

```ts
// src/instrumentation/performance-observer/index.ts（第 153–176 行）
private publishLoAF(entry: LongAnimationFrameEntry): void {
  if (!this.active || !Number.isFinite(entry.duration)) return;
  const startTime = safeTiming(entry.startTime);
  // Instrumentation 只做浏览器字段的安全提取，不在这里判断业务阈值或上报次数。
  this.publisher.publish('performance.loaf', {
    timestamp: performanceTimeOrigin() + startTime,
    startTime,
    duration: entry.duration,
    blockingDuration: safeTiming(entry.blockingDuration),
    renderStart: safeTiming(entry.renderStart),
    styleAndLayoutStart: safeTiming(entry.styleAndLayoutStart),
    scriptCount: Array.isArray(entry.scripts) ? entry.scripts.length : 0,
  });
}

function safeTiming(value: number | undefined): number {
  return value !== undefined && Number.isFinite(value) && value >= 0 ? value : 0;
}
```

浏览器字段 → Signal 字段的映射与兜底规则：

| Signal 字段 | 来源 | 兜底规则 |
| --- | --- | --- |
| `timestamp` | `performanceTimeOrigin() + entry.startTime` | 相对时间换算成绝对时间，才能与业务事件、View 时间线对齐 |
| `startTime` | `entry.startTime` | `safeTiming` → 非法为 0 |
| `duration` | `entry.duration` | 非法则**整条丢弃**（连耗时都不可信的条目没有分析价值） |
| `blockingDuration` | `entry.blockingDuration` | `safeTiming` → 非法为 0 |
| `renderStart` / `styleAndLayoutStart` | 同名可选字段 | `safeTiming` → 非法为 0 |
| `scriptCount` | `entry.scripts.length` | 非数组则为 0（只要数量，不解析具体内容） |

这里能看到采集层的边界感：**只做「安全提取」，不做阈值判断**。

### 5.5 卸载：stop / destroy

```ts
// src/instrumentation/performance-observer/index.ts（第 124–133 行）
stop(): void {
  this.active = false;
  this.disconnectObserver();
}

destroy(): void {
  this.stop();
  this.unsubscribeLifecycle?.();          // 退订 page.lifecycle
  this.unsubscribeLifecycle = undefined;
}

private disconnectObserver(): void {
  this.disconnect?.();
  this.disconnect = undefined;            // 清空句柄，使下次 observe 能通过「尚未挂载」校验
}
```

### 5.6 谁在听（仅作对照，不展开 Collector）

```ts
// src/collectors/performance/loaf.ts（第 29–39 行）
this.signals.subscribe('performance.loaf', (signal) => {
  if (
    !this.active ||
    signal.duration < this.options.minDurationMs ||          // 阈值：监控语义，留在 Collector
    this.emittedEntries >= this.options.maxEntriesPerView    // 每 View 上限：同样留在 Collector

  this.emitter.emit({ /* ... 生成 LoAF Payload ... */ });
```

一眼就能看出分工：**Instrumentation 给出「浏览器说了什么」，Collector 决定「这条算不算问题、要不要发」。**

### 5.7 LoAF 模块的状态流转

```text
install()  → 订阅 page.lifecycle，拿到 unsubscribeLifecycle
start()    → active = true，observe(!everStarted) 挂载 Observer，everStarted = true
   ├─ 条目到达 → publishLoAF → publish('performance.loaf')
   ├─ 收到 hidden/pagehide → disconnectObserver()（摘 Observer，但仍在采集态）
   └─ 收到 visible/pageshow → observe(false)（只观察新条目）
stop()     → active = false，disconnectObserver()
start()    → 重新挂载（此时 buffered = false）
destroy()  → stop() + 退订 page.lifecycle
```

## 六、其他采集手段

### 6.1 Web Vitals：复用第三方库

LCP/FCP/INP/CLS 的计算口径极其复杂（候选值取舍、交互归因、软导航、隐藏时结算时机），自己实现既容易与官方口径不一致，又要持续跟进规范。因此这里复用官方库，模块只做「接入 + 翻译 + 兜底」：

```ts
// src/instrumentation/web-vitals/index.ts（start / stop / destroy / register 节选）
start(): void {
  if (this.destroyed) return;                  // 销毁后永不恢复
  this.active = true;
  if (this.installed) return;                  // 底层监听只安装一次
  this.installed = true;

  const reportOptions = {
    reportAllChanges: this.options.reportAllChanges,
    reportSoftNavs: this.options.reportSoftNavs,
  };

  const report = (metric: Metric): void => {
    if (!this.active || this.destroyed || metric.name === 'TTFB') return;
    if (metric.name !== 'LCP' && metric.name !== 'FCP'
     && metric.name !== 'INP' && metric.name !== 'CLS') return;

    this.publisher.publish('performance.web-vital', {
      name: metric.name,
      metricId: metric.id,
      value: metric.value,
      delta: metric.delta,
      rating: metric.rating,
      navigationType: navigationType(metric.navigationType),
      navigationId: metric.navigationId,
      timestamp: metricTimestamp(metric),
    });
  };

  this.register('LCP', () => onLCP(report, reportOptions));   // 惰性注册：传 thunk
  this.register('FCP', () => onFCP(report, reportOptions));
  this.register('INP', () => onINP(report, reportOptions));
  this.register('CLS', () => onCLS(report, reportOptions));
}

stop(): void    { this.active = false; }                       // 软停止：只关数据出口
destroy(): void { this.active = false; this.destroyed = true; }

private register(name: WebVitalName, callback: () => void): void {
  if (!this.options.enabled[name]) return;                    // 关闭的指标连库函数都不执行
  try {
    callback();
  } catch {
    // 浏览器能力缺失或实现不完整时静默降级，不能影响宿主页面。
  }
}
```

与其他模块最大的不同：**web-vitals 不返回取消句柄，底层监听无法物理卸载**。因此「安装一次 + 两个状态门控」：

| 状态 | 含义 |
| --- | --- |
| `installed` | 监听是否已安装，单向，一生只翻一次 |
| `active` | 采集态，stop 置 false，start 可零成本恢复 |
| `destroyed` | 终态，之后所有回调永久丢弃 |

### 6.2 History：没有事件，就改写全局方法

SPA 的路由跳转既不触发 `pagehide` 也不触发 `pageshow`，而 `pushState`/`replaceState` **没有任何原生事件**。唯一可行的观测手段是改写全局方法：

```ts
// src/instrumentation/history/index.ts（第 76–100 行）
private wrapHistory(): void {
  if (this.originalPushState || this.originalReplaceState) return;  // 防「包装套包装」
  this.originalPushState = history.pushState;
  this.originalReplaceState = history.replaceState;
  const originalPushState = this.originalPushState;                // 局部 const：类型收窄 + 闭包安全
  const originalReplaceState = this.originalReplaceState;

  this.wrappedPushState = (...args: Parameters<History['pushState']>): void => {
    originalPushState.apply(history, args);   // ① 先转发：显式绑定 history 作为 this
    this.publish('history');                  // ② 再发信号：此时 url 已是新地址
  };
  this.wrappedReplaceState = (...args: Parameters<History['replaceState']>): void => {
    originalReplaceState.apply(history, args);
    this.publish('history');
  };

  history.pushState = this.wrappedPushState;
  history.replaceState = this.wrappedReplaceState;
}

private restoreHistory(): void {
  if (this.originalPushState && history.pushState === this.wrappedPushState) {
    history.pushState = this.originalPushState;   // 只有确认挂的是自己装的才还原
  }
  if (this.originalReplaceState && history.replaceState === this.wrappedReplaceState) {
    history.replaceState = this.originalReplaceState;
  }
  // 清空全部句柄，使下次 start 能重新干净地包装
  this.originalPushState = undefined;
  this.originalReplaceState = undefined;
  this.wrappedPushState = undefined;
  this.wrappedReplaceState = undefined;
}

private publish(source: 'initial' | 'history' | 'popstate' | 'hashchange'): void {
  if (!this.active) return;                       // 非采集态直接丢弃
  this.publisher.publish('view.route-change', {
    timestamp: Date.now(),
    url: currentUrl(),
    source,
  });
}
```

改写全局方法的三条底线：**保存原始引用**（还原的唯一凭据）、**保持原语义**（`apply` 绑 this、参数原样转发、先调用原生方法）、**必须可逆**（按引用核对后还原）。另有 `popstate` / `hashchange` 覆盖前进后退与锚点变化。

### 6.3 Page Lifecycle：最基础的公共事实源

```ts
// src/instrumentation/page-lifecycle/index.ts（install / start / stop / handleVisibility 节选）
install(): void {}          // 无一次性准备工作，监听随 start/stop 挂卸

start(): void {
  if (this.active) return;
  this.active = true;
  document.addEventListener('visibilitychange', this.handleVisibility);
  window.addEventListener('pagehide', this.handlePageHide);
  window.addEventListener('pageshow', this.handlePageShow);
}

stop(): void {
  if (!this.active) return;
  this.active = false;
  document.removeEventListener('visibilitychange', this.handleVisibility);
  window.removeEventListener('pagehide', this.handlePageHide);
  window.removeEventListener('pageshow', this.handlePageShow);
}

private readonly handleVisibility = (): void => {
  this.publisher.publish('page.lifecycle', {
    type: document.visibilityState === 'hidden' ? 'hidden' : 'visible',
    timestamp: Date.now(),
    persisted: false,
  });
};
```

它在 `start()` 而非 `install()` 里挂监听，是为了保证 `stop()` 之后不再产生任何信号。它发布的 `page.lifecycle` 是**被依赖最多**的信号：采集器据此暂停后台采集、View 据此处理 BFCache、Transport 据此在离开前冲刷队列。

### 6.4 Animation Frame：rAF 采样

```ts
// src/instrumentation/animation-frame/index.ts（collectFrame 节选）
private readonly collectFrame: FrameRequestCallback = (timestamp) => {
  if (!this.active || !this.sampling) return;

  if (this.firstFrameTime === undefined) {   // 第一帧只用于确定窗口起点
    this.firstFrameTime = timestamp;
  } else {
    this.frameCount += 1;
  }

  const duration = timestamp - this.firstFrameTime;
  if (duration >= this.options.sampleWindowMs) {
    this.sampling = false;
    this.animationFrameId = undefined;
    if (duration > 0 && this.frameCount > 0) {
      this.publisher.publish('performance.frame-window', {
        timestamp: performanceTimeOrigin() + timestamp,   // 相对时间 → 绝对时间
        frameCount: this.frameCount,
        sampleDurationMs: duration,
      });
    }

    this.resetWindow();                      // 清零后再排下一个采样窗口
    this.intervalTimer = setTimeout(() => {
      this.intervalTimer = undefined;
      this.startWindow();
    }, this.options.sampleIntervalMs);
    return;
  }

  this.animationFrameId = requestAnimationFrame(this.collectFrame);
};
```

只输出「帧数 + 窗口时长」，**FPS 的除法留给 Collector 算**。它同样订阅 `page.lifecycle`：后台标签页的 rAF 会被浏览器节流，继续采样会得到失真的 FPS，因此 `hidden` 时 `pause()`、`visible` 时 `resume()`。

## 七、从代码触发开始的完整时序

以 LoAF 为例，把前面所有环节串起来：

```text
① createMonitor(options)
     ├─ normalizeOptions(options)                配置归一化，Fail Fast
     ├─ new SignalHub() / ContextManager / Transport / MonitorPipeline
     ├─ registry.register(...) × 10              按「出口 → 消费者 → 数据源」顺序登记
     └─ webVitals.capabilities() 等              构造期冻结能力表

② monitor.start()
     ├─ lifecycle.canStart() 守卫
     ├─ 首次调用 → registry.install()             正序
     │     ├─ loafCollector.install()  → subscribe('performance.loaf')
     │     ├─ pageLifecycle.install()  →（空）
     │     ├─ performanceObserver.install()
     │     │     └─ subscribe('page.lifecycle', ...)          ← (a) 订阅依赖
     │     └─ animationFrame.install() → subscribe('page.lifecycle', ...)
     ├─ lifecycle.markInstalled()
     ├─ registry.start()                          正序
     │     ├─ transport.start()
     │     ├─ ...Collector.start()                消费者先就绪
     │     ├─ pageLifecycle.start()               先挂可见性监听
     │     └─ performanceObserver.start()
     │           └─ observe(!everStarted)                     ← (b) 监听采集
     │                 └─ new PerformanceObserver(...).observe({ type: 'long-animation-frame' })
     └─ lifecycle.markRunning()

③ 浏览器推送 LoAF 条目
     └─ handler(entry) → publishLoAF(entry)                   ← (c) 发布输出
           └─ publisher.publish('performance.loaf', LoAFSignal)
                 └─ SignalHub.publish：取 'performance.loaf' 桶 → 遍历副本 → 逐个 try/catch
                       └─ LoAFCollector 的监听器收到 → 阈值过滤 → emitter.emit(...)

④ 页面切到后台
     └─ pageLifecycle 发 page.lifecycle(hidden)
           ├─ performanceObserver → disconnectObserver()
           └─ animationFrame      → pause()

⑤ monitor.stop() → registry.stop()（逆序）
     └─ animationFrame.stop() → performanceObserver.stop() → ... → transport.stop()
     └─ lifecycle.markStopped()

⑥ monitor.destroy() → registry.destroy()（逆序）+ signals.clear() + context.destroy()
     └─ lifecycle.markDestroyed()
```

## 八、新增一种采集能力要走的步骤

模块化信号体系的价值之一，就是扩展路径是固定的：

| 步骤 | 要改的地方 | 具体内容 |
| --- | --- | --- |
| 1 | `src/signals/<领域>.ts` | 定义本模块的**负载结构**（如 `XxxSignal`） |
| 2 | `src/signals/index.ts` | 在 `SignalMap` 加一行 `'领域.事实': XxxSignal` |
| 3 | `src/instrumentation/<模块>/index.ts` | 实现 `MonitorModule`：install 订依赖、start 挂监听、回调里 publish |
| 4 | `src/core/monitor.ts` | `registry.register(...)`，位置按「它依赖谁、谁依赖它」决定 |
| 5 | （可选）`src/collectors/...` | 订阅该信号，把它解释成领域数据 |

全程**不需要修改 SignalHub**，也不需要修改任何其他模块 —— 这正是「通过模块 + 信号类型 + SignalHub 统一管理发布订阅」带来的可扩展性。

## 九、小结

| 关注点 | 做法 | 代码位置 |
| --- | --- | --- |
| 采集什么 | 只采集「浏览器发生了什么」，不解释、不决策、不带上下文 | `src/instrumentation/*` |
| 怎么采集 | Observer / 第三方库 / 改写全局方法 / 原生事件 / rAF，按需选型 | 各模块 `start()` |
| 依赖怎么满足 | `install()` 订阅依赖，注册顺序保证订阅时依赖已就绪 | `monitor.ts` 注册顺序 |
| 信号怎么组织 | 一个模块 ↔ 一种信号类型 ↔ 一个负载结构，登记在 `SignalMap` | `src/signals/` |
| 事实怎么传递 | 共享一个 SignalHub，按类型分桶，发布端/订阅端两个受限视图 | `src/core/signal-hub.ts` |
| 怎么停下来 | 正序启动、逆序释放；无法卸载的监听靠状态门控 | `module-registry.ts` |
| 出错怎么办 | 单模块异常就地吞掉；能力缺失静默降级并返回合法空函数 | 各模块 `try/catch` |

**一句话**：Instrumentation 负责把浏览器里五花八门的机制，翻译成各自专属的 Raw Signal；`SignalMap` 把这些信号类型与负载结构集中登记；SignalHub 用「按类型分桶 + 两个受限视图」实现统一的发布订阅，让同一份事实可以被多方消费而彼此互不知情；生命周期与注册顺序则保证这条链在启动、暂停、销毁的每一个瞬间，都不会出现「有人发、没人收」或「还在发、已经拆」的裂缝。
