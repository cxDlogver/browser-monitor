## 第一章 项目介绍

> **浏览器监控 SDK 要建立的不是一个“收集日志”的工具，而是一条从真实用户现场到指标分析和问题追溯的数据链路。**

Web 应用上线后，运行环境从可控走向不可控。用户使用的设备、浏览器、网络质量和操作路径各不相同，测试环境中没有暴露的问题，可能只在某类用户、某个版本或某种网络条件下出现。如果客户端没有持续记录这些运行事实，团队就无法客观判断系统表现，也无法在异常发生后还原现场。

### 1. 项目要解决的问题

应用上线后的信息缺口可以分为三个方向：

```text
线上应用的信息缺口
├─ 运行结果不清楚：页面是否够快、系统是否稳定、业务流程是否完成
├─ 异常过程不完整：只看到错误结果，看不到问题发生前后的关键事实
└─ 监控工程不受控：全局包装、异构数据和重复逻辑反过来影响业务
```

#### 【线上使用过程不可见】# Browser Monitor SDK 项目知识梳理

## 1. 项目目标与建设背景

### 【项目目标】

Browser Monitor SDK 的建设目标可以归纳为两个闭环：**正常运行时判断项目是否达标，异常发生时快速还原现场并定位问题。**

#### <u>1. 正常运行：用真实线上数据判断项目是否达标</u>

项目在开发环境或测试环境中运行正常，只能说明它在有限条件下能够工作，不能代表真实用户环境中的表现。应用上线后，不同用户的设备性能、浏览器版本、网络质量和操作路径都存在差异，因此项目是否达到预期，需要依赖真实运行数据持续验证。

监控系统首先需要为三类结果提供数据基础：

- **性能指标**：页面加载、内容渲染、交互响应以及持续运行过程是否具有良好的用户体验。
- **稳定性指标**：运行时错误、请求失败、资源加载异常等问题是否控制在合理范围内。
- **业务指标**：用户是否到达关键业务节点、核心业务流程是否完成，以及主要在哪个阶段失败或流失。

因此，正常运行状态下形成的基本闭环是：

```text
应用上线运行
    ↓
采集真实用户运行数据
    ↓
计算性能 / 稳定性 / 业务指标
    ↓
按页面、版本、设备、网络等维度分析
    ↓
判断项目是否达到业务目标和用户体验目标
```

监控的价值不只是得到某一次指标结果，而是建立一套稳定的数据口径，使不同版本、页面和运行环境能够持续进行比较，从而判断一次发布究竟带来了改善还是退化。

#### <u>2. 异常运行：还原线上现场并快速定位问题</u>

第二个目标是解决线上问题难以复现和难以定位的问题。

用户反馈“页面报错”“按钮没有反应”或者“提交失败”时，单独的一条 JavaScript 错误、接口日志或者错误堆栈通常不足以说明问题发生的完整过程。

一次真实的问题可能经历：

```text
进入页面
    ↓
执行关键操作
    ↓
发起业务请求
    ↓
请求失败
    ↓
页面状态异常
    ↓
产生运行时错误
```

如果点击、请求、页面变化和 Error 分散在不同的数据中，并且彼此没有关联，那么最终只能看到“哪里报错了”，很难进一步回答“为什么会报错”。

因此，异常情况下需要记录并关联：

```text
Session
   ↓
View / 页面
   ↓
用户关键操作
   ↓
Network Request
   ↓
Error / 页面异常
```

最终形成：

```text
线上异常
    ↓
找到异常发生时的页面和运行环境
    ↓
关联异常发生前的关键操作
    ↓
继续关联对应请求和页面变化
    ↓
还原问题发生过程
    ↓
定位可能原因
    ↓
分析受影响的页面 / 版本 / 用户环境
```

监控系统不仅要帮助找到某一次异常，还要进一步回答问题主要集中在哪些页面、版本、浏览器、设备或者网络环境中，从而判断问题的影响范围。

### 【项目需要解决的问题】

上述两个目标背后，真正需要解决的是**应用上线以后，浏览器端真实运行过程缺少持续、完整的数据记录**。

线上环境与开发环境最大的区别在于不可控。

同一份前端代码可能运行在不同：

```text
设备性能
浏览器版本
网络环境
页面状态
用户操作路径
应用版本
```

测试环境不一定能够覆盖这些组合，因此一些问题只有在线上某类用户、某个版本或者特定网络条件下才会出现。

这会形成两个核心的信息缺口。

#### <u>1. 缺少能够持续评价项目状态的数据</u>

如果没有客户端监控，只能依赖开发阶段测试、人工体验或者零散服务端数据判断项目状态。

但是服务端日志无法完整回答：

- 用户是否真正看到了页面内容；
- 页面加载和交互是否足够快；
- 页面渲染过程中是否发生卡顿；
- 用户是否真正完成了关键业务流程；
- 某些问题是否只发生在特定设备、浏览器或网络环境。

因此，需要在真实用户环境中持续采集性能、稳定性和业务过程数据，形成项目上线后的长期评价依据。

#### <u>2. 缺少能够还原浏览器运行现场的数据</u>

浏览器中的一次完整操作通常横跨多个不同机制。

例如：

```text
用户点击
→ DOM Event

页面请求
→ Fetch / XMLHttpRequest

运行时异常
→ error / unhandledrejection

性能变化
→ Performance API

SPA 页面切换
→ History API
```

这些信息不会天然组成一条完整的问题链路。

浏览器只分别暴露不同时间发生的事实，而不会自动告诉监控系统：

> 某一次点击触发了哪个请求，这个请求发生在哪个页面，请求失败之后又引发了哪个 Error。

因此，前端监控需要主动记录这些关键事实，并为不同数据建立页面、会话、操作和请求之间的关联。

### 【为什么需要 Browser Monitor SDK】

解决上述问题，并不意味着把各种监听和上报逻辑直接写进业务页面。

如果每个业务页面分别实现：

```text
页面 A
├─ 性能监听
├─ Error 监听
├─ Fetch 监听
└─ 数据上报

页面 B
├─ 性能监听
├─ Error 监听
├─ Fetch 监听
└─ 数据上报
```

那么监控能力就会和业务代码长期绑定。

随着页面和监控需求增加，很容易演变为：

```text
新增一种指标
→ 多个页面分别修改

修改数据格式
→ 多套监控代码分别修改

调整脱敏规则
→ 各业务重新适配

修改发送策略
→ 所有采集代码受到影响
```

而监控本身具有明显的公共能力特征。

不同页面虽然业务不同，但都需要处理：

```text
浏览器事实采集
→ 形成监控数据
→ 补充运行上下文
→ 数据校验和脱敏
→ 控制数据量
→ 缓存和批量发送
```

性能、错误、请求和业务事件虽然数据内容不同，但它们在采集之后都会面对公共上下文、字段校验、敏感信息过滤、采样、限频、缓存和发送等共同问题。

因此，需要把这些能力从具体业务中抽离出来，形成独立的 Browser Monitor SDK。

整体关系可以表示为：

```text
业务应用
    │
    ├─ 只负责正常业务逻辑
    │
    └─ 接入 Monitor SDK
             ↓
        统一观察浏览器运行过程
             ↓
        统一形成监控数据
             ↓
        统一处理和上报
```

业务执行仍然是主流程，监控只是旁路观察。

例如业务调用 `fetch` 时，SDK 可以记录请求开始时间、结束状态和耗时，但是必须把原来的 Response 或异常继续返回给业务代码。**监控失败可以导致少采一条数据，但不能改变业务本身的执行结果。**

SDK 化最终解决的是两个层次的问题：

```text
业务层
负责完成用户真正的业务目标

Monitor SDK
负责统一观察、记录和传递线上运行事实
```

这样既能够保证不同页面拥有一致的监控能力，也能够使后续新增监控指标、扩展新的数据类型或调整数据处理方式时，主要在 SDK 内部完成，而不需要让大量业务代码重复修改。

最终形成整个项目的起点：

```text
线上环境不可控
        ↓
需要真实数据判断项目是否达标
+
需要完整运行事实定位线上异常
        ↓
浏览器信息来自不同 API，天然分散
        ↓
需要持续记录和关联关键运行事实
        ↓
这些能力具有明显的跨页面、跨业务复用特征
        ↓
构建 Browser Monitor SDK
        ↓
为业务提供统一、低侵入、可持续演进的监控能力
```

## 2. Monitor SDK 的设计思想

Monitor SDK 的设计思想可以按照它需要解决的五类不同问题进行划分：

```text
业务边界问题
→ 监控能力如何与业务代码解耦

数据差异问题
→ 不同来源、不同结构的数据如何进入统一链路

现场割裂问题
→ 分散的数据如何重新关联成一次完整运行过程

工程演进问题
→ SDK 内部如何拆分，避免局部变化影响整体

安全与成本问题
→ 应该采什么、采多少，以及怎样保证监控不反过来影响业务
```

这五个问题分别对应 **业务边界、数据边界、关联边界、代码边界和资源边界**，因此可以作为 Monitor SDK 设计的五个核心思想。

### 【设计思想一：监控能力与业务代码解耦】

#### <u>1. 核心问题</u>

如果性能采集、错误监听、请求监听和数据上报逻辑直接散落在具体页面或业务组件中，监控能力就会与业务代码形成强耦合。

例如每个页面分别实现：

```text
业务页面
├─ 业务逻辑
├─ Error 监听
├─ Fetch 监听
├─ Performance 监听
└─ 数据上报
```

随着页面和监控需求增加，会产生几个问题：

- 相同监控逻辑在不同业务页面中重复实现；
- 新增或修改一种监控能力时，需要修改大量业务代码；
- 不同业务可能形成不同的数据采集和处理标准；
- 监控逻辑本身的异常可能影响业务执行。

因此，监控不能成为具体业务逻辑的一部分，而应该作为独立的基础能力存在。

#### <u>2. 核心目标</u>

核心目标是：

> **将通用监控能力从业务代码中抽离，形成独立的 Monitor SDK，使业务负责完成业务目标，SDK 负责旁路观察运行过程。**

业务代码与监控代码形成明确边界：

```text
业务代码
→ 完成页面展示、请求、交易等业务逻辑

Monitor SDK
→ 观察页面运行过程
→ 形成监控数据
→ 处理并上报
```

即使监控发生异常，也应该最多损失一部分监控数据，而不能改变业务原有执行结果。业务是主流程，监控是旁路观察者。

#### <u>3. 设计思想</u>

业务与监控的解耦主要通过两种接入方式实现。

第一种是 **自动采集 / 自动插装**。

对于所有 Web 应用都具有的通用浏览器事实，可以由 SDK 在初始化后统一监听：

```text
Monitor SDK 初始化
        ↓
注册浏览器 Instrumentation
        ↓
自动观察
├─ Performance API
├─ window.error
├─ unhandledrejection
├─ fetch / XMLHttpRequest
├─ History
└─ Page Lifecycle
```

业务页面只需要初始化 SDK，不需要在每一个请求、异常或性能指标旁边重新编写监控代码。

第二种是 **显式业务埋点**。

浏览器只能知道“发生了 click”，却不知道这个 click 对业务意味着什么。

例如：

```text
click
```

SDK 无法可靠判断它代表：

```text
提交订单
领取优惠券
登录成功
完成支付
```

因此，业务特有的语义仍然需要显式表达：

```ts
monitor.track('order_submit', {
  orderType: 'normal',
});
```

最终形成：

```text
通用运行事实
→ SDK 自动采集

特定业务语义
→ 业务通过监控 API 显式埋点
```

自动采集减少业务侵入，显式埋点补充无法自动推断的业务语义，两者共同完成业务与监控的解耦。

### 【设计思想二：异构数据使用统一监控管线】

#### <u>1. 核心问题</u>

浏览器中需要监控的数据并不是一种数据。

不同数据来自完全不同的浏览器能力：

```text
Performance
→ PerformanceObserver / web-vitals / rAF

Error
→ error / unhandledrejection

Network
→ fetch / XMLHttpRequest / Resource Timing

Event
→ DOM Event / 业务 API

View
→ History / Page Lifecycle
```

它们不仅获取方式不同，原始数据结构和最终含义也完全不同。

例如：

```text
LCP
→ value / rating / navigationType

Error
→ message / stack / type

Network
→ method / url / status / duration

Event
→ name / target / properties
```

如果每一种数据从采集一直独立实现到发送，就会形成多条彼此割裂的监控链路：

```text
Performance → 自己处理 → 自己发送
Error       → 自己处理 → 自己发送
Network     → 自己处理 → 自己发送
```

最终会产生重复逻辑以及不一致的数据标准。

#### <u>2. 核心目标</u>

核心目标不是把所有监控数据变成完全一样的数据结构，而是：

> **允许不同数据保留自己的领域语义，同时让它们进入同一套采集、治理和上报框架。**

因此要区分两个层次：

```text
不同
→ 数据来源不同
→ 采集方式不同
→ 领域字段不同
→ 指标计算逻辑不同

统一
→ 公共上下文
→ 基础协议
→ 脱敏规则
→ 采样与限频
→ 队列
→ 批量发送
```

这就是“**统一不等于抹平差异**”。

#### <u>3. 设计思想</u>

整个 SDK 建立稳定的数据流水线：

```text
浏览器事实
    ↓
Instrumentation
    ↓
Raw Signal
    ↓
Collector
    ↓
Context
    ↓
Protocol
    ↓
Processing
    ↓
Transport
```

其中可以进一步理解为三个阶段。

第一阶段解决**怎么获得数据**：

```text
Instrumentation
→ 面向不同浏览器 API 捕获原始事实
```

例如：

```text
Fetch Instrumentation
PerformanceObserver Instrumentation
Global Error Instrumentation
DOM Event Instrumentation
```

第二阶段解决**这些事实代表什么**：

```text
Collector
→ 将浏览器事实转换成具体监控语义
```

例如：

```text
PerformanceEntry
→ Performance Collector
→ Performance Metric

Fetch Result
→ Network Collector
→ Network Record

window.error
→ Error Collector
→ Error Record
```

第三阶段解决**所有数据共同如何处理和发送**：

```text
Monitoring Data
    ↓
Normalize
    ↓
Redact
    ↓
Dedupe / Sampling / Rate Limit
    ↓
Queue / Batch
    ↓
Transport
```

因此这一层设计可以概括为：

> **多源采集、领域转换、统一治理、统一输出。**

### 【设计思想三：通过 Context 和关联标识还原完整运行现场】

#### <u>1. 核心问题</u>

线上问题通常不是由一条孤立的数据构成的。

一次用户操作可能经历：

```text
用户进入订单页
      ↓
点击提交订单
      ↓
发起 POST /orders
      ↓
接口返回 500
      ↓
页面状态处理异常
      ↓
JavaScript Error
```

Monitor SDK 可能分别产生：

```text
View Record
Event Record
Network Record
Error Record
Performance Record
```

这些数据表达的是同一次运行过程中的不同侧面。

如果数据之间没有关系，那么后台只能看到：

```text
一个点击
一个请求
一个 Error
一个性能指标
```

却不知道这些数据是否来自同一个用户、同一次页面访问或者同一次操作。

#### <u>2. 核心目标</u>

核心目标是：

> **让不同监控数据保留它们在真实运行过程中的上下文和关联关系，从孤立的数据记录进一步形成可以追溯的问题链路。**

这里需要特别区分 **关联** 和 **去重**。

同一次请求可能产生：

```text
Network Record
→ 描述请求状态和耗时

Error Record
→ 描述一个可检索、可聚合的异常
```

这两条数据不是重复数据，因为它们回答的问题不同。

真正的重复是：

```text
同一个 Error
因为重复监听
→ Error A
→ Error A
→ Error A
```

前者需要**关联**，后者才需要**去重**。

#### <u>3. 设计思想</u>

需要为监控数据建立分层上下文：

```text
Session
└─ View
   └─ Action / Interaction
      ├─ Request
      └─ Error
```

常见关联标识可以包括：

```text
sessionId
viewId
actionId / interactionId
requestId
traceId / spanId
```

不同标识解决不同范围的问题：

```text
sessionId
→ 是否属于同一次连续使用

viewId
→ 是否发生在同一次页面访问

actionId
→ 是否由同一次用户操作触发

requestId
→ Error 与具体请求之间的关系

traceId
→ 需要时进一步关联前后端调用链
```

同时，Context 必须强调一个关键原则：

> **上下文应该在事件发生时绑定，而不是等到上报时再读取。**

例如：

```text
页面 A
→ 发起 Request-01
→ 用户进入页面 B
→ Request-01 返回
```

如果发送数据时才读取：

```ts
window.location.href;
```

Request-01 很可能会被错误归到页面 B。

因此需要在事件发生阶段保存当时的上下文快照：

```text
Request-01
{
  sessionId: "S1",
  viewId: "VIEW-A",
  ...
}
```

即使后续经过缓存和批量发送，它仍然属于原来的 View。

同时也不能为了追求关联而强行制造因果关系。

例如 LCP 通常属于 View 级性能指标，并不意味着它一定由某一次 click 引起。因此关联应该按照实际语义逐层建立：

```text
同一 Session
≠ 一定存在因果关系

同一 View
≠ 一定由同一 Action 引起

拥有 requestId / actionId
→ 才表达更强的直接关联
```

这样才能既支持现场还原，又避免产生错误的因果解释。

### 【设计思想四：按照变化原因拆分 SDK 模块，并统一管理生命周期】

#### <u>1. 核心问题</u>

业务代码需要与监控解耦，Monitor SDK 内部本身同样需要解耦。

例如以下变化的原因完全不同：

```text
浏览器新增 Performance API
发送接口发生变化
新增一种 Error 类型
修改敏感信息过滤规则
增加 SPA 路由识别方式
```

如果所有逻辑都放在一个大的 Monitor 类中：

```text
Monitor
├─ Hook Fetch
├─ Performance
├─ Error
├─ Context
├─ Redact
├─ Queue
└─ Send
```

那么一次局部修改就可能影响整个 SDK。

此外，浏览器监控需要修改或监听大量全局能力，例如：

```text
fetch
XMLHttpRequest
History
window.error
DOM Event
PerformanceObserver
```

如果这些全局资源没有统一生命周期，还会产生重复 Hook、监听器残留和资源泄漏等问题。

#### <u>2. 核心目标</u>

这一层的目标是：

> **按照不同的变化原因建立稳定模块边界，使一个能力的变化尽量只影响所属模块，同时统一控制所有全局监控能力的生命周期。**

这里的模块化和第一层“业务解耦”并不是同一个问题。

第一层解决：

```text
业务系统
↕
Monitor SDK
```

之间的边界。

这一层解决：

```text
Monitor SDK 内部
Instrumentation / Collector / Context / Processing / Transport
```

之间的边界。

#### <u>3. 设计思想</u>

SDK 可以按照变化原因拆分：

```text
core
→ SDK 生命周期与模块编排

instrumentation
→ 浏览器 API 和 Hook

collectors
→ Performance / Event / Error / Network / View 领域语义

context
→ Session / View / User / Runtime Context

protocol
→ 模块间数据契约

processing
→ Normalize / Redact / Dedupe / Sampling / Rate Limit

transport
→ Queue / Batch / Sender / Retry / Flush

shared
→ 无领域语义的基础能力
```

这种拆分不是按照“代码长得像什么”，而是按照“什么原因会让代码变化”。

例如：

```text
新增一种性能指标
→ 主要修改 Performance Collector

调整 URL 脱敏规则
→ 修改 Processing / Redact

改变批量发送机制
→ 修改 Transport

改变 SPA 路由判断方式
→ 修改 View / History 相关能力
```

而不需要修改整条监控链路。

在模块拆分之外，全局能力还必须拥有完整生命周期：

```text
未安装
   ↓ install
已就绪
   ↓ start
正在采集
   ↓ stop
暂停采集
   ↓ start
重新采集

任意可释放状态
   ↓ uninstall / destroy
恢复浏览器环境
```

生命周期至少需要保证：

- `start()` 重复执行不会重复 Hook；
- `stop()` 可以停止继续生产监控数据；
- 再次 `start()` 可以恢复；
- `destroy()` 可以注销监听器、Observer、Timer，并恢复被包装的全局 API；
- 生命周期函数具有幂等性。

因此，这一层最终解决的是两个问题：

```text
代码层
→ 局部变化不扩散

运行层
→ 全局 Hook 和资源可安装、启停和释放
```

### 【设计思想五：以最小必要数据为原则控制安全和运行成本】

#### <u>1. 核心问题</u>

监控天然存在一个容易出现的误区：

> 为了以后能够排查问题，把能够采集的数据尽可能全部采集下来。

但监控数据越多，并不意味着监控效果一定越好。

无限制采集会同时带来：

```text
隐私与安全风险
+
浏览器 CPU / 内存开销
+
网络上报成本
+
存储成本
+
无效数据噪声
+
后续分析成本
```

而 Monitor SDK 本身与业务共享主线程、内存和网络，因此监控开销过大时，甚至会降低它正在监控的用户体验。

#### <u>2. 核心目标</u>

核心目标是：

> **只采集实现监控目标所必要的数据，并使采集、处理、缓存和上报成本始终处于可控范围内。**

因此监控的优先级始终低于业务正确性。

数据完整性应该围绕监控目标定义，而不是围绕“尽可能多记录”定义。

#### <u>3. 设计思想</u>

首先是**数据最小化**。

默认采集：

```text
事件类型
发生时间
必要目标标识
必要运行环境
页面和 Session 信息
问题定位需要的关联信息
```

默认不应该记录：

```text
Password
Token
Cookie 中的敏感内容
Authorization
API Secret / API Key
完整表单输入
无明确用途的 DOM 内容
无差别 Request / Response Body
```

业务需要额外字段时，应通过明确白名单决定。

其次是**敏感信息必须尽早处理**。

错误方式是：

```text
原始数据
→ Queue
→ Batch
→ 发送前 Redact
```

因为敏感信息已经进入 SDK 内部缓存。

正确方式应该是：

```text
Collector
    ↓
Normalize
    ↓
Redact
    ↓
安全数据
    ↓
Queue
```

即敏感数据不能进入后续缓存和发送链路。

第三是**按照数据价值决定采集频率**。

不同数据没有必要采用相同策略。

例如：

```text
JavaScript Error
→ 通常事件触发时记录

LCP
→ 页面生命周期中的结果指标

FPS / Frame Time
→ 高频产生，需要窗口采样

DOM Event
→ 只记录白名单中的关键操作

Network
→ 可按请求类型、URL 或采样策略过滤
```

高频数据需要：

```text
Sampling
Rate Limit
Aggregation
Window
```

而不是每一个原始事件都发送。

最后是**控制发送成本**：

```text
单条小数据
    ↓
Memory Queue
    ↓
Batch
    ↓
达到数量 / 时间阈值
    ↓
一次发送
```

页面隐藏或离开时，再进行受控 Flush。

### 【整体设计思想】

五个设计思想最终可以收敛为一条完整逻辑：

```text
1. 业务边界
监控不应该侵入具体业务
        ↓
独立 SDK
自动采集 + 显式业务埋点


2. 数据边界
监控数据来源和结构不同
        ↓
Instrumentation + Collector
多源采集、领域转换
        ↓
统一 Processing + Transport


3. 关联边界
一次真实运行会产生多条监控数据
        ↓
Session / View / Action / Request Context
        ↓
建立关联而不是简单合并数据
        ↓
还原完整线上现场


4. 代码边界
SDK 自身也会不断增加和修改能力
        ↓
按照变化原因进行模块拆分
        ↓
统一生命周期和全局 Hook 管理
        ↓
局部变化不扩散


5. 资源边界
监控不能无限采集
        ↓
最小必要原则
        ↓
Redact / Sampling / Rate Limit / Batch
        ↓
安全和运行成本受控
```

最终，Monitor SDK 的整体设计原则可以概括为：

> **在不改变业务执行的前提下，以低侵入方式持续观察浏览器运行事实；通过稳定的数据管线将异构数据转换为可治理的监控数据，通过 Context 保留真实运行关系，再以模块化架构和受控的数据策略保证整个监控能力能够长期、安全地演进。**

服务端日志可以记录接口收到了什么请求、返回了什么结果，却不能完整描述浏览器端的运行过程。接口未被调用，可能是按钮根本没有触发，也可能是前端在发起请求前已经报错。接口返回正常，也不代表用户看到了正确界面，因为后续渲染和状态更新仍然可能失败。

对研发团队来说，线上现场至少需要回答以下问题：

- 用户进入了哪个页面，当时的应用版本、浏览器和网络环境是什么？
- 用户执行了哪些关键操作，页面和路由随后发生了什么变化？
- 操作过程中发起了哪些请求，请求的耗时、结果和失败阶段是什么？
- 页面是否发生了运行时错误、未处理的 Promise 拒绝或资源加载异常？

这些事实如果没有在发生时及时采集，事后往往无法从其他系统中补回。监控 SDK 因此要成为客户端运行事实的稳定入口，让原本不可见的过程变得可查询。

#### 【项目是否达标缺少客观依据】

开发环境流畅、测试用例通过，只能证明系统在有限条件下可以工作。真实用户面对的是不同性能的设备、不同的网络质量和不同的访问路径。项目是否达到生产要求，不能只靠个人体感或上线前的一次测试来判断。

要对项目进行持续评估，需要从真实运行数据中得到三类结果：

- **性能结果**：页面加载、内容渲染、用户交互和持续运行时的表现是否符合预期。
- **稳定性结果**：错误率、请求失败率、异常影响的用户和页面范围是否处于可接受区间。
- **业务结果**：用户是否到达关键节点，核心流程是否完成，失败主要集中在哪个阶段。

指标还需要与页面、版本、浏览器、设备和网络等条件结合。整体数据正常，不代表所有用户都正常；局部环境中的严重退化，可能会被平均结果掩盖。SDK 提供的数据必须能支撑这些维度下的筛选和对比，才能用于版本评估和长期治理。

#### 【单条错误不足以还原问题】

一条错误堆栈能够指出代码在哪里失败，却不一定能解释它为什么失败。例如，用户点击提交后，一个请求超时，后续代码继续读取空结果，最终在另一个位置抛出异常。如果请求失败、用户操作和运行时错误是三条互不相关的记录，排查人员很容易把最后的报错位置误当成根因。

真正有用的追溯信息，不是无限量记录用户的所有行为，而是围绕问题保留必要的因果线索：

```text
进入页面
  └─ 点击关键按钮
       └─ 发起业务请求
            ├─ 请求成功 → 流程继续
            └─ 请求失败 → 页面状态异常 → 抛出运行时错误
```

这条链路中的事件要能通过会话、页面访问、操作或请求等上下文建立联系。只有这样，监控平台才能从“报错统计”进一步走到“现场还原”。

**<u>边界：这里的可追溯性用于分析运行过程，不等同于由浏览器客户端单独承担法律合规审计。</u>**

#### 【监控不能成为新的故障来源】

浏览器监控不可避免地会接触全局能力。为了观察网络请求，可能需要包装 `fetch` 和 `XMLHttpRequest`；为了识别单页应用的页面变化，可能需要观察 History API；为了捕获错误和页面生命周期，还需要注册全局事件监听。

这些操作如果缺少统一约束，会带来直接风险：

- 同一 API 被多次包装，一次请求产生多份重复数据。
- 包装函数没有正确传递参数、返回值或调用上下文，改变原有 API 行为。
- 页面或应用卸载后，监听器、定时器和缓存没有清理，造成资源残留。
- SDK 内部的采集、处理或上报异常向外传播，中断正常业务逻辑。

所以，对全局能力的管理不是一个附加优化项，而是 SDK 能否安全接入生产环境的前提。监控必须保持低侵入，即使自身失败，也不应改变用户正在使用的应用。

#### 【异构数据不能各自形成孤岛】

性能指标、运行时错误、网络请求、用户行为和业务事件的来源不同，它们要表达的内容也不同。性能数据关心数值、单位和采集时机；错误数据关心类型、消息和堆栈；请求数据关心目标、耗时和结果；业务事件则关心具体业务含义。

这些差异需要保留，否则数据会失去解释能力。但它们在进入监控链路后，又都要面对相同的工程问题：

**公共上下文补全；字段校验；敏感信息过滤；采样与限频；重复数据处理；缓存与批量发送；失败后的降级或重试。**

如果每类数据都自己解决一遍这些问题，不仅会产生大量重复代码，还会让不同数据形成不同的脱敏、采样和上报口径。随着监控类型增加，这种分裂会让数据越来越难以治理。

### 2. 项目目标

项目的目标可以用两个闭环概括，但每个闭环都必须由持续、稳定且语义明确的数据支撑：

```text
正常运行
  └─ 采集真实数据 → 计算性能、稳定性与业务指标 → 判断项目是否达标

发生异常
  └─ 关联关键操作、页面、请求与错误 → 还原问题现场 → 定位原因与影响范围
```

#### 【建立可计算的数据基础】

SDK 采集的不应是一批只适合人工阅读的文本日志，而应是语义稳定、可以持续计算的数据。每条数据除了表达自身内容，还需要带上完成后续分析所必需的上下文。

一条数据至少要能说清：

- **是什么**：数据类型、名称和具体内容。
- **何时发生**：事件时间以及必要的持续时间。
- **在哪里发生**：页面、路由和页面访问标识。
- **在什么环境中发生**：应用、版本、运行环境、浏览器和设备等信息。
- **与哪些事件相关**：会话、用户、操作或请求链路的关联标识。

当这些信息具有一致语义时，监控平台才能进行按版本对比、按页面统计、按环境筛选和按链路追溯。

#### 【让指标能够验证真实目标】

监控不仅是在出现错误时报警。在没有明显故障的时候，它也要持续回答“项目是否在变好”和“当前版本是否满足要求”。

因此，SDK 要为三类指标提供可信的原始数据：

1. **性能指标**：衡量页面显示、交互响应、布局稳定和持续运行状态。它们用于判断用户是否能及时看到内容、页面是否能及时响应操作。
2. **稳定性指标**：衡量运行时错误、资源异常、请求失败及其影响范围。它们用于识别某个版本、页面或环境中是否出现集中退化。
3. **业务指标**：衡量用户是否到达关键节点、核心流程是否完成，以及用户主要在哪一步离开或失败。这类指标需要由业务方给出明确语义，SDK 不能从普通点击中自行推断。

指标的价值不在于某一次统计结果，而在于能够持续比较。只有数据口径稳定，团队才能判断发布前后的变化是真实改善、真实退化，还是采集方式变化造成的假象。

---

#### 【建立能够还原现场的关联能力】

错误、请求、页面变化和用户操作都只是线上现场的一个切面。项目的目标不是将它们堆放在几个互不相关的列表里，而是保留它们在原始运行过程中的关系。

一次有效的追溯，应当能够逐步缩小问题范围：

- 通过会话标识，确认数据是否来自同一次连续使用。
- 通过页面访问标识，判断事件发生时用户正在哪个页面或路由中。
- 通过操作链路，确定某个请求、页面更新或错误是否由某次关键操作引起。
- 通过请求与错误上下文，区分前端逻辑失败、接口异常、网络问题和浏览器环境问题。

这种关联能力会同时改善问题定位和影响范围分析。不仅能找到一个问题的可能原因，还能回答它集中出现在哪些版本、页面、用户或环境中。

#### 【保持低侵入，并允许监控能力持续演进】

监控 SDK 是被业务应用引入的基础能力，不应反过来要求业务页面理解内部采集、处理和发送细节。对普通页面来说，通用监控能力应在接入后按配置生效；只有登录成功、提交订单或完成关键步骤这类特定业务语义，才需要由业务方显式埋点。

低侵入不只是“少写几行接入代码”，还包括：

- 监控功能可以按环境、数据类型或业务需求开启与关闭。
- SDK 内部异常不影响业务代码的正常返回和异常处理。
- 应用销毁或不再需要监控时，所有全局修改和运行资源都有对应的释放路径。
- 增加新数据类型时，不需要重写已经稳定的公共处理和上报逻辑。

最终，业务只需要表达自己特有的监控需求，SDK 则负责保持通用链路的一致性。这是接入成本可控、新能力可以长期迭代的基础。

### 3. 设计思想

从数据角度看，整个监控闭环可以表达为：

**浏览器事实与业务埋点 → 明确的数据语义 → 一致的公共治理 → 可靠上报 → 指标计算与问题追溯**

这条链路的关键不在于把所有事情放在一起完成，而在于给不同的变化建立稳定边界：业务逻辑变化、浏览器能力变化、数据类型增加和上报策略调整，不应彼此牵连。

#### 【用稳定边界隔离变化】

业务解耦、能力复用和职责分离，本质上是同一个设计思路：**把不同原因引起的变化隔离开，使每次修改只影响它本来应该影响的范围。**

这一思路可以通过几个实际变化来检验：

- 页面从多页应用调整为单页应用时，变化应主要落在页面访问边界的识别上，不应迫使错误、性能和发送逻辑一起重写。
- 增加一种新的性能指标时，只需补充这类数据的获取和语义转换，不应再实现一套脱敏、采样和发送机制。
- 发送策略从单条实时发送调整为批量发送时，不应要求各类采集逻辑同步修改。
- 业务方增加一个“支付完成”埋点时，只需提供业务语义，不需要理解数据如何缓存和发送。

如果一个局部需求总会引发整条链路修改，说明责任边界已经混在一起。稳定边界的价值，不是让结构看起来更复杂，而是让变化变得可预期。

#### 【全局能力必须具有完整生命周期】

对 `fetch`、`XMLHttpRequest`、History API 和全局事件的监听，都会与业务共享同一个浏览器运行环境。因此，每项全局能力都必须回答四个问题：何时安装；如何避免重复安装；暂停时如何停止产生数据；彻底卸载时如何恢复环境。

从概念上看，它的生命周期应当是：

```text
未安装 ──安装──→ 已就绪 ──启动──→ 正在采集
   ↑                        │             │
   └──────卸载与恢复──────┘                │
                            ↑             │
                            └───暂停──────┘
```

这里的关键是区分“暂停采集”和“彻底释放”。暂停后可以再次启动，原有包装和注册关系不需要重复建立；卸载则要恢复被包装的全局 API，移除监听器和定时器，并清理内部缓存。

生命周期还必须具有幂等性。重复执行启动不应创建第二层包装，重复停止不应抛出异常，已卸载的能力不应继续生产数据。这些约束共同保证 SDK 不会在单页应用重复初始化、模块热更新或测试清理时破坏运行环境。

#### 【自动采集与业务埋点各司其职】

监控数据中，一部分是所有 Web 应用都具有的通用事实，另一部分则只有当前业务才能解释。这两类数据不应使用同一种接入方式。

```text
监控数据来源
├─ 通用浏览器事实
│  └─ 错误、请求、性能、页面变化 → 由 SDK 按配置自动采集
└─ 特定业务事件
   └─ 登录成功、提交订单、完成关键步骤 → 由业务显式埋点
```

自动采集的价值是保证基础覆盖。新页面接入 SDK 后，不需要为每个请求、错误或性能指标重复编写埋点。显式埋点的价值则是提供精确的业务语义，例如同一次点击在不同页面中可能代表完全不同的业务动作，SDK 不应通过 DOM 结构猜测其含义。

两者结合后，业务方只需要为真正重要的业务节点提供语义，通用运行事实由 SDK 保持稳定采集。

#### 【统一不等于抹平数据差异】

错误、请求、性能和业务事件不需要拥有完全相同的内容。错误需要保留错误类型和堆栈，请求需要保留方法、目标、耗时和状态，性能数据需要保留指标值、单位和采集语义。强行将这些内容压成同一组字段，反而会让数据失去领域含义。

需要统一的是它们的公共语义和进入后续链路的方式：

```text
一条标准监控数据
├─ 基本信息：唯一标识、数据类型、名称、发生时间
├─ 应用上下文：应用、版本、环境
├─ 运行上下文：会话、页面访问、用户与设备
├─ 关联信息：操作链、请求链或其他关联标识
└─ 特有内容：错误、请求、性能或业务数据自己的字段
```

这种结构让不同数据可以共用同一套公共规则，又不会牺牲各自的解释能力。增加新数据类型时，只要它能转换成这种可预期的表达，便可以进入已有的数据治理和上报链路。

#### 【事件发生时就要绑定正确上下文】

上下文不是在数据发送前临时读取当前页面状态。事件从发生到真正发送之间可能经过缓存和批量等待，此时页面、路由甚至用户状态都可能已经变化。如果在发送时才补上下文，旧页面上的错误就可能被错误地归到新页面。

因此，数据在产生时就要获得当时的上下文快照。一次线上现场可以被表达为：

```text
Session-01
└─ View-01（商品详情页）
   ├─ Event-01：用户点击“立即购买”
   ├─ Request-01：创建订单请求超时
   └─ Error-01：后续逻辑读取空订单结果
```

这里的价值不在于标识本身，而在于让分散的数据重新回到同一次使用过程中。当排查人员查看 Error-01 时，可以继续追溯引发它的操作和请求，而不是只能停留在最后一条堆栈上。

#### 【先约束采集，再追求数据完整】

监控系统很容易陷入“记录越多，定位越容易”的误区。实际上，无边界采集会同时增加隐私风险、运行成本和分析噪声。数据完整性应当围绕明确的监控目标定义，而不是围绕“尽可能多地记录”定义。

##### <u>1. 采集内容遵循最小必要原则</u>

默认只采集操作类型、目标标识、时间和定位问题所必需的上下文。密码、令牌、表单原文和用户输入内容不属于默认采集范围。需要上报的业务属性由业务白名单明确定义，不从页面 DOM 或请求内容中无差别提取。

##### <u>2. 敏感数据不进入后续队列</u>

字段校验、过滤和脱敏必须发生在数据进入缓存或发送队列之前。如果先保存原始数据，再希望于发送时统一清理，敏感信息已经进入了 SDK 的内部存储边界，风险并没有被真正消除。

##### <u>3. 运行开销必须受控</u>

监控与业务共享主线程、内存和网络资源。对高频数据需要采样或限频，内存队列需要明确容量上限，小数据需要合并发送，页面隐藏或离开时需要有受控的收尾策略。当浏览器不支持某项能力时，SDK 应该明确降级，不伪造零值，也不强行使用高成本的替代方案。

> **监控的优先级始终低于业务正确性。它要尽可能准确地描述线上事实，但不能为了得到更多数据而改变用户正在经历的系统。**
