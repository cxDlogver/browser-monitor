# 浏览器监控 SDK 项目介绍

## 1. 项目背景

Web 应用上线并不意味着研发过程已经结束。应用进入真实环境后，用户会通过不同的设备、浏览器和网络访问系统，也会沿着不同的业务路径完成操作。实验环境中难以完全复现这些差异，仅依靠用户反馈、服务端日志或开发人员手动排查，通常无法回答以下问题：

- 用户在页面中经历了什么，问题发生前执行过哪些关键操作？
- 页面是否能够及时加载并稳定响应，核心性能指标是否满足既定要求？
- 网络请求、脚本执行和业务流程是否出现异常，异常影响了哪些用户与功能？
- 关键业务流程是否按预期完成，产品上线后是否达到性能目标和业务目标？
- 当线上问题无法稳定复现时，是否有足够的数据还原现场并定位原因？

浏览器监控 SDK 的作用，是在不侵入具体业务流程的前提下，持续采集用户使用应用时产生的性能、行为、网络、错误和业务数据，将分散在不同页面、不同时间点的事实连接起来，再经过规范化处理与可靠上报，为监控平台提供可计算、可检索、可关联的数据基础。

它并不是简单地“记录更多日志”，而是为线上应用建立一套统一的可观测机制：系统既能够用数据证明自己运行得足够好，也能够在运行异常时说明问题发生在哪里、为什么发生以及造成了什么影响。

## 2. 要解决的问题

### 2.1 线上运行过程不可见

开发人员通常只能直接观察开发、测试环境中的运行状态。应用交付给真实用户后，用户环境、访问路径和操作过程无法被完整掌握。一旦缺少持续采集的数据，团队就难以判断某次异常究竟来自代码、接口、网络、浏览器环境，还是特定的业务操作。

监控 SDK 需要把线上运行过程中有诊断价值的事实记录下来，包括页面访问与跳转、关键交互、资源和接口请求、性能指标、运行时错误以及业务埋点等，使原本不可见的客户端状态转化为可查询、可分析的数据。

### 2.2 性能目标和业务目标缺乏客观依据

项目是否达到生产要求，不能只依赖主观体验或少量测试结果。对于有明确性能要求、稳定性要求或审计要求的系统，需要持续回收真实环境中的数据，计算性能指标和业务指标，并从用户、页面、版本、设备、网络等维度观察其变化。

监控 SDK 因此需要提供稳定的数据采集入口，使监控平台能够回答：

- 页面加载、渲染和交互性能是否达到目标；
- 请求成功率、错误率和耗时是否处于可接受范围；
- 核心业务流程的到达率、完成率和失败分布是否符合预期；
- 新版本发布后，性能和稳定性是否发生退化；
- 特定用户群体、浏览器或网络环境是否存在集中问题。

### 2.3 异常发生后缺少可追溯的上下文

单条错误信息通常只能说明“哪里报错”，不能解释“为什么报错”。如果没有错误发生前后的页面状态、用户行为、路由变化和网络请求等上下文，线上问题往往难以复现，定位过程只能依赖猜测。

监控 SDK 需要围绕同一次访问或同一条操作链路组织数据，让错误与其发生前后的关键步骤建立关联。这样，监控平台不仅能够发现异常，还能沿着数据链路还原现场，缩小排查范围，提升问题定位和恢复效率。

### 2.4 监控逻辑容易侵入业务并影响应用

浏览器监控通常需要监听全局事件，或者包装 `fetch`、`XMLHttpRequest`、`history` 等浏览器能力。如果缺少统一管理，重复初始化、重复包装、监听器未释放或异常处理不完整，都可能改变原有 API 行为，产生重复数据、内存泄漏，甚至影响正常业务。

因此，SDK 自身必须是可控的：监控能力应当能够安装、启动、停止和释放；对全局对象的修改应可恢复；多次初始化应具备幂等性；SDK 内部异常不得继续向业务传播。监控系统首先要保证自己不会成为新的故障来源。

### 2.5 多种数据来源缺少统一规范

性能、错误、网络、行为和业务事件具有不同的触发方式与原始结构，但在进入上报和分析链路后，它们都会面对相同的问题：如何补充公共上下文、如何校验和格式化、如何控制发送频率、如何处理失败重试，以及如何关联同一次会话中的其他事件。

如果每一种数据都独立实现完整链路，系统会出现大量重复逻辑，数据格式也会逐渐失去一致性。SDK 需要在保留各类数据差异的同时，为它们建立统一的数据模型和处理管线。

## 3. 项目目标

浏览器监控 SDK 的核心目标，是建立从“浏览器端事实产生”到“监控平台可观测”的完整数据链路。

### 3.1 持续采集可计算的数据

SDK 应能够采集性能、错误、网络、行为和业务等不同类型的数据，为性能指标、稳定性指标和业务指标的计算提供原始事实。采集结果需要包含必要的时间、页面、会话、用户、环境和版本信息，以支持后续聚合、筛选和趋势对比。

### 3.2 支撑目标验证与持续观测

通过真实用户数据，团队可以判断系统是否达到预设的性能、稳定性和业务目标，并持续观察版本迭代带来的变化。监控结果既服务于上线后的问题发现，也服务于发布评估、性能治理和业务决策。

### 3.3 建立异常定位与追溯能力

SDK 应保留异常发生时必要的上下文，并使用会话、页面访问或链路标识把相关事件连接起来。团队可以据此还原用户操作路径，识别问题发生的具体阶段，分析根因与影响范围。

### 3.4 以低侵入方式接入业务

SDK 应独立于业务代码运行。通用数据通过浏览器全局能力自动采集，只有具有特定业务含义的数据才由业务方显式埋点。业务接入应保持简单，监控功能的增减不应迫使业务页面大范围修改。

### 3.5 支持监控能力独立演进

新增一种监控数据时，应主要通过增加采集器、适配器或处理模块完成，而不是修改整条监控链路。公共能力由基础模块复用，各类监控能力可以独立开发、测试、启用和停用，从而降低功能迭代的影响范围。

## 4. 设计思想

### 4.1 监控能力与业务逻辑解耦

监控 SDK 作为独立模块接入应用，负责通用事件的自动采集和统一处理；业务代码只在需要表达业务语义时调用公开埋点接口。SDK 不依赖具体页面实现，业务也不需要理解数据上报链路的内部细节。

这种边界能够避免监控逻辑散落在组件和页面中，也使 SDK 可以在多个项目中复用。对现有业务而言，接入监控应当是一项可配置、可关闭、可移除的能力，而不是不可分离的运行依赖。

### 4.2 对浏览器全局能力进行生命周期管理

对全局 API 的监听或包装必须由统一的生命周期控制。每项监控能力都应明确其安装、运行、停止和卸载行为，并保存原始引用，以便在停用 SDK 时恢复环境。

生命周期管理应遵守以下约束：

- **幂等安装**：同一能力多次启动时，不重复包装 API 或注册监听器；
- **可逆释放**：停止监控后移除监听器、定时器和缓存，并恢复被包装的全局能力；
- **行为兼容**：保留原始 API 的参数、返回值、异常和调用上下文；
- **故障隔离**：采集、格式化或上报失败不得影响业务调用；
- **状态可控**：各项能力可以按配置独立启用或停用。

这一设计保证 SDK 能够安全地长期运行，也便于单页应用中的重复挂载、模块热更新以及测试环境下的初始化与清理。

### 4.3 自动采集与业务埋点结合

浏览器提供的通用事实适合自动采集，例如运行时错误、未处理的 Promise 拒绝、页面性能、资源加载、接口请求和路由变化。具有业务含义的事实则应通过显式埋点补充，例如登录成功、订单提交、关键步骤完成或权限校验失败。

两种方式共同组成监控数据来源：自动采集降低接入成本并保证基础覆盖，业务埋点补充领域语义和关键流程。新增页面通常不需要重新搭建监控链路；通用能力自动生效，需要额外观察的业务节点只需增加对应埋点。

### 4.4 以采集器隔离数据来源差异

不同监控数据由独立采集器负责。采集器只关注某类原始事实的获取与基础转换，例如错误采集器处理异常事件，网络采集器处理请求过程，性能采集器读取性能条目，行为采集器记录关键交互。

采集器不直接承担完整的发送逻辑，而是向统一处理管线输出标准事件。由此，新增监控能力时只需实现约定接口并注册到 SDK，无须复制公共的数据补全、缓存和上报代码。

### 4.5 以统一事件模型连接分散事实

所有采集结果在进入公共链路前，都应被转换为统一事件模型。统一不代表抹平差异，而是将公共字段固定下来，将各类事件的特有内容放入对应的数据载荷中。

一个标准事件通常需要表达以下信息：

- 事件标识、事件类型、名称与发生时间；
- 应用、版本、环境与发布信息；
- 页面地址、路由、来源页与页面访问标识；
- 用户标识、会话标识和设备环境；
- 事件特有数据，例如错误堆栈、请求耗时、性能值或业务属性；
- 用于关联、采样、去重和追踪的辅助信息。

统一事件模型使不同来源的数据可以使用同一套处理、存储与查询方式，同时为跨事件关联和指标计算建立稳定的数据契约。

### 4.6 使用统一管线处理和上报数据

标准事件进入公共处理管线后，依次完成上下文补全、数据规范化、过滤、采样、去重、缓存、批量发送和失败处理。采集器与传输模块之间通过稳定接口连接，避免数据来源直接依赖具体上报实现。

整体数据流可以概括为：

```text
浏览器事件 / 业务埋点
          ↓
      独立采集器
          ↓
  标准化与公共上下文补全
          ↓
  过滤 / 采样 / 去重 / 缓存
          ↓
       统一传输层
          ↓
        监控平台
          ↓
  指标计算 / 检索 / 告警 / 追溯
```

通过这条管线，采集方式、数据处理策略和传输方式可以分别演进。例如，更换上报协议不要求修改错误采集器；新增性能指标也不需要重写重试和批量发送逻辑。

### 4.7 按职责进行分层与模块化拆分

SDK 按职责划分为若干相互协作的模块：

| 层次           | 主要职责                                         |
| -------------- | ------------------------------------------------ |
| 接入与配置层   | 提供初始化、配置合并、启停控制和公开埋点接口     |
| 采集层         | 监听浏览器能力与业务事件，获得不同来源的原始数据 |
| 适配与标准化层 | 将原始数据转换为统一事件，补充公共上下文         |
| 处理层         | 完成过滤、采样、去重、聚合、限流和敏感信息处理   |
| 缓存与调度层   | 管理事件队列、批量策略、发送时机与页面卸载场景   |
| 传输层         | 以统一接口完成上报、超时控制、失败重试与降级     |
| 平台消费层     | 负责存储、检索、指标计算、可视化、告警和问题追溯 |

模块之间依赖明确的接口和数据契约，而不是共享隐式状态。某项能力发生变化时，应优先在其所属模块内完成修改，减少对其他模块及业务代码的影响。

## 5. 总体设计方案

浏览器监控 SDK 采用“插件化采集、标准化事件、管线化处理、统一传输”的总体方案。

SDK 初始化时，由核心模块读取配置、创建运行上下文并启动已启用的采集器。采集器监听浏览器事件或接收业务埋点，将获得的原始数据交给适配模块。适配模块生成标准事件并补充应用、页面、用户、会话和环境信息。处理管线随后根据配置执行过滤、采样、去重与数据清洗，将合格事件写入发送队列。调度模块依据数量、时间、页面生命周期和网络状态决定发送时机，传输层最终以统一协议上报至监控平台。

当 SDK 停止或销毁时，核心模块按注册顺序释放采集器与公共资源，移除监听器，清理定时任务，并恢复被包装的浏览器 API。整个过程应保持可重复、可恢复和对业务透明。

该方案的关键价值在于建立稳定边界：

- 对业务侧，提供低成本、低侵入且语义明确的接入方式；
- 对采集侧，允许不同数据类型独立实现和扩展；
- 对处理侧，用统一模型和公共管线保证数据质量；
- 对传输侧，集中处理发送效率、可靠性与异常隔离；
- 对平台侧，输出结构一致、能够关联和计算的数据。

## 6. 设计约束

为了使监控能力在真实生产环境中长期可靠运行，项目设计需要持续遵守以下约束：

1. **不能影响业务正确性**：任何监控逻辑失败，都不应改变业务 API 的既有行为或阻断用户操作。
2. **控制运行开销**：采集频率、监听范围、缓存大小和发送策略需要受控，避免明显增加主线程、内存和网络负担。
3. **保证数据可解释**：每类数据都应具有明确语义、版本和字段约束，指标计算不能依赖含义不稳定的事件。
4. **默认保护敏感信息**：采集范围遵循最小必要原则，对 URL、请求内容、用户输入和身份信息提供过滤、脱敏与禁采机制。
5. **支持按需配置**：业务可以按环境和场景启用采集器、调整采样与上报策略，并控制调试信息。
6. **保证生命周期完整**：所有安装的监听、包装、定时任务和缓存都必须存在对应的释放路径。
7. **保持扩展边界稳定**：新增数据类型通过标准接口接入，避免对核心链路和既有采集器进行非必要修改。

在这些约束下，浏览器监控 SDK 才能同时满足可观测性与工程可靠性的要求：它既要尽可能完整地描述线上事实，也必须克制自身对应用运行的影响。
