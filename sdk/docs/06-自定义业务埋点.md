# 06 · 自定义业务埋点：代码逻辑与完整链路

> 本文只讲**业务主动埋点**这一条通道：从 `monitor.track()` 被调用开始，到数据被服务端接收为止。
> 每一步都标注**代码路径**（文件 + 关键函数/行号），并配一个贯穿全文的示例。
> 相关背景：[03 · Collector 与信封组装](./03-Collector与信封组装.md)、[04 · Processing 加工链路](./04-Processing加工链路.md)、[05 · Transport 发送链路](./05-Transport发送链路.md)。

---

## 〇、一句话概括与调用栈

业务只要写一行：

```ts
monitor.track('checkout.submit', { orderId: 'o-88', amount: 199.9 });
```

SDK 内部实际走过的调用栈是：

| # | 位置 | 代码路径 | 做什么 |
| --- | --- | --- | --- |
| 1 | 公开 API | `src/core/monitor.ts` → `BrowserMonitor.track()` | 运行态门控 |
| 2 | 采集器 | `src/collectors/event/custom/index.ts` → `CustomEventCollector.track()` | 命名规范化、组装 payload |
| 3 | 数据契约 | `protocol/src/schemas.ts` → `CustomEventPayload` | 由共享协议包定义上报结构 |
| 4 | 统一出口 | `src/core/pipeline.ts` → `MonitorPipeline.emit()` | 补齐信封 |
| 5 | 上下文 | `src/context/snapshot.ts` → `ContextManager.snapshotAt()` | 按发生时间补 session/view/runtime/user |
| 6 | 加工 | `src/processing/pipeline.ts` + `src/processing/*` 七个阶段 | 校验、脱敏、去重、采样、限流 |
| 7 | 发送 | `src/transport/flush/index.ts` + `queue` / `batch` / `retry` / `sender` | 入队、切批、重试、发送 |

```text
业务代码
  └─ monitor.track()                         src/core/monitor.ts
       └─ CustomEventCollector.track()       src/collectors/event/custom/index.ts
            └─ MonitorPipeline.emit()       src/core/pipeline.ts
                 ├─ ContextManager.snapshotAt()   src/context/snapshot.ts
                 ├─ ProcessingPipeline.process()  src/processing/pipeline.ts
                 └─ Transport.enqueue()           src/transport/flush/index.ts
                      └─ MemoryQueue → takeBatch → sendWithRetry → HttpSender
```

<u>**最大特点：这条链路不经过 Signal Hub。** 自动采集（性能、路由）需要「浏览器事实 → 信号 → 解释」三层，而业务埋点的调用本身就是事实来源，所以第 2 步直接注入了 `MonitorPipeline`。</u>

## 一、数据契约

### 1.1 输入：`TelemetryDraft`

```ts
// src/core/pipeline.ts（第 33–46 行）
export interface TelemetryDraft<T extends TelemetryPayload = TelemetryPayload> {
  name: string;                 // 事件名
  timestamp: number;            // 发生时间（不是处理时间）
  payload: T;
  correlation?: CorrelationContext;
  context?: TelemetryContext;   // 自定义埋点不传，交给 Pipeline 解析
}
```

### 1.2 领域负载：`CustomEventPayload`

```ts
// protocol/src/schemas.ts（共享协议包）
export interface CustomEventPayload {
  type: 'event';
  name: string;
  source: 'custom';
  properties?: Readonly<Record<string, unknown>>;
}
```

`properties` 用 `Record<string, unknown>` 是刻意的宽松 —— 业务字段千变万化，类型无法枚举；代价是必须由 Processing 的脱敏与体积守卫兜底。

### 1.3 输出：`TelemetryEnvelope`

```ts
// protocol/src/schemas.ts（共享协议包）
export interface TelemetryEnvelope<T extends TelemetryPayload = TelemetryPayload> {
  protocolVersion: '2.0';
  eventId: string;
  type: T['type'];
  name: string;
  occurredAt: number;
  app: AppContextData;
  context: TelemetryContext;
  correlation: CorrelationContext;
  payload: T;
}
```

## 二、代码逐行走读

### 2.1 入口与门控 —— `src/core/monitor.ts`

```190:194:sdk/src/core/monitor.ts
  // 自定义事件上报：非运行态直接丢弃，避免宿主在页面卸载后仍写入内存队列。
  track(name: string, properties?: Readonly<Record<string, unknown>>): void {
    if (!this.lifecycle.isRunning()) return;
    this.customEvents.track(name, properties);
  }
```

`isRunning()` 来自 `src/core/lifecycle.ts`，因此：

| 状态 | `track()` 行为 |
| --- | --- |
| `created`（未 start） | **丢弃** |
| `running` | 正常上报 |
| `stopped` | **丢弃** |
| `destroyed` | **丢弃** |

`customEvents` 在构造期创建，直接持有 Pipeline：

```ts
// src/core/monitor.ts（第 82–84 行）
const processing = createProcessingPipeline(this.options.processing);
const pipeline = new MonitorPipeline(this.context, processing, this.transport);
this.customEvents = new CustomEventCollector(pipeline);
```

注意它**没有** `registry.register(customEvents)` —— 因为它是唯一不需要 install/start/stop/destroy 的采集器（没有全局监听要挂）。

### 2.2 组装草稿 —— `src/collectors/event/custom/index.ts`

```ts
// src/collectors/event/custom/index.ts（完整文件）
export class CustomEventCollector {
  constructor(private readonly emitter: TelemetryEmitter) {}

  track(name: string, properties?: Readonly<Record<string, unknown>>): void {
    const normalizedName = name.trim();                          // ① 名称规范化
    if (!normalizedName) throw new Error('Event name is required.');  // ② 空名抛错

    this.emitter.emit({                                          // ③ 提交草稿
      name: normalizedName,
      timestamp: Date.now(),                                     // ④ 取调用时刻
      payload: {
        type: 'event',
        name: normalizedName,
        source: 'custom',
        ...(properties ? { properties } : {}),                   // ⑤ 无属性时不产生该字段
      },
    });
  }
}
```

逐条解释：

| 标记 | 说明 |
| --- | --- |
| ① | `trim()` 保证 ' checkout.submit ' 与 'checkout.submit' 聚合为同一个事件名 |
| ② | **全 SDK 唯一的抛错点**。其他环节一律「静默丢弃」，但埋点名字为空属于业务编程错误，必须立刻暴露 |
| ③ | `emitter` 就是 `MonitorPipeline`，只暴露 `emit` 一个方法 |
| ④ | 时间戳取**调用时刻**，决定了这条数据归属哪个 View |
| ⑤ | 不传 `properties` 时连字段都不产生，避免上报体里的空对象噪声 |

### 2.3 补齐信封 —— `src/core/pipeline.ts`

```67:89:sdk/src/core/pipeline.ts
  emit<T extends TelemetryPayload>(draft: TelemetryDraft<T>): void {
    const envelope: TelemetryEnvelope<T> = {
      protocolVersion: '2.0',
      eventId: createId('event'),
      type: draft.payload.type,
      name: draft.name,
      occurredAt: draft.timestamp,

      payload: draft.payload,

  }
```

自定义埋点走 `draft.context ?? ...` 的**后半段**（它不传 context）。

### 2.4 上下文补齐 —— `src/context/snapshot.ts`

```74:96:sdk/src/context/snapshot.ts
  snapshotAt(timestamp: number): TelemetryContext {
    let view = this.view.resolveAt(timestamp);
    // History Instrumentation 尚未产生初始信号时，保证首条数据仍有合法 View。
    if (!view) view = this.startView(currentUrl(), timestamp, 'initial').current;
    return this.snapshotForView(view);
  }

  snapshotForView(view: ViewRecord): TelemetryContext {
    const user = this.user.snapshot();
    return Object.freeze({
      sessionId: this.session.snapshot().sessionId,
      viewId: view.viewId,
      url: view.url,
      runtime: this.runtime.snapshot(),
      ...(user ? { user } : {}),
    });
  }
```

业务**不需要**提供任何上下文：`sessionId`、`viewId`、`url`、`runtime`、`user` 全部由 SDK 按调用时刻补齐。

### 2.5 加工（重点：脱敏）—— `src/processing/*`

七个阶段完整说明见 [04 文档](./04-Processing加工链路.md)。对自定义埋点来说，与其他数据类型的差异只有一处：**第 ③ 关 `redact` 会递归处理 `properties`**。

```ts

  // 只有业务自定义事件带任意属性，结构化 payload 字段固定，无需递归
  if (payload.type === 'event' && payload.properties) {
    payload = { ...payload, properties: redactValue(payload.properties, this.keys) };
  }
  ...
}
```

```ts
// src/processing/redact/index.ts（第 9–28 行）
function redactValue(value: unknown, sensitiveKeys: ReadonlySet<string>, depth = 0): unknown {
  if (depth > 5) return '[TRUNCATED]';                                          // 深度截断
  if (Array.isArray(value)) {
    return value.slice(0, 50).map((item) => redactValue(item, sensitiveKeys, depth + 1)); // 长度截断
  }
  if (!isRecord(value)) return value;                                           // 基本类型原样
  const result: Record<string, unknown> = {};
  for (const [key, nested] of Object.entries(value)) {
    result[key] = sensitiveKeys.has(key.toLowerCase())                          // 键名忽略大小写
      ? REDACTED                                                                // 命中即整值替换
      : redactValue(nested, sensitiveKeys, depth + 1);
  }
  return result;
}
```

## 三、完整示例：电商下单埋点

### 3.1 业务侧代码

  app: { name: 'checkout-web', version: '2.3.1', environment: 'production' },
  transport: { dsn: 'https://monitor.example.com/api/v2/ingest/bm_pk_xxx/envelopes' },

    dedupeWindowMs: 1000,
    samplingRate: 1,

// ① 用户身份（可在 start 之前调用）

## 四、业务侧埋点设计建议

### 4.1 命名：`领域.动作`

```text
✅ page.view     checkout.submit    cart.add     video.play
❌ 下单           click1             evt_001      CheckoutSubmit
```

`name` 参与采样键（`sessionId:type:name`）与去重指纹，命名稳定才能保证行为稳定。

### 4.2 `properties` 只放可分析维度

| 该放 | 不该放 |
| --- | --- |
| 枚举：`channel: 'h5'` | 整个表单对象 |
| 业务 ID：`orderId` / `skuId` | 手机、身份证、地址 |
| 数值：`amount` / `itemCount` | DOM 节点、函数、Map / Set |
| 时间字符串 `toISOString()` | `Date` 对象（会变成 `{}`） |

### 4.3 建议在业务侧统一封装

```ts
// src/tracking/index.ts（业务侧自建）
import { monitor } from '@/monitor';

type EventMap = {
  'page.view': { pageId: string; tab?: string };
  'checkout.submit': { orderId: string; channel: 'h5' | 'pc'; amount: number; itemCount: number };
};

export function track<K extends keyof EventMap>(name: K, properties: EventMap[K]): void {
  if (!String(name).trim()) return;   // 兜住 track 会抛错的特性
  monitor.track(name, properties as Record<string, unknown>);
}
```

### 4.4 调用时机

| 场景 | 结果 |
| --- | --- |
| `monitor.start()` 之后 | ✅ |
| `start()` 之前（模块顶层） | ❌ 静默丢弃 |
| `destroy()` 之后 | ❌ 静默丢弃 |
| `pagehide` 里调用 | ⚠️ 可以，但建议配合 `monitor.flush()`；SDK 已订阅 `page.lifecycle` 自动 Beacon 冲刷 |

## 五、五个必须知道的坑

**坑 1：`Date` / `Map` / `Set` / class 实例 / DOM 节点会变成 `{}`**

`isRecord`（`src/shared/type-guards/index.ts`）只判断 `typeof value === 'object'`，而 `Object.entries(new Date())` 返回空数组：

```ts
monitor.track('order.paid', { paidAt: new Date() });
// → 到服务端变成 { "paidAt": {} }
```

正确写法：`{ paidAt: new Date().toISOString() }`

**坑 2：1 秒内同名同参会被去重**

指纹包含 `payload`，不含 `timestamp` / `eventId`：

```ts
monitor.track('cart.add', { skuId: 'A1' });   // 通过
monitor.track('cart.add', { skuId: 'A1' });   // 800ms 后 → 被 dedupe 丢弃
```

要保留，就在 `properties` 里加入区分维度（如 `clickIndex`），或调大/关闭 `dedupeWindowMs`。

**坑 3：采样是按 `name` 整体决定的**

采样键 `sessionId:type:name`。某次会话里 `checkout.submit` 若未命中采样，这次会话里**所有**该类事件都不上报。关键漏斗事件建议全量采。

**坑 4：限流额度全局共享**

`rateLimit` 默认 120 条 / 60 秒，**所有事件类型共用**。高频埋点（滚动、鼠标移动）刷满额度会挤掉关键埋点。

**坑 5：循环引用不会炸管道，但数据被截断**

`redact` 深度上限 5 先把结构展开成有限深度（`[TRUNCATED]` 收尾），因此后续 `dedupe` 的 `JSON.stringify` 不会抛错 —— 但你拿不到完整数据。

## 六、数据没上报？排查顺序

| 现象 | 原因 | 检查点 |
| --- | --- | --- |
| 一条都没有 | 未 `start()` | `monitor.start()` 是否执行 |
| 一条都没有 | DSN 错 | `transport.dsn`、跨域/被拦截 |
| 部分缺失 | 被去重 | 同名同参是否 1s 内重复 |
| 部分缺失 | 被采样 | `samplingRate < 1`，键为 `sessionId:type:name` |
| 部分缺失 | 被限流 | 60s 内总事件数是否超 `maxEvents` |
| 部分缺失 | URL 被排除 | `processing.excludeUrls` 是否命中 |
| 字段变了 | 被脱敏 | 是否为 `[REDACTED]` / `[TRUNCATED]` |
| 字段变 `{}` | 传了非纯对象 | `Date` / `Map` / DOM 节点需先转基本类型 |
| 抛异常 | `track('')` | 业务封装里做空名保护 |

联调时可用：

```ts
monitor.getCapabilities();   // 环境支持哪些指标
void monitor.flush();        // 强制冲刷，立即看到数据
```

> `getQueueSize()` / `getDroppedCount()` 定义在 `Transport` 上，未通过 `Monitor` 接口暴露；需要观测队列丢弃时需扩展 `Monitor` 接口。

## 七、小结

| 关注点 | 结论 | 代码路径 |
| --- | --- | --- |
| 入口 | `monitor.track(name, properties)`，非运行态静默丢弃 | `src/core/monitor.ts` |
| 名称 | `trim` 后为空**抛错**（全 SDK 唯一抛错点） | `src/collectors/event/custom/index.ts` |
| payload | `{ type:'event', name, source:'custom', properties? }` | `protocol/src/schemas.ts` |
| 上下文 | 业务无需提供，由 `snapshotAt(timestamp)` 反查 | `src/context/snapshot.ts` |
| 脱敏 | **唯一**会被递归脱敏的 payload；深度 5、数组 50 | `src/processing/redact/index.ts` |
| 去重 | 指纹含 payload，1s 内同名同参会被丢 | `src/processing/dedupe/index.ts` |
| 采样 | 按 `sessionId:type:name` 稳定采样 | `src/processing/sampling/index.ts` |
| 上报 | 与性能数据共用同一条 Transport 链路 | `src/transport/*` |

**一句话**：自定义埋点业务侧只需一行 `track`，正确性取决于三件事 —— **在 `start()` 之后调用**、**`properties` 只放基本类型与可分析维度**、**理解去重/采样/限流的静默丢弃语义**；而脱敏与上下文补齐由 SDK 统一兜住，业务不需要也不应自己处理。
