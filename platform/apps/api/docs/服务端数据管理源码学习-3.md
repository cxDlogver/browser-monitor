# 服务端数据管理源码学习-3

> **学习目标**：在前两篇已经建立 PostgreSQL、SQL、Schema、Constraint、Index、Transaction 与 Concurrency Control 的基础上，继续进入 Time-Series Data Management（时序数据管理）。这一篇不把 TimescaleDB 当成一个孤立产品来背 API，而是先回答“为什么监控数据和普通业务表不同、为什么时间会成为第一查询维度、为什么持续写入会迫使系统引入分区、预聚合和生命周期策略”，再结合 Browser Monitor 当前源码逐步理解 Hypertable、Chunk、time_bucket、Continuous Aggregate、Hierarchical Rollup、Percentile / HyperLogLog、Compression、Retention 与查询路由。
>
> **分析范围**：项目事实以当前 browser-monitor/platform 源码为准；TimescaleDB 通用知识以 Tiger Data / TimescaleDB 官方资料为主要依据。本文会严格区分“当前仓库已经实现的能力”“TimescaleDB 的通用能力”“2026 年官方产品演进方向”。
>
> **与前两篇的关系**：
>
> - 服务端数据管理源码学习.md：Database → Connection → SQL → Schema / Drizzle → Constraint → Index。
> - 服务端数据管理源码学习-2.md：Transaction → Concurrency Control。
> - 本文：Time-Series Data → TimescaleDB → Hypertable → Continuous Aggregate → Rollup → Data Lifecycle。
>
> **与 Redis 文档的关系**：PostgreSQL / TimescaleDB 继续承担长期权威数据和时序历史；Redis 主要承担 Runtime State、Cache、Coordination 与短生命周期状态。本文重点解决“持续增长的历史数据怎样长期保存和高效查询”，而不是运行时缓存问题。

## 9. 时序数据管理从“持续增长的数据为什么不能只按普通业务表理解”开始

前两篇已经建立：

~~~text
PostgreSQL
    ↓
长期保存业务事实
    ↓
Table / Row / Column
    ↓
Constraint
    ↓
Index
    ↓
Transaction
    ↓
Concurrency Control
~~~

这些能力已经足够处理很多典型业务数据：

~~~text
users

projects

project_members

account_tokens

project_invitations
~~~

它们虽然也会增长，但核心访问模式通常是：

~~~text
根据 ID 找一条

根据 User 找相关 Project

根据 Token 找 Session

根据状态筛选业务记录
~~~

Browser Monitor 还有另一类完全不同的数据：

~~~text
telemetry_events

performance_samples

view_records

custom_event_samples

custom_signal_samples

custom_metric_samples
~~~

这类数据具有四个共同特征：

~~~text
持续产生
    ↓
天然带时间
    ↓
数量增长很快
    ↓
查询经常围绕时间范围和聚合
~~~

因此数据管理问题从：

~~~text
怎样保存一条业务 Row
~~~

进一步变成：

~~~text
怎样长期管理一条持续增长的时间轴
~~~

### 【Time-Series Data 的核心不是“有 timestamp”，而是时间决定了数据组织和查询方式】

很多普通业务表也有：

~~~text
created_at
updated_at
~~~

但不能因此全部称为时序数据。

真正的 Time-Series Workload 通常满足：

~~~text
Time
    ↓
是主要排序维度

Time Range
    ↓
是主要查询条件

New Data
    ↓
持续追加到时间轴尾部

Historical Data
    ↓
越来越少被单条修改

Analytics
    ↓
经常按时间 Bucket 聚合
~~~

例如 Browser Monitor 查询性能：

~~~text
Project P001

最近 24 小时

每一分钟

LCP
p50 / p75 / p95
Sample Count
Good / Poor Count
~~~

这里真正的查询结构是：

~~~text
Entity Scope
    +
Time Range
    +
Time Bucket
    +
Aggregation
~~~

而不是普通：

~~~text
Primary Key Lookup
~~~

#### <u>1. Time-Series Data 通常是 Append-heavy，而不是 Update-heavy</u>

普通业务数据：

~~~text
projects

同一 Row
可能被多次 UPDATE
~~~

而监控 Event：

~~~text
10:00:01
10:00:02
10:00:03
...
~~~

更多是：

~~~text
New Time
    ↓
New Row
~~~

形成：

~~~text
Append-heavy
~~~

当前 telemetry_events 就是典型：

~~~text
每次 SDK 上报
    ↓
追加新 Event
~~~

虽然 performance_samples 因 Web Vitals sequence 会修订同一个 Sample，但整体数据流仍然是：

~~~text
持续新增新的时间点 / Sample
~~~

#### <u>2. Time-Series Data 的查询通常天然带时间边界</u>

例如：

~~~sql
WHERE project_id = $1
  AND observed_at >= $2
  AND observed_at < $3
~~~

这和：

~~~sql
WHERE id = $1
~~~

是两种完全不同的访问模式。

所以时序数据设计时必须把：

~~~text
Time Column
~~~

提升成：

~~~text
Physical Data Organization
+
Query Planning
+
Lifecycle Management
~~~

的核心维度。

#### <u>3. Time-Series Data 会持续增长，所以“永远保存全部明细”本身就是一个设计决策</u>

假设：

~~~text
100 events / second
~~~

一天：

~~~text
8,640,000 rows
~~~

如果：

~~~text
1000 events / second
~~~

一天：

~~~text
86,400,000 rows
~~~

持续半年以后：

~~~text
Row Count
Storage
Index
Vacuum
Query Cost
Backup
~~~

都会继续增长。

因此 Time-Series Data Management 必须从一开始就回答：

~~~text
Raw Data 保留多久？

历史是否需要降采样？

什么时候压缩？

什么时候删除？

长期查询需要什么粒度？
~~~

这也是为什么：

~~~text
Retention
Compression
Rollup
~~~

不是“数据库优化小技巧”，而是时序系统的数据生命周期设计。

### 【当前 Browser Monitor 已经把关系型业务表和时序表放在同一个 PostgreSQL / TimescaleDB 实例中】

当前 Migration 首先启用：

~~~sql
CREATE EXTENSION IF NOT EXISTS timescaledb;
CREATE EXTENSION IF NOT EXISTS timescaledb_toolkit;
~~~

因此当前架构不是：

~~~text
PostgreSQL Server
+
另一个独立 TimescaleDB Server
~~~

而是：

~~~text
PostgreSQL
    +
TimescaleDB Extension
    +
Timescale Toolkit
~~~

TimescaleDB 本质上是 PostgreSQL Extension，所以应用仍然继续使用：

~~~text
PostgreSQL Protocol

pg Driver

Connection Pool

SQL

Transaction
~~~

而在 PostgreSQL 之上额外得到：

~~~text
Hypertable
Chunk
time_bucket
Continuous Aggregate
Compression / Columnstore
Retention Policy
Time-series Hyperfunctions
~~~

这也是为什么前两篇 PostgreSQL 基础并没有失效。

相反：

> **TimescaleDB 是在 PostgreSQL 数据管理能力之上，为 Time-Series / Analytics Workload 增加新的物理组织、聚合和生命周期能力。**

### 【当前项目中的时序数据可以按 Raw、Projected 与 Aggregate 三层理解】

当前不是只有一张 telemetry_events。

完整链路：

~~~text
SDK Event
    ↓
Raw Event
telemetry_events
    ↓
Worker
    ↓
Domain Projection
performance_samples
view_records
custom_signal_samples
custom_metric_samples
    ↓
Continuous Aggregate
*_rollup_1m
    ↓
Hierarchical Rollup
*_rollup_1h
~~~

因此当前 Data Model 实际已经形成：

~~~text
Raw Layer
    ↓
保留原始事实与追溯能力

Projection Layer
    ↓
把协议 Event 转换成领域查询模型

Aggregate Layer
    ↓
预计算长期分析结果
~~~

这三层承担完全不同的数据职责。

## 10. Hypertable 通过时间分区把一张逻辑表拆成多个可管理 Chunk

如果只使用普通 PostgreSQL Table：

~~~text
performance_samples
    ↓
1 million rows
    ↓
100 million rows
    ↓
1 billion rows
~~~

逻辑上仍然是一张越来越大的表。

Index 可以优化访问路径，但它不能改变一个事实：

~~~text
所有历史数据
仍然属于同一个不断增长的数据集合
~~~

Time-Series Workload 更适合：

~~~text
按照时间范围
把数据拆成多个 Partition
~~~

TimescaleDB 对这一模型的核心抽象就是：

~~~text
Hypertable
~~~

### 【Hypertable 对应用表现为一张 Table，内部按时间管理多个 Chunk】

当前源码：

~~~sql
CREATE TABLE telemetry_events (
  ...
  occurred_at timestamptz NOT NULL,
  ...
);

SELECT create_hypertable(
  'telemetry_events',
  'occurred_at',
  if_not_exists => TRUE
);
~~~

从应用角度仍然：

~~~sql
INSERT INTO telemetry_events ...

SELECT ...
FROM telemetry_events
WHERE ...
~~~

应用不需要手动知道：

~~~text
chunk_1
chunk_2
chunk_3
~~~

TimescaleDB 在内部把逻辑 Hypertable 切成多个时间 Chunk。

可以理解成：

~~~text
telemetry_events
Logical Hypertable
        │
        ├── Chunk A
        │   旧时间范围
        │
        ├── Chunk B
        │   中间时间范围
        │
        └── Chunk C
            最近时间范围
~~~

所以：

~~~text
Hypertable
    ↓
Application-facing Logical Table

Chunk
    ↓
Physical Time Partition
~~~

需要区分。

### 【Chunk 让查询可以排除完全无关的历史时间范围】

假设：

~~~text
Database 中有 180 天数据
~~~

查询：

~~~text
最近 1 小时
~~~

如果能够根据：

~~~text
observed_at
~~~

判断只有最新几个 Chunk 与请求时间范围重叠，那么 Planner 可以：

~~~text
Prune Old Chunks
    ↓
只扫描相关时间分区
~~~

这就是时序分区的核心收益之一。

它不是：

~~~text
让一条 Row 的 GET 变快
~~~

而是：

~~~text
让随着历史无限增长的数据集
仍然能够把查询限制在相关时间范围
~~~

### 【当前项目已经把多张持续增长的表转换成 Hypertable】

0001_platform.sql 中包括：

~~~text
telemetry_events
    time = occurred_at

performance_samples
    time = observed_at

view_records
    time = started_at

custom_event_samples
    time = occurred_at
~~~

0005_custom_observability.sql 又增加：

~~~text
custom_signal_samples
    time = occurred_at

custom_metric_samples
    time = occurred_at
~~~

所以当前 TimescaleDB 并不是：

~~~text
只优化一张性能表
~~~

而是形成了一层统一的：

~~~text
Time-Series Storage Layer
~~~

### 【时序表中的 Primary Key 通常需要把时间列纳入唯一性设计】

当前 telemetry_events：

~~~sql
PRIMARY KEY (
  project_id,
  event_id,
  occurred_at
)
~~~

performance_samples：

~~~sql
PRIMARY KEY (
  project_id,
  sample_id,
  observed_at
)
~~~

当前 Ingestion 源码专门说明：

~~~text
Timescale unique indexes
must include the partitioning timestamp
~~~

但协议幂等定义是：

~~~text
eventId
~~~

而不是：

~~~text
eventId + occurredAt
~~~

所以项目进一步使用：

~~~text
Advisory Lock
+
Existing Event Query
+
Insert
~~~

补足协议级幂等语义。

这里可以第一次看到：

> **Physical Partition Rule 和 Business Uniqueness Rule 不一定完全相同。**

数据模型必须同时处理：

~~~text
TimescaleDB Physical Constraint

和

Application Business Invariant
~~~

### 【Hypertable 仍然需要 Index，分区不能替代索引】

当前：

~~~sql
CREATE INDEX telemetry_project_time_idx
ON telemetry_events(
  project_id,
  occurred_at DESC
);
~~~

以及：

~~~sql
CREATE INDEX performance_project_time_idx
ON performance_samples(
  project_id,
  observed_at DESC
);
~~~

还存在：

~~~sql
CREATE INDEX performance_project_route_time_idx
ON performance_samples(
  project_id,
  route_name,
  observed_at DESC
);
~~~

这些设计说明：

~~~text
Hypertable
    ↓
先限制 Time Partition

Index
    ↓
再在相关 Chunk 中
寻找 Project / Route / Time
~~~

两层可以共同工作。

所以：

~~~text
Partition
≠
Index
~~~

更完整地说：

~~~text
Chunk Pruning
    ↓
减少需要访问的物理分区

Index Access
    ↓
减少每个相关分区内部需要扫描的数据
~~~

### 【当前项目没有显式指定 Chunk Interval，因此不能从源码假设固定分区大小】

当前 create_hypertable：

~~~sql
SELECT create_hypertable(
  'performance_samples',
  'observed_at',
  if_not_exists => TRUE
);
~~~

没有显式写：

~~~text
chunk_time_interval
~~~

因此当前仓库可以确认：

~~~text
按时间创建 Hypertable
~~~

但不能仅凭源码确认：

~~~text
每个 Chunk 一定是 1 天
或 7 天
~~~

实际 Chunk Interval 需要结合：

~~~text
实际 TimescaleDB Version
默认配置
运行环境
~~~

检查。

当前 Docker 使用：

~~~text
timescale/timescaledb-ha:pg17
~~~

也没有在 Migration 中锁定 TimescaleDB Extension 版本。

因此如果未来进行生产容量治理，应该把：

~~~text
TimescaleDB Version
+
Chunk Interval
+
Ingest Rate
+
Chunk Size
~~~

一起纳入显式配置和验证。

## 11. 时序写入模型需要同时管理 Raw Event、Projection 与可修订 Sample

普通日志系统常常只有：

~~~text
Event
    ↓
Append
~~~

但 Browser Monitor 的数据链更复杂。

当前：

~~~text
SDK
    ↓
telemetry_events
    ↓
Outbox
    ↓
Worker
    ↓
performance_samples
view_records
custom_signal_samples
custom_metric_samples
~~~

这意味着当前系统不是单纯的 Event Storage，而是形成：

~~~text
Raw Telemetry
    ↓
Traceability

Domain Projection
    ↓
Analytics Query Model
~~~

这里不要直接把项目定义成完整 Event Sourcing Architecture，因为当前系统并没有把全部业务状态都通过 Event Replay 构建。

### 【Raw Event 保存客户端实际发送过什么】

telemetry_events 保存：

~~~text
event_id
occurred_at
received_at
type
name
environment
app_version
session_id
view_id
route_name
event jsonb
processed_at
~~~

它更接近：

~~~text
Raw Fact Layer
~~~

作用包括：

~~~text
审计
问题追踪
原始事件检索
Worker Processing Source
~~~

### 【Projection 将协议 Event 转换成面向查询的领域模型】

例如：

~~~text
Performance Event
    ↓
performance_samples

View Event
    ↓
view_records

Custom Signal
    ↓
custom_signal_samples

Custom Metric
    ↓
custom_metric_samples
~~~

如果所有查询都直接解析 telemetry_events.event JSONB，那么每一次 Analytics 都需要重新理解：

~~~text
协议结构
Event Type
Value
Lifecycle
Sequence
~~~

所以 Worker 提前把 Raw Event 变成：

~~~text
Domain-specific Tables
~~~

本质上是在做：

~~~text
Write-time Processing
    ↓
换取
Read-time Simplicity
~~~

### 【Performance Sample 展示了时序数据不一定永远只 Append】

performance_samples 有：

~~~text
sample_id
sequence
state
last_updated_at
~~~

同一个 Web Vital Sample：

~~~text
sequence 0
    ↓
sequence 1
    ↓
sequence 2 final
~~~

会对同一领域 Sample 进行修订。

所以：

~~~text
Time-Series
≠
只能 INSERT
~~~

更准确：

~~~text
大部分新时间点持续 Append

但某些业务模型
允许对最近时间范围进行 UPDATE / Finalize
~~~

这会直接影响后面的：

~~~text
Continuous Aggregate Refresh Window
Compression Timing
Finalization Strategy
~~~

因为最近数据仍然可能变化，而更旧数据通常更稳定。

### 【当前系统已经形成 Hot Recent Data 与 Stable Historical Data 的自然分界】

例如：

~~~text
Performance Sample

刚上报
    ↓
provisional

后续 sequence
    ↓
更新

最终
    ↓
final

时间继续过去
    ↓
基本不会再修改
~~~

因此整个时序生命周期天然可以理解成：

~~~text
Recent Hot Data
    ↓
仍可能变化
    ↓
Row-oriented / Frequent Refresh

Historical Stable Data
    ↓
很少变化
    ↓
Compression / Rollup / Retention
~~~

这也是后续 Compression 与 Continuous Aggregate 策略能够成立的业务基础。

## 12. Time Range Query 与 time_bucket 把原始时间轴转换成可分析的时间窗口

保存大量时序数据只是第一步。

真正的监控产品需要回答：

~~~text
最近 1 小时 LCP 怎么变化？

过去 7 天每天访问量是多少？

过去 30 天 p75 是否恶化？

哪个 Route 的 Poor Rate 更高？
~~~

这类问题具有统一结构：

~~~text
Time Range
+
Dimensions
+
Aggregation
~~~

### 【Time Range 是 Analytics Query 的第一层过滤边界】

当前 Analytics 输入：

~~~text
from
to
environment
version
routeName
metric
~~~

服务端默认：

~~~text
to = now

from = to - 24 hours
~~~

并限制最早查询范围约为：

~~~text
180 days
~~~

因此查询不是：

~~~text
SELECT all history
~~~

而是：

~~~text
先定义 Query Window
    ↓
再在时间窗口内做计算
~~~

这和 TimescaleDB 的 Chunk Pruning 模型天然一致。

### 【time_bucket 把连续时间轴转换成固定粒度 Bucket】

当前：

~~~sql
time_bucket(
  INTERVAL '1 minute',
  observed_at
)
~~~

可以理解：

~~~text
10:00:01
10:00:15
10:00:49
    ↓
10:00 Bucket

10:01:03
10:01:30
    ↓
10:01 Bucket
~~~

于是：

~~~text
Continuous Timeline
    ↓
Discrete Time Buckets
~~~

后续才能计算：

~~~text
COUNT
AVG
MIN
MAX
Percentile
Good Rate
Distinct Session
~~~

### 【Bucket Size 决定查询分辨率与结果规模】

如果查询 24 小时：

~~~text
1-minute Bucket
    ↓
1440 points
~~~

如果查询 180 天仍然返回 1-minute Bucket：

~~~text
259,200 points
~~~

不仅数据库聚合成本高：

~~~text
API Response
Network
Frontend Chart
~~~

也会变得很重。

所以长期趋势通常需要：

~~~text
Time Range 越大
    ↓
Bucket 越粗
~~~

这就是后面：

~~~text
1 minute Rollup
    ↓
1 hour Rollup
~~~

的意义。

### 【近期明细查询可以直接使用精确聚合】

当前最近 29 天的 Performance 查询直接从 performance_samples 计算：

~~~sql
count(*)

avg(value)

percentile_cont(0.50)
percentile_cont(0.75)
percentile_cont(0.90)
percentile_cont(0.95)
~~~

这属于：

~~~text
Query-time Exact Aggregation
~~~

优点：

~~~text
直接基于明细
口径精确
能灵活增加过滤条件
~~~

代价：

~~~text
数据越多
Query-time 计算越重
~~~

因此它适合：

~~~text
Recent Window
~~~

而不适合无限历史。

### 【原始事件列表使用 Cursor Pagination，而不是 Offset Pagination】

Raw Event 查询是另一种时序访问模式：

~~~text
按时间倒序
逐页查看明细
~~~

当前使用：

~~~text
(occurred_at, event_id)
~~~

作为稳定 Cursor。

下一页：

~~~sql
WHERE (
  occurred_at,
  event_id
) < (
  :cursorOccurredAt,
  :cursorEventId
)
~~~

这比：

~~~text
OFFSET 100000
~~~

更适合持续新增的时序表。

因此 Time-Series Query 不只有：

~~~text
Aggregate Query
~~~

还包括：

~~~text
Time-ordered Detail Scan
~~~

两种查询模型需要分别设计。
