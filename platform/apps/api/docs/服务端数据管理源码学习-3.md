# 服务端数据管理源码学习-3

> **学习目标**：在前两篇已经建立 PostgreSQL、SQL、Schema、Constraint、Index、Transaction 与 Concurrency Control 的基础上，继续进入 Time-Series Data Management（时序数据管理）。这一篇不把 TimescaleDB 当成一个孤立产品来背 API，而是先回答“为什么监控数据和普通业务表不同、为什么时间会成为第一查询维度、为什么持续写入会迫使系统引入分区、预聚合和生命周期策略”，再结合 Browser Monitor 当前源码逐步理解 Hypertable、Chunk、time_bucket、Continuous Aggregate、Hierarchical Rollup、Percentile / HyperLogLog、Compression、Retention 与查询路由。
>
> **分析范围**：项目事实以当前 browser-monitor/platform 源码为准；TimescaleDB 通用知识以 Tiger Data / TimescaleDB 官方资料为主要依据。本文会严格区分“当前仓库已经实现的能力”“TimescaleDB 的通用能力”“2026 年官方产品演进方向”。
>
> **与前两篇的关系**：
>
> - 服务端数据管理源码学习.md：Database → Connection → SQL → Schema / Drizzle → Constraint → Index。
> - 服务端数据管理源码学习-2.md：Transaction → Concurrency Control。
> - 本文：Time-Series Data → TimescaleDB → Hypertable → Continuous Aggregate → Rollup → Data Lifecycle。
>
> **与 Redis 文档的关系**：PostgreSQL / TimescaleDB 继续承担长期权威数据和时序历史；Redis 主要承担 Runtime State、Cache、Coordination 与短生命周期状态。本文重点解决“持续增长的历史数据怎样长期保存和高效查询”，而不是运行时缓存问题。

## 9. 时序数据管理从“持续增长的数据为什么不能只按普通业务表理解”开始

前两篇已经建立：

~~~text
PostgreSQL
    ↓
长期保存业务事实
    ↓
Table / Row / Column
    ↓
Constraint
    ↓
Index
    ↓
Transaction
    ↓
Concurrency Control
~~~

这些能力已经足够处理很多典型业务数据：

~~~text
users

projects

project_members

account_tokens

project_invitations
~~~

它们虽然也会增长，但核心访问模式通常是：

~~~text
根据 ID 找一条

根据 User 找相关 Project

根据 Token 找 Session

根据状态筛选业务记录
~~~

Browser Monitor 还有另一类完全不同的数据：

~~~text
telemetry_events

performance_samples

view_records

custom_event_samples

custom_signal_samples

custom_metric_samples
~~~

这类数据具有四个共同特征：

~~~text
持续产生
    ↓
天然带时间
    ↓
数量增长很快
    ↓
查询经常围绕时间范围和聚合
~~~

因此数据管理问题从：

~~~text
怎样保存一条业务 Row
~~~

进一步变成：

~~~text
怎样长期管理一条持续增长的时间轴
~~~

### 【Time-Series Data 的核心不是“有 timestamp”，而是时间决定了数据组织和查询方式】

很多普通业务表也有：

~~~text
created_at
updated_at
~~~

但不能因此全部称为时序数据。

真正的 Time-Series Workload 通常满足：

~~~text
Time
    ↓
是主要排序维度

Time Range
    ↓
是主要查询条件

New Data
    ↓
持续追加到时间轴尾部

Historical Data
    ↓
越来越少被单条修改

Analytics
    ↓
经常按时间 Bucket 聚合
~~~

例如 Browser Monitor 查询性能：

~~~text
Project P001

最近 24 小时

每一分钟

LCP
p50 / p75 / p95
Sample Count
Good / Poor Count
~~~

这里真正的查询结构是：

~~~text
Entity Scope
    +
Time Range
    +
Time Bucket
    +
Aggregation
~~~

而不是普通：

~~~text
Primary Key Lookup
~~~

#### <u>1. Time-Series Data 通常是 Append-heavy，而不是 Update-heavy</u>

普通业务数据：

~~~text
projects

同一 Row
可能被多次 UPDATE
~~~

而监控 Event：

~~~text
10:00:01
10:00:02
10:00:03
...
~~~

更多是：

~~~text
New Time
    ↓
New Row
~~~

形成：

~~~text
Append-heavy
~~~

当前 telemetry_events 就是典型：

~~~text
每次 SDK 上报
    ↓
追加新 Event
~~~

虽然 performance_samples 因 Web Vitals sequence 会修订同一个 Sample，但整体数据流仍然是：

~~~text
持续新增新的时间点 / Sample
~~~

#### <u>2. Time-Series Data 的查询通常天然带时间边界</u>

例如：

~~~sql
WHERE project_id = $1
  AND observed_at >= $2
  AND observed_at < $3
~~~

这和：

~~~sql
WHERE id = $1
~~~

是两种完全不同的访问模式。

所以时序数据设计时必须把：

~~~text
Time Column
~~~

提升成：

~~~text
Physical Data Organization
+
Query Planning
+
Lifecycle Management
~~~

的核心维度。

#### <u>3. Time-Series Data 会持续增长，所以“永远保存全部明细”本身就是一个设计决策</u>

假设：

~~~text
100 events / second
~~~

一天：

~~~text
8,640,000 rows
~~~

如果：

~~~text
1000 events / second
~~~

一天：

~~~text
86,400,000 rows
~~~

持续半年以后：

~~~text
Row Count
Storage
Index
Vacuum
Query Cost
Backup
~~~

都会继续增长。

因此 Time-Series Data Management 必须从一开始就回答：

~~~text
Raw Data 保留多久？

历史是否需要降采样？

什么时候压缩？

什么时候删除？

长期查询需要什么粒度？
~~~

这也是为什么：

~~~text
Retention
Compression
Rollup
~~~

不是“数据库优化小技巧”，而是时序系统的数据生命周期设计。

### 【当前 Browser Monitor 已经把关系型业务表和时序表放在同一个 PostgreSQL / TimescaleDB 实例中】

当前 Migration 首先启用：

~~~sql
CREATE EXTENSION IF NOT EXISTS timescaledb;
CREATE EXTENSION IF NOT EXISTS timescaledb_toolkit;
~~~

因此当前架构不是：

~~~text
PostgreSQL Server
+
另一个独立 TimescaleDB Server
~~~

而是：

~~~text
PostgreSQL
    +
TimescaleDB Extension
    +
Timescale Toolkit
~~~

TimescaleDB 本质上是 PostgreSQL Extension，所以应用仍然继续使用：

~~~text
PostgreSQL Protocol

pg Driver

Connection Pool

SQL

Transaction
~~~

而在 PostgreSQL 之上额外得到：

~~~text
Hypertable
Chunk
time_bucket
Continuous Aggregate
Compression / Columnstore
Retention Policy
Time-series Hyperfunctions
~~~

这也是为什么前两篇 PostgreSQL 基础并没有失效。

相反：

> **TimescaleDB 是在 PostgreSQL 数据管理能力之上，为 Time-Series / Analytics Workload 增加新的物理组织、聚合和生命周期能力。**

### 【当前项目中的时序数据可以按 Raw、Projected 与 Aggregate 三层理解】

当前不是只有一张 telemetry_events。

完整链路：

~~~text
SDK Event
    ↓
Raw Event
telemetry_events
    ↓
Worker
    ↓
Domain Projection
performance_samples
view_records
custom_signal_samples
custom_metric_samples
    ↓
Continuous Aggregate
*_rollup_1m
    ↓
Hierarchical Rollup
*_rollup_1h
~~~

因此当前 Data Model 实际已经形成：

~~~text
Raw Layer
    ↓
保留原始事实与追溯能力

Projection Layer
    ↓
把协议 Event 转换成领域查询模型

Aggregate Layer
    ↓
预计算长期分析结果
~~~

这三层承担完全不同的数据职责。

## 10. Hypertable 通过时间分区把一张逻辑表拆成多个可管理 Chunk

如果只使用普通 PostgreSQL Table：

~~~text
performance_samples
    ↓
1 million rows
    ↓
100 million rows
    ↓
1 billion rows
~~~

逻辑上仍然是一张越来越大的表。

Index 可以优化访问路径，但它不能改变一个事实：

~~~text
所有历史数据
仍然属于同一个不断增长的数据集合
~~~

Time-Series Workload 更适合：

~~~text
按照时间范围
把数据拆成多个 Partition
~~~

TimescaleDB 对这一模型的核心抽象就是：

~~~text
Hypertable
~~~

### 【Hypertable 对应用表现为一张 Table，内部按时间管理多个 Chunk】

当前源码：

~~~sql
CREATE TABLE telemetry_events (
  ...
  occurred_at timestamptz NOT NULL,
  ...
);

SELECT create_hypertable(
  'telemetry_events',
  'occurred_at',
  if_not_exists => TRUE
);
~~~

从应用角度仍然：

~~~sql
INSERT INTO telemetry_events ...

SELECT ...
FROM telemetry_events
WHERE ...
~~~

应用不需要手动知道：

~~~text
chunk_1
chunk_2
chunk_3
~~~

TimescaleDB 在内部把逻辑 Hypertable 切成多个时间 Chunk。

可以理解成：

~~~text
telemetry_events
Logical Hypertable
        │
        ├── Chunk A
        │   旧时间范围
        │
        ├── Chunk B
        │   中间时间范围
        │
        └── Chunk C
            最近时间范围
~~~

所以：

~~~text
Hypertable
    ↓
Application-facing Logical Table

Chunk
    ↓
Physical Time Partition
~~~

需要区分。

### 【Chunk 让查询可以排除完全无关的历史时间范围】

假设：

~~~text
Database 中有 180 天数据
~~~

查询：

~~~text
最近 1 小时
~~~

如果能够根据：

~~~text
observed_at
~~~

判断只有最新几个 Chunk 与请求时间范围重叠，那么 Planner 可以：

~~~text
Prune Old Chunks
    ↓
只扫描相关时间分区
~~~

这就是时序分区的核心收益之一。

它不是：

~~~text
让一条 Row 的 GET 变快
~~~

而是：

~~~text
让随着历史无限增长的数据集
仍然能够把查询限制在相关时间范围
~~~

### 【当前项目已经把多张持续增长的表转换成 Hypertable】

0001_platform.sql 中包括：

~~~text
telemetry_events
    time = occurred_at

performance_samples
    time = observed_at

view_records
    time = started_at

custom_event_samples
    time = occurred_at
~~~

0005_custom_observability.sql 又增加：

~~~text
custom_signal_samples
    time = occurred_at

custom_metric_samples
    time = occurred_at
~~~

所以当前 TimescaleDB 并不是：

~~~text
只优化一张性能表
~~~

而是形成了一层统一的：

~~~text
Time-Series Storage Layer
~~~

### 【时序表中的 Primary Key 通常需要把时间列纳入唯一性设计】

当前 telemetry_events：

~~~sql
PRIMARY KEY (
  project_id,
  event_id,
  occurred_at
)
~~~

performance_samples：

~~~sql
PRIMARY KEY (
  project_id,
  sample_id,
  observed_at
)
~~~

当前 Ingestion 源码专门说明：

~~~text
Timescale unique indexes
must include the partitioning timestamp
~~~

但协议幂等定义是：

~~~text
eventId
~~~

而不是：

~~~text
eventId + occurredAt
~~~

所以项目进一步使用：

~~~text
Advisory Lock
+
Existing Event Query
+
Insert
~~~

补足协议级幂等语义。

这里可以第一次看到：

> **Physical Partition Rule 和 Business Uniqueness Rule 不一定完全相同。**

数据模型必须同时处理：

~~~text
TimescaleDB Physical Constraint

和

Application Business Invariant
~~~

### 【Hypertable 仍然需要 Index，分区不能替代索引】

当前：

~~~sql
CREATE INDEX telemetry_project_time_idx
ON telemetry_events(
  project_id,
  occurred_at DESC
);
~~~

以及：

~~~sql
CREATE INDEX performance_project_time_idx
ON performance_samples(
  project_id,
  observed_at DESC
);
~~~

还存在：

~~~sql
CREATE INDEX performance_project_route_time_idx
ON performance_samples(
  project_id,
  route_name,
  observed_at DESC
);
~~~

这些设计说明：

~~~text
Hypertable
    ↓
先限制 Time Partition

Index
    ↓
再在相关 Chunk 中
寻找 Project / Route / Time
~~~

两层可以共同工作。

所以：

~~~text
Partition
≠
Index
~~~

更完整地说：

~~~text
Chunk Pruning
    ↓
减少需要访问的物理分区

Index Access
    ↓
减少每个相关分区内部需要扫描的数据
~~~

### 【当前项目没有显式指定 Chunk Interval，因此不能从源码假设固定分区大小】

当前 create_hypertable：

~~~sql
SELECT create_hypertable(
  'performance_samples',
  'observed_at',
  if_not_exists => TRUE
);
~~~

没有显式写：

~~~text
chunk_time_interval
~~~

因此当前仓库可以确认：

~~~text
按时间创建 Hypertable
~~~

但不能仅凭源码确认：

~~~text
每个 Chunk 一定是 1 天
或 7 天
~~~

实际 Chunk Interval 需要结合：

~~~text
实际 TimescaleDB Version
默认配置
运行环境
~~~

检查。

当前 Docker 使用：

~~~text
timescale/timescaledb-ha:pg17
~~~

也没有在 Migration 中锁定 TimescaleDB Extension 版本。

因此如果未来进行生产容量治理，应该把：

~~~text
TimescaleDB Version
+
Chunk Interval
+
Ingest Rate
+
Chunk Size
~~~

一起纳入显式配置和验证。

## 11. 时序写入模型需要同时管理 Raw Event、Projection 与可修订 Sample

普通日志系统常常只有：

~~~text
Event
    ↓
Append
~~~

但 Browser Monitor 的数据链更复杂。

当前：

~~~text
SDK
    ↓
telemetry_events
    ↓
Outbox
    ↓
Worker
    ↓
performance_samples
view_records
custom_signal_samples
custom_metric_samples
~~~

这意味着当前系统不是单纯的 Event Storage，而是形成：

~~~text
Raw Telemetry
    ↓
Traceability

Domain Projection
    ↓
Analytics Query Model
~~~

这里不要直接把项目定义成完整 Event Sourcing Architecture，因为当前系统并没有把全部业务状态都通过 Event Replay 构建。

### 【Raw Event 保存客户端实际发送过什么】

telemetry_events 保存：

~~~text
event_id
occurred_at
received_at
type
name
environment
app_version
session_id
view_id
route_name
event jsonb
processed_at
~~~

它更接近：

~~~text
Raw Fact Layer
~~~

作用包括：

~~~text
审计
问题追踪
原始事件检索
Worker Processing Source
~~~

### 【Projection 将协议 Event 转换成面向查询的领域模型】

例如：

~~~text
Performance Event
    ↓
performance_samples

View Event
    ↓
view_records

Custom Signal
    ↓
custom_signal_samples

Custom Metric
    ↓
custom_metric_samples
~~~

如果所有查询都直接解析 telemetry_events.event JSONB，那么每一次 Analytics 都需要重新理解：

~~~text
协议结构
Event Type
Value
Lifecycle
Sequence
~~~

所以 Worker 提前把 Raw Event 变成：

~~~text
Domain-specific Tables
~~~

本质上是在做：

~~~text
Write-time Processing
    ↓
换取
Read-time Simplicity
~~~

### 【Performance Sample 展示了时序数据不一定永远只 Append】

performance_samples 有：

~~~text
sample_id
sequence
state
last_updated_at
~~~

同一个 Web Vital Sample：

~~~text
sequence 0
    ↓
sequence 1
    ↓
sequence 2 final
~~~

会对同一领域 Sample 进行修订。

所以：

~~~text
Time-Series
≠
只能 INSERT
~~~

更准确：

~~~text
大部分新时间点持续 Append

但某些业务模型
允许对最近时间范围进行 UPDATE / Finalize
~~~

这会直接影响后面的：

~~~text
Continuous Aggregate Refresh Window
Compression Timing
Finalization Strategy
~~~

因为最近数据仍然可能变化，而更旧数据通常更稳定。

### 【当前系统已经形成 Hot Recent Data 与 Stable Historical Data 的自然分界】

例如：

~~~text
Performance Sample

刚上报
    ↓
provisional

后续 sequence
    ↓
更新

最终
    ↓
final

时间继续过去
    ↓
基本不会再修改
~~~

因此整个时序生命周期天然可以理解成：

~~~text
Recent Hot Data
    ↓
仍可能变化
    ↓
Row-oriented / Frequent Refresh

Historical Stable Data
    ↓
很少变化
    ↓
Compression / Rollup / Retention
~~~

这也是后续 Compression 与 Continuous Aggregate 策略能够成立的业务基础。

## 12. Time Range Query 与 time_bucket 把原始时间轴转换成可分析的时间窗口

保存大量时序数据只是第一步。

真正的监控产品需要回答：

~~~text
最近 1 小时 LCP 怎么变化？

过去 7 天每天访问量是多少？

过去 30 天 p75 是否恶化？

哪个 Route 的 Poor Rate 更高？
~~~

这类问题具有统一结构：

~~~text
Time Range
+
Dimensions
+
Aggregation
~~~

### 【Time Range 是 Analytics Query 的第一层过滤边界】

当前 Analytics 输入：

~~~text
from
to
environment
version
routeName
metric
~~~

服务端默认：

~~~text
to = now

from = to - 24 hours
~~~

并限制最早查询范围约为：

~~~text
180 days
~~~

因此查询不是：

~~~text
SELECT all history
~~~

而是：

~~~text
先定义 Query Window
    ↓
再在时间窗口内做计算
~~~

这和 TimescaleDB 的 Chunk Pruning 模型天然一致。

### 【time_bucket 把连续时间轴转换成固定粒度 Bucket】

当前：

~~~sql
time_bucket(
  INTERVAL '1 minute',
  observed_at
)
~~~

可以理解：

~~~text
10:00:01
10:00:15
10:00:49
    ↓
10:00 Bucket

10:01:03
10:01:30
    ↓
10:01 Bucket
~~~

于是：

~~~text
Continuous Timeline
    ↓
Discrete Time Buckets
~~~

后续才能计算：

~~~text
COUNT
AVG
MIN
MAX
Percentile
Good Rate
Distinct Session
~~~

### 【Bucket Size 决定查询分辨率与结果规模】

如果查询 24 小时：

~~~text
1-minute Bucket
    ↓
1440 points
~~~

如果查询 180 天仍然返回 1-minute Bucket：

~~~text
259,200 points
~~~

不仅数据库聚合成本高：

~~~text
API Response
Network
Frontend Chart
~~~

也会变得很重。

所以长期趋势通常需要：

~~~text
Time Range 越大
    ↓
Bucket 越粗
~~~

这就是后面：

~~~text
1 minute Rollup
    ↓
1 hour Rollup
~~~

的意义。

### 【近期明细查询可以直接使用精确聚合】

当前最近 29 天的 Performance 查询直接从 performance_samples 计算：

~~~sql
count(*)

avg(value)

percentile_cont(0.50)
percentile_cont(0.75)
percentile_cont(0.90)
percentile_cont(0.95)
~~~

这属于：

~~~text
Query-time Exact Aggregation
~~~

优点：

~~~text
直接基于明细
口径精确
能灵活增加过滤条件
~~~

代价：

~~~text
数据越多
Query-time 计算越重
~~~

因此它适合：

~~~text
Recent Window
~~~

而不适合无限历史。

### 【原始事件列表使用 Cursor Pagination，而不是 Offset Pagination】

Raw Event 查询是另一种时序访问模式：

~~~text
按时间倒序
逐页查看明细
~~~

当前使用：

~~~text
(occurred_at, event_id)
~~~

作为稳定 Cursor。

下一页：

~~~sql
WHERE (
  occurred_at,
  event_id
) < (
  :cursorOccurredAt,
  :cursorEventId
)
~~~

这比：

~~~text
OFFSET 100000
~~~

更适合持续新增的时序表。

因此 Time-Series Query 不只有：

~~~text
Aggregate Query
~~~

还包括：

~~~text
Time-ordered Detail Scan
~~~

两种查询模型需要分别设计。

## 13. Continuous Aggregate 把高频重复统计从查询时计算改成后台增量维护

如果每一个 Dashboard Request 都直接：

~~~text
Raw Hypertable
    ↓
扫描 Time Range
    ↓
GROUP BY time_bucket
    ↓
COUNT / AVG / Percentile
    ↓
返回结果
~~~

那么 Query Cost 会随着：

~~~text
Time Range
+
Raw Row Count
~~~

不断增加。

这时出现一个核心优化方向：

~~~text
Query-time Computation
        ↓
Precomputation
~~~

也就是提前维护常用统计结果。

PostgreSQL 本身有 Materialized View，TimescaleDB 在 Time-Series 场景进一步提供：

~~~text
Continuous Aggregate
~~~

### 【普通 View、Materialized View 与 Continuous Aggregate 解决的是不同层次的问题】

普通 View：

~~~text
View
    ↓
保存 Query Definition

每次 SELECT
    ↓
重新执行底层 Query
~~~

它不保存聚合结果。

Materialized View：

~~~text
Query
    ↓
Materialize Result
    ↓
Disk
~~~

查询变快，但数据变化后需要刷新物化结果。

TimescaleDB Continuous Aggregate：

~~~text
Time-Series Source
        ↓
Continuous Aggregate
        ↓
围绕受影响的时间 Bucket
增量维护聚合结果
~~~

核心目标是：

> **避免每一次刷新都重新扫描全部历史数据，而是围绕受影响的时间 Bucket 增量维护聚合结果。**

因此：

~~~text
View
    ↓
Logical Query

Materialized View
    ↓
Stored Result

Continuous Aggregate
    ↓
Time-aware Incrementally Maintained Result
~~~

需要区分。

### 【当前项目的一分钟 Rollup 是 Continuous Aggregate】

performance_rollup_1m：

~~~sql
CREATE MATERIALIZED VIEW performance_rollup_1m
WITH (timescaledb.continuous) AS
SELECT
  time_bucket(
    INTERVAL '1 minute',
    observed_at
  ) AS bucket,

  project_id,
  name,
  environment,
  app_version,
  route_name,
  threshold_version_id,

  count(*)::bigint AS sample_count,
  min(value) AS minimum,
  max(value) AS maximum,
  avg(value) AS average,

  percentile_agg(value)
    AS value_percentiles,

  count(*) FILTER (
    WHERE server_rating = 'good'
  ) AS good_count,

  hyperloglog(
    8192,
    session_id
  ) AS session_hll,

  hyperloglog(
    8192,
    view_id
  ) AS view_hll

FROM performance_samples

GROUP BY
  bucket,
  project_id,
  name,
  environment,
  app_version,
  route_name,
  threshold_version_id

WITH NO DATA;
~~~

这个定义可以拆成：

~~~text
Source
    ↓
performance_samples

Time Dimension
    ↓
1 minute bucket

Business Dimensions
    ↓
project
metric
environment
version
route
threshold version

Measures
    ↓
count
min
max
avg
rating count
percentile state
distinct-count state
~~~

所以 Continuous Aggregate 本质上仍然是：

~~~text
Dimension
+
Measure
~~~

的分析模型，只是维护方式发生了变化。

### 【WITH NO DATA 表示创建定义时不立即执行完整历史回填】

当前：

~~~sql
WITH NO DATA
~~~

表示先创建 Continuous Aggregate Definition，而不是 CREATE 时立即同步计算所有已有历史。

后续再由：

~~~text
Refresh Policy
~~~

维护需要的时间范围。

这可以避免：

~~~text
Migration 执行时
因为历史数据巨大
长时间阻塞
~~~

但也意味着：

~~~text
View Definition Created
≠
历史 Aggregate 已经全部存在
~~~

如果已有大量历史数据，需要另外检查 Backfill / Refresh 是否已经覆盖目标时间范围。

### 【Continuous Aggregate Policy 定义哪些时间需要刷新以及多久执行一次】

当前一分钟 Rollup：

~~~sql
SELECT add_continuous_aggregate_policy(
  'performance_rollup_1m',

  start_offset => INTERVAL '29 days',

  end_offset => INTERVAL '10 seconds',

  schedule_interval => INTERVAL '10 seconds',

  if_not_exists => TRUE
);
~~~

这三个参数不能混为一谈。

#### <u>1. start_offset 定义 Refresh Window 往历史追多远</u>

当前：

~~~text
29 days
~~~

可以理解成：

~~~text
每次 Policy Run

关注：
now - 29 days
到
now - 10 seconds

这段可能发生变化的数据
~~~

它不是：

~~~text
Aggregate 只能保存 29 天
~~~

保存多久由 Retention Policy 另外控制。

所以：

~~~text
Refresh Window
≠
Retention Window
~~~

#### <u>2. end_offset 给最靠近现在的活跃写入留出缓冲区</u>

当前：

~~~text
10 seconds
~~~

表示最靠近 Now 的 10 秒暂时不进入这次物化刷新。

原因是最近数据通常：

~~~text
仍在持续写入
可能出现迟到事件
可能继续 UPDATE
~~~

这和前面 Recent Hot Data 的模型一致。

#### <u>3. schedule_interval 决定后台 Job 多久运行一次</u>

当前：

~~~text
10 seconds
~~~

因此：

~~~text
Policy Scheduler
    ↓
每约 10 秒
    ↓
更新指定 Refresh Window
~~~

这是：

~~~text
Freshness
vs
Background Cost
~~~

的权衡。

越频繁，Dashboard Aggregate 越新，但 Background Refresh Cost 越高。

### 【Continuous Aggregate 不等于结果绝对实时】

需要建立：

~~~text
Raw Data Arrives
    ↓
Continuous Aggregate
并不会在每条 INSERT 的同一个瞬间
一定立即物化
~~~

中间存在：

~~~text
Refresh Lag
~~~

TimescaleDB 还提供 Real-time Aggregate 模式：

~~~text
Materialized Historical Part
+
Recent Raw Part
~~~

组合查询。

从 TimescaleDB 2.13 起，Real-time Aggregate 默认关闭，需要显式把 materialized_only 设置为 false 才启用。

当前项目需要区分：

~~~text
custom_signal_rollup_1m
custom_metric_rollup_1m
~~~

明确执行：

~~~sql
ALTER MATERIALIZED VIEW custom_signal_rollup_1m
SET (timescaledb.materialized_only = false);

ALTER MATERIALIZED VIEW custom_metric_rollup_1m
SET (timescaledb.materialized_only = false);
~~~

而 0001 中较早创建的：

~~~text
performance_rollup_1m
view_rollup_1m
custom_event_rollup_1m
telemetry_rollup_1m
~~~

并没有显式设置 materialized_only。

同时当前 Docker Image：

~~~text
timescale/timescaledb-ha:pg17
~~~

没有在文档或 Compose 中锁死具体 TimescaleDB Extension Version。

因此不能只根据源码断言：

~~~text
所有 Continuous Aggregate
都一定启用了 Real-time Aggregate
~~~

当前查询设计实际上也不依赖这一点，因为近期 29 天直接查询明细。

### 【Continuous Aggregate 最重要的价值是把重复查询成本移动到可控的后台维护】

如果没有 Rollup：

~~~text
100 个 Dashboard Requests
    ↓
100 次扫描 Raw Data
    ↓
100 次重新计算
~~~

使用 Continuous Aggregate：

~~~text
Raw Data
    ↓
后台增量维护
    ↓
Stored Aggregate
    ↓
大量 Dashboard Request
复用结果
~~~

所以它解决的是：

~~~text
Repeated Analytical Computation
~~~

而不仅是：

~~~text
SQL 写得更短
~~~

## 14. Hierarchical Continuous Aggregate 用多层粒度控制长期查询成本

只有一分钟 Rollup 仍然存在一个问题。

假设：

~~~text
180 days
×
1440 minute buckets / day
~~~

一分钟数据点数量约：

~~~text
259,200 buckets
~~~

长期 Dashboard 并不需要这么高的时间分辨率。

因此项目继续建立：

~~~text
1 minute
    ↓
1 hour
~~~

的 Hierarchical Rollup。

### 【当前小时 Rollup 不是重新扫描 Raw Table，而是继续聚合一分钟 Rollup】

0002_hourly_aggregates.sql：

~~~sql
CREATE MATERIALIZED VIEW performance_rollup_1h
WITH (timescaledb.continuous) AS
SELECT

  time_bucket(
    INTERVAL '1 hour',
    bucket
  ) AS bucket,

  project_id,
  name,
  environment,
  app_version,
  route_name,
  threshold_version_id,

  sum(sample_count)::bigint
    AS sample_count,

  min(minimum)
    AS minimum,

  max(maximum)
    AS maximum,

  sum(
    average * sample_count
  )
  /
  NULLIF(
    sum(sample_count),
    0
  )
    AS average,

  rollup(value_percentiles)
    AS value_percentiles,

  rollup(session_hll)
    AS session_hll,

  rollup(view_hll)
    AS view_hll

FROM performance_rollup_1m

GROUP BY
  ...
~~~

完整链路：

~~~text
performance_samples
Raw / Projected Detail
        ↓
performance_rollup_1m
        ↓
performance_rollup_1h
~~~

而不是：

~~~text
Raw
    ↓
每次重新计算 1h
~~~

这就是：

~~~text
Hierarchical Continuous Aggregate
~~~

### 【Hierarchical Rollup 的本质是 Downsampling】

Downsampling：

~~~text
High Resolution
    ↓
Lower Resolution
~~~

例如：

~~~text
Second-level Raw Data
    ↓
1 minute
    ↓
1 hour
    ↓
1 day
~~~

越往历史：

~~~text
精细粒度价值下降

长期趋势价值保留
~~~

所以可以让：

~~~text
Recent
    ↓
High Resolution

Historical
    ↓
Lower Resolution
~~~

同时存在。

### 【不是所有 Aggregate 都可以简单地再次 SUM】

这是 Hierarchical Rollup 最重要的数学问题。

#### <u>1. Count 可以直接相加</u>

一分钟：

~~~text
10:00 count = 100
10:01 count = 120
10:02 count = 80
~~~

小时：

~~~text
sum(count)
~~~

成立。

#### <u>2. Min / Max 可以继续取 Min / Max</u>

~~~text
min(
  minute minimum
)
~~~

等于整个小时最小值。

~~~text
max(
  minute maximum
)
~~~

等于整个小时最大值。

#### <u>3. Average 不能直接 average(avg)</u>

假设：

~~~text
Minute A
1 sample
average = 100

Minute B
100 samples
average = 10
~~~

直接：

~~~text
(100 + 10) / 2
= 55
~~~

是错误的。

正确：

~~~text
Weighted Average

sum(
  average * sample_count
)
/
sum(
  sample_count
)
~~~

当前项目正是：

~~~sql
sum(average * sample_count)
/
NULLIF(sum(sample_count), 0)
~~~

因此：

> **能否 Rollup，不取决于它是不是一个数字，而取决于是否保留了再次聚合所需的信息。**

### 【小时 Policy 比分钟 Policy 更慢，因为历史粒度对实时性要求不同】

一分钟：

~~~text
schedule_interval = 10 seconds
~~~

小时：

~~~text
schedule_interval = 5 minutes
~~~

当前小时 Policy：

~~~text
start_offset = 179 days

end_offset = 1 hour

schedule_interval = 5 minutes
~~~

可以看到：

~~~text
1m Rollup
    ↓
Near-real-time

1h Rollup
    ↓
Historical Trend
~~~

所以维护频率不同。

这体现：

~~~text
Granularity
+
Freshness Requirement
~~~

共同决定 Background Policy。

## 15. 两步聚合让 Percentile 与 Distinct Count 可以跨时间 Bucket 再次 Rollup

Count、Sum、Min、Max 很容易理解。

真正困难的是：

~~~text
p75

Distinct Session Count
~~~

因为它们不能简单对局部结果再次使用普通算术。

### 【Percentile 不能通过每分钟 p75 再求 p75 得到小时 p75】

假设两个一分钟 Bucket：

~~~text
Bucket A
1000 个样本
p75 = 100

Bucket B
10 个样本
p75 = 1000
~~~

如果直接：

~~~text
percentile(
  100,
  1000
)
~~~

已经丢失：

~~~text
原始分布
样本量
尾部分布
~~~

所以无法恢复整体真实 p75。

因此项目没有在一分钟 Rollup 中直接只保存：

~~~text
p50
p75
p95
~~~

而是保存：

~~~sql
percentile_agg(value)
AS value_percentiles
~~~

也就是：

~~~text
Intermediate Aggregate State
~~~

### 【Two-step Aggregate 把累计状态和最终读数拆开】

Timescale Toolkit 使用：

~~~text
Step 1
Aggregate

Raw Values
    ↓
percentile_agg
    ↓
Percentile State
~~~

然后：

~~~text
Step 2
Accessor

Percentile State
    ↓
approx_percentile(0.75, ...)
    ↓
p75
~~~

如果需要继续从一分钟聚合成一小时：

~~~text
Minute States
    ↓
rollup(...)
    ↓
Hour State
    ↓
approx_percentile(...)
~~~

这就是：

~~~text
Aggregate
    ↓
Rollup
    ↓
Accessor
~~~

三阶段。

它比：

~~~text
直接保存 p75 number
~~~

多保留了可以继续组合的信息。

### 【当前项目通过 percentile_agg → rollup → approx_percentile 支持长期分位数】

一分钟：

~~~sql
percentile_agg(value)
AS value_percentiles
~~~

一小时：

~~~sql
rollup(value_percentiles)
AS value_percentiles
~~~

长期查询：

~~~text
approx_percentile(
  0.75,
  rollup(value_percentiles)
)
~~~

于是：

~~~text
Raw Value
    ↓
Percentile Intermediate State
    ↓
Hierarchical Rollup
    ↓
Approximate p50 / p75 / p95
~~~

这也是为什么项目长期 Rollup 查询使用：

~~~text
Approximate Percentile
~~~

而近期 Raw Query 使用：

~~~text
PostgreSQL percentile_cont
Exact Percentile
~~~

两者口径必须明确区分。

### 【Approximate Percentile 的价值来自资源成本，而不是比精确算法更正确】

Exact：

~~~text
Raw Values
    ↓
Sort / Exact Calculation
    ↓
Precise Percentile
~~~

数据规模越大，成本越高。

Approximate：

~~~text
Compact Statistical State
    ↓
Merge / Rollup
    ↓
Approximate Percentile
~~~

换取：

~~~text
Lower Memory
Lower CPU
Composable Rollup
~~~

代价：

~~~text
存在近似误差
~~~

所以项目选择：

~~~text
Recent 29d
    ↓
Exact

Historical
    ↓
Approximate
~~~

本质是：

~~~text
Precision
vs
Cost
~~~

的分层策略。

### 【Distinct Count 同样不能直接把每分钟 DISTINCT 数相加】

假设：

~~~text
10:00
Session A
Session B

count distinct = 2

10:01
Session A
Session C

count distinct = 2
~~~

直接：

~~~text
2 + 2 = 4
~~~

错误。

真实小时 Distinct：

~~~text
A
B
C

= 3
~~~

原因：

~~~text
同一个 Entity
可能跨多个 Bucket 重复出现
~~~

所以：

~~~text
Local Distinct Count
~~~

不是：

~~~text
Rollup-able Numeric State
~~~

### 【HyperLogLog 保存的是可以继续 Merge 的基数估计状态】

当前一分钟 Rollup：

~~~sql
hyperloglog(
  8192,
  session_id
)
AS session_hll
~~~

以及：

~~~sql
hyperloglog(
  8192,
  view_id
)
AS view_hll
~~~

小时 Rollup：

~~~sql
rollup(session_hll)

rollup(view_hll)
~~~

最终查询：

~~~text
distinct_count(
  rollup(session_hll)
)
~~~

因此完整链路：

~~~text
Raw IDs
    ↓
HLL Intermediate State
    ↓
Rollup
    ↓
Approximate Distinct Count
~~~

这和 Percentile 使用的是同一个更高层思想：

> **不要过早把复杂统计压缩成一个不可再组合的最终数字，而要保存能够继续 Merge 的中间状态。**

### 【Two-step Aggregate 是当前长期分析设计的核心抽象】

因此当前系统中的聚合可以重新分类：

| Measure | 1m 保存 | 1h Rollup | Final Query |
|---|---|---|---|
| Count | count | sum | sum / value |
| Sum | sum | sum | sum |
| Min | min | min | min |
| Max | max | max | max |
| Average | average + count | weighted average | average |
| Percentile | percentile state | rollup state | approx_percentile |
| Distinct Session | HLL state | rollup state | distinct_count |
| Distinct View | HLL state | rollup state | distinct_count |

所以：

~~~text
Long-term Analytics
~~~

真正依赖的是：

~~~text
Composable Aggregate State
~~~

而不仅仅是：

~~~text
Materialized View
~~~
