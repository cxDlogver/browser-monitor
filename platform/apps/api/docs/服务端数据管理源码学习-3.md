# 服务端数据管理源码学习-3

> **专题定位**：本篇进入 TimescaleDB / Time-Series Data Management。学习目标不是直接记忆 Hypertable、Continuous Aggregate、Compression 等 API，而是从 Browser Monitor 当前源码出发，逐步回答“为什么项目需要时序数据管理、TimescaleDB 在 PostgreSQL / Redis / Worker / Analytics 之间承担什么职责、源码为什么这样设计”，再从项目实现中抽象出能够脱离当前项目独立成立的时序数据管理知识框架。
>
> **学习方式**：每一节只推进一个核心问题，并严格按照“项目原文 → 项目整体链路 → 对应源码 → 源码执行逻辑 → 抽象框架 → 通用知识体系 → 回到项目分析”的路径展开。先建立整体位置，再进入 Hypertable、Chunk、Continuous Aggregate、Rollup、Compression、Retention 等内部机制。
>
> **与已有知识的关系**：
>
> - 服务端数据管理源码学习.md：Database → Connection → SQL → Schema / Drizzle → Constraint → Index。
> - 服务端数据管理源码学习-2.md：Transaction → Concurrency Control。
> - Redis体系源码学习.md：Runtime State → Cache → Session → Rate Limit → Atomicity → Reliability → Scale → Production Governance。
> - 本篇：Time-Series Data Management → TimescaleDB → 时序组织 → 时序聚合 → 历史生命周期。
>
> **分析边界**：项目事实以当前 browser-monitor/platform 源码为准。通用概念只在源码能够引出时展开，并明确区分“当前项目已经实现”“TimescaleDB 通用能力”“后续可继续深入的设计”。

## 1. TimescaleDB 是 PostgreSQL 之上的时序数据管理层，而不是项目中的另一套独立数据库

这一节先不进入：

~~~text
Hypertable
Chunk
Continuous Aggregate
Compression
Retention
~~~

因为这些都是 TimescaleDB 内部能力。

在理解内部机制之前，必须先回答一个更基础的问题：

> **当前 Browser Monitor 已经使用 PostgreSQL，为什么还需要 TimescaleDB？TimescaleDB 在整个服务端数据管理链路中到底处于什么位置？**

如果这个位置没有建立清楚，后面学习 TimescaleDB 很容易退化成：

~~~text
create_hypertable 是什么

time_bucket 怎么写

Continuous Aggregate 怎么配置

Compression Policy 有哪些参数
~~~

最终只记住零散 API，而没有建立“什么时候需要这一类数据管理能力”的系统框架。

这一节因此只做一件事：

~~~text
把 TimescaleDB 放回完整 Server Data Architecture
~~~

### 【第一层：先从项目整体数据链路定位 TimescaleDB】

#### <u>1. 项目原文已经明确给出 TimescaleDB 所处的数据处理阶段</u>

当前 platform/README.md 对完整链路的描述是：

> Monitor SDK → 公开 DSN → Ingestion API → telemetry_events + Outbox → Worker → TimescaleDB 聚合 → Analytics API → React 看板

先不看任何 TimescaleDB API，只把这条链拆成职责：

~~~text
Monitor SDK
    ↓
数据产生

Ingestion API
    ↓
数据接收

telemetry_events + Outbox
    ↓
原始事实可靠落库
+
记录后续处理任务

Worker
    ↓
异步加工
形成领域查询模型

TimescaleDB
    ↓
时序数据组织
+
时序聚合
+
历史数据生命周期

Analytics API
    ↓
查询与统计服务

React Dashboard
    ↓
展示
~~~

因此从项目原文就能先得到一个非常重要的结论：

~~~text
TimescaleDB
并不位于数据入口

TimescaleDB
也不负责前端 Session / Cache / Rate Limit

TimescaleDB
主要出现在数据已经可靠接收以后
进入长期时序分析的阶段
~~~

所以它在当前项目中的位置更接近：

~~~text
Data Ingestion
    ↓
Durable Storage
    ↓
Async Processing
    ↓
Time-Series Management
    ↓
Analytics
~~~

而不是：

~~~text
Request
    ↓
TimescaleDB
    ↓
Response
~~~

这样一条孤立链路。

#### <u>2. TimescaleDB 所处的位置说明它解决的是“长期历史数据怎样管理”</u>

把 Browser Monitor 再压缩成一条数据生命周期：

~~~text
Browser
    ↓
产生 Telemetry

API
    ↓
接收 Telemetry

PostgreSQL Transaction
    ↓
保证 Raw Event + Outbox
可靠提交

Worker
    ↓
把 Raw Event
加工成查询模型

TimescaleDB
    ↓
管理不断增长的
Time-Series Data

Analytics API
    ↓
按照时间范围
查询趋势与统计

Redis
    ↓
缓存最终 Query Result

Web
    ↓
展示
~~~

这里已经可以发现：

~~~text
PostgreSQL Transaction
解决：
这批数据是否可靠成为事实

Worker
解决：
原始数据怎样被加工

TimescaleDB
解决：
长期时序数据怎样组织和查询

Redis
解决：
运行时结果怎样快速复用
~~~

所以 TimescaleDB 的核心问题不是：

~~~text
数据能不能存进去？
~~~

因为普通 PostgreSQL 本身已经可以 INSERT。

它真正面对的是：

~~~text
数据持续产生以后
怎样长期组织？

历史越来越多以后
怎样按时间范围查询？

同一类统计不断被重复计算
怎样降低成本？

旧数据价值变化以后
怎样压缩、降采样和清理？
~~~

这才是：

~~~text
Time-Series Data Management
~~~

的真正入口。

### 【第二层：从部署源码确认 TimescaleDB 与 PostgreSQL 的真实关系】

理解项目链路以后，再进入部署代码。

这里最重要的是先纠正一个容易出现的概念错误：

~~~text
PostgreSQL
TimescaleDB
Redis

≠

三个完全独立的数据库系统
~~~

当前项目不是这样设计的。

#### <u>1. Docker Service 名叫 timescaledb，但应用连接的仍然是 PostgreSQL</u>

当前 docker-compose.yml：

~~~yaml
timescaledb:
  image: timescale/timescaledb-ha:pg17

  environment:
    POSTGRES_DB: monitor
    POSTGRES_USER: monitor
    POSTGRES_PASSWORD: ...

  ports:
    - "5432:5432"
~~~

API / Worker 使用：

~~~text
DATABASE_URL
    ↓
postgres://monitor:...@timescaledb:5432/monitor
~~~

这里可以直接看到：

~~~text
Protocol
    ↓
postgres://

Port
    ↓
5432

Database
    ↓
monitor

User
    ↓
PostgreSQL User
~~~

应用没有使用另一套：

~~~text
timescale://
~~~

协议。

因此运行关系应该理解成：

~~~text
Application
    ↓
PostgreSQL Driver
    ↓
PostgreSQL Protocol
    ↓
PostgreSQL Database Engine
    +
TimescaleDB Extension
~~~

而不是：

~~~text
Application
 ├── PostgreSQL Database
 └── TimescaleDB Database
~~~

#### <u>2. Migration 进一步证明 TimescaleDB 是 PostgreSQL 内部扩展能力</u>

当前 0001_platform.sql 一开始：

~~~sql
CREATE EXTENSION IF NOT EXISTS pgcrypto;

CREATE EXTENSION IF NOT EXISTS timescaledb;

CREATE EXTENSION IF NOT EXISTS timescaledb_toolkit;
~~~

这段代码表达的层级非常清楚：

~~~text
PostgreSQL Database
│
├── PostgreSQL Native Capability
│
├── pgcrypto Extension
│
├── timescaledb Extension
│
└── timescaledb_toolkit Extension
~~~

所以前两篇已经学过的：

~~~text
Table

SQL

Index

Constraint

Transaction

MVCC

Connection Pool
~~~

并没有因为 TimescaleDB 出现而失效。

更准确地说：

~~~text
PostgreSQL
    ↓
提供通用关系型数据管理基础

TimescaleDB
    ↓
在 PostgreSQL 之上
增加 Time-Series Capability
~~~

后面才会逐步展开：

~~~text
Hypertable

Chunk

time_bucket

Continuous Aggregate

Retention

Compression / Columnstore

Time-Series Hyperfunctions
~~~

因此需要先固定一个概念：

> **TimescaleDB 不是 PostgreSQL 的替代数据库，而是建立在 PostgreSQL 之上的时序数据管理扩展层。**

#### <u>3. PostgreSQL 与 TimescaleDB 是“基础能力 + 专用工作负载能力”的关系</u>

可以抽象成：

~~~text
PostgreSQL
│
├── General Relational Data Management
│   ├── Table
│   ├── Relation
│   ├── SQL
│   ├── Index
│   ├── Constraint
│   ├── Transaction
│   └── Concurrency Control
│
└── TimescaleDB Extension
    └── Time-Series Data Management
        ├── Time Partition
        ├── Time Range Query
        ├── Time Bucket
        ├── Incremental Aggregate
        ├── Historical Rollup
        └── Data Lifecycle
~~~

因此：

~~~text
TimescaleDB Knowledge
~~~

不是另外一套和 PostgreSQL 毫无关系的知识。

而是：

~~~text
PostgreSQL Knowledge
        ↓
遇到 Time-Series Workload
        ↓
增加专门的数据组织与分析能力
~~~

这也是本篇为什么必须建立在前两篇 PostgreSQL 学习之后。

### 【第三层：当前项目之所以需要 TimescaleDB，是因为数据 Workload 已经发生变化】

既然 PostgreSQL 本身可以建表、插入、索引和查询，那么自然要继续问：

> **为什么当前项目不能只停留在普通 PostgreSQL 数据模型？**

答案不应该简化成：

~~~text
TimescaleDB 更快
~~~

而应该先比较项目中的两类数据。

#### <u>1. 一类是关系型业务状态，核心是实体当前状态与关系</u>

当前 Migration 中：

~~~text
users

user_sessions

account_tokens

projects

project_members

ingestion_keys

allowed_origins

threshold_versions

project_invitations

outbox_tasks
~~~

这些数据主要表达：

~~~text
User 是谁

Project 是什么

谁属于哪个 Project

当前使用哪个 Threshold

Token 是否有效

Outbox Task 当前处于什么状态
~~~

典型访问方式：

~~~sql
WHERE id = ?

WHERE user_id = ?

WHERE project_id = ?

WHERE token_hash = ?

WHERE active = true
~~~

它们的核心问题更接近：

~~~text
Entity
    ↓
Relation
    ↓
Constraint
    ↓
Transaction
    ↓
Current Business State
~~~

这就是前两篇 PostgreSQL 学习主要解决的：

~~~text
Relational Business Data
~~~

#### <u>2. 另一类是持续产生的监控事实，核心是系统随时间怎样变化</u>

当前 Migration 中还有：

~~~text
telemetry_events

performance_samples

view_records

custom_event_samples

custom_signal_samples

custom_metric_samples
~~~

这些表都有非常重要的时间字段：

~~~text
occurred_at

observed_at

started_at
~~~

例如 performance_samples 形成的逻辑更像：

~~~text
10:00:01
LCP = 2100

10:00:05
LCP = 2500

10:00:10
INP = 180

10:00:16
LCP = 1900

...
~~~

系统真正关心的通常不是：

~~~text
根据 Primary Key
找某一条 Sample
~~~

而是：

~~~text
Project P001

过去 24 小时

LCP

每一分钟

count
avg
p50
p75
p95
good / poor
~~~

查询结构变成：

~~~text
Entity Scope
    +
Time Range
    +
Time Bucket
    +
Aggregation
~~~

这就是：

~~~text
Time-Series Workload
~~~

#### <u>3. Time-Series 的关键不是“表里有 timestamp”，而是时间成为第一组织维度</u>

普通业务表同样可能有：

~~~text
created_at
updated_at
~~~

但它们不一定是 Time-Series。

判断一份数据是不是典型时序工作负载，更重要的是：

~~~text
Time
    ↓
是否决定数据排序？

Time Range
    ↓
是否是主要查询条件？

New Data
    ↓
是否持续沿时间轴追加？

Analytics
    ↓
是否经常按时间 Bucket 聚合？

Lifecycle
    ↓
历史数据价值是否随时间变化？
~~~

所以可以抽象：

~~~text
Relational Entity Data
        ↓
Entity-centered

Time-Series Data
        ↓
Time-centered
~~~

这个区别非常重要。

后面所有 TimescaleDB 能力都不是凭空产生，而是从这个 Workload 差异自然推出来的。

### 【第四层：Time-Series Workload 会产生三类新的数据管理问题】

当前项目引入 TimescaleDB，不是因为普通 PostgreSQL 无法存数据，而是因为随着监控数据规模增长，会出现三类越来越突出的系统问题。

#### <u>1. 第一类问题是 Growing Dataset：持续增长的数据需要稳定的物理组织方式</u>

普通项目表可能：

~~~text
projects
    ↓
几百
几千
几万 Rows
~~~

而 Telemetry 是：

~~~text
每秒持续产生
~~~

假设：

~~~text
100 events / second
~~~

一天就是：

~~~text
8,640,000 events
~~~

如果：

~~~text
1000 events / second
~~~

一天就是：

~~~text
86,400,000 events
~~~

持续运行以后：

~~~text
Time
    ↓
Row Count
    ↓
Storage
    ↓
Index Size
    ↓
Query Cost
    ↓
Maintenance Cost
~~~

都会持续增加。

所以第一类核心问题不是“怎样让数据停止增长”，而是：

~~~text
Growing Dataset
        ↓
Physical Organization
        ↓
怎样把持续增长的数据
拆成可管理的物理范围
~~~

普通：

~~~text
一张表 + 一个 Index
~~~

并不能完整回答：

~~~text
数据持续增长以后
物理数据怎样继续组织和访问
~~~

的问题。

这里需要提前区分两个层次：

~~~text
Hypertable / Chunk
        ↓
组织增长
        ↓
把持续增长的 Time-Series Dataset
按时间范围拆成可管理的 Physical Partitions

Compression / Retention / Downsampling
        ↓
治理长期增长
        ↓
控制历史数据继续占用的存储、扫描和保留成本
~~~

因此 Hypertable 解决的是 **Growing Dataset 的 Physical Organization**，而不是让总数据量不再增长。真正的长期数据量治理还要继续进入 Historical Data Lifecycle。

#### <u>2. 第二类问题是 Analytical Query：查询通常扫描范围后再聚合</u>

普通业务查询：

~~~sql
SELECT *
FROM projects
WHERE id = $1;
~~~

而监控 Analytics 更接近：

~~~sql
SELECT
  time_bucket(
    INTERVAL '1 minute',
    observed_at
  ),
  percentile_cont(0.75)
FROM performance_samples
WHERE
  project_id = $1
  AND observed_at >= $2
  AND observed_at < $3
GROUP BY ...;
~~~

后者往往经历：

~~~text
Time Range Scan
    ↓
Filter
    ↓
Group
    ↓
Aggregate
    ↓
Percentile / Distinct
    ↓
Return Trend
~~~

同一个 Dashboard 还会不断重复类似计算。

于是第二类问题变成：

~~~text
Repeated Analytical Computation
~~~

而不只是：

~~~text
Single Row Lookup
~~~

#### <u>3. 第三类问题是 Data Lifecycle：历史数据价值随时间发生变化</u>

监控数据通常具有很明显的时间价值变化：

~~~text
刚产生
    ↓
定位问题价值最高
需要完整明细
需要高分辨率

几天以后
    ↓
仍需要分析
但单条 Event 价值下降

几个月以后
    ↓
更多关注长期趋势
而不是每一条原始记录
~~~

所以：

~~~text
所有 Raw Data
永远以相同精度保存
~~~

并不是唯一合理方案。

当前项目已经明确：

~~~text
Raw / Detail
    ↓
30 days

Aggregate
    ↓
180 days
~~~

这说明时序数据系统必须继续回答：

~~~text
什么时候保留 Raw？

什么时候聚合？

什么时候压缩？

什么时候降低时间分辨率？

什么时候删除？
~~~

第三类核心问题因此是：

~~~text
Historical Data Lifecycle
~~~

### 【第五层：TimescaleDB 的核心能力可以从三类 Workload 问题自然推出】

到这里还没有深入任何一个 API，但已经能够自然推出 TimescaleDB 为什么会出现。

~~~text
Time-Series Workload
│
├── ① Growing Dataset
│      ↓
│   Physical Organization
│      ↓
│   Time Partition
│   Hypertable
│   Chunk
│
├── ② Analytical Query
│      ↓
│   time_bucket
│   Continuous Aggregate
│   Hyperfunctions
│   Rollup
│
└── ③ Data Lifecycle
       ↓
    Compression / Columnstore
    Retention
    Downsampling
~~~

因此 TimescaleDB 不应该被记成：

~~~text
一个比 PostgreSQL 更快的数据库
~~~

而应该记成：

> **TimescaleDB 在 PostgreSQL 通用关系型能力之上，为持续增长、以时间范围查询和聚合为主要访问模式的数据增加专门的数据组织、分析和生命周期能力。**

这也是后面整个学习顺序的来源：

~~~text
为什么需要 Time-Series Management
        ↓
持续增长的数据怎样按时间组织
        ↓
Hypertable / Chunk
        ↓
组织增长，而不是停止增长

然后
        ↓
数据怎样按时间聚合
        ↓
time_bucket / Continuous Aggregate

然后
        ↓
历史数据怎样降采样和继续聚合
        ↓
Rollup / Two-step Aggregate

最后
        ↓
历史数据怎样控制长期成本
        ↓
Compression / Retention
~~~

也就是说：

~~~text
TimescaleDB API
~~~

不是学习起点。

真正的起点是：

~~~text
Time-Series Workload
~~~

### 【第六层：回到源码，当前 TimescaleDB 实际已经承担四层职责】

建立通用框架以后，再重新看当前项目源码。

当前项目不是只使用：

~~~text
create_hypertable
~~~

一个功能。

整个 Migration 已经形成四层能力。

#### <u>1. Time-Series Storage 负责组织 Raw 与 Projection Data</u>

源码：

~~~sql
SELECT create_hypertable(
  'telemetry_events',
  'occurred_at',
  if_not_exists => TRUE
);

SELECT create_hypertable(
  'performance_samples',
  'observed_at',
  if_not_exists => TRUE
);

SELECT create_hypertable(
  'view_records',
  'started_at',
  if_not_exists => TRUE
);
~~~

这层负责：

~~~text
持续增长的 Raw / Projected Data
        ↓
按照时间维度组织
~~~

这里下一节才深入：

~~~text
Hypertable
+
Chunk
+
Chunk Pruning
+
Index
~~~

#### <u>2. Time-Series Analytics 负责把时间轴转换成统计结果</u>

源码：

~~~sql
CREATE MATERIALIZED VIEW performance_rollup_1m
WITH (timescaledb.continuous) AS
SELECT
  time_bucket(
    INTERVAL '1 minute',
    observed_at
  ) AS bucket,
  ...
FROM performance_samples
GROUP BY ...;
~~~

它把：

~~~text
Raw Samples
    ↓
Continuous Timeline
~~~

转换成：

~~~text
1-minute Aggregate
~~~

后面还存在：

~~~text
1m
    ↓
1h
~~~

形成：

~~~text
Precomputation
+
Downsampling
~~~

#### <u>3. Statistical State 负责保存可继续组合的分析状态</u>

当前不仅计算：

~~~text
count
avg
min
max
~~~

还使用：

~~~sql
percentile_agg(value)
~~~

以及：

~~~sql
hyperloglog(
  8192,
  session_id
)
~~~

说明当前数据库层还承担：

~~~text
Percentile

Distinct Session

Distinct View
~~~

这类复杂统计。

后续会单独进入：

~~~text
Two-step Aggregate
~~~

解释为什么不能简单保存：

~~~text
一个 p75 number
或
一个 count distinct number
~~~

而需要保留可 Rollup 的中间状态。

#### <u>4. Historical Lifecycle 负责决定旧数据怎样继续存在</u>

当前 Migration 还存在：

~~~text
add_compression_policy

add_retention_policy
~~~

说明系统已经明确：

~~~text
Data Age
    ↓
Storage Strategy
    ↓
Resolution
    ↓
Retention
~~~

会随时间发生变化。

最终形成：

~~~text
Recent
    ↓
Raw Detail

Older
    ↓
Compressed Detail

Historical
    ↓
Aggregate

Expired
    ↓
Delete
~~~

所以当前 TimescaleDB 的真实职责已经不是：

~~~text
一个数据库插件
~~~

而是完整的：

~~~text
Time-Series Storage
+
Analytics
+
Statistical Processing
+
Historical Lifecycle
~~~

### 【第七层：TimescaleDB 与 PostgreSQL、Redis 的职责边界必须放在同一张图中】

理解 TimescaleDB 以后，需要把前面已经学过的 PostgreSQL 与 Redis 一起放回来。

~~~text
                    Server Data
                         │
       ┌─────────────────┼─────────────────┐
       │                 │                 │
       ▼                 ▼                 ▼
 Relational State   Time-Series State   Runtime State
       │                 │                 │
       ▼                 ▼                 ▼
 PostgreSQL        PostgreSQL +          Redis
                   TimescaleDB
~~~

这里严格来说：

~~~text
TimescaleDB
仍然属于 PostgreSQL 数据库体系
~~~

只是面对不同 Workload。

#### <u>1. PostgreSQL 的核心是长期关系型业务事实是否正确</u>

典型：

~~~text
users

~~~

核心关注：

~~~text

Durability

~~~

可以概括：

~~~text
Authoritative Relational State
~~~

#### <u>2. TimescaleDB 的核心是持续增长的历史事实怎样长期管理</u>

典型：

~~~text

~~~

核心关注：

~~~text

High Ingest

Time Range Query

Aggregation

Historical Lifecycle
~~~

可以概括：

~~~text
Authoritative Time-Series History
~~~

#### <u>3. Redis 的核心是运行中的共享状态怎样高频访问</u>

典型：

~~~text

Analytics Cache

Cache Version
~~~

核心关注：

~~~text

Derived State
~~~

可以概括：

~~~text
Runtime / Derived State
~~~

因此不要建立：

~~~text

~~~

这种性能排序模型。

~~~text
    ↓

    ↓

~~~

它们解决的是不同的数据管理问题。

### 【第八层：脱离当前项目，建立是否需要 Time-Series Data Management 的判断框架】

以后遇到其他系统，不应该看到：

~~~text
数据很多
~~~

就直接决定：

~~~text
使用 TimescaleDB
~~~

应该顺着数据语义和访问模式判断。

#### <u>1. 数据是否天然沿时间持续产生</u>

典型：

~~~text
Metrics

Telemetry

IoT Sensor Data

Financial Ticks

Observability Events
~~~

共同模式：

~~~text

    ↓
New Data

Time T2
    ↓
New Data

    ↓
New Data
~~~

如果数据主要不是这样产生，TimescaleDB 未必有意义。

#### <u>2. 主要查询是否围绕 Time Range</u>

例如：

~~~text

最近 24 小时

过去 7 天

过去 30 天
~~~

~~~text

~~~

那么普通 PostgreSQL 可能已经足够。

#### <u>3. 是否需要大量时间聚合</u>

例如：

~~~text

每天
~~~

并计算：

~~~text
COUNT

AVG

SUM

P75

P95

Distinct
~~~

这时 Time-Series Analytics 特征开始变强。

#### <u>4. 数据是否会长期持续增长</u>

例如：

~~~text
Today
    ↓
10M rows

Next Month
    ↓
300M rows

Next Year
    ↓
Billions of rows
~~~

如果数据规模会沿时间持续累积：

~~~text
Partition

Lifecycle
~~~

就会逐渐成为核心设计问题。

#### <u>5. 历史数据是否允许降低时间精度</u>

例如：

~~~text
最近 24h
    ↓
Raw

最近 30d
    ↓
1-minute

半年历史
    ↓
1-hour
~~~

如果答案是 Yes：

~~~text
Continuous Aggregate

Downsampling

Retention
~~~

会具有很高价值。

因此可以形成完整判断链：

~~~text
Data
 ↓
是否 Time-oriented？
 ↓ Yes
是否持续产生？
 ↓ Yes
是否主要 Time Range Query？
 ↓ Yes

 ↓ Yes

 ↓ Yes

成为候选方案
~~~

这里仍然是：

~~~text
候选方案
~~~

~~~text

~~~

最终还需要结合：

~~~text

Scale

Deployment Model
~~~

进行判断。

### 【第九层：回到 Browser Monitor，给当前 TimescaleDB 一个准确定位】

经过前面的项目源码、Workload 和通用框架，现在可以准确描述当前项目：

> **Browser Monitor 是一个以 PostgreSQL 为统一持久化基础，利用 TimescaleDB Extension 管理大量遥测时序历史，再使用 Redis 管理运行时状态和查询缓存的数据平台。**

完整数据层：

~~~text
                     Browser Monitor Data Layer

             ┌─────────────────┼──────────────────┐
             │                 │                  │
             ▼                 ▼                  ▼
     Relational Business   Time-Series Data   Runtime State
             │                 │                  │
             ▼                 ▼                  ▼

             │                 │                  │
      User / Project       Telemetry          Session
~~~

因此 TimescaleDB 在当前项目中承担：


### 【第一节最终形成 TimescaleDB 的整体位置框架】

这一节不要求记住任何具体 API。

真正需要形成的是：

~~~text
PostgreSQL
解决：

        ↓
~~~

这就是后续整个 TimescaleDB 学习的起点。

## 2. Hypertable 与 Chunk 把一张不断增长的逻辑表拆成多张真实 PostgreSQL 子表

这一节先把三个最容易混淆的问题直接回答清楚：

~~~text
问题 1：
Chunk 是逻辑概念，还是实际存储？

答案：
Chunk 是 TimescaleDB 自动创建和管理的真实 PostgreSQL 子表。
真正的数据 Row 会存入这些 Chunk。
它不是 TypeScript 代码，也不是内存里的一个对象。


问题 2：
create_hypertable 以后 performance_samples 还存在吗？

答案：
存在。

应用仍然：
INSERT INTO performance_samples
SELECT ... FROM performance_samples

performance_samples 仍然是应用看到的逻辑表。


问题 3：
performance_samples 还会不会一直变大？

答案：
逻辑上会。

例如总共有 1 亿条 performance_samples，
SELECT COUNT(*) 看到的仍然是 1 亿条。

但物理上不再是：
“一张 PostgreSQL 物理表里堆 1 亿条”。

而变成：
performance_samples
    ↓
Chunk A：一部分时间范围的数据
Chunk B：一部分时间范围的数据
Chunk C：一部分时间范围的数据
...
~~~

这就是这一节首先要建立的模型。

### 【第一层：先看普通 PostgreSQL Table 实际是什么】

先完全不考虑 TimescaleDB。

假设项目只创建：

~~~sql
CREATE TABLE performance_samples (
  project_id uuid NOT NULL,
  sample_id varchar(256) NOT NULL,
  observed_at timestamptz NOT NULL,
  name varchar(16) NOT NULL,
  value double precision NOT NULL
);
~~~

然后持续写：

~~~sql
INSERT INTO performance_samples
VALUES (...);
~~~

那么可以先简单理解为：

~~~text
performance_samples
        │
        ▼
一张 PostgreSQL Physical Table
        │
        ├── Row 1
        ├── Row 2
        ├── Row 3
        ├── ...
        └── Row 100,000,000
~~~

假设每天写 1000 万条：

~~~text
Day 1       1000 万
Day 2       2000 万
Day 3       3000 万
...
Day 100     10 亿
~~~

那么 Logical Table 和主要 Physical Data Structure 都在不断变大。

这里不是说 PostgreSQL 普通表一定不能存十亿数据，而是随着 Time-Series 数据持续增长，会越来越突出：

~~~text
大索引
大范围时间查询
历史数据删除
Vacuum / Maintenance
冷热数据管理
~~~

这些问题。

TimescaleDB 的第一步不是做聚合。

它先改变：

> **这张持续增长的 Table 在 PostgreSQL 内部怎样组织。**

### 【第二层：当前项目先创建普通 Table，再把它转换成 Hypertable】

来看当前项目真实源码。

0001_platform.sql：

~~~sql
CREATE TABLE performance_samples (
  project_id uuid NOT NULL REFERENCES projects(id) ON DELETE CASCADE,
  sample_id varchar(256) NOT NULL,
  observed_at timestamptz NOT NULL,
  last_updated_at timestamptz NOT NULL,
  name varchar(16) NOT NULL,
  value double precision NOT NULL CHECK (value >= 0),
  ...
  PRIMARY KEY (
    project_id,
    sample_id,
    observed_at
  )
);
~~~

执行到这里：

~~~text
performance_samples
        ↓
普通 PostgreSQL Table
~~~

紧接着：

~~~sql
SELECT create_hypertable(
  'performance_samples',
  'observed_at',
  if_not_exists => TRUE
);
~~~

这一步的含义不是：

~~~text
删除 performance_samples
然后创建一个 TimescaleDB 专用文件
~~~

也不是：

~~~text
复制一份 performance_samples
到另外一个数据库
~~~

而是：

~~~text
performance_samples
        ↓
仍然保留这个 Table 名称和 SQL 接口
        ↓
TimescaleDB 接管它的数据分区方式
        ↓
变成 Hypertable
~~~

可以先理解成：

~~~text
转换前

performance_samples
        ↓
普通 PostgreSQL Table


转换后

performance_samples
        ↓
TimescaleDB Hypertable
        ↓
底层自动管理多个 PostgreSQL Chunk Tables
~~~

应用程序依然：

~~~sql
INSERT INTO performance_samples ...

SELECT ...
FROM performance_samples
WHERE ...
~~~

不需要切换成另一套 SQL。

### 【第三层：Hypertable 是应用看到的一张逻辑表，Chunk 才是真正存 Row 的 PostgreSQL 子表】

这是这一节最重要的地方。

假设：

~~~sql
SELECT create_hypertable(
  'performance_samples',
  'observed_at'
);
~~~

然后数据库里已经产生一段时间的数据。

对业务代码来说仍然只有：

~~~text
performance_samples
~~~

但数据库内部可以近似理解成：

~~~text
                     performance_samples
                         Hypertable
                       应用访问入口
                            │
          ┌─────────────────┼─────────────────┐
          │                 │                 │
          ▼                 ▼                 ▼
      Chunk A           Chunk B           Chunk C
   PostgreSQL Table   PostgreSQL Table   PostgreSQL Table

   一段时间数据       一段时间数据       一段时间数据
~~~

注意：

> **Chunk 不是程序概念上的数组分片。**

它是数据库内部真实创建和管理的 PostgreSQL 子表。

内部对象通常会位于 TimescaleDB 自己的 internal schema 中，名称类似：

~~~text
_timescaledb_internal._hyper_..._chunk
~~~

所以可以非常具体地理解：

~~~text
performance_samples
        ↓
是业务 SQL 使用的统一表名

_timescaledb_internal....
        ↓
是 TimescaleDB 在 PostgreSQL 内部
创建并管理的真实 Chunk Table
~~~

#### <u>1. Hypertable 和 Chunk 到底谁存数据</u>

| 对象 | 是不是数据库对象 | 是否真正承载 Row | 谁直接使用 |
|---|---|---:|---|
| performance_samples Hypertable | 是 | 对应用表现为完整数据集 | 应用程序 |
| Chunk | 是，真实 PostgreSQL 子表 | 是，实际 Row 分布在这些 Chunk 中 | TimescaleDB 自动管理 |

所以从应用视角：

~~~sql
SELECT *
FROM performance_samples;
~~~

看到所有数据。

从底层视角：

~~~text
这些 Row
实际分布在多个 Chunk
~~~

### 【第四层：Table 的总数据量仍然一直增长，但单张物理表不再无限增长】

#### <u>1. 从业务和 SQL 视角看，Hypertable 仍然一直增长</u>

假设每天 1000 万条：

~~~text
Day 1
performance_samples
逻辑上有 1000 万

Day 2
逻辑上有 2000 万

Day 10
逻辑上有 1 亿
~~~

执行：

~~~sql
SELECT COUNT(*)
FROM performance_samples;
~~~

仍然是在查询整张 Hypertable 的全部逻辑数据。

所以：

~~~text
Logical Dataset
仍然持续增长
~~~

#### <u>2. 从物理存储视角看，不再是一个 Physical Table 无限增长</u>

为了理解，假设：

~~~text
Chunk Interval = 1 day
~~~

这只是教学示例，不代表当前项目实际配置。

那么可能形成：

~~~text
performance_samples
Logical Dataset = 5000 万 Rows

底层：

Chunk 2026-10-01
    1000 万 Rows

Chunk 2026-10-02
    1000 万 Rows

Chunk 2026-10-03
    1000 万 Rows

Chunk 2026-10-04
    1000 万 Rows

Chunk 2026-10-05
    1000 万 Rows
~~~

所以：

~~~text
总数据：
仍然越来越多

但是：

单个 Physical Chunk：
只管理自己的时间范围
~~~

因此不能说：

~~~text
Hypertable 让 Table 不增长
~~~

正确表述是：

> **Hypertable 让整个逻辑数据集继续增长，但把不断增长的数据拆给多个较小的物理 Chunk 管理。**

### 【第五层：Chunk 为什么按照 observed_at 拆分】

回到项目：

~~~sql
SELECT create_hypertable(
  'performance_samples',
  'observed_at'
);
~~~

这两个参数分别表达：

~~~text
performance_samples
        ↓
哪张 Table 要被 TimescaleDB 管理

observed_at
        ↓
根据哪个字段
决定 Row 应该进入哪个 Chunk
~~~

所以 observed_at 不只是普通查询字段。

它同时变成：

~~~text
Partitioning Column
~~~

#### <u>1. 假设一个 Chunk 覆盖一天</u>

这里只为了理解。

例如：

~~~text
Chunk A

2026-10-01 00:00
~
2026-10-02 00:00


Chunk B

2026-10-02 00:00
~
2026-10-03 00:00


Chunk C

2026-10-03 00:00
~
2026-10-04 00:00
~~~

插入：

~~~text
Sample A

observed_at =
2026-10-01 08:20
~~~

TimescaleDB 判断这个时间属于 Chunk A 的时间范围，所以 Row 实际进入 Chunk A。

再插入：

~~~text
Sample B

observed_at =
2026-10-03 15:00
~~~

它会进入 Chunk C。

应用完全不用自己判断日期并选择目标表。

### 【第六层：真实 INSERT 过程到底发生了什么】

当前 Worker 最终只需要执行类似：

~~~sql
INSERT INTO performance_samples (
  project_id,
  sample_id,
  observed_at,
  ...
)
VALUES (...);
~~~

应用只知道：

~~~text
performance_samples
~~~

TimescaleDB 内部则可以理解为：

~~~text
Node / Worker
    ↓
INSERT INTO performance_samples
    ↓
PostgreSQL 接收 SQL
    ↓
TimescaleDB 识别：
performance_samples 是 Hypertable
    ↓
读取 Row 的 observed_at
    ↓
根据 observed_at
判断目标时间范围
    ↓
找到对应 Chunk
    ↓
Row 实际写入对应 Chunk
~~~

所以真正链路：

~~~text
Application SQL
       ↓
Hypertable
       ↓
Partition Routing
       ↓
Physical Chunk
       ↓
Row Storage
~~~

如果新的时间范围还没有对应 Chunk，TimescaleDB 会按自己的分区管理机制创建或使用新的 Chunk。

所以数据增长不再简单意味着一张物理表无限扩大，而更接近：

~~~text
Time Axis
    ↓
不断产生新的 Physical Partitions
~~~

### 【第七层：Chunk 是数据库对象，不是应用程序代码】

TimescaleDB 是 PostgreSQL Extension。

Extension 运行在 PostgreSQL Server 内部。

因此：

~~~text
Node.js
NestJS
Worker
~~~

都不会创建：

~~~text
class Chunk
new Chunk(...)
~~~

关系是：

~~~text
Node.js Application
        │
        │ SQL
        ▼
PostgreSQL
        │
        ├── TimescaleDB Extension
        │
        └── PostgreSQL Storage
                 │
                 ├── Chunk Table A
                 ├── Chunk Table B
                 └── Chunk Table C
~~~

所以：

> **Chunk 是 TimescaleDB 在 PostgreSQL 内部创建、注册和管理的真实子表，而不是 TypeScript / JavaScript 代码结构。**

### 【第八层：查询 performance_samples 时为什么不用手动查询 Chunk】

假设数据库内部：

~~~text
performance_samples

    Chunk A
    Chunk B
    Chunk C
    Chunk D
    Chunk E
~~~

应用依然可以：

~~~sql
SELECT *
FROM performance_samples
WHERE
  project_id = $1
  AND observed_at >= $2
  AND observed_at < $3;
~~~

原因是：

~~~text
performance_samples
~~~

对应用仍然代表：

~~~text
完整 Hypertable
~~~

PostgreSQL Planner 与 TimescaleDB 会根据时间条件：

~~~text
observed_at >= T1
observed_at < T2
~~~

判断：

~~~text
哪些 Chunk
可能包含这个时间范围
~~~

#### <u>1. 一个具体查询例子</u>

假设底层：

~~~text
Chunk A
10 月 1 日

Chunk B
10 月 2 日

Chunk C
10 月 3 日

Chunk D
10 月 4 日

Chunk E
10 月 5 日
~~~

用户查询：

~~~sql
WHERE observed_at >= '2026-10-03 10:00'
  AND observed_at <  '2026-10-03 11:00'
~~~

数据库可以判断：

~~~text
Chunk A
10/1
    ↓
一定没有
    ↓
跳过

Chunk B
10/2
    ↓
一定没有
    ↓
跳过

Chunk C
10/3
    ↓
可能存在
    ↓
查询

Chunk D
10/4
    ↓
一定没有
    ↓
跳过

Chunk E
10/5
    ↓
一定没有
    ↓
跳过
~~~

最终：

~~~text
5 Chunks
    ↓
只访问相关 Chunk
~~~

这就是：

~~~text
Chunk Pruning
~~~

也可以理解成：

~~~text
Partition Pruning
~~~

它解决的是：

> **先排除时间上绝对不可能包含目标数据的物理分区。**

### 【第九层：Chunk Pruning 和 Index 是两个不同层级】

当前项目：

~~~sql
SELECT create_hypertable(
  'performance_samples',
  'observed_at'
);
~~~

随后还有：

~~~sql
CREATE INDEX performance_project_time_idx
ON performance_samples(
  project_id,
  observed_at DESC
);
~~~

以及：

~~~sql
CREATE INDEX performance_project_route_time_idx
ON performance_samples(
  project_id,
  route_name,
  observed_at DESC
);
~~~

如果 Chunk 已经把数据拆开，为什么还需要 Index？

因为解决的是两个不同问题。

#### <u>1. Chunk Pruning 先确定查询哪些物理分区</u>

查询：

~~~sql
WHERE
  project_id = 'P001'
  AND observed_at >= T1
  AND observed_at < T2
~~~

第一步：

~~~text
observed_at 范围
    ↓
判断 Chunk 时间范围
    ↓
确定只需要相关 Chunks
~~~

解决的是：

> **哪些物理分区需要参与查询？**

#### <u>2. Index 再在相关 Chunk 内找目标 Row</u>

假设某个 Chunk 里面仍然有：

~~~text
1000 万 Rows
~~~

其中包含：

~~~text
Project A
Project B
Project C
...
~~~

还需要找：

~~~text
project_id = P001
~~~

这时才继续依赖：

~~~text
Index
~~~

所以查询路径：

~~~text
SELECT performance_samples
        ↓
WHERE observed_at BETWEEN T1 AND T2
        ↓
Chunk Pruning
        ↓
只保留相关 Chunks
        ↓
WHERE project_id = P001
        ↓
相关 Chunk 上的 Index
        ↓
Matching Rows
~~~

这就是：

~~~text
Partition
+
Index
~~~

两级访问。

#### <u>3. 当前索引直接对应真实 Query Pattern</u>

例如：

~~~sql
CREATE INDEX performance_project_time_idx
ON performance_samples(
  project_id,
  observed_at DESC
);
~~~

对应：

~~~text
Project
    +
Time Range
~~~

而：

~~~sql
CREATE INDEX performance_project_route_time_idx
ON performance_samples(
  project_id,
  route_name,
  observed_at DESC
);
~~~

对应：

~~~text
Project
    +
Route
    +
Time Range
~~~

因此当前访问路径可以理解成：

~~~text
Time Condition
    ↓
Chunk Pruning

Project / Route Condition
    ↓
Index Scan
~~~

Hypertable 没有替代 PostgreSQL Index，而是在 Index 之前增加了一层 Time Partition Pruning。

### 【第十层：为什么分成多个 Chunk 后，Index 也更容易管理】

普通大表：

~~~text
performance_samples
1 billion Rows
        ↓
一个非常大的 Index
~~~

可能意味着：

~~~text
Index Tree 更大

Memory Working Set 更大

写入需要持续维护大型 Index
~~~

分 Chunk 后可以近似理解成：

~~~text
Chunk A
    ↓
Index A

Chunk B
    ↓
Index B

Chunk C
    ↓
Index C
~~~

最近数据主要写入：

~~~text
Newest Chunk
~~~

因此活跃写入主要维护：

~~~text
Newest Chunk 对应的索引
~~~

而不是所有历史时间范围组成的一个单一超大物理结构。

所以 Chunk 改变的不只是：

~~~text
查询时少扫描一些数据
~~~

还改变：

~~~text
数据维护单位

索引维护单位

历史生命周期管理单位
~~~

### 【第十一层：Chunk Interval 决定一个 Physical Chunk 覆盖多大的时间范围】

现在再引入：

~~~text
Chunk Interval
~~~

就比较容易理解。

假设：

~~~text
chunk_time_interval = 1 day
~~~

就是：

~~~text
一个 Chunk
负责约一天的时间范围
~~~

于是：

~~~text
Day 1
    ↓
Chunk A

Day 2
    ↓
Chunk B

Day 3
    ↓
Chunk C
~~~

#### <u>1. Chunk Interval 不是每多少 Row 建一个 Chunk</u>

不是：

~~~text
每 100 万 Rows
创建一个 Chunk
~~~

而是：

~~~text
根据 Time Range
划分 Chunk
~~~

例如同一天：

~~~text
Project A
100 Rows

Project B
1000 万 Rows
~~~

如果都属于同一时间范围，仍然进入该时间范围对应的 Chunk。

所以：

~~~text
Chunk Row Count
≈
Ingest Rate
×
Chunk Time Interval
~~~

#### <u>2. Chunk 太大会重新接近 Giant Table 问题</u>

假设：

~~~text
一个 Chunk = 90 days
~~~

而每天写入量非常大。

那么一个 Chunk 本身就可能非常大：

~~~text
Large Chunk
    ↓
Large Index
    ↓
Large Working Set
    ↓
Maintenance Cost
~~~

#### <u>3. Chunk 太小又会产生大量管理开销</u>

例如：

~~~text
一个 Chunk = 1 minute
~~~

长期运行后会产生大量 Chunk。

随之增加：

~~~text
Metadata

Planning Overhead

Index Object Count

Background Job Management
~~~

所以 Chunk Interval 是典型 Trade-off：

~~~text
Larger Chunk
    ↓
Fewer Chunks
Lower Metadata Cost
but Larger Per-chunk Working Set

Smaller Chunk
    ↓
Smaller Individual Partition
but More Chunks / Metadata
~~~

### 【第十二层：当前项目的 Chunk Interval 到底是多少】

这个地方必须区分：

~~~text
源码明确了什么
~~~

和：

~~~text
源码没有明确什么
~~~

当前项目：

~~~sql
SELECT create_hypertable(
  'performance_samples',
  'observed_at',
  if_not_exists => TRUE
);
~~~

没有显式写：

~~~text
chunk_time_interval
~~~

所以：

> **从当前仓库不能确定 performance_samples 实际每个 Chunk 是一天、七天还是其他长度。**

当前代码只明确：

~~~text
Hypertable：
performance_samples

Partition Column：
observed_at
~~~

没有明确：

~~~text
Chunk Interval
~~~

因此文档中的“一天一个 Chunk”只能作为教学示例，不能描述成当前项目事实。

如果未来进入生产容量治理，需要结合：

~~~text
Actual TimescaleDB Version

Runtime Configuration

Ingest Rate

Chunk Count

Chunk Size

Index Size
~~~

再决定是否显式配置 Chunk Interval。

### 【第十三层：当前项目为什么选择 observed_at，而不是 last_updated_at】

performance_samples 有：

~~~text
observed_at

last_updated_at
~~~

为什么：

~~~sql
create_hypertable(
  'performance_samples',
  'observed_at'
)
~~~

而不是：

~~~text
last_updated_at
~~~

因为这两个时间表达的业务语义不同。

#### <u>1. observed_at 表示指标属于哪个实际观测时间</u>

例如：

~~~text
2026-10-01 10:05

用户这次 LCP = 2300ms
~~~

Analytics 查询：

~~~text
10:00 ~ 11:00
LCP 怎么变化
~~~

自然应该按照：

~~~text
observed_at
~~~

组织。

#### <u>2. last_updated_at 表示这一 Row 最后什么时候被修订</u>

例如 Web Vital：

~~~text
第一次：
sequence = 0

第二次：
sequence = 1

第三次：
sequence = 2
~~~

last_updated_at 会不断变化。

但是：

~~~text
这次性能观测属于哪个时间段
~~~

仍然由：

~~~text
observed_at
~~~

决定。

所以：

~~~text
Partition Time
~~~

应该与：

~~~text
业务主时间轴
~~~

一致。

### 【第十四层：当前项目不同 Hypertable 使用不同业务时间轴】

源码：

~~~text
telemetry_events
    ↓
occurred_at
~~~

因为关心：

~~~text
Event 什么时候发生
~~~

performance_samples：

~~~text
observed_at
~~~

因为关心：

~~~text
Metric 什么时候被观测
~~~

view_records：

~~~text
started_at
~~~

因为关心：

~~~text
View 什么时候开始
~~~

custom_event_samples：

~~~text
occurred_at
~~~

custom_signal_samples：

~~~text
occurred_at
~~~

custom_metric_samples：

~~~text
occurred_at
~~~

因此：

> **Partition Column 不是统一找一个 created_at，而是选择真正定义业务时间轴的字段。**

### 【第十五层：Primary Key 为什么也包含时间字段】

当前：

~~~sql
PRIMARY KEY (
  project_id,
  sample_id,
  observed_at
);
~~~

而不是：

~~~sql
PRIMARY KEY (
  project_id,
  sample_id
);
~~~

telemetry_events 同样：

~~~sql
PRIMARY KEY (
  project_id,
  event_id,
  occurred_at
);
~~~

这与 Hypertable 的分区模型有关。

TimescaleDB 对 Hypertable 上的 Unique Index / Primary Key 有分区列相关约束。

#### <u>1. 为什么唯一键需要包含时间分区列</u>

假设：

~~~text
Chunk A
10/01

Chunk B
10/02
~~~

如果只声明：

~~~text
event_id UNIQUE
~~~

数据库要保证：

~~~text
Chunk A
不存在 E1

Chunk B
不存在 E1

其他所有 Chunks
也不存在 E1
~~~

这会变成跨 Partition 的全局唯一判断。

当前项目的物理唯一键：

~~~text
project_id
+
event_id
+
occurred_at
~~~

把分区时间也纳入唯一性定义。

#### <u>2. Physical Uniqueness 不一定等于 Business Uniqueness</u>

业务可能真正认为：

~~~text
同一个 Project 下
eventId 应该唯一
~~~

但物理 Primary Key 是：

~~~text
project_id
+
event_id
+
occurred_at
~~~

理论上如果 event_id 相同但 occurred_at 不同，物理键仍不同。

所以：

~~~text
Physical Constraint
~~~

和：

~~~text
Business Idempotency
~~~

不是完全相同的概念。

当前项目后续在 Ingestion 层还会通过：

~~~text
Advisory Lock

Existing Event Query

Insert
~~~

补足协议级幂等语义。

这说明：

> **Time Partition 的物理约束有时会反过来影响 Primary Key 设计，而真正的业务唯一语义可能还需要应用层额外保证。**

### 【第十六层：Hypertable 与 PostgreSQL Partitioning 的关系】

PostgreSQL 本身就支持 Partitioning。

TimescaleDB Hypertable 可以先理解成：

~~~text
PostgreSQL Partitioning 基础
        ↓
TimescaleDB
增加 Time-oriented 自动管理
~~~

如果完全手工管理，也可以设计：

~~~text
performance_2026_10_01

performance_2026_10_02

performance_2026_10_03
~~~

但应用和运维就需要自己处理更多：

~~~text
创建新 Partition

管理时间范围

写入路由

删除旧 Partition

维护分区相关策略
~~~

TimescaleDB 的价值之一就是：

~~~text
把 Time-oriented Partition Management
做成数据库 Extension 能力
~~~

因此 Hypertable 可以直观理解成：

> **TimescaleDB 自动管理的一张按时间持续分区的 PostgreSQL 表。**

### 【第十七层：把当前项目的真实物理结构重新画清楚】

当前：

~~~sql
CREATE TABLE performance_samples (...);

SELECT create_hypertable(
  'performance_samples',
  'observed_at'
);
~~~

为了说明，假设教学示例中的 Chunk Interval 为一天。

可以理解成：

~~~text
Node.js / Worker
        │
        │
        │ INSERT INTO performance_samples
        ▼
┌────────────────────────────────────┐
│          PostgreSQL Server         │
│                                    │
│  ┌──────────────────────────────┐  │
│  │    TimescaleDB Extension     │  │
│  └──────────────────────────────┘  │
│                 │                  │
│                 ▼                  │
│       performance_samples          │
│          Hypertable                │
│        统一 SQL 访问入口             │
│                 │                  │
│       根据 observed_at 路由          │
│                 │                  │
│        ┌────────┼────────┐         │
│        ▼        ▼        ▼         │
│      Chunk A  Chunk B  Chunk C     │
│        │        │        │         │
│      PG Table PG Table PG Table    │
│        │        │        │         │
│      Index A  Index B  Index C     │
│                                    │
└────────────────────────────────────┘
~~~

插入：

~~~text
observed_at =
2026-10-02 12:30
~~~

最终：

~~~text
performance_samples
        ↓
TimescaleDB Routing
        ↓
对应时间范围的 Chunk
        ↓
真实 Row 存入该 Chunk
~~~

这就是整个物理机制。

### 【第十八层：当前源码实际上连续定义了三个不同层次】

当前：

~~~sql
CREATE TABLE performance_samples (...);
~~~

第一步定义：

~~~text
Row 长什么样

字段类型

Constraint

Foreign Key

Primary Key
~~~

这是：

~~~text
Logical Data Schema
~~~

然后：

~~~sql
SELECT create_hypertable(
  'performance_samples',
  'observed_at'
);
~~~

第二步定义：

~~~text
这份数据
怎样按照时间被物理组织
~~~

这是：

~~~text
Physical Time Partition Strategy
~~~

接着：

~~~sql
CREATE INDEX performance_project_time_idx
ON performance_samples(
  project_id,
  observed_at DESC
);
~~~

第三步定义：

~~~text
进入相关 Chunk 后
怎样快速找到目标 Rows
~~~

这是：

~~~text
Query Access Path
~~~

所以当前源码真正的层次是：

~~~text
CREATE TABLE
    ↓
定义 Row / Schema

create_hypertable
    ↓
定义 Physical Time Partition Strategy

CREATE INDEX
    ↓
定义 Query Access Path
~~~

这三部分不是互相独立的 SQL，而是一条完整的数据组织链。

### 【第二节最终形成 Hypertable 与 Chunk 的直观框架】

最终只需要固定十个事实：

~~~text
1.
performance_samples
仍然是应用访问的 PostgreSQL Table 名称

2.
create_hypertable 以后
应用的 INSERT / SELECT 基本不需要改写

3.
Hypertable 是应用看到的统一逻辑数据集

4.
Chunk 是 TimescaleDB 在 PostgreSQL 内部
创建和管理的真实子表

5.
真正的数据 Row
会按照时间被写入对应 Chunk

6.
整个 Hypertable 的总数据量
仍然会不断增加

7.
变化的是：
不再由一个单一 Physical Table
承担全部历史数据

8.
查询带时间条件时
TimescaleDB 可以先排除无关 Chunk

9.
进入相关 Chunk 后
仍然依靠 PostgreSQL Index
查找 Project / Route / Sample 等 Row

10.
Chunk 还是后续
Compression / Retention / Historical Lifecycle
的重要管理单位
~~~

最终可以压缩成一句：

> **Hypertable 是应用继续访问的一张 PostgreSQL 逻辑表；Chunk 是 TimescaleDB 在 PostgreSQL 内部自动创建的真实子表，真正的数据 Row 按时间分布到这些 Chunk 中。因此总数据仍在增长，但不再由一张单一物理表无限膨胀。**

## 3. Time Range Query 将时序数据从原始 Row 转换成可分析的趋势结果

第二节解决的是：

~~~text
数据怎样存

performance_samples
    ↓
Hypertable
    ↓
Chunk
    ↓
Physical Row Storage
~~~

第三节继续解决：

> **这些已经存进 Chunk 的数据，在一次 Analytics 查询中，怎样从原始 Row 变成前端可以展示的时间趋势？**

这一节不把：

~~~text
Time Range
Chunk Pruning
Index
time_bucket
GROUP BY
Aggregate
~~~

拆成多个互相并列的大标题。

因为它们本质上属于同一条 Query Pipeline。

整个查询真正只有四个主要部分：

~~~text
Time-Series Query
│
├── 一、Data Selection
│      ↓
│   找到本次查询真正需要的 Raw Rows
│
├── 二、Analytical Aggregation
│      ↓
│   把 Raw Rows 转换成 Trend Points
│
├── 三、Query Model
│      ↓
│   Detail Query 与 Aggregate Query
│   使用不同结果模型
│
└── 四、Temporal Alignment
       ↓
    多条时序序列通过统一 Bucket
    对齐到同一时间坐标轴
~~~

先建立完整执行链：

~~~text
Analytics Request
        ↓
Project Scope
+
from / to
        ↓
Relevant Chunks
        ↓
Matching Raw Rows
        ↓
        ├──────────── Detail Query
        │                   ↓
        │              Order + Cursor
        │
        └──────────── Aggregate Query
                            ↓
                        time_bucket
                            ↓
                     Business Dimension
                            ↓
                         GROUP BY
                            ↓
                        Aggregate
                            ↓
                         Trend Point
~~~

### 【一、Data Selection 先确定本次查询真正需要哪些 Raw Rows】

这一部分还没有开始做统计。

它只解决：

> **数据库里已经积累了大量历史数据，这次请求究竟需要读取哪一部分？**

当前 AnalyticsService 把这一层统一封装在 filters() 中。

#### <u>1. 项目源码先把业务 Scope 与 Time Range 转成 SQL Predicate</u>

当前源码：

~~~ts
private filters(
  alias: string,
  timeColumn: string,
  projectId: string,
  filters: AnalyticsFilters,
): SqlFilter {
  const values: unknown[] = [
    projectId,
    filters.from,
    filters.to,
  ];

  const conditions = [
    alias + ".project_id = $1",
    alias + "." + timeColumn + " >= $2",
    alias + "." + timeColumn + " < $3",
  ];

  const add = (
    column: string,
    value: string | undefined,
  ): void => {
    if (!value) return;

    values.push(value);

    conditions.push(
      alias + "." + column + " = $" + values.length,
    );
  };

  add("environment", filters.environment);
  add("app_version", filters.version);
  add("route_name", filters.routeName);

  if (filters.metric && alias === "p") {
    add("name", filters.metric);
  }

  return {
    where: conditions.join(" AND "),
    values,
  };
}
~~~

针对 performance_samples：

~~~ts
const filter = this.filters(
  "p",
  "observed_at",
  projectId,
  filters,
);
~~~

最终会形成类似：

~~~sql
WHERE
  p.project_id = $1
  AND p.observed_at >= $2
  AND p.observed_at < $3
~~~

如果还有：

~~~text
environment
version
routeName
metric
~~~

则继续增加：

~~~sql
AND p.environment = ...
AND p.app_version = ...
AND p.route_name = ...
AND p.name = ...
~~~

这里可以把所有条件分成两类：

~~~text
Business Scope
│
├── project_id
├── environment
├── app_version
├── route_name
└── metric

Time Scope
│
├── from
└── to
~~~

所以 Data Selection 的第一步不是 time_bucket。

而是：

~~~text
All Historical Data
        ↓
Business Scope
+
Time Scope
        ↓
Candidate Raw Data
~~~

#### <u>2. Time Range 不只是业务过滤条件，也直接对应 Hypertable 的物理分区边界</u>

假设：

~~~text
from = 2026-10-03 10:00

to   = 2026-10-03 11:00
~~~

SQL：

~~~sql
p.observed_at >= '2026-10-03 10:00'
AND
p.observed_at < '2026-10-03 11:00'
~~~

业务上表示：

~~~text
用户只想看
10:00 ~ 11:00
这一个小时的数据
~~~

但第二节已经知道：

~~~text
performance_samples
按照 observed_at
被划分到不同 Chunks
~~~

所以这个条件同时能够帮助数据库判断：

~~~text
哪些 Chunk 的时间范围
与 10:00 ~ 11:00
完全不相交
~~~

这些 Chunk 就没有必要参与本次查询。

例如教学示例中：

~~~text
Chunk A
10/01

Chunk B
10/02

Chunk C
10/03

Chunk D
10/04
~~~

查询：

~~~text
10/03 10:00
~
10/03 11:00
~~~

可以先得到：

~~~text
Chunk A
    ↓
时间不重叠
    ↓
排除

Chunk B
    ↓
时间不重叠
    ↓
排除

Chunk C
    ↓
存在重叠
    ↓
参与查询

Chunk D
    ↓
时间不重叠
    ↓
排除
~~~

这就是：

~~~text
Chunk Pruning
~~~

所以这里真正的关系是：

~~~text
WHERE observed_at >= from
AND   observed_at < to
        │
        ├── 业务意义：
        │   选择用户想看的时间范围
        │
        └── 物理意义：
            排除无关 Chunk
~~~

#### <u>3. Chunk Pruning 只缩小 Physical Partition 范围，还没有找到最终 Rows</u>

假设最终只剩：

~~~text
Chunk C
~~~

但 Chunk C 里可能仍然有：

~~~text
Project A
Project B
Project C

LCP
INP
CLS

/checkout
/home
/search

数百万甚至更多 Rows
~~~

所以：

~~~text
Relevant Chunk
≠
Final Result
~~~

Chunk Pruning 只解决：

~~~text
从哪些物理子表读取？
~~~

还需要继续解决：

~~~text
这些子表里面
哪些 Row 真正满足条件？
~~~

#### <u>4. Index 与其他 Predicate 再在相关 Chunk 中寻找真正匹配的 Row</u>

当前项目已经建立：

~~~sql
CREATE INDEX performance_project_time_idx
ON performance_samples(
  project_id,
  observed_at DESC
);
~~~

以及：

~~~sql
CREATE INDEX performance_project_route_time_idx
ON performance_samples(
  project_id,
  route_name,
  observed_at DESC
);
~~~

所以：

~~~sql
WHERE
  project_id = 'P001'
  AND route_name = '/checkout'
  AND observed_at >= T1
  AND observed_at < T2
~~~

可以形成：

~~~text
Hypertable
    ↓
Time Range
    ↓
Relevant Chunks
    ↓
Project / Route / Time Predicate
    ↓
Index / Scan
    ↓
Matching Raw Rows
~~~

这里要保留一个 PostgreSQL 基础边界：

> **存在 Index 不代表 PostgreSQL 每次一定执行 Index Scan。**

真实 Physical Plan 仍由 PostgreSQL Planner 根据：

~~~text
数据统计

Predicate Selectivity

Chunk Size

查询范围

Index Cost

Sequential Scan Cost

Parallelism
~~~

决定。

因此当前索引的准确含义是：

~~~text
项目为
Project + Time

以及
Project + Route + Time

提供了合适的 Index Access Path
~~~

而不是：

~~~text
所有查询一定使用这个 Index
~~~

#### <u>5. Data Selection 最终只应该理解成一条连续链</u>

所以前面的 Scope、Time Range、Chunk Pruning、Index 不应该各自被提升成平级知识模块。

它们共同完成一件事情：

~~~text
Data Selection

All Historical Data
        ↓
Project / Dimension Scope
        ↓
Time Range
        ↓
Chunk Pruning
        ↓
Index / Predicate
        ↓
Matching Raw Rows
~~~

到这里为止，数据库已经找到本次查询真正需要的原始数据。

但还没有：

~~~text
一分钟一个点

平均值

p75

趋势图
~~~

这些属于下一阶段。

### 【二、Analytical Aggregation 再把 Raw Rows 转换成 Trend Points】

假设 Data Selection 最终得到：

| observed_at | name | value |
|---|---|---:|
| 10:00:05 | LCP | 2100 |
| 10:00:18 | LCP | 2500 |
| 10:00:45 | INP | 180 |
| 10:01:03 | LCP | 1900 |
| 10:01:25 | LCP | 2300 |
| 10:01:40 | INP | 120 |
| 10:02:08 | LCP | 3000 |

这些仍然是一条一条 Raw Sample。

前端趋势图需要的却是：

~~~text
10:00
LCP p75 = ...

10:01
LCP p75 = ...

10:02
LCP p75 = ...
~~~

所以接下来需要：

~~~text
Analytical Aggregation
~~~

这一部分也只是一条连续链：

~~~text
Matching Raw Rows
        ↓
time_bucket
        ↓
Business Dimension
        ↓
GROUP BY
        ↓
Aggregate
        ↓
Trend Point
~~~

#### <u>1. time_bucket 只负责把 timestamp 映射到统计时间窗口</u>

当前 performance()：

~~~sql
SELECT
  time_bucket(
    INTERVAL '1 minute',
    observed_at
  ) AS bucket,
  name,
  ...
~~~

对于每一条 Row：

~~~text
10:00:05
    ↓
10:00:00

10:00:18
    ↓
10:00:00

10:00:45
    ↓
10:00:00

10:01:03
    ↓
10:01:00

10:01:59
    ↓
10:01:00
~~~

所以 time_bucket 可以先理解成：

~~~text
Timestamp
    ↓
Bucket Function
    ↓
Bucket Start Time
~~~

例如：

~~~text
time_bucket(
  1 minute,
  10:00:37
)

=
10:00:00
~~~

它不会：

~~~text
创建 Chunk

创建 Table

移动 Row

改变 observed_at

重新分区
~~~

它只是查询中的时间分组函数。

#### <u>2. Chunk 与 time_bucket 都使用时间，但属于完全不同层次</u>

第二节的 Chunk：

~~~text
Chunk
    ↓
Physical Storage Partition
~~~

这一节的 time_bucket：

~~~text
time_bucket
    ↓
Analytical Time Group
~~~

可以直接比较：

| 维度 | Chunk | time_bucket |
|---|---|---|
| 所属阶段 | 数据存储 | 查询分析 |
| 是不是实际表 | 是 | 不是 |
| 是否真正保存 Row | 是 | 否 |
| 什么时候产生作用 | INSERT / Storage Management | SELECT / Aggregation |
| 核心输入 | Partition Time + Chunk Interval | Timestamp + Bucket Interval |
| 解决的问题 | Row 物理存在哪里 | Row 属于哪个统计时间组 |

因此：

~~~text
Chunk
=
物理时间分区

time_bucket
=
统计时间分组
~~~

二者不能混为一谈。

#### <u>3. Chunk Interval 与 time_bucket Interval 可以完全不同</u>

为了理解，假设：

~~~text
Chunk Interval = 1 day
~~~

表示：

~~~text
物理上
一天的数据
可能存放在同一个 Chunk
~~~

但查询仍然可以：

~~~sql
time_bucket(
  INTERVAL '1 minute',
  observed_at
)
~~~

那么：

~~~text
一个 1-day Chunk
内部可以产生
1440 个 1-minute Analytical Buckets
~~~

反过来：

~~~text
Chunk Interval = 1 hour
~~~

查询也可以：

~~~sql
time_bucket(
  INTERVAL '1 day',
  observed_at
)
~~~

这时一个 1-day Analytical Bucket 可以覆盖多个 1-hour Physical Chunks。

所以：

~~~text
Physical Partition Granularity
和
Analytical Granularity
~~~

是两个独立设计参数。

#### <u>4. time_bucket 只是给每一条 Row 计算 bucket，真正形成统计组还需要 GROUP BY</u>

执行：

~~~sql
time_bucket(
  INTERVAL '1 minute',
  observed_at
) AS bucket
~~~

以后，数据可以理解成：

| observed_at | bucket | name | value |
|---|---|---|---:|
| 10:00:05 | 10:00:00 | LCP | 2100 |
| 10:00:18 | 10:00:00 | LCP | 2500 |
| 10:00:45 | 10:00:00 | INP | 180 |
| 10:01:03 | 10:01:00 | LCP | 1900 |
| 10:01:25 | 10:01:00 | LCP | 2300 |

此时 Row 仍然没有合并，只是多了 bucket 这个计算结果。

源码继续：

~~~sql
GROUP BY
  bucket,
  name
~~~

才把：

~~~text
相同 Bucket
+
相同 Metric Name
~~~

归为同一个 Statistical Group。

#### <u>5. Business Dimension 决定一个时间 Bucket 内还要按什么继续拆组</u>

为什么不能只：

~~~sql
GROUP BY bucket
~~~

因为同一分钟可能同时存在：

~~~text
10:00

LCP
LCP
LCP

INP
INP

CLS
CLS
~~~

如果只按 bucket，会把：

~~~text
LCP + INP + CLS
~~~

混在同一个统计组。

所以真正的 Group Key 是：

~~~text
Time Dimension
+
Business Dimension
~~~

当前就是：

~~~text
bucket
+
name
~~~

即：

~~~text
10:00 + LCP

10:00 + INP

10:00 + CLS

10:01 + LCP
...
~~~

可以抽象：

~~~text
Aggregate Group
=
Time Bucket
×
Business Dimensions
~~~

未来如果继续加入 environment、route、browser、region 等 Dimension，本质是在扩展 Group Cardinality，而不是改变 time_bucket 的作用。

#### <u>6. Aggregate 才真正把多条 Raw Rows 压缩成一个统计结果</u>

当前源码：

~~~sql
count(*)::bigint
  AS count,

count(DISTINCT session_id)::bigint
  AS session_count,

count(DISTINCT view_id)::bigint
  AS view_count,

avg(value)
  AS average,

percentile_cont(0.50)
  WITHIN GROUP (ORDER BY value)
  AS p50,

percentile_cont(0.75)
  WITHIN GROUP (ORDER BY value)
  AS p75,

percentile_cont(0.90)
  WITHIN GROUP (ORDER BY value)
  AS p90,

percentile_cont(0.95)
  WITHIN GROUP (ORDER BY value)
  AS p95
~~~

还会继续统计：

~~~sql
count(*) FILTER (
  WHERE server_rating = 'good'
)
  AS good_count,

count(*) FILTER (
  WHERE server_rating = 'needs-improvement'
)
  AS needs_improvement_count,

count(*) FILTER (
  WHERE server_rating = 'poor'
)
  AS poor_count
~~~

例如 10:00 的 LCP：

~~~text
1900
2100
2300
2500
~~~

最终得到：

~~~text
bucket = 10:00

name = LCP

count = 4

average = 2200

p50 = ...

p75 = ...

p90 = ...

p95 = ...
~~~

于是：

~~~text
Many Raw Rows
        ↓
Aggregate
        ↓
One Trend Point
~~~

这才是前端图表真正消费的数据。

### 【三、Query Model 决定读取 Raw Detail 还是 Aggregate Trend】

到这里需要再抽象一层。

Time-Series Query 并不等于：

~~~text
所有查询都必须 time_bucket
~~~

当前项目实际上同时存在两种完全不同的查询模型：

~~~text
Time-Series Query
│
├── Detail Query
│      ↓
│   保留每一条原始事实
│
└── Aggregate Query
       ↓
    把大量 Raw Rows
    压缩成 Trend Points
~~~

它们前半段都可能经历：

~~~text
Business Scope
    ↓
Time Range
    ↓
Chunk Pruning
    ↓
Row Filtering
~~~

真正不同的是：

~~~text
Matching Rows
之后怎样返回结果
~~~

#### <u>1. Detail Query 保留原始 Row，不进入 time_bucket</u>

当前 rawEvents()：

~~~ts
async rawEvents(
  userId: string,
  projectId: string,
  filters: AnalyticsFilters,
  cursor: string | undefined,
  limit: number,
  ...
) {
  await this.projects.requireAccess(
    userId,
    projectId,
  );

  const filter = this.filters(
    "e",
    "occurred_at",
    projectId,
    filters,
  );

  ...
}
~~~

这里同样使用：

~~~text
project_id

occurred_at >= from

occurred_at < to
~~~

所以同样首先经历：

~~~text
Scope
    ↓
Time Range
    ↓
Relevant Chunks
    ↓
Matching telemetry_events Rows
~~~

但是后面没有：

~~~text
time_bucket

GROUP BY

Aggregate
~~~

而是继续：

~~~sql
ORDER BY
  occurred_at DESC,
  event_id DESC
~~~

并使用 Cursor Pagination。

当前 Cursor 条件：

~~~sql
(
  e.occurred_at,
  e.event_id
)
<
(
  cursorOccurredAt,
  cursorEventId
)
~~~

完整链路：

~~~text
Detail Query
    ↓
Business Scope
    ↓
Time Range
    ↓
Chunk Pruning
    ↓
Matching Rows
    ↓
Time Order
    ↓
Cursor Pagination
    ↓
Raw Events
~~~

它的目标是：

> **保留每一条事实，让用户能够看到具体发生了什么。**

这种查询需要的是：

~~~text
Detail
+
Order
+
Pagination
~~~

而不是：

~~~text
一分钟一个统计值
~~~

#### <u>2. Aggregate Query 不关心每一条 Row，而关心一段时间整体表现</u>

当前 performance()：

~~~text
performance_samples
    ↓
Scope / Time Range
    ↓
Matching Rows
    ↓
time_bucket
    ↓
GROUP BY
    ↓
Aggregate
    ↓
Trend Points
~~~

它最终不会返回：

~~~text
10:00:05 LCP = 2100

10:00:18 LCP = 2500

10:00:35 LCP = 1900
~~~

而是返回：

~~~text
10:00
LCP
count = ...
average = ...
p75 = ...
p95 = ...
~~~

因此它的目标是：

> **回答这一段时间整体表现如何变化，而不是逐条展示所有事实。**

#### <u>3. 两种 Query Model 的差异本质上是结果表示方式不同</u>

| 查询模型 | Detail Query | Aggregate Query |
|---|---|---|
| 目标 | 查看具体事实 | 查看趋势 |
| Time Range | 有 | 有 |
| Chunk Pruning | 有 | 有 |
| Row Predicate | 有 | 有 |
| time_bucket | 无 | 有 |
| GROUP BY | 无 | 有 |
| Aggregate Function | 无 | 有 |
| 排序 | 通常按时间 | 通常按 Bucket |
| 分页 | 常见 Cursor | 通常直接返回 Trend Points |
| 返回粒度 | 一条 Row | 一个统计组 |

所以更准确的流程是：

~~~text
先选择数据
    ↓
再根据业务问题
选择结果模型
~~~

即：

~~~text
Matching Rows
        ↓
        ├── Detail
        │     ↓
        │  Order / Cursor
        │
        └── Aggregate
              ↓
           Bucket / Group / Aggregate
~~~

#### <u>4. Query Model 应由产品问题决定，而不是由数据库类型决定</u>

例如：

~~~text
过去 10 分钟发生了哪些错误？
    ↓
Detail Query
~~~

而：

~~~text
过去 24 小时每分钟错误率是多少？
    ↓
Aggregate Query
~~~

所以不是：

~~~text
用了 TimescaleDB
    ↓
所有查询都应该 time_bucket
~~~

而是：

~~~text
Product Question
    ↓
Result Model
    ↓
Query Model
~~~

这是能够脱离当前项目复用的判断方式。

### 【四、Temporal Alignment 用统一 Bucket 把多条时序序列放到同一时间坐标轴】

当前 performance() 还有一个比单表聚合更进一步的设计：

它不是只查询：

~~~text
performance_samples
~~~

而是同时查询：

~~~text
performance_samples
+
view_records
~~~

并把两条时序序列放到同一个分钟时间轴上。

当前 SQL：

~~~sql
WITH metric_points AS (
  ...
),
view_points AS (
  ...
)

SELECT
  m.*,
  COALESCE(
    v.page_views,
    0
  ) AS page_views

FROM metric_points m

LEFT JOIN view_points v
USING (bucket)

ORDER BY
  m.bucket,
  m.name
~~~

这一部分需要先分别看两条序列，再看它们怎样通过 bucket 对齐。

#### <u>1. Performance Series 先形成自己的分钟时间点</u>

当前：

~~~sql
SELECT
  time_bucket(
    INTERVAL '1 minute',
    observed_at
  ) AS bucket,
  name,
  ...
FROM performance_samples p
WHERE ...
GROUP BY
  bucket,
  name
~~~

结果可以理解成：

| bucket | name | count | p75 |
|---|---|---:|---:|
| 10:00 | LCP | 20 | 2300 |
| 10:00 | INP | 15 | 180 |
| 10:01 | LCP | 22 | 2400 |
| 10:01 | INP | 18 | 170 |

形成：

~~~text
Performance Series
        ↓
10:00
10:01
10:02
...
~~~

#### <u>2. View Series 也被映射到同样的一分钟时间轴</u>

当前：

~~~sql
SELECT
  time_bucket(
    INTERVAL '1 minute',
    started_at
  ) AS bucket,

  count(*)::bigint
    AS page_views

FROM view_records v

WHERE ...

GROUP BY bucket
~~~

结果：

| bucket | page_views |
|---|---:|
| 10:00 | 100 |
| 10:01 | 120 |
| 10:02 | 95 |

形成：

~~~text
View Series
        ↓
10:00
10:01
10:02
...
~~~

虽然两个表原始时间字段不同：

~~~text
performance_samples
    ↓
observed_at

view_records
    ↓
started_at
~~~

但经过：

~~~text
同一个 1 minute time_bucket
~~~

以后，都映射成：

~~~text
bucket
~~~

这个共同时间键。

#### <u>3. USING(bucket) 实际上是在做时间对齐</u>

当前：

~~~sql
LEFT JOIN view_points v
USING (bucket)
~~~

不是普通业务主键 Join。

它不是：

~~~text
performance_id
=
view_id
~~~

而是：

~~~text
两条不同 Time Series
在同一个时间窗口里
分别发生了什么
~~~

例如：

~~~text
10:00

Performance:
LCP Samples = 20

View:
Page Views = 100
~~~

通过：

~~~text
bucket = 10:00
~~~

对齐成：

~~~text
10:00
│
├── LCP Samples = 20
└── Page Views   = 100
~~~

因此 bucket 在这里除了作为：

~~~text
统计时间分组
~~~

还承担：

~~~text
Temporal Join Key
~~~

#### <u>4. Temporal Alignment 让跨序列指标成为可能</u>

当前最终返回：

~~~ts
sampleCoverage:
  Number(row.page_views) > 0
    ? Number(row.view_count)
      / Number(row.page_views)
    : 0
~~~

这个指标依赖：

~~~text
Performance View Count
        ↓
同一分钟

Page View Count
        ↓
同一分钟
~~~

如果两条序列没有统一时间粒度：

~~~text
Performance
10:00:05
10:00:18
10:00:43

View
10:00:02
10:00:37
10:00:58
~~~

就无法直接形成：

~~~text
10:00
统一统计结果
~~~

time_bucket 先把两边都映射到：

~~~text
10:00
~~~

于是才能进行：

~~~text
Temporal Alignment
        ↓
Cross-series Metric
~~~

#### <u>5. 这种模式可以抽象成通用 Multi-Series Analytics</u>

脱离当前项目：

~~~text
Series A
    ↓
自己的 Timestamp
    ↓
Common Bucket
        ┐
        │
        ├── Temporal Join
        │
Series B│
    ↓   │
自己的 Timestamp
    ↓   │
Common Bucket
        ┘
        ↓
Composite Metric
~~~

常见场景：

~~~text
Requests
+
Errors
    ↓
Error Rate

Orders
+
Users
    ↓
Orders per User

CPU
+
Traffic
    ↓
Resource per Request

Performance Samples
+
Page Views
    ↓
Sample Coverage
~~~

所以 time_bucket 不仅可以用于：

~~~text
Single-Series Aggregation
~~~

还可以作为：

~~~text
Cross-Series Temporal Alignment
~~~

的共同时间坐标。

### 【五、第三节收束：时序查询先选数据，再决定结果模型】

这一节真正只有四个主要分支：

~~~text
Time-Series Query
│
├── 一、Data Selection
│   │
│   ├── Business Scope
│   ├── Time Range
│   ├── Chunk Pruning
│   └── Index / Predicate
│
├── 二、Analytical Aggregation
│   │
│   ├── time_bucket
│   ├── Business Dimension
│   ├── GROUP BY
│   └── Aggregate
│
├── 三、Query Model
│   │
│   ├── Detail Query
│   │     └── Order + Cursor
│   │
│   └── Aggregate Query
│         └── Bucket + Group + Aggregate
│
└── 四、Temporal Alignment
    │
    ├── Series A → Common Bucket
    ├── Series B → Common Bucket
    └── Join by Bucket → Composite Metric
~~~

#### <u>1. Data Selection 只解决本次请求需要读取哪些 Raw Rows</u>

~~~text
All Historical Data
        ↓
Business Scope
        ↓
Time Range
        ↓
Chunk Pruning
        ↓
Index / Predicate
        ↓
Matching Raw Rows
~~~

核心问题：

> **这次请求到底需要读取哪些原始数据？**

#### <u>2. Analytical Aggregation 解决 Raw Rows 怎样变成趋势</u>

~~~text
Matching Raw Rows
        ↓
time_bucket
        ↓
Business Dimension
        ↓
GROUP BY
        ↓
Aggregate
        ↓
Trend Point
~~~

核心问题：

> **这些 Raw Rows 怎样被压缩成时间趋势？**

#### <u>3. Query Model 决定返回具体事实还是统计趋势</u>

~~~text
Matching Rows
        ↓
        ├── Detail
        │     ↓
        │  Raw Facts
        │
        └── Aggregate
              ↓
           Trend Points
~~~

核心问题：

> **产品真正需要的是具体事实，还是整体趋势？**

#### <u>4. Temporal Alignment 解决多个时序数据源怎样关联</u>

~~~text
Series A
    ↓
Bucket
        ┐
        ├── Join
        │
Series B│
    ↓   │
Bucket  ┘
        ↓
Composite Metric
~~~

核心问题：

> **不同来源的数据怎样被放到同一个时间坐标轴上做关联计算？**

#### <u>第三节最重要的三个概念边界</u>

第一：

~~~text
Chunk
=
物理存储分区

time_bucket
=
查询统计分组
~~~

第二：

~~~text
Time Range
=
本次请求读取哪一段历史数据

time_bucket
=
读出来以后怎样按时间重新组织
~~~

第三：

~~~text
Detail Query
=
保留 Raw Facts

Aggregate Query
=
压缩为 Trend Points
~~~

因此可以把整个第三节压缩成：

> **时序查询首先通过业务 Scope 与 Time Range 缩小需要读取的物理数据范围，再根据产品问题选择 Detail 或 Aggregate 结果模型；Aggregate Query 使用 time_bucket、Business Dimension、GROUP BY 和统计函数把 Raw Rows 转换成 Trend Points，而多个不同时间序列还可以通过统一 Bucket 对齐后形成跨序列指标。**

## 4. Continuous Aggregate 把重复的查询时聚合转换成数据库后台维护的预计算结果

第三节已经解决：

~~~text
Raw Time-Series Data
        ↓
Data Selection
        ↓
Matching Raw Rows
        ↓
time_bucket
        ↓
GROUP BY
        ↓
Aggregate
        ↓
Trend Points
~~~

这里继续出现一个新的问题。

假设 Dashboard 查询：

~~~text
过去 24 小时
每分钟 LCP
count / avg / p75 / p95
~~~

当前近期查询每请求一次，数据库都会重新：

~~~text
读取 Raw Rows
    ↓
重新 time_bucket
    ↓
重新 GROUP BY
    ↓
重新 count
    ↓
重新 avg
    ↓
重新算 percentile
~~~

如果同一个 Dashboard 被大量重复访问，那么历史数据上的同一批统计会被反复计算。

因此这一节真正解决的问题是：

> **对于已经发生、而且经常被重复统计的历史数据，为什么每次查询都重新从 Raw Rows 开始计算？**

Continuous Aggregate 就是从这个问题出现的。

整个知识框架只有四个主要部分：

~~~text
Continuous Aggregate
│
├── 一、Repeated Computation
│      ↓
│   为什么需要 Precomputation
│
├── 二、Materialization
│      ↓
│   Continuous Aggregate
│   实际保存了什么
│
├── 三、Refresh
│      ↓
│   Raw Data 变化以后
│   预计算结果怎样更新
│
└── 四、Read Architecture
       ↓
    Raw Detail
    1m Aggregate
    1h Aggregate
    如何在当前项目中分工
~~~

### 【一、Repeated Computation 是 Continuous Aggregate 出现的直接原因】

#### <u>1. 当前近期 Performance 查询是标准 Query-time Aggregation</u>

analytics.service.ts 中：

~~~ts
async performance(
  userId: string,
  projectId: string,
  filters: AnalyticsFilters,
) {
  await this.projects.requireAccess(
    userId,
    projectId,
  );

  if (this.useRollups(filters)) {
    return this.performanceFromRollups(
      projectId,
      filters,
    );
  }

  ...
}
~~~

如果时间范围没有进入历史 Rollup：

~~~ts
const filter = this.filters(
  "p",
  "observed_at",
  projectId,
  filters,
);
~~~

然后直接查询：

~~~sql
FROM performance_samples p
WHERE ...
~~~

再执行：

~~~sql
time_bucket(
  INTERVAL '1 minute',
  observed_at
)
~~~

随后：

~~~sql
GROUP BY
  bucket,
  name
~~~

并重新计算：

~~~sql
count(*)

count(DISTINCT session_id)

count(DISTINCT view_id)

avg(value)

percentile_cont(0.50)

percentile_cont(0.75)

percentile_cont(0.90)

percentile_cont(0.95)
~~~

这就是：

~~~text
Query-time Aggregation
~~~

完整逻辑：

~~~text
Request
    ↓
Raw performance_samples
    ↓
Time Range
    ↓
Matching Rows
    ↓
time_bucket
    ↓
GROUP BY
    ↓
Aggregate
    ↓
Result
~~~

#### <u>2. Query-time Aggregation 本身没有问题，问题出现在大量重复计算</u>

例如数据库已经有：

~~~text
10 月 1 日
1000 万条 performance_samples
~~~

用户第一次请求：

~~~text
10 月 1 日
每分钟 LCP p75
~~~

数据库需要：

~~~text
读取相关 Rows
    ↓
分成分钟 Bucket
    ↓
计算每分钟 p75
~~~

这本身是合理的。

但第二个用户请求完全相同的数据时：

~~~text
10 月 1 日
每分钟 LCP p75
~~~

数据库又重新：

~~~text
读取
    ↓
分组
    ↓
排序 / percentile
    ↓
计算
~~~

第三次、第四次仍然重复相同工作。

最终形成：

~~~text
Historical Raw Data
        │
        ├── Query 1
        │      ↓
        │   Aggregate
        │
        ├── Query 2
        │      ↓
        │   Same Aggregate
        │
        ├── Query 3
        │      ↓
        │   Same Aggregate
        │
        └── Query N
               ↓
            Same Aggregate
~~~

真正的问题不是 SELECT 本身，而是：

> **大量基本不会再变化的历史数据，被反复执行相同的聚合计算。**

#### <u>3. Precomputation 把重复工作从 Read Path 搬到后台</u>

假设：

~~~text
10:00 ~ 10:01
~~~

这一分钟已经结束，并且其中存在：

~~~text
100000 条 LCP Samples
~~~

后续大量查询真正需要的可能只是：

~~~text
10:00

count
min
max
avg
p75
good count
poor count
...
~~~

那么就可以提前计算一次：

~~~text
100000 Raw Rows
        ↓
Background Aggregate
        ↓
1 Aggregate State
~~~

以后多个请求直接读取：

~~~text
已经计算好的 Aggregate Result
~~~

于是查询结构从：

~~~text
Read
    ↓
Heavy Compute
~~~

变成：

~~~text
Background
    ↓
Heavy Compute

Read
    ↓
Lightweight Query
~~~

这就是：

~~~text
Precomputation
~~~

所以 Continuous Aggregate 首先不是一个 SQL API，而是一种设计思想：

> **把高频、昂贵、重复、结构稳定的分析计算提前维护。**

### 【二、Materialization 把聚合结果真正保存下来】

当前项目的 performance_rollup_1m：

~~~sql
CREATE MATERIALIZED VIEW
performance_rollup_1m

WITH (
  timescaledb.continuous
)

AS

SELECT
  time_bucket(
    INTERVAL '1 minute',
    observed_at
  ) AS bucket,

  project_id,
  name,
  environment,
  app_version,
  route_name,
  threshold_version_id,

  count(*)::bigint
    AS sample_count,

  min(value)
    AS minimum,

  max(value)
    AS maximum,

  avg(value)
    AS average,

  percentile_agg(value)
    AS value_percentiles,

  count(*) FILTER (
    WHERE server_rating = 'good'
  )::bigint
    AS good_count,

  count(*) FILTER (
    WHERE server_rating = 'needs-improvement'
  )::bigint
    AS needs_improvement_count,

  count(*) FILTER (
    WHERE server_rating = 'poor'
  )::bigint
    AS poor_count,

  hyperloglog(
    8192,
    session_id
  ) AS session_hll,

  hyperloglog(
    8192,
    view_id
  ) AS view_hll,

  ...

FROM performance_samples

GROUP BY
  bucket,
  project_id,
  name,
  environment,
  app_version,
  route_name,
  threshold_version_id

WITH NO DATA;
~~~

这段代码可以按职责拆成：

~~~text
Source
    ↓
performance_samples

Grouping
    ↓
1 minute
+
Business Dimensions

Aggregation
    ↓
count
min
max
avg
percentile state
rating count
HLL state
...

Destination
    ↓
performance_rollup_1m
~~~

#### <u>1. 普通 View 只保存查询定义，不保存预计算结果</u>

普通 View：

~~~sql
CREATE VIEW ...
AS
SELECT ...
~~~

可以理解成：

~~~text
View
    ↓
保存 Query Definition
~~~

当查询：

~~~sql
SELECT *
FROM my_view;
~~~

数据库仍然需要根据 View 定义执行底层 Query。

所以：

~~~text
View
≠
Precomputed Result
~~~

#### <u>2. Materialized View 会真正保存 Query Result</u>

Materialized View：

~~~text
Raw Table
    ↓
Aggregate Query
    ↓
Materialized Result
    ↓
Persistent Storage
~~~

以后查询 Materialized View 时，可以读取已经物化的结果，而不是每次重新执行完整原始计算。

因此：

~~~text
View
    ↓
保存 Query Definition

Materialized View
    ↓
保存 Query Result
~~~

#### <u>3. Continuous Aggregate 是面向 Time-Series 的增量 Materialized View</u>

当前：

~~~sql
WITH (
  timescaledb.continuous
)
~~~

告诉 TimescaleDB：

~~~text
这个 Materialized View
由 TimescaleDB 按 Time-Series 模型
持续维护
~~~

所以关系可以理解成：

~~~text
View
    ↓
只保存 Query Definition


Materialized View
    ↓
保存 Query Result
    ↓
需要 Refresh


Continuous Aggregate
    ↓
保存 Time-Series Aggregate Result
    +
跟踪需要更新的时间范围
    +
执行增量 Refresh
~~~

#### <u>4. Continuous Aggregate 的数据不是 Redis Cache，也不是应用内存</u>

它不是：

~~~text
Node.js Memory
~~~

不是：

~~~text
Redis
~~~

也不是：

~~~text
SELECT 时临时产生的数据
~~~

它属于：

~~~text
PostgreSQL / TimescaleDB
内部持久化管理的
预计算 Aggregate Data
~~~

可以先直观理解：

~~~text
performance_samples
Raw Hypertable
        ↓
Continuous Aggregate Definition
        ↓
TimescaleDB Internal
Materialized Aggregate Storage
        ↓
performance_rollup_1m
作为 SQL 查询入口
~~~

#### <u>5. Materialization 保存的是聚合状态，不是 Raw Row 副本</u>

假设 Raw Data：

~~~text
10:00:05 LCP 2100
10:00:08 LCP 2500
10:00:12 LCP 1900
10:00:27 LCP 2300
...
10000 Rows
~~~

Continuous Aggregate 不会再复制这 10000 条 Raw Rows。

而会形成类似：

~~~text
bucket = 10:00

project_id = P001

name = LCP

sample_count = 10000

minimum = ...

maximum = ...

average = ...

value_percentiles = ...

good_count = ...

poor_count = ...

session_hll = ...

view_hll = ...
~~~

所以：

~~~text
Many Raw Rows
        ↓
Materialization
        ↓
Much Smaller Aggregate State
~~~

这才是它降低长期分析成本的根本原因。

### 【三、Refresh 让已经物化的 Aggregate 跟随 Raw Data 持续变化】

如果只：

~~~text
Raw Data
    ↓
算一次 Aggregate
    ↓
以后永远不更新
~~~

当然无法满足持续写入的时序系统。

因为当前：

~~~text
performance_samples
~~~

还在不断产生新 Row，而且部分最近 Sample 还可能被修订。

因此 Continuous Aggregate 需要继续解决：

> **Raw Data 发生变化以后，已经保存的 Aggregate Result 怎样更新？**

这就是 Refresh。

#### <u>1. WITH NO DATA 表示创建定义时不立即完整回填历史</u>

当前：

~~~sql
WITH NO DATA;
~~~

它不是：

~~~text
这个 Continuous Aggregate
永远没有数据
~~~

而是：

~~~text
CREATE 时
先建立 Continuous Aggregate Definition

不立即扫描全部历史
完成完整 Materialization
~~~

因此创建后可以理解成：

~~~text
Continuous Aggregate Definition
    ↓
已经存在

Historical Aggregate Data
    ↓
需要后续 Refresh / Backfill
逐步产生
~~~

这样可以避免数据库已经有大量历史数据时，Migration 创建 Aggregate 的同时立即执行一次非常重的全历史聚合。

#### <u>2. 当前项目通过 Refresh Policy 自动维护一分钟 Aggregate</u>

源码：

~~~sql
SELECT add_continuous_aggregate_policy(
  'performance_rollup_1m',

  start_offset
    => INTERVAL '29 days',

  end_offset
    => INTERVAL '10 seconds',

  schedule_interval
    => INTERVAL '10 seconds',

  if_not_exists
    => TRUE
);
~~~

前面的：

~~~sql
CREATE MATERIALIZED VIEW ...
AS
SELECT ...
~~~

回答：

~~~text
What to Compute
~~~

而 Refresh Policy 回答：

~~~text
When to Refresh

以及

Which Time Range to Refresh
~~~

所以：

~~~text
Continuous Aggregate Definition
        ↓
聚合规则

Refresh Policy
        ↓
维护规则
~~~

#### <u>3. 三个 Policy 参数要放在同一个 Refresh Window 中理解</u>

当前：

~~~text
start_offset = 29 days

end_offset = 10 seconds

schedule_interval = 10 seconds
~~~

可以画成：

~~~text
Past                                              Now
│                                                  │
│<---------------------- 29 days ----------------->│
│                                                  │
└──────── Refresh Window ────────────────┐          │
                                        │<--10s--->│
~~~

近似理解：

~~~text
Refresh Window

now - 29 days
        ↓
到
        ↓
now - 10 seconds
~~~

start_offset：

~~~text
决定向历史回看多远
~~~

end_offset：

~~~text
决定离 Now 留出多少最新数据缓冲区
~~~

schedule_interval：

~~~text
决定后台 Refresh Job 多久运行一次
~~~

因此：

~~~text
start_offset
+
end_offset
    ↓
定义 Refresh Window

schedule_interval
    ↓
定义 Refresh Frequency
~~~

#### <u>4. Refresh Window 与 Retention Window 不是同一个概念</u>

当前：

~~~text
start_offset = 29 days
~~~

不代表：

~~~text
performance_rollup_1m
只能保留 29 天
~~~

29 天描述的是：

~~~text
Refresh Policy
向历史维护多远
~~~

而保存多久属于：

~~~text
Retention Policy
~~~

所以必须固定：

~~~text
Refresh Window
≠
Retention Window
~~~

#### <u>5. end_offset 为最新的热数据留下缓冲</u>

当前：

~~~text
end_offset = 10 seconds
~~~

表示 Policy 的物化范围不会一直追到绝对 Now。

最近的数据可能仍在：

~~~text
持续写入

迟到上报

Sample Sequence 更新

Provisional → Final
~~~

因此保留：

~~~text
10-second Buffer
~~~

避免后台物化一直围绕最热的数据窗口反复工作。

这个 10 秒只是当前项目配置，不是所有 Continuous Aggregate 的固定规则。

#### <u>6. schedule_interval 是 Freshness 与 Background Cost 的权衡</u>

当前：

~~~text
schedule_interval = 10 seconds
~~~

意味着后台 Job 大约每 10 秒触发一次维护。

更频繁：

~~~text
Aggregate Freshness 更高
~~~

但：

~~~text
Background Refresh Cost 更高
~~~

更慢：

~~~text
后台成本更低
~~~

但：

~~~text
Aggregate Lag 更大
~~~

因此这是：

~~~text
Freshness
vs
Maintenance Cost
~~~

的设计参数。

#### <u>7. Continuous Aggregate 的关键是增量维护，而不是反复完整重算历史</u>

如果每 10 秒都：

~~~text
扫描 29 天全部 Raw Data
    ↓
重新计算所有 Bucket
~~~

那么即使自动化了，成本仍然非常高。

Continuous Aggregate 的核心是：

~~~text
Raw Data Change
    ↓
Affected Time Range / Bucket
    ↓
Invalidation
    ↓
Incremental Refresh
~~~

例如：

~~~text
10:00 Bucket
已经稳定

10:01 Bucket
已经稳定

10:02 Bucket
新数据发生变化
~~~

理想维护目标不是：

~~~text
10:00 重新算
10:01 重新算
10:02 重新算
~~~

而是优先重新处理受到变化影响的范围。

所以：

~~~text
Continuous
~~~

不是指：

~~~text
每一条 INSERT
同步重新计算完整 Aggregate
~~~

而是：

~~~text
持续跟踪变化
+
后台增量维护预计算结果
~~~

#### <u>8. Continuous Aggregate 不是应用层 Dual Write</u>

当前应用代码没有：

~~~text
INSERT performance_samples

然后：

UPDATE performance_rollup_1m
~~~

这种业务逻辑。

应用只写：

~~~text
Raw Hypertable
~~~

例如：

~~~text
performance_samples
~~~

而 Aggregate Maintenance 由 TimescaleDB 后台机制负责：

~~~text
Application
    ↓
Raw Hypertable

TimescaleDB Background Job
    ↓
Continuous Aggregate
~~~

因此不是：

~~~text
Application
    ↓
Dual Write
    ├── Raw
    └── Aggregate
~~~

这减少了应用自己维护两份数据一致性的复杂度。

### 【四、Read Architecture 决定 Raw、1m Aggregate 与 1h Aggregate 怎样分工】

当前项目并没有：

~~~text
创建 Continuous Aggregate
    ↓
以后所有查询都改成读它
~~~

而是形成分层 Read Architecture。

#### <u>1. 当前近期 Performance 查询仍然直接读取 Raw Data</u>

源码：

~~~ts
private useRollups(
  filters: AnalyticsFilters,
): boolean {
  return (
    filters.from.getTime()
    <
    Date.now()
    -
    29 * 24 * 60 * 60_000
  );
}
~~~

因此：

~~~text
from >= now - 29 days
        ↓
performance()
直接查询 performance_samples

from < now - 29 days
        ↓
performanceFromRollups()
~~~

可以确认当前读取边界：

~~~text
Recent
    ↓
Raw Query

Historical
    ↓
Rollup Query
~~~

#### <u>2. 1m Continuous Aggregate 当前主要是中间聚合层</u>

performance_rollup_1m：

~~~text
performance_samples
        ↓
1 minute Aggregate
~~~

但是当前历史 Performance API 并不是直接读取：

~~~text
performance_rollup_1m
~~~

而是读取：

~~~sql
FROM performance_rollup_1h
~~~

因为 0002_hourly_aggregates.sql 又定义：

~~~sql
CREATE MATERIALIZED VIEW
performance_rollup_1h

WITH (
  timescaledb.continuous
)

AS

SELECT
  time_bucket(
    INTERVAL '1 hour',
    bucket
  ) AS bucket,

  ...

FROM performance_rollup_1m

GROUP BY ...
~~~

所以真实链路：

~~~text
performance_samples
        ↓
performance_rollup_1m
        ↓
performance_rollup_1h
        ↓
Historical Analytics
~~~

因此：

~~~text
performance_rollup_1m
~~~

在当前项目中主要承担：

~~~text
Intermediate Aggregate Layer
~~~

而：

~~~text
performance_rollup_1h
~~~

才是历史 Performance Query 直接使用的 Read Model。

#### <u>3. 当前项目形成三层数据粒度</u>

完整结构：

~~~text
Raw Layer
performance_samples
        │
        │
        ├── Recent Analytics
        │      ↓
        │   Query-time
        │   Exact Calculation
        │
        ▼
1m Continuous Aggregate
        │
        ▼
1h Continuous Aggregate
        │
        ▼
Historical Analytics
~~~

也可以理解：

~~~text
Recent
    ↓
Raw Detail
    ↓
High Resolution
    ↓
Exact Query-time Aggregation


Historical
    ↓
Precomputed Aggregate
    ↓
Lower Resolution
    ↓
Lower Read Cost
~~~

当前源码可以确认的是：

~~~text
Recent → Raw

Historical → Rollup
~~~

至于作者为什么做这种选择，源码没有直接写成设计注释。

但从技术效果看，这种设计可以让 Recent Query 保留：

~~~text
最新 Raw Data

Exact percentile_cont

Exact COUNT DISTINCT

更灵活的过滤
~~~

而 Historical Query 使用：

~~~text
Precomputed State

更粗粒度

更低查询成本
~~~

这部分属于根据代码结构做出的设计分析，需要和源码事实区分。

#### <u>4. Continuous Aggregate 与 Redis Cache 是两个不同层级的优化</u>

当前项目还存在：

~~~ts
await this.redis.set(
  key,
  JSON.stringify(value),
  "EX",
  15,
);
~~~

Redis 缓存的是：

~~~text
某一次完整 Analytics Query Result
~~~

而 Continuous Aggregate 保存的是：

~~~text
数据库内部长期复用的
Aggregate Data Model
~~~

完整关系：

~~~text
Raw Data
    ↓
Continuous Aggregate
    ↓
Analytics Query
    ↓
Redis Query Result Cache
    ↓
API Response
~~~

因此：

~~~text
Continuous Aggregate
    ↓
优化数据库内部数据模型与统计成本

Redis Cache
    ↓
优化 API Read Path
~~~

二者不是替代关系。

#### <u>5. Real-time Continuous Aggregate 是另一种处理最新数据的机制，但当前项目不能直接假设全部启用</u>

因为 Refresh Policy 存在：

~~~text
end_offset = 10 seconds
~~~

所以可能出现：

~~~text
最新 Raw Data 已写入

但
Materialized Aggregate
暂时还没有刷新到
~~~

TimescaleDB 提供 Real-time Aggregate 模式，可以把：

~~~text
已 Materialize 的历史数据

+

最新 Raw Data
~~~

在查询时组合。

但当前较早创建的：

~~~text
performance_rollup_1m
view_rollup_1m
custom_event_rollup_1m
telemetry_rollup_1m
~~~

没有在这一段 Migration 中显式设置：

~~~text
materialized_only = false
~~~

因此不能仅凭当前源码断言：

~~~text
所有 1m Continuous Aggregate
都一定启用了 Real-time Aggregate
~~~

更重要的是，当前 performance() 对近期数据本身就直接读取 Raw Table，所以近期可见性并不依赖这一能力。

### 【五、脱离项目形成 Continuous Aggregate 的完整判断框架】

Continuous Aggregate 可以抽象成：

~~~text
Time-Series Raw Data
        ↓
Repeated Analytical Query
        ↓
Repeated Computation
        ↓
Precompute Stable Work
        ↓
Materialized Aggregate State
        ↓
Incremental Refresh
        ↓
Fast Historical Read
~~~

完整能力结构：

~~~text
Continuous Aggregate
│
├── Source
│      ↓
│   Raw Hypertable
│
├── Definition
│      ↓
│   time_bucket
│   Dimensions
│   Aggregate State
│
├── Materialization
│      ↓
│   Persist Precomputed Result
│
├── Invalidation
│      ↓
│   Track Changed Time Ranges
│
├── Refresh Policy
│      ↓
│   start_offset
│   end_offset
│   schedule_interval
│
└── Read
       ↓
    Query Aggregate Result
~~~

是否值得引入 Continuous Aggregate，可以顺着：

~~~text
Query 是否频繁执行？
        ↓
结果是否大量重复？
        ↓
底层 Raw Data 是否很多？
        ↓
历史 Bucket 是否相对稳定？
        ↓
是否可以接受一定 Refresh Lag？
        ↓
聚合维度是否比较稳定？
        ↓
Continuous Aggregate
可能有价值
~~~

典型适合：

~~~text
过去 30 天每小时 CPU avg

过去 90 天每天订单数

过去半年每小时 LCP p75

长期 PV / UV
~~~

而少见、临时、组合维度高度动态的查询，可能直接查询 Raw Data 更合理。

所以：

> **Continuous Aggregate 不是把所有 SQL 都预计算，而是把高频、昂贵、重复、结构稳定的时序聚合提前维护。**

### 【六、第四节收束：当前项目把计算从请求路径逐步移动到后台】

当前项目最终形成：

~~~text
performance_samples
Raw Hypertable
        │
        ├──────────────────────────┐
        │                          │
        ▼                          ▼
Recent Query               Background Precompute
        │                          │
Query-time Aggregate              1m CAGG
        │                          │
Exact                             ▼
Statistics                       1h CAGG
        │                          │
        ▼                          ▼
Recent Result             Historical Read Model
~~~

这一节最重要的四个边界：

~~~text
Continuous Aggregate
≠
普通 View
~~~

因为它保存聚合结果。

~~~text
Continuous Aggregate
≠
普通 Materialized View
~~~

因为它针对时序数据持续增量维护，而不是把“完整历史重新刷新”作为唯一模型。

~~~text
Continuous Aggregate
≠
Redis Cache
~~~

因为它属于数据库长期分析数据模型，而 Redis 是短生命周期 Query Result Cache。

~~~text
Continuous Aggregate
≠
应用 Dual Write
~~~

应用继续写 Raw Hypertable，Aggregate 由 TimescaleDB 后台机制维护。

最终可以压缩成：

> **Continuous Aggregate 的核心不是单纯“查询更快”，而是把高频重复的时序聚合从请求路径搬到数据库后台：Raw Data 仍然作为事实保存，TimescaleDB 将稳定历史按时间 Bucket 物化成 Aggregate State，并通过 Refresh 持续维护，历史查询再直接读取这些预计算结果。**

## 5. Hypercore 通过 Rowstore、Columnstore 与数据生命周期同时兼顾实时写入和历史分析

前四节已经建立了两条主线：

~~~text
TimescaleDB
│
├── Data Organization
│   ├── Hypertable
│   └── Chunk
│
└── Query & Analytics
    ├── Time Range Query
    ├── time_bucket
    └── Continuous Aggregate
~~~

但目前还有一个问题没有解决：

> **一份时序数据写入以后，会长期以完全相同的物理形式存在吗？**

答案是否定的。

时序数据最大的特点之一就是：

~~~text
数据年龄不断变化
        ↓
访问模式也不断变化
~~~

例如监控数据：

~~~text
刚产生
    ↓
频繁 INSERT
可能 UPDATE
可能迟到
可能需要立即查看

1 天以后
    ↓
基本稳定
查询以扫描和统计为主

30 天以后
    ↓
单条 Raw Row 价值进一步降低

180 天以后
    ↓
可能只保留 Aggregate
或者直接删除
~~~

因此 TimescaleDB 不只是：

~~~text
把数据分 Chunk
+
加速 Query
~~~

还建立了另一条完整体系：

~~~text
Time-Series Data Lifecycle
│
├── Recent Data
│      ↓
│   Rowstore
│
├── Historical Data
│      ↓
│   Columnstore
│
├── Long-term Analytics
│      ↓
│   Continuous Aggregate / Rollup
│
└── Expired Data
       ↓
    Retention
~~~

TimescaleDB 当前把这套混合 Row / Column 存储体系称为 Hypercore。新数据优先进入适合快速写入和更新的 Rowstore，数据变冷以后可以转换到 Columnstore，从而降低存储量并提高历史分析扫描效率。

### 【一、Rowstore 与 Columnstore 解决的是两种不同的数据访问模式】

理解 Hypercore 之前，必须先理解为什么数据库会同时需要：

~~~text
Row-oriented Storage
+
Column-oriented Storage
~~~

它们不是：

~~~text
新存储
vs
旧存储
~~~

而是针对不同 Workload 的两种物理组织方式。

#### <u>1. Rowstore 按一整行数据组织，天然适合实时写入和单条修改</u>

假设 performance_samples 有：

~~~text
observed_at
project_id
name
value
route_name
session_id
view_id
environment
~~~

Rowstore 可以直观理解成：

~~~text
Row 1
┌──────────┬─────────┬─────┬───────┬──────────┐
│ 10:00:01 │ P001    │ LCP │ 2100  │ /home    │ ...
└──────────┴─────────┴─────┴───────┴──────────┘

Row 2
┌──────────┬─────────┬─────┬───────┬──────────┐
│ 10:00:02 │ P001    │ LCP │ 2300  │ /detail  │ ...
└──────────┴─────────┴─────┴───────┴──────────┘

Row 3
...
~~~

同一条记录的字段放在一起。

所以当系统收到：

~~~sql
INSERT INTO performance_samples (...)
VALUES (...);
~~~

数据库写入的是一整条新 Row。

如果：

~~~sql
UPDATE performance_samples
SET state = 'final'
WHERE ...
~~~

也是定位某一条 Row 后修改。

因此 Rowstore 特别适合：

~~~text
INSERT

UPDATE

DELETE

UPSERT

Point Lookup

Recent Data Access
~~~

这正符合刚产生的时序数据特点。

#### <u>2. 当前项目的 Recent Performance Data 就具有明显 Row-oriented Workload</u>

当前 performance_samples 并不是绝对不可修改的数据。

它存在：

~~~text
sequence

state = provisional / final

last_updated_at
~~~

意味着最近的数据可能经历：

~~~text
第一次 Sample
    ↓
sequence = 0

后续修订
    ↓
sequence = 1

最终确认
    ↓
state = final
~~~

因此最近数据不是：

~~~text
写入以后永久不变
~~~

而是：

~~~text
High Write
+
Possible Update
+
Low-latency Read
~~~

Rowstore 非常适合这个阶段。

#### <u>3. Columnstore 按列组织，更适合扫描大量历史数据</u>

再看一个 Analytics Query：

~~~sql
SELECT
  avg(value)
FROM performance_samples
WHERE
  observed_at >= ...
  AND observed_at < ...
~~~

真正主要需要的是：

~~~text
observed_at

value
~~~

但一条 Raw Row 还有：

~~~text
session_id
view_id
route_name
environment
app_version
detail
...
~~~

如果数据按 Row 存储，扫描大量 Row 时会持续面对完整记录。

Columnstore 则可以近似理解：

~~~text
observed_at column
────────────────────────
10:00:01
10:00:02
10:00:03
10:00:04
...


value column
────────────────────────
2100
2300
1800
2500
...


project_id column
────────────────────────
P001
P001
P001
P002
...


name column
────────────────────────
LCP
LCP
INP
LCP
...
~~~

查询 AVG(value) 时，更容易围绕需要的 Column 做扫描。

所以：

~~~text
Rowstore
    ↓
以 Row 为主要访问单位

Columnstore
    ↓
以 Column 为主要分析单位
~~~

#### <u>4. Columnstore 为什么通常还会获得更高压缩率</u>

因为同一列的数据通常具有：

~~~text
相同 Data Type

相似 Value Distribution

大量重复值
~~~

例如：

~~~text
project_id

P001
P001
P001
P001
P001
...
~~~

或者：

~~~text
name

LCP
LCP
LCP
LCP
...
~~~

把同类值放在一起以后，更适合做编码和压缩。

因此 Columnstore 同时服务：

~~~text
Analytical Scan
+
Compression
~~~

而不是只解决磁盘空间。

#### <u>5. Rowstore 与 Columnstore 的核心不是性能高低，而是 Workload 不同</u>

不要理解成：

~~~text
Columnstore
>
Rowstore
~~~

更准确：

| Workload | Rowstore | Columnstore |
|---|---:|---:|
| 高频 INSERT | 更适合 | 不是主要优势 |
| 高频 UPDATE | 更适合 | 可支持，但不是传统优势 |
| 单 Row Lookup | 更自然 | 不一定占优 |
| 扫描大量历史数据 | 成本更高 | 更适合 |
| 聚合大量 Column | 一般 | 更适合 |
| Compression | 通常较低 | 通常更高 |

因此核心矛盾是：

~~~text
Real-time Write
        ↓
Rowstore 更合适

Historical Analytics
        ↓
Columnstore 更合适
~~~

TimescaleDB 要解决的是：

> **同一份 Time-Series Data 既需要实时写入，又需要长期分析，为什么一定要二选一？**

这就是 Hypercore 的入口。

### 【二、Hypercore 让同一个 Hypertable 的不同 Chunk 使用不同存储形态】

第二节已经知道：

~~~text
Hypertable
    ↓
Chunk A
Chunk B
Chunk C
...
~~~

例如教学示例：

~~~text
performance_samples
│
├── Chunk A
│   10/01
│
├── Chunk B
│   10/02
│
├── Chunk C
│   10/03
│
└── Chunk D
    10/04
~~~

Hypercore 的关键不是：

~~~text
把整张 Hypertable
统一改成 Columnstore
~~~

而是利用 Chunk：

~~~text
不同年龄的数据
可以处于不同物理存储阶段
~~~

#### <u>1. Recent Chunk 保持 Rowstore</u>

假设现在是 10/04。

当前活跃 Chunk：

~~~text
Chunk D
~~~

仍然不断收到：

~~~text
INSERT

UPDATE

late-arriving data
~~~

那么：

~~~text
Chunk D
    ↓
Rowstore
~~~

有利于：

~~~text
快速写入

最近数据更新

最新数据查询
~~~

#### <u>2. Historical Chunk 可以转入 Columnstore</u>

随着时间继续，10/01 的数据基本稳定：

~~~text
几乎没有 INSERT

很少 UPDATE

主要 Query：
过去 7 天
过去 30 天
趋势
平均
p75
COUNT
~~~

于是：

~~~text
Chunk A
    ↓
Columnstore
~~~

就更合理。

所以同一张 performance_samples 可以出现：

~~~text
performance_samples
Hypertable
│
├── Chunk A
│      ↓
│   Columnstore
│
├── Chunk B
│      ↓
│   Columnstore
│
├── Chunk C
│      ↓
│   Columnstore
│
└── Chunk D
       ↓
    Rowstore
~~~

注意：

> **不是 Rowstore Table 和 Columnstore Table 两套业务表。**

应用仍然：

~~~sql
SELECT *
FROM performance_samples;
~~~

TimescaleDB 自己处理不同 Chunk 的底层存储格式。

#### <u>3. Hypercore 的核心单位再次回到了 Chunk</u>

这说明第二节学习 Chunk 时不能只理解成：

~~~text
为了 Chunk Pruning
~~~

Chunk 至少承担三类角色：

~~~text
Chunk
│
├── Partition Unit
│      ↓
│   按时间拆分数据
│
├── Query Unit
│      ↓
│   Chunk Pruning
│
└── Lifecycle Unit
       ↓
    Rowstore
    Columnstore
    Retention
~~~

这就把 Hypertable 和 Data Lifecycle 连接起来了。

#### <u>4. 数据转入 Columnstore 后，应用 SQL 语义仍然保持 PostgreSQL 模型</u>

Hypercore 改变的是：

~~~text
Physical Storage Layout
~~~

而不是：

~~~text
应用数据模型
~~~

也不是：

~~~text
SQL 语言
~~~

可以理解：

~~~text
Application
    ↓
Same PostgreSQL SQL
    ↓
Hypertable
    ↓
TimescaleDB
    ↓
根据 Chunk Storage Format
选择对应执行路径
~~~

### 【三、Columnstore 不只是压缩，还重新组织数据以服务历史分析】

这里需要纠正一个容易形成的旧概念：

~~~text
Compression
=
单纯把文件压小
~~~

在 TimescaleDB 体系中，更准确的是：

~~~text
Historical Chunk
    ↓
Columnization
    ↓
Columnar Organization
    +
Compression
    ↓
Analytical Storage
~~~

因此 Columnstore 同时解决：

~~~text
Storage Cost
+
Analytical Query Performance
~~~

而不是只有磁盘压缩。

#### <u>1. Columnstore 内部还需要按照 Query Pattern 组织数据</u>

Columnstore 并不是简单：

~~~text
一列数据
全部堆成一个巨大数组
~~~

还需要继续回答：

~~~text
哪些数据应该放在一起？

放在一起以后
应该按照什么顺序排列？
~~~

TimescaleDB 中很重要的两个概念是：

~~~text
SEGMENTBY

ORDERBY
~~~

它们决定 Columnstore 内部如何组织数据。

#### <u>2. SEGMENTBY 决定哪些业务实体的数据应该放在一起</u>

假设有大量 Performance Samples：

~~~text
Project P001
Project P002
Project P003

LCP
INP
CLS
~~~

而最常见 Query 是：

~~~sql
WHERE
  project_id = 'P001'
  AND name = 'LCP'
~~~

那么可以让：

~~~text
project_id
+
name
~~~

成为 Segment Key。

物理组织可以近似理解：

~~~text
Segment A

project_id = P001
name = LCP

    ↓

这一组 Performance Data


Segment B

project_id = P001
name = INP


Segment C

project_id = P002
name = LCP
~~~

这样查询：

~~~text
P001 + LCP
~~~

时，更容易排除其他 Segment。

所以：

~~~text
SEGMENTBY
    ↓
回答：
哪些数据应该被组织在一起？
~~~

#### <u>3. ORDERBY 决定 Segment 内的数据怎样排列</u>

例如：

~~~text
project_id = P001
name = LCP
~~~

这个 Segment 内可能有：

~~~text
10:00
10:01
10:02
...
~~~

时序查询最常见：

~~~text
WHERE observed_at BETWEEN T1 AND T2
~~~

因此可以：

~~~text
ORDERBY observed_at DESC
~~~

近似形成：

~~~text
Segment:
P001 + LCP

observed_at

10:30
10:29
10:28
10:27
...
~~~

所以：

~~~text
SEGMENTBY
    ↓
哪些数据放在一起

ORDERBY
    ↓
放在一起以后怎样排列
~~~

二者不能混为一谈。

#### <u>4. Columnstore Query 并不是先解压全部数据再执行普通扫描</u>

现代 Hypercore 的分析路径还会利用：

~~~text
Chunk Pruning

Segment / Batch Filtering

Column Selection

Metadata

Vectorized Execution
~~~

例如：

~~~sql
SELECT avg(value)
FROM metrics
WHERE
  project_id = 'P001'
  AND time BETWEEN T1 AND T2;
~~~

可以逐步缩小：

~~~text
所有 Chunks
    ↓
只留下时间相关 Chunks
    ↓
只留下 project=P001 的相关 Segment / Batch
    ↓
只读取 time / value 等需要的 Column
    ↓
执行 Aggregate
~~~

本节只需要建立一个核心认识：

> **Columnstore 不只是压缩，而是在历史数据阶段重新组织物理布局，使扫描、聚合和存储成本同时受益。**

更深入的 Batch Metadata、Chunk Skipping、Vectorized Execution 后续再放到 Query Engine & Performance 专题。

### 【四、当前项目旧 Compression API 与现行 Hypercore / Columnstore 属于同一能力的版本演进】

现在回到 Browser Monitor。

当前 0001_platform.sql：

~~~sql
ALTER TABLE performance_samples SET (
  timescaledb.compress,
  timescaledb.compress_segmentby =
    'project_id,name',
  timescaledb.compress_orderby =
    'observed_at DESC'
);
~~~

然后：

~~~sql
SELECT add_compression_policy(
  'performance_samples',
  INTERVAL '24 hours',
  if_not_exists => TRUE
);
~~~

其他表也是类似：

~~~text
telemetry_events

segmentby:
project_id,type

orderby:
occurred_at DESC
~~~

以及：

~~~text
view_records

segmentby:
project_id

orderby:
started_at DESC
~~~

#### <u>1. 当前项目源码使用的是旧 Compression API</u>

这一点必须明确：

~~~text
当前 Browser Monitor

timescaledb.compress

compress_segmentby

compress_orderby

add_compression_policy
~~~

这是当前源码事实。

不能为了匹配最新文档，直接把源码解释成：

~~~text
已经使用
enable_columnstore
~~~

因为当前仓库并没有这样写。

#### <u>2. 当前 TimescaleDB 官方主线已经转向 Hypercore / Columnstore API</u>

现行官方体系更强调：

~~~text
Hypercore

Rowstore

Columnstore

enable_columnstore

segmentby

orderby

add_columnstore_policy
~~~

所以需要建立：

~~~text
Concept
    ↓
Historical Data
→ Columnar Organization
→ Compression
→ Analytical Scan

Current API Direction
    ↓
Hypercore / Columnstore

Current Project Source
    ↓
Legacy Compression API
~~~

这样知识体系不会被当前仓库中的旧 API 绑死。

#### <u>3. 当前项目的 segmentby 已经直接反映真实 Query Pattern</u>

当前：

~~~text
compress_segmentby
=
project_id,name
~~~

为什么是：

~~~text
project_id
+
name
~~~

而不是：

~~~text
session_id
+
value
~~~

因为 Performance Analytics 最常见的访问模型是：

~~~text
一个 Project

某个 Metric

一段 Time Range
~~~

也就是：

~~~text
Project
+
Metric
+
Time
~~~

因此：

~~~text
SEGMENTBY
=
project_id,name
~~~

让相同：

~~~text
Project + Metric
~~~

的数据尽量聚集。

然后：

~~~text
ORDERBY
=
observed_at DESC
~~~

让 Segment 内继续按照时间组织。

所以当前物理布局其实和前面学习的 Query Pattern 完全一致：

~~~text
Query Pattern

Project
+
Metric
+
Time

        ↓

Columnstore Layout

SEGMENTBY
project_id,name

ORDERBY
observed_at DESC
~~~

这里再次体现：

> **存储布局应该从 Query Pattern 反推，而不是只根据字段名称设计。**

### 【五、Retention 决定数据生命周期的终点，而不是单纯执行 DELETE】

有了：

~~~text
Recent
    ↓
Rowstore

Historical
    ↓
Columnstore
~~~

还没有结束。

数据继续变老：

~~~text
30 days

180 days

1 year
...
~~~

最终还需要回答：

> **这份 Raw Data 还有没有继续保存的价值？**

这就是：

~~~text
Retention
~~~

#### <u>1. 普通思路可能是逐 Row DELETE 旧数据</u>

例如：

~~~sql
DELETE FROM performance_samples
WHERE
  observed_at
  < now() - INTERVAL '30 days';
~~~

如果：

~~~text
每天上千万 Rows
~~~

那么可能需要：

~~~text
找到大量 Row

逐 Row 删除

更新 Index

产生 dead tuples

后续 Vacuum
~~~

这对于持续增长的 Time-Series Data 成本很高。

#### <u>2. Time Partition 让 Retention 可以围绕 Chunk 工作</u>

因为已经有：

~~~text
Chunk A
10/01

Chunk B
10/02

Chunk C
10/03
~~~

假设 Retention 是：

~~~text
30 days
~~~

如果：

~~~text
Chunk A
整个时间范围
已经早于 30 days
~~~

就可以直接：

~~~text
Drop Chunk
~~~

而不是：

~~~text
在 Chunk A 里面
DELETE 数百万 Row
~~~

所以前面学习 Hypertable / Chunk 的价值再次出现：

~~~text
Chunk
    ↓
不仅用于 Query Pruning

还用于：
Lifecycle Management
~~~

#### <u>3. 当前项目的 Raw Retention 是 30 天</u>

当前源码：

~~~sql
SELECT add_retention_policy(
  'telemetry_events',
  INTERVAL '30 days',
  if_not_exists => TRUE
);

SELECT add_retention_policy(
  'performance_samples',
  INTERVAL '30 days',
  if_not_exists => TRUE
);

SELECT add_retention_policy(
  'view_records',
  INTERVAL '30 days',
  if_not_exists => TRUE
);
~~~

因此：

~~~text
Raw Detail
    ↓
主要保留 30 days
~~~

这意味着：

~~~text
30 天以后
~~~

不是：

~~~text
所有监控历史
完全消失
~~~

因为还有：

~~~text
Continuous Aggregate
~~~

保存更长期的趋势。

#### <u>4. Aggregate Retention 比 Raw Retention 更长</u>

当前：

~~~sql
SELECT add_retention_policy(
  'performance_rollup_1m',
  INTERVAL '180 days',
  if_not_exists => TRUE
);
~~~

后续：

~~~text
performance_rollup_1h
    ↓
180 days
~~~

所以项目形成：

~~~text
Raw Data
    ↓
30 days

Aggregate Data
    ↓
180 days
~~~

这是典型的：

~~~text
Multi-resolution History
~~~

或者：

~~~text
Downsampled Historical Storage
~~~

思想。

即：

~~~text
Recent
    ↓
保留细节

Historical
    ↓
保留趋势
~~~

而不是：

~~~text
所有数据
统一以 Raw 形式
保留 180 天
~~~

### 【六、Compression、Continuous Aggregate 与 Retention 必须放进同一个生命周期理解】

这三个能力不要分别记成：

~~~text
Compression
一套功能

Continuous Aggregate
一套功能

Retention
一套功能
~~~

真正的时间序列生命周期是：

~~~text
Incoming Data
        ↓
Recent Raw
        ↓
Rowstore
        ↓
        │
        │ Time Passes
        ▼
Historical Raw
        ↓
Columnstore
+
Compression
        ↓
        │
        ├──────────────┐
        │              │
        ▼              ▼
     Detail        Continuous Aggregate
                      ↓
                     1m
                      ↓
                     1h
        │              │
        │              │
        ▼              ▼
Raw Retention      Aggregate Retention
30 days            180 days
        │              │
        ▼              ▼
Drop Raw Chunk     Keep Trend Longer
~~~

于是形成完整关系：

~~~text
Data Age
    ↓
Access Pattern
    ↓
Storage Format
    ↓
Resolution
    ↓
Retention
~~~

这才是 TimescaleDB Data Lifecycle 体系。

### 【七、回到 Browser Monitor，可以完整解释 24h / 30d / 180d 三个时间边界】

当前项目实际上已经形成明确 Data Lifecycle。

#### <u>1. 0 ～ 24 小时：最新 Raw Data</u>

当前：

~~~sql
add_compression_policy(
  'performance_samples',
  INTERVAL '24 hours'
)
~~~

说明当前源码期望：

~~~text
大约 24h 内
    ↓
Recent / Hot Raw Data
~~~

这个阶段最有可能：

~~~text
持续写入

修订

近期查询
~~~

#### <u>2. 24 小时以后：旧 Raw Data 进入历史存储阶段</u>

当前旧 API 表达：

~~~text
Chunk older than 24h
    ↓
Compression
~~~

从现代 TimescaleDB 体系理解，就是：

~~~text
Hot Row-oriented Data
        ↓
随着数据变冷
        ↓
Historical Columnar / Compressed Data
~~~

因此当前项目的：

~~~text
24 hours
~~~

本质上定义了：

~~~text
Hot
    ↓
Historical
~~~

的生命周期边界。

#### <u>3. 30 天以后：Raw Detail 不再长期保留</u>

当前：

~~~text
Raw Retention
=
30 days
~~~

所以：

~~~text
Historical Raw Chunk
        ↓
超过 30 天
        ↓
Drop
~~~

#### <u>4. 180 天以内：继续依靠 Aggregate 保存历史趋势</u>

当前：

~~~text
1m / 1h Aggregate
        ↓
180 days
~~~

所以：

~~~text
30 ~ 180 days
~~~

仍然可以知道：

~~~text
趋势

count

average

percentile state

distinct state
~~~

但不再保证可以读取：

~~~text
每一条 Raw Event
或
每一条 Raw Sample
~~~

#### <u>5. 当前项目最终生命周期</u>

~~~text
0
│
├── 0 ~ 24h
│      ↓
│   Hot Raw
│   高频写入 / 查询
│
├── 24h ~ 30d
│      ↓
│   Historical Raw
│   Compressed / Column-oriented
│
├── 30d
│      ↓
│   Raw Retention Boundary
│   Raw Detail 删除
│
├── 30d ~ 180d
│      ↓
│   Aggregate History
│   1m / 1h Rollup
│
└── 180d
       ↓
    Aggregate Retention Boundary
~~~

这张生命周期图比单独记：

~~~text
24h compression

30d retention

180d retention
~~~

更重要。

### 【八、脱离项目形成完整的 Time-Series Data Lifecycle 设计框架】

以后设计任意时序系统，都可以依次回答五个问题。

#### <u>1. Recent Data 需要多久保持高频可写</u>

例如：

~~~text
1 hour

1 day

7 days
~~~

决定：

~~~text
Hot Window
~~~

#### <u>2. 数据什么时候进入 Historical Storage 阶段</u>

即：

~~~text
Rowstore
    ↓
Columnstore
~~~

边界。

需要考虑：

~~~text
Late-arriving Data

Update Frequency

Query Pattern

Storage Cost
~~~

#### <u>3. Columnstore 怎样按照主要 Query Pattern 组织</u>

回答：

~~~text
SEGMENTBY 什么？

ORDERBY 什么？
~~~

不能凭字段名称决定。

应该从：

~~~text
WHERE 常查什么？

GROUP BY 常按什么？

Time Range 怎么查？
~~~

反推。

#### <u>4. Raw Data 需要保存多久</u>

例如：

~~~text
30 days
~~~

回答：

~~~text
什么时候
不再需要逐条事实？
~~~

#### <u>5. Aggregate Data 需要保存多久以及保留什么粒度</u>

例如：

~~~text
Raw
    ↓
30 days

1m
    ↓
90 days

1h
    ↓
1 year

1d
    ↓
5 years
~~~

这就进入：

~~~text
Multi-resolution Storage
~~~

设计。

### 【九、第五节收束：TimescaleDB Storage & Lifecycle 是完整数据管理主线】

这一节最终不是在学：

~~~text
add_compression_policy
~~~

或者：

~~~text
add_retention_policy
~~~

两个函数。

真正建立的是：

~~~text
Time-Series Storage Lifecycle
│
├── 一、Storage Format
│   │
│   ├── Rowstore
│   └── Columnstore
│
├── 二、Hypercore
│   │
│   ├── Recent Chunk → Rowstore
│   └── Historical Chunk → Columnstore
│
├── 三、Columnar Layout
│   │
│   ├── SEGMENTBY
│   ├── ORDERBY
│   └── Compression
│
└── 四、Data Retention
    │
    ├── Raw Retention
    ├── Aggregate Retention
    └── Multi-resolution History
~~~

和前四节连接起来：

~~~text
TimescaleDB
│
├── Storage Organization
│   └── Hypertable / Chunk
│
├── Query
│   └── Time Range / time_bucket
│
├── Precomputation
│   └── Continuous Aggregate
│
└── Storage Lifecycle
    ├── Rowstore
    ├── Columnstore
    ├── Compression
    └── Retention
~~~

到这里，TimescaleDB 的基础数据管理框架才比较完整。

### 【当前项目与 TimescaleDB 现行体系的最终映射】

| TimescaleDB 体系 | 当前推荐 / 现行概念 | Browser Monitor 当前源码 |
|---|---|---|
| 时间分区 | Hypertable / Chunk | create_hypertable() |
| 热数据存储 | Rowstore | Hypertable 最近 Chunk |
| 历史数据存储 | Hypercore Columnstore | 旧 Compression API |
| 分组布局 | segmentby | compress_segmentby |
| 时间布局 | orderby | compress_orderby |
| 自动转入历史存储 | add_columnstore_policy() | add_compression_policy() |
| Raw 生命周期 | Retention | add_retention_policy(...30 days) |
| 历史趋势 | Continuous Aggregate | *_rollup_1m / *_rollup_1h |
| Aggregate 生命周期 | Retention | ...180 days |

学习时应该以：

~~~text
Hypercore
    ↓

~~~

作为知识主框架，再把当前项目的旧 Compression API 映射回来，而不是反过来用旧 API 定义 TimescaleDB。

## 6. Background Jobs 与 Policy Framework 将数据维护从应用代码转移到数据库调度器

前几节已经连续遇到很多这样的 SQL：

~~~sql
SELECT add_continuous_aggregate_policy(...);

SELECT add_compression_policy(...);

SELECT add_retention_policy(...);
~~~

按照 TimescaleDB 当前体系，还会看到：

~~~sql
SELECT add_columnstore_policy(...);
~~~

如果只分别学习这些 API，很容易形成：

~~~text
Continuous Aggregate
    ↓
有一个 Refresh Policy

Columnstore
    ↓
有一个 Columnstore Policy

Retention
    ↓
有一个 Retention Policy
~~~

看起来像三个互不相关的功能。

实际上，它们背后共享的是同一套基础设施：

~~~text
TimescaleDB Automation Framework
│
├── Policy
│     ↓
│   描述“要自动维护什么”
│
├── Background Job
│     ↓
│   一个真正被注册、调度和执行的任务
│
├── Scheduler
│     ↓
│   决定 Job 什么时候运行
│
└── Background Worker
      ↓
    真正执行 Job
~~~

这一节真正要解决的是：

> **Policy、Job、Scheduler、Worker 到底是什么关系，以及数据库为什么能够自己定时完成 Refresh、Columnstore 转换和 Retention，而不需要 Node.js 写定时任务。**

### 【一、Policy 与 Job 是维护规则和可执行任务的关系】

#### <u>1. Policy 不是正在运行的代码，而是一条自动维护规则</u>

例如当前项目：

~~~sql
SELECT add_retention_policy(
  'performance_samples',
  INTERVAL '30 days',
  if_not_exists => TRUE
);
~~~

这条 SQL 表达的是：

~~~text
Target
    ↓
performance_samples

Rule
    ↓
超过 30 天的数据
应该被 Retention
~~~

也就是：

~~~text
Retention Policy
=
数据生命周期规则
~~~

同样：

~~~sql
SELECT add_compression_policy(
  'performance_samples',
  INTERVAL '24 hours',
  if_not_exists => TRUE
);
~~~

表达：

~~~text
超过约 24h 的 Chunk
    ↓
进入历史压缩阶段
~~~

Continuous Aggregate：

~~~sql
SELECT add_continuous_aggregate_policy(
  'performance_rollup_1m',
  start_offset => INTERVAL '29 days',
  end_offset => INTERVAL '10 seconds',
  schedule_interval => INTERVAL '10 seconds'
);
~~~

表达：

~~~text
这个 Aggregate
应该按照指定时间窗口
定期 Refresh
~~~

所以 Policy 首先回答的是：

> **数据库应该自动维持什么状态？**

#### <u>2. Job 才是 Scheduler 可以真正执行的任务实体</u>

当 TimescaleDB 注册这些 Policy 后，会创建对应的后台 Job。

可以把关系理解成：

~~~text
add_retention_policy(...)
        ↓
Retention Policy
        ↓
Background Job


add_continuous_aggregate_policy(...)
        ↓
Refresh Policy
        ↓
Background Job


add_columnstore_policy(...)
        ↓
Columnstore Policy
        ↓
Background Job
~~~

这些 Job 可以通过：

~~~sql
SELECT *
FROM timescaledb_information.jobs;
~~~

进行查看。

因此不要理解成：

~~~text
Policy
=
Job
~~~

更准确：

~~~text
Policy
    ↓
Declarative Rule

Job
    ↓
Executable Scheduled Task
~~~

#### <u>3. Policy 与 Job 可以用配置规则和任务实例理解</u>

可以类比：

~~~text
Policy

“每天定期清理超过 30 天的数据”
这条维护规则


Job

调度系统中真正注册出来的
具体执行任务
~~~

完整关系：

~~~text
Policy
    ↓
创建 / 配置
    ↓
Job
    ↓
被 Scheduler 管理
    ↓
被 Worker 执行
~~~

所以 add_xxx_policy(...) 不只是：

~~~text
给 Table 增加一个属性
~~~

而是在启动一整条自动维护链路。

### 【二、Scheduler 与 Background Worker 负责真正运行 Job】

Policy 和 Job 都有以后，还缺少两个问题：

~~~text
谁知道什么时候该执行？

谁真正执行？
~~~

答案分别是：

~~~text
Scheduler

Background Worker
~~~

#### <u>1. Scheduler 负责判断哪个 Job 到时间了</u>

例如当前项目的一分钟 Aggregate：

~~~text
schedule_interval
=
10 seconds
~~~

可以理解：

~~~text
Scheduler
    ↓
管理已经注册的 Jobs
    ↓
发现：
performance_rollup_1m Refresh Job
已经到 next_start
    ↓
安排执行
~~~

Scheduler 关注的是：

~~~text
Job A
什么时候执行？

Job B
什么时候执行？

Job C
是否暂停？

Job D
失败后什么时候 Retry？
~~~

因此：

~~~text
Scheduler
≠
具体执行 Retention / Refresh 逻辑
~~~

它主要解决：

~~~text
When to Run
~~~

#### <u>2. Background Worker 才真正执行对应维护逻辑</u>

TimescaleDB 是 PostgreSQL Extension。

所以这套后台任务不是：

~~~text
外部 Linux cron

Node.js setInterval

NestJS Cron

Redis Queue Worker
~~~

而是在 PostgreSQL / TimescaleDB 自己的后台 Worker 基础设施中运行。

可以理解：

~~~text
PostgreSQL Server
│
├── Application Connections
│
│   ├── API Query
│   └── Worker Query
│
└── TimescaleDB Background Workers
        │
        ├── Continuous Aggregate Job
        ├── Retention Job
        ├── Columnstore Job
        └── Custom Job
~~~

#### <u>3. 一次 Job 执行可以抽象成完整生命周期</u>

~~~text
Job Registered
      ↓
等待 Schedule
      ↓
到达 next_start
      ↓
Scheduler 选择 Job
      ↓
Background Worker
      ↓
调用对应 Procedure
      ↓
读取 Job Config
      ↓
执行维护操作
      ↓
Success / Failure
      ↓
记录 Statistics
      ↓
计算下一次 next_start
~~~

这条链就是：

~~~text
Background Job Lifecycle
~~~

### 【三、不同 Policy 只是复用同一 Job Framework 执行不同数据库维护操作】

理解 Job Framework 后，再重新看前面学过的几个 Policy。

它们就不应该被看成三个独立系统：

~~~text
TimescaleDB Job Framework
│
├── Continuous Aggregate Refresh Job
│
├── Columnstore / Compression Job
│
└── Retention Job
~~~

#### <u>1. Continuous Aggregate Policy 的 Job 负责 Refresh</u>

当前：

~~~sql
SELECT add_continuous_aggregate_policy(
  'performance_rollup_1m',
  start_offset => INTERVAL '29 days',
  end_offset => INTERVAL '10 seconds',
  schedule_interval => INTERVAL '10 seconds'
);
~~~

可以重新解释成：

~~~text
Policy
    ↓
Refresh performance_rollup_1m

Job Config
    ↓
start_offset = 29d
end_offset = 10s

Schedule
    ↓
10s

Job Execution
    ↓
Refresh affected aggregate range
~~~

因此第四节中的 Incremental Refresh，不是应用请求触发的，而是由 Background Refresh Job 持续维护。

#### <u>2. Columnstore / Compression Policy Job 负责数据形态转换</u>

当前项目：

~~~sql
SELECT add_compression_policy(
  'performance_samples',
  INTERVAL '24 hours'
);
~~~

现行 Hypercore 体系更倾向使用 Columnstore Policy。

但从 Job Framework 看，两者表达的是同一类自动维护：

~~~text
Scheduler
    ↓
定期运行
    ↓
找到符合年龄条件的 Chunks
    ↓
转换为 Historical Storage
~~~

所以第五节中的：

~~~text
24h
=
Hot → Historical Boundary
~~~

真正能够自动发生，是因为：

~~~text
Columnstore / Compression Policy
        ↓
Background Job
~~~

#### <u>3. Retention Policy Job 负责删除过期 Chunk</u>

当前：

~~~sql
SELECT add_retention_policy(
  'performance_samples',
  INTERVAL '30 days'
);
~~~

后台维护链可以理解成：

~~~text
Scheduler
    ↓
Retention Job
    ↓
检查 Chunk Age
    ↓
Chunk 已完全超过 Retention Window？
    ↓
Yes
    ↓
Drop Chunk
~~~

所以 30 days 不是：

~~~text
一到第 30 天
由 API 请求顺便 DELETE
~~~

而是：

~~~text
后台 Job
按照自己的调度周期
发现符合条件的 Chunk 后清理
~~~

三类 Policy 可以统一成：

~~~text
                    Job Scheduler
                          │
          ┌───────────────┼────────────────┐
          │               │                │
          ▼               ▼                ▼
    CAGG Refresh      Columnstore       Retention
        Job               Job              Job
          │               │                │
          ▼               ▼                ▼
 Refresh Buckets     Convert Chunks     Drop Chunks
~~~

上层 Policy 不同：

~~~text
Refresh Rule

Storage Transition Rule

Retention Rule
~~~

底层 Automation Framework 是共享的。

### 【四、Job Config 与 Schedule 分别描述怎么执行和什么时候执行】

查看：

~~~sql
SELECT *
FROM timescaledb_information.jobs;
~~~

会遇到很多字段。

与其逐个平铺记忆，不如把 Job 信息分成四类：

~~~text
Job
│
├── Identity
├── Execution
├── Schedule
└── Failure Policy
~~~

#### <u>1. Identity 描述这个 Job 是谁</u>

主要包括：

~~~text
job_id

application_name

owner

hypertable_name
~~~

例如：

~~~text
Job 1001

Retention Policy

Target:
performance_samples
~~~

其中最重要的是：

~~~text
job_id
~~~

后续修改 Job 时通常需要使用 Job ID。

#### <u>2. Execution 描述这个 Job 实际执行什么</u>

主要包括：

~~~text
proc_schema

proc_name

config
~~~

可以理解：

~~~text
Job
    ↓
调用哪个 Procedure？

Procedure
    ↓
拿到什么 Config？
~~~

例如 Custom Job：

~~~sql
SELECT add_job(
  'process_hourly_reports',
  '1 hour',
  config => '{"hypertable":"metrics"}'
);
~~~

这里：

~~~text
process_hourly_reports
    ↓
执行逻辑

config JSON
    ↓
运行参数
~~~

#### <u>3. Schedule 描述什么时候执行</u>

主要包括：

~~~text
schedule_interval

next_start

initial_start

fixed_schedule

timezone
~~~

最基本：

~~~text
schedule_interval
=
执行频率
~~~

例如：

~~~text
10 seconds

5 minutes

1 hour
~~~

next_start 表示：

~~~text
下一次计划执行时间
~~~

因此 Scheduler 实际关注：

~~~text
Current Time
    ↓
是否到达 next_start？
~~~

#### <u>4. Failure Policy 描述失败后怎样处理</u>

主要包括：

~~~text
max_runtime

max_retries

retry_period
~~~

可以理解：

~~~text
Job Running
    ↓
是否超过 max_runtime？

Failure
    ↓
还能 Retry 几次？

Retry
    ↓
等待多久？
~~~

所以 Job Framework 不只是：

~~~text
定时执行 SQL
~~~

还包含：

~~~text
Execution Lifecycle
+
Failure Handling
~~~

### 【五、Job Observability 是数据库自动化进入生产后的必要部分】

执行：

~~~sql
add_retention_policy(...)
~~~

返回成功，只能说明：

~~~text
Policy / Job
已经注册
~~~

不能说明：

~~~text
以后每一次执行
都会永久成功
~~~

Job 后续可能因为：

~~~text
Lock

Resource Pressure

SQL Error

Permission

Crash

Timeout

Version Issue
~~~

而失败。

所以：

> **自动化不等于无需监控。**

#### <u>1. jobs 查看系统计划运行什么</u>

查询：

~~~sql
SELECT *
FROM timescaledb_information.jobs;
~~~

主要回答：

~~~text
有哪些 Job？

目标 Hypertable 是谁？

执行哪个 Procedure？

多久运行一次？

下一次什么时候？

是否 Scheduled？

Config 是什么？
~~~

可以理解成：

~~~text
Job Definition / Schedule View
~~~

#### <u>2. job_stats 查看这些 Job 实际运行得怎么样</u>

计划存在以后，还需要知道：

~~~text
到底有没有成功执行？
~~~

因此可以查询 Job 运行统计信息。

重点关注：

~~~text
last_run_status

last_run_started_at

last_successful_finish

total_runs

total_successes

total_failures
~~~

概念上：

~~~text
jobs
    ↓
What should run?

job_stats
    ↓
How has it actually run?
~~~

#### <u>3. job_errors 继续回答为什么失败</u>

如果：

~~~text
last_run_status = Failed
~~~

还需要知道：

~~~text
Why?
~~~

Job Error 信息可以继续提供：

~~~text
Job ID

执行 Procedure

PostgreSQL Error Code

Error Message

Process ID
~~~

所以完整观察链：

~~~text
jobs
    ↓
这个 Job 应该怎么运行？

job_stats
    ↓
它实际运行得怎么样？

job_errors
    ↓
失败原因是什么？
~~~

### 【六、Job 失败不一定让 API 挂掉，但会让数据库维护状态逐渐失真】

Background Job 的特殊之处在于：

~~~text
它不是用户请求链路
~~~

所以 Job 失败时，经常不会立刻表现成：

~~~text
API 500
~~~

但会让数据库内部状态越来越偏离预期。

#### <u>1. Continuous Aggregate Refresh Job 失败会造成 Aggregate Stale</u>

假设：

~~~text
API
正常

Worker
正常

Raw Data
持续写入
~~~

但是：

~~~text
Continuous Aggregate Refresh Job
失败
~~~

可能结果：

~~~text
performance_samples
持续有新数据

但是

performance_rollup_1m
performance_rollup_1h

越来越旧
~~~

于是 Dashboard 历史统计可能出现：

~~~text
Stale Aggregate
~~~

所以：

~~~text
Raw Data Fresh
≠
Aggregate Fresh
~~~

#### <u>2. Columnstore / Compression Job 失败会让旧 Chunk 一直停留在热存储状态</u>

如果：

~~~text
Compression / Columnstore Job
失败
~~~

可能出现：

~~~text
旧 Chunk
一直保持 Rowstore
~~~

直接后果：

~~~text
Storage Cost ↑

Historical Query Cost ↑

Maintenance Cost ↑
~~~

所以：

~~~text
数据还能查询
~~~

不代表：

~~~text
生命周期策略仍然正常
~~~

#### <u>3. Retention Job 失败会让过期数据不断积累</u>

如果：

~~~text
Retention Job
失败
~~~

那么：

~~~text
30 天 Raw Retention Boundary
~~~

并不会被真正执行。

最终：

~~~text
Old Chunks
持续累积
        ↓
Storage 持续增长
~~~

所以需要固定一个工程边界：

~~~text
Application Health
≠
TimescaleDB Lifecycle Health
~~~

应用接口健康和数据库后台维护健康，需要分别观察。

### 【七、当前 Browser Monitor 已经注册大量 Policy，但尚未形成 Job Monitoring 闭环】

回到当前项目。

0001_platform.sql 已经创建：

~~~text
4 个 1m Continuous Aggregate Refresh Policies

4 个 Raw Retention Policies

4 个 Aggregate Retention Policies

4 个 Compression Policies
~~~

0002_hourly_aggregates.sql 又增加：

~~~text
4 个 1h Continuous Aggregate Refresh Policies

4 个 1h Aggregate Retention Policies
~~~

0005_custom_observability.sql 又继续增加：

~~~text
2 个 1m Refresh Policies

4 个 Retention Policies

2 个 Compression Policies
~~~

这说明 Migration 完成以后，数据库内部实际上会注册相当数量的 Background Jobs。

#### <u>1. 当前源码可以确认的是 Policy Registration</u>

当前仓库明确存在：

~~~text
add_continuous_aggregate_policy

add_retention_policy

add_compression_policy
~~~

因此可以确认：

~~~text
Policy / Background Job
会被注册
~~~

#### <u>2. 当前源码不能确认已经建立 Job Health Monitoring</u>

目前已读取的仓库资料中，还没有看到应用层主动查询：

~~~text
timescaledb_information.jobs

timescaledb_information.job_stats

timescaledb_information.job_errors
~~~

并建立：

~~~text
Dashboard

Alert

Lag Monitoring
~~~

闭环。

所以必须区分：

~~~text
Confirmed Implementation

Policy / Background Jobs
已经大量注册
~~~

与：

~~~text
Current Source Not Confirmed

还没有确认
TimescaleDB Job Health
已经进入应用监控闭环
~~~

不能把“TimescaleDB 提供可观察能力”直接描述成“当前项目已经实现”。

#### <u>3. Database Maintenance Monitoring 可以形成独立模型</u>

如果未来补全，可以关注：

~~~text
Background Job Health
│
├── Job Inventory
│      ↓
│   jobs
│
├── Freshness
│      ↓
│   last_successful_finish
│   next_start
│
├── Reliability
│      ↓
│   total_runs
│   total_failures
│
├── Error
│      ↓
│   job_errors
│
└── Lag
       ↓
    now - last_successful_finish
~~~

尤其 Continuous Aggregate 的 Refresh Lag 非常关键。

例如：

~~~text
schedule_interval = 10s
~~~

但：

~~~text
last_successful_finish
=
10 分钟以前
~~~

即使：

~~~text
API 返回 200
~~~

也已经说明：

~~~text
Aggregate Maintenance
严重落后
~~~

### 【八、Custom Job 说明 Job Framework 不只服务内置 Policy】

TimescaleDB Job Scheduler 不只是：

~~~text
Internal Policy Executor
~~~

它还可以注册：

~~~text
User-defined Job
~~~

例如概念上：

~~~sql
SELECT add_job(
  'process_hourly_reports',
  '1h'
);
~~~

或者：

~~~sql
SELECT add_job(
  'process_hourly_reports',
  '1h',
  config => '{"hypertable":"metrics"}'
);
~~~

然后 Scheduler 周期调用对应 PostgreSQL Procedure。

#### <u>1. Custom Job 的基本模型</u>

~~~text
PostgreSQL Procedure
        ↓
add_job(...)
        ↓
Job Registration
        ↓
Scheduler
        ↓
Background Worker
        ↓
Procedure Execution
~~~

因此：

~~~text
TimescaleDB Automation Framework
│
├── Built-in Policy Jobs
│   ├── Refresh
│   ├── Retention
│   └── Columnstore
│
└── Custom Jobs
    └── User Procedure
~~~

#### <u>2. alter_job 修改任务运行配置，而不是重写 Procedure</u>

例如：

~~~sql
SELECT alter_job(
  1000,
  scheduled => false
);
~~~

可以用于：

~~~text
暂停调度
~~~

也可以调整：

~~~text
schedule_interval

next_start

config
~~~

因此需要区分：

~~~text
Procedure
    ↓
What to Do

Job Config
    ↓
How to Run

Schedule
    ↓
When to Run
~~~

#### <u>3. delete_job 删除的是任务注册</u>

例如：

~~~sql
SELECT delete_job(1234);
~~~

表示：

~~~text
Scheduler
不再管理这个 Job
~~~

不等于：

~~~text
删除业务 Table
~~~

也不等于：

~~~text
删除 PostgreSQL Procedure
~~~

### 【九、TimescaleDB Background Worker 与当前应用 Worker 是两套完全不同的异步系统】

这对 Browser Monitor 特别重要。

当前项目已经有自己的：

~~~text
Application Worker
~~~

负责：

~~~text
Outbox
    ↓
Projection
    ↓
performance_samples
view_records
custom_signal_samples
...
~~~

同时数据库内部还有：

~~~text
TimescaleDB Background Worker
~~~

二者不能混淆。

#### <u>1. Application Worker 属于业务处理层</u>

它运行在：

~~~text
Node.js Application Layer
~~~

负责：

~~~text
业务数据加工
~~~

例如：

~~~text
Raw Telemetry Event
        ↓
Performance Projection
        ↓
performance_samples
~~~

#### <u>2. TimescaleDB Background Worker 属于数据库基础设施层</u>

它负责：

~~~text
Continuous Aggregate Refresh

Columnstore / Compression

Retention

Custom Database Job
~~~

也就是：

~~~text
数据库自动维护
~~~

而不是业务事件处理。

#### <u>3. 当前项目完整异步链可以画成</u>

~~~text
Browser SDK
    ↓
API
    ↓
telemetry_events
    ↓
Application Worker
    ↓
performance_samples
    ↓
TimescaleDB Background Jobs
    ├── Refresh Aggregate
    ├── Columnstore / Compression
    └── Retention
~~~

所以：

~~~text
Application Worker
≠
TimescaleDB Background Worker
~~~

前者解决：

~~~text
业务状态如何加工
~~~

后者解决：

~~~text
数据库如何自动维护
~~~

### 【十、脱离项目建立完整的 TimescaleDB Automation Framework】

现在可以彻底抽象：

~~~text
                 TimescaleDB Automation
                          │
              ┌───────────┴───────────┐
              │                       │
              ▼                       ▼
         Built-in Policy          Custom Job
              │                       │
      ┌───────┼────────┐              │
      ▼       ▼        ▼              ▼
   Refresh  Column   Retention    User Procedure
              │                       │
              └───────────┬───────────┘
                          ▼
                         Job
                          │
          ┌───────────────┼────────────────┐
          │               │                │
          ▼               ▼                ▼
       Config          Schedule        Retry Policy
          │               │                │
          └───────────────┼────────────────┘
                          ▼
                      Scheduler
                          │
                          ▼
                  Background Worker
                          │
                          ▼
                       Execute
                          │
                    ┌─────┴─────┐
                    ▼           ▼
                 Success      Failure
                    │           │
                    ▼           ▼
                job_stats   job_errors
~~~

这张图就是本节真正需要建立的 TimescaleDB 自动化体系。

### 【十一、生产环境中的 Policy 需要同时设计四个维度】

以后再看到：

~~~sql
add_xxx_policy(...)
~~~

不能只问：

~~~text
参数怎么写？
~~~

而应该同时考虑四个问题。

#### <u>1. Trigger Condition 决定什么时候符合处理条件</u>

例如：

~~~text
older than 24h

older than 30d

now - 29d ~ now - 10s
~~~

回答：

~~~text
什么数据
现在应该进入这个维护阶段？
~~~

#### <u>2. Schedule 决定多久执行一次</u>

例如：

~~~text
10 seconds

5 minutes

1 hour
~~~

回答：

~~~text
系统多久检查 / 执行一次？
~~~

#### <u>3. Cost 决定后台维护会消耗多少数据库资源</u>

Job 执行会占用：

~~~text
CPU

Memory

I/O

Locks

Worker Capacity
~~~

所以不能：

~~~text
所有 Job
都配置成最高频率
~~~

而完全不考虑资源竞争。

因此 Job 本身也是数据库 Workload，需要容量治理。

#### <u>4. Observability 决定自动化是否真的健康</u>

每个 Policy 都应该能够回答：

~~~text
最近成功是什么时候？

是否正在失败？

失败多少次？

现在是否 Lag？

下次何时运行？
~~~

所以完整的 Policy Design 应该包含：

~~~text
Rule
+
Schedule
+
Resource
+
Monitoring
~~~

而不是只包含：

~~~text
Retention = 30 days
~~~

### 【十二、第六节收束：TimescaleDB 具备数据库内部 Automation & Operations Framework】

这一节真正建立的是：

~~~text
TimescaleDB Automation
│
├── 一、Policy
│   └── 声明数据库希望维持什么状态
│
├── 二、Job
│   └── 把 Policy 转换成可调度执行任务
│
├── 三、Scheduler / Worker
│   └── 决定什么时候运行并真正执行
│
└── 四、Observability
    ├── jobs
    ├── job_stats
    └── job_errors
~~~

前面六节现在可以连接成：

~~~text
TimescaleDB
│
├── Storage Organization
│   └── Hypertable / Chunk
│
├── Query
│   └── Time Range / time_bucket
│
├── Precomputation
│   └── Continuous Aggregate
│
├── Storage Lifecycle
│   └── Rowstore / Columnstore / Retention
│
└── Automation
    └── Policy / Job / Scheduler / Worker
~~~

这意味着 TimescaleDB 不只是：

~~~text
一个能够存储 Time-Series Data
的 PostgreSQL Extension
~~~

而是进一步具备：

> **主动维护时序数据生命周期的数据库内部自动化框架。**

### 【当前项目最终映射】

~~~text
Application
│
├── API
│
└── Node Worker
│      ↓
│   业务数据加工
│
▼
PostgreSQL + TimescaleDB
│
├── Raw Hypertables
│
├── Continuous Aggregates
│
└── Background Job Framework
    │
    ├── 1m Refresh Jobs
    │
    ├── 1h Refresh Jobs
    │
    ├── Compression Jobs
    │
    └── Retention Jobs
~~~

当前源码已经完成：

~~~text
Policy Registration
~~~

但从目前已读取仓库资料中，还不能确认已经建立：

~~~text
Job Monitoring
+
Failure Alert
+
Refresh Lag Alert
~~~

这应该作为：

~~~text
当前实现
~~~

与：

~~~text
完整生产治理体系
~~~

之间的边界。

## 7. 下一节进入 Hierarchical Continuous Aggregate

到这里，TimescaleDB 的基础体系已经覆盖：

~~~text
Data Organization

Query

Precomputation

Storage Lifecycle

Automation
~~~

下一步再进入：

~~~text
Advanced Analytics
~~~

才比较自然。

因此下一节进入：

> **Hierarchical Continuous Aggregate 通过多层时间粒度构建长期历史分析模型。**

重点先讲：

~~~text
Raw
    ↓
1m
    ↓
1h
    ↓
1d
~~~

为什么要逐层 Downsampling；

~~~text
1h CAGG
为什么可以建立在 1m CAGG 上？
~~~

以及：

~~~text
Refresh Policy
为什么也要形成层级依赖？
~~~

然后再下一节单独进入：

~~~text
Two-step Aggregate
+
Hyperfunctions
~~~

解释：

~~~text
Average 为什么不能简单 avg(avg)

Percentile 为什么不能 percentile(p75)

Distinct Count 为什么不能 sum(distinct count)

为什么要保存可继续 Rollup 的统计中间状态
~~~

这样就不会把 Hierarchical CAGG 与 Percentile / HLL 混成同一节。
