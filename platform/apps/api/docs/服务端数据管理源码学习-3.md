# 服务端数据管理源码学习-3

> **专题定位**：本篇进入 TimescaleDB / Time-Series Data Management。学习目标不是直接记忆 Hypertable、Continuous Aggregate、Compression 等 API，而是从 Browser Monitor 当前源码出发，逐步回答“为什么项目需要时序数据管理、TimescaleDB 在 PostgreSQL / Redis / Worker / Analytics 之间承担什么职责、源码为什么这样设计”，再从项目实现中抽象出能够脱离当前项目独立成立的时序数据管理知识框架。
>
> **学习方式**：每一节只推进一个核心问题，并严格按照“项目原文 → 项目整体链路 → 对应源码 → 源码执行逻辑 → 抽象框架 → 通用知识体系 → 回到项目分析”的路径展开。先建立整体位置，再进入 Hypertable、Chunk、Continuous Aggregate、Rollup、Compression、Retention 等内部机制。
>
> **与已有知识的关系**：
>
> - 服务端数据管理源码学习.md：Database → Connection → SQL → Schema / Drizzle → Constraint → Index。
> - 服务端数据管理源码学习-2.md：Transaction → Concurrency Control。
> - Redis体系源码学习.md：Runtime State → Cache → Session → Rate Limit → Atomicity → Reliability → Scale → Production Governance。
> - 本篇：Time-Series Data Management → TimescaleDB → 时序组织 → 时序聚合 → 历史生命周期。
>
> **分析边界**：项目事实以当前 browser-monitor/platform 源码为准。通用概念只在源码能够引出时展开，并明确区分“当前项目已经实现”“TimescaleDB 通用能力”“后续可继续深入的设计”。

## 1. TimescaleDB 是 PostgreSQL 之上的时序数据管理层，而不是项目中的另一套独立数据库

这一节先不进入：

~~~text
Hypertable
Chunk
Continuous Aggregate
Compression
Retention
~~~

因为这些都是 TimescaleDB 内部能力。

在理解内部机制之前，必须先回答一个更基础的问题：

> **当前 Browser Monitor 已经使用 PostgreSQL，为什么还需要 TimescaleDB？TimescaleDB 在整个服务端数据管理链路中到底处于什么位置？**

如果这个位置没有建立清楚，后面学习 TimescaleDB 很容易退化成：

~~~text
create_hypertable 是什么

time_bucket 怎么写

Continuous Aggregate 怎么配置

Compression Policy 有哪些参数
~~~

最终只记住零散 API，而没有建立“什么时候需要这一类数据管理能力”的系统框架。

这一节因此只做一件事：

~~~text
把 TimescaleDB 放回完整 Server Data Architecture
~~~

### 【第一层：先从项目整体数据链路定位 TimescaleDB】

#### <u>1. 项目原文已经明确给出 TimescaleDB 所处的数据处理阶段</u>

当前 platform/README.md 对完整链路的描述是：

> Monitor SDK → 公开 DSN → Ingestion API → telemetry_events + Outbox → Worker → TimescaleDB 聚合 → Analytics API → React 看板

先不看任何 TimescaleDB API，只把这条链拆成职责：

~~~text
Monitor SDK
    ↓
数据产生

Ingestion API
    ↓
数据接收

telemetry_events + Outbox
    ↓
原始事实可靠落库
+
记录后续处理任务

Worker
    ↓
异步加工
形成领域查询模型

TimescaleDB
    ↓
时序数据组织
+
时序聚合
+
历史数据生命周期

Analytics API
    ↓
查询与统计服务

React Dashboard
    ↓
展示
~~~

因此从项目原文就能先得到一个非常重要的结论：

~~~text
TimescaleDB
并不位于数据入口

TimescaleDB
也不负责前端 Session / Cache / Rate Limit

TimescaleDB
主要出现在数据已经可靠接收以后
进入长期时序分析的阶段
~~~

所以它在当前项目中的位置更接近：

~~~text
Data Ingestion
    ↓
Durable Storage
    ↓
Async Processing
    ↓
Time-Series Management
    ↓
Analytics
~~~

而不是：

~~~text
Request
    ↓
TimescaleDB
    ↓
Response
~~~

这样一条孤立链路。

#### <u>2. TimescaleDB 所处的位置说明它解决的是“长期历史数据怎样管理”</u>

把 Browser Monitor 再压缩成一条数据生命周期：

~~~text
Browser
    ↓
产生 Telemetry

API
    ↓
接收 Telemetry

PostgreSQL Transaction
    ↓
保证 Raw Event + Outbox
可靠提交

Worker
    ↓
把 Raw Event
加工成查询模型

TimescaleDB
    ↓
管理不断增长的
Time-Series Data

Analytics API
    ↓
按照时间范围
查询趋势与统计

Redis
    ↓
缓存最终 Query Result

Web
    ↓
展示
~~~

这里已经可以发现：

~~~text
PostgreSQL Transaction
解决：
这批数据是否可靠成为事实

Worker
解决：
原始数据怎样被加工

TimescaleDB
解决：
长期时序数据怎样组织和查询

Redis
解决：
运行时结果怎样快速复用
~~~

所以 TimescaleDB 的核心问题不是：

~~~text
数据能不能存进去？
~~~

因为普通 PostgreSQL 本身已经可以 INSERT。

它真正面对的是：

~~~text
数据持续产生以后
怎样长期组织？

历史越来越多以后
怎样按时间范围查询？

同一类统计不断被重复计算
怎样降低成本？

旧数据价值变化以后
怎样压缩、降采样和清理？
~~~

这才是：

~~~text
Time-Series Data Management
~~~

的真正入口。

### 【第二层：从部署源码确认 TimescaleDB 与 PostgreSQL 的真实关系】

理解项目链路以后，再进入部署代码。

这里最重要的是先纠正一个容易出现的概念错误：

~~~text
PostgreSQL
TimescaleDB
Redis

≠

三个完全独立的数据库系统
~~~

当前项目不是这样设计的。

#### <u>1. Docker Service 名叫 timescaledb，但应用连接的仍然是 PostgreSQL</u>

当前 docker-compose.yml：

~~~yaml
timescaledb:
  image: timescale/timescaledb-ha:pg17

  environment:
    POSTGRES_DB: monitor
    POSTGRES_USER: monitor
    POSTGRES_PASSWORD: ...

  ports:
    - "5432:5432"
~~~

API / Worker 使用：

~~~text
DATABASE_URL
    ↓
postgres://monitor:...@timescaledb:5432/monitor
~~~

这里可以直接看到：

~~~text
Protocol
    ↓
postgres://

Port
    ↓
5432

Database
    ↓
monitor

User
    ↓
PostgreSQL User
~~~

应用没有使用另一套：

~~~text
timescale://
~~~

协议。

因此运行关系应该理解成：

~~~text
Application
    ↓
PostgreSQL Driver
    ↓
PostgreSQL Protocol
    ↓
PostgreSQL Database Engine
    +
TimescaleDB Extension
~~~

而不是：

~~~text
Application
 ├── PostgreSQL Database
 └── TimescaleDB Database
~~~

#### <u>2. Migration 进一步证明 TimescaleDB 是 PostgreSQL 内部扩展能力</u>

当前 0001_platform.sql 一开始：

~~~sql
CREATE EXTENSION IF NOT EXISTS pgcrypto;

CREATE EXTENSION IF NOT EXISTS timescaledb;

CREATE EXTENSION IF NOT EXISTS timescaledb_toolkit;
~~~

这段代码表达的层级非常清楚：

~~~text
PostgreSQL Database
│
├── PostgreSQL Native Capability
│
├── pgcrypto Extension
│
├── timescaledb Extension
│
└── timescaledb_toolkit Extension
~~~

所以前两篇已经学过的：

~~~text
Table

SQL

Index

Constraint

Transaction

MVCC

Connection Pool
~~~

并没有因为 TimescaleDB 出现而失效。

更准确地说：

~~~text
PostgreSQL
    ↓
提供通用关系型数据管理基础

TimescaleDB
    ↓
在 PostgreSQL 之上
增加 Time-Series Capability
~~~

后面才会逐步展开：

~~~text
Hypertable

Chunk

time_bucket

Continuous Aggregate

Retention

Compression / Columnstore

Time-Series Hyperfunctions
~~~

因此需要先固定一个概念：

> **TimescaleDB 不是 PostgreSQL 的替代数据库，而是建立在 PostgreSQL 之上的时序数据管理扩展层。**

#### <u>3. PostgreSQL 与 TimescaleDB 是“基础能力 + 专用工作负载能力”的关系</u>

可以抽象成：

~~~text
PostgreSQL
│
├── General Relational Data Management
│   ├── Table
│   ├── Relation
│   ├── SQL
│   ├── Index
│   ├── Constraint
│   ├── Transaction
│   └── Concurrency Control
│
└── TimescaleDB Extension
    └── Time-Series Data Management
        ├── Time Partition
        ├── Time Range Query
        ├── Time Bucket
        ├── Incremental Aggregate
        ├── Historical Rollup
        └── Data Lifecycle
~~~

因此：

~~~text
TimescaleDB Knowledge
~~~

不是另外一套和 PostgreSQL 毫无关系的知识。

而是：

~~~text
PostgreSQL Knowledge
        ↓
遇到 Time-Series Workload
        ↓
增加专门的数据组织与分析能力
~~~

这也是本篇为什么必须建立在前两篇 PostgreSQL 学习之后。

### 【第三层：当前项目之所以需要 TimescaleDB，是因为数据 Workload 已经发生变化】

既然 PostgreSQL 本身可以建表、插入、索引和查询，那么自然要继续问：

> **为什么当前项目不能只停留在普通 PostgreSQL 数据模型？**

答案不应该简化成：

~~~text
TimescaleDB 更快
~~~

而应该先比较项目中的两类数据。

#### <u>1. 一类是关系型业务状态，核心是实体当前状态与关系</u>

当前 Migration 中：

~~~text
users

user_sessions

account_tokens

projects

project_members

ingestion_keys

allowed_origins

threshold_versions

project_invitations

outbox_tasks
~~~

这些数据主要表达：

~~~text
User 是谁

Project 是什么

谁属于哪个 Project

当前使用哪个 Threshold

Token 是否有效

Outbox Task 当前处于什么状态
~~~

典型访问方式：

~~~sql
WHERE id = ?

WHERE user_id = ?

WHERE project_id = ?

WHERE token_hash = ?

WHERE active = true
~~~

它们的核心问题更接近：

~~~text
Entity
    ↓
Relation
    ↓
Constraint
    ↓
Transaction
    ↓
Current Business State
~~~

这就是前两篇 PostgreSQL 学习主要解决的：

~~~text
Relational Business Data
~~~

#### <u>2. 另一类是持续产生的监控事实，核心是系统随时间怎样变化</u>

当前 Migration 中还有：

~~~text
telemetry_events

performance_samples

view_records

custom_event_samples

custom_signal_samples

custom_metric_samples
~~~

这些表都有非常重要的时间字段：

~~~text
occurred_at

observed_at

started_at
~~~

例如 performance_samples 形成的逻辑更像：

~~~text
10:00:01
LCP = 2100

10:00:05
LCP = 2500

10:00:10
INP = 180

10:00:16
LCP = 1900

...
~~~

系统真正关心的通常不是：

~~~text
根据 Primary Key
找某一条 Sample
~~~

而是：

~~~text
Project P001

过去 24 小时

LCP

每一分钟

count
avg
p50
p75
p95
good / poor
~~~

查询结构变成：

~~~text
Entity Scope
    +
Time Range
    +
Time Bucket
    +
Aggregation
~~~

这就是：

~~~text
Time-Series Workload
~~~

#### <u>3. Time-Series 的关键不是“表里有 timestamp”，而是时间成为第一组织维度</u>

普通业务表同样可能有：

~~~text
created_at
updated_at
~~~

但它们不一定是 Time-Series。

判断一份数据是不是典型时序工作负载，更重要的是：

~~~text
Time
    ↓
是否决定数据排序？

Time Range
    ↓
是否是主要查询条件？

New Data
    ↓
是否持续沿时间轴追加？

Analytics
    ↓
是否经常按时间 Bucket 聚合？

Lifecycle
    ↓
历史数据价值是否随时间变化？
~~~

所以可以抽象：

~~~text
Relational Entity Data
        ↓
Entity-centered

Time-Series Data
        ↓
Time-centered
~~~

这个区别非常重要。

后面所有 TimescaleDB 能力都不是凭空产生，而是从这个 Workload 差异自然推出来的。

### 【第四层：Time-Series Workload 会产生三类新的数据管理问题】

当前项目引入 TimescaleDB，不是因为普通 PostgreSQL 无法存数据，而是因为随着监控数据规模增长，会出现三类越来越突出的系统问题。

#### <u>1. 第一类问题是 Data Growth：数据会沿时间持续增长</u>

普通项目表可能：

~~~text
projects
    ↓
几百
几千
几万 Rows
~~~

而 Telemetry 是：

~~~text
每秒持续产生
~~~

假设：

~~~text
100 events / second
~~~

一天就是：

~~~text
8,640,000 events
~~~

如果：

~~~text
1000 events / second
~~~

一天就是：

~~~text
86,400,000 events
~~~

持续运行以后：

~~~text
Time
    ↓
Row Count
    ↓
Storage
    ↓
Index Size
    ↓
Query Cost
    ↓
Maintenance Cost
~~~

都会持续增加。

所以第一类核心问题是：

~~~text
Growing Dataset
~~~

普通：

~~~text
一张表 + 一个 Index
~~~

并不能完整回答：

~~~text
几年以后这张表怎样继续管理
~~~

的问题。

#### <u>2. 第二类问题是 Analytical Query：查询通常扫描范围后再聚合</u>

普通业务查询：

~~~sql
SELECT *
FROM projects
WHERE id = $1;
~~~

而监控 Analytics 更接近：

~~~sql
SELECT
  time_bucket(
    INTERVAL '1 minute',
    observed_at
  ),
  percentile_cont(0.75)
FROM performance_samples
WHERE
  project_id = $1
  AND observed_at >= $2
  AND observed_at < $3
GROUP BY ...;
~~~

后者往往经历：

~~~text
Time Range Scan
    ↓
Filter
    ↓
Group
    ↓
Aggregate
    ↓
Percentile / Distinct
    ↓
Return Trend
~~~

同一个 Dashboard 还会不断重复类似计算。

于是第二类问题变成：

~~~text
Repeated Analytical Computation
~~~

而不只是：

~~~text
Single Row Lookup
~~~

#### <u>3. 第三类问题是 Data Lifecycle：历史数据价值随时间发生变化</u>

监控数据通常具有很明显的时间价值变化：

~~~text
刚产生
    ↓
定位问题价值最高
需要完整明细
需要高分辨率

几天以后
    ↓
仍需要分析
但单条 Event 价值下降

几个月以后
    ↓
更多关注长期趋势
而不是每一条原始记录
~~~

所以：

~~~text
所有 Raw Data
永远以相同精度保存
~~~

并不是唯一合理方案。

当前项目已经明确：

~~~text
Raw / Detail
    ↓
30 days

Aggregate
    ↓
180 days
~~~

这说明时序数据系统必须继续回答：

~~~text
什么时候保留 Raw？

什么时候聚合？

什么时候压缩？

什么时候降低时间分辨率？

什么时候删除？
~~~

第三类核心问题因此是：

~~~text
Historical Data Lifecycle
~~~

### 【第五层：TimescaleDB 的核心能力可以从三类 Workload 问题自然推出】

到这里还没有深入任何一个 API，但已经能够自然推出 TimescaleDB 为什么会出现。

~~~text
Time-Series Workload
│
├── ① Data Growth
│      ↓
│   Time Partition
│   Hypertable
│   Chunk
│
├── ② Analytical Query
│      ↓
│   time_bucket
│   Continuous Aggregate
│   Hyperfunctions
│   Rollup
│
└── ③ Data Lifecycle
       ↓
    Compression / Columnstore
    Retention
    Downsampling
~~~

因此 TimescaleDB 不应该被记成：

~~~text
一个比 PostgreSQL 更快的数据库
~~~

而应该记成：

> **TimescaleDB 在 PostgreSQL 通用关系型能力之上，为持续增长、以时间范围查询和聚合为主要访问模式的数据增加专门的数据组织、分析和生命周期能力。**

这也是后面整个学习顺序的来源：

~~~text
为什么需要 Time-Series Management
        ↓
数据怎样按时间组织
        ↓
Hypertable / Chunk

然后
        ↓
数据怎样按时间聚合
        ↓
time_bucket / Continuous Aggregate

然后
        ↓
历史数据怎样降采样和继续聚合
        ↓
Rollup / Two-step Aggregate

最后
        ↓
历史数据怎样控制长期成本
        ↓
Compression / Retention
~~~

也就是说：

~~~text
TimescaleDB API
~~~

不是学习起点。

真正的起点是：

~~~text
Time-Series Workload
~~~

### 【第六层：回到源码，当前 TimescaleDB 实际已经承担四层职责】

建立通用框架以后，再重新看当前项目源码。

当前项目不是只使用：

~~~text
create_hypertable
~~~

一个功能。

整个 Migration 已经形成四层能力。

#### <u>1. Time-Series Storage 负责组织 Raw 与 Projection Data</u>

源码：

~~~sql
SELECT create_hypertable(
  'telemetry_events',
  'occurred_at',
  if_not_exists => TRUE
);

SELECT create_hypertable(
  'performance_samples',
  'observed_at',
  if_not_exists => TRUE
);

SELECT create_hypertable(
  'view_records',
  'started_at',
  if_not_exists => TRUE
);
~~~

这层负责：

~~~text
持续增长的 Raw / Projected Data
        ↓
按照时间维度组织
~~~

这里下一节才深入：

~~~text
Hypertable
+
Chunk
+
Chunk Pruning
+
Index
~~~

#### <u>2. Time-Series Analytics 负责把时间轴转换成统计结果</u>

源码：

~~~sql
CREATE MATERIALIZED VIEW performance_rollup_1m
WITH (timescaledb.continuous) AS
SELECT
  time_bucket(
    INTERVAL '1 minute',
    observed_at
  ) AS bucket,
  ...
FROM performance_samples
GROUP BY ...;
~~~

它把：

~~~text
Raw Samples
    ↓
Continuous Timeline
~~~

转换成：

~~~text
1-minute Aggregate
~~~

后面还存在：

~~~text
1m
    ↓
1h
~~~

形成：

~~~text
Precomputation
+
Downsampling
~~~

#### <u>3. Statistical State 负责保存可继续组合的分析状态</u>

当前不仅计算：

~~~text
count
avg
min
max
~~~

还使用：

~~~sql
percentile_agg(value)
~~~

以及：

~~~sql
hyperloglog(
  8192,
  session_id
)
~~~

说明当前数据库层还承担：

~~~text
Percentile

Distinct Session

Distinct View
~~~

这类复杂统计。

后续会单独进入：

~~~text
Two-step Aggregate
~~~

解释为什么不能简单保存：

~~~text
一个 p75 number
或
一个 count distinct number
~~~

而需要保留可 Rollup 的中间状态。

#### <u>4. Historical Lifecycle 负责决定旧数据怎样继续存在</u>

当前 Migration 还存在：

~~~text
add_compression_policy

add_retention_policy
~~~

说明系统已经明确：

~~~text
Data Age
    ↓
Storage Strategy
    ↓
Resolution
    ↓
Retention
~~~

会随时间发生变化。

最终形成：

~~~text
Recent
    ↓
Raw Detail

Older
    ↓
Compressed Detail

Historical
    ↓
Aggregate

Expired
    ↓
Delete
~~~

所以当前 TimescaleDB 的真实职责已经不是：

~~~text
一个数据库插件
~~~

而是完整的：

~~~text
Time-Series Storage
+
Analytics
+
Statistical Processing
+
Historical Lifecycle
~~~

### 【第七层：TimescaleDB 与 PostgreSQL、Redis 的职责边界必须放在同一张图中】

理解 TimescaleDB 以后，需要把前面已经学过的 PostgreSQL 与 Redis 一起放回来。

~~~text
                    Server Data
                         │
       ┌─────────────────┼─────────────────┐
       │                 │                 │
       ▼                 ▼                 ▼
 Relational State   Time-Series State   Runtime State
       │                 │                 │
       ▼                 ▼                 ▼
 PostgreSQL        PostgreSQL +          Redis
                   TimescaleDB
~~~

这里严格来说：

~~~text
TimescaleDB
仍然属于 PostgreSQL 数据库体系
~~~

只是面对不同 Workload。

#### <u>1. PostgreSQL 的核心是长期关系型业务事实是否正确</u>

典型：

~~~text
users

projects

project_members

threshold_versions

outbox_tasks
~~~

核心关注：

~~~text
Relation

Constraint

Transaction

Concurrency

Durability

Business Invariant
~~~

可以概括：

~~~text
Authoritative Relational State
~~~

#### <u>2. TimescaleDB 的核心是持续增长的历史事实怎样长期管理</u>

典型：

~~~text
telemetry_events

performance_samples

view_records

custom_signal_samples
~~~

核心关注：

~~~text
Time Partition

High Ingest

Time Range Query

Aggregation

Downsampling

Historical Lifecycle
~~~

可以概括：

~~~text
Authoritative Time-Series History
~~~

#### <u>3. Redis 的核心是运行中的共享状态怎样高频访问</u>

典型：

~~~text
Session

Rate Limit

Recent Window

Analytics Cache

Cache Version
~~~

核心关注：

~~~text
Low Latency

TTL

Atomic Mutation

Runtime Shared State

Derived State
~~~

可以概括：

~~~text
Runtime / Derived State
~~~

因此不要建立：

~~~text
PostgreSQL = 慢

TimescaleDB = 快

Redis = 最快
~~~

这种性能排序模型。

应该建立：

~~~text
PostgreSQL
    ↓
Relational / Transactional Model

TimescaleDB
    ↓
Time-Series / Analytical Model

Redis
    ↓
Runtime State Model
~~~

它们解决的是不同的数据管理问题。

### 【第八层：脱离当前项目，建立是否需要 Time-Series Data Management 的判断框架】

以后遇到其他系统，不应该看到：

~~~text
数据很多
~~~

就直接决定：

~~~text
使用 TimescaleDB
~~~

应该顺着数据语义和访问模式判断。

#### <u>1. 数据是否天然沿时间持续产生</u>

典型：

~~~text
Metrics

Logs

Telemetry

IoT Sensor Data

Financial Ticks

Observability Events
~~~

共同模式：

~~~text
Time T1
    ↓
New Data

Time T2
    ↓
New Data

Time T3
    ↓
New Data
~~~

如果数据主要不是这样产生，TimescaleDB 未必有意义。

#### <u>2. 主要查询是否围绕 Time Range</u>

例如：

~~~text
最近 1 小时

最近 24 小时

过去 7 天

过去 30 天
~~~

如果系统核心查询仍然只是：

~~~text
WHERE id = ?
~~~

那么普通 PostgreSQL 可能已经足够。

#### <u>3. 是否需要大量时间聚合</u>

例如：

~~~text
每分钟

每小时

每天
~~~

并计算：

~~~text
COUNT

AVG

SUM

P75

P95

Distinct
~~~

这时 Time-Series Analytics 特征开始变强。

#### <u>4. 数据是否会长期持续增长</u>

例如：

~~~text
Today
    ↓
10M rows

Next Month
    ↓
300M rows

Next Year
    ↓
Billions of rows
~~~

如果数据规模会沿时间持续累积：

~~~text
Partition
Rollup
Lifecycle
~~~

就会逐渐成为核心设计问题。

#### <u>5. 历史数据是否允许降低时间精度</u>

例如：

~~~text
最近 24h
    ↓
Raw

最近 30d
    ↓
1-minute

半年历史
    ↓
1-hour
~~~

如果答案是 Yes：

~~~text
Continuous Aggregate

Downsampling

Retention
~~~

会具有很高价值。

因此可以形成完整判断链：

~~~text
Data
 ↓
是否 Time-oriented？
 ↓ Yes
是否持续产生？
 ↓ Yes
是否主要 Time Range Query？
 ↓ Yes
是否频繁 Aggregate？
 ↓ Yes
是否随时间长期增长？
 ↓ Yes
是否需要 Historical Lifecycle？
 ↓ Yes

Time-Series Data Management
        ↓
TimescaleDB
成为候选方案
~~~

这里仍然是：

~~~text
候选方案
~~~

而不是：

~~~text
唯一方案
~~~

最终还需要结合：

~~~text
Current PostgreSQL Stack

Scale

Operation Cost

Query Complexity

Team Capability

Deployment Model
~~~

进行判断。

### 【第九层：回到 Browser Monitor，给当前 TimescaleDB 一个准确定位】

经过前面的项目源码、Workload 和通用框架，现在可以准确描述当前项目：

> **Browser Monitor 是一个以 PostgreSQL 为统一持久化基础，利用 TimescaleDB Extension 管理大量遥测时序历史，再使用 Redis 管理运行时状态和查询缓存的数据平台。**

完整数据层：

~~~text
                     Browser Monitor Data Layer
                               │
             ┌─────────────────┼──────────────────┐
             │                 │                  │
             ▼                 ▼                  ▼
     Relational Business   Time-Series Data   Runtime State
             │                 │                  │
             ▼                 ▼                  ▼
        PostgreSQL        TimescaleDB             Redis
             │                 │                  │
      User / Project       Telemetry          Session
      Permission           Performance        Rate Limit
      Threshold            View               Cache
      Outbox               Custom Signal      Counter
                               │
                               ▼
                         Continuous Aggregate
                               │
                               ▼
                            Rollup
                               │
                               ▼
                         Analytics API
~~~

因此 TimescaleDB 在当前项目中承担：

~~~text
不是：
另一个 PostgreSQL 替代品

不是：
Redis Cache 的替代品

而是：
PostgreSQL 之上的
Time-Series Data Management Layer
~~~

### 【第一节最终形成 TimescaleDB 的整体位置框架】

这一节不要求记住任何具体 API。

真正需要形成的是：

~~~text
PostgreSQL
解决：
数据怎样成为可靠的关系型业务事实
        ↓
系统开始产生大量
持续增长的时间数据
        ↓
普通 PostgreSQL 能继续保存
但 Workload 已经发生变化
        ↓
Data Growth
+
Time Range Query
+
Repeated Aggregation
+
Historical Lifecycle
        ↓
TimescaleDB
在 PostgreSQL 之上
增加 Time-Series Data Management
~~~

最终固定三个边界：

~~~text
TimescaleDB
≠
PostgreSQL 的替代品

TimescaleDB
≠
Redis 的替代品

TimescaleDB
=
PostgreSQL
+
Time-Series Data Management Capability
~~~

这就是后续整个 TimescaleDB 学习的起点。

## 2. 下一节进入 Hypertable、Chunk 与时间分区

理解 TimescaleDB 为什么存在以后，下一节自然要回答：

> **既然底层仍然是 PostgreSQL Table，TimescaleDB 到底怎样让一张持续增长的时序表在物理层面变得可管理？**

下一节沿着：

~~~text
普通 PostgreSQL Table
        ↓
持续增长以后出现什么问题

Partition
        ↓
Hypertable
        ↓
Chunk
        ↓
Chunk Pruning
        ↓
Index
~~~

下一节仍然按照：

