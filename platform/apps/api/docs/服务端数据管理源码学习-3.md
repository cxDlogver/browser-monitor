# 服务端数据管理源码学习-3

> **专题定位**：本篇进入 TimescaleDB / Time-Series Data Management。学习目标不是直接记忆 Hypertable、Continuous Aggregate、Compression 等 API，而是从 Browser Monitor 当前源码出发，逐步回答“为什么项目需要时序数据管理、TimescaleDB 在 PostgreSQL / Redis / Worker / Analytics 之间承担什么职责、源码为什么这样设计”，再从项目实现中抽象出能够脱离当前项目独立成立的时序数据管理知识框架。
>
> **学习方式**：每一节只推进一个核心问题，并严格按照“项目原文 → 项目整体链路 → 对应源码 → 源码执行逻辑 → 抽象框架 → 通用知识体系 → 回到项目分析”的路径展开。先建立整体位置，再进入 Hypertable、Chunk、Continuous Aggregate、Rollup、Compression、Retention 等内部机制。
>
> **与已有知识的关系**：
>
> - 服务端数据管理源码学习.md：Database → Connection → SQL → Schema / Drizzle → Constraint → Index。
> - 服务端数据管理源码学习-2.md：Transaction → Concurrency Control。
> - Redis体系源码学习.md：Runtime State → Cache → Session → Rate Limit → Atomicity → Reliability → Scale → Production Governance。
> - 本篇：Time-Series Data Management → TimescaleDB → 时序组织 → 时序聚合 → 历史生命周期。
>
> **分析边界**：项目事实以当前 browser-monitor/platform 源码为准。通用概念只在源码能够引出时展开，并明确区分“当前项目已经实现”“TimescaleDB 通用能力”“后续可继续深入的设计”。

## 1. TimescaleDB 是 PostgreSQL 之上的时序数据管理层，而不是项目中的另一套独立数据库

这一节先不进入：

~~~text
Hypertable
Chunk
Continuous Aggregate
Compression
Retention
~~~

因为这些都是 TimescaleDB 内部能力。

在理解内部机制之前，必须先回答一个更基础的问题：

> **当前 Browser Monitor 已经使用 PostgreSQL，为什么还需要 TimescaleDB？TimescaleDB 在整个服务端数据管理链路中到底处于什么位置？**

如果这个位置没有建立清楚，后面学习 TimescaleDB 很容易退化成：

~~~text
create_hypertable 是什么

time_bucket 怎么写

Continuous Aggregate 怎么配置

Compression Policy 有哪些参数
~~~

最终只记住零散 API，而没有建立“什么时候需要这一类数据管理能力”的系统框架。

这一节因此只做一件事：

~~~text
把 TimescaleDB 放回完整 Server Data Architecture
~~~

### 【第一层：先从项目整体数据链路定位 TimescaleDB】

#### <u>1. 项目原文已经明确给出 TimescaleDB 所处的数据处理阶段</u>

当前 platform/README.md 对完整链路的描述是：

> Monitor SDK → 公开 DSN → Ingestion API → telemetry_events + Outbox → Worker → TimescaleDB 聚合 → Analytics API → React 看板

先不看任何 TimescaleDB API，只把这条链拆成职责：

~~~text
Monitor SDK
    ↓
数据产生

Ingestion API
    ↓
数据接收

telemetry_events + Outbox
    ↓
原始事实可靠落库
+
记录后续处理任务

Worker
    ↓
异步加工
形成领域查询模型

TimescaleDB
    ↓
时序数据组织
+
时序聚合
+
历史数据生命周期

Analytics API
    ↓
查询与统计服务

React Dashboard
    ↓
展示
~~~

因此从项目原文就能先得到一个非常重要的结论：

~~~text
TimescaleDB
并不位于数据入口

TimescaleDB
也不负责前端 Session / Cache / Rate Limit

TimescaleDB
主要出现在数据已经可靠接收以后
进入长期时序分析的阶段
~~~

所以它在当前项目中的位置更接近：

~~~text
Data Ingestion
    ↓
Durable Storage
    ↓
Async Processing
    ↓
Time-Series Management
    ↓
Analytics
~~~

而不是：

~~~text
Request
    ↓
TimescaleDB
    ↓
Response
~~~

这样一条孤立链路。

#### <u>2. TimescaleDB 所处的位置说明它解决的是“长期历史数据怎样管理”</u>

把 Browser Monitor 再压缩成一条数据生命周期：

~~~text
Browser
    ↓
产生 Telemetry

API
    ↓
接收 Telemetry

PostgreSQL Transaction
    ↓
保证 Raw Event + Outbox
可靠提交

Worker
    ↓
把 Raw Event
加工成查询模型

TimescaleDB
    ↓
管理不断增长的
Time-Series Data

Analytics API
    ↓
按照时间范围
查询趋势与统计

Redis
    ↓
缓存最终 Query Result

Web
    ↓
展示
~~~

这里已经可以发现：

~~~text
PostgreSQL Transaction
解决：
这批数据是否可靠成为事实

Worker
解决：
原始数据怎样被加工

TimescaleDB
解决：
长期时序数据怎样组织和查询

Redis
解决：
运行时结果怎样快速复用
~~~

所以 TimescaleDB 的核心问题不是：

~~~text
数据能不能存进去？
~~~

因为普通 PostgreSQL 本身已经可以 INSERT。

它真正面对的是：

~~~text
数据持续产生以后
怎样长期组织？

历史越来越多以后
怎样按时间范围查询？

同一类统计不断被重复计算
怎样降低成本？

旧数据价值变化以后
怎样压缩、降采样和清理？
~~~

这才是：

~~~text
Time-Series Data Management
~~~

的真正入口。

### 【第二层：从部署源码确认 TimescaleDB 与 PostgreSQL 的真实关系】

理解项目链路以后，再进入部署代码。

这里最重要的是先纠正一个容易出现的概念错误：

~~~text
PostgreSQL
TimescaleDB
Redis

≠

三个完全独立的数据库系统
~~~

当前项目不是这样设计的。

#### <u>1. Docker Service 名叫 timescaledb，但应用连接的仍然是 PostgreSQL</u>

当前 docker-compose.yml：

~~~yaml
timescaledb:
  image: timescale/timescaledb-ha:pg17

  environment:
    POSTGRES_DB: monitor
    POSTGRES_USER: monitor
    POSTGRES_PASSWORD: ...

  ports:
    - "5432:5432"
~~~

API / Worker 使用：

~~~text
DATABASE_URL
    ↓
postgres://monitor:...@timescaledb:5432/monitor
~~~

这里可以直接看到：

~~~text
Protocol
    ↓
postgres://

Port
    ↓
5432

Database
    ↓
monitor

User
    ↓
PostgreSQL User
~~~

应用没有使用另一套：

~~~text
timescale://
~~~

协议。

因此运行关系应该理解成：

~~~text
Application
    ↓
PostgreSQL Driver
    ↓
PostgreSQL Protocol
    ↓
PostgreSQL Database Engine
    +
TimescaleDB Extension
~~~

而不是：

~~~text
Application
 ├── PostgreSQL Database
 └── TimescaleDB Database
~~~

#### <u>2. Migration 进一步证明 TimescaleDB 是 PostgreSQL 内部扩展能力</u>

当前 0001_platform.sql 一开始：

~~~sql
CREATE EXTENSION IF NOT EXISTS pgcrypto;

CREATE EXTENSION IF NOT EXISTS timescaledb;

CREATE EXTENSION IF NOT EXISTS timescaledb_toolkit;
~~~

这段代码表达的层级非常清楚：

~~~text
PostgreSQL Database
│
├── PostgreSQL Native Capability
│
├── pgcrypto Extension
│
├── timescaledb Extension
│
└── timescaledb_toolkit Extension
~~~

所以前两篇已经学过的：

~~~text
Table

SQL

Index

Constraint

Transaction

MVCC

Connection Pool
~~~

并没有因为 TimescaleDB 出现而失效。

更准确地说：

~~~text
PostgreSQL
    ↓
提供通用关系型数据管理基础

TimescaleDB
    ↓
在 PostgreSQL 之上
增加 Time-Series Capability
~~~

后面才会逐步展开：

~~~text
Hypertable

Chunk

time_bucket

Continuous Aggregate

Retention

Compression / Columnstore

Time-Series Hyperfunctions
~~~

因此需要先固定一个概念：

> **TimescaleDB 不是 PostgreSQL 的替代数据库，而是建立在 PostgreSQL 之上的时序数据管理扩展层。**

#### <u>3. PostgreSQL 与 TimescaleDB 是“基础能力 + 专用工作负载能力”的关系</u>

可以抽象成：

~~~text
PostgreSQL
│
├── General Relational Data Management
│   ├── Table
│   ├── Relation
│   ├── SQL
│   ├── Index
│   ├── Constraint
│   ├── Transaction
│   └── Concurrency Control
│
└── TimescaleDB Extension
    └── Time-Series Data Management
        ├── Time Partition
        ├── Time Range Query
        ├── Time Bucket
        ├── Incremental Aggregate
        ├── Historical Rollup
        └── Data Lifecycle
~~~

因此：

~~~text
TimescaleDB Knowledge
~~~

不是另外一套和 PostgreSQL 毫无关系的知识。

而是：

~~~text
PostgreSQL Knowledge
        ↓
遇到 Time-Series Workload
        ↓
增加专门的数据组织与分析能力
~~~

这也是本篇为什么必须建立在前两篇 PostgreSQL 学习之后。

### 【第三层：当前项目之所以需要 TimescaleDB，是因为数据 Workload 已经发生变化】

既然 PostgreSQL 本身可以建表、插入、索引和查询，那么自然要继续问：

> **为什么当前项目不能只停留在普通 PostgreSQL 数据模型？**

答案不应该简化成：

~~~text
TimescaleDB 更快
~~~

而应该先比较项目中的两类数据。

#### <u>1. 一类是关系型业务状态，核心是实体当前状态与关系</u>

当前 Migration 中：

~~~text
users

user_sessions

account_tokens

projects

project_members

ingestion_keys

allowed_origins

threshold_versions

project_invitations

outbox_tasks
~~~

这些数据主要表达：

~~~text
User 是谁

Project 是什么

谁属于哪个 Project

当前使用哪个 Threshold

Token 是否有效

Outbox Task 当前处于什么状态
~~~

典型访问方式：

~~~sql
WHERE id = ?

WHERE user_id = ?

WHERE project_id = ?

WHERE token_hash = ?

WHERE active = true
~~~

它们的核心问题更接近：

~~~text
Entity
    ↓
Relation
    ↓
Constraint
    ↓
Transaction
    ↓
Current Business State
~~~

这就是前两篇 PostgreSQL 学习主要解决的：

~~~text
Relational Business Data
~~~

#### <u>2. 另一类是持续产生的监控事实，核心是系统随时间怎样变化</u>

当前 Migration 中还有：

~~~text
telemetry_events

performance_samples

view_records

custom_event_samples

custom_signal_samples

custom_metric_samples
~~~

这些表都有非常重要的时间字段：

~~~text
occurred_at

observed_at

started_at
~~~

例如 performance_samples 形成的逻辑更像：

~~~text
10:00:01
LCP = 2100

10:00:05
LCP = 2500

10:00:10
INP = 180

10:00:16
LCP = 1900

...
~~~

系统真正关心的通常不是：

~~~text
根据 Primary Key
找某一条 Sample
~~~

而是：

~~~text
Project P001

过去 24 小时

LCP

每一分钟

count
avg
p50
p75
p95
good / poor
~~~

查询结构变成：

~~~text
Entity Scope
    +
Time Range
    +
Time Bucket
    +
Aggregation
~~~

这就是：

~~~text
Time-Series Workload
~~~

#### <u>3. Time-Series 的关键不是“表里有 timestamp”，而是时间成为第一组织维度</u>

普通业务表同样可能有：

~~~text
created_at
updated_at
~~~

但它们不一定是 Time-Series。

判断一份数据是不是典型时序工作负载，更重要的是：

~~~text
Time
    ↓
是否决定数据排序？

Time Range
    ↓
是否是主要查询条件？

New Data
    ↓
是否持续沿时间轴追加？

Analytics
    ↓
是否经常按时间 Bucket 聚合？

Lifecycle
    ↓
历史数据价值是否随时间变化？
~~~

所以可以抽象：

~~~text
Relational Entity Data
        ↓
Entity-centered

Time-Series Data
        ↓
Time-centered
~~~

这个区别非常重要。

后面所有 TimescaleDB 能力都不是凭空产生，而是从这个 Workload 差异自然推出来的。

### 【第四层：Time-Series Workload 会产生三类新的数据管理问题】

当前项目引入 TimescaleDB，不是因为普通 PostgreSQL 无法存数据，而是因为随着监控数据规模增长，会出现三类越来越突出的系统问题。

#### <u>1. 第一类问题是 Growing Dataset：持续增长的数据需要稳定的物理组织方式</u>

普通项目表可能：

~~~text
projects
    ↓
几百
几千
几万 Rows
~~~

而 Telemetry 是：

~~~text
每秒持续产生
~~~

假设：

~~~text
100 events / second
~~~

一天就是：

~~~text
8,640,000 events
~~~

如果：

~~~text
1000 events / second
~~~

一天就是：

~~~text
86,400,000 events
~~~

持续运行以后：

~~~text
Time
    ↓
Row Count
    ↓
Storage
    ↓
Index Size
    ↓
Query Cost
    ↓
Maintenance Cost
~~~

都会持续增加。

所以第一类核心问题不是“怎样让数据停止增长”，而是：

~~~text
Growing Dataset
        ↓
Physical Organization
        ↓
怎样把持续增长的数据
拆成可管理的物理范围
~~~

普通：

~~~text
一张表 + 一个 Index
~~~

并不能完整回答：

~~~text
数据持续增长以后
物理数据怎样继续组织和访问
~~~

的问题。

这里需要提前区分两个层次：

~~~text
Hypertable / Chunk
        ↓
组织增长
        ↓
把持续增长的 Time-Series Dataset
按时间范围拆成可管理的 Physical Partitions

Compression / Retention / Downsampling
        ↓
治理长期增长
        ↓
控制历史数据继续占用的存储、扫描和保留成本
~~~

因此 Hypertable 解决的是 **Growing Dataset 的 Physical Organization**，而不是让总数据量不再增长。真正的长期数据量治理还要继续进入 Historical Data Lifecycle。

#### <u>2. 第二类问题是 Analytical Query：查询通常扫描范围后再聚合</u>

普通业务查询：

~~~sql
SELECT *
FROM projects
WHERE id = $1;
~~~

而监控 Analytics 更接近：

~~~sql
SELECT
  time_bucket(
    INTERVAL '1 minute',
    observed_at
  ),
  percentile_cont(0.75)
FROM performance_samples
WHERE
  project_id = $1
  AND observed_at >= $2
  AND observed_at < $3
GROUP BY ...;
~~~

后者往往经历：

~~~text
Time Range Scan
    ↓
Filter
    ↓
Group
    ↓
Aggregate
    ↓
Percentile / Distinct
    ↓
Return Trend
~~~

同一个 Dashboard 还会不断重复类似计算。

于是第二类问题变成：

~~~text
Repeated Analytical Computation
~~~

而不只是：

~~~text
Single Row Lookup
~~~

#### <u>3. 第三类问题是 Data Lifecycle：历史数据价值随时间发生变化</u>

监控数据通常具有很明显的时间价值变化：

~~~text
刚产生
    ↓
定位问题价值最高
需要完整明细
需要高分辨率

几天以后
    ↓
仍需要分析
但单条 Event 价值下降

几个月以后
    ↓
更多关注长期趋势
而不是每一条原始记录
~~~

所以：

~~~text
所有 Raw Data
永远以相同精度保存
~~~

并不是唯一合理方案。

当前项目已经明确：

~~~text
Raw / Detail
    ↓
30 days

Aggregate
    ↓
180 days
~~~

这说明时序数据系统必须继续回答：

~~~text
什么时候保留 Raw？

什么时候聚合？

什么时候压缩？

什么时候降低时间分辨率？

什么时候删除？
~~~

第三类核心问题因此是：

~~~text
Historical Data Lifecycle
~~~

### 【第五层：TimescaleDB 的核心能力可以从三类 Workload 问题自然推出】

到这里还没有深入任何一个 API，但已经能够自然推出 TimescaleDB 为什么会出现。

~~~text
Time-Series Workload
│
├── ① Growing Dataset
│      ↓
│   Physical Organization
│      ↓
│   Time Partition
│   Hypertable
│   Chunk
│
├── ② Analytical Query
│      ↓
│   time_bucket
│   Continuous Aggregate
│   Hyperfunctions
│   Rollup
│
└── ③ Data Lifecycle
       ↓
    Compression / Columnstore
    Retention
    Downsampling
~~~

因此 TimescaleDB 不应该被记成：

~~~text
一个比 PostgreSQL 更快的数据库
~~~

而应该记成：

> **TimescaleDB 在 PostgreSQL 通用关系型能力之上，为持续增长、以时间范围查询和聚合为主要访问模式的数据增加专门的数据组织、分析和生命周期能力。**

这也是后面整个学习顺序的来源：

~~~text
为什么需要 Time-Series Management
        ↓
持续增长的数据怎样按时间组织
        ↓
Hypertable / Chunk
        ↓
组织增长，而不是停止增长

然后
        ↓
数据怎样按时间聚合
        ↓
time_bucket / Continuous Aggregate

然后
        ↓
历史数据怎样降采样和继续聚合
        ↓
Rollup / Two-step Aggregate

最后
        ↓
历史数据怎样控制长期成本
        ↓
Compression / Retention
~~~

也就是说：

~~~text
TimescaleDB API
~~~

不是学习起点。

真正的起点是：

~~~text
Time-Series Workload
~~~

### 【第六层：回到源码，当前 TimescaleDB 实际已经承担四层职责】

建立通用框架以后，再重新看当前项目源码。

当前项目不是只使用：

~~~text
create_hypertable
~~~

一个功能。

整个 Migration 已经形成四层能力。

#### <u>1. Time-Series Storage 负责组织 Raw 与 Projection Data</u>

源码：

~~~sql
SELECT create_hypertable(
  'telemetry_events',
  'occurred_at',
  if_not_exists => TRUE
);

SELECT create_hypertable(
  'performance_samples',
  'observed_at',
  if_not_exists => TRUE
);

SELECT create_hypertable(
  'view_records',
  'started_at',
  if_not_exists => TRUE
);
~~~

这层负责：

~~~text
持续增长的 Raw / Projected Data
        ↓
按照时间维度组织
~~~

这里下一节才深入：

~~~text
Hypertable
+
Chunk
+
Chunk Pruning
+
Index
~~~

#### <u>2. Time-Series Analytics 负责把时间轴转换成统计结果</u>

源码：

~~~sql
CREATE MATERIALIZED VIEW performance_rollup_1m
WITH (timescaledb.continuous) AS
SELECT
  time_bucket(
    INTERVAL '1 minute',
    observed_at
  ) AS bucket,
  ...
FROM performance_samples
GROUP BY ...;
~~~

它把：

~~~text
Raw Samples
    ↓
Continuous Timeline
~~~

转换成：

~~~text
1-minute Aggregate
~~~

后面还存在：

~~~text
1m
    ↓
1h
~~~

形成：

~~~text
Precomputation
+
Downsampling
~~~

#### <u>3. Statistical State 负责保存可继续组合的分析状态</u>

当前不仅计算：

~~~text
count
avg
min
max
~~~

还使用：

~~~sql
percentile_agg(value)
~~~

以及：

~~~sql
hyperloglog(
  8192,
  session_id
)
~~~

说明当前数据库层还承担：

~~~text
Percentile

Distinct Session

Distinct View
~~~

这类复杂统计。

后续会单独进入：

~~~text
Two-step Aggregate
~~~

解释为什么不能简单保存：

~~~text
一个 p75 number
或
一个 count distinct number
~~~

而需要保留可 Rollup 的中间状态。

#### <u>4. Historical Lifecycle 负责决定旧数据怎样继续存在</u>

当前 Migration 还存在：

~~~text
add_compression_policy

add_retention_policy
~~~

说明系统已经明确：

~~~text
Data Age
    ↓
Storage Strategy
    ↓
Resolution
    ↓
Retention
~~~

会随时间发生变化。

最终形成：

~~~text
Recent
    ↓
Raw Detail

Older
    ↓
Compressed Detail

Historical
    ↓
Aggregate

Expired
    ↓
Delete
~~~

所以当前 TimescaleDB 的真实职责已经不是：

~~~text
一个数据库插件
~~~

而是完整的：

~~~text
Time-Series Storage
+
Analytics
+
Statistical Processing
+
Historical Lifecycle
~~~

### 【第七层：TimescaleDB 与 PostgreSQL、Redis 的职责边界必须放在同一张图中】

理解 TimescaleDB 以后，需要把前面已经学过的 PostgreSQL 与 Redis 一起放回来。

~~~text
                    Server Data
                         │
       ┌─────────────────┼─────────────────┐
       │                 │                 │
       ▼                 ▼                 ▼
 Relational State   Time-Series State   Runtime State
       │                 │                 │
       ▼                 ▼                 ▼
 PostgreSQL        PostgreSQL +          Redis
                   TimescaleDB
~~~

这里严格来说：

~~~text
TimescaleDB
仍然属于 PostgreSQL 数据库体系
~~~

只是面对不同 Workload。

#### <u>1. PostgreSQL 的核心是长期关系型业务事实是否正确</u>

典型：

~~~text
users

~~~

核心关注：

~~~text

Durability

~~~

可以概括：

~~~text
Authoritative Relational State
~~~

#### <u>2. TimescaleDB 的核心是持续增长的历史事实怎样长期管理</u>

典型：

~~~text

~~~

核心关注：

~~~text

High Ingest

Time Range Query

Aggregation

Historical Lifecycle
~~~

可以概括：

~~~text
Authoritative Time-Series History
~~~

#### <u>3. Redis 的核心是运行中的共享状态怎样高频访问</u>

典型：

~~~text

Analytics Cache

Cache Version
~~~

核心关注：

~~~text

Derived State
~~~

可以概括：

~~~text
Runtime / Derived State
~~~

因此不要建立：

~~~text

~~~

这种性能排序模型。

~~~text
    ↓

    ↓

~~~

它们解决的是不同的数据管理问题。

### 【第八层：脱离当前项目，建立是否需要 Time-Series Data Management 的判断框架】

以后遇到其他系统，不应该看到：

~~~text
数据很多
~~~

就直接决定：

~~~text
使用 TimescaleDB
~~~

应该顺着数据语义和访问模式判断。

#### <u>1. 数据是否天然沿时间持续产生</u>

典型：

~~~text
Metrics

Telemetry

IoT Sensor Data

Financial Ticks

Observability Events
~~~

共同模式：

~~~text

    ↓
New Data

Time T2
    ↓
New Data

    ↓
New Data
~~~

如果数据主要不是这样产生，TimescaleDB 未必有意义。

#### <u>2. 主要查询是否围绕 Time Range</u>

例如：

~~~text

最近 24 小时

过去 7 天

过去 30 天
~~~

~~~text

~~~

那么普通 PostgreSQL 可能已经足够。

#### <u>3. 是否需要大量时间聚合</u>

例如：

~~~text

每天
~~~

并计算：

~~~text
COUNT

AVG

SUM

P75

P95

Distinct
~~~

这时 Time-Series Analytics 特征开始变强。

#### <u>4. 数据是否会长期持续增长</u>

例如：

~~~text
Today
    ↓
10M rows

Next Month
    ↓
300M rows

Next Year
    ↓
Billions of rows
~~~

如果数据规模会沿时间持续累积：

~~~text
Partition

Lifecycle
~~~

就会逐渐成为核心设计问题。

#### <u>5. 历史数据是否允许降低时间精度</u>

例如：

~~~text
最近 24h
    ↓
Raw

最近 30d
    ↓
1-minute

半年历史
    ↓
1-hour
~~~

如果答案是 Yes：

~~~text
Continuous Aggregate

Downsampling

Retention
~~~

会具有很高价值。

因此可以形成完整判断链：

~~~text
Data
 ↓
是否 Time-oriented？
 ↓ Yes
是否持续产生？
 ↓ Yes
是否主要 Time Range Query？
 ↓ Yes

 ↓ Yes

 ↓ Yes

成为候选方案
~~~

这里仍然是：

~~~text
候选方案
~~~

~~~text

~~~

最终还需要结合：

~~~text

Scale

Deployment Model
~~~

进行判断。

### 【第九层：回到 Browser Monitor，给当前 TimescaleDB 一个准确定位】

经过前面的项目源码、Workload 和通用框架，现在可以准确描述当前项目：

> **Browser Monitor 是一个以 PostgreSQL 为统一持久化基础，利用 TimescaleDB Extension 管理大量遥测时序历史，再使用 Redis 管理运行时状态和查询缓存的数据平台。**

完整数据层：

~~~text
                     Browser Monitor Data Layer

             ┌─────────────────┼──────────────────┐
             │                 │                  │
             ▼                 ▼                  ▼
     Relational Business   Time-Series Data   Runtime State
             │                 │                  │
             ▼                 ▼                  ▼

             │                 │                  │
      User / Project       Telemetry          Session
~~~

因此 TimescaleDB 在当前项目中承担：


### 【第一节最终形成 TimescaleDB 的整体位置框架】

这一节不要求记住任何具体 API。

真正需要形成的是：

~~~text
PostgreSQL
解决：

        ↓
~~~

这就是后续整个 TimescaleDB 学习的起点。

## 2. Hypertable 与 Chunk 把一张不断增长的逻辑表拆成多张真实 PostgreSQL 子表

这一节先把三个最容易混淆的问题直接回答清楚：

~~~text
问题 1：
Chunk 是逻辑概念，还是实际存储？

答案：
Chunk 是 TimescaleDB 自动创建和管理的真实 PostgreSQL 子表。
真正的数据 Row 会存入这些 Chunk。
它不是 TypeScript 代码，也不是内存里的一个对象。


问题 2：
create_hypertable 以后 performance_samples 还存在吗？

答案：
存在。

应用仍然：
INSERT INTO performance_samples
SELECT ... FROM performance_samples

performance_samples 仍然是应用看到的逻辑表。


问题 3：
performance_samples 还会不会一直变大？

答案：
逻辑上会。

例如总共有 1 亿条 performance_samples，
SELECT COUNT(*) 看到的仍然是 1 亿条。

但物理上不再是：
“一张 PostgreSQL 物理表里堆 1 亿条”。

而变成：
performance_samples
    ↓
Chunk A：一部分时间范围的数据
Chunk B：一部分时间范围的数据
Chunk C：一部分时间范围的数据
...
~~~

这就是这一节首先要建立的模型。

### 【第一层：先看普通 PostgreSQL Table 实际是什么】

先完全不考虑 TimescaleDB。

假设项目只创建：

~~~sql
CREATE TABLE performance_samples (
  project_id uuid NOT NULL,
  sample_id varchar(256) NOT NULL,
  observed_at timestamptz NOT NULL,
  name varchar(16) NOT NULL,
  value double precision NOT NULL
);
~~~

然后持续写：

~~~sql
INSERT INTO performance_samples
VALUES (...);
~~~

那么可以先简单理解为：

~~~text
performance_samples
        │
        ▼
一张 PostgreSQL Physical Table
        │
        ├── Row 1
        ├── Row 2
        ├── Row 3
        ├── ...
        └── Row 100,000,000
~~~

假设每天写 1000 万条：

~~~text
Day 1       1000 万
Day 2       2000 万
Day 3       3000 万
...
Day 100     10 亿
~~~

那么 Logical Table 和主要 Physical Data Structure 都在不断变大。

这里不是说 PostgreSQL 普通表一定不能存十亿数据，而是随着 Time-Series 数据持续增长，会越来越突出：

~~~text
大索引
大范围时间查询
历史数据删除
Vacuum / Maintenance
冷热数据管理
~~~

这些问题。

TimescaleDB 的第一步不是做聚合。

它先改变：

> **这张持续增长的 Table 在 PostgreSQL 内部怎样组织。**

### 【第二层：当前项目先创建普通 Table，再把它转换成 Hypertable】

来看当前项目真实源码。

0001_platform.sql：

~~~sql
CREATE TABLE performance_samples (
  project_id uuid NOT NULL REFERENCES projects(id) ON DELETE CASCADE,
  sample_id varchar(256) NOT NULL,
  observed_at timestamptz NOT NULL,
  last_updated_at timestamptz NOT NULL,
  name varchar(16) NOT NULL,
  value double precision NOT NULL CHECK (value >= 0),
  ...
  PRIMARY KEY (
    project_id,
    sample_id,
    observed_at
  )
);
~~~

执行到这里：

~~~text
performance_samples
        ↓
普通 PostgreSQL Table
~~~

紧接着：

~~~sql
SELECT create_hypertable(
  'performance_samples',
  'observed_at',
  if_not_exists => TRUE
);
~~~

这一步的含义不是：

~~~text
删除 performance_samples
然后创建一个 TimescaleDB 专用文件
~~~

也不是：

~~~text
复制一份 performance_samples
到另外一个数据库
~~~

而是：

~~~text
performance_samples
        ↓
仍然保留这个 Table 名称和 SQL 接口
        ↓
TimescaleDB 接管它的数据分区方式
        ↓
变成 Hypertable
~~~

可以先理解成：

~~~text
转换前

performance_samples
        ↓
普通 PostgreSQL Table


转换后

performance_samples
        ↓
TimescaleDB Hypertable
        ↓
底层自动管理多个 PostgreSQL Chunk Tables
~~~

应用程序依然：

~~~sql
INSERT INTO performance_samples ...

SELECT ...
FROM performance_samples
WHERE ...
~~~

不需要切换成另一套 SQL。

### 【第三层：Hypertable 是应用看到的一张逻辑表，Chunk 才是真正存 Row 的 PostgreSQL 子表】

这是这一节最重要的地方。

假设：

~~~sql
SELECT create_hypertable(
  'performance_samples',
  'observed_at'
);
~~~

然后数据库里已经产生一段时间的数据。

对业务代码来说仍然只有：

~~~text
performance_samples
~~~

但数据库内部可以近似理解成：

~~~text
                     performance_samples
                         Hypertable
                       应用访问入口
                            │
          ┌─────────────────┼─────────────────┐
          │                 │                 │
          ▼                 ▼                 ▼
      Chunk A           Chunk B           Chunk C
   PostgreSQL Table   PostgreSQL Table   PostgreSQL Table

   一段时间数据       一段时间数据       一段时间数据
~~~

注意：

> **Chunk 不是程序概念上的数组分片。**

它是数据库内部真实创建和管理的 PostgreSQL 子表。

内部对象通常会位于 TimescaleDB 自己的 internal schema 中，名称类似：

~~~text
_timescaledb_internal._hyper_..._chunk
~~~

所以可以非常具体地理解：

~~~text
performance_samples
        ↓
是业务 SQL 使用的统一表名

_timescaledb_internal....
        ↓
是 TimescaleDB 在 PostgreSQL 内部
创建并管理的真实 Chunk Table
~~~

#### <u>1. Hypertable 和 Chunk 到底谁存数据</u>

| 对象 | 是不是数据库对象 | 是否真正承载 Row | 谁直接使用 |
|---|---|---:|---|
| performance_samples Hypertable | 是 | 对应用表现为完整数据集 | 应用程序 |
| Chunk | 是，真实 PostgreSQL 子表 | 是，实际 Row 分布在这些 Chunk 中 | TimescaleDB 自动管理 |

所以从应用视角：

~~~sql
SELECT *
FROM performance_samples;
~~~

看到所有数据。

从底层视角：

~~~text
这些 Row
实际分布在多个 Chunk
~~~

### 【第四层：Table 的总数据量仍然一直增长，但单张物理表不再无限增长】

#### <u>1. 从业务和 SQL 视角看，Hypertable 仍然一直增长</u>

假设每天 1000 万条：

~~~text
Day 1
performance_samples
逻辑上有 1000 万

Day 2
逻辑上有 2000 万

Day 10
逻辑上有 1 亿
~~~

执行：

~~~sql
SELECT COUNT(*)
FROM performance_samples;
~~~

仍然是在查询整张 Hypertable 的全部逻辑数据。

所以：

~~~text
Logical Dataset
仍然持续增长
~~~

#### <u>2. 从物理存储视角看，不再是一个 Physical Table 无限增长</u>

为了理解，假设：

~~~text
Chunk Interval = 1 day
~~~

这只是教学示例，不代表当前项目实际配置。

那么可能形成：

~~~text
performance_samples
Logical Dataset = 5000 万 Rows

底层：

Chunk 2026-10-01
    1000 万 Rows

Chunk 2026-10-02
    1000 万 Rows

Chunk 2026-10-03
    1000 万 Rows

Chunk 2026-10-04
    1000 万 Rows

Chunk 2026-10-05
    1000 万 Rows
~~~

所以：

~~~text
总数据：
仍然越来越多

但是：

单个 Physical Chunk：
只管理自己的时间范围
~~~

因此不能说：

~~~text
Hypertable 让 Table 不增长
~~~

正确表述是：

> **Hypertable 让整个逻辑数据集继续增长，但把不断增长的数据拆给多个较小的物理 Chunk 管理。**

### 【第五层：Chunk 为什么按照 observed_at 拆分】

回到项目：

~~~sql
SELECT create_hypertable(
  'performance_samples',
  'observed_at'
);
~~~

这两个参数分别表达：

~~~text
performance_samples
        ↓
哪张 Table 要被 TimescaleDB 管理

observed_at
        ↓
根据哪个字段
决定 Row 应该进入哪个 Chunk
~~~

所以 observed_at 不只是普通查询字段。

它同时变成：

~~~text
Partitioning Column
~~~

#### <u>1. 假设一个 Chunk 覆盖一天</u>

这里只为了理解。

例如：

~~~text
Chunk A

2026-10-01 00:00
~
2026-10-02 00:00


Chunk B

2026-10-02 00:00
~
2026-10-03 00:00


Chunk C

2026-10-03 00:00
~
2026-10-04 00:00
~~~

插入：

~~~text
Sample A

observed_at =
2026-10-01 08:20
~~~

TimescaleDB 判断这个时间属于 Chunk A 的时间范围，所以 Row 实际进入 Chunk A。

再插入：

~~~text
Sample B

observed_at =
2026-10-03 15:00
~~~

它会进入 Chunk C。

应用完全不用自己判断日期并选择目标表。

### 【第六层：真实 INSERT 过程到底发生了什么】

当前 Worker 最终只需要执行类似：

~~~sql
INSERT INTO performance_samples (
  project_id,
  sample_id,
  observed_at,
  ...
)
VALUES (...);
~~~

应用只知道：

~~~text
performance_samples
~~~

TimescaleDB 内部则可以理解为：

~~~text
Node / Worker
    ↓
INSERT INTO performance_samples
    ↓
PostgreSQL 接收 SQL
    ↓
TimescaleDB 识别：
performance_samples 是 Hypertable
    ↓
读取 Row 的 observed_at
    ↓
根据 observed_at
判断目标时间范围
    ↓
找到对应 Chunk
    ↓
Row 实际写入对应 Chunk
~~~

所以真正链路：

~~~text
Application SQL
       ↓
Hypertable
       ↓
Partition Routing
       ↓
Physical Chunk
       ↓
Row Storage
~~~

如果新的时间范围还没有对应 Chunk，TimescaleDB 会按自己的分区管理机制创建或使用新的 Chunk。

所以数据增长不再简单意味着一张物理表无限扩大，而更接近：

~~~text
Time Axis
    ↓
不断产生新的 Physical Partitions
~~~

### 【第七层：Chunk 是数据库对象，不是应用程序代码】

TimescaleDB 是 PostgreSQL Extension。

Extension 运行在 PostgreSQL Server 内部。

因此：

~~~text
Node.js
NestJS
Worker
~~~

都不会创建：

~~~text
class Chunk
new Chunk(...)
~~~

关系是：

~~~text
Node.js Application
        │
        │ SQL
        ▼
PostgreSQL
        │
        ├── TimescaleDB Extension
        │
        └── PostgreSQL Storage
                 │
                 ├── Chunk Table A
                 ├── Chunk Table B
                 └── Chunk Table C
~~~

所以：

> **Chunk 是 TimescaleDB 在 PostgreSQL 内部创建、注册和管理的真实子表，而不是 TypeScript / JavaScript 代码结构。**

### 【第八层：查询 performance_samples 时为什么不用手动查询 Chunk】

假设数据库内部：

~~~text
performance_samples

    Chunk A
    Chunk B
    Chunk C
    Chunk D
    Chunk E
~~~

应用依然可以：

~~~sql
SELECT *
FROM performance_samples
WHERE
  project_id = $1
  AND observed_at >= $2
  AND observed_at < $3;
~~~

原因是：

~~~text
performance_samples
~~~

对应用仍然代表：

~~~text
完整 Hypertable
~~~

PostgreSQL Planner 与 TimescaleDB 会根据时间条件：

~~~text
observed_at >= T1
observed_at < T2
~~~

判断：

~~~text
哪些 Chunk
可能包含这个时间范围
~~~

#### <u>1. 一个具体查询例子</u>

假设底层：

~~~text
Chunk A
10 月 1 日

Chunk B
10 月 2 日

Chunk C
10 月 3 日

Chunk D
10 月 4 日

Chunk E
10 月 5 日
~~~

用户查询：

~~~sql
WHERE observed_at >= '2026-10-03 10:00'
  AND observed_at <  '2026-10-03 11:00'
~~~

数据库可以判断：

~~~text
Chunk A
10/1
    ↓
一定没有
    ↓
跳过

Chunk B
10/2
    ↓
一定没有
    ↓
跳过

Chunk C
10/3
    ↓
可能存在
    ↓
查询

Chunk D
10/4
    ↓
一定没有
    ↓
跳过

Chunk E
10/5
    ↓
一定没有
    ↓
跳过
~~~

最终：

~~~text
5 Chunks
    ↓
只访问相关 Chunk
~~~

这就是：

~~~text
Chunk Pruning
~~~

也可以理解成：

~~~text
Partition Pruning
~~~

它解决的是：

> **先排除时间上绝对不可能包含目标数据的物理分区。**

### 【第九层：Chunk Pruning 和 Index 是两个不同层级】

当前项目：

~~~sql
SELECT create_hypertable(
  'performance_samples',
  'observed_at'
);
~~~

随后还有：

~~~sql
CREATE INDEX performance_project_time_idx
ON performance_samples(
  project_id,
  observed_at DESC
);
~~~

以及：

~~~sql
CREATE INDEX performance_project_route_time_idx
ON performance_samples(
  project_id,
  route_name,
  observed_at DESC
);
~~~

如果 Chunk 已经把数据拆开，为什么还需要 Index？

因为解决的是两个不同问题。

#### <u>1. Chunk Pruning 先确定查询哪些物理分区</u>

查询：

~~~sql
WHERE
  project_id = 'P001'
  AND observed_at >= T1
  AND observed_at < T2
~~~

第一步：

~~~text
observed_at 范围
    ↓
判断 Chunk 时间范围
    ↓
确定只需要相关 Chunks
~~~

解决的是：

> **哪些物理分区需要参与查询？**

#### <u>2. Index 再在相关 Chunk 内找目标 Row</u>

假设某个 Chunk 里面仍然有：

~~~text
1000 万 Rows
~~~

其中包含：

~~~text
Project A
Project B
Project C
...
~~~

还需要找：

~~~text
project_id = P001
~~~

这时才继续依赖：

~~~text
Index
~~~

所以查询路径：

~~~text
SELECT performance_samples
        ↓
WHERE observed_at BETWEEN T1 AND T2
        ↓
Chunk Pruning
        ↓
只保留相关 Chunks
        ↓
WHERE project_id = P001
        ↓
相关 Chunk 上的 Index
        ↓
Matching Rows
~~~

这就是：

~~~text
Partition
+
Index
~~~

两级访问。

#### <u>3. 当前索引直接对应真实 Query Pattern</u>

例如：

~~~sql
CREATE INDEX performance_project_time_idx
ON performance_samples(
  project_id,
  observed_at DESC
);
~~~

对应：

~~~text
Project
    +
Time Range
~~~

而：

~~~sql
CREATE INDEX performance_project_route_time_idx
ON performance_samples(
  project_id,
  route_name,
  observed_at DESC
);
~~~

对应：

~~~text
Project
    +
Route
    +
Time Range
~~~

因此当前访问路径可以理解成：

~~~text
Time Condition
    ↓
Chunk Pruning

Project / Route Condition
    ↓
Index Scan
~~~

Hypertable 没有替代 PostgreSQL Index，而是在 Index 之前增加了一层 Time Partition Pruning。

### 【第十层：为什么分成多个 Chunk 后，Index 也更容易管理】

普通大表：

~~~text
performance_samples
1 billion Rows
        ↓
一个非常大的 Index
~~~

可能意味着：

~~~text
Index Tree 更大

Memory Working Set 更大

写入需要持续维护大型 Index
~~~

分 Chunk 后可以近似理解成：

~~~text
Chunk A
    ↓
Index A

Chunk B
    ↓
Index B

Chunk C
    ↓
Index C
~~~

最近数据主要写入：

~~~text
Newest Chunk
~~~

因此活跃写入主要维护：

~~~text
Newest Chunk 对应的索引
~~~

而不是所有历史时间范围组成的一个单一超大物理结构。

所以 Chunk 改变的不只是：

~~~text
查询时少扫描一些数据
~~~

还改变：

~~~text
数据维护单位

索引维护单位

历史生命周期管理单位
~~~

### 【第十一层：Chunk Interval 决定一个 Physical Chunk 覆盖多大的时间范围】

现在再引入：

~~~text
Chunk Interval
~~~

就比较容易理解。

假设：

~~~text
chunk_time_interval = 1 day
~~~

就是：

~~~text
一个 Chunk
负责约一天的时间范围
~~~

于是：

~~~text
Day 1
    ↓
Chunk A

Day 2
    ↓
Chunk B

Day 3
    ↓
Chunk C
~~~

#### <u>1. Chunk Interval 不是每多少 Row 建一个 Chunk</u>

不是：

~~~text
每 100 万 Rows
创建一个 Chunk
~~~

而是：

~~~text
根据 Time Range
划分 Chunk
~~~

例如同一天：

~~~text
Project A
100 Rows

Project B
1000 万 Rows
~~~

如果都属于同一时间范围，仍然进入该时间范围对应的 Chunk。

所以：

~~~text
Chunk Row Count
≈
Ingest Rate
×
Chunk Time Interval
~~~

#### <u>2. Chunk 太大会重新接近 Giant Table 问题</u>

假设：

~~~text
一个 Chunk = 90 days
~~~

而每天写入量非常大。

那么一个 Chunk 本身就可能非常大：

~~~text
Large Chunk
    ↓
Large Index
    ↓
Large Working Set
    ↓
Maintenance Cost
~~~

#### <u>3. Chunk 太小又会产生大量管理开销</u>

例如：

~~~text
一个 Chunk = 1 minute
~~~

长期运行后会产生大量 Chunk。

随之增加：

~~~text
Metadata

Planning Overhead

Index Object Count

Background Job Management
~~~

所以 Chunk Interval 是典型 Trade-off：

~~~text
Larger Chunk
    ↓
Fewer Chunks
Lower Metadata Cost
but Larger Per-chunk Working Set

Smaller Chunk
    ↓
Smaller Individual Partition
but More Chunks / Metadata
~~~

### 【第十二层：当前项目的 Chunk Interval 到底是多少】

这个地方必须区分：

~~~text
源码明确了什么
~~~

和：

~~~text
源码没有明确什么
~~~

当前项目：

~~~sql
SELECT create_hypertable(
  'performance_samples',
  'observed_at',
  if_not_exists => TRUE
);
~~~

没有显式写：

~~~text
chunk_time_interval
~~~

所以：

> **从当前仓库不能确定 performance_samples 实际每个 Chunk 是一天、七天还是其他长度。**

当前代码只明确：

~~~text
Hypertable：
performance_samples

Partition Column：
observed_at
~~~

没有明确：

~~~text
Chunk Interval
~~~

因此文档中的“一天一个 Chunk”只能作为教学示例，不能描述成当前项目事实。

如果未来进入生产容量治理，需要结合：

~~~text
Actual TimescaleDB Version

Runtime Configuration

Ingest Rate

Chunk Count

Chunk Size

Index Size
~~~

再决定是否显式配置 Chunk Interval。

### 【第十三层：当前项目为什么选择 observed_at，而不是 last_updated_at】

performance_samples 有：

~~~text
observed_at

last_updated_at
~~~

为什么：

~~~sql
create_hypertable(
  'performance_samples',
  'observed_at'
)
~~~

而不是：

~~~text
last_updated_at
~~~

因为这两个时间表达的业务语义不同。

#### <u>1. observed_at 表示指标属于哪个实际观测时间</u>

例如：

~~~text
2026-10-01 10:05

用户这次 LCP = 2300ms
~~~

Analytics 查询：

~~~text
10:00 ~ 11:00
LCP 怎么变化
~~~

自然应该按照：

~~~text
observed_at
~~~

组织。

#### <u>2. last_updated_at 表示这一 Row 最后什么时候被修订</u>

例如 Web Vital：

~~~text
第一次：
sequence = 0

第二次：
sequence = 1

第三次：
sequence = 2
~~~

last_updated_at 会不断变化。

但是：

~~~text
这次性能观测属于哪个时间段
~~~

仍然由：

~~~text
observed_at
~~~

决定。

所以：

~~~text
Partition Time
~~~

应该与：

~~~text
业务主时间轴
~~~

一致。

### 【第十四层：当前项目不同 Hypertable 使用不同业务时间轴】

源码：

~~~text
telemetry_events
    ↓
occurred_at
~~~

因为关心：

~~~text
Event 什么时候发生
~~~

performance_samples：

~~~text
observed_at
~~~

因为关心：

~~~text
Metric 什么时候被观测
~~~

view_records：

~~~text
started_at
~~~

因为关心：

~~~text
View 什么时候开始
~~~

custom_event_samples：

~~~text
occurred_at
~~~

custom_signal_samples：

~~~text
occurred_at
~~~

custom_metric_samples：

~~~text
occurred_at
~~~

因此：

> **Partition Column 不是统一找一个 created_at，而是选择真正定义业务时间轴的字段。**

### 【第十五层：Primary Key 为什么也包含时间字段】

当前：

~~~sql
PRIMARY KEY (
  project_id,
  sample_id,
  observed_at
);
~~~

而不是：

~~~sql
PRIMARY KEY (
  project_id,
  sample_id
);
~~~

telemetry_events 同样：

~~~sql
PRIMARY KEY (
  project_id,
  event_id,
  occurred_at
);
~~~

这与 Hypertable 的分区模型有关。

TimescaleDB 对 Hypertable 上的 Unique Index / Primary Key 有分区列相关约束。

#### <u>1. 为什么唯一键需要包含时间分区列</u>

假设：

~~~text
Chunk A
10/01

Chunk B
10/02
~~~

如果只声明：

~~~text
event_id UNIQUE
~~~

数据库要保证：

~~~text
Chunk A
不存在 E1

Chunk B
不存在 E1

其他所有 Chunks
也不存在 E1
~~~

这会变成跨 Partition 的全局唯一判断。

当前项目的物理唯一键：

~~~text
project_id
+
event_id
+
occurred_at
~~~

把分区时间也纳入唯一性定义。

#### <u>2. Physical Uniqueness 不一定等于 Business Uniqueness</u>

业务可能真正认为：

~~~text
同一个 Project 下
eventId 应该唯一
~~~

但物理 Primary Key 是：

~~~text
project_id
+
event_id
+
occurred_at
~~~

理论上如果 event_id 相同但 occurred_at 不同，物理键仍不同。

所以：

~~~text
Physical Constraint
~~~

和：

~~~text
Business Idempotency
~~~

不是完全相同的概念。

当前项目后续在 Ingestion 层还会通过：

~~~text
Advisory Lock

Existing Event Query

Insert
~~~

补足协议级幂等语义。

这说明：

> **Time Partition 的物理约束有时会反过来影响 Primary Key 设计，而真正的业务唯一语义可能还需要应用层额外保证。**

### 【第十六层：Hypertable 与 PostgreSQL Partitioning 的关系】

PostgreSQL 本身就支持 Partitioning。

TimescaleDB Hypertable 可以先理解成：

~~~text
PostgreSQL Partitioning 基础
        ↓
TimescaleDB
增加 Time-oriented 自动管理
~~~

如果完全手工管理，也可以设计：

~~~text
performance_2026_10_01

performance_2026_10_02

performance_2026_10_03
~~~

但应用和运维就需要自己处理更多：

~~~text
创建新 Partition

管理时间范围

写入路由

删除旧 Partition

维护分区相关策略
~~~

TimescaleDB 的价值之一就是：

~~~text
把 Time-oriented Partition Management
做成数据库 Extension 能力
~~~

因此 Hypertable 可以直观理解成：

> **TimescaleDB 自动管理的一张按时间持续分区的 PostgreSQL 表。**

### 【第十七层：把当前项目的真实物理结构重新画清楚】

当前：

~~~sql
CREATE TABLE performance_samples (...);

SELECT create_hypertable(
  'performance_samples',
  'observed_at'
);
~~~

为了说明，假设教学示例中的 Chunk Interval 为一天。

可以理解成：

~~~text
Node.js / Worker
        │
        │
        │ INSERT INTO performance_samples
        ▼
┌────────────────────────────────────┐
│          PostgreSQL Server         │
│                                    │
│  ┌──────────────────────────────┐  │
│  │    TimescaleDB Extension     │  │
│  └──────────────────────────────┘  │
│                 │                  │
│                 ▼                  │
│       performance_samples          │
│          Hypertable                │
│        统一 SQL 访问入口             │
│                 │                  │
│       根据 observed_at 路由          │
│                 │                  │
│        ┌────────┼────────┐         │
│        ▼        ▼        ▼         │
│      Chunk A  Chunk B  Chunk C     │
│        │        │        │         │
│      PG Table PG Table PG Table    │
│        │        │        │         │
│      Index A  Index B  Index C     │
│                                    │
└────────────────────────────────────┘
~~~

插入：

~~~text
observed_at =
2026-10-02 12:30
~~~

最终：

~~~text
performance_samples
        ↓
TimescaleDB Routing
        ↓
对应时间范围的 Chunk
        ↓
真实 Row 存入该 Chunk
~~~

这就是整个物理机制。

### 【第十八层：当前源码实际上连续定义了三个不同层次】

当前：

~~~sql
CREATE TABLE performance_samples (...);
~~~

第一步定义：

~~~text
Row 长什么样

字段类型

Constraint

Foreign Key

Primary Key
~~~

这是：

~~~text
Logical Data Schema
~~~

然后：

~~~sql
SELECT create_hypertable(
  'performance_samples',
  'observed_at'
);
~~~

第二步定义：

~~~text
这份数据
怎样按照时间被物理组织
~~~

这是：

~~~text
Physical Time Partition Strategy
~~~

接着：

~~~sql
CREATE INDEX performance_project_time_idx
ON performance_samples(
  project_id,
  observed_at DESC
);
~~~

第三步定义：

~~~text
进入相关 Chunk 后
怎样快速找到目标 Rows
~~~

这是：

~~~text
Query Access Path
~~~

所以当前源码真正的层次是：

~~~text
CREATE TABLE
    ↓
定义 Row / Schema

create_hypertable
    ↓
定义 Physical Time Partition Strategy

CREATE INDEX
    ↓
定义 Query Access Path
~~~

这三部分不是互相独立的 SQL，而是一条完整的数据组织链。

### 【第二节最终形成 Hypertable 与 Chunk 的直观框架】

最终只需要固定十个事实：

~~~text
1.
performance_samples
仍然是应用访问的 PostgreSQL Table 名称

2.
create_hypertable 以后
应用的 INSERT / SELECT 基本不需要改写

3.
Hypertable 是应用看到的统一逻辑数据集

4.
Chunk 是 TimescaleDB 在 PostgreSQL 内部
创建和管理的真实子表

5.
真正的数据 Row
会按照时间被写入对应 Chunk

6.
整个 Hypertable 的总数据量
仍然会不断增加

7.
变化的是：
不再由一个单一 Physical Table
承担全部历史数据

8.
查询带时间条件时
TimescaleDB 可以先排除无关 Chunk

9.
进入相关 Chunk 后
仍然依靠 PostgreSQL Index
查找 Project / Route / Sample 等 Row

10.
Chunk 还是后续
Compression / Retention / Historical Lifecycle
的重要管理单位
~~~

最终可以压缩成一句：

> **Hypertable 是应用继续访问的一张 PostgreSQL 逻辑表；Chunk 是 TimescaleDB 在 PostgreSQL 内部自动创建的真实子表，真正的数据 Row 按时间分布到这些 Chunk 中。因此总数据仍在增长，但不再由一张单一物理表无限膨胀。**

## 3. Time Range Query 将时序数据从原始 Row 转换成可分析的趋势结果

第二节解决的是：

~~~text
数据怎样存

performance_samples
    ↓
Hypertable
    ↓
Chunk
    ↓
Physical Row Storage
~~~

第三节继续解决：

> **这些已经存进 Chunk 的数据，在一次 Analytics 查询中，怎样从原始 Row 变成前端可以展示的时间趋势？**

这一节不把：

~~~text
Time Range
Chunk Pruning
Index
time_bucket
GROUP BY
Aggregate
~~~

拆成多个互相并列的大标题。

因为它们本质上属于同一条 Query Pipeline。

整个查询真正只有四个主要部分：

~~~text
Time-Series Query
│
├── 一、Data Selection
│      ↓
│   找到本次查询真正需要的 Raw Rows
│
├── 二、Analytical Aggregation
│      ↓
│   把 Raw Rows 转换成 Trend Points
│
├── 三、Query Model
│      ↓
│   Detail Query 与 Aggregate Query
│   使用不同结果模型
│
└── 四、Temporal Alignment
       ↓
    多条时序序列通过统一 Bucket
    对齐到同一时间坐标轴
~~~

先建立完整执行链：

~~~text
Analytics Request
        ↓
Project Scope
+
from / to
        ↓
Relevant Chunks
        ↓
Matching Raw Rows
        ↓
        ├──────────── Detail Query
        │                   ↓
        │              Order + Cursor
        │
        └──────────── Aggregate Query
                            ↓
                        time_bucket
                            ↓
                     Business Dimension
                            ↓
                         GROUP BY
                            ↓
                        Aggregate
                            ↓
                         Trend Point
~~~

### 【一、Data Selection 先确定本次查询真正需要哪些 Raw Rows】

这一部分还没有开始做统计。

它只解决：

> **数据库里已经积累了大量历史数据，这次请求究竟需要读取哪一部分？**

当前 AnalyticsService 把这一层统一封装在 filters() 中。

#### <u>1. 项目源码先把业务 Scope 与 Time Range 转成 SQL Predicate</u>

当前源码：

~~~ts
private filters(
  alias: string,
  timeColumn: string,
  projectId: string,
  filters: AnalyticsFilters,
): SqlFilter {
  const values: unknown[] = [
    projectId,
    filters.from,
    filters.to,
  ];

  const conditions = [
    alias + ".project_id = $1",
    alias + "." + timeColumn + " >= $2",
    alias + "." + timeColumn + " < $3",
  ];

  const add = (
    column: string,
    value: string | undefined,
  ): void => {
    if (!value) return;

    values.push(value);

    conditions.push(
      alias + "." + column + " = $" + values.length,
    );
  };

  add("environment", filters.environment);
  add("app_version", filters.version);
  add("route_name", filters.routeName);

  if (filters.metric && alias === "p") {
    add("name", filters.metric);
  }

  return {
    where: conditions.join(" AND "),
    values,
  };
}
~~~

针对 performance_samples：

~~~ts
const filter = this.filters(
  "p",
  "observed_at",
  projectId,
  filters,
);
~~~

最终会形成类似：

~~~sql
WHERE
  p.project_id = $1
  AND p.observed_at >= $2
  AND p.observed_at < $3
~~~

如果还有：

~~~text
environment
version
routeName
metric
~~~

则继续增加：

~~~sql
AND p.environment = ...
AND p.app_version = ...
AND p.route_name = ...
AND p.name = ...
~~~

这里可以把所有条件分成两类：

~~~text
Business Scope
│
├── project_id
├── environment
├── app_version
├── route_name
└── metric

Time Scope
│
├── from
└── to
~~~

所以 Data Selection 的第一步不是 time_bucket。

而是：

~~~text
All Historical Data
        ↓
Business Scope
+
Time Scope
        ↓
Candidate Raw Data
~~~

#### <u>2. Time Range 不只是业务过滤条件，也直接对应 Hypertable 的物理分区边界</u>

假设：

~~~text
from = 2026-10-03 10:00

to   = 2026-10-03 11:00
~~~

SQL：

~~~sql
p.observed_at >= '2026-10-03 10:00'
AND
p.observed_at < '2026-10-03 11:00'
~~~

业务上表示：

~~~text
用户只想看
10:00 ~ 11:00
这一个小时的数据
~~~

但第二节已经知道：

~~~text
performance_samples
按照 observed_at
被划分到不同 Chunks
~~~

所以这个条件同时能够帮助数据库判断：

~~~text
哪些 Chunk 的时间范围
与 10:00 ~ 11:00
完全不相交
~~~

这些 Chunk 就没有必要参与本次查询。

例如教学示例中：

~~~text
Chunk A
10/01

Chunk B
10/02

Chunk C
10/03

Chunk D
10/04
~~~

查询：

~~~text
10/03 10:00
~
10/03 11:00
~~~

可以先得到：

~~~text
Chunk A
    ↓
时间不重叠
    ↓
排除

Chunk B
    ↓
时间不重叠
    ↓
排除

Chunk C
    ↓
存在重叠
    ↓
参与查询

Chunk D
    ↓
时间不重叠
    ↓
排除
~~~

这就是：

~~~text
Chunk Pruning
~~~

所以这里真正的关系是：

~~~text
WHERE observed_at >= from
AND   observed_at < to
        │
        ├── 业务意义：
        │   选择用户想看的时间范围
        │
        └── 物理意义：
            排除无关 Chunk
~~~

#### <u>3. Chunk Pruning 只缩小 Physical Partition 范围，还没有找到最终 Rows</u>

假设最终只剩：

~~~text
Chunk C
~~~

但 Chunk C 里可能仍然有：

~~~text
Project A
Project B
Project C

LCP
INP
CLS

/checkout
/home
/search

数百万甚至更多 Rows
~~~

所以：

~~~text
Relevant Chunk
≠
Final Result
~~~

Chunk Pruning 只解决：

~~~text
从哪些物理子表读取？
~~~

还需要继续解决：

~~~text
这些子表里面
哪些 Row 真正满足条件？
~~~

#### <u>4. Index 与其他 Predicate 再在相关 Chunk 中寻找真正匹配的 Row</u>

当前项目已经建立：

~~~sql
CREATE INDEX performance_project_time_idx
ON performance_samples(
  project_id,
  observed_at DESC
);
~~~

以及：

~~~sql
CREATE INDEX performance_project_route_time_idx
ON performance_samples(
  project_id,
  route_name,
  observed_at DESC
);
~~~

所以：

~~~sql
WHERE
  project_id = 'P001'
  AND route_name = '/checkout'
  AND observed_at >= T1
  AND observed_at < T2
~~~

可以形成：

~~~text
Hypertable
    ↓
Time Range
    ↓
Relevant Chunks
    ↓
Project / Route / Time Predicate
    ↓
Index / Scan
    ↓
Matching Raw Rows
~~~

这里要保留一个 PostgreSQL 基础边界：

> **存在 Index 不代表 PostgreSQL 每次一定执行 Index Scan。**

真实 Physical Plan 仍由 PostgreSQL Planner 根据：

~~~text
数据统计

Predicate Selectivity

Chunk Size

查询范围

Index Cost

Sequential Scan Cost

Parallelism
~~~

决定。

因此当前索引的准确含义是：

~~~text
项目为
Project + Time

以及
Project + Route + Time

提供了合适的 Index Access Path
~~~

而不是：

~~~text
所有查询一定使用这个 Index
~~~

#### <u>5. Data Selection 最终只应该理解成一条连续链</u>

所以前面的 Scope、Time Range、Chunk Pruning、Index 不应该各自被提升成平级知识模块。

它们共同完成一件事情：

~~~text
Data Selection

All Historical Data
        ↓
Project / Dimension Scope
        ↓
Time Range
        ↓
Chunk Pruning
        ↓
Index / Predicate
        ↓
Matching Raw Rows
~~~

到这里为止，数据库已经找到本次查询真正需要的原始数据。

但还没有：

~~~text
一分钟一个点

平均值

p75

趋势图
~~~

这些属于下一阶段。

### 【二、Analytical Aggregation 再把 Raw Rows 转换成 Trend Points】

假设 Data Selection 最终得到：

| observed_at | name | value |
|---|---|---:|
| 10:00:05 | LCP | 2100 |
| 10:00:18 | LCP | 2500 |
| 10:00:45 | INP | 180 |
| 10:01:03 | LCP | 1900 |
| 10:01:25 | LCP | 2300 |
| 10:01:40 | INP | 120 |
| 10:02:08 | LCP | 3000 |

这些仍然是一条一条 Raw Sample。

前端趋势图需要的却是：

~~~text
10:00
LCP p75 = ...

10:01
LCP p75 = ...

10:02
LCP p75 = ...
~~~

所以接下来需要：

~~~text
Analytical Aggregation
~~~

这一部分也只是一条连续链：

~~~text
Matching Raw Rows
        ↓
time_bucket
        ↓
Business Dimension
        ↓
GROUP BY
        ↓
Aggregate
        ↓
Trend Point
~~~

#### <u>1. time_bucket 只负责把 timestamp 映射到统计时间窗口</u>

当前 performance()：

~~~sql
SELECT
  time_bucket(
    INTERVAL '1 minute',
    observed_at
  ) AS bucket,
  name,
  ...
~~~

对于每一条 Row：

~~~text
10:00:05
    ↓
10:00:00

10:00:18
    ↓
10:00:00

10:00:45
    ↓
10:00:00

10:01:03
    ↓
10:01:00

10:01:59
    ↓
10:01:00
~~~

所以 time_bucket 可以先理解成：

~~~text
Timestamp
    ↓
Bucket Function
    ↓
Bucket Start Time
~~~

例如：

~~~text
time_bucket(
  1 minute,
  10:00:37
)

=
10:00:00
~~~

它不会：

~~~text
创建 Chunk

创建 Table

移动 Row

改变 observed_at

重新分区
~~~

它只是查询中的时间分组函数。

#### <u>2. Chunk 与 time_bucket 都使用时间，但属于完全不同层次</u>

第二节的 Chunk：

~~~text
Chunk
    ↓
Physical Storage Partition
~~~

这一节的 time_bucket：

~~~text
time_bucket
    ↓
Analytical Time Group
~~~

可以直接比较：

| 维度 | Chunk | time_bucket |
|---|---|---|
| 所属阶段 | 数据存储 | 查询分析 |
| 是不是实际表 | 是 | 不是 |
| 是否真正保存 Row | 是 | 否 |
| 什么时候产生作用 | INSERT / Storage Management | SELECT / Aggregation |
| 核心输入 | Partition Time + Chunk Interval | Timestamp + Bucket Interval |
| 解决的问题 | Row 物理存在哪里 | Row 属于哪个统计时间组 |

因此：

~~~text
Chunk
=
物理时间分区

time_bucket
=
统计时间分组
~~~

二者不能混为一谈。

#### <u>3. Chunk Interval 与 time_bucket Interval 可以完全不同</u>

为了理解，假设：

~~~text
Chunk Interval = 1 day
~~~

表示：

~~~text
物理上
一天的数据
可能存放在同一个 Chunk
~~~

但查询仍然可以：

~~~sql
time_bucket(
  INTERVAL '1 minute',
  observed_at
)
~~~

那么：

~~~text
一个 1-day Chunk
内部可以产生
1440 个 1-minute Analytical Buckets
~~~

反过来：

~~~text
Chunk Interval = 1 hour
~~~

查询也可以：

~~~sql
time_bucket(
  INTERVAL '1 day',
  observed_at
)
~~~

这时一个 1-day Analytical Bucket 可以覆盖多个 1-hour Physical Chunks。

所以：

~~~text
Physical Partition Granularity
和
Analytical Granularity
~~~

是两个独立设计参数。

#### <u>4. time_bucket 只是给每一条 Row 计算 bucket，真正形成统计组还需要 GROUP BY</u>

执行：

~~~sql
time_bucket(
  INTERVAL '1 minute',
  observed_at
) AS bucket
~~~

以后，数据可以理解成：

| observed_at | bucket | name | value |
|---|---|---|---:|
| 10:00:05 | 10:00:00 | LCP | 2100 |
| 10:00:18 | 10:00:00 | LCP | 2500 |
| 10:00:45 | 10:00:00 | INP | 180 |
| 10:01:03 | 10:01:00 | LCP | 1900 |
| 10:01:25 | 10:01:00 | LCP | 2300 |

此时 Row 仍然没有合并，只是多了 bucket 这个计算结果。

源码继续：

~~~sql
GROUP BY
  bucket,
  name
~~~

才把：

~~~text
相同 Bucket
+
相同 Metric Name
~~~

归为同一个 Statistical Group。

#### <u>5. Business Dimension 决定一个时间 Bucket 内还要按什么继续拆组</u>

为什么不能只：

~~~sql
GROUP BY bucket
~~~

因为同一分钟可能同时存在：

~~~text
10:00

LCP
LCP
LCP

INP
INP

CLS
CLS
~~~

如果只按 bucket，会把：

~~~text
LCP + INP + CLS
~~~

混在同一个统计组。

所以真正的 Group Key 是：

~~~text
Time Dimension
+
Business Dimension
~~~

当前就是：

~~~text
bucket
+
name
~~~

即：

~~~text
10:00 + LCP

10:00 + INP

10:00 + CLS

10:01 + LCP
...
~~~

可以抽象：

~~~text
Aggregate Group
=
Time Bucket
×
Business Dimensions
~~~

未来如果继续加入 environment、route、browser、region 等 Dimension，本质是在扩展 Group Cardinality，而不是改变 time_bucket 的作用。

#### <u>6. Aggregate 才真正把多条 Raw Rows 压缩成一个统计结果</u>

当前源码：

~~~sql
count(*)::bigint
  AS count,

count(DISTINCT session_id)::bigint
  AS session_count,

count(DISTINCT view_id)::bigint
  AS view_count,

avg(value)
  AS average,

percentile_cont(0.50)
  WITHIN GROUP (ORDER BY value)
  AS p50,

percentile_cont(0.75)
  WITHIN GROUP (ORDER BY value)
  AS p75,

percentile_cont(0.90)
  WITHIN GROUP (ORDER BY value)
  AS p90,

percentile_cont(0.95)
  WITHIN GROUP (ORDER BY value)
  AS p95
~~~

还会继续统计：

~~~sql
count(*) FILTER (
  WHERE server_rating = 'good'
)
  AS good_count,

count(*) FILTER (
  WHERE server_rating = 'needs-improvement'
)
  AS needs_improvement_count,

count(*) FILTER (
  WHERE server_rating = 'poor'
)
  AS poor_count
~~~

例如 10:00 的 LCP：

~~~text
1900
2100
2300
2500
~~~

最终得到：

~~~text
bucket = 10:00

name = LCP

count = 4

average = 2200

p50 = ...

p75 = ...

p90 = ...

p95 = ...
~~~

于是：

~~~text
Many Raw Rows
        ↓
Aggregate
        ↓
One Trend Point
~~~

这才是前端图表真正消费的数据。

### 【三、Query Model 决定读取 Raw Detail 还是 Aggregate Trend】

到这里需要再抽象一层。

Time-Series Query 并不等于：

~~~text
所有查询都必须 time_bucket
~~~

当前项目实际上同时存在两种完全不同的查询模型：

~~~text
Time-Series Query
│
├── Detail Query
│      ↓
│   保留每一条原始事实
│
└── Aggregate Query
       ↓
    把大量 Raw Rows
    压缩成 Trend Points
~~~

它们前半段都可能经历：

~~~text
Business Scope
    ↓
Time Range
    ↓
Chunk Pruning
    ↓
Row Filtering
~~~

真正不同的是：

~~~text
Matching Rows
之后怎样返回结果
~~~

#### <u>1. Detail Query 保留原始 Row，不进入 time_bucket</u>

当前 rawEvents()：

~~~ts
async rawEvents(
  userId: string,
  projectId: string,
  filters: AnalyticsFilters,
  cursor: string | undefined,
  limit: number,
  ...
) {
  await this.projects.requireAccess(
    userId,
    projectId,
  );

  const filter = this.filters(
    "e",
    "occurred_at",
    projectId,
    filters,
  );

  ...
}
~~~

这里同样使用：

~~~text
project_id

occurred_at >= from

occurred_at < to
~~~

所以同样首先经历：

~~~text
Scope
    ↓
Time Range
    ↓
Relevant Chunks
    ↓
Matching telemetry_events Rows
~~~

但是后面没有：

~~~text
time_bucket

GROUP BY

Aggregate
~~~

而是继续：

~~~sql
ORDER BY
  occurred_at DESC,
  event_id DESC
~~~

并使用 Cursor Pagination。

当前 Cursor 条件：

~~~sql
(
  e.occurred_at,
  e.event_id
)
<
(
  cursorOccurredAt,
  cursorEventId
)
~~~

完整链路：

~~~text
Detail Query
    ↓
Business Scope
    ↓
Time Range
    ↓
Chunk Pruning
    ↓
Matching Rows
    ↓
Time Order
    ↓
Cursor Pagination
    ↓
Raw Events
~~~

它的目标是：

> **保留每一条事实，让用户能够看到具体发生了什么。**

这种查询需要的是：

~~~text
Detail
+
Order
+
Pagination
~~~

而不是：

~~~text
一分钟一个统计值
~~~

#### <u>2. Aggregate Query 不关心每一条 Row，而关心一段时间整体表现</u>

当前 performance()：

~~~text
performance_samples
    ↓
Scope / Time Range
    ↓
Matching Rows
    ↓
time_bucket
    ↓
GROUP BY
    ↓
Aggregate
    ↓
Trend Points
~~~

它最终不会返回：

~~~text
10:00:05 LCP = 2100

10:00:18 LCP = 2500

10:00:35 LCP = 1900
~~~

而是返回：

~~~text
10:00
LCP
count = ...
average = ...
p75 = ...
p95 = ...
~~~

因此它的目标是：

> **回答这一段时间整体表现如何变化，而不是逐条展示所有事实。**

#### <u>3. 两种 Query Model 的差异本质上是结果表示方式不同</u>

| 查询模型 | Detail Query | Aggregate Query |
|---|---|---|
| 目标 | 查看具体事实 | 查看趋势 |
| Time Range | 有 | 有 |
| Chunk Pruning | 有 | 有 |
| Row Predicate | 有 | 有 |
| time_bucket | 无 | 有 |
| GROUP BY | 无 | 有 |
| Aggregate Function | 无 | 有 |
| 排序 | 通常按时间 | 通常按 Bucket |
| 分页 | 常见 Cursor | 通常直接返回 Trend Points |
| 返回粒度 | 一条 Row | 一个统计组 |

所以更准确的流程是：

~~~text
先选择数据
    ↓
再根据业务问题
选择结果模型
~~~

即：

~~~text
Matching Rows
        ↓
        ├── Detail
        │     ↓
        │  Order / Cursor
        │
        └── Aggregate
              ↓
           Bucket / Group / Aggregate
~~~

#### <u>4. Query Model 应由产品问题决定，而不是由数据库类型决定</u>

例如：

~~~text
过去 10 分钟发生了哪些错误？
    ↓
Detail Query
~~~

而：

~~~text
过去 24 小时每分钟错误率是多少？
    ↓
Aggregate Query
~~~

所以不是：

~~~text
用了 TimescaleDB
    ↓
所有查询都应该 time_bucket
~~~

而是：

~~~text
Product Question
    ↓
Result Model
    ↓
Query Model
~~~

这是能够脱离当前项目复用的判断方式。

### 【四、Temporal Alignment 用统一 Bucket 把多条时序序列放到同一时间坐标轴】

当前 performance() 还有一个比单表聚合更进一步的设计：

它不是只查询：

~~~text
performance_samples
~~~

而是同时查询：

~~~text
performance_samples
+
view_records
~~~

并把两条时序序列放到同一个分钟时间轴上。

当前 SQL：

~~~sql
WITH metric_points AS (
  ...
),
view_points AS (
  ...
)

SELECT
  m.*,
  COALESCE(
    v.page_views,
    0
  ) AS page_views

FROM metric_points m

LEFT JOIN view_points v
USING (bucket)

ORDER BY
  m.bucket,
  m.name
~~~

这一部分需要先分别看两条序列，再看它们怎样通过 bucket 对齐。

#### <u>1. Performance Series 先形成自己的分钟时间点</u>

当前：

~~~sql
SELECT
  time_bucket(
    INTERVAL '1 minute',
    observed_at
  ) AS bucket,
  name,
  ...
FROM performance_samples p
WHERE ...
GROUP BY
  bucket,
  name
~~~

结果可以理解成：

| bucket | name | count | p75 |
|---|---|---:|---:|
| 10:00 | LCP | 20 | 2300 |
| 10:00 | INP | 15 | 180 |
| 10:01 | LCP | 22 | 2400 |
| 10:01 | INP | 18 | 170 |

形成：

~~~text
Performance Series
        ↓
10:00
10:01
10:02
...
~~~

#### <u>2. View Series 也被映射到同样的一分钟时间轴</u>

当前：

~~~sql
SELECT
  time_bucket(
    INTERVAL '1 minute',
    started_at
  ) AS bucket,

  count(*)::bigint
    AS page_views

FROM view_records v

WHERE ...

GROUP BY bucket
~~~

结果：

| bucket | page_views |
|---|---:|
| 10:00 | 100 |
| 10:01 | 120 |
| 10:02 | 95 |

形成：

~~~text
View Series
        ↓
10:00
10:01
10:02
...
~~~

虽然两个表原始时间字段不同：

~~~text
performance_samples
    ↓
observed_at

view_records
    ↓
started_at
~~~

但经过：

~~~text
同一个 1 minute time_bucket
~~~

以后，都映射成：

~~~text
bucket
~~~

这个共同时间键。

#### <u>3. USING(bucket) 实际上是在做时间对齐</u>

当前：

~~~sql
LEFT JOIN view_points v
USING (bucket)
~~~

不是普通业务主键 Join。

它不是：

~~~text
performance_id
=
view_id
~~~

而是：

~~~text
两条不同 Time Series
在同一个时间窗口里
分别发生了什么
~~~

例如：

~~~text
10:00

Performance:
LCP Samples = 20

View:
Page Views = 100
~~~

通过：

~~~text
bucket = 10:00
~~~

对齐成：

~~~text
10:00
│
├── LCP Samples = 20
└── Page Views   = 100
~~~

因此 bucket 在这里除了作为：

~~~text
统计时间分组
~~~

还承担：

~~~text
Temporal Join Key
~~~

#### <u>4. Temporal Alignment 让跨序列指标成为可能</u>

当前最终返回：

~~~ts
sampleCoverage:
  Number(row.page_views) > 0
    ? Number(row.view_count)
      / Number(row.page_views)
    : 0
~~~

这个指标依赖：

~~~text
Performance View Count
        ↓
同一分钟

Page View Count
        ↓
同一分钟
~~~

如果两条序列没有统一时间粒度：

~~~text
Performance
10:00:05
10:00:18
10:00:43

View
10:00:02
10:00:37
10:00:58
~~~

就无法直接形成：

~~~text
10:00
统一统计结果
~~~

time_bucket 先把两边都映射到：

~~~text
10:00
~~~

于是才能进行：

~~~text
Temporal Alignment
        ↓
Cross-series Metric
~~~

#### <u>5. 这种模式可以抽象成通用 Multi-Series Analytics</u>

脱离当前项目：

~~~text
Series A
    ↓
自己的 Timestamp
    ↓
Common Bucket
        ┐
        │
        ├── Temporal Join
        │
Series B│
    ↓   │
自己的 Timestamp
    ↓   │
Common Bucket
        ┘
        ↓
Composite Metric
~~~

常见场景：

~~~text
Requests
+
Errors
    ↓
Error Rate

Orders
+
Users
    ↓
Orders per User

CPU
+
Traffic
    ↓
Resource per Request

Performance Samples
+
Page Views
    ↓
Sample Coverage
~~~

所以 time_bucket 不仅可以用于：

~~~text
Single-Series Aggregation
~~~

还可以作为：

~~~text
Cross-Series Temporal Alignment
~~~

的共同时间坐标。

### 【五、第三节收束：时序查询先选数据，再决定结果模型】

这一节真正只有四个主要分支：

~~~text
Time-Series Query
│
├── 一、Data Selection
│   │
│   ├── Business Scope
│   ├── Time Range
│   ├── Chunk Pruning
│   └── Index / Predicate
│
├── 二、Analytical Aggregation
│   │
│   ├── time_bucket
│   ├── Business Dimension
│   ├── GROUP BY
│   └── Aggregate
│
├── 三、Query Model
│   │
│   ├── Detail Query
│   │     └── Order + Cursor
│   │
│   └── Aggregate Query
│         └── Bucket + Group + Aggregate
│
└── 四、Temporal Alignment
    │
    ├── Series A → Common Bucket
    ├── Series B → Common Bucket
    └── Join by Bucket → Composite Metric
~~~

#### <u>1. Data Selection 只解决本次请求需要读取哪些 Raw Rows</u>

~~~text
All Historical Data
        ↓
Business Scope
        ↓
Time Range
        ↓
Chunk Pruning
        ↓
Index / Predicate
        ↓
Matching Raw Rows
~~~

核心问题：

> **这次请求到底需要读取哪些原始数据？**

#### <u>2. Analytical Aggregation 解决 Raw Rows 怎样变成趋势</u>

~~~text
Matching Raw Rows
        ↓
time_bucket
        ↓
Business Dimension
        ↓
GROUP BY
        ↓
Aggregate
        ↓
Trend Point
~~~

核心问题：

> **这些 Raw Rows 怎样被压缩成时间趋势？**

#### <u>3. Query Model 决定返回具体事实还是统计趋势</u>

~~~text
Matching Rows
        ↓
        ├── Detail
        │     ↓
        │  Raw Facts
        │
        └── Aggregate
              ↓
           Trend Points
~~~

核心问题：

> **产品真正需要的是具体事实，还是整体趋势？**

#### <u>4. Temporal Alignment 解决多个时序数据源怎样关联</u>

~~~text
Series A
    ↓
Bucket
        ┐
        ├── Join
        │
Series B│
    ↓   │
Bucket  ┘
        ↓
Composite Metric
~~~

核心问题：

> **不同来源的数据怎样被放到同一个时间坐标轴上做关联计算？**

#### <u>第三节最重要的三个概念边界</u>

第一：

~~~text
Chunk
=
物理存储分区

time_bucket
=
查询统计分组
~~~

第二：

~~~text
Time Range
=
本次请求读取哪一段历史数据

time_bucket
=
读出来以后怎样按时间重新组织
~~~

第三：

~~~text
Detail Query
=
保留 Raw Facts

Aggregate Query
=
压缩为 Trend Points
~~~

因此可以把整个第三节压缩成：

> **时序查询首先通过业务 Scope 与 Time Range 缩小需要读取的物理数据范围，再根据产品问题选择 Detail 或 Aggregate 结果模型；Aggregate Query 使用 time_bucket、Business Dimension、GROUP BY 和统计函数把 Raw Rows 转换成 Trend Points，而多个不同时间序列还可以通过统一 Bucket 对齐后形成跨序列指标。**

## 4. 下一节进入 Continuous Aggregate 与预计算

到这里已经知道，当前近期查询每次都会：

~~~text
Request
    ↓
Time Range
    ↓
Raw Rows
    ↓
time_bucket
    ↓
GROUP BY
    ↓
重新计算：

count

avg

distinct

p50

p75

p90

p95
~~~

新的问题自然出现：

> **如果同一个 Dashboard 查询被大量重复请求，为什么每一次都要重新扫描 Raw Rows、重新分桶、重新聚合？**

这就进入下一层：

~~~text
Query-time Aggregation
        ↓
Repeated Computation
        ↓
Precomputation
        ↓
Continuous Aggregate
~~~

下一节继续按照：

~~~text
当前 performance_rollup_1m 源码
        ↓
CREATE MATERIALIZED VIEW
        ↓
timescaledb.continuous
        ↓
为什么需要预计算
        ↓
Continuous Aggregate
与普通 View / Materialized View 的区别
        ↓
Refresh Policy
        ↓
回到当前 Browser Monitor
~~~

逐层展开。
