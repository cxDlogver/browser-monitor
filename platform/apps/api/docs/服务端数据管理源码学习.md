# 服务端数据管理源码学习

> **学习目标**：从数据库零基础开始，在已经建立的 NestJS + Fastify API 框架认知上，继续向下理解服务端的数据管理体系。本文不会先背数据库 API，而是先回答“数据为什么需要独立保存、数据库是什么、PostgreSQL 在系统中处于什么位置、表如何组织数据”等基础问题，再逐步进入数据库连接、SQL、关系模型、事务、并发控制、Redis、TimescaleDB 和数据可靠性。
>
> **分析范围**：通用数据库知识以 PostgreSQL 官方文档为主要参考；项目部分以当前 `browser-monitor/platform` 源码为事实基准。第一部分只建立数据库最基础的概念，不提前深入事务、索引、锁、MVCC、WAL 等内部机制。
>
> **与已有文档的关系**：[`NestJS-Fastify-API源码学习.md`](./NestJS-Fastify-API源码学习.md) 已经解释请求如何经过 Fastify、NestJS、Controller 和 Service。本文从它停下来的 `Database / Redis` 继续向下展开。

## 1. 数据库基础建立从数据持久化到关系型数据组织的整体认知

### 【数据管理从“程序中的数据为什么会消失”开始】

#### <u>1. 程序能够暂时保存数据，但程序本身不是长期数据存储</u>

先从最简单的 Node.js 程序开始：

```ts
const users = [];

users.push({
  id: 1,
  name: 'Tom',
});
```

此时程序里确实已经存在数据：

```text
Node.js Process（Node.js 进程）
        │
        │ 内存
        ▼
users

[
  { id: 1, name: "Tom" }
]
```

这里首先要区分两个概念：

```text
Program（程序）
    负责执行代码

Data（数据）
    表示程序需要记录的事实
```

例如：

```text
Tom 注册了账号
Project A 被创建
/home 页面产生了一次 LCP
```

这些都是系统需要记录的事实。

但是上面的 `users` 数组只存在于当前 Node.js 进程使用的内存中。程序运行时可以访问它；程序退出以后，这部分内存不再属于这个进程，数组中的内容也不会自动成为可以长期恢复的数据。

可以先把过程理解成：

```text
程序启动
   ↓
创建 users 数组
   ↓
用户注册
   ↓
users 中出现数据
   ↓
程序退出
   ↓
当前进程中的内存状态消失
```

对于临时计算结果，这没有问题。

例如：

```ts
const total = price * count;
```

`total` 只需要服务当前计算。

但下面这些数据不能随着程序退出而消失：

```text
用户账号
项目配置
订单
权限关系
监控事件
性能数据
后台任务
```

因此服务端需要把“程序执行”与“数据长期保存”拆成两套能力：

```text
Application（应用程序）
        ↓
处理请求和业务逻辑

Persistent Storage（持久化存储）
        ↓
长期保存业务事实
```

这里的 **Persistent（持久化）**，可以先简单理解为：

> 数据不会因为当前应用进程结束就一起消失。

这也是数据库进入服务端体系的第一个原因。

---

#### <u>2. 长期保存数据并不意味着所有场景都必须使用数据库</u>

如果只是希望程序重启以后数据仍然存在，也可以把数据写入文件：

```ts
fs.writeFileSync(
  'users.json',
  JSON.stringify(users),
);
```

这样：

```text
Node.js 进程退出
        ↓
users 内存消失

但是

users.json
        ↓
仍然存在于磁盘
```

因此不能把数据库简单定义成：

> “数据库就是为了让数据不丢。”

文件同样可以长期保存数据。

真正的区别在于，当系统逐渐变复杂以后，我们不只是需要“把数据写下来”，还需要系统化地管理这些数据。

例如一个服务端可能逐渐出现：

```text
100 万用户
500 万订单
几千万条监控事件
```

同时多个请求都在访问这些数据：

```text
Request A
    ↓
查询用户

Request B
    ↓
创建订单

Request C
    ↓
修改项目

Request D
    ↓
查询最近 7 天性能数据
```

如果都由业务代码直接维护几个 JSON 文件，程序就必须自己处理很多问题：

```text
数据应该如何分类？

如何快速找到一条数据？

如何修改其中一部分？

两个请求同时修改怎么办？

哪些字段必须存在？

哪些数据不能重复？

两个数据之间有什么关系？

一次操作只完成了一半怎么办？

数据量很大以后怎么查询？
```

因此服务端最终需要的不是一个单纯的文件，而是一套完整的数据管理能力：

```text
保存
 ↓
组织
 ↓
查询
 ↓
修改
 ↓
约束
 ↓
并发处理
 ↓
故障恢复
```

数据库体系正是围绕这些问题建立起来的。

---

### 【Database 和 DBMS 描述的是不同层次】

#### <u>1. Database 表示被组织起来的数据</u>

**Database（数据库）** 可以先理解为：

> 一组按照一定结构组织并长期保存的数据。

例如 Browser Monitor 需要保存：

```text
User
Project
Telemetry Event
Performance Sample
Outbox Task
```

这些数据不能只存在于当前 API 进程中，而需要进入独立的数据存储体系。

从最粗粒度看：

```text
Application
    ↓
Database
```

应用负责业务处理，数据库负责保存业务事实。

但到这里还有一个问题：

> 谁负责真正创建、读取、修改和管理这些数据？

这就需要继续区分第二个概念。

---

#### <u>2. DBMS 是负责管理数据库的软件</u>

**DBMS（Database Management System，数据库管理系统）** 是专门负责管理数据库的软件。

常见 DBMS 包括：

```text
PostgreSQL
MySQL
SQLite
```

它们不是某一张表，也不是某一条数据，而是一整套数据管理软件。

因此更完整的层次是：

```text
Application
    ↓
DBMS
    ↓
Database
    ↓
Data
```

DBMS 帮助应用完成：

```text
创建数据库
创建表
写入数据
查询数据
修改数据
删除数据
限制非法数据
处理多个客户端同时访问
管理事务
管理索引
备份和恢复
```

所以在后续学习中要始终区分：

```text
Database
    数据本身的逻辑集合

DBMS
    管理数据库的软件

PostgreSQL
    一种 DBMS
```

日常开发中人们经常会口语化地说“连接 PostgreSQL 数据库”，这种说法没有问题，但建立知识体系时需要知道其中包含了不同层次。

---

### 【PostgreSQL 在当前服务端中是独立的数据服务】

#### <u>1. API 不直接操作数据库文件</u>

Browser Monitor 当前使用 PostgreSQL / TimescaleDB 作为主要持久化数据系统。

从运行关系看，可以先建立：

```text
Browser
   │
   │ HTTP
   ▼
Browser Monitor API
   │
   │ Database Request
   ▼
PostgreSQL Server
   │
   ▼
Database
```

PostgreSQL 官方把它描述为 **Client / Server Model（客户端 / 服务器模型）**：PostgreSQL Server 负责管理数据库文件、接受客户端连接，并代表客户端执行数据库操作；Web Server 也可以作为 PostgreSQL Client。[1]

因此：

```text
Browser
   ↓
API Server
```

在这段通信中：

```text
Browser = Client
API     = Server
```

但是：

```text
API
 ↓
PostgreSQL
```

在这段通信中：

```text
API        = Client
PostgreSQL = Server
```

这说明 **Client（客户端）和 Server（服务器）描述的是一段通信关系中的角色，而不是某个程序永久固定的身份。**

这一点后面理解 Database Connection（数据库连接）时非常重要。

---

#### <u>2. 当前项目通过统一连接地址找到 PostgreSQL</u>

项目的基础设施配置中存在：

```text
DATABASE_URL
```

API 的 `InfrastructureModule` 使用它创建数据库能力：

```ts
{
  provide: DATABASE,
  inject: [API_CONFIG],
  useFactory: (config: ApiConfig): DatabaseHandle =>
    createDatabase(config.DATABASE_URL),
}
```

源码位置：

```text
browser-monitor/platform/apps/api/src/infrastructure/infrastructure.module.ts
```

这里暂时只需要理解：

```text
DATABASE_URL
      ↓
告诉应用 PostgreSQL 在哪里以及如何连接
      ↓
createDatabase(...)
      ↓
建立应用的数据访问能力
```

`createDatabase()` 内部的 Connection（连接）、Pool（连接池）、Driver（驱动）会在下一部分单独展开。

第一部分只需要明确：**NestJS 并不负责保存数据，NestJS 只是把数据库能力装配到应用中；真正负责数据管理的是后面的 PostgreSQL 数据体系。**

---

### 【关系型数据库首先使用 Table、Row 和 Column 组织数据】

#### <u>1. 大量数据必须先形成稳定结构</u>

假设数据库里只是保存：

```text
Tom
Jerry
2300
/home
project-a
2026-09-30
```

虽然数据都存在，但程序无法知道：

```text
Tom 是用户还是项目？

2300 是时间还是性能值？

/home 属于哪个项目？

2026-09-30 对应哪条数据？
```

因此数据不仅需要被保存，还需要被组织。

PostgreSQL 属于 **Relational Database（关系型数据库）**。在这一阶段，可以先从最基础的 Table（表）开始理解。

PostgreSQL 官方文档说明，一张表由 Row（行）和 Column（列）组成，每一列有名字和数据类型。[2]

例如：

```text
users
```

可以表示为：

| id | name | email |
| --- | --- | --- |
| 1 | Tom | tom@example.com |
| 2 | Jerry | jerry@example.com |

这里有三个基础概念。

**Table（表）**

表示同一类数据的集合。

例如：

```text
users
projects
telemetry_events
```

分别保存不同类型的数据。

**Row（行）**

表示一条具体数据。

例如：

```text
1 | Tom | tom@example.com
```

可以表示一个具体用户。

**Column（列）**

表示这一类数据具有哪些属性。

例如 User 可能包含：

```text
id
name
email
```

所以当前阶段可以先形成：

```text
Database
   ↓
Table
   ↓
Row
   ↓
Column
```

但要注意，这只是为了建立入门层次的简化图。

PostgreSQL 实际还有：

```text
PostgreSQL Server
        ↓
Database
        ↓
Schema
        ↓
Table
```

这里的 **Schema（模式 / 数据库对象命名空间）** 与项目里的 `schema.ts` 不是完全相同的概念。PostgreSQL Schema 会在后续“数据库对象组织”部分单独解释，现在不提前展开。

---

### 【Browser Monitor 的 schema.ts 把项目中的数据结构声明出来】

#### <u>1. 项目把数据库模型放在独立 database package 中</u>

当前项目的数据定义主要位于：

```text
browser-monitor/platform/packages/database/src/schema.ts
```

其中可以看到：

```ts
export const users = pgTable(...)
export const projects = pgTable(...)
export const projectMembers = pgTable(...)
export const telemetryEvents = pgTable(...)
export const outboxTasks = pgTable(...)
export const performanceSamples = pgTable(...)
export const viewRecords = pgTable(...)
```

这里的 `pgTable(...)` 来自 Drizzle。

这一阶段暂时不要把注意力放到 Drizzle API，而只把这些代码翻译成数据设计：

```text
users
    保存用户

projects
    保存监控项目

project_members
    保存用户和项目之间的成员关系

telemetry_events
    保存浏览器上传的原始监控事件

outbox_tasks
    保存等待 Worker 处理的后台任务

performance_samples
    保存处理后的性能样本

view_records
    保存页面访问记录
```

因此 `schema.ts` 最重要的价值不是“用了一个 ORM”，而是：

> 项目把系统需要长期保存的事实明确拆成了不同的数据模型。

---

#### <u>2. telemetry_events 展示了一个事件如何从对象变成结构化数据</u>

例如：

```ts
export const telemetryEvents = pgTable(
  'telemetry_events',
  {
    projectId: ...,
    eventId: ...,
    occurredAt: ...,
    receivedAt: ...,
    type: ...,
    name: ...,
    environment: ...,
    appVersion: ...,
    sessionId: ...,
    viewId: ...,
    routeName: ...,
    event: ...,
  },
);
```

把代码翻译成普通语言就是：

```text
创建一张 telemetry_events 表

每一条监控事件都要记录：

属于哪个项目
事件自己的 ID
什么时候发生
服务器什么时候收到
事件属于什么类型
事件叫什么
运行环境是什么
应用版本是什么
属于哪个 Session
属于哪个 View
发生在哪个页面
完整事件数据是什么
```

于是 SDK 上报：

```text
Project A
/home
LCP
2300ms
production
v2.3.0
```

进入数据库以后，不再只是一个临时 JavaScript 对象，而会成为可以长期查询的一条结构化记录。

整个变化可以理解成：

```text
Browser Runtime Event
        ↓
Telemetry JSON
        ↓
Ingestion API
        ↓
telemetry_events Table
        ↓
长期保存的一条 Row
```

这就是从“程序运行时数据”进入“数据库事实”的第一条完整链路。

### 【关系型数据库还需要描述不同数据之间的联系】

#### <u>1. 系统中的数据不是互相独立的几个文件</u>

当前项目存在：

```text
users
projects
project_members
telemetry_events
```

这些表并不是四组互不相关的数据。

例如：

```text
User
  ↓
加入
  ↓
Project
```

项目使用：

```text
project_members
```

记录这层联系。

其数据中包含：

```text
projectId
userId
role
```

可以表达：

```text
User A
   │
   │ owner
   ▼
Project A
```

同样：

```text
Telemetry Event
      │
      │ projectId
      ▼
   Project
```

表示某一条监控事件属于哪个项目。

因此关系型数据库的学习不能停留在：

```text
一张表
另一张表
再一张表
```

真正的系统会逐渐形成：

```text
User
  │
  ▼
Project Member
  │
  ▼
Project
  │
  ├─────────────┐
  ▼             ▼
Telemetry     Threshold
Event         Config
  │
  ▼
Outbox Task
```

后续学习 Primary Key（主键）和 Foreign Key（外键）时，就会正式解释数据库如何保证这些关系。

现在只需要建立：

> **关系型数据库不仅负责保存不同类型的数据，还需要描述和约束这些数据之间的联系。**

### 【当前项目的数据管理已经包含多种不同性质的数据】

从 `schema.ts` 可以继续发现，Browser Monitor 保存的并不是单一类型的数据。

可以先粗略分为三组。

#### <u>1. 业务管理数据描述平台本身的业务事实</u>

例如：

```text
users
projects
project_members
ingestion_keys
allowed_origins
threshold_versions
```

这些数据回答：

```text
有哪些用户？

有哪些项目？

用户属于哪些项目？

项目使用什么写入 Key？

允许哪些 Origin？

当前采用哪套指标阈值？
```

它们更接近普通业务系统常见的数据。

#### <u>2. 监控数据描述浏览器真实发生过的事件</u>

例如：

```text
telemetry_events
performance_samples
view_records
custom_signal_samples
custom_metric_samples
```

这些数据回答：

```text
什么时候发生了什么事件？

某个页面的 LCP 是多少？

某个 View 持续多久？

某个 Trace / Span 发生在哪里？

某个自定义指标值是多少？
```

这类数据通常会不断增长，并且天然带有时间属性。

这也是项目后续引入 TimescaleDB（时序数据库扩展能力）的原因之一。

#### <u>3. 任务数据描述还有哪些后台工作需要完成</u>

例如：

```text
outbox_tasks
dead_letter_tasks
```

它们回答：

```text
哪些事件还没有处理？

哪些任务正在处理？

哪些任务失败了？

哪些任务已经多次重试仍然失败？
```

所以数据库不是简单的“业务资料仓库”。

在当前项目里，它同时承担：

```text
业务状态
+
监控事实
+
后台任务状态
```

三类责任。

这也为后面的 Transaction（事务）和 Outbox（事务型任务表）埋下了伏笔：某些业务事实和任务状态不能各写各的，而需要保证它们一起成功或一起失败。

这一点会在事务章节正式展开。

### 【数据库在已有 NestJS 服务端框架中的位置进一步明确】

前面的 NestJS 文档已经建立：

```text
Browser
 ↓
Fastify
 ↓
NestJS
 ↓
Controller
 ↓
Service
 ↓
Database / Redis
```

学习完这一部分后，最后一层已经可以继续展开：

```text
Browser
   ↓
HTTP
   ↓
Fastify
   ↓
NestJS
   ↓
Controller
   ↓
Service
   ↓
Database Client
   ↓
PostgreSQL Server
   ↓
Database
   ↓
Table
   ↓
Row
```

以监控事件为例：

```text
Monitor SDK
   ↓
POST /api/v3/ingest/:publicKey/envelopes
   ↓
IngestionController
   ↓
IngestionService
   ↓
Database Access
   ↓

   ↓

   ↓

```

这时候可以更准确地理解“Service 访问数据库”这句话。

它不是：

```text
Service
  ↓
直接操作硬盘文件
```

而是：

```text
Service
  ↓
数据库客户端能力
  ↓
PostgreSQL Server
  ↓
由 PostgreSQL 管理实际数据
```

数据库因此位于业务逻辑之后，但又不是业务代码的一部分。

### 【第一部分先建立清晰边界，不提前进入数据库内部实现】

这一阶段最重要的是把容易混淆的名词放回正确层次。

| 概念 | 当前阶段的理解 |
| --- | --- |
| Data（数据） | 系统希望记录的事实 |
| Memory（内存） | 当前进程运行期间使用的临时空间 |
| Persistent Storage（持久化存储） | 程序退出后仍能保存数据的存储 |
| Database（数据库） | 被组织并长期保存的数据集合 |
| DBMS（数据库管理系统） | 负责管理数据库的软件 |
| PostgreSQL | 当前项目使用的关系型 DBMS |
| Table（表） | 同一类数据的集合 |
| Row（行） | 一条具体数据 |
| Column（列） | 这类数据包含哪些属性 |
| Relational Database（关系型数据库） | 用关系模型组织数据，并描述不同数据之间联系的一类数据库 |

这一部分暂时不需要深入：

```text
SQL 如何执行
Connection 如何建立
Connection Pool 如何复用连接
Primary Key 如何实现
Index 为什么能加速查询
Transaction 如何保证一致性
MVCC 如何控制并发
WAL 如何保证恢复
```

它们都有明确的位置，但需要按依赖顺序继续学习，而不是一次性堆在一起。

### 【第一部分最终收敛为一条数据持久化链路】

第一阶段只需要稳定建立下面这条链：

```text
现实中的业务事实
例如：
用户注册
项目创建
浏览器产生 LCP

        ↓

Application
应用程序负责处理业务

        ↓

Database Management System
数据库管理系统

当前项目：PostgreSQL

        ↓

Database
组织和长期保存数据

        ↓

Table
按数据类型组织

        ↓

Row
一条具体数据

        ↓

Column
描述数据具有哪些属性
```

放回 Browser Monitor：

```text
浏览器产生 LCP
       ↓
Monitor SDK
       ↓
Ingestion API
       ↓
IngestionService
       ↓
PostgreSQL
       ↓
telemetry_events
       ↓
形成长期保存的监控事实
```

这条链建立以后，下一部分再继续回答一个新的问题：

> 应用代码和 PostgreSQL 是两个独立运行的程序，它们到底怎样建立通信？

因此下一知识点进入：

```text
Database Connection（数据库连接）
        ↓
Database Driver（数据库驱动）
        ↓
Connection Pool（数据库连接池）
```

并直接从当前项目的：

```text
packages/database/src/client.ts
```

开始分析。


## 2. 数据库连接把应用程序与 PostgreSQL 连接成可复用的数据访问链路

第一部分已经建立了 Database（数据库）、DBMS（数据库管理系统）、PostgreSQL、Table（表）、Row（行）和 Column（列）之间的关系。接下来需要继续解决一个更具体的问题：

> Node.js API 和 PostgreSQL 是两个独立运行的程序，业务代码到底怎样把 SQL 发送给 PostgreSQL，并在大量请求同时到来时控制数据库连接？

当前项目把这一层集中在：

```text
browser-monitor/platform/packages/database/src/client.ts
```

核心源码如下：

```ts
import { drizzle, type NodePgDatabase } from 'drizzle-orm/node-postgres';
import { Pool } from 'pg';

import * as schema from './schema.js';

export interface DatabaseHandle {
  pool: Pool;
  db: NodePgDatabase<typeof schema>;
  close(): Promise<void>;
}

export function createDatabase(connectionString: string): DatabaseHandle {
  const pool = new Pool({
    connectionString,
    max: 20,
    idleTimeoutMillis: 30_000,
    connectionTimeoutMillis: 5_000,
  });

  const db = drizzle(pool, { schema });

  return {
    pool,
    db,
    close: () => pool.end(),
  };
}
```

这段代码背后的完整结构可以先概括为：

```text
Application
    ↓
Database Driver（数据库驱动）
    ↓
Connection Pool（数据库连接池）
    ↓
Connection（数据库连接）
    ↓
PostgreSQL Server
```

后面的所有数据库读写，都是建立在这条链路上。

### 【Database Connection 是应用和 PostgreSQL 之间的一条通信通道】

#### <u>1. Node.js 和 PostgreSQL 是两个独立运行的程序</u>

当前项目中的 API 运行在 Node.js 进程中，而 PostgreSQL 是独立运行的数据库服务。

```text
Node.js Process
Browser Monitor API

        ↕

PostgreSQL Process
Database Server
```

它们甚至可以运行在不同机器：

```text
Server A
Node.js API
    │
    │ TCP/IP Network
    ▼
Server B
PostgreSQL
```

PostgreSQL 官方将这一结构定义为 **Client / Server Model（客户端 / 服务器模型）**：PostgreSQL Server 管理数据库文件、接受客户端连接并执行数据库操作；Web Server 也可以作为 PostgreSQL Client。[[7]](https://www.postgresql.org/docs/18/tutorial-arch.html)

因此：

```text
Browser
   ↓
API
```

这段关系中：

```text
Browser = Client
API     = Server
```

但：

```text
API
 ↓
PostgreSQL
```

这段关系中：

```text
API        = Client
PostgreSQL = Server
```

Client（客户端）和 Server（服务器）描述的是一次通信中的角色，而不是某个程序永远固定的身份。

为了让 Node.js Client 与 PostgreSQL Server 通信，双方首先需要建立 **Database Connection（数据库连接）**。

可以先把 Connection 理解为：

> Node.js 应用与 PostgreSQL 之间已经建立好的一条通信通道。

业务代码并不是直接读取 PostgreSQL 的数据库文件，而是：

```text
Service
   ↓
发送数据库请求
   ↓
Connection
   ↓
PostgreSQL
   ↓
执行数据库操作
   ↓
Connection
   ↓
返回结果
```

---

#### <u>2. Connection 和一次 Query 是两个不同概念</u>

建立一条 Connection 之后，可以通过它连续执行多条数据库命令：

```text
Connection A
   │
   ├── SELECT ...
   ├── INSERT ...
   ├── UPDATE ...
   └── SELECT ...
```

所以：

```text
Connection
    一条持续存在的通信通道

Query
    通过这条连接发送的一次数据库操作
```

二者不能混为一谈：

```text
Connection ≠ Query
```

同一条 Connection 可以先后承载多次 Query，这正是后面“连接复用”的基础。

---

#### <u>3. PostgreSQL Connection 本身也会占用服务端资源</u>

数据库连接不是没有成本的。

PostgreSQL 官方说明，PostgreSQL 可以同时处理多个客户端连接，并为客户端连接建立对应的服务端处理进程。[[7]](https://www.postgresql.org/docs/18/tutorial-arch.html)

可以简单理解成：

```text
Node.js
   │
   ├── Connection 1 ── PostgreSQL Backend 1
   ├── Connection 2 ── PostgreSQL Backend 2
   └── Connection 3 ── PostgreSQL Backend 3
```

因此：

```text
连接数量增加
      ↓
PostgreSQL 需要维护的连接资源增加
```

这解释了为什么服务端不能简单采用：

```text
每来一个 HTTP Request
        ↓
重新建立一个数据库连接
        ↓
执行完成立即断开
```

如果并发请求快速增长，数据库连接数量也可能快速增长。数据库连接因此是一种需要限制数量、重复使用并正确释放的基础设施资源。

### 【Connection String 描述应用需要连接哪个 PostgreSQL 数据库】

#### <u>1. connectionString 集中描述数据库连接信息</u>

当前项目：

```ts
export function createDatabase(
  connectionString: string,
): DatabaseHandle
```

API 创建数据库能力时传入：

```ts
createDatabase(config.DATABASE_URL)
```

因此链路是：

```text
DATABASE_URL
      ↓
connectionString
      ↓
new Pool(...)
      ↓
PostgreSQL
```

典型 PostgreSQL Connection String（数据库连接字符串）可以写成：

```text
postgresql://monitor_user:password@postgres:5432/browser_monitor
```

可以拆成：

| 部分 | 含义 |
| --- | --- |
| `postgresql://` | 使用 PostgreSQL |
| `monitor_user` | User（数据库用户） |
| `password` | Password（数据库密码） |
| `postgres` | Host（数据库服务器地址） |
| `5432` | Port（端口） |
| `browser_monitor` | Database Name（数据库名称） |

所以连接字符串本质上回答：

> 应用应该连接哪里、使用什么身份、进入哪个数据库。

---

#### <u>2. DATABASE_URL 属于运行配置而不是固定业务逻辑</u>

项目没有把生产数据库地址直接写死在业务代码里，而是：

```ts
createDatabase(config.DATABASE_URL)
```

因此可以做到：

```text
开发环境
    ↓
DATABASE_URL = 开发数据库

测试环境
    ↓
DATABASE_URL = 测试数据库

生产环境
    ↓
DATABASE_URL = 生产数据库
```

但代码始终保持：

```ts
createDatabase(config.DATABASE_URL)
```

这里体现了一个基础服务端边界：

> 应用代码负责定义“怎样使用数据库”，运行环境负责提供“具体连接哪个数据库”。

由于连接字符串中通常包含账号、密码等敏感信息，完整的 `DATABASE_URL` 也不应该被直接写入 Git 仓库或随意打印到日志。

### 【Database Driver 让 Node.js 能够使用 PostgreSQL】

#### <u>1. Database Driver 负责应用与数据库之间的底层通信</u>

JavaScript 业务代码本身不会自动理解 PostgreSQL 的通信方式。

因此应用通常需要引入：

**Database Driver（数据库驱动）**

可以先理解为：

> 应用程序中负责建立数据库连接、发送数据库命令并接收数据库返回结果的程序库。

结构变成：

```text
业务代码
   ↓
Database Driver
   ↓
PostgreSQL Protocol
   ↓
PostgreSQL Server
```

业务代码只需要调用驱动提供的 JavaScript API，不需要自己实现 PostgreSQL 网络协议。

---

#### <u>2. 当前项目使用 pg 作为 Node.js 的 PostgreSQL Driver</u>

项目代码：

```ts
import { Pool } from 'pg';
```

这里的 `pg` 来自 **node-postgres**，承担 Node.js 与 PostgreSQL 之间的客户端通信能力。

例如项目中存在：

```ts
await this.database.pool.query(
  'SELECT 1',
);
```

从业务代码看只是一次函数调用，但完整过程可以理解成：

```text
JavaScript
   ↓
pg
   ↓
取得一个 PostgreSQL Client
   ↓
通过 Connection 发送 SQL
   ↓
PostgreSQL 执行
   ↓
返回结果
   ↓
pg 转换成 JavaScript 可使用的结果对象
```

因此：

```text
pg
≠ PostgreSQL
≠ Database
```

`pg` 是 Node.js 侧使用 PostgreSQL 的数据库驱动。

### 【Connection Pool 通过复用和限制 Connection 控制数据库访问】

#### <u>1. 每次请求重新建立连接会产生重复开销和连接压力</u>

如果没有连接池，每次数据库访问都重新创建 Connection：

```text
Request 1 → 建立连接 → SQL → 断开连接
Request 2 → 建立连接 → SQL → 断开连接
Request 3 → 建立连接 → SQL → 断开连接
```

应用会不断重复：

```text
创建网络连接
      ↓
完成数据库认证
      ↓
PostgreSQL 建立连接处理资源
      ↓
执行 SQL
      ↓
关闭连接
```

而高并发场景下，还可能在短时间内创建大量连接。

因此服务端通常引入：

**Connection Pool（数据库连接池）**

它的主要目标不是改变 SQL 的执行速度，而是：

```text
统一创建连接
+
重复使用连接
+
限制连接数量
+
管理连接生命周期
```

---

#### <u>2. Connection Pool 可以理解成统一管理的一组可复用连接</u>

连接池可以建立成：

```text
                 Connection Pool
              ┌──────────────────┐
Request A ───→│ Connection 1     │
Request B ───→│ Connection 2     │──→ PostgreSQL
Request C ───→│ Connection 3     │
Request D ───→│ ...              │
              └──────────────────┘
```

某个请求执行完成以后：

```text
Connection
    ↓
不立即销毁
    ↓
重新回到 Pool
    ↓
等待后续请求继续使用
```

所以连接生命周期从：

```text
Request
   ↓
创建 Connection
   ↓
执行 SQL
   ↓
销毁 Connection
```

变成：

```text
Application 启动
      ↓
Pool 存在
      ↓
按需建立 Connection
      ↓
Request 借用
      ↓
使用完成
      ↓
归还 Pool
      ↓
其他 Request 再次使用
      ↓
Application 关闭
      ↓
Pool 统一关闭
```

核心思想就是：

> **Connection Reuse（连接复用）。**

---

#### <u>3. 当前项目通过 pg.Pool 建立进程级连接池</u>

项目：

```ts
const pool = new Pool({
  connectionString,
  max: 20,
  idleTimeoutMillis: 30_000,
  connectionTimeoutMillis: 5_000,
});
```

node-postgres 官方说明，新建的 Pool 初始是空的，Client 会在实际需要时按需创建，而不是创建 Pool 时一次性建立到 `max` 数量。[[8]](https://node-postgres.com/apis/pool)

因此：

```text
new Pool()

并不等于

立即创建 20 条 Connection
```

更接近：

```text
new Pool()
   ↓
Pool 初始为空
   ↓
第一次数据库请求
   ↓
创建 Connection 1
   ↓
并发增加
   ↓
继续按需创建 Connection
   ↓
最多受 max 控制
```

这也是理解 `max: 20` 的前提。

### 【连接池参数定义了数据库连接的数量和等待边界】

#### <u>1. max: 20 表示当前 Pool 最多包含 20 个 Client</u>

项目：

```ts
max: 20
```

node-postgres 将 `max` 定义为 Pool 最多包含的 Client 数量。[[8]](https://node-postgres.com/apis/pool)

所以：

```text
max = 20
```

不是：

```text
服务最多处理 20 个 HTTP Request
```

而是：

```text
这个 Pool
同时最多管理 20 个数据库 Client
```

HTTP 请求并不会从进入 Controller 开始就一直占用数据库连接。请求可能还在执行参数校验、业务计算、Redis 操作等逻辑。

因此：

```text
HTTP 并发数
≠
数据库连接数
```

---

#### <u>2. Pool 已满时新的连接请求需要等待已有 Client 被归还</u>

假设：

```text
max = 20
```

并且当前：

```text
Connection 1  → 正在使用
Connection 2  → 正在使用
...
Connection 20 → 正在使用
```

第 21 个需要 Client 的任务到来时，Pool 不会继续无限创建 Connection，而会等待已有 Client 被释放。

node-postgres 官方说明：如果 Pool 已满并且所有 Client 都被借出，新的 `pool.connect()` 请求会进入等待队列，直到某个 Client 被释放。[[8]](https://node-postgres.com/apis/pool)

因此连接池除了复用连接，还承担：

> 在应用并发与数据库连接容量之间建立限制。

---

#### <u>3. idleTimeoutMillis: 30_000 负责清理长期空闲连接</u>

项目：

```ts
idleTimeoutMillis: 30_000
```

表示 Client 被归还到 Pool 后，如果长期处于空闲状态，可以在约 30 秒后被断开并从 Pool 中移除。[[8]](https://node-postgres.com/apis/pool)

可以理解成：

```text
高峰流量
   ↓
Pool 按需创建较多 Connection
   ↓
流量下降
   ↓
部分 Connection 长时间空闲
   ↓
超过 idleTimeoutMillis
   ↓
关闭空闲 Connection
```

这样可以避免高峰期创建的连接在低流量阶段长期占用数据库资源。

---

#### <u>4. connectionTimeoutMillis: 5_000 给建立新连接设置等待上限</u>

项目：

```ts
connectionTimeoutMillis: 5_000
```

node-postgres 将它定义为建立新 Client 时等待连接成功的超时时间。[[8]](https://node-postgres.com/apis/pool)

可以理解成：

```text
尝试连接 PostgreSQL
        ↓
数据库不可达 / 网络异常
        ↓
持续等待
        ↓
达到约 5 秒
        ↓
连接失败
```

这里体现一个很通用的服务端原则：

> 对外部资源的等待必须存在明确边界，避免请求无限挂起。

数据库、Redis、HTTP 下游服务都会遇到类似问题。

### 【pool.query 和 pool.connect 对应不同的连接使用方式】

#### <u>1. pool.query 适合一次独立 SQL，Pool 自动负责借用和归还 Client</u>

当前项目的健康检查：

```ts
await Promise.all([
  this.database.pool.query('SELECT 1'),
  this.redis.ping(),
]);
```

源码位置：

```text
browser-monitor/platform/apps/api/src/health/health.controller.ts
```

这里使用：

```ts
pool.query(...)
```

node-postgres 官方说明，`pool.query()` 会使用当前第一个可用的空闲 Client 执行 Query，并在内部自动完成 Client 的获取和释放。[[8]](https://node-postgres.com/apis/pool)

因此调用方可以简单理解成：

```text
pool.query(SQL)
      ↓
Pool 找到 / 创建可用 Client
      ↓
执行 SQL
      ↓
返回结果
      ↓
Client 自动回到 Pool
```

这种方式非常适合：

```text
一次独立 SELECT
一次独立 INSERT
一次独立 UPDATE
一次独立 DELETE
```

当前项目的 Analytics、Auth、Projects、Health 等模块中大量使用了：

```ts
this.database.pool.query(...)
```

---

#### <u>2. pool.connect 会显式从 Pool 借出一个 Client</u>

项目中的另一种形式：

```ts
const client =
  await this.database.pool.connect();
```

这里意味着：

```text
Connection Pool
      ↓
取出一个 Client
      ↓
交给当前代码持续使用
```

之后：

```ts
await client.query(...);
await client.query(...);
await client.query(...);
```

这些操作都明确通过同一个 Client 执行。

使用完成以后必须：

```ts
client.release();
```

也就是：

```text
Pool
 ↓
借出 Client
 ↓
业务代码使用
 ↓
client.release()
 ↓
归还 Pool
```

node-postgres 官方明确要求，通过 `pool.connect()` 获取的 Client 使用完成后必须执行 `release()`；否则可用 Client 会逐渐耗尽，后续连接请求可能一直等待或超时。[[8]](https://node-postgres.com/apis/pool)

这类问题通常称为：

**Connection Leak（连接泄漏）**

也就是：

> 程序取得数据库 Client 后没有正确归还，导致连接池中的可用连接越来越少。

---

#### <u>3. Transaction 必须固定在同一个 Client 上执行</u>

当前 `IngestionService` 已经出现：

```ts
const client =
  await this.database.pool.connect();

try {
  await client.query('BEGIN');

  await client.query(...);
  await client.query(...);

  await client.query('COMMIT');
} catch (error) {
  await client.query('ROLLBACK');
  throw error;
} finally {
  client.release();
}
```

这一节暂时不展开 Transaction（事务）的完整原理，只先解释为什么这里必须使用 `pool.connect()`。

如果写成：

```ts
await pool.query('BEGIN');
await pool.query(...);
await pool.query(...);
await pool.query('COMMIT');
```

Pool 可能把不同 Query 分配给不同 Client：

```text
BEGIN
  ↓
Connection A

SQL 1
  ↓
Connection B

SQL 2
  ↓
Connection C
```

但 PostgreSQL Transaction 是绑定到同一个数据库 Client / Session 上的。

node-postgres 官方明确要求：一个 Transaction 中的所有语句必须使用同一个 Client，并明确说明不能使用 `pool.query()` 组织事务。[[9]](https://node-postgres.com/features/transactions)

因此目前可以先建立一个非常重要的判断：

```text
一次独立 SQL
    ↓
pool.query()

需要固定在同一 Connection 上的一组 SQL
例如 Transaction
    ↓
pool.connect()
    ↓
client.query(...)
    ↓
client.release()
```

后续进入事务章节时，会继续解释为什么 `BEGIN / COMMIT / ROLLBACK` 必须形成这一结构。

### 【Drizzle 位于 pg 之上并提供更高层的数据访问能力】

#### <u>1. Drizzle 和 pg 不是同一层能力</u>

项目代码：

```ts
import { drizzle } from 'drizzle-orm/node-postgres';
import { Pool } from 'pg';

const pool = new Pool(...);
const db = drizzle(pool, { schema });
```

这里又引入：

**ORM（Object Relational Mapping，对象关系映射）**

当前项目使用：

```text
Drizzle ORM
```

Drizzle 的 PostgreSQL 接入可以建立在 node-postgres 之上。官方 PostgreSQL 接入文档也将 `pg` 作为 Node.js 驱动。[[10]](https://orm.drizzle.team/docs/get-started-postgresql)

因此完整结构可以画成：

```text
                  Application
                       │
              ┌────────┴────────┐
              │                 │
           Raw SQL          Drizzle ORM
              │                 │
              └────────┬────────┘
                       ▼
                      pg
                       ↓
                Connection Pool
                       ↓
                  PostgreSQL
```

三层不要混淆：

```text
PostgreSQL
    真正管理数据库

pg
    Node.js 与 PostgreSQL 通信

Drizzle
    建立在数据库驱动之上的更高层数据访问能力
```

---

#### <u>2. 当前项目同时保留 pool 和 db 两种数据库访问入口</u>

当前项目统一定义：

```ts
export interface DatabaseHandle {
  pool: Pool;
  db: NodePgDatabase<typeof schema>;
  close(): Promise<void>;
}
```

可以理解成：

```text
DatabaseHandle
    │
    ├── pool
    │     ↓
    │   pg / Raw SQL
    │
    ├── db
    │     ↓
    │   Drizzle
    │
    └── close()
          ↓
        关闭连接池
```

对当前 `main` 分支进行源码搜索，可以找到大量：

```ts
this.database.pool.query(...)
```

以及：

```ts
this.database.pool.connect()
```

例如：

```text
AnalyticsService
AuthService
ProjectsService
IngestionService
HealthController
OutboxWorker
```

而当前默认分支中没有搜索到业务层直接调用：

```ts
this.database.db...
```

因此依据当前源码，可以得到一个有限结论：

> 当前项目虽然创建了 Drizzle Database 实例并使用 Drizzle Schema 描述数据模型，但现有业务查询大量直接通过 `pg.Pool` 和 Raw SQL（原生 SQL）完成。

这只描述当前版本的实现状态，并不表示项目以后不能使用 Drizzle Query API。

### 【DatabaseHandle 和 NestJS Provider 让同一进程共享一套数据库基础设施】

#### <u>1. 每个 Service 自己 new Pool 会导致连接池重复创建</u>

如果每个业务模块都自己：

```ts
new Pool(...)
```

可能形成：

```text
AuthService
   ↓
Pool A

ProjectsService
   ↓
Pool B

AnalyticsService
   ↓
Pool C

IngestionService
   ↓
Pool D
```

假设每个 Pool 都配置：

```text
max = 20
```

那么一个 API 进程理论上就可能出现：

```text
4 × 20 = 80
```

个 Client 上限。

所以数据库连接池通常不是业务 Service 自己创建的临时对象，而应该成为进程级共享基础设施。

---

#### <u>2. 当前 API 通过 NestJS Provider 共享 DatabaseHandle</u>

项目：

```ts
{
  provide: DATABASE,
  inject: [API_CONFIG],
  useFactory: (config: ApiConfig): DatabaseHandle =>
    createDatabase(config.DATABASE_URL),
}
```

然后业务模块通过：

```ts
constructor(
  @Inject(DATABASE)
  private readonly database: DatabaseHandle,
) {}
```

使用同一个数据库能力。

结构变成：

```text
             InfrastructureModule
                     │
                     ▼
               DatabaseHandle
                     │
        ┌────────────┼────────────┐
        ▼            ▼            ▼
   AuthService  ProjectsService AnalyticsService
```

NestJS 默认 Provider Scope（Provider 作用域）是 Singleton（单例），也就是一个 Provider 实例在应用生命周期内被多个依赖方共享。NestJS 官方也把数据库 Connection Pool 作为适合共享的典型资源。[[11]](https://docs.nestjs.com/fundamentals/injection-scopes)

因此当前 API 不是：

```text
Request A → new Pool()
Request B → new Pool()
Request C → new Pool()
```

而是：

```text
API Process
      │
      ▼
一个 DatabaseHandle
      │
      ▼
一个 Pool
      │
      ├── Request A
      ├── Request B
      └── Request C
```

### 【连接池是进程级资源而不是整个系统唯一的一套连接】

#### <u>1. API、Worker 和 Audit Worker 会分别创建自己的 Pool</u>

当前系统除了：

```text
apps/api
```

还有：

```text
apps/worker
apps/audit-worker
```

Worker：

```ts
const database =
  createDatabase(config.DATABASE_URL);
```

Audit Worker：

```ts
const database =
  createDatabase(config.DATABASE_URL);
```

因此运行时更接近：

```text
API Process
    ↓
Pool A
    ↓
max = 20

Worker Process
    ↓
Pool B
    ↓
max = 20

Audit Worker Process
    ↓
Pool C
    ↓
max = 20
```

如果三个进程都运行并连接同一个 PostgreSQL，那么连接池配置的理论最大值需要按多个 Pool 一起计算：

```text
20 + 20 + 20 = 60
```

但这不表示进程启动后立刻创建 60 条连接，因为每个 node-postgres Pool 都是按需创建 Client。[[8]](https://node-postgres.com/apis/pool)

---

#### <u>2. 多实例部署时需要从整个系统计算数据库连接预算</u>

假设以后生产环境部署：

```text
API × 4
Worker × 2
Audit Worker × 1
```

那么不能只看：

```text
max = 20
```

而需要考虑：

```text
实例数量
×
每个实例的 Pool.max
=
整个系统可能占用的数据库连接规模
```

因此连接池大小不是一个孤立参数。

合理判断需要同时考虑：

```text
PostgreSQL 可以承受多少连接
        ↓
应用有多少 Process / Replica
        ↓
每个进程配置多少 Pool.max
        ↓
峰值 SQL 并发有多大
        ↓
是否存在长期占用 Connection 的任务
```

这就是 Connection Pool Sizing（连接池容量设计）的核心思路。

### 【应用关闭时需要主动关闭数据库连接池】

#### <u>1. pool.end 负责释放 Pool 中的连接和内部资源</u>

`DatabaseHandle`：

```ts
return {
  pool,
  db,
  close: () => pool.end(),
};
```

node-postgres 官方说明，`pool.end()` 会等待 Pool 中正在使用的 Client 被归还，然后断开 Client，并关闭连接池内部资源。它通常用于程序准备结束时清理数据库连接。[[8]](https://node-postgres.com/apis/pool)

所以服务退出不能只理解为：

```text
不再接 HTTP 请求
```

还需要释放：

```text
Database Connection
Redis Connection
Timer
Worker Task
其他外部资源
```

---

#### <u>2. 当前 API 和 Worker 都显式处理数据库关闭</u>

API：

```ts
async onApplicationShutdown(): Promise<void> {
  await Promise.allSettled([
    this.database.close(),
    this.redis.quit(),
  ]);
}
```

Worker：

```ts
async function shutdown(): Promise<void> {
  if (shuttingDown) return;

  shuttingDown = true;
  worker.stop();

  clearInterval(finalizeTimer);
  clearInterval(housekeepingTimer);

  await runPromise.catch(() => undefined);

  await Promise.allSettled([
    database.close(),
    redis.quit(),
  ]);
}
```

Worker 的退出顺序尤其值得注意：

```text
收到 SIGINT / SIGTERM
        ↓
worker.stop()
停止领取新任务
        ↓
等待当前 runPromise 结束
        ↓
database.close()
redis.quit()
        ↓
释放外部连接
```

这种做法属于：

**Graceful Shutdown（优雅关闭）**

也就是：

> 服务退出前先停止接收新的工作，再等待当前工作结束，最后按顺序释放数据库、Redis 等外部资源。

如果反过来：

```text
任务仍在执行
      ↓
先关闭数据库 Pool
      ↓
正在执行的 SQL 失去连接
```

就可能导致处理中任务异常失败。

### 【数据库连接层最终形成从业务代码到 PostgreSQL 的完整访问链】

学习完这一部分后，第一部分中简单的：

```text
Service
   ↓
Database
```

已经可以展开成：

```text
NestJS Service / Worker
        ↓
DatabaseHandle
        ↓
┌────────────────────────┐
│                        │
│ pool              db   │
│  │                 │   │
│  │             Drizzle │
│  │                 │   │
│  └────────┬────────┘   │
│           ▼            │
│          pg            │
│           ↓            │
│   Connection Pool      │
└───────────┬────────────┘
            ↓
        Connection
            ↓
   PostgreSQL Server
            ↓
        Database
            ↓
          Table
```

当前项目大量普通查询的实际链路是：

```text
Service
   ↓
database.pool.query(...)
   ↓
pg Pool
   ↓
取得 / 创建可用 Client
   ↓
PostgreSQL Connection
   ↓
发送 SQL
   ↓
PostgreSQL 执行
   ↓
返回 Result
   ↓
Client 回到 Pool
```

而需要固定使用同一条 Connection 的场景则是：

```text
Service
   ↓
pool.connect()
   ↓
取得 Client
   ↓
client.query(...)
client.query(...)
client.query(...)
   ↓
client.release()
   ↓
Client 回到 Pool
```

因此这一节最终需要建立的边界是：

| 概念 | 在当前项目中的位置 | 作用 |
| --- | --- | --- |
| PostgreSQL | 数据库服务 | 真正管理和处理数据 |
| `pg` | Node.js Database Driver | 负责 Node.js 与 PostgreSQL 通信 |
| Connection | `pg.Client` 背后的数据库连接 | 承载数据库通信 |
| Connection Pool | `pg.Pool` | 创建、复用、限制和回收 Connection |
| Drizzle | `drizzle-orm/node-postgres` | 提供 Schema 和更高层数据访问能力 |
| DatabaseHandle | `packages/database/src/client.ts` | 统一封装 `pool`、`db` 和关闭逻辑 |
| NestJS Provider | `InfrastructureModule` | 在 API 进程中共享 DatabaseHandle |

于是数据库访问的完整主链已经形成：

```text
HTTP Request
      ↓
Controller
      ↓
Service
      ↓
DatabaseHandle
      ↓
Connection Pool
      ↓
Connection
      ↓
PostgreSQL
      ↓
SQL
      ↓
Result
      ↓
Service
```

下一部分可以继续沿着这条链进入 **SQL（Structured Query Language，结构化查询语言）**：应用通过 `pool.query(sql, params)` 到底向 PostgreSQL 发送了什么，`SELECT / INSERT / UPDATE / DELETE` 分别解决什么问题，以及当前项目为什么使用 `$1`、`$2` 这样的参数占位符。



## 3. SQL 将业务数据操作翻译成 PostgreSQL 可以执行的数据库命令

上一部分已经建立：

```text
Service
   ↓
DatabaseHandle
   ↓
pg.Pool
   ↓
Connection
   ↓
PostgreSQL
```

现在继续解决 Connection 建立以后最核心的问题：

> 应用通过 Connection 到底向 PostgreSQL 发送什么？

答案就是 **SQL（Structured Query Language，结构化查询语言）**。

SQL 可以先理解为：

> 应用向关系型数据库描述“要查询什么数据、插入什么数据、修改什么数据、删除什么数据”的语言。

当前项目中最常见的形式是：

```ts
await this.database.pool.query(
  `SELECT ...`,
  [userId],
);
```

完整执行链路可以理解成：

```text
Service
   ↓
pool.query(sql, params)
   ↓
pg
   ↓
Connection
   ↓
PostgreSQL
   ↓
解析并执行 SQL
   ↓
返回 Result
   ↓
Service 使用结果
```

SQL 因此不是独立于前面连接体系的知识，而是通过 Connection 真正发送给 PostgreSQL 的数据库命令。

### 【SQL 操作先分为数据库结构和数据库数据两个方向】

#### <u>1. DDL 负责定义数据库应该以什么结构保存数据</u>

例如：

```sql
CREATE TABLE users (...);
```

表示：

```text
创建 users Table
```

还有：

```sql
ALTER TABLE ...
DROP TABLE ...
```

这类 SQL 主要负责定义或修改数据库结构，可以归入：

**DDL（Data Definition Language，数据定义语言）**

常见操作包括：

```text
CREATE
ALTER
DROP
```

在当前 Browser Monitor 项目中，这类操作主要出现在：

```text
browser-monitor/platform/packages/database/migrations/
```

也就是 Migration（数据库迁移）文件中。

原因是：

```text
创建 Table
修改 Column
建立 Index
修改数据库结构
```

通常属于数据库版本演进，而不是每个 HTTP Request 都需要执行的业务操作。

Migration 会在后续独立章节中展开，这一节只需要先知道 SQL 不只是操作 Row，也可以定义数据库结构。[[17]](https://www.postgresql.org/docs/current/sql.html)

---

#### <u>2. 日常业务代码主要通过 SELECT、INSERT、UPDATE、DELETE 操作数据</u>

业务运行阶段最常见的四类 SQL 是：

| 业务目标 | SQL | 作用 |
| --- | --- | --- |
| 创建数据 | `INSERT` | 插入新的 Row |
| 查询数据 | `SELECT` | 读取已有 Row |
| 修改数据 | `UPDATE` | 修改已有 Row |
| 删除数据 | `DELETE` | 删除已有 Row |

它们可以与常见的：

**CRUD（Create / Read / Update / Delete，增查改删）**

建立对应关系：

```text
Create
  ↓
INSERT

Read
  ↓
SELECT

Update
  ↓
UPDATE

Delete
  ↓
DELETE
```

但 SQL 不只有 CRUD。

后面还会继续接触：

```text
JOIN
GROUP BY
ORDER BY
COUNT
AVG
WITH
Window Function
Transaction
Lock
```

当前阶段先把最基础的数据读写链路建立起来。

### 【SELECT 从已经存在的 Table 中读取数据】

#### <u>1. SELECT 和 FROM 分别描述“取什么”和“从哪里取”</u>

最简单的查询：

```sql
SELECT id, name
FROM users;
```

可以直接翻译为：

```text
SELECT id, name
    ↓
需要返回哪些 Column

FROM users
    ↓
从哪张 Table 读取
```

也就是：

> 从 `users` 表中读取 `id` 和 `name` 两列。

PostgreSQL 的 `SELECT` 用于从 Table、View 等数据来源中读取数据。[[18]](https://www.postgresql.org/docs/current/sql-select.html)

---

#### <u>2. WHERE 用来限定哪些 Row 符合查询条件</u>

如果只写：

```sql
SELECT id, name
FROM users;
```

表示可能读取所有 User。

如果只希望读取指定 User：

```sql
SELECT id, name
FROM users
WHERE id = '123';
```

可以理解成：

```text
users
 ↓
检查每一条 Row
 ↓
只保留 id = 123 的 Row
 ↓
返回 id、name
```

所以：

```text
SELECT
    决定返回哪些字段

FROM
    决定从哪里读取

WHERE
    决定哪些 Row 符合条件
```

`WHERE` 因此不是简单的附加语法，而是在定义数据库操作的数据范围。

### 【ProjectsService.list 展示了业务查询如何翻译成 SELECT】

#### <u>1. 当前项目通过 SELECT 查询用户可以访问的 Project</u>

当前源码：

```text
browser-monitor/platform/apps/api/src/projects/projects.service.ts
```

其中：

```ts
const result = await this.database.pool.query<ProjectAccess>(
  `SELECT p.id, p.display_name, p.app_name, p.enabled, pm.role
   FROM projects p
   JOIN project_members pm ON pm.project_id = p.id
   WHERE pm.user_id = $1
   ORDER BY p.created_at DESC`,
  [userId],
);
```

它真正解决的业务问题是：

> 查询当前用户加入的所有 Project，并返回用户在每个 Project 中的 Role。

整条业务关系是：

```text
User
  ↓
project_members
  ↓
Project
```

SQL 只是把这层业务关系翻译成数据库查询。

---

#### <u>2. SELECT 指定最终需要返回的字段</u>

这部分：

```sql
SELECT
  p.id,
  p.display_name,
  p.app_name,
  p.enabled,
  pm.role
```

表示最终需要：

```text
Project ID
Project Display Name
Project App Name
Project Enabled
当前 User 在 Project 中的 Role
```

这里：

```text
p
pm
```

是 **Alias（别名）**。

例如：

```sql
FROM projects p
```

表示：

```text
projects Table
简称 p
```

所以：

```sql
p.id
```

就是：

```text
projects.id
```

在复杂 SQL 中使用 Alias 可以减少重复表名，并明确字段来自哪一张 Table。

---

#### <u>3. FROM 定义查询最基础的数据来源</u>

项目 SQL：

```sql
FROM projects p
```

表示：

```text
以 projects Table 作为查询基础
```

但只查询：

```text
projects
```

还不能回答：

> 当前这个 User 属于哪些 Project？

因为用户与项目之间的关系记录在：

```text
project_members
```

所以查询还需要继续引入 JOIN。

### 【JOIN 按照数据关系把不同 Table 组合起来查询】

#### <u>1. project_members 是 User 和 Project 之间的关系数据</u>

假设有：

`projects`

| id | display_name |
| --- | --- |
| p1 | Monitor A |
| p2 | Monitor B |

以及：

`project_members`

| project_id | user_id | role |
| --- | --- | --- |
| p1 | u1 | owner |
| p2 | u2 | owner |
| p2 | u1 | member |

现在要回答：

```text
u1 可以访问哪些 Project？
```

只看：

```text
projects
```

无法知道 User 与 Project 的对应关系。

所以项目使用：

```sql
JOIN project_members pm
  ON pm.project_id = p.id
```

这里：

```text
projects.id
       ↕
project_members.project_id
```

就是两张 Table 的关联条件。

`JOIN ... ON ...` 的核心作用可以先理解为：

> 根据指定关系，把不同 Table 中可以对应起来的 Row 组合到同一次查询中。[[18]](https://www.postgresql.org/docs/current/sql-select.html)

---

#### <u>2. WHERE 再把组合结果限制到当前 User</u>

JOIN 后可能得到：

```text
Project A - User 1 - owner
Project B - User 2 - owner
Project B - User 1 - member
```

然后：

```sql
WHERE pm.user_id = $1
```

假设：

```text
$1 = u1
```

最终留下：

```text
Project A - User 1 - owner
Project B - User 1 - member
```

所以完整查询链是：

```text
projects
   ↓
JOIN project_members
   ↓
建立 Project 和 Member 的对应关系
   ↓
WHERE user_id = 当前 User
   ↓
得到当前 User 可以访问的 Project
```

这里体现了一个重要的数据设计思想：

> SQL 并不是先背语法，再寻找业务用途；更自然的方式是先理解业务数据关系，再把关系翻译成 SQL。

### 【ORDER BY 为查询结果定义明确顺序】

#### <u>1. 当前项目按 Project 创建时间倒序返回结果</u>

查询最后：

```sql
ORDER BY p.created_at DESC
```

其中：

```text
ORDER BY
    排序

created_at
    根据创建时间

DESC
    Descending（降序）
```

因此：

```text
较新的 Project
      ↓
排在前面
```

如果是：

```sql
ASC
```

则表示：

**Ascending（升序）**

可以理解成：

```text
较小 / 较早
      ↓
较大 / 较晚
```

PostgreSQL 不保证没有 `ORDER BY` 的查询结果天然具有稳定业务顺序，所以只要业务依赖排序，就应该在 SQL 中明确表达。[[18]](https://www.postgresql.org/docs/current/sql-select.html)

### 【INSERT 向 Table 中创建新的 Row】

#### <u>1. INSERT 描述向哪张 Table 写入哪些 Column 和 Value</u>

最基础形式：

```sql
INSERT INTO users(name, email)
VALUES ('Tom', 'tom@example.com');
```

可以翻译为：

```text
INSERT INTO users
    ↓
向 users Table 写入数据

(name, email)
    ↓
需要写入哪些 Column

VALUES (...)
    ↓
这些 Column 对应什么 Value
```

PostgreSQL 的 `INSERT` 用于向 Table 中插入新的 Row。[[19]](https://www.postgresql.org/docs/current/sql-insert.html)

---

#### <u>2. 当前项目创建 Project 就是一条典型 INSERT</u>

`ProjectsService.create()`：

```ts
const project = await client.query<{ id: string }>(
  `INSERT INTO projects(
     display_name,
     app_name,
     user_hash_salt
   )
   VALUES ($1, $2, $3)
   RETURNING id`,
  [
    displayName.trim(),
    appName.trim(),
    userHashSalt,
  ],
);
```

假设实际值是：

```text
displayName = Monitor
appName = shop-web
userHashSalt = abc
```

这条 SQL 的业务含义就是：

```text
projects Table
      ↓
创建一个新的 Row

display_name = Monitor
app_name = shop-web
user_hash_salt = abc
```

所以 INSERT 的核心不是记住格式，而是：

```text
我要创建哪一类数据？
      ↓
对应哪张 Table？

新数据需要哪些属性？
      ↓
对应哪些 Column？

这些属性的具体值是什么？
      ↓
VALUES / Parameters
```

### 【RETURNING 让写操作直接把新增或修改后的数据返回给应用】

#### <u>1. 当前项目使用 RETURNING 取得数据库生成的 Project ID</u>

Project INSERT 后：

```sql
RETURNING id
```

表示：

> 数据写入完成后，把新 Row 的 `id` 返回给应用。

完整过程：

```text
INSERT Project
      ↓
PostgreSQL 创建 Row
      ↓
生成 / 得到 id
      ↓
RETURNING id
      ↓
Node.js 得到查询结果
```

项目随后：

```ts
const projectId = project.rows[0]!.id;
```

从 Result 中取出：

```text
第一条 Row
    ↓
id
```

再继续：

```ts
INSERT INTO project_members(...)
```

因此形成：

```text
INSERT projects
      ↓
RETURNING id
      ↓
project.rows[0].id
      ↓
projectId
      ↓
INSERT project_members
```

PostgreSQL 的 `RETURNING` 可以让 INSERT、UPDATE、DELETE 等写操作直接返回受影响 Row 的字段值。[[19]](https://www.postgresql.org/docs/current/sql-insert.html)

### 【UPDATE 修改已经存在的 Row】

#### <u>1. UPDATE 由目标 Table、SET 和 WHERE 共同决定修改内容</u>

当前项目：

```ts
await client.query(
  `UPDATE ingestion_keys
   SET expires_at = now() + INTERVAL '24 hours'
   WHERE project_id = $1
     AND active
     AND expires_at IS NULL`,
  [projectId],
);
```

可以拆成：

```sql
UPDATE ingestion_keys
```

表示：

```text
修改 ingestion_keys Table
```

然后：

```sql
SET expires_at = ...
```

表示：

```text
把 expires_at 修改成新的值
```

最后：

```sql
WHERE ...
```

表示：

```text
只有满足条件的 Row 才会被修改
```

PostgreSQL 的 `UPDATE` 会修改满足 `WHERE` 条件的 Row，没有出现在 `SET` 中的字段保持原值。[[20]](https://www.postgresql.org/docs/current/sql-update.html)

---

#### <u>2. UPDATE 中 WHERE 是定义修改范围的重要安全边界</u>

例如：

```sql
UPDATE users
SET enabled = false;
```

没有 `WHERE` 时，含义是：

```text
users 中所有 Row
      ↓
enabled 全部修改为 false
```

而：

```sql
UPDATE users
SET enabled = false
WHERE id = $1;
```

才是：

```text
只修改指定 User
```

因此看到 `UPDATE` 时，不能只关注：

```text
SET 改成什么
```

还必须关注：

```text
WHERE 到底限定了哪些 Row
```

写操作的数据范围本身就是数据库安全和正确性的核心组成部分。

### 【DELETE 删除符合条件的 Row】

#### <u>1. 当前项目通过 DELETE 清理 Project 原有 Origin</u>

`ProjectsService.replaceOrigins()`：

```ts
await client.query(
  'DELETE FROM allowed_origins WHERE project_id = $1',
  [projectId],
);
```

含义是：

```text
allowed_origins
      ↓
找到 project_id = 当前 Project 的 Row
      ↓
全部删除
```

随后：

```ts
for (const origin of normalized) {
  await client.query(
    `INSERT INTO allowed_origins(
       project_id,
       origin
     )
     VALUES ($1, $2)`,
    [projectId, origin],
  );
}
```

形成：

```text
删除旧 Origins
      ↓
插入新的 Origins
```

这里整体又被：

```text
BEGIN
...
COMMIT
```

包住。

为什么“先删后写”的多条 SQL 需要作为一个整体执行，就是后面 Transaction（事务）章节要解决的问题。

---

#### <u>2. DELETE 没有 WHERE 时会影响整张 Table</u>

例如：

```sql
DELETE FROM users;
```

表示：

```text
删除 users 中所有 Row
```

而：

```sql
DELETE FROM users
WHERE id = $1;
```

才表示：

```text
只删除指定 User
```

因此：

```text
UPDATE
DELETE
```

都应该自然检查：

```text
WHERE
=
本次操作的数据范围
```

### 【pool.query 将固定 SQL 结构和动态参数分开传给 PostgreSQL】

#### <u>1. $1、$2、$3 是 Parameter Placeholder</u>

项目中大量出现：

```ts
this.database.pool.query(
  `SELECT ...
   WHERE pm.user_id = $1`,
  [userId],
);
```

这里：

```sql
$1
```

是：

**Parameter Placeholder（参数占位符）**

可以理解成：

```text
Query Text

WHERE pm.user_id = $1
                   ↑
                第一个参数


Parameters

[
  userId
]
```

如果：

```text
userId = u123
```

那么执行时：

```text
$1
 ↓
u123
```

同理：

```sql
VALUES ($1, $2, $3)
```

配合：

```ts
[
  displayName,
  appName,
  userHashSalt,
]
```

表示：

```text
$1 → displayName
$2 → appName
$3 → userHashSalt
```

node-postgres 支持这种 **Parameterized Query（参数化查询）**，把 Query Text（SQL 文本）和 Parameter Values（参数值）分开交给 PostgreSQL。[[21]](https://node-postgres.com/features/queries)

---

#### <u>2. 参数化查询避免把外部数据直接拼进 SQL 结构</u>

如果代码自己拼接：

```ts
const sql =
  `SELECT *
   FROM users
   WHERE name = '\${name}'`;
```

此时：

```text
用户输入
    ↓
直接进入 SQL 字符串
    ↓
输入内容可能改变 SQL 结构
```

就可能产生：

**SQL Injection（SQL 注入）**

也就是：

> 外部输入原本应该只作为数据，却因为字符串拼接变成 SQL 语法的一部分，从而改变数据库真正执行的命令。

因此 node-postgres 官方明确建议不要直接把 Parameter 拼接进 SQL 文本，而是使用参数化查询。[[21]](https://node-postgres.com/features/queries)

项目采用：

```ts
pool.query(
  'SELECT ... WHERE id = $1',
  [id],
);
```

就是把：

```text
SQL Structure
    ↓
由开发者固定

External Value
    ↓
单独作为 Parameter
```

这体现了一个非常重要的边界：

> 外部输入应该作为数据参与查询，而不应该直接成为 SQL 代码结构的一部分。

---

#### <u>3. Parameter 适合替代 Value，不能直接替代 Table Name 或 Column Name</u>

下面这种方式是正常的：

```sql
WHERE id = $1
```

因为：

```text
$1
 ↓
Value
```

但是不能简单写：

```sql
SELECT *
FROM $1
```

再传：

```ts
['users']
```

希望 `$1` 直接成为 Table Name。

node-postgres 官方明确说明，PostgreSQL Parameter 不支持替代 Database、Schema、Table、Column 等 Identifier（标识符）。[[21]](https://node-postgres.com/features/queries)

因此要区分：

```text
Value
    普通数据值
    ↓
    可以使用 $1 / $2 参数化

Identifier
    Database / Schema / Table / Column 名
    ↓
    不能直接使用 $1 替代
```

这也是后续设计动态 SQL 时必须明确的边界。

### 【pg.Result 把 PostgreSQL 执行结果转换成 Node.js 可以继续处理的数据】

#### <u>1. result.rows 保存 SQL 实际返回的 Row</u>

项目：

```ts
const result =
  await this.database.pool.query<ProjectAccess>(...);
```

Query 成功后返回：

```text
pg.Result
```

其中最常见的字段包括：

```text
result.rows
result.rowCount
result.command
```

node-postgres 官方说明，`rows` 是数据库返回的数据 Row 数组；默认情况下，每个 Row 会被转换成 JavaScript Object。[[22]](https://node-postgres.com/apis/result)

例如数据库查询：

```sql
SELECT id, name
FROM users;
```

返回：

| id | name |
| --- | --- |
| 1 | Tom |
| 2 | Jerry |

Node.js 中的：

```ts
result.rows
```

可以近似理解成：

```ts
[
  {
    id: '1',
    name: 'Tom',
  },
  {
    id: '2',
    name: 'Jerry',
  },
]
```

所以当前项目：

```ts
return result.rows.map((row) => ({
  id: row.id,
  displayName: row.display_name,
  appName: row.app_name,
  enabled: row.enabled,
  role: row.role,
}));
```

实际做的是：

```text
Database Result
snake_case

display_name
app_name

       ↓

Application Object
camelCase

displayName
appName
```

因此又形成一层边界：

```text
Database Data Model
      ↓
SQL Result
      ↓
Service 转换
      ↓
Application Data Model
```

数据库字段结构不需要原封不动暴露给 Controller 或前端。

---

#### <u>2. result.rowCount 表示命令处理了多少 Row</u>

项目 `IngestionService` 中存在：

```ts
const insertedCount =
  inserted.rowCount ?? 0;
```

`rowCount` 对 INSERT、UPDATE、DELETE 等命令可以用来表示服务器处理的 Row 数量。[[22]](https://node-postgres.com/apis/result)

例如：

```sql
UPDATE users
SET enabled = false
WHERE role = 'guest';
```

可能：

```text
rowCount = 100
```

但如果 SQL 没有：

```sql
RETURNING ...
```

那么：

```text
rows
```

可能仍然为空。

所以：

```text
rowCount
    ↓
命令影响多少 Row

rows
    ↓
命令实际返回哪些 Row
```

两者不要混淆。

### 【SELECT 1 用最小 SQL 验证数据库链路是否可以正常执行】

#### <u>1. SELECT 不一定必须读取具体 Table</u>

当前健康检查：

```ts
await this.database.pool.query(
  'SELECT 1',
);
```

这里：

```sql
SELECT 1
```

没有：

```sql
FROM ...
```

也没有访问业务 Table。

它只是让 PostgreSQL 返回常量：

```text
1
```

如果：

```text
Pool 可以取得 Client
Connection 正常
PostgreSQL 可以响应
SQL 可以执行
```

那么这条 Query 就能够成功。

所以当前项目用它作为：

**Database Readiness Check（数据库就绪检查）**

验证的是：

```text
API
 ↓
pg Pool
 ↓
Connection
 ↓
PostgreSQL
 ↓
SQL Execution
```

这一整条数据库访问链是否已经可用。

### 【SQL 的核心是把业务问题翻译成数据操作】

#### <u>1. 业务问题可以沿着固定路径逐步翻译成 SQL</u>

SQL 不应该只理解成需要记忆的一组英文关键字。

更稳定的思考方式是：

```text
业务问题
   ↓
我要操作哪类数据？
   ↓
Table
   ↓
我要做什么？
   │
   ├── 查询 → SELECT
   ├── 创建 → INSERT
   ├── 修改 → UPDATE
   └── 删除 → DELETE
   ↓
影响哪些 Row？
   ↓
WHERE
   ↓
是否涉及其他 Table？
   ↓
JOIN
   ↓
结果是否需要明确顺序？
   ↓
ORDER BY
   ↓
哪些内容是动态业务数据？
   ↓
$1 / $2 Parameter
   ↓
pool.query(sql, params)
```

放回当前 `ProjectsService.list()`：

```text
业务需求
“查询当前 User 加入的所有 Project”
        ↓
projects
+
project_members
        ↓
JOIN
        ↓
WHERE user_id = $1
        ↓
ORDER BY created_at DESC
        ↓
SELECT 需要字段
        ↓
pool.query(...)
        ↓
result.rows
        ↓
Service 转换为应用数据结构
```

所以：

```ts
const result =
  await this.database.pool.query<ProjectAccess>(
    `SELECT p.id, p.display_name, p.app_name, p.enabled, pm.role
     FROM projects p
     JOIN project_members pm ON pm.project_id = p.id
     WHERE pm.user_id = $1
     ORDER BY p.created_at DESC`,
    [userId],
  );
```

应该从“业务关系”理解，而不是只从“SQL 语法”理解。

### 【SQL 层补完整了从业务需求到 PostgreSQL Result 的数据访问链】

这一节完成以后，数据库访问链可以继续扩展成：

```text
Business Requirement
        ↓
Service
        ↓
SQL
        ↓
pool.query(
  Query Text,
  Parameters
)
        ↓
pg
        ↓
Connection Pool
        ↓
Connection
        ↓
PostgreSQL
        ↓
Table
        ↓
SELECT / INSERT / UPDATE / DELETE
        ↓
pg.Result
        ↓
result.rows / rowCount
        ↓
Service
        ↓
API Result
```

当前阶段需要稳定区分：

| 概念 | 核心含义 |
| --- | --- |
| SQL | 应用描述数据库操作的语言 |
| `SELECT` | 查询数据 |
| `INSERT` | 创建 Row |
| `UPDATE` | 修改 Row |
| `DELETE` | 删除 Row |
| `WHERE` | 限定操作哪些 Row |
| `JOIN` | 按数据关系组合不同 Table |
| `ORDER BY` | 指定结果顺序 |
| `RETURNING` | 写操作后返回指定字段 |
| `$1 / $2` | Parameter Placeholder（参数占位符） |
| Parameters | 实际动态数据 |
| `result.rows` | SQL 返回的 Row |
| `result.rowCount` | 命令处理的 Row 数量 |

当前项目最典型的数据访问形式：

```ts
pool.query(
  `SELECT ...
   FROM ...
   WHERE ... = $1`,
  [value],
);
```

可以完整理解为：

```text
固定 SQL 结构
+
独立 Parameter Value
+
Connection Pool 执行
+
PostgreSQL 处理数据
+
pg.Result 返回 Node.js
```

下一部分继续进入关系型数据库的数据约束体系，从当前 `schema.ts` 出发学习：

```text
Data Type（数据类型）
Primary Key（主键）
Unique Constraint（唯一约束）
Foreign Key（外键）
NULL / NOT NULL
Default Value（默认值）
```

先理解数据库如何定义“什么数据才是合法数据”，再进入 Transaction（事务）与并发控制会更加自然。



## 4. 关系型数据库通过数据类型和约束定义合法数据状态

前面已经建立了从 Service、Connection 到 SQL 的数据库访问链。现在继续解决一个更基础的问题：

> SQL 可以把数据写入 PostgreSQL，但数据库是不是任何数据都会接受？

不是。关系型数据库除了保存数据，还要定义：

```text
Column 应该保存什么类型
Column 能不能为 NULL
一条 Row 如何被唯一识别
哪些业务值不能重复
不同 Table 之间的引用是否真实存在
某个状态值是否落在允许范围内
没有提供值时采用什么默认值
```

这些规则共同构成 Column Definition（字段定义）和 Constraint（约束）。

当前项目主要通过：

```text
packages/database/src/schema.ts
```

描述 TypeScript / Drizzle 侧的数据模型，同时通过：

```text
packages/database/migrations/*.sql
```

真正创建和修改 PostgreSQL 中的 Table、Constraint 与 Index。

### 【Data Type 限定 Column 可以保存哪一类数据】

#### <u>1. Column 不只是一个字段名，还具有明确的数据类型</u>

当前项目：

```ts
id: uuid('id').primaryKey().defaultRandom(),
email: varchar('email', { length: 320 }).notNull(),
passwordHash: text('password_hash').notNull(),
createdAt: timestamp('created_at', { withTimezone: true })
  .notNull()
  .defaultNow(),
```

分别描述：

```text
id
 ↓
uuid

email
 ↓
varchar(320)

password_hash
 ↓
text

created_at
 ↓
timestamp with time zone
```

数据库因此不只是知道“有哪些 Column”，还知道这些 Column 能接受什么类型的数据。[[26]](https://www.postgresql.org/docs/current/datatype.html)

---

#### <u>2. 当前项目主要使用 uuid、字符串、布尔、数值、时间和 jsonb</u>

`uuid` 主要承担稳定身份，例如：

```text
users.id
projects.id
user_sessions.id
outbox_tasks.id
```

项目常见：

```ts
uuid('id')
  .primaryKey()
  .defaultRandom()
```

Migration 中对应：

```sql
id uuid
PRIMARY KEY
DEFAULT gen_random_uuid()
```

UUID 是 PostgreSQL 原生支持的 128-bit 标识类型。[[27]](https://www.postgresql.org/docs/current/datatype-uuid.html)

字符串主要使用：

```text
varchar(n)
    有明确最大长度的字符串

text
    普通长文本
```

例如：

```ts
varchar('display_name', { length: 120 })
text('last_error')
```

状态值常使用：

```ts
boolean('enabled')
```

计数和顺序常使用：

```ts
integer('attempts')
integer('sequence')
```

性能值等允许小数的数据使用：

```ts
doublePrecision('value')
```

时间字段：

```ts
timestamp('created_at', {
  withTimezone: true,
})
```

在 PostgreSQL 中对应 `timestamptz` / `timestamp with time zone`。[[28]](https://www.postgresql.org/docs/current/datatype-datetime.html)

监控系统中的时间字段虽然类型相同，但业务语义不同：

```text
occurred_at
    浏览器真正产生事件的时间

received_at
    服务端收到事件的时间

completed_at
    后台任务真正完成的时间
```

`jsonb` 则用于结构复杂或扩展频繁的 JSON 数据，例如：

```text
event
detail
properties
attributes
environment
summary
analysis
```

所以 Data Type 不只是存储格式，也是在表达数据本身的业务性质。

### 【NULL、NOT NULL 和 DEFAULT 定义字段是否必须存在以及初始状态】

#### <u>1. NULL 表示当前没有有效值，而不是空字符串或 0</u>

例如：

```text
completed_at = NULL
```

可以表达：

> 当前任务还没有完成，因此不存在完成时间。

它不同于：

```text
completed_at = 0
completed_at = ""
completed_at = 1970-01-01
```

当前：

```ts
completedAt:
  timestamp('completed_at', {
    withTimezone: true,
  })
```

没有调用 `.notNull()`，因此允许 NULL。

业务状态可以表达成：

```text
pending / processing
        ↓
completed_at = NULL

completed
        ↓
completed_at = 实际完成时间
```

---

#### <u>2. NOT NULL 表示缺少该字段就不能形成合法 Row</u>

例如：

```ts
email:
  varchar('email', { length: 320 })
    .notNull()
```

表示 User 必须拥有 Email。

PostgreSQL 的 NOT NULL Constraint 会阻止 Column 保存 NULL。[[29]](https://www.postgresql.org/docs/current/ddl-constraints.html)

当前项目中的：

```text
users.email
projects.display_name
telemetry_events.event_id
performance_samples.value
```

都属于缺少值就失去基本业务意义的字段。

---

#### <u>3. DEFAULT 为新 Row 建立合理初始状态</u>

项目：

```ts
enabled:
  boolean('enabled')
    .notNull()
    .default(true)

status:
  varchar('status', { length: 24 })
    .notNull()
    .default('pending')

attempts:
  integer('attempts')
    .notNull()
    .default(0)
```

因此新 Outbox Task 可以自动形成：

```text
status = pending
attempts = 0
available_at = now()
created_at = now()
```

`.defaultRandom()` 和 `.defaultNow()` 分别对应数据库自动生成 UUID 与当前时间。

DEFAULT 的核心问题是：

> INSERT 没有显式提供值时，数据库应该采用什么合理初始值？

### 【Primary Key 唯一识别 Table 中的一条 Row】

#### <u>1. Primary Key 是 Table 的核心身份标识</u>

项目：

```ts
id:
  uuid('id')
    .primaryKey()
    .defaultRandom()
```

Primary Key（主键）可以理解为：

> 能唯一找到这张 Table 中某一条 Row 的 Column 或 Column 组合。

PostgreSQL 的 Primary Key 同时具有 UNIQUE 与 NOT NULL 的要求。[[29]](https://www.postgresql.org/docs/current/ddl-constraints.html)

---

#### <u>2. Primary Key 可以由多个 Column 共同组成</u>

项目的 `project_members`：

```ts
primaryKey({
  columns: [
    table.projectId,
    table.userId,
  ],
})
```

对应：

```sql
PRIMARY KEY (
  project_id,
  user_id
)
```

这是 Composite Primary Key（复合主键）。

它表达的业务规则是：

> 同一个 User 在同一个 Project 中只能存在一条成员关系。

因此必须建立：

```text
Primary Key
不一定 = 单独的 id Column
```

真正要问的是：

> 哪个字段或字段组合能够唯一识别这个业务事实？

### 【Unique Constraint 与 Unique Index 阻止不允许的重复业务值】

#### <u>1. Primary Key 和 Unique 都能限制重复，但职责不同</u>

当前 `users` 中：

```text
id
 ↓
Primary Key

email
 ↓
Unique
```

可以理解：

```text
Primary Key
    Row 的主要身份

Unique
    某个业务值或业务组合不能重复
```

Email 可能发生变化，所以它不一定适合作为 User 的稳定身份，但业务上仍然要求不能有两个用户使用相同 Email。

---

#### <u>2. Unique 可以约束多个 Column 的组合</u>

当前：

```ts
uniqueIndex(
  'allowed_origins_project_origin_unique'
).on(
  table.projectId,
  table.origin,
)
```

表示：

```text
(project_id, origin)
```

这个组合不能重复。

例如：

| project_id | origin | 是否允许 |
| --- | --- | --- |
| p1 | https://a.com | ✅ |
| p1 | https://b.com | ✅ |
| p2 | https://a.com | ✅ |
| p1 | https://a.com | ❌ 再次出现时冲突 |

这就是 Composite Unique（组合唯一）。

### 【Foreign Key 保证不同 Table 之间的引用真实存在】

#### <u>1. Foreign Key 阻止 Row 引用不存在的实体</u>

当前：

```ts
userId:
  uuid('user_id')
    .notNull()
    .references(
      () => users.id,
      { onDelete: 'cascade' },
    )
```

表示：

```text
user_sessions.user_id
          ↓
      users.id
```

即每条 Session 必须属于一个真实存在的 User。

PostgreSQL 的 Foreign Key 用于维护 Referential Integrity（引用完整性）。[[29]](https://www.postgresql.org/docs/current/ddl-constraints.html)

---

#### <u>2. ON DELETE 定义 Parent 删除后 Child 的生命周期</u>

项目大量使用：

```ts
.references(
  () => projects.id,
  { onDelete: 'cascade' },
)
```

CASCADE 表示：

```text
删除 Parent
      ↓
Child 已失去独立意义
      ↓
数据库自动删除关联 Row
```

例如：

```text
project_members
ingestion_keys
allowed_origins
telemetry_events
performance_samples
```

都强依赖 Project。

另一种：

```ts
.references(
  () => users.id,
  { onDelete: 'set null' },
)
```

SET NULL 表示：

```text
删除 Parent
      ↓
Child 仍需保留
      ↓
引用字段改成 NULL
```

例如 Audit Log 即使原 User 被删除，也可能仍然需要保留历史记录。

因此：

```text
CASCADE
    Child 没有 Parent 就失去意义

SET NULL
    Child 仍有独立价值
    只是引用对象已经不存在
```

### 【CHECK Constraint 在基础类型之外继续限制业务合法值】

#### <u>1. CHECK 可以限制状态集合和数值范围</u>

当前首版 Migration：

```sql
role varchar(16)
NOT NULL
CHECK (
  role IN ('owner', 'member')
)
```

表示：

```text
role = owner   ✅
role = member  ✅
role = admin   ❌
```

又例如：

```sql
value double precision
NOT NULL
CHECK (value >= 0)
```

数据库不仅检查 `value` 是数字，还检查它不能小于 0。

PostgreSQL 的 CHECK Constraint 会在 Row 写入或修改时验证指定条件。[[29]](https://www.postgresql.org/docs/current/ddl-constraints.html)

---

#### <u>2. 当前 Migration 中存在多组业务状态 CHECK</u>

`0001_platform.sql` 中包括：

```text
account_tokens.purpose
    verify-email / reset-password

project_members.role
    owner / member

project_invitations.role
    owner / member

outbox_tasks.status
    pending / processing / completed / failed

performance_samples.state
    provisional / final

performance_samples.value
    >= 0

performance_samples.sequence
    >= 0
```

这些规则说明数据库不只是保存结果，它还承担保护业务状态合法性的责任。

### 【当前项目的 Migration 不是由 schema.ts 自动生成】

#### <u>1. 当前仓库没有 drizzle-kit 生成 Migration 的链路</u>

当前数据库包：

```json
"scripts": {
  "migrate": "tsx src/migrate.ts"
}
```

当前仓库没有：

```text
drizzle-kit
drizzle.config.ts
drizzle-kit generate
drizzle-kit migrate
```

所以当前实际链路不是：

```text
schema.ts
   ↓
Drizzle Kit 分析
   ↓
自动生成 Migration SQL
```

而是：

```text
开发者维护 migrations/*.sql
        ↓
src/migrate.ts
        ↓
读取 SQL 文件
        ↓
client.query(sql)
        ↓
PostgreSQL 执行
```

当前 `migrate.ts` 的核心逻辑：

```ts
const files = (await readdir(migrationDirectory))
  .filter((name) => name.endsWith('.sql'))
  .sort();

for (const name of files) {
  const sql = await readFile(...);

  await client.query('BEGIN');
  await client.query(sql);
  await client.query(
    'INSERT INTO monitor_schema_migrations(name) VALUES ($1)',
    [name],
  );
  await client.query('COMMIT');
}
```

它不会分析 `schema.ts`，也不会根据 Drizzle Model 自动生成 CHECK、UNIQUE 或 Foreign Key。

---

#### <u>2. Migration 中的 CHECK 直接来自手写 SQL Migration</u>

例如：

```sql
CREATE TABLE project_members (
  ...
  role varchar(16)
    NOT NULL
    CHECK (role IN ('owner', 'member'))
);
```

其中：

```sql
CHECK (role IN ('owner', 'member'))
```

就是直接存在于：

```text
packages/database/migrations/0001_platform.sql
```

中的 SQL。

它不是 PostgreSQL 或 Drizzle 根据：

```ts
varchar('role', { length: 16 })
```

自动推导出来的。

数据库仅从 `varchar(16)` 不可能知道业务上只允许 `owner` / `member`。

---

#### <u>3. Drizzle 本身支持 CHECK，但当前 schema.ts 没有声明这些 CHECK</u>

Drizzle ORM 本身支持通过 `check(...)` 声明 CHECK Constraint。[[30]](https://orm.drizzle.team/docs/indexes-constraints)

因此当前差异不能解释成：

```text
Drizzle 不支持 CHECK
```

更准确的是：

```text
当前 schema.ts
没有把部分 CHECK 规则声明进去

当前 Migration SQL
手动包含了这些 CHECK
```

例如：

`schema.ts`：

```ts
role:
  varchar('role', { length: 16 })
    .notNull()
```

只表达：

```text
varchar(16)
+
NOT NULL
```

而 Migration：

```sql
role varchar(16)
NOT NULL
CHECK (
  role IN ('owner', 'member')
)
```

还表达：

```text
role 只能 owner / member
```

当前仓库没有记录最初为什么没有把这些 CHECK 同步进 `schema.ts`，因此不能推断作者当时的具体原因。

能够确认的是：

> 当前 `schema.ts` 与 Migration SQL 的约束描述并不完全一致。

---

#### <u>4. 已存在数据库的真实约束不能只根据 schema.ts 推断</u>

当前项目至少存在三个层次：

```text
Application Validation
        ↓
TypeScript / Zod / Service

Drizzle Model
        ↓
schema.ts

Database Migration
        ↓
migrations/*.sql
```

最终 PostgreSQL 中真实存在什么 Constraint，取决于：

```text
哪些 Migration 已经执行
+
后续 Migration 又修改了什么
```

因此分析已有数据库结构时应该沿着：

```text
完整 Migration Chain
        ↓
当前 PostgreSQL Schema
```

判断实际结构，而不能只把 `schema.ts` 当作唯一事实源。

两套定义长期不一致可以理解为 Schema Drift（结构定义漂移）。

### 【outbox_event_unique 是唯一索引名称，真正的规则由索引 Column 决定】

#### <u>1. uniqueIndex 的字符串参数是数据库对象名称</u>

当前 `outbox_tasks`：

```ts
uniqueIndex('outbox_event_unique')
  .on(
    table.projectId,
    table.eventId,
    table.occurredAt,
  )
```

可以拆成：

```text
uniqueIndex(...)
    ↓
声明 Unique Index（唯一索引）

'outbox_event_unique'
    ↓
这个 Index 的名字

.on(...)
    ↓
这个 Index 由哪些 Column 构成
```

所以：

```text
outbox_event_unique
```

不是特殊关键字，也不是业务字段。

它只是开发者给这个数据库对象起的名字。

---

#### <u>2. 真正的唯一性规则是三个 Column 组合不能重复</u>

真正重要的是：

```ts
.on(
  table.projectId,
  table.eventId,
  table.occurredAt,
)
```

即：

```text
(project_id, event_id, occurred_at)
```

这个组合不能重复。

允许：

| project_id | event_id | occurred_at |
| --- | --- | --- |
| p1 | e1 | 10:00 |
| p1 | e2 | 10:00 |
| p2 | e1 | 10:00 |
| p1 | e1 | 10:01 |

但不允许再次出现：

| project_id | event_id | occurred_at |
| --- | --- | --- |
| p1 | e1 | 10:00 |
| p1 | e1 | 10:00 |

它并不是：

```text
project_id 单独不能重复
event_id 单独不能重复
occurred_at 单独不能重复
```

而是三者组合不能重复。

PostgreSQL 的多列 Unique Index 会按照索引列组合执行唯一性检查。[[31]](https://www.postgresql.org/docs/current/indexes-unique.html)

---

#### <u>3. outbox_event_unique 保护“一条事件只对应一条 Outbox Task”的业务不变量</u>

`outbox_tasks` 保存的是：

```text
某条 Telemetry Event
后续等待 Worker 处理的后台任务
```

对于：

```text
Project A
+
Event E1
+
Occurred Time T1
```

不希望存在两条：

```text
Outbox Task 1
Project A / E1 / T1

Outbox Task 2
Project A / E1 / T1
```

否则同一事件可能重复进入 Worker 处理链。

所以这个 Unique Index 实际表达：

> 对同一个 Project 中同一个事件发生记录，只允许存在一条对应的 Outbox Task。

即：

```text
Telemetry Event
Project A + E1 + T1
        ↓
最多对应一条
        ↓
Outbox Task
```

---

#### <u>4. outbox_event_unique 这个名字主要用于识别和维护索引对象</u>

如果数据库显式创建：

```sql
CREATE UNIQUE INDEX outbox_event_unique
ON outbox_tasks (
  project_id,
  event_id,
  occurred_at
);
```

那么：

```text
outbox_event_unique
```

就是 PostgreSQL 中这个 Index 的对象名。

它可以用于：

```text
Migration
Schema Diff
数据库管理工具
系统目录查询
问题排查
DROP INDEX
```

例如：

```sql
DROP INDEX outbox_event_unique;
```

因此要区分：

```text
outbox_event_unique
    ↓
索引名称
    ↓
方便管理和定位数据库对象


(project_id, event_id, occurred_at)
    ↓
索引 Column
    ↓
真正决定唯一性规则
```

### 【schema.ts 的 outbox_event_unique 与首版 Migration 的 UNIQUE 写法并不完全相同】

#### <u>1. schema.ts 显式给 Unique Index 命名</u>

当前：

```ts
uniqueIndex('outbox_event_unique')
  .on(
    table.projectId,
    table.eventId,
    table.occurredAt,
  )
```

显式指定：

```text
Index Name
=
outbox_event_unique
```

---

#### <u>2. 0001_platform.sql 只声明 UNIQUE，没有显式写这个索引名</u>

首版 Migration：

```sql
CREATE TABLE outbox_tasks (
  ...
  UNIQUE (
    project_id,
    event_id,
    occurred_at
  )
);
```

这里没有：

```text
outbox_event_unique
```

因为当前 Migration 不是从 `schema.ts` 自动生成，所以：

```text
schema.ts 中给 Index 起名
        ↓
不会自动让已经手写的 Migration
出现同一个名字
```

通过这条匿名 UNIQUE Constraint 创建数据库时，PostgreSQL 会为 Constraint 以及支撑它的唯一索引使用系统生成的对象名，而不是读取 `schema.ts` 中的 `outbox_event_unique`。

这再次说明：

```text
schema.ts
和
migrations/*.sql
```

在当前项目里是两个需要人工保持一致的描述层。

---

#### <u>3. UNIQUE Constraint 与 Unique Index 表达侧重点不同但关系紧密</u>

Migration：

```sql
UNIQUE (
  project_id,
  event_id,
  occurred_at
)
```

更强调：

```text
数据约束：
这组值不能重复
```

Drizzle：

```ts
uniqueIndex('outbox_event_unique')
  .on(...)
```

更直接表达：

```text
建立一个 Unique Index
```

PostgreSQL 使用唯一索引执行 UNIQUE / PRIMARY KEY 的唯一性检查。[[32]](https://www.postgresql.org/docs/current/index-unique-checks.html)

所以在当前例子中，两者都在保护同一个业务不变量：

```text
project_id
+
event_id
+
occurred_at

不能出现重复组合
```

### 【数据库约束与应用层 Validation 负责不同保护边界】

#### <u>1. Application Validation 负责当前业务入口是否接受输入</u>

例如：

```text
HTTP Request
   ↓
Zod Validation
   ↓
Service
   ↓
Database
```

应用层 Validation 可以更早阻止非法输入、提供更清晰错误信息并完成复杂业务判断。

---

#### <u>2. Database Constraint 负责任何写入路径都不能制造非法状态</u>

数据库写入未来还可能来自：

```text
API
Worker
CLI
后台脚本
Migration
其他服务
```

因此：

```text
Application Validation
        ↓
当前入口是否接受这份输入

Database Constraint
        ↓
这种数据状态是否允许存在
```

例如两个并发请求都在应用层检查 Email 不存在，两边都可能认为可以注册。

真正阻止数据库最终出现两个相同 Email 的最后边界应该是数据库 UNIQUE。

所以：

```text
应用校验
+
数据库约束
```

不是简单重复，而是不同层次的保护。

### 【数据模型本质上是在声明系统允许存在的业务不变量】

以 `users` 为例：

```text
User 必须有唯一身份
        ↓
Primary Key

没有显式 ID 时自动生成
        ↓
Default

User 必须有 Email
        ↓
NOT NULL

Email 是有限长度字符串
        ↓
Data Type

不同 User 的 Email 不能重复
        ↓
Unique
```

再看 `project_members`：

```text
必须属于真实 Project
        ↓
Foreign Key

必须属于真实 User
        ↓
Foreign Key

Project ID / User ID 不能为空
        ↓
NOT NULL

同一 User 在同一 Project 只能出现一次
        ↓
Composite Primary Key

Role 只能 owner / member
        ↓
CHECK
```

因此一张 Table 的 Schema 不只是字段清单。

它真正定义的是：

> 什么样的一条 Row 才是系统允许存在的合法业务事实。

### 【本节最终形成数据进入 PostgreSQL 前的约束链】

完整写入链可以扩展为：

```text
Business Input
      ↓
Application Validation
      ↓
SQL INSERT / UPDATE
      ↓
PostgreSQL
      ↓
Data Type
      ↓
NULL / NOT NULL
      ↓
DEFAULT
      ↓
CHECK
      ↓
UNIQUE
      ↓
PRIMARY KEY
      ↓
FOREIGN KEY
      ↓
所有规则满足
      ↓
Row 写入成功
```

如果其中任何一层失败：

```text
Data Type 不匹配
NOT NULL 失败
CHECK 不通过
Unique 冲突
Primary Key 冲突
Foreign Key 引用不存在
```

PostgreSQL 都可以拒绝写入。

这一节最终需要稳定区分：

| 概念 | 核心问题 |
| --- | --- |
| Data Type | Column 可以保存什么类型的数据 |
| NULL | 当前是否允许没有值 |
| NOT NULL | 这个业务事实是否必须存在 |
| DEFAULT | 没有提供值时使用什么初始值 |
| Primary Key | 什么字段或组合唯一识别 Row |
| Unique | 哪些业务值或组合不能重复 |
| Foreign Key | 引用的数据是否真实存在 |
| ON DELETE CASCADE | Parent 删除后 Child 是否一起删除 |
| ON DELETE SET NULL | Parent 删除后是否保留 Child 并清空引用 |
| CHECK | 数据是否满足额外业务规则 |
| Unique Index Name | 如何识别和维护唯一索引对象 |

最终要建立：

```text
Database
不仅负责
“把数据保存下来”

还负责定义：

什么数据可以存在
什么数据不能存在
哪些数据必须唯一
哪些引用必须真实
哪些状态组合才合法
```

下一节可以继续进入 Index（索引），从当前已经出现的 Primary Key、Unique Index、普通 `index(...)` 和复合索引开始，解释索引为什么能减少查询扫描范围，以及当前项目为什么存在 `telemetry_project_time_idx`、`outbox_claim_idx`、`performance_project_time_idx` 等具体索引。


## 5. Index 通过有序搜索结构为高频 Query 建立更低成本的数据访问路径

前面已经建立了 Table、Row、Column、Primary Key、Unique、Foreign Key 和 SQL 的完整基础。现在继续解决：

> 当一张 Table 有几十万、几百万甚至更多 Row 时，PostgreSQL 怎样更快找到目标数据，而不是每次都从头扫描？

答案是 **Index（索引）**。

当前项目已经存在大量 Index：

```ts
index('telemetry_project_time_idx')
  .on(table.projectId, table.occurredAt)

index('performance_project_time_idx')
  .on(table.projectId, table.observedAt)

index('outbox_claim_idx')
  .on(table.status, table.availableAt)
```

这一节不只学习“有哪些 Index”，还需要回答四个底层问题：

```text
Index 为什么快？
B-Tree 到底是什么？
Index Key 一定是数字吗？
Composite Index 为什么有 Column 顺序？
```

### 【没有合适 Index 时 PostgreSQL 可能需要顺序扫描大量 Row】

#### <u>1. Sequential Scan 会按 Table 数据页逐步检查 Row</u>

假设：

```text
telemetry_events
=
1,000,000 Rows
```

执行：

```sql
SELECT *
FROM telemetry_events
WHERE event_id = 'e123';
```

如果没有合适 Index，一个直接执行方式是：

```text
Row 1
 ↓
event_id 是不是 e123？

Row 2
 ↓
event_id 是不是 e123？

...

Row 1,000,000
```

这种方式称为 **Sequential Scan（顺序扫描，简称 Seq Scan）**。

如果最终只需要少量 Row，却检查了大量数据页和 Row，就会产生较高扫描成本。

---

#### <u>2. Sequential Scan 并不是错误或一定很慢</u>

例如：

```sql
SELECT *
FROM telemetry_events;
```

本来就要读取绝大多数甚至全部 Row。这时顺序读取 Table 可能比先访问 Index、再根据 Index 逐条访问 Table 更划算。

所以：

```text
Seq Scan = 慢
Index Scan = 快
```

不是绝对规则。

PostgreSQL 会由 Query Planner（查询规划器）根据数据量、过滤比例、统计信息、排序要求和成本估算选择执行计划。[[36]](https://www.postgresql.org/docs/current/indexes.html)

### 【Index 是独立于 Table 的辅助查找结构】

#### <u>1. Index 不只是给 Column 加一个名字</u>

可以先用书的目录理解：

```text
一本 1000 页的书
      ↓
没有目录
      ↓
从第一页开始不断寻找目标主题

有目录
      ↓
主题 → 页码
      ↓
直接跳到目标范围
```

数据库 Index 类似：

```text
Index Key
    ↓
定位候选数据位置
    ↓
再访问真实 Table Row
```

所以 Index 与 Table 是两套不同结构：

```text
Table
    保存完整 Row

Index
    保存用于检索的 Key
    +
    定位真实 Row 所需的信息
```

---

#### <u>2. Key + Row Locator 描述“索引里存什么”，但不是“索引为什么快”</u>

可以先粗略理解普通 B-Tree Leaf Entry：

```text
Index Key
+
Row Locator
```

例如：

```text
occurred_at = 10:05
        ↓
Row Locator
        ↓
找到 Table 中真正的 Row
```

PostgreSQL 中 Table Row 的物理位置通常通过 TID（Tuple Identifier，元组位置标识）定位。

但是如果只是维护一个无序：

```text
Key → TID
```

列表：

```text
23 → A
51 → B
18 → C
30 → D
```

查询 `30` 时仍然可能需要逐个检查。

所以真正使 B-Tree Index 快的不是单纯存在“键值对应关系”，而是：

```text
Key 有明确顺序
+
Key 被组织进多层平衡搜索树
```

### 【PostgreSQL 默认普通 Index 使用 B-Tree】

#### <u>1. B-Tree 是 Multi-way Balanced Tree 而不是 Binary Tree</u>

PostgreSQL 将 B-Tree 定义为 **Multi-way Balanced Tree（多路平衡树）**。[[37]](https://www.postgresql.org/docs/current/btree.html)

它不是 Binary Tree（二叉树）。

二叉树通常是：

```text
        50
       /  \
     左    右
```

而 B-Tree 一个 Page 可以包含大量 Key，并分出很多 Child Page：

```text
              [20 | 40 | 60 | 80]
             /     |    |    |    \
          <20   20~40 40~60 60~80  >80
```

所以：

```text
B-Tree
=
多路
+
有序
+
平衡
```

---

#### <u>2. B-Tree 不是一个连续数组，而是由多个 Page 组成</u>

为了理解排序，有时会把 Index 简化成：

```text
[10, 20, 30, 40, 50]
```

但真实 PostgreSQL B-Tree 并不是一个连续大数组。

它更接近：

```text
Root Page
    ↓
Internal Page
    ↓
Internal Page
    ↓
Leaf Page
```

每个 Page 中可以保存很多 Index Entry。

例如简化结构：

```text
Root Page
[20 | 40 | 60]

   ├── Page A
   │   [1 5 10 15]
   │
   ├── Page B
   │   [20 25 30 35]
   │
   ├── Page C
   │   [40 45 50 55]
   │
   └── Page D
       [60 70 80 90]
```

这里：

```text
物理结构
    多个独立 Page

逻辑结构
    按 Key Range 组织成有序树
```

所以“B-Tree 有序”并不表示整个 Index 必须像 JavaScript Array 一样连续存储。

### 【B-Tree 通过每一层 Page 不断缩小目标范围】

#### <u>1. Internal Page 保存范围分隔 Key 和下一层 Page 的导航信息</u>

假设查询：

```sql
WHERE age = 32
```

Root：

```text
[20 | 40 | 60 | 80]
```

比较后知道：

```text
32
在
20 ~ 40
```

于是其他范围都不需要继续访问。

下一层：

```text
[25 | 30 | 35]
```

再次判断：

```text
32
在
30 ~ 35
```

继续只访问对应 Child Page。

最后：

```text
Root
 ↓
Internal Page
 ↓
Internal Page
 ↓
Leaf Page
```

找到目标 Key。

---

#### <u>2. Index 快的核心是每层都能排除大量不可能的数据范围</u>

没有 Index 时：

```text
1,000,000 Rows
      ↓
大量 Row 逐个检查
```

B-Tree：

```text
Root
 ↓
排除大量范围
 ↓
Internal Page
 ↓
继续排除
 ↓
Leaf Page
```

算法层面常粗略表示为：

```text
Sequential Search
    O(N)

Balanced Tree Search
    O(log N)
```

对于 B-Tree 更准确可以理解为树高与 `log_B(N)` 相关，其中一个 Page 可以包含很多 Entry，所以分支数 `B` 很大。

数据库层真正重要的收益是：

> 查询通常只需要访问少量 Index Page，而不是读取大量无关 Table Page。

### 【B-Tree 的有序性让等值、范围和排序查询都能获益】

#### <u>1. Key 有序让等值查询可以快速定位</u>

例如 Index Key：

```text
18
19
20
21
...
30
31
...
```

查询：

```sql
WHERE age = 30
```

B-Tree 可以通过层级导航直接定位 `30` 所在 Leaf Page。

---

#### <u>2. Leaf 范围有序让范围查询可以连续扫描</u>

例如：

```sql
WHERE age >= 30
AND age < 40
```

B-Tree 可以：

```text
先定位 30
    ↓
沿有序 Leaf 范围继续扫描
    ↓
30
31
32
...
39
    ↓
遇到 40 后停止
```

而不需要检查其他范围。

因此 B-Tree 很适合：

```text
=
<
<=
>
>=
Range Query
```

等比较。[[37]](https://www.postgresql.org/docs/current/btree.html)

---

#### <u>3. B-Tree 的顺序还可以帮助 ORDER BY</u>

如果：

```text
Index
=
(project_id, occurred_at)
```

数据逻辑顺序就是：

```text
Project A
  时间 1
  时间 2
  时间 3

Project B
  时间 1
  时间 2
```

在适合的 Query 中，PostgreSQL 可以按照 Index 顺序读取结果，而不一定需要先产生全部候选 Row 再单独 Sort。

B-Tree 可以正向或反向扫描，所以单列 B-Tree 即使默认 ASC，也可以支持相反方向的 ORDER BY；多列 Index 中 ASC / DESC 的组合则会更加重要。[[38]](https://www.postgresql.org/docs/current/indexes-ordering.html)

### 【B-Tree Key 不要求是 Number，只要求存在稳定排序关系】

#### <u>1. String 完全可以成为 B-Tree Key</u>

例如：

```sql
CREATE INDEX users_name_idx
ON users(name);
```

字符串可以按照数据库定义的比较和 Collation（排序规则）形成顺序：

```text
Alice
Bob
David
Lucy
Tom
```

查询：

```sql
WHERE name = 'Lucy'
```

仍然可以执行：

```text
Root
 ↓
判断 Lucy 属于哪个字符串范围
 ↓
Internal Page
 ↓
Leaf Page
 ↓
Lucy
```

因此 B-Tree 不是“数字树”。

PostgreSQL 官方说明，只要数据类型能够形成 well-defined linear order（明确的线性顺序），就可以用于 B-Tree Index。[[37]](https://www.postgresql.org/docs/current/btree.html)

---

#### <u>2. 当前项目中的 Index Key 本身就包含 UUID、String 和 Timestamp</u>

例如：

```ts
index('telemetry_project_type_time_idx')
  .on(
    table.projectId,
    table.type,
    table.occurredAt,
  )
```

其中：

```text
projectId
    UUID

type
    varchar / String

occurredAt
    Timestamp
```

因此整个 Composite Key 是：

```text
(
  UUID,
  String,
  Timestamp
)
```

它并不是转成一个 Number 再索引，而是按照每个类型对应的比较规则形成复合顺序。

---

#### <u>3. Composite Key 按 Column 顺序逐列比较</u>

例如逻辑值：

```text
(A, error, 10:00)
(A, error, 10:01)
(A, view,  09:00)
(B, error, 08:00)
```

比较过程类似字典序：

```text
先比较 project_id
      ↓
相同
      ↓
比较 type
      ↓
仍相同
      ↓
比较 occurred_at
```

所以 B-Tree Key 可以来自 Number、String、Timestamp、UUID、Boolean，也可以是多个 Column 组成的 Composite Key。

核心要求不是“是不是数字”，而是：

> 数据类型之间能够按照 PostgreSQL 的 Operator Class / Collation 等规则形成一致、稳定的比较顺序。[[37]](https://www.postgresql.org/docs/current/btree.html)

### 【Composite Index 的 Column 顺序决定复合 Key 的主要排序层级】

#### <u>1. `(project_id, occurred_at)` 先按 Project 再按 Time 组织</u>

当前 Migration：

```sql
CREATE INDEX telemetry_project_time_idx
ON telemetry_events(
  project_id,
  occurred_at DESC
);
```

可以粗略理解成：

```text
(Project A, 10:05)
(Project A, 10:04)
(Project A, 10:03)
(Project B, 10:05)
(Project B, 10:04)
```

查询：

```sql
WHERE project_id = $1
AND occurred_at >= $2
AND occurred_at < $3
```

可以先定位：

```text
Project 对应的 Index 范围
```

再在这个范围内定位：

```text
Time Range
```

---

#### <u>2. Leading Column 决定复合 B-Tree 最主要的缩小范围能力</u>

当前：

```text
INDEX(project_id, occurred_at)
```

非常适合：

```sql
WHERE project_id = ?
AND occurred_at >= ?
AND occurred_at < ?
```

也适合：

```sql
WHERE project_id = ?
```

但如果只有：

```sql
WHERE occurred_at >= ?
```

时间值会散布在不同 Project 分组中，这个 Index 通常没有“先 Project 再时间”的查询高效。

PostgreSQL 官方说明，多列 B-Tree 在 Leading Columns（前导 / 左侧列）存在有效约束时通常最有效。[[39]](https://www.postgresql.org/docs/current/indexes-multicolumn.html)

PostgreSQL 也可能通过 Skip Scan 等优化在特定情况下使用缺少前导列条件的复合索引，因此不能机械理解成“没有最左列就绝对不能使用”。

### 【当前监控平台的 Index 设计直接对应真实 Query Pattern】

#### <u>1. telemetry_project_time_idx 对应 Project + Time 查询</u>

当前监控分析大量查询都包含：

```text
project_id = ...
+
occurred_at 的时间范围
```

所以 Migration：

```sql
CREATE INDEX telemetry_project_time_idx
ON telemetry_events(
  project_id,
  occurred_at DESC
);
```

本质是在为：

```text
某个 Project
+
某段时间
```

这一高频访问模式建立专门路径。

---

#### <u>2. telemetry_project_type_time_idx 对应 Project + Type + Time 查询</u>

当前：

```sql
CREATE INDEX telemetry_project_type_time_idx
ON telemetry_events(
  project_id,
  type,
  occurred_at DESC
);
```

适合：

```text
Project
  ↓
Event Type
  ↓
Time Range
```

例如：

```text
Project A
+
error
+
过去 1 小时
```

---

#### <u>3. performance_project_time_idx 对应性能指标的 Project + Time 查询</u>

当前：

```ts
index('performance_project_time_idx')
  .on(
    table.projectId,
    table.observedAt,
  )
```

与 Analytics 常见：

```sql
WHERE p.project_id = $1
  AND p.observed_at >= $2
  AND p.observed_at < $3
```

直接对应。

所以 Index 设计的核心原则是：

> 先看真实 Query Pattern，再设计 Index，而不是看到一个 Column 就建立 Index。

### 【同一 Table 可以为不同 Query Pattern 建立不同 Index】

#### <u>1. telemetry_events 同时存在通用和更具体的查询路径</u>

当前：

```text
telemetry_project_time_idx
    (project_id, occurred_at)

telemetry_project_type_time_idx
    (project_id, type, occurred_at)
```

因为系统既会：

```text
按 Project + Time 查询
```

也会：

```text
按 Project + Type + Time 查询
```

如果只有：

```text
(project_id, type, occurred_at)
```

那么只按 `project_id + occurred_at` 查询时，`type` 夹在中间，不一定是最理想的扫描结构。

这说明：

> Index 本质上是在为重要 Query 建立专门的数据访问路径。

### 【Primary Key、Unique 与 Foreign Key 和 Index 的关系不同】

#### <u>1. Primary Key 和 Unique Constraint 会依赖 Unique B-Tree Index</u>

PostgreSQL 对：

```sql
PRIMARY KEY (id)
```

以及：

```sql
UNIQUE(email)
```

都会建立相应 Unique B-Tree Index，用于唯一性检查和定位。

因此通常不需要再建立一个完全重复的普通 Index。

---

#### <u>2. Foreign Key 的引用方不会因为关系存在就自动获得合适查询 Index</u>

例如：

```text
project_members.user_id
      ↓
users.id
```

Foreign Key 解决：

```text
这条关系是否合法
```

而：

```ts
index('project_members_user_idx')
  .on(table.userId)
```

解决：

```text
如何更快查询某 User 对应的 Member Row
```

所以：

```text
Foreign Key
    关系正确性

Index
    查询访问效率
```

职责不同。

### 【Partial Index 只为满足指定条件的 Row 建立索引】

#### <u>1. outbox_claim_idx 在真实 Migration 中是 Partial Index</u>

当前 `schema.ts`：

```ts
index('outbox_claim_idx')
  .on(
    table.status,
    table.availableAt,
  )
```

但实际 Migration：

```sql
CREATE INDEX outbox_claim_idx
ON outbox_tasks(
  status,
  available_at
)
WHERE status IN (
  'pending',
  'processing'
);
```

表示：

```text
pending
processing
    ↓
进入 Index

completed
failed
    ↓
不进入 Index
```

这种只覆盖 Table 子集的 Index 称为 **Partial Index（部分索引）**。[[40]](https://www.postgresql.org/docs/current/indexes-partial.html)

---

#### <u>2. outbox_claim_idx 与 Worker Claim Query 是直接对应的</u>

Worker 当前查询：

```sql
SELECT id
FROM outbox_tasks
WHERE (
  status = 'pending'
  AND available_at <= now()
) OR (
  status = 'processing'
  AND locked_at < now() - INTERVAL '5 minutes'
)
ORDER BY available_at, created_at
LIMIT $1
FOR UPDATE SKIP LOCKED
```

Worker 真正关心的是：

```text
当前仍可能被领取的任务
```

所以让：

```text
completed
failed
```

不进入 Claim Index，可以减少无关 Index Entry。

---

#### <u>3. outbox_claim_idx 并没有完整覆盖 Worker Query 的所有条件</u>

Index：

```text
(status, available_at)
```

但 Query 还使用：

```text
locked_at
created_at
```

所以不能简单说：

> 这个 Index 完整覆盖了 Worker Claim Query。

更准确的是：

```text
Index
    帮助缩小 pending / processing 候选范围
    尤其支持 status + available_at 路径

后续
    仍可能过滤 locked_at
    仍可能处理 created_at 排序
```

最终执行路径需要通过 EXPLAIN 验证。

### 【Query Planner 决定最终是否使用 Index】

#### <u>1. 创建 Index 不代表 PostgreSQL 强制走 Index</u>

即使存在：

```text
telemetry_project_time_idx
```

如果 Query 会返回大多数 Row，Planner 仍可能选择 Seq Scan。

所以 Index 的准确定位是：

> 给 PostgreSQL 提供一种可能更低成本的访问路径，而不是强制数据库必须使用 Index。

---

#### <u>2. EXPLAIN 用于确认 Query 实际采用什么执行计划</u>

例如：

```sql
EXPLAIN
SELECT *
FROM telemetry_events
WHERE project_id = '...'
AND occurred_at >= '...'
AND occurred_at < '...';
```

可能看到：

```text
Index Scan
```

也可能：

```text
Bitmap Index Scan
      ↓
Bitmap Heap Scan
```

或者：

```text
Seq Scan
```

因此数据库性能优化应该形成：

```text
Query
 ↓
分析 WHERE / JOIN / ORDER BY / LIMIT
 ↓
设计 Index
 ↓
EXPLAIN / EXPLAIN ANALYZE
 ↓
查看 Planner 实际选择
 ↓
验证扫描范围、Row 数和执行时间
```

[[41]](https://www.postgresql.org/docs/current/using-explain.html)

### 【Index 的读性能收益需要用写入和存储成本交换】

#### <u>1. INSERT、UPDATE、DELETE 也需要维护相关 Index</u>

例如 INSERT：

```text
写 Table
+
更新 Index A
+
更新 Index B
+
更新 Index C
```

因此：

```text
Index 增加
    ↓
SELECT 可选访问路径增加

同时
    ↓
磁盘占用增加
INSERT / UPDATE / DELETE 维护成本增加
```

所以：

```text
更多 Index
≠
数据库一定更快
```

正确目标是：

> 给重要 Query 提供足够有效、但不过度重复的数据访问路径。

### 【本节最终形成 Index 为什么快的完整认知链】

Index 不能只理解成：

```text
给 Column 建一个键值对
```

也不能只理解成：

```text
把所有值排序成一个数组
```

对 PostgreSQL B-Tree 更完整的模型是：

```text
Table 中存在大量 Row
        ↓
为高频 Query 选择 Index Key
        ↓
Index Entry 保存 Key
以及定位 Row 所需的信息
        ↓
Key 按比较规则形成有序关系
        ↓
多个 Page 组成 Multi-way Balanced B-Tree
        ↓
Root / Internal Page
不断排除不可能的数据范围
        ↓
定位少量 Leaf Page
        ↓
取得候选 Row Locator
        ↓
访问真正 Table Row
```

所以 B-Tree 快主要来自：

```text
1. Key 有稳定顺序

2. 多层树结构
   每层排除大量范围

3. Multi-way
   一个 Page 可以导航很多 Child Page

4. Balanced
   Root 到 Leaf 的路径保持较短

5. Leaf 范围有序
   适合连续 Range Scan

6. Composite Key
   可以围绕真实 Query Pattern
   同时组织多个 Column
```

而 Index Key：

```text
不要求是 Number
```

只要求：

```text
能够按照数据库规则形成稳定比较顺序
```

所以可以是：

```text
Number
String
Timestamp
UUID
Boolean
Composite Key
...
```

当前项目中的典型 Composite Key：

```text
(project_id, occurred_at)

(project_id, type, occurred_at)

(project_id, observed_at)

(project_id, name, occurred_at)
```

其实就是把 Browser Monitor 最常见的：

```text
Project
+
业务维度
+
Time Range
```

查询方式提前编码进数据库访问结构。
