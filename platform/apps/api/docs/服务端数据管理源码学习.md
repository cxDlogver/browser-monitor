# 服务端数据管理源码学习

> **学习目标**：从数据库零基础开始，在已经建立的 NestJS + Fastify API 框架认知上，继续向下理解服务端的数据管理体系。本文不会先背数据库 API，而是先回答“数据为什么需要独立保存、数据库是什么、PostgreSQL 在系统中处于什么位置、表如何组织数据”等基础问题，再逐步进入数据库连接、SQL、关系模型、事务、并发控制、Redis、TimescaleDB 和数据可靠性。
>
> **分析范围**：通用数据库知识以 PostgreSQL 官方文档为主要参考；项目部分以当前 `browser-monitor/platform` 源码为事实基准。第一部分只建立数据库最基础的概念，不提前深入事务、索引、锁、MVCC、WAL 等内部机制。
>
> **与已有文档的关系**：[`NestJS-Fastify-API源码学习.md`](./NestJS-Fastify-API源码学习.md) 已经解释请求如何经过 Fastify、NestJS、Controller 和 Service。本文从它停下来的 `Database / Redis` 继续向下展开。

## 1. 数据管理从“程序中的数据为什么会消失”开始

### 【程序能够暂时保存数据，但程序本身不是长期数据存储】

先从最简单的 Node.js 程序开始：

```ts
const users = [];

users.push({
  id: 1,
  name: 'Tom',
});
```

此时程序里确实已经存在数据：

```text
Node.js Process（Node.js 进程）
        │
        │ 内存
        ▼
users

[
  { id: 1, name: "Tom" }
]
```

这里首先要区分两个概念：

```text
Program（程序）
    负责执行代码

Data（数据）
    表示程序需要记录的事实
```

例如：

```text
Tom 注册了账号
Project A 被创建
/home 页面产生了一次 LCP
```

这些都是系统需要记录的事实。

但是上面的 `users` 数组只存在于当前 Node.js 进程使用的内存中。程序运行时可以访问它；程序退出以后，这部分内存不再属于这个进程，数组中的内容也不会自动成为可以长期恢复的数据。

可以先把过程理解成：

```text
程序启动
   ↓
创建 users 数组
   ↓
用户注册
   ↓
users 中出现数据
   ↓
程序退出
   ↓
当前进程中的内存状态消失
```

对于临时计算结果，这没有问题。

例如：

```ts
const total = price * count;
```

`total` 只需要服务当前计算。

但下面这些数据不能随着程序退出而消失：

```text
用户账号
项目配置
订单
权限关系
监控事件
性能数据
后台任务
```

因此服务端需要把“程序执行”与“数据长期保存”拆成两套能力：

```text
Application（应用程序）
        ↓
处理请求和业务逻辑

Persistent Storage（持久化存储）
        ↓
长期保存业务事实
```

这里的 **Persistent（持久化）**，可以先简单理解为：

> 数据不会因为当前应用进程结束就一起消失。

这也是数据库进入服务端体系的第一个原因。

---

### 【长期保存数据并不意味着所有场景都必须使用数据库】

如果只是希望程序重启以后数据仍然存在，也可以把数据写入文件：

```ts
fs.writeFileSync(
  'users.json',
  JSON.stringify(users),
);
```

这样：

```text
Node.js 进程退出
        ↓
users 内存消失

但是

users.json
        ↓
仍然存在于磁盘
```

因此不能把数据库简单定义成：

> “数据库就是为了让数据不丢。”

文件同样可以长期保存数据。

真正的区别在于，当系统逐渐变复杂以后，我们不只是需要“把数据写下来”，还需要系统化地管理这些数据。

例如一个服务端可能逐渐出现：

```text
100 万用户
500 万订单
几千万条监控事件
```

同时多个请求都在访问这些数据：

```text
Request A
    ↓
查询用户

Request B
    ↓
创建订单

Request C
    ↓
修改项目

Request D
    ↓
查询最近 7 天性能数据
```

如果都由业务代码直接维护几个 JSON 文件，程序就必须自己处理很多问题：

```text
数据应该如何分类？

如何快速找到一条数据？

如何修改其中一部分？

两个请求同时修改怎么办？

哪些字段必须存在？

哪些数据不能重复？

两个数据之间有什么关系？

一次操作只完成了一半怎么办？

数据量很大以后怎么查询？
```

因此服务端最终需要的不是一个单纯的文件，而是一套完整的数据管理能力：

```text
保存
 ↓
组织
 ↓
查询
 ↓
修改
 ↓
约束
 ↓
并发处理
 ↓
故障恢复
```

数据库体系正是围绕这些问题建立起来的。

## 2. Database 和 DBMS 描述的是不同层次

### 【Database 表示被组织起来的数据】

**Database（数据库）** 可以先理解为：

> 一组按照一定结构组织并长期保存的数据。

例如 Browser Monitor 需要保存：

```text
User
Project
Telemetry Event
Performance Sample
Outbox Task
```

这些数据不能只存在于当前 API 进程中，而需要进入独立的数据存储体系。

从最粗粒度看：

```text
Application
    ↓
Database
```

应用负责业务处理，数据库负责保存业务事实。

但到这里还有一个问题：

> 谁负责真正创建、读取、修改和管理这些数据？

这就需要继续区分第二个概念。

---

### 【DBMS 是负责管理数据库的软件】

**DBMS（Database Management System，数据库管理系统）** 是专门负责管理数据库的软件。

常见 DBMS 包括：

```text
PostgreSQL
MySQL
SQLite
```

它们不是某一张表，也不是某一条数据，而是一整套数据管理软件。

因此更完整的层次是：

```text
Application
    ↓
DBMS
    ↓
Database
    ↓
Data
```

DBMS 帮助应用完成：

```text
创建数据库
创建表
写入数据
查询数据
修改数据
删除数据
限制非法数据
处理多个客户端同时访问
管理事务
管理索引
备份和恢复
```

所以在后续学习中要始终区分：

```text
Database
    数据本身的逻辑集合

DBMS
    管理数据库的软件

PostgreSQL
    一种 DBMS
```

日常开发中人们经常会口语化地说“连接 PostgreSQL 数据库”，这种说法没有问题，但建立知识体系时需要知道其中包含了不同层次。

---

## 3. PostgreSQL 在当前服务端中是独立的数据服务

### 【API 不直接操作数据库文件】

Browser Monitor 当前使用 PostgreSQL / TimescaleDB 作为主要持久化数据系统。

从运行关系看，可以先建立：

```text
Browser
   │
   │ HTTP
   ▼
Browser Monitor API
   │
   │ Database Request
   ▼
PostgreSQL Server
   │
   ▼
Database
```

PostgreSQL 官方把它描述为 **Client / Server Model（客户端 / 服务器模型）**：PostgreSQL Server 负责管理数据库文件、接受客户端连接，并代表客户端执行数据库操作；Web Server 也可以作为 PostgreSQL Client。[1]

因此：

```text
Browser
   ↓
API Server
```

在这段通信中：

```text
Browser = Client
API     = Server
```

但是：

```text
API
 ↓
PostgreSQL
```

在这段通信中：

```text
API        = Client
PostgreSQL = Server
```

这说明 **Client（客户端）和 Server（服务器）描述的是一段通信关系中的角色，而不是某个程序永久固定的身份。**

这一点后面理解 Database Connection（数据库连接）时非常重要。

---

### 【当前项目通过统一连接地址找到 PostgreSQL】

项目的基础设施配置中存在：

```text
DATABASE_URL
```

API 的 `InfrastructureModule` 使用它创建数据库能力：

```ts
{
  provide: DATABASE,
  inject: [API_CONFIG],
  useFactory: (config: ApiConfig): DatabaseHandle =>
    createDatabase(config.DATABASE_URL),
}
```

源码位置：

```text
browser-monitor/platform/apps/api/src/infrastructure/infrastructure.module.ts
```

这里暂时只需要理解：

```text
DATABASE_URL
      ↓
告诉应用 PostgreSQL 在哪里以及如何连接
      ↓
createDatabase(...)
      ↓
建立应用的数据访问能力
```

`createDatabase()` 内部的 Connection（连接）、Pool（连接池）、Driver（驱动）会在下一部分单独展开。

第一部分只需要明确：**NestJS 并不负责保存数据，NestJS 只是把数据库能力装配到应用中；真正负责数据管理的是后面的 PostgreSQL 数据体系。**

## 4. 关系型数据库首先使用 Table、Row 和 Column 组织数据

### 【大量数据必须先形成稳定结构】

假设数据库里只是保存：

```text
Tom
Jerry
2300
/home
project-a
2026-09-30
```

虽然数据都存在，但程序无法知道：

```text
Tom 是用户还是项目？

2300 是时间还是性能值？

/home 属于哪个项目？

2026-09-30 对应哪条数据？
```

因此数据不仅需要被保存，还需要被组织。

PostgreSQL 属于 **Relational Database（关系型数据库）**。在这一阶段，可以先从最基础的 Table（表）开始理解。

PostgreSQL 官方文档说明，一张表由 Row（行）和 Column（列）组成，每一列有名字和数据类型。[2]

例如：

```text
users
```

可以表示为：

| id | name | email |
| --- | --- | --- |
| 1 | Tom | tom@example.com |
| 2 | Jerry | jerry@example.com |

这里有三个基础概念。

**Table（表）**

表示同一类数据的集合。

例如：

```text
users
projects
telemetry_events
```

分别保存不同类型的数据。

**Row（行）**

表示一条具体数据。

例如：

```text
1 | Tom | tom@example.com
```

可以表示一个具体用户。

**Column（列）**

表示这一类数据具有哪些属性。

例如 User 可能包含：

```text
id
name
email
```

所以当前阶段可以先形成：

```text
Database
   ↓
Table
   ↓
Row
   ↓
Column
```

但要注意，这只是为了建立入门层次的简化图。

PostgreSQL 实际还有：

```text
PostgreSQL Server
        ↓
Database
        ↓
Schema
        ↓
Table
```

这里的 **Schema（模式 / 数据库对象命名空间）** 与项目里的 `schema.ts` 不是完全相同的概念。PostgreSQL Schema 会在后续“数据库对象组织”部分单独解释，现在不提前展开。

## 5. Browser Monitor 的 schema.ts 把项目中的数据结构声明出来

### 【项目把数据库模型放在独立 database package 中】

当前项目的数据定义主要位于：

```text
browser-monitor/platform/packages/database/src/schema.ts
```

其中可以看到：

```ts
export const users = pgTable(...)
export const projects = pgTable(...)
export const projectMembers = pgTable(...)
export const telemetryEvents = pgTable(...)
export const outboxTasks = pgTable(...)
export const performanceSamples = pgTable(...)
export const viewRecords = pgTable(...)
```

这里的 `pgTable(...)` 来自 Drizzle。

这一阶段暂时不要把注意力放到 Drizzle API，而只把这些代码翻译成数据设计：

```text
users
    保存用户

projects
    保存监控项目

project_members
    保存用户和项目之间的成员关系

telemetry_events
    保存浏览器上传的原始监控事件

outbox_tasks
    保存等待 Worker 处理的后台任务

performance_samples
    保存处理后的性能样本

view_records
    保存页面访问记录
```

因此 `schema.ts` 最重要的价值不是“用了一个 ORM”，而是：

> 项目把系统需要长期保存的事实明确拆成了不同的数据模型。

---

### 【telemetry_events 展示了一个事件如何从对象变成结构化数据】

例如：

```ts
export const telemetryEvents = pgTable(
  'telemetry_events',
  {
    projectId: ...,
    eventId: ...,
    occurredAt: ...,
    receivedAt: ...,
    type: ...,
    name: ...,
    environment: ...,
    appVersion: ...,
    sessionId: ...,
    viewId: ...,
    routeName: ...,
    event: ...,
  },
);
```

把代码翻译成普通语言就是：

```text
创建一张 telemetry_events 表

每一条监控事件都要记录：

属于哪个项目
事件自己的 ID
什么时候发生
服务器什么时候收到
事件属于什么类型
事件叫什么
运行环境是什么
应用版本是什么
属于哪个 Session
属于哪个 View
发生在哪个页面
完整事件数据是什么
```

于是 SDK 上报：

```text
Project A
/home
LCP
2300ms
production
v2.3.0
```

进入数据库以后，不再只是一个临时 JavaScript 对象，而会成为可以长期查询的一条结构化记录。

整个变化可以理解成：

```text
Browser Runtime Event
        ↓
Telemetry JSON
        ↓
Ingestion API
        ↓
telemetry_events Table
        ↓
长期保存的一条 Row
```

这就是从“程序运行时数据”进入“数据库事实”的第一条完整链路。

## 6. 关系型数据库还需要描述不同数据之间的联系

### 【系统中的数据不是互相独立的几个文件】

当前项目存在：

```text
users
projects
project_members
telemetry_events
```

这些表并不是四组互不相关的数据。

例如：

```text
User
  ↓
加入
  ↓
Project
```

项目使用：

```text
project_members
```

记录这层联系。

其数据中包含：

```text
projectId
userId
role
```

可以表达：

```text
User A
   │
   │ owner
   ▼
Project A
```

同样：

```text
Telemetry Event
      │
      │ projectId
      ▼
   Project
```

表示某一条监控事件属于哪个项目。

因此关系型数据库的学习不能停留在：

```text
一张表
另一张表
再一张表
```

真正的系统会逐渐形成：

```text
User
  │
  ▼
Project Member
  │
  ▼
Project
  │
  ├─────────────┐
  ▼             ▼
Telemetry     Threshold
Event         Config
  │
  ▼
Outbox Task
```

后续学习 Primary Key（主键）和 Foreign Key（外键）时，就会正式解释数据库如何保证这些关系。

现在只需要建立：

> **关系型数据库不仅负责保存不同类型的数据，还需要描述和约束这些数据之间的联系。**

## 7. 当前项目的数据管理已经包含多种不同性质的数据

从 `schema.ts` 可以继续发现，Browser Monitor 保存的并不是单一类型的数据。

可以先粗略分为三组。

### 【业务管理数据描述平台本身的业务事实】

例如：

```text
users
projects
project_members
ingestion_keys
allowed_origins
threshold_versions
```

这些数据回答：

```text
有哪些用户？

有哪些项目？

用户属于哪些项目？

项目使用什么写入 Key？

允许哪些 Origin？

当前采用哪套指标阈值？
```

它们更接近普通业务系统常见的数据。

### 【监控数据描述浏览器真实发生过的事件】

例如：

```text
telemetry_events
performance_samples
view_records
custom_signal_samples
custom_metric_samples
```

这些数据回答：

```text
什么时候发生了什么事件？

某个页面的 LCP 是多少？

某个 View 持续多久？

某个 Trace / Span 发生在哪里？

某个自定义指标值是多少？
```

这类数据通常会不断增长，并且天然带有时间属性。

这也是项目后续引入 TimescaleDB（时序数据库扩展能力）的原因之一。

### 【任务数据描述还有哪些后台工作需要完成】

例如：

```text
outbox_tasks
dead_letter_tasks
```

它们回答：

```text
哪些事件还没有处理？

哪些任务正在处理？

哪些任务失败了？

哪些任务已经多次重试仍然失败？
```

所以数据库不是简单的“业务资料仓库”。

在当前项目里，它同时承担：

```text
业务状态
+
监控事实
+
后台任务状态
```

三类责任。

这也为后面的 Transaction（事务）和 Outbox（事务型任务表）埋下了伏笔：某些业务事实和任务状态不能各写各的，而需要保证它们一起成功或一起失败。

这一点会在事务章节正式展开。

## 8. 数据库在已有 NestJS 服务端框架中的位置进一步明确

前面的 NestJS 文档已经建立：

```text
Browser
 ↓
Fastify
 ↓
NestJS
 ↓
Controller
 ↓
Service
 ↓
Database / Redis
```

学习完这一部分后，最后一层已经可以继续展开：

```text
Browser
   ↓
HTTP
   ↓
Fastify
   ↓
NestJS
   ↓
Controller
   ↓
Service
   ↓
Database Client
   ↓
PostgreSQL Server
   ↓
Database
   ↓
Table
   ↓
Row
```

以监控事件为例：

```text
Monitor SDK
   ↓
POST /api/v3/ingest/:publicKey/envelopes
   ↓
IngestionController
   ↓
IngestionService
   ↓
Database Access
   ↓
PostgreSQL
   ↓
telemetry_events
   ↓
一条长期保存的监控事件
```

这时候可以更准确地理解“Service 访问数据库”这句话。

它不是：

```text
Service
  ↓
直接操作硬盘文件
```

而是：

```text
Service
  ↓
数据库客户端能力
  ↓
PostgreSQL Server
  ↓
由 PostgreSQL 管理实际数据
```

数据库因此位于业务逻辑之后，但又不是业务代码的一部分。

## 9. 第一部分先建立清晰边界，不提前进入数据库内部实现

这一阶段最重要的是把容易混淆的名词放回正确层次。

| 概念 | 当前阶段的理解 |
| --- | --- |
| Data（数据） | 系统希望记录的事实 |
| Memory（内存） | 当前进程运行期间使用的临时空间 |
| Persistent Storage（持久化存储） | 程序退出后仍能保存数据的存储 |
| Database（数据库） | 被组织并长期保存的数据集合 |
| DBMS（数据库管理系统） | 负责管理数据库的软件 |
| PostgreSQL | 当前项目使用的关系型 DBMS |
| Table（表） | 同一类数据的集合 |
| Row（行） | 一条具体数据 |
| Column（列） | 这类数据包含哪些属性 |
| Relational Database（关系型数据库） | 用关系模型组织数据，并描述不同数据之间联系的一类数据库 |

这一部分暂时不需要深入：

```text
SQL 如何执行
Connection 如何建立
Connection Pool 如何复用连接
Primary Key 如何实现
Index 为什么能加速查询
Transaction 如何保证一致性
MVCC 如何控制并发
WAL 如何保证恢复
```

它们都有明确的位置，但需要按依赖顺序继续学习，而不是一次性堆在一起。

## 10. 第一部分最终收敛为一条数据持久化链路

第一阶段只需要稳定建立下面这条链：

```text
现实中的业务事实
例如：
用户注册
项目创建
浏览器产生 LCP

        ↓

Application
应用程序负责处理业务

        ↓

Database Management System
数据库管理系统

当前项目：PostgreSQL

        ↓

Database
组织和长期保存数据

        ↓

Table
按数据类型组织

        ↓

Row
一条具体数据

        ↓

Column
描述数据具有哪些属性
```

放回 Browser Monitor：

```text
浏览器产生 LCP
       ↓
Monitor SDK
       ↓
Ingestion API
       ↓
IngestionService
       ↓
PostgreSQL
       ↓
telemetry_events
       ↓
形成长期保存的监控事实
```

这条链建立以后，下一部分再继续回答一个新的问题：

> 应用代码和 PostgreSQL 是两个独立运行的程序，它们到底怎样建立通信？
