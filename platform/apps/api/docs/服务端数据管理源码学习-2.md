# 服务端数据管理源码学习-2

## 7. Transaction（事务）把多个数据库操作组织成一个可靠的业务执行单元

前面已经建立了数据库最基本的数据管理链路：

~~~text
Application
↓
Database Client
↓
PostgreSQL Server
↓
SQL
↓
Table / Row
↓
Index
~~~

到这里，我们已经能够完成：

~~~text
保存数据
查询数据
修改数据
删除数据
通过 Constraint 保证数据合法
通过 Index 提高查询效率
~~~

但真实业务还有一个新的问题：

> 一次业务操作往往需要修改多张表、执行多条 SQL。只保证每一条 SQL 本身正确，并不能保证整个业务操作正确。

例如当前 Browser Monitor 创建一个 Project，并不是只执行一条 INSERT，而是需要连续完成：

~~~text
创建 projects
↓
创建 project_members
↓
创建 ingestion_keys
↓
创建 allowed_origins
↓
写入 audit_logs
~~~

这些数据共同表达同一个业务事实：

~~~text
一个完整可使用的 Project 已经创建
~~~

如果只完成前两步：

~~~text
projects               成功
project_members        成功
ingestion_keys         失败
allowed_origins        没执行
audit_logs             没执行
~~~

数据库虽然每一条已经成功的 SQL 都是合法的，但整体业务状态已经不完整。

Transaction（事务）就是从这里进入数据管理体系的。

Transaction 可以先理解为：

> 将一组必须共同成功或共同失败的数据库操作，放入同一个数据库执行范围。

PostgreSQL 对事务的基本定义也是：把多个步骤组织为一个整体，从外部看要么全部发生，要么全部不发生；事务执行过程中的中间状态不会作为已经提交的数据暴露给其他并发事务。

### 【Transaction 的边界来自业务操作，而不是 SQL 数量】

#### <u>1. 多条 SQL 不代表一定需要事务</u>

事务设计不能简单理解为：

~~~text
有多条 SQL
↓
所以一定使用 Transaction
~~~

例如：

~~~text
查询 Project
查询 Project Member
查询 Threshold
~~~

虽然执行了三条 SQL，但它们可能只是三个互相独立的普通读取，不一定要求作为一个不可拆分的整体。

而创建 Project：

~~~text
INSERT projects
INSERT project_members
INSERT ingestion_keys
INSERT allowed_origins
INSERT audit_logs
~~~

这些 SQL 共同表达：

~~~text
Project 创建完成
~~~

因此需要共享同一个 Transaction Boundary（事务边界）：

~~~text
BEGIN
↓
INSERT projects
↓
INSERT project_members
↓
INSERT ingestion_keys
↓
INSERT allowed_origins
↓
INSERT audit_logs
↓
COMMIT
~~~

Transaction Boundary 表示：

> 一个事务从哪里开始，到哪里结束，以及哪些数据库操作必须共同提交或者共同回滚。

真正应该判断的是：

~~~text
这些 SQL 是否共同描述一个业务状态变化？
↓
如果只成功一部分，业务状态是否仍然正确？
↓
如果不正确，就需要考虑共同的 Transaction Boundary
~~~

#### <u>2. ProjectsService.create() 直接体现事务边界</u>

当前源码位于：

~~~text
browser-monitor/platform/apps/api/src/projects/projects.service.ts
~~~

核心逻辑：

~~~ts
const client = await this.database.pool.connect();
try {
  await client.query('BEGIN');
  const project = await client.query(
    'INSERT INTO projects(display_name, app_name, user_hash_salt) VALUES ($1, $2, $3) RETURNING id',
    [displayName.trim(), appName.trim(), userHashSalt],
  );
  const projectId = project.rows[0].id;
  await client.query(
    "INSERT INTO project_members(project_id, user_id, role) VALUES ($1, $2, 'owner')",
    [projectId, userId],
  );
  await client.query(
    "INSERT INTO ingestion_keys(project_id, public_key, label) VALUES ($1, $2, 'default')",
    [projectId, publicKey],
  );
  await client.query(
    'INSERT INTO allowed_origins(project_id, origin) VALUES ($1, $2)',
    [projectId, defaultOrigin],
  );
  await client.query('COMMIT');
} catch (error) {
  await client.query('ROLLBACK');
  throw error;
} finally {
  client.release();
}
~~~

这里不是因为“有多条 SQL”才使用事务，而是因为：

~~~text
Project
+
Owner
+
Ingestion Key
+
Allowed Origin
+
Audit Log
~~~

共同组成：

~~~text
完整 Project 创建
~~~

任意一步失败，都不应该留下部分完成状态。

### 【PostgreSQL 中每一条 SQL 本身也运行在事务中】

#### <u>1. 没有手动 BEGIN 不代表没有事务</u>

例如：

~~~sql
UPDATE projects
SET enabled = false
WHERE id = $1;
~~~

即使应用没有主动写 BEGIN，PostgreSQL 仍会把这一条语句放在一个事务中执行。

可以先理解成：

~~~text
隐式开始 Transaction
↓
执行 UPDATE
↓
成功
↓
自动 COMMIT
~~~

这种方式通常称为 Autocommit（自动提交）。

因此：

~~~text
没有 BEGIN
≠
没有 Transaction
~~~

更准确的是：

~~~text
普通单条 SQL
↓
自己形成一个事务
↓
SQL 成功后自动提交
~~~

#### <u>2. 显式事务用于让多条 SQL 共用同一个事务</u>

当业务需要：

~~~text
SQL 1
SQL 2
SQL 3
~~~

共同成功时，应用主动定义：

~~~sql
BEGIN;
SQL 1;
SQL 2;
SQL 3;
COMMIT;
~~~

这称为 Explicit Transaction（显式事务），也就是开发者明确控制事务的开始和结束。

所以：

~~~text
单条 SQL
↓
通常由数据库自动形成一个事务

多条 SQL 需要共同成功
↓
开发者显式建立 Transaction
~~~

---

### 【BEGIN、COMMIT 和 ROLLBACK 控制事务生命周期】

#### <u>1. BEGIN 表示事务开始</u>

~~~sql
BEGIN;
~~~

表示后续数据库操作开始进入同一个 Transaction，直到 COMMIT 或 ROLLBACK 才结束。

#### <u>2. COMMIT 表示确认整个事务</u>

~~~sql
COMMIT;
~~~

表示：

~~~text
当前 Transaction 成功结束
↓
事务中的修改成为已提交状态
~~~

需要注意：

~~~text
COMMIT
≠
到这里才开始真正执行前面的 SQL
~~~

SQL 在事务过程中已经真正执行。

例如：

~~~sql
BEGIN;
UPDATE projects SET enabled = false WHERE id = 'A';
SELECT enabled FROM projects WHERE id = 'A';
~~~

当前 Transaction 自己已经能够看到：

~~~text
enabled = false
~~~

说明 UPDATE 已经执行。

只是：

~~~text
这个修改还没有 COMMIT
↓
其他事务不能把它当成已经提交的数据
~~~

所以更准确的执行过程是：

~~~text
BEGIN
↓
SQL 真正执行
↓
当前 Transaction 基于修改后的状态继续运行
↓
COMMIT
↓
整个 Transaction 成为已提交状态
~~~

#### <u>3. ROLLBACK 放弃当前事务产生的修改</u>

如果：

~~~text
BEGIN
↓
SQL 1 成功
↓
SQL 2 成功
↓
SQL 3 失败
↓
ROLLBACK
~~~

最终不会留下：

~~~text
SQL 1 已提交
SQL 2 已提交
SQL 3 失败
~~~

而是整个 Transaction 不提交。

当前项目普遍使用：

~~~ts
try {
  await client.query('BEGIN');
  await client.query(sql1);
  await client.query(sql2);
  await client.query('COMMIT');
} catch (error) {
  await client.query('ROLLBACK');
  throw error;
}
~~~

PostgreSQL 中一条普通 SQL 在事务内部发生错误后，当前 Transaction 通常会进入失败状态，所以 catch 中的 ROLLBACK 是在明确结束这个失败事务。

---

### 【SAVEPOINT 允许事务内部进行局部回滚】

如果希望：

~~~text
事务整体继续存在
但撤销其中一部分修改
~~~

可以使用 SAVEPOINT（保存点）。

例如：

~~~sql
BEGIN;
INSERT INTO projects(...);
SAVEPOINT before_member;
INSERT INTO project_members(...);
ROLLBACK TO before_member;
INSERT INTO project_members(...);
COMMIT;
~~~

ROLLBACK TO SAVEPOINT 只撤销保存点之后的操作，而不会结束整个 Transaction。

当前 Browser Monitor 源码没有直接使用 SAVEPOINT，但它属于完整事务体系的一部分。Drizzle 的嵌套事务能力也建立在数据库的保存点能力之上。

### 【Transaction 必须绑定同一个 Database Connection】

#### <u>1. Connection Pool 中存在多个连接</u>

当前项目在：

~~~text
browser-monitor/platform/packages/database/src/client.ts
~~~

创建：

~~~ts
const pool = new Pool({
  connectionString,
  max: 20,
  idleTimeoutMillis: 30_000,
  connectionTimeoutMillis: 5_000,
});
~~~

Pool（Connection Pool，连接池）负责维护和复用多个 PostgreSQL Connection（数据库连接）。

普通查询可以：

~~~ts
await this.database.pool.query(sql);
~~~

因为单条 SQL 只需要一个可用 Connection 即可。

Transaction 不一样。

~~~text
BEGIN
SQL 1
SQL 2
SQL 3
COMMIT
~~~

必须全部发生在同一个 Connection 上。

#### <u>2. pool.connect() 为事务取得一个固定 Client</u>

当前源码统一：

~~~ts
const client = await this.database.pool.connect();
~~~

这里的 Client 可以理解为：

~~~text
从 Pool 中临时借出的一个固定 PostgreSQL Connection
~~~

随后：

~~~ts
await client.query('BEGIN');
await client.query(sql1);
await client.query(sql2);
await client.query('COMMIT');
~~~

一直使用同一个 Client。

完整过程：

~~~text
Pool
↓
pool.connect()
↓
Client A
├── BEGIN
├── SQL 1
├── SQL 2
├── SQL 3
└── COMMIT
↓
client.release()
↓
Client A 回到 Pool
~~~

#### <u>3. 不能使用多个 pool.query() 拼接一个事务</u>

错误方式：

~~~ts
await pool.query('BEGIN');
await pool.query(sql1);
await pool.query(sql2);
await pool.query('COMMIT');
~~~

因为实际可能变成：

~~~text
BEGIN  → Connection A
SQL 1  → Connection C
SQL 2  → Connection B
COMMIT → Connection A
~~~

这些命令不在同一个数据库 Connection 上，也就不属于同一个 PostgreSQL Transaction。

node-postgres 官方明确要求：一个 Transaction 中的所有语句必须使用同一个 Client。

#### <u>4. finally 中必须释放 Connection</u>

当前源码：

~~~ts
finally {
  client.release();
}
~~~

保证无论 COMMIT、ROLLBACK 还是抛出异常，Connection 最终都归还连接池。

否则：

~~~text
不断 pool.connect()
↓
Connection 不 release
↓
可用 Connection 越来越少
↓
请求开始等待
↓
连接池耗尽
~~~

### 【Atomicity（原子性）保证多个修改不会只完成一部分】

ACID 是 Transaction 的四个核心性质：

~~~text
Atomicity
Consistency
Isolation
Durability
~~~

不能只记名称，而要知道每一个性质解决什么问题。

Atomicity（原子性）表示：

> 一个 Transaction 中的多个数据库修改，要么共同提交，要么共同回滚。

当前 Project 创建：

~~~text
Project
├── Owner
├── Ingestion Key
├── Allowed Origin
└── Audit Log
~~~

没有 Transaction 时可能出现：

~~~text
Project      成功
Owner        成功
Key          失败
Origin       未执行
Audit        未执行
~~~

加入 Transaction：

~~~text
BEGIN
↓
Project
↓
Owner
↓
Key
↓
Origin
↓
Audit
↓
COMMIT
~~~

任意一步失败：

~~~text
ROLLBACK
~~~

最终只允许：

~~~text
Project 完整创建
~~~

或者：

~~~text
Project 没有创建
~~~

#### <u>replaceOrigins() 也是典型原子操作</u>

当前逻辑：

~~~text
BEGIN
↓
DELETE 旧 Origins
↓
INSERT 新 Origins
↓
INSERT Audit Log
↓
COMMIT
~~~

如果 DELETE 已经提交但 INSERT 失败，Project 的 Allowed Origins 可能被意外清空。

所以“替换 Origin 列表”整体就是一个事务边界。

#### <u>rotateKey() 保护 Key 切换过程</u>

当前逻辑：

~~~text
BEGIN
↓
旧 Key 设置 expires_at
↓
创建新 Key
↓
记录 Audit Log
↓
COMMIT
~~~

旧 Key 进入失效过程、新 Key 创建和审计记录共同描述一次 Key Rotation，因此应该一起提交或一起回滚。

---

### 【Consistency（一致性）由事务、数据库约束和业务规则共同维持】

Consistency（一致性）回答：

> 一次业务操作完成后，数据库是否仍然满足系统定义的合法规则。

它不能理解成：

~~~text
用了 Transaction
↓
业务一定正确
~~~

例如：

~~~text
project_members.project_id
必须对应真实存在的 projects.id
~~~

这是 Foreign Key（外键）保证的关系规则。

例如：

~~~text
同一个 Project + Version
不能重复
~~~

这是 UNIQUE Constraint（唯一约束）保证的规则。

但：

~~~text
创建 Project 后
必须同时存在 Owner、Key、Origin
~~~

这种规则属于 Application Business Logic（应用业务逻辑），数据库不会自动知道。

所以更准确的是：

~~~text
Business Logic
+
Constraint
+
Transaction
+
必要的并发控制
↓
共同维持 Consistency
~~~

Transaction 能保证几个修改共同提交，但如果业务代码本身把状态计算错了，Transaction 不会自动理解业务语义并修复错误。

---

### 【Isolation（隔离性）处理多个事务同时执行时的数据可见性】

真实服务端同时存在很多请求和 Worker：

~~~text
Request A → Transaction A
Request B → Transaction B
Request C → Transaction C
Worker 1  → Transaction D
Worker 2  → Transaction E
~~~

Isolation（隔离性）解决的是：

> 多个 Transaction 并发运行时，一个 Transaction 可以看到其他 Transaction 的哪些变化，以及冲突发生时怎样处理。

PostgreSQL 使用 MVCC（Multi-Version Concurrency Control，多版本并发控制）作为重要基础。

这一阶段先理解：

~~~text
数据库能够维护不同的数据版本
↓
不同 Transaction 根据规则看到适合自己的版本
↓
普通读取和写入不需要全部互相阻塞
~~~

MVCC 内部的 Transaction ID、Row Version、Snapshot 和 Visibility 会在下一部分并发控制中继续展开。

---

### 【Isolation Level 定义并发事务的数据可见范围】

常见 Isolation Level（事务隔离级别）有：

~~~text
Read Uncommitted（读未提交）
Read Committed（读已提交）
Repeatable Read（可重复读）
Serializable（串行化）
~~~

#### <u>1. Dirty Read（脏读）表示读到其他事务未提交的数据</u>

~~~text
Transaction A
UPDATE balance = 0
尚未 COMMIT

Transaction B
读取 balance = 0

Transaction A
ROLLBACK
~~~

B 曾经读取到一个最终没有成立的数据，这就是 Dirty Read。

PostgreSQL 的 Read Committed 不允许 Dirty Read。

#### <u>2. Nonrepeatable Read（不可重复读）表示同一 Row 前后读取变化</u>

~~~text
Transaction A
第一次 SELECT
balance = 100

Transaction B
UPDATE balance = 50
COMMIT

Transaction A
第二次 SELECT
balance = 50
~~~

同一个 Transaction 两次读取同一个 Row 得到不同结果，这就是 Nonrepeatable Read。

#### <u>3. Phantom Read（幻读）表示满足条件的 Row 集合变化</u>

第一次：

~~~sql
SELECT *
FROM orders
WHERE status = 'pending';
~~~

得到 10 Rows。

其他 Transaction 新增一条 pending 数据并 COMMIT，当前 Transaction 再执行同样的 Query，得到 11 Rows。

变化的是：

~~~text
满足查询条件的数据集合
~~~

这就是 Phantom Read。

#### <u>4. PostgreSQL 默认使用 Read Committed</u>

当前项目没有显式修改 Isolation Level，因此采用 PostgreSQL 默认的：

~~~text
Read Committed（读已提交）
~~~

在 Read Committed 下：

~~~text
不会读取其他 Transaction 未提交的数据
~~~

但同一个 Transaction 内两次普通 SELECT：

~~~text
可能看到其他 Transaction
在两次查询之间已经提交的新状态
~~~

因此：

~~~text
使用 Transaction
≠
所有并发问题自动消失
~~~

Transaction 定义执行范围，Isolation Level、Lock、Constraint 和 Retry 继续处理并发问题。

#### <u>5. Serializable 提供更强隔离，但可能要求应用重试</u>

Serializable（串行化）的目标不是简单让所有 Transaction 物理上一个一个执行，而是保证成功提交后的结果可以解释成某种串行执行顺序。

如果 PostgreSQL 判断当前并发执行无法满足这种要求，可能让其中一个 Transaction 发生 Serialization Failure（串行化失败），应用需要重新执行整个业务事务。

所以：

~~~text
更高 Isolation
↓
更强隔离保证
+
更多冲突检测
+
更高 Retry 要求
~~~

不能简单认为：

~~~text
Serializable 最强
↓
所有业务都应该使用 Serializable
~~~

更合理的判断顺序是：

~~~text
先确认真正的并发问题
↓
Read Committed 是否已经足够
↓
Constraint 是否可以解决
↓
是否需要 FOR UPDATE
↓
是否需要 Advisory Lock
↓
是否真的需要更高 Isolation Level
~~~

当前 Browser Monitor 更接近：

~~~text
Read Committed
+
Constraint
+
FOR UPDATE
+
Advisory Lock
+
Idempotency
~~~

---

### 【Transaction 和 Lock 解决的是不同层次的问题】

Transaction 主要回答：

~~~text
一次业务操作
能不能只完成一部分？
~~~

Lock（锁）主要回答：

~~~text
多个 Transaction
能不能同时修改同一个受保护资源？
~~~

因此：

~~~text
Transaction
≠
Lock
~~~

但真实数据库逻辑经常组合为：

~~~text
BEGIN
↓
获得 Lock
↓
读取当前状态
↓
执行修改
↓
COMMIT / ROLLBACK
↓
释放 Lock
~~~

---

### 【FOR UPDATE 把“读取后修改”放入受保护的并发区间】

当前 ProjectsService.acceptInvitation()：

~~~sql
SELECT id, project_id, email, role
FROM project_invitations
WHERE token_hash = $1
AND accepted_at IS NULL
AND expires_at > now()
FOR UPDATE
~~~

完整业务：

~~~text
BEGIN
↓
SELECT Invitation FOR UPDATE
↓
检查邀请是否有效
↓
检查 Email
↓
INSERT / UPDATE project_members
↓
UPDATE invitation.accepted_at
↓
COMMIT
~~~

FOR UPDATE 属于 Row-Level Lock（行级锁）。

可以先理解为：

> 当前 Transaction 不只是读取这条 Row，而是准备基于它的当前状态继续修改，因此在 Transaction 结束前，对其他冲突修改进行限制。

两个 Request 同时接受同一个 Invitation：

~~~text
Request A
BEGIN
↓
SELECT ... FOR UPDATE
↓
获得 Row Lock

Request B
BEGIN
↓
SELECT 同一个 Row FOR UPDATE
↓
等待 A
~~~

A 完成：

~~~text
UPDATE accepted_at
↓
COMMIT
↓
释放 Lock
~~~

B 才继续执行。

所以 Lock 通常和 Transaction 生命周期绑定：

~~~text
获得 Lock
↓
Transaction 持续
↓
COMMIT / ROLLBACK
↓
释放 Lock
~~~

---

### 【Advisory Lock 保护没有现成 Row 可以锁的业务资源】

当前 Ingestion 中还有：

~~~sql
pg_advisory_xact_lock(...)
~~~

它属于 Advisory Lock（建议锁，也可以理解成应用自定义含义的逻辑锁）。

FOR UPDATE 锁的是：

~~~text
已经存在的数据库 Row
~~~

但某些业务冲突对象还没有对应 Row。

例如 Ingestion 需要按照：

~~~text
projectId + eventId
~~~

做幂等去重，但目标 Event 此时可能根本没有插入 telemetry_events。

所以没有 Row 可以 SELECT ... FOR UPDATE。

当前源码使用：

~~~sql
SELECT pg_advisory_xact_lock(
  hashtextextended($1 || ':' || ids.event_id, 0)
)
~~~

业务先构造：

~~~text
ingest:{projectId}:{eventId}
~~~

再映射成 PostgreSQL 可以使用的 Lock Key。

可以理解为：

~~~text
数据库中还没有目标 Row
↓
Application 先定义一个逻辑资源
↓
PostgreSQL 按这个资源 Key 协调并发 Transaction
~~~

pg_advisory_xact_lock 是 Transaction-Level Advisory Lock（事务级建议锁），在 COMMIT 或 ROLLBACK 后自动释放。

### 【Ingestion 用 Advisory Lock 保护事件去重和写入】

当前 IngestionService 先在一个 Request 内去重：

~~~ts
const seenEventIds = new Set<string>();
const uniqueValid = valid.filter((event) => {
  if (seenEventIds.has(event.eventId)) return false;
  seenEventIds.add(event.eventId);
  return true;
});
~~~

然后进入数据库 Transaction：

~~~ts
await client.query('BEGIN');
const eventIds = uniqueValid.map((event) => event.eventId).sort();
~~~

接着对每个 eventId 建立事务级 Advisory Lock，再查询数据库中是否已经存在：

~~~sql
SELECT event_id
FROM telemetry_events
WHERE project_id = $1
AND event_id = ANY($2::text[])
GROUP BY event_id
~~~

完整关系：

~~~text
BEGIN
↓
锁定 project + eventId
↓
查询已经存在的 Event
↓
过滤 Duplicate
↓
写 telemetry_events
↓
写 outbox_tasks
↓
COMMIT
↓
自动释放 Advisory Lock
~~~

它解决的是典型 Check-Then-Act Race（先检查再操作的竞态）。

如果没有并发保护：

~~~text
Request A 检查：不存在
Request B 检查：不存在
↓
A 准备 INSERT
B 也准备 INSERT
~~~

两个 Request 都基于旧状态做出同一个决定。

因此：

~~~text
检查
+
决定
+
写入
~~~

需要位于同一个受保护的并发区间中。

### 【统一的加锁顺序用于降低 Deadlock（死锁）风险】

当前 Ingestion：

~~~ts
const eventIds = uniqueValid.map((event) => event.eventId).sort();
~~~

并在 SQL 中继续 ORDER BY event_id。

原因是让所有 Transaction 按相同顺序获得多个锁。

假设：

~~~text
Transaction A
先锁 event-1
再锁 event-2

Transaction B
先锁 event-2
再锁 event-1
~~~

可能形成：

~~~text
A 拿着 event-1
等待 event-2

B 拿着 event-2
等待 event-1
~~~

双方互相等待，就是 Deadlock（死锁）。

PostgreSQL 能检测 Deadlock，并终止其中一个 Transaction，但工程上仍应该尽量减少 Deadlock。

当前项目统一：

~~~text
所有 eventId 先排序
↓
所有 Transaction 按同一顺序申请 Lock
~~~

例如：

~~~text
A 输入：event-3,event-1,event-2
↓
event-1,event-2,event-3

B 输入：event-2,event-3,event-1
↓
event-1,event-2,event-3
~~~

都按：

~~~text
1 → 2 → 3
~~~

取得 Lock，可以明显降低循环等待风险。

因此 Transaction 设计还要继续考虑：

~~~text
事务会锁哪些资源？
多个资源按什么顺序加锁？
Lock 持续多久？
冲突以后是等待还是失败？
~~~

---

### 【Durability（持久性）保证 COMMIT 后的数据能够面对故障恢复】

Durability（持久性）回答：

~~~text
PostgreSQL 已经告诉 Application
COMMIT 成功

如果数据库进程随后崩溃
已经提交的数据还能不能恢复？
~~~

事务不仅需要：

~~~text
多个 SQL 一起成功
~~~

还要求：

~~~text
已经成功 COMMIT 的数据
不能因为普通数据库进程崩溃直接消失
~~~

PostgreSQL 在这一层会继续涉及：

~~~text
WAL（Write-Ahead Logging，预写日志）
Checkpoint（检查点）
Crash Recovery（崩溃恢复）
~~~

当前 Transaction 阶段不深入 WAL 内部结构，只先建立关系：

~~~text
Transaction
↓
COMMIT
↓
数据库确认已提交
↓
WAL / 持久化机制
↓
故障后恢复已提交状态
~~~

因此 ACID 可以放回四类问题：

~~~text
Atomicity
一次事务不能只成功一部分

Consistency
最终状态仍满足系统规则

Isolation
并发 Transaction 如何互相观察和冲突

Durability
已经 COMMIT 的数据如何可靠保存
~~~

### 【Outbox 展示事务如何同时保存业务事实和后台任务】

当前 Ingestion 不仅需要写：

~~~text
telemetry_events
~~~

还需要写：

~~~text
outbox_tasks
~~~

因为：

~~~text
telemetry_events
表示 Event 已经被服务端可靠接收

outbox_tasks
表示 Event 后续还需要 Worker 处理
~~~

如果分别提交：

~~~text
INSERT telemetry_events
↓
COMMIT
↓
服务异常
↓
INSERT outbox_tasks 没执行
~~~

会产生：

~~~text
Event 已经存在
↓
但是没有 Worker Task
↓
Event 永远不会进入后续 Projection
~~~

当前源码通过 CTE 把已经真正插入的 telemetry_events 继续写入 outbox_tasks，并把整个操作放在同一个 Transaction 中。

核心关系：

~~~text
BEGIN
↓
telemetry_events
+
outbox_tasks
↓
COMMIT
~~~

这就是 Transactional Outbox（事务型发件箱 / 事务任务表）的核心：

> 把业务事实和需要异步处理的任务记录放进同一个数据库 Transaction，避免业务数据已经成功但后台任务没有产生。

当前 Ingestion 链路：

~~~text
SDK Event
↓
BEGIN
↓
Advisory Lock
↓
检查 Duplicate
↓
INSERT telemetry_events
↓
INSERT outbox_tasks
↓
UPDATE ingestion_keys.last_used_at
↓
COMMIT
↓
Worker 后续读取 Outbox
~~~

### 【PostgreSQL Transaction 不能自动覆盖 Redis 和外部系统】

Transaction 有明确系统边界。

当前 Ingestion 在 PostgreSQL COMMIT 后才执行 Redis 统计：

~~~text
PostgreSQL Transaction
↓
COMMIT
↓
Redis multi()
↓
更新 Dashboard Counter / Receive Rate
~~~

PostgreSQL Transaction 只能直接保证 PostgreSQL 内的数据操作。

它不能自动把：

~~~text
PostgreSQL
+
Redis
~~~

变成同一个本地事务。

同样不能自动覆盖：

~~~text
PostgreSQL
+
Mailer
~~~

或者：

~~~text
PostgreSQL
+
第三方 HTTP API
~~~

例如：

~~~text
PostgreSQL COMMIT 成功
↓
Redis 更新失败
~~~

此时不能再普通地 ROLLBACK PostgreSQL，因为 PostgreSQL Transaction 已经结束，而且 Redis 本来就不属于这个 Transaction。

因此需要区分：

~~~text
Local Transaction（本地事务）
一个数据库系统内部的事务

Cross-System Consistency（跨系统一致性）
多个独立系统之间如何保持状态协调
~~~

当前 Browser Monitor 的设计是：

~~~text
PostgreSQL
保存核心业务事实
↓
必须可靠

Redis
保存统计、缓存版本等辅助状态
↓
允许短时间不同步
↓
后续可以重新计算或刷新
~~~

这属于 Eventual Consistency（最终一致性）：不要求所有系统每一个瞬间都完全一致，但经过后续更新、重试或重新计算后最终达到一致状态。

### 【外部网络调用通常不应该长时间放在数据库事务内部】

当前 AuthService.register()：

~~~text
BEGIN
↓
写 users
↓
旧 Verification Token 失效
↓
创建新 Verification Token
↓
COMMIT
↓
release Connection
↓
sendVerification()
~~~

Mailer 在 COMMIT 之后调用。

如果写成：

~~~text
BEGIN
↓
数据库修改
↓
调用 Mail Server
↓
等待网络响应
↓
COMMIT
~~~

那么网络调用期间：

~~~text
Database Connection 一直被占用
+
相关 Lock 一直不释放
+
Transaction 一直保持打开
~~~

网络请求又可能发生延迟、超时和重试，因此会把一个原本很短的数据库事务拉长。

正确原则是：

~~~text
Transaction Boundary
只覆盖必须共同保证的数据操作
~~~

而不是：

~~~text
整个 Service 方法
全部放进 Transaction
~~~

### 【Long Transaction（长事务）会扩大 Lock 和 Connection 占用问题】

假设：

~~~text
BEGIN
↓
SELECT Invitation FOR UPDATE
↓
复杂计算 5 秒
↓
HTTP 调用 3 秒
↓
COMMIT
~~~

那么：

~~~text
Row Lock
Database Connection
Transaction State
~~~

都会被长时间持有。

大量长事务可能形成：

~~~text
Lock 等待增加
↓
Connection 长时间被占用
↓
Pool 可用 Connection 减少
↓
请求排队
↓
响应时间继续上升
~~~

所以：

~~~text
Transaction 越长
≠
越安全
~~~

更合理的是：

~~~text
Transaction 开始前
完成普通计算和参数准备
↓
BEGIN
↓
快速读取和修改需要保护的数据
↓
COMMIT
↓
Transaction 结束后
再执行可以独立完成的外部操作
~~~

当前 ProjectsService.create() 也是先生成 publicKey、userHashSalt、defaultOrigin，再取得 Client 和 BEGIN。

### 【EventProcessor 展示 Projection 与 processed 状态为什么需要共同提交】

当前：

~~~text
browser-monitor/platform/apps/worker/src/processor.ts
~~~

事务结构：

~~~text
BEGIN
↓
根据 Event 类型写入 Projection
performance_samples
或 view_records
或 custom_signal_samples
↓
UPDATE telemetry_events.processed_at
↓
COMMIT
~~~

这里共同保护：

~~~text
Projection 已经产生
+
原始 telemetry_event 已经 processed
~~~

因为两者描述的是同一个处理事实。

如果 Projection 成功，但是更新 processed_at 失败：

~~~text
ROLLBACK
~~~

会把这一轮数据库处理整体撤销。

### 【Worker 整体可靠性不能只依赖一个超大事务】

OutboxWorker.handle() 的链路：

~~~text
processor.process()
↓
Projection Transaction COMMIT
↓
UPDATE outbox_tasks → completed
↓
Redis analytics version +1
~~~

Projection Transaction 和 Outbox completed 并不属于同一个大 Transaction。

因此可能存在：

~~~text
Projection 已经 COMMIT
↓
进程突然退出
↓
Outbox 仍然 processing
~~~

之后 stale task 会被重新领取。

这说明：

~~~text
Transaction
不能解决整个异步系统中的所有可靠性问题
~~~

系统还需要：

~~~text
Retry（重试）
+
Idempotency（幂等）
~~~

Idempotency 可以理解为：

> 同一个任务因为故障被重新执行多次时，最终结果仍然应该与正确执行一次一致，而不是不断制造重复结果。

当前 Processor 中的：

~~~text
ON CONFLICT DO NOTHING
Sequence 检查
FOR UPDATE
Advisory Lock
~~~

都在帮助重复执行和并发执行最终收敛到正确状态。

所以完整可靠性链路是：

~~~text
Transaction
保证一次局部数据库修改完整

Outbox
保证任务不会因为 API 与 Worker 分离而直接丢失

Retry
处理临时失败

Idempotency
处理重复执行

Lock
处理并发冲突
~~~

### 【Worker Claim 展示单条 SQL 也可以完成完整原子操作】

当前 OutboxWorker.claim() 没有显式写 BEGIN，而是直接执行：

~~~sql
WITH candidates AS (
  SELECT id FROM outbox_tasks
  WHERE (
    status = 'pending' AND available_at <= now()
  ) OR (
    status = 'processing' AND locked_at < now() - INTERVAL '5 minutes'
  )
  ORDER BY available_at, created_at
  LIMIT $1
  FOR UPDATE SKIP LOCKED
)
UPDATE outbox_tasks o SET
  status = 'processing',
  locked_at = now(),
  locked_by = $2,
  attempts = attempts + 1
FROM candidates c
WHERE o.id = c.id
RETURNING o.id, o.project_id, o.event_id, o.event, o.attempts;
~~~

这一整条 SQL 本身运行在一个隐式 Transaction 中。

它一次完成：

~~~text
查找候选 Task
↓
锁定候选 Row
↓
修改为 processing
↓
记录 locked_by
↓
attempts + 1
↓
返回已经领取的 Task
~~~

FOR UPDATE SKIP LOCKED 表示：

~~~text
如果候选 Row 已经被其他 Worker 锁住
↓
不等待这个 Row
↓
直接跳过
↓
继续领取其他 Task
~~~

所以多个 Worker 可以并行领取不同任务。

这里也说明：

~~~text
能够在一条原子 SQL 中完成的事情
不一定需要人为写一个更长的显式 Transaction
~~~

### 【Dead Letter Transaction 保证任务失败状态完整迁移】

当前 Worker 达到最大重试次数：

~~~text
attempts >= 8
~~~

执行：

~~~text
BEGIN
↓
INSERT / UPDATE dead_letter_tasks
↓
UPDATE outbox_tasks
status = failed
↓
COMMIT
~~~

两个变化共同表达：

~~~text
普通 Outbox Task
↓
多次失败
↓
Dead Letter
~~~

如果 Dead Letter 写入成功，但 Outbox 仍然 processing：

~~~text
任务已经进入失败记录
+
仍可能继续被普通 Worker 消费
~~~

反过来，如果 Outbox 已经 failed，但没有 Dead Letter：

~~~text
后续排查和人工 Retry
缺少失败任务记录
~~~

所以这里也需要清晰的 Transaction Boundary。

### 【Transaction Retry 通常需要重新执行整个业务事务】

Transaction 可能因为：

~~~text
Deadlock
Serialization Failure
Connection Failure
~~~

失败。

如果失败原因允许 Retry，通常不能简单：

~~~text
最后一条 SQL 失败
↓
只重新执行最后一条 SQL
~~~

例如：

~~~text
BEGIN
↓
读取 Version = 3
↓
计算 nextVersion = 4
↓
准备 INSERT Version 4
↓
出现并发冲突
~~~

重试时另一个 Transaction 可能已经：

~~~text
COMMIT Version 4
~~~

最新状态已经发生变化。

所以 Retry 通常应该：

~~~text
重新 BEGIN
↓
重新读取最新状态
↓
重新计算
↓
重新执行整个业务 Transaction
~~~

事务逻辑因此应该尽量保持：

~~~text
边界清楚
输入清楚
可以重新执行
~~~

### 【updateThresholds 展示 Atomicity 和并发正确性是两个问题】

当前 updateThresholds()：

~~~text
BEGIN
↓
旧 threshold_versions.active = false
↓
计算 max(version) + 1
↓
INSERT 新 Version
active = true
↓
COMMIT
~~~

Transaction 可以保证：

~~~text
旧 Version 失活
+
新 Version 创建
~~~

不会只完成一半。

这是 Atomicity。

但两个 Request 同时执行时，两边都有可能先得到：

~~~text
max(version) = 3
~~~

都尝试：

~~~text
version = 4
~~~

数据库还存在：

~~~text
UNIQUE(project_id, version)
~~~

以及每个 Project 只有一个 active Version 的唯一约束。

因此其中一个 Transaction 可能因为 Constraint Conflict（约束冲突）失败。

这不是 Transaction 失效，而是：

~~~text
Transaction
保证失败不留下半套状态

Unique Constraint
阻止非法并发结果提交

Application
决定冲突后返回错误还是 Retry
~~~

所以看到 BEGIN / COMMIT 后，还要继续判断：

~~~text
是否存在并发读改写？
是否存在唯一性竞争？
是否需要 FOR UPDATE？
是否需要 Advisory Lock？
是否需要更高 Isolation？
是否需要 Retry？
~~~

### 【Drizzle Transaction 是 PostgreSQL Transaction 的更高层封装】

当前 DatabaseHandle：

~~~ts
export interface DatabaseHandle {
  pool: Pool;
  db: NodePgDatabase<typeof schema>;
  close(): Promise<void>;
}
~~~

项目同时拥有：

~~~text
database.pool
↓
node-postgres
↓
Raw SQL

database.db
↓
Drizzle
↓
Query Builder / ORM API
~~~

当前复杂事务大量使用 pool.connect() + Raw SQL，因为源码使用了：

~~~text
FOR UPDATE
SKIP LOCKED
CTE
pg_advisory_xact_lock
jsonb_to_recordset
RETURNING
~~~

这些 PostgreSQL 具体能力。

Drizzle 也提供：

~~~ts
await this.database.db.transaction(async (tx) => {
  await tx.insert(projects).values(...);
  await tx.insert(projectMembers).values(...);
});
~~~

它帮助应用管理：

~~~text
BEGIN
↓
tx 中执行 Query
↓
成功 → COMMIT
异常 → ROLLBACK
~~~

所以：

~~~text
pg Transaction
~~~

和：

~~~text
Drizzle Transaction
~~~

不是两种不同的数据库事务。

真正关系是：

~~~text
Application
├── node-postgres Client
│   ↓
│   BEGIN / COMMIT / ROLLBACK
│
└── Drizzle Transaction API
    ↓
    Transaction Abstraction
    ↓
PostgreSQL Transaction
~~~

最终真正实现事务语义的仍然是 PostgreSQL。

### 【Migration 也需要 Transaction 保证结构修改与迁移记录一致】

当前：

~~~text
browser-monitor/platform/packages/database/src/migrate.ts
~~~

执行：

~~~ts
await client.query('BEGIN');
await client.query(sql);
await client.query(
  'INSERT INTO monitor_schema_migrations(name) VALUES ($1)',
  [name],
);
await client.query('COMMIT');
~~~

它共同保证：

~~~text
Migration SQL 已经真正执行
+
monitor_schema_migrations 已经记录
~~~

如果 Migration SQL 失败：

~~~text
ROLLBACK
~~~

就不会错误留下：

~~~text
Migration 已应用
~~~

的记录。

否则下一次启动可能因为看到 Migration Record 而错误跳过实际上没有完成的结构变更。

所以 Transaction 不只用于普通 CRUD，而适用于任何：

~~~text
多个数据库事实
必须作为同一个状态变化
~~~

的场景。

### 【Transaction 在完整数据管理体系中连接业务正确性与并发控制】

到这里，前面的数据库知识可以连接成：

~~~text
业务操作
↓
SQL
↓
Table / Row
↓
Constraint
保证单条数据和关系合法
↓
Index
提供高效访问路径
↓
Transaction
组织多个数据修改
↓
Isolation
控制并发 Transaction 的可见性
↓
Row Lock / Advisory Lock
保护具体冲突资源
↓
COMMIT / ROLLBACK
确定 Transaction 最终结果
↓
WAL / Recovery
保证已提交结果可以恢复
~~~

Transaction 本身不能替代：

~~~text
Constraint
Index
Lock
Retry
Idempotency
Outbox
WAL
~~~

这些机制解决不同层次的问题。

例如当前 Ingestion 的完整可靠性链路不是：

~~~text
用了 Transaction
↓
数据一定正确
~~~

而是：

~~~text
Protocol Validation
↓
业务校验
↓
Request 内 eventId 去重
↓
BEGIN
↓
Advisory Lock
↓
数据库重复检查
↓
Constraint / ON CONFLICT
↓
telemetry_events + outbox_tasks
↓
COMMIT
↓
Worker Claim
↓
Worker Transaction
↓
Idempotent Projection
↓
Retry / Dead Letter
~~~

Transaction 负责解决其中：

~~~text
一次数据库状态变化
不能只完成一部分
~~~

接下来进入 Concurrency Control（并发控制）和 MVCC 时，重点会从：

~~~text
一个 Transaction 内部
如何保证完整执行
~~~

进一步转向：

~~~text
多个 Transaction 同时执行时
PostgreSQL 如何通过 MVCC、Snapshot、Row Version、Lock 和 Isolation Level
决定每个 Transaction 看见什么、等待什么，以及什么时候必须失败重试
~~~

这也是 Transaction 之后继续进入数据库并发体系的自然连接点。
