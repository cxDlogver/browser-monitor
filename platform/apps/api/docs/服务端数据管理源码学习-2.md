# 服务端数据管理源码学习-2

## 7. Transaction（事务）把多个数据库操作组织成一个可靠的业务执行单元

前面的数据管理部分已经依次建立了 Database、Connection、SQL、Schema、Constraint、Index 等基础能力。到这里，应用已经能够把业务事实保存到 PostgreSQL 中，并通过约束保证单条数据和数据关系合法，通过 Index 为常见 Query 提供更高效的访问路径。

但是这些能力仍然没有解决一个非常重要的问题：

> 一次真实业务操作通常不是执行一条 SQL，而是需要连续修改多张表、多个 Row。即使每一条 SQL 单独执行都没有问题，也可能因为中间某一步失败，使数据库停留在一个业务上不完整的状态。

例如 Browser Monitor 创建一个 Project 时，需要同时完成：

~~~text
创建 projects
↓
创建 project_members
↓
创建 ingestion_keys
↓
创建 allowed_origins
↓
记录 audit_logs
~~~

这些修改共同表达一个完整业务事实：

~~~text
一个完整可使用的 Project 已经创建
~~~

如果没有 Transaction（事务），可能出现：

~~~text
projects               已创建
project_members        已创建
ingestion_keys         创建失败
allowed_origins        尚未执行
audit_logs             尚未执行
~~~

从数据库角度看，前两条 INSERT 可能都完全合法。

但从业务角度看，此时已经产生了不完整的 Project：

~~~text
Project 存在
Owner 存在
但是没有 Ingestion Key
也没有默认 Allowed Origin
~~~

所以数据管理不能只关注：

~~~text
一条 SQL 能不能成功
~~~

还必须继续关注：

~~~text
一组共同描述业务状态变化的 SQL
能不能作为一个整体成功
~~~

Transaction（事务）就是用来解决这一层问题的。

PostgreSQL 官方把事务描述为：将多个步骤组合成一个整体，从其他并发事务的角度看，这组操作要么全部发生，要么完全不发生；事务执行过程中产生的中间状态不会作为已经提交的数据库状态暴露出去。

---

### 【Transaction 的核心不是“多条 SQL”，而是“一个业务状态变化”】

#### <u>1. Transaction Boundary（事务边界）决定哪些操作必须共同成功</u>

Transaction Boundary（事务边界）表示：

> 一个事务从哪里开始、在哪里结束，以及哪些数据库操作必须共同 COMMIT（提交）或者共同 ROLLBACK（回滚）。

事务设计首先不能简单理解为：

~~~text
有多条 SQL
↓
所以一定使用 Transaction
~~~

例如：

~~~text
查询 Project
查询 Project Members
查询 Threshold
~~~

虽然执行了多条 SELECT，但如果它们只是几个独立读取，不要求形成同一个时间点上的一致视图，那么未必需要主动建立显式 Transaction。

反过来，有些操作虽然 SQL 数量不多，却天然属于一个业务事务。

例如接受 Invitation：

~~~text
创建 / 更新 project_members
+
把 project_invitations.accepted_at 标记为已接受
~~~

如果只完成第一步：

~~~text
User 已经成为 Project Member
但是 Invitation 仍然显示未接受
~~~

业务状态就出现矛盾。

因此判断事务边界真正应该问的是：

~~~text
这几次数据变化
是否共同表达同一个业务状态变化？
↓
如果只成功其中一部分
数据库是否会进入一个业务上错误的中间状态？
↓
如果答案是“会”
这些操作就应该考虑放在同一个 Transaction Boundary 中
~~~

#### <u>2. ProjectsService.create() 是最直接的事务边界示例</u>

当前源码位于：

~~~text
browser-monitor/platform/apps/api/src/projects/projects.service.ts
~~~

核心代码：

~~~ts
const client = await this.database.pool.connect();
try {
  await client.query('BEGIN');
  const project = await client.query<{ id: string }>(
    'INSERT INTO projects(display_name, app_name, user_hash_salt) VALUES ($1, $2, $3) RETURNING id',
    [displayName.trim(), appName.trim(), userHashSalt],
  );
  const projectId = project.rows[0]!.id;
  await client.query(
    "INSERT INTO project_members(project_id, user_id, role) VALUES ($1, $2, 'owner')",
    [projectId, userId],
  );
  await client.query(
    "INSERT INTO ingestion_keys(project_id, public_key, label) VALUES ($1, $2, 'default')",
    [projectId, publicKey],
  );
  await client.query(
    'INSERT INTO allowed_origins(project_id, origin) VALUES ($1, $2)',
    [projectId, defaultOrigin],
  );
  await client.query(
    "INSERT INTO audit_logs(project_id, actor_user_id, action, detail) VALUES ($1, $2, 'project.created', jsonb_build_object('appName', $3::text))",
    [projectId, userId, appName.trim()],
  );
  await client.query('COMMIT');
} catch (error) {
  await client.query('ROLLBACK');
  throw error;
} finally {
  client.release();
}
~~~

这里的逻辑不是：

~~~text
因为有五条 SQL
所以套一个 BEGIN / COMMIT
~~~

而是：

~~~text
Project
+
Owner Membership
+
Default Ingestion Key
+
Default Allowed Origin
+
Audit Log
~~~

共同定义：

~~~text
Project 创建完成
~~~

因此整个 create() 内真正需要被数据库原子保护的是：

~~~text
BEGIN
↓
创建 Project
↓
创建 Owner Membership
↓
创建 Ingestion Key
↓
创建 Allowed Origin
↓
创建 Audit Log
↓
COMMIT
~~~

如果其中任何一步失败：

~~~text
ROLLBACK
~~~

恢复到事务开始之前的数据库状态。

这就是事务边界与业务边界的直接对应。

### 【PostgreSQL 中每一条 SQL 本身也运行在 Transaction 中】

#### <u>1. 没有显式 BEGIN 不代表没有 Transaction</u>

例如：

~~~sql
UPDATE projects
SET enabled = false
WHERE id = $1;
~~~

应用虽然没有写：

~~~sql
BEGIN;
~~~

这条 SQL 仍然运行在一个数据库事务中。

PostgreSQL 会表现得像：

~~~text
隐式开始 Transaction
↓
执行 UPDATE
↓
执行成功
↓
自动 COMMIT
~~~

这种使用方式通常称为 Autocommit（自动提交）。

所以：

~~~text
没有手写 BEGIN
≠
数据库没有 Transaction
~~~

更准确的是：

~~~text
普通单条 SQL
↓
数据库自动建立事务范围
↓
SQL 成功后自动提交
~~~

#### <u>2. Explicit Transaction（显式事务）让多条 SQL 共用同一个事务</u>

当业务需要：

~~~text
SQL 1
SQL 2
SQL 3
~~~

共同成功时，才需要显式：

~~~sql
BEGIN;
SQL 1;
SQL 2;
SQL 3;
COMMIT;
~~~

因此单条 SQL 和多条 SQL 的区别可以理解成：

~~~text
单条 SQL
↓
数据库自动管理一个很短的 Transaction

多条 SQL 共同组成一个业务操作
↓
应用显式控制 Transaction Boundary
~~~

这也解释了为什么当前项目中很多简单 UPDATE / DELETE 直接使用：

~~~ts
this.database.pool.query(...)
~~~

而复杂业务状态变化会先：

~~~ts
const client = await this.database.pool.connect();
await client.query('BEGIN');
~~~

---

### 【BEGIN、COMMIT 与 ROLLBACK 控制 Transaction 生命周期】

#### <u>1. BEGIN 表示从这里开始进入同一个事务范围</u>

~~~sql
BEGIN;
~~~

执行后：

~~~text
后续 SQL
↓
进入当前 Transaction
~~~

直到：

~~~text
COMMIT
或者
ROLLBACK
~~~

事务才真正结束。

#### <u>2. SQL 在 COMMIT 前已经执行，不是等 COMMIT 才开始执行</u>

这是事务最容易产生误解的地方之一。

错误理解：

~~~text
BEGIN
↓
SQL 1
SQL 2
SQL 3
↓
这些 SQL 只是被“记下来”
↓
COMMIT
↓
数据库才真正执行 SQL
~~~

实际不是这样。

例如：

~~~sql
BEGIN;
UPDATE projects
SET enabled = false
WHERE id = 'project-a';
SELECT enabled
FROM projects
WHERE id = 'project-a';
~~~

当前 Transaction 自己已经可以读取到：

~~~text
enabled = false
~~~

说明前面的 UPDATE 已经真正执行。

只是这个修改：

~~~text
尚未 COMMIT
↓
没有成为其他 Transaction 可以按照已提交规则观察到的最终状态
~~~

因此正确模型是：

~~~text
BEGIN
↓
SQL 真正执行
↓
当前 Transaction 内部状态发生变化
↓
后续 SQL 可以继续基于这个新状态执行
↓
COMMIT
↓
整个 Transaction 成为已提交状态
~~~

#### <u>3. COMMIT 确认当前事务最终成功</u>

~~~sql
COMMIT;
~~~

表示：

~~~text
当前 Transaction 正常结束
↓
其中所有修改共同成为已提交数据
~~~

所以 COMMIT 的意义不是“执行 SQL”，而是：

~~~text
确认这个 Transaction 的整体结果
~~~

#### <u>4. ROLLBACK 放弃当前事务产生的修改</u>

假设：

~~~text
BEGIN
↓
SQL 1 成功
↓
SQL 2 成功
↓
SQL 3 失败
~~~

如果业务要求三条 SQL 共同成功，就应该：

~~~sql
ROLLBACK;
~~~

最终数据库不会留下：

~~~text
SQL 1 的业务修改
SQL 2 的业务修改
但 SQL 3 没有完成
~~~

而是放弃这个 Transaction 的整体修改。

当前项目中的经典结构：

~~~ts
try {
  await client.query('BEGIN');
  await client.query(sql1);
  await client.query(sql2);
  await client.query('COMMIT');
} catch (error) {
  await client.query('ROLLBACK');
  throw error;
} finally {
  client.release();
}
~~~

这里的 catch 并不只是 JavaScript 异常处理习惯。

它和 PostgreSQL Transaction 状态直接相关。

当 Transaction 中某条 SQL 发生错误以后，PostgreSQL 通常会把当前事务标记为失败状态。之后不能假装什么都没发生继续正常 COMMIT，而应该 ROLLBACK 当前事务，结束失败状态。

---

### 【SAVEPOINT 允许在一个 Transaction 内部建立局部回滚点】

完整事务体系中还有一个重要概念：

SAVEPOINT（保存点）。

假设一个较长 Transaction 中，希望：

~~~text
前面的操作保留
只撤销中间某一小段
~~~

可以：

~~~sql
BEGIN;
INSERT INTO projects(...);
SAVEPOINT before_member;
INSERT INTO project_members(...);
ROLLBACK TO before_member;
INSERT INTO project_members(...);
COMMIT;
~~~

这里：

~~~sql
ROLLBACK TO before_member;
~~~

不会结束整个 Transaction。

它只把：

~~~text
SAVEPOINT before_member
之后产生的修改
~~~

撤销。

因此可以区分：

~~~text
ROLLBACK
↓
结束整个 Transaction

ROLLBACK TO SAVEPOINT
↓
只回到 Transaction 内部某个保存点
~~~

当前 Browser Monitor 没有直接使用 SAVEPOINT，但它是事务完整知识体系的一部分。

Drizzle 的 Nested Transaction（嵌套事务）能力，本质上通常也是通过数据库 Savepoint 这一类机制实现，而不是创建真正独立的第二个 PostgreSQL 顶层事务。

### 【一个 Transaction 必须始终绑定同一个 Database Connection】

#### <u>1. Connection Pool 中同时存在多个 PostgreSQL Connection</u>

当前项目数据库初始化位于：

~~~text
browser-monitor/platform/packages/database/src/client.ts
~~~

源码：

~~~ts
const pool = new Pool({
  connectionString,
  max: 20,
  idleTimeoutMillis: 30_000,
  connectionTimeoutMillis: 5_000,
});
~~~

Pool（Connection Pool，连接池）不是一个单独 Connection。

更准确地理解：

~~~text
Application
↓
Pool
├── Connection A
├── Connection B
├── Connection C
├── ...
└── 最多到 max
↓
PostgreSQL
~~~

普通单条 SQL：

~~~ts
await pool.query(sql);
~~~

只需要：

~~~text
Pool 找一个可用 Connection
↓
执行这条 SQL
↓
执行完成
~~~

但 Transaction 不一样。

Transaction 的：

~~~text
BEGIN
SQL 1
SQL 2
SQL 3
COMMIT
~~~

全部必须发生在：

~~~text
同一个 PostgreSQL Connection
~~~

上。

#### <u>2. pool.connect() 的作用是为事务拿到一个固定 Client</u>

当前项目事务统一先：

~~~ts
const client = await this.database.pool.connect();
~~~

这里的 Client 可以理解为：

~~~text
从 Pool 中临时借出的固定 Connection
~~~

然后整个 Transaction 都通过它执行：

~~~ts
await client.query('BEGIN');
await client.query(sql1);
await client.query(sql2);
await client.query(sql3);
await client.query('COMMIT');
~~~

因此真正结构是：

~~~text
Pool
↓
pool.connect()
↓
Client A / Connection A
├── BEGIN
├── SQL 1
├── SQL 2
├── SQL 3
└── COMMIT
↓
client.release()
↓
Connection A 返回 Pool
~~~

#### <u>3. 不能用多个 pool.query() 拼接一个事务</u>

错误代码：

~~~ts
await pool.query('BEGIN');
await pool.query(sql1);
await pool.query(sql2);
await pool.query('COMMIT');
~~~

问题在于：

~~~text
pool.query()
每次都由 Pool 自己选择可用 Connection
~~~

于是可能真实执行成：

~~~text
BEGIN  → Connection A
SQL 1  → Connection C
SQL 2  → Connection B
COMMIT → Connection A
~~~

虽然代码顺序看起来像一个 Transaction，但数据库层实际不是同一个 Connection。

node-postgres 官方专门强调：一个 Transaction 中的所有 Statement（语句）必须使用同一个 Client，不能用 pool.query() 来组织 Transaction。

#### <u>4. finally 中的 client.release() 防止连接泄漏</u>

当前项目：

~~~ts
finally {
  client.release();
}
~~~

无论：

~~~text
COMMIT 成功
ROLLBACK
业务抛异常
数据库报错
~~~

最终都要尽可能把 Connection 归还 Pool。

如果持续：

~~~text
pool.connect()
↓
没有 release
~~~

会逐步形成：

~~~text
Connection A 被占用
Connection B 被占用
Connection C 被占用
...
↓
Pool 中没有可用 Connection
↓
新 Request 开始等待
↓
数据库访问延迟持续增加
~~~

所以：

~~~text
Transaction 生命周期
和
Connection 生命周期
~~~

在 node-postgres 的手动事务代码中必须一起管理。

### 【ACID 不是四句定义，而是 Transaction 需要解决的四类问题】

ACID 分别是：

~~~text
Atomicity
Consistency
Isolation
Durability
~~~

如果只背：

~~~text
原子性
一致性
隔离性
持久性
~~~

很容易把它们混在一起。

更有用的方式是分别问：

~~~text
Atomicity
一次业务操作会不会只完成一部分？

Consistency
事务结束后数据是否仍满足系统规则？

Isolation
多个 Transaction 同时执行时互相能看到什么、会不会冲突？

Durability
COMMIT 已经成功的数据，数据库崩溃后能不能恢复？
~~~

---

### 【Atomicity（原子性）保证 Transaction 不会停留在“只成功一半”】

Atomicity 表示：

> 一个 Transaction 中的数据库修改，对外表现为不可拆分的整体：要么共同 COMMIT，要么共同 ROLLBACK。

当前 Project Create 可以画成：

~~~text
完整 Project
├── projects
├── project_members
├── ingestion_keys
├── allowed_origins
└── audit_logs
~~~

如果没有 Atomicity：

~~~text
projects               成功
project_members        成功
ingestion_keys         失败
allowed_origins        未执行
audit_logs             未执行
~~~

业务层可能得到一个半成品 Project。

有 Transaction 后：

~~~text
BEGIN
↓
Project
↓
Member
↓
Key
↓
Origin
↓
Audit
↓
全部成功
↓
COMMIT
~~~

或者：

~~~text
BEGIN
↓
Project
↓
Member
↓
Key 失败
↓
ROLLBACK
~~~

最终不会把前两步保留下来。

#### <u>1. replaceOrigins() 说明 Atomicity 不是只用于“创建”</u>

当前 replaceOrigins()：

~~~text
BEGIN
↓
DELETE 当前 Project 的旧 Origins
↓
逐个 INSERT 新 Origins
↓
INSERT Audit Log
↓
COMMIT
~~~

如果没有 Transaction：

~~~text
DELETE 成功
↓
旧 Origins 已经全部删除
↓
第二个 INSERT 失败
~~~

Project 可能突然失去全部合法 Origin 配置。

所以业务上真正的原子操作是：

~~~text
把旧 Origin 集合
整体替换成新 Origin 集合
~~~

而不是：

~~~text
DELETE 是一个操作
INSERT 1 是一个操作
INSERT 2 是一个操作
~~~

#### <u>2. rotateKey() 说明状态迁移也需要 Atomicity</u>

当前 rotateKey()：

~~~text
BEGIN
↓
现有 active Key
设置 expires_at = now() + 24 hours
↓
INSERT 新 Key
↓
INSERT Audit Log
↓
COMMIT
~~~

业务想表达：

~~~text
开始从旧 Key 向新 Key 过渡
~~~

如果只完成：

~~~text
旧 Key 开始过期
~~~

而：

~~~text
新 Key 创建失败
~~~

就可能让系统进入错误过渡状态。

所以 Atomicity 保护的是：

~~~text
一个完整状态迁移
~~~

而不仅仅是“几条 INSERT”。

#### <u>3. retryDeadLetter() 说明不同 Table 之间也可以是一个原子状态变化</u>

当前 retryDeadLetter()：

~~~text
BEGIN
↓
DELETE dead_letter_tasks
↓
UPDATE outbox_tasks
status = pending
attempts = 0
available_at = now()
↓
COMMIT
~~~

业务语义：

~~~text
这个 Task 从 Dead Letter
重新回到可执行 Outbox
~~~

如果只 DELETE Dead Letter，却没有恢复 Outbox：

~~~text
失败任务记录消失
任务又没有回到正常队列
~~~

所以这两个 Table 的变化必须共同提交。

---

### 【Consistency（一致性）不是 Transaction 自动理解业务，而是多种机制共同维护合法状态】

Consistency 可以理解成：

> 数据库从一个合法状态变化到另一个合法状态，最终仍满足数据库约束和业务规则。

这里最容易出现一个误区：

~~~text
有 Transaction
↓
数据库一定 Consistent
~~~

这并不完整。

例如：

~~~text
project_members.project_id
必须引用真实 Project
~~~

依赖的是：

~~~text
Foreign Key Constraint
~~~

再例如：

~~~text
同一个 Project + Version
不能重复
~~~

依赖：

~~~text
UNIQUE Constraint / Unique Index
~~~

再例如：

~~~text
一个 Project 创建完成时
必须具有 Owner、Default Key、Default Origin
~~~

这部分规则属于：

~~~text
Application Business Logic
~~~

PostgreSQL 并不知道：

~~~text
“没有 Default Origin 的 Project 在业务上不能算创建完成”
~~~

除非应用或数据库结构专门把这条业务规则表达出来。

因此完整关系是：

~~~text
Business Logic
+
Schema
+
Constraint
+
Transaction
+
Concurrency Control
↓
共同维持 Consistency
~~~

Transaction 的作用是：

~~~text
如果应用决定 A、B、C 必须共同变化
↓
数据库提供机制让 A、B、C 一起提交或回滚
~~~

但 Transaction 不会自动判断：

~~~text
你的业务规则是不是写对了
金额是不是算错了
权限是不是判断错了
状态机是不是设计错了
~~~

这也是 ACID 中 Consistency 最容易被过度简化的地方。

---

### 【Isolation（隔离性）解决多个 Transaction 同时执行时的数据可见性和冲突】

到目前为止，所有例子都像：

~~~text
一个 Request
↓
一个 Transaction
↓
数据库
~~~

但真实服务端是：

~~~text
Request A → Transaction A
Request B → Transaction B
Request C → Transaction C
Worker 1  → Transaction D
Worker 2  → Transaction E
~~~

这些 Transaction 可能同时访问相同 Table，甚至相同 Row。

Isolation（隔离性）关注：

> 多个 Transaction 并发执行时，一个 Transaction 能看到另外一个 Transaction 的哪些数据变化，以及发生冲突时应该等待、失败还是继续读取其他版本。

这里开始进入数据库 Concurrency Control（并发控制）。

---

### 【MVCC 让 PostgreSQL 不需要把所有并发操作简单变成互相阻塞】

PostgreSQL 的核心并发控制机制之一是：

MVCC（Multi-Version Concurrency Control，多版本并发控制）。

当前阶段不要先进入 xmin、xmax、Tuple Header 等内部实现。

先建立宏观模型：

~~~text
同一逻辑 Row
↓
在不同事务变化过程中
可能存在不同版本
↓
Transaction 根据 Snapshot / 可见性规则
决定自己应该看到哪个版本
~~~

这样做的一个重要价值是：

~~~text
普通 SELECT
不需要因为其他 Transaction 正在 UPDATE
就简单全部等待
~~~

也就是：

~~~text
Read
和
Write
~~~

不需要完全互斥。

因此 Isolation 的目标不是：

~~~text
所有 Transaction 一个一个排队执行
~~~

而是：

~~~text
尽量保留并发能力
+
同时控制不同 Transaction 可以看到的数据状态
~~~

后续 MVCC 专题再继续深入：

~~~text
Transaction ID
Snapshot
Row Version
Visibility
Vacuum
~~~

Transaction 章节只先把 MVCC 放到正确位置。

### 【Isolation Level（事务隔离级别）定义并发 Transaction 能看到哪些变化】

SQL 标准常见四个 Isolation Level：

~~~text
Read Uncommitted（读未提交）
Read Committed（读已提交）
Repeatable Read（可重复读）
Serializable（串行化）
~~~

隔离级别不是：

~~~text
事务开
/
事务关
~~~

而是：

~~~text
Transaction 之间隔离到什么程度
~~~

不同级别主要对应几种典型并发异常。

#### <u>1. Dirty Read（脏读）是读到了其他 Transaction 尚未提交的数据</u>

假设：

~~~text
Transaction A
BEGIN
UPDATE account SET balance = 0
还没有 COMMIT
~~~

此时 Transaction B 如果能够读取：

~~~text
balance = 0
~~~

随后 A：

~~~text
ROLLBACK
~~~

那么：

~~~text
B 曾经读取到一个最终根本没有成立的数据
~~~

这就是 Dirty Read（脏读）。

PostgreSQL 的 Read Committed 不允许 Dirty Read。

另外 PostgreSQL 虽然接受 Read Uncommitted 这个隔离级别名称，但实际行为仍然按照 Read Committed 处理，因此 PostgreSQL 中不会提供真正的脏读语义。

#### <u>2. Nonrepeatable Read（不可重复读）是同一个 Transaction 两次读同一 Row 得到不同结果</u>

~~~text
Transaction A
BEGIN
SELECT balance
→ 100

Transaction B
UPDATE balance = 50
COMMIT

Transaction A
再次 SELECT balance
→ 50
~~~

同一个 Transaction 中：

~~~text
第一次读 100
第二次读 50
~~~

就是 Nonrepeatable Read。

在 Read Committed 下，这是允许出现的。

原因是 PostgreSQL Read Committed 的每一条普通 Statement 通常会基于这条 Statement 开始时已经提交的数据建立可见视图。

因此同一 Transaction 中：

~~~text
Query 1
和
Query 2
~~~

可能看到不同时间点上已经提交的数据。

#### <u>3. Phantom Read（幻读）是同样条件查询得到的 Row 集合变化</u>

Transaction A：

~~~sql
SELECT *
FROM orders
WHERE status = 'pending';
~~~

第一次得到：

~~~text
10 Rows
~~~

Transaction B：

~~~text
INSERT 一条新的 pending order
COMMIT
~~~

A 再次执行相同条件：

~~~text
11 Rows
~~~

这里变化的不是某一个既有 Row 的一个字段，而是：

~~~text
满足 Predicate（查询条件）的 Row 集合发生变化
~~~

这就是 Phantom Read。

#### <u>4. PostgreSQL 的 Repeatable Read 比 SQL 标准最低要求更强</u>

PostgreSQL 的 Repeatable Read：

~~~text
不会产生 Dirty Read
不会产生 Nonrepeatable Read
PostgreSQL 实现中也不会产生 Phantom Read
~~~

但是仍然可能产生：

~~~text
Serialization Anomaly（串行化异常）
~~~

也就是多个事务虽然各自看到稳定 Snapshot，但最终组合结果无法解释成任何合理的串行执行顺序。

#### <u>5. 当前项目默认使用 Read Committed</u>

当前 Browser Monitor 没有看到显式设置：

~~~text
SET TRANSACTION ISOLATION LEVEL ...
~~~

因此使用 PostgreSQL 默认：

~~~text
Read Committed
~~~

这意味着当前项目的并发正确性并不是靠：

~~~text
把所有 Transaction 都提升成 Serializable
~~~

而更多依赖：

~~~text
Read Committed
+
Constraint
+
FOR UPDATE
+
Advisory Lock
+
ON CONFLICT
+
Idempotency
~~~

这是一种非常常见的工程方式。

### 【Serializable（串行化）不是简单“把所有事务物理串行执行”】

Serializable 是 PostgreSQL 能提供的最严格常用隔离级别。

它的目标不是：

~~~text
A 完全执行完
↓
B 才开始
↓
C 再开始
~~~

而是：

> 即使这些 Transaction 实际上并发执行，最终成功提交的结果也必须能够等价解释成某一种串行顺序执行的结果。

如果数据库判断当前并发结果不能满足这种要求，就可能让某一个 Transaction：

~~~text
Serialization Failure
↓
ROLLBACK
~~~

应用需要重新执行整个事务。

所以 Serializable 的代价不仅是“性能可能下降”，还包括：

~~~text
Transaction 可能因为并发关系失败
↓
Application 必须实现正确 Retry
~~~

因此数据库并发设计不能简单：

~~~text
Serializable 最强
↓
所以全部使用 Serializable
~~~

而应该：

~~~text
明确真正并发风险
↓
判断默认 Read Committed 是否足够
↓
是否可以用 Constraint
↓
是否可以针对具体 Row 使用 FOR UPDATE
↓
是否可以针对业务资源使用 Advisory Lock
↓
是否真的需要更强 Isolation Level
~~~

---

### 【Transaction 和 Lock（锁）不是同一个概念】

这两个概念经常一起出现，因此非常容易混淆。

Transaction 解决：

~~~text
一次业务状态变化
是否可以只成功一部分？
~~~

Lock 解决：

~~~text
多个并发 Transaction
是否可以同时访问或修改同一个受保护资源？
~~~

例如接受 Invitation：

~~~text
Transaction
保证：
Member 创建
+
Invitation 标记 accepted
共同成功
~~~

同时：

~~~text
FOR UPDATE
保证：
多个并发 Request
不能同时基于同一个未接受 Invitation
完成冲突修改
~~~

所以典型结构是：

~~~text
BEGIN
↓
获得 Lock
↓
读取受保护状态
↓
完成修改
↓
COMMIT / ROLLBACK
↓
释放 Lock
~~~

---

### 【FOR UPDATE 把“读当前状态再修改”放进受保护的临界区】

当前 ProjectsService.acceptInvitation()：

~~~sql
SELECT id, project_id, email, role
FROM project_invitations
WHERE token_hash = $1
AND accepted_at IS NULL
AND expires_at > now()
FOR UPDATE
~~~

完整流程：

~~~text
BEGIN
↓
SELECT Invitation FOR UPDATE
↓
确认 Invitation 仍有效
↓
确认 Email 匹配
↓
INSERT / UPDATE project_members
↓
UPDATE project_invitations.accepted_at
↓
COMMIT
~~~

FOR UPDATE 属于 Row-Level Lock（行级锁）的使用方式。

可以理解为：

> 当前 Transaction 不只是“看看这一行”，而是准备基于它当前的值完成后续修改，因此需要防止其他 Transaction 同时进行冲突修改。

假设两个 Request 同时提交相同 Invitation Token。

Request A：

~~~text
BEGIN
↓
SELECT Invitation FOR UPDATE
↓
得到 Row Lock
~~~

Request B：

~~~text
BEGIN
↓
SELECT 同一 Invitation FOR UPDATE
↓
发现冲突
↓
等待 A
~~~

A：

~~~text
INSERT project_members
↓
UPDATE accepted_at
↓
COMMIT
~~~

COMMIT 后：

~~~text
A 的 Row Lock 释放
~~~

B 才能继续。

B 再继续执行时，就不能继续假设：

~~~text
accepted_at 仍然是 NULL
~~~

因为数据库状态已经被 A 提交。

这里体现：

~~~text
读
↓
判断
↓
修改
~~~

如果它们是一个并发敏感的业务步骤，往往不能只靠普通 SELECT。

---

### 【Row Lock 通常跟随 Transaction 生命周期，而不是单条 SQL 生命周期】

显式 Transaction：

~~~text
BEGIN
↓
SELECT ... FOR UPDATE
↓
获得 Row Lock
↓
后续执行业务 SQL
↓
COMMIT / ROLLBACK
↓
释放 Lock
~~~

如果 Transaction 很长：

~~~text
Lock 就会被持有很长时间
~~~

这也是后面为什么要控制 Long Transaction（长事务）。

对于一条单独自动提交的 SQL：

~~~text
SQL 开始
↓
隐式 Transaction
↓
获得需要的 Lock
↓
SQL 完成
↓
自动 COMMIT
↓
Lock 释放
~~~

所以 Lock 的真正边界通常仍然由 Transaction 决定。

### 【Advisory Lock 解决“还没有目标 Row 可以锁”的业务并发问题】

当前 Ingestion 中使用：

~~~sql
pg_advisory_xact_lock(...)
~~~

这是 Advisory Lock（建议锁）。

Advisory 的意思不是：

~~~text
数据库只是建议你锁
~~~

而是：

> 锁本身的业务含义由 Application 定义，PostgreSQL 只负责根据你给出的 Lock Key 协调并发。

FOR UPDATE 必须先有：

~~~text
一个真实存在的 Row
~~~

然后：

~~~text
锁这个 Row
~~~

但 Ingestion 的去重问题是：

~~~text
projectId + eventId
~~~

而这个 Event 可能：

~~~text
现在根本还没有插入 telemetry_events
~~~

因此无法：

~~~text
SELECT 目标 Row FOR UPDATE
~~~

当前源码改用：

~~~sql
SELECT pg_advisory_xact_lock(
  hashtextextended($1 || ':' || ids.event_id, 0)
)
~~~

把：

~~~text
ingest:{projectId}:{eventId}
~~~

映射成一个 Lock Key。

于是：

~~~text
虽然目标 Event Row 还不存在
↓
Application 已经定义
project + eventId 是一个并发互斥资源
↓
PostgreSQL 根据这个 Lock Key
协调多个 Transaction
~~~

这里用的是：

~~~text
Transaction-Level Advisory Lock
~~~

也就是：

~~~text
锁属于当前 Transaction
↓
COMMIT / ROLLBACK
↓
自动释放
~~~

---

### 【Ingestion 把“检查是否重复”和“真正写入”放进同一个并发保护区】

当前 IngestionService 先处理一个 Request 内部自己的重复 eventId：

~~~ts
const seenEventIds = new Set<string>();
const uniqueValid = valid.filter((event) => {
  if (seenEventIds.has(event.eventId)) return false;
  seenEventIds.add(event.eventId);
  return true;
});
~~~

这只能解决：

~~~text
同一个 HTTP Request
内部重复 eventId
~~~

不能解决：

~~~text
两个不同 HTTP Request
同时上传相同 eventId
~~~

因此进入 PostgreSQL 后：

~~~ts
await client.query('BEGIN');
const eventIds = uniqueValid.map((event) => event.eventId).sort();
~~~

随后申请：

~~~text
projectId + eventId
~~~

对应的 Advisory Lock。

然后再查询：

~~~sql
SELECT event_id
FROM telemetry_events
WHERE project_id = $1
AND event_id = ANY($2::text[])
GROUP BY event_id
~~~

整体链路：

~~~text
BEGIN
↓
获取每个 eventId 对应 Advisory Lock
↓
查询 telemetry_events 是否已经存在
↓
构造 existingIds
↓
过滤 pending Event
↓
INSERT telemetry_events
↓
INSERT outbox_tasks
↓
UPDATE ingestion_keys.last_used_at
↓
COMMIT
↓
Transaction-Level Advisory Lock 自动释放
~~~

为什么不能：

~~~text
先 SELECT
↓
发现不存在
↓
之后再 INSERT
~~~

但不加任何并发保护？

因为会产生 Check-Then-Act Race（先检查再操作竞态）。

例如：

~~~text
Request A
SELECT
event-1 不存在

Request B
SELECT
event-1 也不存在

Request A
INSERT event-1

Request B
也尝试 INSERT event-1
~~~

两个 Request 的“检查结果”都来自：

~~~text
真正 INSERT 之前的旧状态
~~~

所以：

~~~text
检查
↓
判断
↓
写入
~~~

如果业务要求它们基于同一受保护状态，就要让它们形成 Critical Section（临界区）。

当前项目通过 Transaction-Level Advisory Lock 完成这个保护。

### 【确定性的加锁顺序用于降低 Deadlock（死锁）】

Ingestion 中有一行：

~~~ts
const eventIds = uniqueValid.map((event) => event.eventId).sort();
~~~

SQL 中又：

~~~sql
ORDER BY ids.event_id
~~~

源码注释明确说明这样做是为了避免 overlapping batches（相互重叠的 Batch）出现 Deadlock。

Deadlock（死锁）可以这样理解：

Transaction A：

~~~text
已经获得 Lock 1
↓
等待 Lock 2
~~~

Transaction B：

~~~text
已经获得 Lock 2
↓
等待 Lock 1
~~~

形成：

~~~text
A 等 B
↑   ↓
B 等 A
~~~

谁都无法继续。

PostgreSQL 能检测 Deadlock，并主动终止其中一个 Transaction。

但是更好的工程设计是：

~~~text
尽量避免创造容易形成 Deadlock 的锁顺序
~~~

假设两个 Batch：

~~~text
Batch A:
event-3,event-1,event-2

Batch B:
event-2,event-3,event-1
~~~

如果各自按输入顺序加锁，就可能：

~~~text
A 先拿 event-3
B 先拿 event-2
↓
之后互相继续申请对方持有的 Lock
~~~

当前项目先排序：

~~~text
A:
event-1,event-2,event-3

B:
event-1,event-2,event-3
~~~

所有 Transaction 都遵循：

~~~text
1 → 2 → 3
~~~

这一固定顺序。

这样大幅降低：

~~~text
A 拿 1 等 2
同时 B 拿 2 等 1
~~~

这种循环等待。

所以事务设计继续向下时，还必须思考：

~~~text
会获取哪些 Lock？
是否一次获取多个 Lock？
多个 Lock 的获取顺序是否固定？
Lock 会持续多久？
发生冲突时数据库会等待多久？
~~~

---

### 【Isolation 不等于取消并发，而是控制并发】

一个常见误解是：

~~~text
有 Transaction Isolation
↓
Transaction A 执行时
Transaction B 不能执行
~~~

如果数据库真的这样做：

~~~text
A 完成
↓
B 完成
↓
C 完成
~~~

系统并发能力会非常差。

PostgreSQL 更接近：

~~~text
A、B、C 可以同时运行
~~~

只有发生真正冲突时才：

~~~text
等待
或者
某个 Transaction 失败
或者
通过 MVCC 读取适合自己的 Row Version
~~~

例如：

~~~text
Transaction A
修改 Project A

Transaction B
修改 Project B
~~~

两个资源彼此独立，就没有理由全局互斥。

甚至：

~~~text
Transaction A
正在 UPDATE 某 Row

Transaction B
执行普通 SELECT
~~~

在 MVCC 下，普通读通常也不需要简单等待写事务全部结束。

所以 Isolation 的核心目标是：

~~~text
保留尽可能高的并发
+
同时保证 Transaction 不观察到不可接受的数据状态
~~~

### 【Durability（持久性）解决 COMMIT 成功以后数据库崩溃怎么办】

ACID 最后一项是 Durability（持久性）。

它回答：

~~~text
PostgreSQL 已经向 Application 返回
COMMIT 成功

下一秒数据库进程崩溃
甚至服务器发生故障

已经确认成功的 Transaction
还能不能恢复？
~~~

如果 COMMIT 成功的数据一崩溃就消失，那么：

~~~text
Application 已经收到成功
↓
用户认为操作完成
↓
数据库恢复后数据不存在
~~~

系统就不能称为可靠提交。

因此 PostgreSQL 还需要：

WAL（Write-Ahead Logging，预写日志）。

当前阶段只建立它的位置：

~~~text
Transaction 修改数据
↓
COMMIT
↓
PostgreSQL 需要保证足够的恢复信息
已经进入可靠存储路径
↓
后续即使发生 Crash
也能根据 WAL 等机制恢复已提交状态
~~~

更底层的：

~~~text
WAL Record
LSN
Checkpoint
fsync
Crash Recovery
~~~

应该放到后面的数据库可靠性章节，不在 Transaction 章节一次深入。

所以 ACID 的四个问题可以重新放回整体：

~~~text
Atomicity
一次事务不能只完成一部分

Consistency
事务结束后数据仍满足系统规则

Isolation
并发事务之间怎样观察和协调

Durability
已经 COMMIT 的状态怎样面对故障继续存在
~~~

### 【Transactional Outbox 解决“业务数据成功，但异步任务没有产生”的双写问题】

当前 Browser Monitor Ingestion 是理解 Transaction 最重要的项目案例。

SDK 上报 Event 后，API 需要同时产生：

~~~text
telemetry_events
+
outbox_tasks
~~~

两张表承担不同职责：

~~~text
telemetry_events
↓
这个原始 Event 已经被服务端可靠接收

outbox_tasks
↓
这个 Event 后续还有后台处理任务
~~~

如果分开：

~~~text
INSERT telemetry_events
↓
COMMIT
↓
服务进程崩溃
↓
INSERT outbox_tasks 没有执行
~~~

系统会变成：

~~~text
Raw Event 已经存在
↓
但没有 Worker Task
↓
Projection 永远不会产生
~~~

这就是典型 Dual Write Problem（双写问题）的一种表现。

当前源码使用一条 CTE：

~~~sql
WITH input AS (...),
inserted_events AS (
  INSERT INTO telemetry_events(...)
  SELECT ...
  FROM input
  ON CONFLICT DO NOTHING
  RETURNING event_id, occurred_at, event
)
INSERT INTO outbox_tasks(project_id, event_id, occurred_at, event)
SELECT $1, event_id, occurred_at, event
FROM inserted_events
RETURNING event_id;
~~~

这条 SQL 本身已经把：

~~~text
真正插入 telemetry_events 的 Event
↓
继续生成 outbox_tasks
~~~

连起来。

而整条 SQL 又处于：

~~~text
BEGIN
...
COMMIT
~~~

中。

所以：

~~~text
telemetry_events
+
outbox_tasks
~~~

共享一个 PostgreSQL Transaction。

这就是 Transactional Outbox（事务型 Outbox）的核心：

> 把核心业务事实和“后续需要异步处理”的任务记录写入同一个本地数据库 Transaction，从而避免数据库状态已经提交但任务消息没有产生。

当前链路：

~~~text
SDK Event
↓
Protocol / Schema Validation
↓
业务校验
↓
BEGIN
↓
Advisory Lock
↓
数据库 Duplicate Check
↓
INSERT telemetry_events
↓
INSERT outbox_tasks
↓
UPDATE ingestion_keys.last_used_at
↓
COMMIT
↓
Worker 后续消费 Outbox
~~~

这里 Transaction 解决的是：

~~~text
Event
和
Task
不能只存在一个
~~~

后面的 Worker Retry、Dead Letter、幂等则解决：

~~~text
Task 创建以后
如何可靠地被执行
~~~

### 【PostgreSQL Transaction 只能直接保护 PostgreSQL 内的数据，不能自动跨越 Redis】

当前 Ingestion 在 PostgreSQL：

~~~text
COMMIT
~~~

之后，才执行 Redis：

~~~ts
await this.redis
  .multi()
  .hincrby(...)
  .zadd(...)
  .exec()
  .catch(() => undefined);
~~~

这段设计非常重要，因为它展示了 Transaction 的边界。

PostgreSQL Transaction 可以直接保证：

~~~text
telemetry_events
outbox_tasks
ingestion_keys
~~~

这些 PostgreSQL 内部数据。

但它不能自动把：

~~~text
PostgreSQL
+
Redis
~~~

变成一个 Transaction。

例如：

~~~text
PostgreSQL COMMIT 成功
↓
Redis HINCRBY 失败
~~~

这时候不能简单：

~~~text
ROLLBACK PostgreSQL
~~~

原因有两个：

~~~text
1. PostgreSQL Transaction 已经 COMMIT 结束

2. Redis 本来也不属于这个 PostgreSQL Transaction
~~~

因此服务端需要区分：

~~~text
Local Transaction（本地事务）
↓
一个数据库系统内部的原子操作

Cross-System Consistency（跨系统一致性）
↓
多个独立系统之间如何协调状态
~~~

当前项目的设计是：

~~~text
PostgreSQL
↓
核心事实
↓
必须可靠

Redis
↓
Dashboard Counter
Recent Receive Rate
Analytics Cache Version
↓
属于派生 / 辅助状态
↓
允许短时间不同步
~~~

源码甚至明确：

~~~text
Redis statistics failure
不能把一个已经成功 COMMIT 的 Ingestion
重新变成 SDK 应该 Retry 的错误
~~~

这说明项目把：

~~~text
核心事实正确
~~~

和：

~~~text
辅助统计立即更新
~~~

设置成了不同可靠性等级。

这就是 Eventual Consistency（最终一致性）进入系统设计的位置。

### 【外部网络调用通常不应该被长时间包在数据库 Transaction 内】

AuthService.register() 当前流程：

~~~text
准备 Password Hash
↓
BEGIN
↓
INSERT / UPDATE User
↓
让旧 Verification Token 失效
↓
创建新 Verification Token
↓
COMMIT
↓
release Connection
↓
Mailer.sendVerification()
~~~

Mailer 位于 COMMIT 后。

如果改成：

~~~text
BEGIN
↓
数据库修改
↓
请求 Mail Provider
↓
等待外部网络响应
↓
COMMIT
~~~

会出现：

~~~text
Transaction 一直打开
+
Connection 一直占用
+
Transaction 中已经拿到的 Lock 一直不释放
~~~

而网络调用具有：

~~~text
延迟不可控
超时
第三方故障
Retry
~~~

等特点。

所以 Transaction Boundary 的一个核心设计原则是：

> 事务只应该覆盖必须共同保证的数据操作，不应该因为“这些代码都在一个 Service 方法里”就把所有操作一起包进去。

### 【Long Transaction（长事务）会扩大 Lock、Connection 和 MVCC 成本】

假设：

~~~text
BEGIN
↓
SELECT Invitation FOR UPDATE
↓
执行复杂 CPU 计算 5 秒
↓
请求第三方 HTTP API 3 秒
↓
再 UPDATE
↓
COMMIT
~~~

这 8 秒期间：

~~~text
Connection 被当前 Request 占用
Row Lock 可能持续存在
Transaction Snapshot / State 持续存在
其他冲突 Transaction 持续等待
~~~

高并发下可能演变：

~~~text
Long Transaction 增加
↓
Lock Wait 增加
↓
Connection 被长期占用
↓
Pool 可用 Connection 减少
↓
更多 Request 等待 Connection
↓
整体数据库延迟进一步增加
~~~

长事务还会进一步影响 PostgreSQL 的旧版本清理等内部过程，但这部分放到 MVCC / Vacuum 章节继续展开。

当前阶段建立原则：

~~~text
Transaction
应该足够大
保证业务正确

同时应该足够小
尽快释放 Connection 和 Lock
~~~

当前 ProjectsService.create() 在 BEGIN 前先完成：

~~~ts
const publicKey = createOpaqueToken('bm_pk_');
const userHashSalt = createOpaqueToken();
const defaultOrigin = new URL(this.config.PUBLIC_BASE_URL).origin;
~~~

这些普通计算不需要占用 Database Transaction。

之后才：

~~~text
pool.connect()
↓
BEGIN
~~~

这是合理缩短事务范围的体现。

### 【EventProcessor 的 Transaction 保证 Projection 和 processed_at 共同成为事实】

Worker 的 EventProcessor：

~~~text
browser-monitor/platform/apps/worker/src/processor.ts
~~~

核心结构：

~~~ts
const client = await this.database.pool.connect();
try {
  await client.query('BEGIN');
  if (event.payload.type === 'performance') {
    await this.processPerformance(client, projectId, event, event.payload);
  } else if (event.payload.type === 'view') {
    await this.processView(client, projectId, event, event.payload);
  } else {
    await this.processCustomSignal(client, projectId, event, event.payload);
  }
  await client.query(
    'UPDATE telemetry_events SET processed_at = now() WHERE project_id = $1 AND event_id = $2 AND occurred_at = $3',
    [projectId, event.eventId, new Date(event.occurredAt)],
  );
  await client.query('COMMIT');
} catch (error) {
  await client.query('ROLLBACK');
  throw error;
} finally {
  client.release();
}
~~~

这里的业务状态变化是：

~~~text
Event 已经完成 Projection
~~~

它需要两个事实共同成立：

~~~text
对应 Projection 数据已经写入
+
telemetry_events.processed_at 已更新
~~~

如果：

~~~text
Projection 写入成功
但是 processed_at 更新失败
~~~

而没有 Transaction：

~~~text
Projection 已经存在
Raw Event 却仍然显示未处理
~~~

后续 Worker 可能再次把它当作未处理事件。

当前 Transaction 让：

~~~text
Projection
+
processed_at
~~~

共同 COMMIT。

### 【Processor 内部再次使用 Advisory Lock + FOR UPDATE，说明 Transaction 与 Concurrency Control 会叠加】

processPerformance() 中：

~~~sql
SELECT pg_advisory_xact_lock(hashtextextended($1, 0))
~~~

锁对象：

~~~text
performance:{projectId}:{sampleId}
~~~

随后又：

~~~sql
SELECT observed_at, sequence, state
FROM performance_samples
WHERE project_id = $1
AND sample_id = $2
ORDER BY observed_at DESC
LIMIT 1
FOR UPDATE
~~~

为什么两层都存在？

源码注释已经说明：

~~~text
多个 Worker 可能同时收到
同一个 performance sample
的 provisional / final revision

必须把：
sequence 检查
+
最终写入
变成跨进程受保护的临界区
~~~

Advisory Lock 保护的是：

~~~text
project + sampleId
这个逻辑业务资源
~~~

FOR UPDATE 又保护：

~~~text
已经存在的 performance_samples Row
~~~

这说明并发控制不是只有一种 Lock。

可以按问题选择：

~~~text
目标 Row 已经存在
↓
FOR UPDATE 可以直接保护 Row

目标逻辑资源可能还没有 Row
↓
Advisory Lock 可以先保护业务 Key
~~~

### 【Worker 的整个执行链并没有被强行放进一个超级 Transaction】

OutboxWorker.handle() 当前结构：

~~~text
processor.process()
↓
内部 Transaction
Projection + processed_at
↓
COMMIT
↓
UPDATE outbox_tasks → completed
↓
另一个独立数据库操作
↓
Redis analytics version +1
~~~

也就是说：

~~~text
Projection Transaction
~~~

和：

~~~text
Outbox completed
~~~

不是同一个 Transaction。

因此存在一个现实窗口：

~~~text
Projection 已经 COMMIT
↓
Node Process 突然崩溃
↓
outbox_tasks 还保持 processing
~~~

超过 stale 时间以后：

~~~text
Task 会被重新 Claim
~~~

所以：

~~~text
同一个 Event
可能再次进入 Processor
~~~

这说明现代异步系统不能简单追求：

~~~text
把所有步骤都放进一个巨大 Transaction
~~~

因为一个 Transaction 不能跨越：

~~~text
API
Worker
Redis
多个时间点
多个进程
~~~

系统因此依赖组合能力：

~~~text
Transaction
↓
保证每一个局部数据状态变化完整

Outbox
↓
可靠记录需要异步处理的 Task

Retry
↓
失败以后重新处理

Idempotency
↓
重复执行不能制造重复副作用

Lock
↓
控制并发执行

Dead Letter
↓
长期失败任务进入独立处理路径
~~~

这才是完整可靠性体系。

### 【Idempotency（幂等）是 Transaction 之外必须补充的能力】

Idempotency（幂等）在服务端中可以先理解为：

> 同一个操作因为 Retry 被执行多次，最终业务结果应该和正确执行一次保持一致，或者至少不会不断产生重复副作用。

例如：

~~~text
Worker 处理 Event
↓
Projection 已 COMMIT
↓
Outbox completed 前进程崩溃
↓
Task 被重新 Claim
↓
Processor 再执行一次
~~~

如果第二次执行：

~~~text
再次 INSERT 一份相同 Projection
~~~

就可能产生重复数据。

当前源码因此大量使用：

~~~sql
ON CONFLICT DO NOTHING
~~~

并结合：

~~~text
sampleId
sequence
state
FOR UPDATE
Advisory Lock
~~~

控制重复执行。

因此：

~~~text
Transaction
≠
Idempotency
~~~

Transaction 解决：

~~~text
一次执行内部
不能只完成一半
~~~

Idempotency 解决：

~~~text
整个业务操作
如果被重复执行
结果是否仍然可接受
~~~

### 【Worker Claim 展示“单条 SQL + 隐式 Transaction”也可以完成原子领取】

当前 OutboxWorker.claim()：

~~~sql
WITH candidates AS (
  SELECT id FROM outbox_tasks
  WHERE (
    status = 'pending' AND available_at <= now()
  ) OR (
    status = 'processing' AND locked_at < now() - INTERVAL '5 minutes'
  )
  ORDER BY available_at, created_at
  LIMIT $1
  FOR UPDATE SKIP LOCKED
)
UPDATE outbox_tasks o SET
  status = 'processing',
  locked_at = now(),
  locked_by = $2,
  attempts = attempts + 1
FROM candidates c
WHERE o.id = c.id
RETURNING o.id, o.project_id, o.event_id, o.event, o.attempts;
~~~

这里没有显式 BEGIN。

但不能理解成：

~~~text
没有 Transaction
~~~

这一整条 SQL 本身在 PostgreSQL 隐式事务中执行。

它一次完成：

~~~text
找到候选 Task
↓
对候选 Row 加 FOR UPDATE Lock
↓
跳过已经被其他 Worker 锁住的 Row
↓
把自己真正领取的 Row 更新为 processing
↓
写 locked_by
↓
attempts + 1
↓
RETURNING 已领取 Task
~~~

这样就避免：

~~~text
SELECT Task
↓
SQL 已结束
↓
另一个 Worker 也 SELECT 到同一个 Task
↓
两个 Worker 再分别 UPDATE
~~~

这种竞态窗口。

FOR UPDATE SKIP LOCKED 的意义：

~~~text
FOR UPDATE
↓
准备锁定候选 Row

SKIP LOCKED
↓
如果某 Row 已经被其他 Worker 锁住
不要等待
直接跳过
继续寻找其他 Task
~~~

这特别适合：

~~~text
数据库 Table 充当任务队列
+
多个 Worker 并行消费
~~~

的场景。

### 【单条原子 SQL 与显式 Transaction 是两种不同粒度的设计手段】

如果一个状态变化能够用一条 SQL 完成：

~~~text
SELECT 候选
+
UPDATE 状态
+
RETURNING
~~~

数据库本身就能在这一条 Statement 的 Transaction 范围内保证它的原子性。

因此：

~~~text
显式 Transaction
不是越多越好
~~~

而应该：

~~~text
如果一条 SQL 已经能够原子完成
↓
不必人为把范围拉长

如果多个 SQL 必须共同提交
↓
再建立显式 Transaction
~~~

这也是缩短事务的重要方法。

### 【Dead Letter Transaction 保证任务从正常队列进入失败队列时状态完整】

当前 OutboxWorker.fail() 在 attempts >= 8 时：

~~~text
BEGIN
↓
INSERT / UPDATE dead_letter_tasks
↓
UPDATE outbox_tasks
status = failed
last_error = ...
locked_at = NULL
locked_by = NULL
↓
COMMIT
~~~

业务状态变化是：

~~~text
这个 Task 已经无法通过正常 Retry 恢复
↓
进入 Dead Letter
~~~

因此两个事实必须共同成立：

~~~text
Dead Letter 中可以查询到失败任务
+
Outbox 中这个 Task 已经被标记 failed
~~~

如果只完成第一步：

~~~text
Dead Letter 已经存在
+
Outbox 还可能继续被 Worker 当成普通任务处理
~~~

如果只完成第二步：

~~~text
Outbox failed
+
却没有 Dead Letter 中的错误详情
~~~

后续：

~~~text
人工排查
重新 Retry
失败历史分析
~~~

都会缺少必要数据。

因此：

~~~text
INSERT dead_letter_tasks
+
UPDATE outbox_tasks
~~~

必须共享一个 Transaction Boundary。

### 【Transaction Retry 通常需要重新执行整个事务，而不是只重放最后一条 SQL】

Transaction 可能因为：

~~~text
Deadlock
Serialization Failure
Temporary Database Error
~~~

失败。

如果错误属于可 Retry 类型：

~~~text
不能简单只重新执行最后一条失败 SQL
~~~

原因是整个 Transaction 之前读取的状态可能已经过期。

例如：

~~~text
BEGIN
↓
SELECT max(version)
得到 3
↓
Application 计算 nextVersion = 4
↓
INSERT version = 4
↓
发生并发冲突
~~~

当这个 Transaction Retry 时：

~~~text
另一个 Transaction
可能已经成功 COMMIT version = 4
~~~

这时旧的：

~~~text
nextVersion = 4
~~~

已经不再正确。

所以应该：

~~~text
重新 BEGIN
↓
重新读取数据库最新状态
↓
重新计算
↓
重新执行整个业务 Transaction
~~~

这就是为什么可 Retry Transaction 应该尽量：

~~~text
边界清晰
输入清晰
内部逻辑可重复执行
~~~

### 【updateThresholds 展示 Atomicity 和 Concurrency Correctness（并发正确性）是两个不同问题】

当前 ProjectsService.updateThresholds()：

~~~text
BEGIN
↓
UPDATE threshold_versions
SET active = false
WHERE project_id = ...
AND active
↓
INSERT 新 Threshold Version
version = max(version) + 1
active = true
↓
COMMIT
~~~

这个 Transaction 可以保证：

~~~text
旧 Version 失活
+
新 Version 创建
~~~

不会只完成一半。

这是 Atomicity。

但是如果：

~~~text
Request A
和
Request B
~~~

同时调用 updateThresholds：

A 可能读到：

~~~text
max(version) = 3
~~~

B 也可能读到：

~~~text
max(version) = 3
~~~

两边都试图：

~~~text
INSERT version = 4
~~~

当前数据库有：

~~~text
UNIQUE(project_id, version)
~~~

以及 Migration 中：

~~~text
一个 Project 同一时刻只能有一个 active Version
~~~

的 Unique Constraint / Partial Unique Index。

因此其中一个 Transaction 可能最终因为 Constraint Conflict 失败。

这里不能说：

~~~text
用了 Transaction
为什么还会失败？
~~~

Transaction 的职责是：

~~~text
这个失败 Transaction
不能留下“旧 Version 已经 inactive
但新 Version 没创建”的半状态
~~~

Unique Constraint 的职责是：

~~~text
不允许两个并发 Transaction
都提交相同 Version
~~~

Application 的职责则是：

~~~text
发生这种冲突以后
返回错误
或者
重新 Retry 整个 Transaction
~~~

所以真实并发正确性通常来自：

~~~text
Transaction
+
Constraint
+
Lock / Isolation
+
Retry
~~~

而不是单独一个 BEGIN。

### 【Drizzle Transaction 只是更高层 API，底层仍然是 PostgreSQL Transaction】

当前 DatabaseHandle：

~~~ts
export interface DatabaseHandle {
  pool: Pool;
  db: NodePgDatabase<typeof schema>;
  close(): Promise<void>;
}
~~~

同一个 Pool 上同时创建：

~~~text
database.pool
↓
node-postgres
↓
Raw SQL

database.db
↓
Drizzle
↓
类型安全 Query API
~~~

Drizzle 可以：

~~~ts
await this.database.db.transaction(async (tx) => {
  await tx.insert(projects).values(...);
  await tx.insert(projectMembers).values(...);
});
~~~

它帮助 Application 管理：

~~~text
BEGIN
↓
tx 中执行 Query
↓
Callback 正常完成
↓
COMMIT
~~~

如果 callback 抛错：

~~~text
ROLLBACK
~~~

所以：

~~~text
pg Transaction
和
Drizzle Transaction
~~~

不是两种不同的数据库事务机制。

更准确关系：

~~~text
Application
├── node-postgres
│   ├── pool.connect()
│   ├── BEGIN
│   ├── query
│   └── COMMIT / ROLLBACK
│
└── Drizzle
    └── db.transaction(tx => ...)
        ↓
        封装 Connection / Transaction 生命周期
↓
PostgreSQL Transaction
~~~

当前项目之所以大量直接使用 pg Client，不是因为 Drizzle 不能做 Transaction，而是因为这些场景使用了较多 PostgreSQL 具体能力：

~~~text
FOR UPDATE
SKIP LOCKED
CTE
pg_advisory_xact_lock
jsonb_to_recordset
RETURNING
~~~

Raw SQL 在这些场景下表达更加直接。

### 【Migration Transaction 保证“结构已经修改”和“迁移已经记录”共同成立】

当前：

~~~text
browser-monitor/platform/packages/database/src/migrate.ts
~~~

每个 Migration：

~~~ts
const client = await pool.connect();
try {
  await client.query('BEGIN');
  await client.query(sql);
  await client.query(
    'INSERT INTO monitor_schema_migrations(name) VALUES ($1)',
    [name],
  );
  await client.query('COMMIT');
} catch (error) {
  await client.query('ROLLBACK');
  throw error;
} finally {
  client.release();
}
~~~

这里存在两个数据库事实：

~~~text
Migration SQL 已经执行
+
monitor_schema_migrations 已经记录这个文件
~~~

它们必须共同成立。

如果：

~~~text
Migration SQL 只执行了一部分
↓
但是 monitor_schema_migrations 已经写入
~~~

下一次运行：

~~~text
Migration Runner 看到它已经 applied
↓
直接跳过
~~~

数据库结构可能永远停留在不完整状态。

反过来：

~~~text
Migration SQL 已经成功
↓
但是 applied record 没有写入
~~~

下一次：

~~~text
Runner 又会尝试重复执行同一个 Migration
~~~

所以：

~~~text
Schema Change
+
Migration Record
~~~

也属于一个 Transaction Boundary。

这说明 Transaction 不只是业务 CRUD 技巧。

它是所有：

~~~text
多个数据库事实
必须共同描述一个状态变化
~~~

的通用数据管理机制。

### 【当前项目中的 Transaction 可以按业务目的进一步分类】

当前源码中的事务并不是同一种用途，可以分成几类。

#### <u>1. 创建型 Transaction</u>

例如：

~~~text
ProjectsService.create()
AuthService.register()
~~~

特点：

~~~text
一次业务创建
需要同时产生多条关联数据
~~~

目标：

~~~text
防止只创建出半套对象
~~~

#### <u>2. 状态迁移型 Transaction</u>

例如：

~~~text
rotateKey()
updateThresholds()
verifyEmail()
resetPassword()
retryDeadLetter()
OutboxWorker.fail()
~~~

特点：

~~~text
原来的状态
↓
需要经过多次数据修改
↓
迁移到新状态
~~~

目标：

~~~text
防止状态迁移到一半
~~~

#### <u>3. 数据 + 任务型 Transaction</u>

例如：

~~~text
IngestionService.ingest()
~~~

特点：

~~~text
核心业务事实
+
后续异步任务
~~~

共同提交。

目标：

~~~text
防止数据已经存在
但异步任务丢失
~~~

#### <u>4. Projection 型 Transaction</u>

例如：

~~~text
EventProcessor.process()
~~~

特点：

~~~text
Raw Event
↓
生成派生数据
↓
同时标记 processed
~~~

目标：

~~~text
派生状态和处理状态保持一致
~~~

#### <u>5. Migration 型 Transaction</u>

例如：

~~~text
migrate.ts
~~~

特点：

~~~text
数据库结构修改
+
迁移元数据修改
~~~

目标：

~~~text
Schema State 和 Migration State 一致
~~~

### 【Transaction 的设计流程应该从业务不变量出发，而不是从代码模板出发】

以后看到一个 Service，不应该先问：

~~~text
这里是不是有三条 SQL？
如果有就套 BEGIN？
~~~

而应该按下面顺序分析。

第一步：

~~~text
这个 Service 方法最终想完成什么业务状态变化？
~~~

第二步：

~~~text
为了完成这个状态变化
哪些 Table / Row 必须修改？
~~~

第三步：

~~~text
如果只成功其中一部分
数据库状态还能不能接受？
~~~

如果不能：

~~~text
建立 Transaction Boundary
~~~

第四步：

~~~text
是否存在多个 Request / Worker
同时操作相同数据？
~~~

如果存在：

~~~text
检查 Constraint
Isolation Level
FOR UPDATE
Advisory Lock
ON CONFLICT
~~~

第五步：

~~~text
这个 Transaction 是否会调用 Redis、Mailer、HTTP API？
~~~

如果会：

~~~text
判断这些外部操作是否真的应该进入 Transaction
通常尽量放在 COMMIT 之后
~~~

第六步：

~~~text
Transaction 是否可能因为 Deadlock / Serialization Failure 重试？
~~~

如果可能：

~~~text
保证整个 Transaction 可以重新执行
~~~

第七步：

~~~text
Transaction 是否过长？
是否长时间占用 Connection / Lock？
~~~

必要时继续拆分。

### 【Transaction 在整个数据管理知识体系中连接“单条数据正确”与“多步骤业务正确”】

前面已经有：

~~~text
Schema
↓
定义数据结构

Constraint
↓
保证单条数据和关系合法

Index
↓
优化访问路径
~~~

Transaction 再向上一层：

~~~text
Transaction
↓
保证多次数据库修改
形成一个完整业务状态变化
~~~

继续向并发层：

~~~text
Isolation
MVCC
Row Lock
Advisory Lock
Deadlock
~~~

继续向异步可靠性：

~~~text
Outbox
Retry
Idempotency
Dead Letter
~~~

继续向持久化可靠性：

~~~text
WAL
Checkpoint
Crash Recovery
Backup
~~~

因此数据管理体系可以逐渐形成：

~~~text
业务规则
↓
SQL
↓
Table / Row
↓
Constraint
↓
Index
↓
Transaction
↓
Concurrency Control
├── Isolation Level
├── MVCC
├── Row Lock
├── Advisory Lock
└── Deadlock
↓
Async Reliability
├── Outbox
├── Retry
├── Idempotency
└── Dead Letter
↓
Storage Reliability
├── WAL
├── Checkpoint
├── Crash Recovery
└── Backup
~~~

到 Transaction 这一层以后，数据库学习开始从：

~~~text
“数据怎么存”
~~~

进入：
