# 服务端数据管理源码学习-2

# Transaction（事务）

## 1. Transaction 解决多个数据库操作无法保证完整的问题

服务端中的一个业务操作通常需要修改多个数据。

例如 Browser Monitor 创建项目：

```text
创建 projects 数据

创建 project_members 数据

创建 ingestion_keys 数据

创建 allowed_origins 数据

记录 audit_logs
```

这些操作共同表示：

```text
创建一个完整 Project
```

如果其中一步失败：

```text
projects 创建成功

project_members 创建失败
```

数据库会留下业务无法接受的不完整状态。

Transaction（事务）用于解决这个问题：

> 将多个数据库操作放入同一个执行范围，使它们作为一个整体成功或者失败。

---

## 2. Transaction 的基本执行过程

### 【SQL 执行与最终数据保存的区别】

Transaction 中 SQL 不是等到 COMMIT（提交）之后才执行。

实际过程：

```text
执行 SQL
    ↓
产生数据修改
    ↓
属于当前 Transaction
    ↓
COMMIT
    ↓
成为最终数据库状态
```

例如：

```sql
BEGIN;

UPDATE projects
SET name='B项目'
WHERE id=1;
```

当前 Transaction 中数据已经修改为 B项目。

但是其他 Transaction 不会直接看到这个未提交修改。

执行：

```sql
COMMIT;
```

修改才正式保存。

---

### 【ROLLBACK 如何撤销修改】

如果执行失败：

```sql
ROLLBACK;
```

数据库会取消当前 Transaction 中产生的修改。

PostgreSQL 内部通过数据版本管理和日志机制实现恢复能力，涉及：

- MVCC（Multi-Version Concurrency Control，多版本并发控制）
- WAL（Write Ahead Logging，预写日志）

当前阶段理解：

```text
COMMIT
确认修改

ROLLBACK
取消修改
```

---

## 3. Transaction 的核心能力

### 【Atomicity（原子性）保证操作不会只完成一部分】

原子性表示：

> 一个业务操作中的多个数据库修改，要么全部成功，要么全部失败。

例如接受项目邀请：

需要两个修改：

```sql
INSERT INTO project_members(...);
```

加入项目成员。

```sql
UPDATE project_invitations
SET accepted_at=now();
```

更新邀请状态。

如果没有 Transaction：

```text
INSERT 成功

UPDATE 失败
```

可能出现：

```text
用户已经加入项目

但是邀请仍然显示未接受
```

使用 Transaction：

```sql
BEGIN;

INSERT project_members;

UPDATE project_invitations;

COMMIT;
```

失败时：

```sql
ROLLBACK;
```

恢复到操作开始前状态。

---

### 【Consistency（一致性）保证数据从合法状态进入合法状态】

Consistency（一致性）表示：

> 数据库执行前后，都应该满足数据库规则和业务规则。

它依赖：

```text
Constraint（约束）

Transaction（事务）

Business Logic（业务逻辑）
```

Transaction 本身不知道业务含义。

例如：

```sql
UPDATE projects
SET name='test';
```

如果没有违反数据库约束，Transaction 可以成功。

但是“test 是否符合产品要求”，需要业务代码判断。

---

### 【Isolation（隔离性）控制并发访问】

Isolation（隔离性）解决：

> 多个请求同时操作数据库时，一个 Transaction 是否会影响另一个 Transaction。

例如两个请求同时接受同一个邀请：

```text
请求 A
接受 invite-001

请求 B
接受 invite-001
```

如果没有并发控制，两个请求可能同时认为邀请有效。

后续需要结合 Lock（锁）解决。

---

### 【Durability（持久性）保证提交后的数据保存】

Durability（持久性）表示：

> Transaction 提交成功后，数据不会因为普通故障丢失。

执行：

```sql
COMMIT;
```

数据库确认修改后，数据进入可靠保存状态。

---

## 4. PostgreSQL pg 方式实现 Transaction

项目底层使用 node-postgres（pg）。

典型实现：

```ts
const client = await pool.connect();

try {
  await client.query('BEGIN');

  await client.query(sql1);
  await client.query(sql2);

  await client.query('COMMIT');

} catch(error) {
  await client.query('ROLLBACK');
} finally {
  client.release();
}
```

执行流程：

```text
Pool（连接池）

 ↓

获取固定 Client

 ↓

BEGIN

 ↓

执行 SQL

 ↓

COMMIT / ROLLBACK

 ↓

释放连接
```

---

### 【为什么 Transaction 必须使用同一个 Client】

错误方式：

```ts
pool.query('BEGIN');
pool.query(sql1);
pool.query(sql2);
pool.query('COMMIT');
```

原因：

连接池可能每次返回不同数据库连接。

Transaction 必须绑定同一个 Connection（数据库连接）。

## 5. Drizzle db 方式实现 Transaction

项目使用 Drizzle 管理数据库：

```ts
drizzle(pool,{schema})
```

Drizzle 提供：

```ts
await db.transaction(async(tx)=>{

  await tx.insert(projects);

  await tx.insert(projectMembers);

});
```

底层仍然对应 PostgreSQL：

```text
BEGIN

SQL

COMMIT / ROLLBACK
```

区别：

|方式|特点|
|-|-|
|pg|直接控制 SQL、连接、锁|
|Drizzle|类型安全封装，适合业务 CRUD|

## 6. Transaction 与 Lock（锁）的关系

Transaction 和 Lock 解决不同问题。

Transaction：

```text
保证一次业务操作完整
```

Lock：

```text
解决多个请求同时修改同一数据的问题
```

例如：

```text
两个用户同时接受同一个邀请
```

需要 Lock 控制并发。

---

## 7. PostgreSQL FOR UPDATE 行锁

FOR UPDATE 用于锁定查询结果对应的数据行。

例如：

```text
project_invitations

id = invite-001

accepted_at = NULL
```

请求 A：

```sql
BEGIN;

SELECT *
FROM project_invitations
WHERE id='invite-001'
FOR UPDATE;
```

数据库锁住该行。

请求 B：

```sql
SELECT *
FROM project_invitations
WHERE id='invite-001'
FOR UPDATE;
```

需要等待 A 完成。

A：

```sql
UPDATE project_invitations
SET accepted_at=now();

COMMIT;
```

释放锁。

B 继续执行，读取最新状态。

---

### 【FOR UPDATE 锁的释放】

锁属于 Transaction，不属于 SQL。

显式 Transaction：

```text
BEGIN
 ↓
FOR UPDATE
 ↓
SQL操作
 ↓
COMMIT / ROLLBACK
 ↓
释放锁
```

隐式 Transaction：

```text
SQL执行
 ↓
自动COMMIT
 ↓
释放锁
```

## 8. Browser Monitor 项目中的 Transaction 使用

### 【Create Project】

创建项目需要同时修改：

```text
projects

project_members

ingestion_keys

allowed_origins

audit_logs
```

因此需要 Transaction 保证完整创建。

---

### 【Ingestion 数据写入】

流程：

```text
BEGIN

telemetry_events

outbox_tasks

COMMIT
```

原因：

事件数据和后台处理任务必须同时存在。

否则：

```text
事件保存成功

但是没有任务处理
```

---

## 9. PostgreSQL Transaction 与 Redis 的边界

PostgreSQL：

```text
telemetry_events

outbox_tasks
```

属于核心业务数据，需要可靠提交。

Redis：

```text
统计数据

缓存数据
```

属于辅助数据。

两个系统不能共享同一个 Transaction。

因此：

```text
PostgreSQL COMMIT成功

Redis更新失败
```

不会回滚 PostgreSQL。

通常通过：

```text
异步任务
重试机制
最终一致性
```

处理辅助数据。
