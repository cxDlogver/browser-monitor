# 服务端数据管理源码学习-2

## Transaction（事务）

### 【Transaction 解决业务操作无法完整执行的问题】

服务端中的一次业务操作，通常不是修改一张表或者执行一条 SQL（Structured Query Language，结构化查询语言）即可完成。

例如 Browser Monitor 创建项目时，需要同时完成：

```text
创建 projects 数据

创建 project_members 数据

创建 ingestion_keys 数据

创建 allowed_origins 数据

记录 audit_logs
```

这些数据库修改共同表示一个业务事实：

```text
一个完整 Project 创建成功
```

如果没有 Transaction（事务），其中一步失败时可能出现：

```text
projects 创建成功

但是 project_members 创建失败
```

此时数据库虽然没有报错，但业务状态已经不完整。

Transaction 的作用就是把多个相关数据库操作放入同一个执行范围，使这些操作作为一个整体处理：

```text
全部成功
    ↓
COMMIT（提交）

或者

任意失败
    ↓
ROLLBACK（回滚）
```

---

### 【Transaction 的执行过程】

#### _1. SQL 执行后是否立即修改数据库_

Transaction 中 SQL 并不是等待 COMMIT 后才执行。

实际过程：

```text
执行 SQL
    ↓
产生数据修改
    ↓
修改属于当前 Transaction
    ↓
COMMIT
    ↓
成为数据库最终状态
```

例如：

```sql
BEGIN;

UPDATE projects
SET name='B项目'
WHERE id=1;
```

此时当前 Transaction 已经产生修改，但是其他 Transaction 不一定能够看到这个未提交的数据。

执行：

```sql
COMMIT;
```

修改才正式提交。

---

#### _2. ROLLBACK 如何撤销修改_

如果 Transaction 执行过程中发生错误：

```sql
ROLLBACK;
```

数据库会取消当前 Transaction 中产生的修改。

PostgreSQL 内部通过 MVCC（Multi-Version Concurrency Control，多版本并发控制）和 WAL（Write Ahead Logging，预写日志）等机制保证数据恢复能力。

当前阶段可以理解为：

```text
COMMIT
确认当前修改

ROLLBACK
放弃当前修改
```

---

### 【Transaction 保证数据可靠性的四个机制】

#### _1. Atomicity（原子性）保证操作不会完成一半_

原子性表示：

> 一个业务操作中的多个数据库修改，要么全部成功，要么全部失败。

例如接受项目邀请：

```sql
INSERT INTO project_members(...);
```

表示用户加入项目。

```sql
UPDATE project_invitations
SET accepted_at=now();
```

表示邀请已经接受。

如果没有 Transaction：

```text
INSERT 成功

UPDATE 失败
```

会产生：

```text
用户已经加入项目

但是邀请仍然显示未接受
```

使用 Transaction：

```sql
BEGIN;

INSERT project_members;

UPDATE project_invitations;

COMMIT;
```

失败时：

```sql
ROLLBACK;
```

恢复到操作开始前状态。

---

#### _2. Consistency（一致性）保证数据符合规则_

一致性表示数据库执行前后，都应该满足数据库约束和业务规则。

它依赖：

```text
Constraint（约束）

Transaction（事务）

Business Logic（业务逻辑）
```

Transaction 本身不知道业务含义。

例如：

```sql
UPDATE projects SET name='test';
```

数据库可以判断字段格式、唯一性等规则，但是无法判断产品是否允许这个名称。

---

#### _3. Isolation（隔离性）控制并发访问_

隔离性解决多个请求同时访问数据库时的数据可见性问题。

例如：

```text
请求 A 接受 invite-001

请求 B 同时接受 invite-001
```

两个请求如果同时读取未更新的数据，都可能认为邀请仍然有效。

因此需要 Lock（锁）等并发控制机制。

---

#### _4. Durability（持久性）保证提交后的数据保存_

持久性表示：

> Transaction 提交成功后，数据不会因为普通故障丢失。

执行：

```sql
COMMIT;
```

数据库确认提交后，数据进入可靠保存状态。

---

### 【PostgreSQL pg 方式实现 Transaction】

Browser Monitor 底层使用 node-postgres（pg）。

典型流程：

```text
Pool（连接池）
    ↓
获取 Client（数据库连接）
    ↓
BEGIN
    ↓
执行 SQL
    ↓
COMMIT / ROLLBACK
    ↓
release 释放连接
```

代码：

```ts
const client = await pool.connect();

try {
  await client.query('BEGIN');

  await client.query(sql1);
  await client.query(sql2);

  await client.query('COMMIT');

} catch(error) {
  await client.query('ROLLBACK');
} finally {
  client.release();
}
```

Transaction 必须绑定同一个 Client。

错误方式：

```ts
pool.query('BEGIN');
pool.query(sql1);
pool.query(sql2);
pool.query('COMMIT');
```

原因：连接池可能分配不同连接，多个 SQL 不一定属于同一个 Transaction。

### 【Drizzle db 方式实现 Transaction】

项目使用 Drizzle 管理数据库：

```ts
drizzle(pool,{schema})
```

Drizzle 提供：

```ts
await db.transaction(async(tx)=>{

  await tx.insert(projects);

  await tx.insert(projectMembers);

});
```

本质仍然对应 PostgreSQL：

```text
BEGIN

SQL执行

COMMIT / ROLLBACK
```

区别：

```text
pg
直接控制连接、SQL、锁

Drizzle
提供类型安全的数据库操作封装
```

### 【Transaction 与 Lock（锁）的关系】

Transaction 和 Lock 解决不同问题：

Transaction：

```text
保证一次业务操作完整
```

Lock：

```text
避免多个请求同时修改同一份数据产生冲突
```

例如两个请求同时接受同一个邀请，需要 Transaction 保证修改完整，同时需要 Lock 保证只有一个请求修改成功。

---

### 【PostgreSQL FOR UPDATE 行锁机制】

FOR UPDATE 用于锁定查询结果对应的数据行。

例如：

```text
project_invitations

id = invite-001

accepted_at = NULL
```

请求 A：

```sql
BEGIN;

SELECT *
FROM project_invitations
WHERE id='invite-001'
FOR UPDATE;
```

数据库锁住该行。

请求 B：

```sql
SELECT *
FROM project_invitations
WHERE id='invite-001'
FOR UPDATE;
```

需要等待 A 的 Transaction 结束。

A：

```sql
UPDATE project_invitations
SET accepted_at=now();

COMMIT;
```

释放锁后，B 才继续执行。

锁属于 Transaction，不属于 SQL。

显式 Transaction：

```text
BEGIN
 ↓
FOR UPDATE
 ↓
业务 SQL
 ↓
COMMIT / ROLLBACK
 ↓
释放锁
```

隐式 Transaction：

```text
SQL执行
 ↓
自动 COMMIT
 ↓
释放锁
```

### 【Browser Monitor 项目中的 Transaction】

#### _Create Project_

创建项目涉及：

```text
projects
project_members
ingestion_keys
allowed_origins
audit_logs
```

这些数据共同表示项目创建完成，因此需要放在同一个 Transaction 中。

#### _Ingestion 数据写入_

核心流程：

```text
BEGIN

telemetry_events

outbox_tasks

COMMIT
```

原因：事件数据和后续处理任务必须同时存在。

否则可能出现：

```text
事件保存成功

但是没有后台处理任务
```

#### _PostgreSQL 与 Redis 边界_

PostgreSQL：

```text
telemetry_events
outbox_tasks
```

属于核心业务事实，需要可靠提交。

Redis：

```text
统计数据
缓存数据
```

属于辅助数据。

Redis 不属于 PostgreSQL Transaction，因此：

```text
PostgreSQL COMMIT成功

Redis更新失败
```

不会回滚 PostgreSQL。

通常通过异步任务、重试机制实现最终一致性（Eventual Consistency）。
