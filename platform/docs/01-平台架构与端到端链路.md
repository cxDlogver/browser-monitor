# Browser Monitor 平台架构与端到端链路

Browser Monitor Platform 不是 SDK 的附属接口，而是监控数据从“浏览器事实”变成“可查询结论”的服务端系统。SDK 解决的是页面内采集安全、上下文归属和可靠发送；Platform 继续完成项目身份确认、数据持久化、异步投影、指标计算、时间聚合和可视化。只有两侧连在一起，用户才可以从某个页面的性能异常一路追溯到原始事件。

## 1. 系统边界

### 【三个项目如何协作】

完整系统位于同一个 `browser-monitor/` workspace，但包含三个有明确边界的项目：

| 项目 | 主要输入 | 主要输出 | 不承担的责任 |
| --- | --- | --- | --- |
| `sdk/` | 浏览器 API、业务埋点和接入配置 | 协议 2.0 事件批次 | 数据库存储、指标看板和账号权限 |
| `protocol/` | 共同认可的数据约束 | Zod Schema、类型、常量和 fixture | 采集逻辑、业务处理和网络请求 |
| `platform/` | 协议批次与管理操作 | 原始数据、指标、查询接口和可视化页面 | 页面 Hook 和浏览器运行时采集 |

Protocol 位于二者之间，不是复制到 SDK 和服务端的类型文件。SDK、API 和 Worker 都直接依赖 `@browser-monitor/protocol`，因此字段、枚举或版本变化会在同一个 workspace 的类型检查和协议测试中暴露。

### 【业务应用需要做什么】

业务应用创建 Monitor 时提供 `app.name`、版本、环境、稳定页面名称和平台生成的 DSN。它不需要实现上报接口，也不需要开发监控看板。DSN 中的 public key 用于把公开采集请求映射到平台项目；管理页面仍然使用登录 Session 和项目成员权限，两套身份不能互换。

```ts
createMonitor({
  app: {
    name: 'customer-center',
    version: '1.4.0',
    environment: 'production',
  },
  view: {
    resolveRouteName: ({ pathname }) => pathname,
  },
  transport: {
    dsn: 'https://monitor.example.com/api/v2/ingest/bm_pk_xxx/envelopes',
  },
});
```

`transport.dsn` 是唯一采集地址字段。Platform 负责生成这个地址，SDK 不再保留 `endpoint` 兼容路径，避免同一能力存在两套配置来源。

## 2. Platform 内部结构

### 【运行单元】

```text
platform/
├─ apps/
│  ├─ api/                 # 公开采集、认证、项目管理、分析查询
│  ├─ worker/              # Outbox 消费、数据投影、评级和失败恢复
│  └─ web/                 # 账号、项目设置和数据看板
├─ packages/
│  ├─ database/            # 关系模型、时序表和迁移
│  └─ shared/              # 配置、安全、隐私和阈值规则
├─ infra/                  # Caddy、Compose 和容器镜像
├─ load/                   # 采集容量脚本
└─ docs/                   # 平台链路报告
```

API 与 Worker 是两个独立进程。API 的职责是尽快判定一批数据能否被可靠接收，不在 HTTP 请求中计算复杂指标；Worker 在事务提交之后处理 Outbox，可以独立重启或扩容。Web 不直接连接数据库，只调用带项目权限校验的管理与 Analytics API。

### 【基础设施职责】

Caddy 对外暴露同一站点下的 Web 和 API，减少业务接入时的域名组合。TimescaleDB 同时承载账号、项目等关系数据与遥测时序数据；Redis 承担登录 Session、采集限流、短期查询缓存和运行统计；开发环境使用 Mailpit 接收验证、密码重置和邀请邮件。

## 3. 一条事件的完整路径

### 【总览】

```text
浏览器中的性能变化或业务动作
  ↓
SDK Instrumentation / Collector / Processing
  ↓
TelemetryBatchV2
  ↓ POST /api/v2/ingest/:publicKey/envelopes
API：版本、身份、Origin、限流、事件校验和脱敏
  ↓ 同一数据库事务
telemetry_events + outbox_tasks
  ↓ FOR UPDATE SKIP LOCKED
Worker：领域投影、sequence 合并、服务端评级
  ↓
performance_samples / view_records / custom_event_samples
  ↓ Timescale 连续聚合
分钟与小时 Rollup
  ↓
Analytics API + Redis 15 秒缓存
  ↓
React 总览、性能、页面、事件、原始数据和服务状态页面
```

### 【浏览器到采集接口】

SDK 先把不同来源的浏览器事实转换成统一 `TelemetryEventV2`。Performance、View 和 Custom Event 虽然有不同 payload，但都携带 `eventId`、发生时间、应用身份、Session、View、稳定页面名称和运行环境。Transport 把多条事件组成 `TelemetryBatchV2`，正常运行时使用 Fetch，页面退出时可以使用 Beacon 发送相同 JSON 文档。

采集 API 对 Beacon 的 `text/plain` 字符串和普通 JSON 走同一套解析与校验，不因发送方式不同而形成第二条接收逻辑。请求先确认协议版本和批次头，再解析项目、Origin 和配额，最后逐条验证事件。批次级身份错误会拒绝整个请求；单条 payload 不合法只拒绝对应事件。

### 【可靠接收边界】

API 只有在原始事件和 Outbox 任务同时提交后，才把事件计入 `accepted`。两张表通过一条带 CTE 的 SQL 在同一事务中写入：原始事件插入成功的行才会生成任务。这样 `202` 的含义不是“服务器看到了请求”，而是“服务端已持久保存事件，并留下可恢复的后续处理任务”。

同一 `eventId` 被 SDK 重试发送时计入 `duplicate`，不会生成第二份投影。API 使用请求内去重、项目级 advisory transaction lock 和数据库已有事件检查共同保证幂等；锁按排序后的 eventId 获取，避免重叠批次以不同顺序竞争。

### 【异步处理边界】

Worker 从 `outbox_tasks` 领取任务并把状态改为 `processing`。多实例通过 `FOR UPDATE SKIP LOCKED` 各自领取不同任务；进程在处理过程中退出时，五分钟前遗留的 processing 任务可以再次被领取。领域投影与 `telemetry_events.processed_at` 在同一 Worker 事务中提交，失败则整体回滚。

Performance 会按 `sampleId` 合并多个修订，View 会记录页面开始与结束，自定义事件会保存事件名称和清理后的属性。Worker 处理完成后将 Outbox 标记为 completed，并递增项目的 Analytics 缓存版本，使下一次查询绕过旧缓存。

### 【聚合和查询边界】

明细表按发生时间组织为 Hypertable。连续聚合按一分钟和一小时生成性能、View、自定义事件与遥测数量的查询模型。最近 29 天的精细查询使用明细，跨越更早数据的查询使用小时 Rollup，以避免长时间范围反复扫描全部事件。

Analytics API 在每个入口先检查用户是否属于目标项目，再应用 `from`、`to`、环境、版本、页面和指标过滤。相同项目、过滤条件和缓存版本的结果缓存 15 秒。Worker 每处理成功一条事件就递增版本，所以缓存只是降低重复查询成本，不会长期隐藏新数据。

## 4. 同步链路与异步链路

### 【HTTP 请求结束前必须完成什么】

采集请求返回前必须完成协议版本检查、批次限制、写入键解析、Origin 白名单、项目/IP 限流、逐事件 Schema 校验、应用名称检查、时间范围检查、二次脱敏、幂等判定以及原始事件和 Outbox 的事务提交。任何一个步骤失败，都不能把事件报告为 accepted。

指标评级、分位数聚合和看板查询不在这条同步路径中。它们即使暂时失败，也不应迫使浏览器持续重发已经安全落库的事件。

### 【最终一致如何对用户可见】

数据提交后需要等待 Worker 领取和投影，再由查询接口读取，因此看板不是零延迟强一致。正常情况下，Worker 轮询和 Web 的 15 秒刷新使新数据在约 10～15 秒内可见。服务状态页同时展示最近一分钟接收数、处理数和积压量，用户可以判断等待来自正常异步处理还是 Worker 故障。

## 5. 失败路径和恢复方式

### 【采集阶段失败】

协议不支持、写入键无效、Origin 不允许和事件 Schema 错误属于确定性错误。修改请求之前重复发送不会成功。`408`、`429` 和 `5xx` 才是 SDK 可以有限重试的状态。部分接收响应中的 rejected 项也不会阻止合法事件进入系统。

### 【处理阶段失败】

Worker 失败后将任务恢复为 pending，并按指数退避设置下一次 `available_at`，最长等待五分钟。累计八次仍失败时，任务进入 failed 状态并同步写入 `dead_letter_tasks`。Owner 可以在服务状态页查看错误并触发重试，重试操作会把任务的 attempts 清零并重新放回队列。

### 【平台依赖失败】

`/health/live` 只确认 API 进程存活，`/health/ready` 检查数据库和 Redis 是否可以服务请求。`/internal/metrics` 暴露采集计数、延迟、Outbox 状态和死信数量，供部署环境采集。登录、项目设置和 Analytics 查询依赖 Session；公开 Ingestion 只依赖 DSN、Origin 和限流规则，二者故障面保持分离。

## 6. 从代码定位链路

### 【核心入口】

| 阶段 | 代码位置 |
| --- | --- |
| HTTP 采集入口 | `apps/api/src/ingestion/ingestion.controller.ts` |
| 校验、脱敏和事务写入 | `apps/api/src/ingestion/ingestion.service.ts` |
| Redis 令牌桶 | `apps/api/src/ingestion/rate-limiter.service.ts` |
| Outbox 领取与恢复 | `apps/worker/src/outbox-worker.ts` |
| 领域投影与服务端评级 | `apps/worker/src/processor.ts` |
| 表、Hypertable 和分钟 Rollup | `packages/database/migrations/0001_platform.sql` |
| 小时级分层 Rollup 与聚合策略 | `packages/database/migrations/0002_hourly_aggregates.sql` |
| 实时聚合修正 | `packages/database/migrations/0003_realtime_aggregates.sql` |
| Analytics 查询 | `apps/api/src/analytics/analytics.service.ts` |
| Web 路由和看板 | `apps/web/src/App.tsx`、`apps/web/src/pages/` |

阅读完整实现时，应沿着这张表从上到下追踪同一个 `eventId`。这样看到的是事件状态如何变化，而不是一组彼此孤立的目录。
