# 服务端数据管理源码学习-2

## 7. Transaction（事务）把多个数据库操作组织成一个可靠的业务执行单元

前面的数据管理部分已经依次建立了 Database、Connection、SQL、Schema、Constraint、Index 等基础能力。到这里，应用已经能够把业务事实保存到 PostgreSQL 中，并通过约束保证单条数据和数据关系合法，通过 Index 为常见 Query 提供更高效的访问路径。

但是这些能力仍然没有解决一个非常重要的问题：

> 一次真实业务操作通常不是执行一条 SQL，而是需要连续修改多张表、多个 Row。即使每一条 SQL 单独执行都没有问题，也可能因为中间某一步失败，使数据库停留在一个业务上不完整的状态。

例如 Browser Monitor 创建一个 Project 时，需要同时完成：

~~~text
创建 projects
↓
创建 project_members
↓
创建 ingestion_keys
↓
创建 allowed_origins
↓
记录 audit_logs
~~~

这些修改共同表达一个完整业务事实：

~~~text
一个完整可使用的 Project 已经创建
~~~

如果没有 Transaction（事务），可能出现：

~~~text
projects               已创建
project_members        已创建
ingestion_keys         创建失败
allowed_origins        尚未执行
audit_logs             尚未执行
~~~

从数据库角度看，前两条 INSERT 可能都完全合法。

但从业务角度看，此时已经产生了不完整的 Project：

~~~text
Project 存在
Owner 存在
但是没有 Ingestion Key
也没有默认 Allowed Origin
~~~

所以数据管理不能只关注：

~~~text
一条 SQL 能不能成功
~~~

还必须继续关注：

~~~text
一组共同描述业务状态变化的 SQL
能不能作为一个整体成功
~~~

Transaction（事务）就是用来解决这一层问题的。

PostgreSQL 官方把事务描述为：将多个步骤组合成一个整体，从其他并发事务的角度看，这组操作要么全部发生，要么完全不发生；事务执行过程中产生的中间状态不会作为已经提交的数据库状态暴露出去。

---

这一章不再把 Transaction 当成一组彼此独立的术语，而是沿着“业务边界 → 数据库执行 → 可靠性目标 → 并发交叉 → 跨系统可靠性 → 工程落地”逐层展开。

~~~text
Transaction
├── 第一层：Transaction Boundary
│   └── 先确定哪些数据变化属于同一个业务状态变化
├── 第二层：Execution Model
│   └── 再理解 BEGIN / COMMIT / ROLLBACK、Connection 与 SAVEPOINT
├── 第三层：ACID
│   └── 明确事务分别要保证 Atomicity / Consistency / Isolation / Durability
├── 第四层：Concurrency Intersection
│   └── 只界定 Transaction 与并发控制的关系；MVCC、Isolation Level、Lock、Deadlock 与 Retry 统一进入第 8 章
├── 第五层：System Boundary
│   └── 解释单个 PostgreSQL Transaction 的系统边界，以及 Producer 侧如何用 Transactional Outbox 避免 Dual Write
└── 第六层：Engineering Practice
    └── 最后回到 Drizzle、Migration、项目事务类型和事务设计方法
~~~

因此这一章的核心不是“记住 BEGIN / COMMIT”，而是建立：

~~~text
业务状态变化
↓
Transaction Boundary
↓
数据库执行模型
↓
ACID
↓
并发与系统边界
↓
可靠性组合
↓
项目工程实现
~~~

### 【第一层：Transaction Boundary 从业务状态变化中确定原子执行范围】

第一层先解决最根本的问题：Transaction 到底应该包住什么。判断标准不是 SQL 数量，而是哪些数据变化共同表达一个不可拆分的业务状态变化。

~~~text
Business Operation
↓
识别必须共同成立的数据事实
↓
Transaction Boundary
↓
共同 COMMIT / ROLLBACK
~~~

#### <u>1. Transaction 的核心不是“多条 SQL”，而是“一个业务状态变化”</u>

**1. Transaction Boundary（事务边界）决定哪些操作必须共同成功**
Transaction Boundary（事务边界）表示：

> 一个事务从哪里开始、在哪里结束，以及哪些数据库操作必须共同 COMMIT（提交）或者共同 ROLLBACK（回滚）。

事务设计首先不能简单理解为：

~~~text
有多条 SQL
↓
所以一定使用 Transaction
~~~

例如：

~~~text
查询 Project
查询 Project Members
查询 Threshold
~~~

虽然执行了多条 SELECT，但如果它们只是几个独立读取，不要求形成同一个时间点上的一致视图，那么未必需要主动建立显式 Transaction。

反过来，有些操作虽然 SQL 数量不多，却天然属于一个业务事务。

例如接受 Invitation：

~~~text
创建 / 更新 project_members
+
把 project_invitations.accepted_at 标记为已接受
~~~

如果只完成第一步：

~~~text
User 已经成为 Project Member
但是 Invitation 仍然显示未接受
~~~

业务状态就出现矛盾。

因此判断事务边界真正应该问的是：

~~~text
这几次数据变化
是否共同表达同一个业务状态变化？
↓
如果只成功其中一部分
数据库是否会进入一个业务上错误的中间状态？
↓
如果答案是“会”
这些操作就应该考虑放在同一个 Transaction Boundary 中
~~~

**2. ProjectsService.create() 是最直接的事务边界示例**
当前源码位于：

~~~text
browser-monitor/platform/apps/api/src/projects/projects.service.ts
~~~

核心代码：

~~~ts
const client = await this.database.pool.connect();
try {
  await client.query('BEGIN');
  const project = await client.query<{ id: string }>(
    'INSERT INTO projects(display_name, app_name, user_hash_salt) VALUES ($1, $2, $3) RETURNING id',
    [displayName.trim(), appName.trim(), userHashSalt],
  );
  const projectId = project.rows[0]!.id;
  await client.query(
    "INSERT INTO project_members(project_id, user_id, role) VALUES ($1, $2, 'owner')",
    [projectId, userId],
  );
  await client.query(
    "INSERT INTO ingestion_keys(project_id, public_key, label) VALUES ($1, $2, 'default')",
    [projectId, publicKey],
  );
  await client.query(
    'INSERT INTO allowed_origins(project_id, origin) VALUES ($1, $2)',
    [projectId, defaultOrigin],
  );
  await client.query(
    "INSERT INTO audit_logs(project_id, actor_user_id, action, detail) VALUES ($1, $2, 'project.created', jsonb_build_object('appName', $3::text))",
    [projectId, userId, appName.trim()],
  );
  await client.query('COMMIT');
} catch (error) {
  await client.query('ROLLBACK');
  throw error;
} finally {
  client.release();
}
~~~

这里的逻辑不是：

~~~text
因为有五条 SQL
所以套一个 BEGIN / COMMIT
~~~

而是：

~~~text
Project
+
Owner Membership
+
Default Ingestion Key
+
Default Allowed Origin
+
Audit Log
~~~

共同定义：

~~~text
Project 创建完成
~~~

因此整个 create() 内真正需要被数据库原子保护的是：

~~~text
BEGIN
↓
创建 Project
↓
创建 Owner Membership
↓
创建 Ingestion Key
↓
创建 Allowed Origin
↓
创建 Audit Log
↓
COMMIT
~~~

如果其中任何一步失败：

~~~text
ROLLBACK
~~~

恢复到事务开始之前的数据库状态。

这就是事务边界与业务边界的直接对应。

### 【第二层：Transaction Execution Model 决定事务怎样在同一个 Connection 上真正执行】

确定事务边界以后，下一层才是数据库执行模型：单条 SQL 为什么也有事务、显式 Transaction 如何开始和结束、为什么必须绑定同一个 Connection，以及 SAVEPOINT 在事务内部解决什么问题。

~~~text
Transaction Boundary
↓
固定 Database Connection
↓
BEGIN
↓
SQL 真正执行
↓
COMMIT / ROLLBACK
↓
release Connection
~~~

#### <u>1. PostgreSQL 中每一条 SQL 本身也运行在 Transaction 中</u>

**1. 没有显式 BEGIN 不代表没有 Transaction**
例如：

~~~sql
UPDATE projects
SET enabled = false
WHERE id = $1;
~~~

应用虽然没有写：

~~~sql
BEGIN;
~~~

这条 SQL 仍然运行在一个数据库事务中。

PostgreSQL 会表现得像：

~~~text
隐式开始 Transaction
↓
执行 UPDATE
↓
执行成功
↓
自动 COMMIT
~~~

这种使用方式通常称为 Autocommit（自动提交）。

所以：

~~~text
没有手写 BEGIN
≠
数据库没有 Transaction
~~~

更准确的是：

~~~text
普通单条 SQL
↓
数据库自动建立事务范围
↓
SQL 成功后自动提交
~~~

**2. Explicit Transaction（显式事务）让多条 SQL 共用同一个事务**
当业务需要：

~~~text
SQL 1
SQL 2
SQL 3
~~~

共同成功时，才需要显式：

~~~sql
BEGIN;
SQL 1;
SQL 2;
SQL 3;
COMMIT;
~~~

因此单条 SQL 和多条 SQL 的区别可以理解成：

~~~text
单条 SQL
↓
数据库自动管理一个很短的 Transaction

多条 SQL 共同组成一个业务操作
↓
应用显式控制 Transaction Boundary
~~~

这也解释了为什么当前项目中很多简单 UPDATE / DELETE 直接使用：

~~~ts
this.database.pool.query(...)
~~~

而复杂业务状态变化会先：

~~~ts
const client = await this.database.pool.connect();
await client.query('BEGIN');
~~~

#### <u>2. BEGIN、COMMIT 与 ROLLBACK 控制 Transaction 生命周期</u>

**1. BEGIN 表示从这里开始进入同一个事务范围**
~~~sql
BEGIN;
~~~

执行后：

~~~text
后续 SQL
↓
进入当前 Transaction
~~~

直到：

~~~text
COMMIT
或者
ROLLBACK
~~~

事务才真正结束。

**2. SQL 在 COMMIT 前已经执行，不是等 COMMIT 才开始执行**
这是事务最容易产生误解的地方之一。

错误理解：

~~~text
BEGIN
↓
SQL 1
SQL 2
SQL 3
↓
这些 SQL 只是被“记下来”
↓
COMMIT
↓
数据库才真正执行 SQL
~~~

实际不是这样。

例如：

~~~sql
BEGIN;
UPDATE projects
SET enabled = false
WHERE id = 'project-a';
SELECT enabled
FROM projects
WHERE id = 'project-a';
~~~

当前 Transaction 自己已经可以读取到：

~~~text
enabled = false
~~~

说明前面的 UPDATE 已经真正执行。

只是这个修改：

~~~text
尚未 COMMIT
↓
没有成为其他 Transaction 可以按照已提交规则观察到的最终状态
~~~

因此正确模型是：

~~~text
BEGIN
↓
SQL 真正执行
↓
当前 Transaction 内部状态发生变化
↓
后续 SQL 可以继续基于这个新状态执行
↓
COMMIT
↓
整个 Transaction 成为已提交状态
~~~

**3. COMMIT 确认当前事务最终成功**
~~~sql
COMMIT;
~~~

表示：

~~~text
当前 Transaction 正常结束
↓
其中所有修改共同成为已提交数据
~~~

所以 COMMIT 的意义不是“执行 SQL”，而是：

~~~text
确认这个 Transaction 的整体结果
~~~

**4. ROLLBACK 放弃当前事务产生的修改**
假设：

~~~text
BEGIN
↓
SQL 1 成功
↓
SQL 2 成功
↓
SQL 3 失败
~~~

如果业务要求三条 SQL 共同成功，就应该：

~~~sql
ROLLBACK;
~~~

最终数据库不会留下：

~~~text
SQL 1 的业务修改
SQL 2 的业务修改
但 SQL 3 没有完成
~~~

而是放弃这个 Transaction 的整体修改。

当前项目中的经典结构：

~~~ts
try {
  await client.query('BEGIN');
  await client.query(sql1);
  await client.query(sql2);
  await client.query('COMMIT');
} catch (error) {
  await client.query('ROLLBACK');
  throw error;
} finally {
  client.release();
}
~~~

这里的 catch 并不只是 JavaScript 异常处理习惯。

它和 PostgreSQL Transaction 状态直接相关。

当 Transaction 中某条 SQL 发生错误以后，PostgreSQL 通常会把当前事务标记为失败状态。之后不能假装什么都没发生继续正常 COMMIT，而应该 ROLLBACK 当前事务，结束失败状态。

#### <u>3. SAVEPOINT 允许在一个 Transaction 内部建立局部回滚点</u>

完整事务体系中还有一个重要概念：

SAVEPOINT（保存点）。

假设一个较长 Transaction 中，希望：

~~~text
前面的操作保留
只撤销中间某一小段
~~~

可以：

~~~sql
BEGIN;
INSERT INTO projects(...);
SAVEPOINT before_member;
INSERT INTO project_members(...);
ROLLBACK TO before_member;
INSERT INTO project_members(...);
COMMIT;
~~~

这里：

~~~sql
ROLLBACK TO before_member;
~~~

不会结束整个 Transaction。

它只把：

~~~text
SAVEPOINT before_member
之后产生的修改
~~~

撤销。

因此可以区分：

~~~text
ROLLBACK
↓
结束整个 Transaction

ROLLBACK TO SAVEPOINT
↓
只回到 Transaction 内部某个保存点
~~~

当前 Browser Monitor 没有直接使用 SAVEPOINT，但它是事务完整知识体系的一部分。

Drizzle 的 Nested Transaction（嵌套事务）能力，本质上通常也是通过数据库 Savepoint 这一类机制实现，而不是创建真正独立的第二个 PostgreSQL 顶层事务。

#### <u>4. 一个 Transaction 必须始终绑定同一个 Database Connection</u>

**1. Connection Pool 中同时存在多个 PostgreSQL Connection**
当前项目数据库初始化位于：

~~~text
browser-monitor/platform/packages/database/src/client.ts
~~~

源码：

~~~ts
const pool = new Pool({
  connectionString,
  max: 20,
  idleTimeoutMillis: 30_000,
  connectionTimeoutMillis: 5_000,
});
~~~

Pool（Connection Pool，连接池）不是一个单独 Connection。

更准确地理解：

~~~text
Application
↓
Pool
├── Connection A
├── Connection B
├── Connection C
├── ...
└── 最多到 max
↓
PostgreSQL
~~~

普通单条 SQL：

~~~ts
await pool.query(sql);
~~~

只需要：

~~~text
Pool 找一个可用 Connection
↓
执行这条 SQL
↓
执行完成
~~~

但 Transaction 不一样。

Transaction 的：

~~~text
BEGIN
SQL 1
SQL 2
SQL 3
COMMIT
~~~

全部必须发生在：

~~~text
同一个 PostgreSQL Connection
~~~

上。

**2. pool.connect() 的作用是为事务拿到一个固定 Client**
当前项目事务统一先：

~~~ts
const client = await this.database.pool.connect();
~~~

这里的 Client 可以理解为：

~~~text
从 Pool 中临时借出的固定 Connection
~~~

然后整个 Transaction 都通过它执行：

~~~ts
await client.query('BEGIN');
await client.query(sql1);
await client.query(sql2);
await client.query(sql3);
await client.query('COMMIT');
~~~

因此真正结构是：

~~~text
Pool
↓
pool.connect()
↓
Client A / Connection A
├── BEGIN
├── SQL 1
├── SQL 2
├── SQL 3
└── COMMIT
↓
client.release()
↓
Connection A 返回 Pool
~~~

**3. 不能用多个 pool.query() 拼接一个事务**
错误代码：

~~~ts
await pool.query('BEGIN');
await pool.query(sql1);
await pool.query(sql2);
await pool.query('COMMIT');
~~~

问题在于：

~~~text
pool.query()
每次都由 Pool 自己选择可用 Connection
~~~

于是可能真实执行成：

~~~text
BEGIN  → Connection A
SQL 1  → Connection C
SQL 2  → Connection B
COMMIT → Connection A
~~~

虽然代码顺序看起来像一个 Transaction，但数据库层实际不是同一个 Connection。

node-postgres 官方专门强调：一个 Transaction 中的所有 Statement（语句）必须使用同一个 Client，不能用 pool.query() 来组织 Transaction。

**4. finally 中的 client.release() 防止连接泄漏**
当前项目：

~~~ts
finally {
  client.release();
}
~~~

无论：

~~~text
COMMIT 成功
ROLLBACK
业务抛异常
数据库报错
~~~

最终都要尽可能把 Connection 归还 Pool。

如果持续：

~~~text
pool.connect()
↓
没有 release
~~~

会逐步形成：

~~~text
Connection A 被占用
Connection B 被占用
Connection C 被占用
...
↓
Pool 中没有可用 Connection
↓
新 Request 开始等待
↓
数据库访问延迟持续增加
~~~

所以：

~~~text
Transaction 生命周期
和
Connection 生命周期
~~~

在 node-postgres 的手动事务代码中必须一起管理。

### 【第三层：ACID 从四个维度定义 Transaction 的可靠性目标】

执行模型解决“事务怎样运行”，ACID 继续回答“一个可靠事务究竟要保证什么”。四个字母不是并列背诵点，而是分别处理局部失败、合法状态、并发可见性和故障恢复四类问题。

~~~text
Transaction
├── Atomicity：不能只完成一部分
├── Consistency：结束后仍满足系统规则
├── Isolation：并发事务之间如何观察和影响
└── Durability：COMMIT 后如何面对故障仍然存在
~~~

#### <u>1. ACID 不是四句定义，而是 Transaction 需要解决的四类问题</u>

ACID 分别是：

~~~text
Atomicity
Consistency
Isolation
Durability
~~~

如果只背：

~~~text
原子性
一致性
隔离性
持久性
~~~

很容易把它们混在一起。

更有用的方式是分别问：

~~~text
Atomicity
一次业务操作会不会只完成一部分？

Consistency
事务结束后数据是否仍满足系统规则？

Isolation
多个 Transaction 同时执行时互相能看到什么、会不会冲突？

Durability
COMMIT 已经成功的数据，数据库崩溃后能不能恢复？
~~~

#### <u>2. Atomicity（原子性）保证 Transaction 不会停留在“只成功一半”</u>

Atomicity 表示：

> 一个 Transaction 中的数据库修改，对外表现为不可拆分的整体：要么共同 COMMIT，要么共同 ROLLBACK。

当前 Project Create 可以画成：

~~~text
完整 Project
├── projects
├── project_members
├── ingestion_keys
├── allowed_origins
└── audit_logs
~~~

如果没有 Atomicity：

~~~text
projects               成功
project_members        成功
ingestion_keys         失败
allowed_origins        未执行
audit_logs             未执行
~~~

业务层可能得到一个半成品 Project。

有 Transaction 后：

~~~text
BEGIN
↓
Project
↓
Member
↓
Key
↓
Origin
↓
Audit
↓
全部成功
↓
COMMIT
~~~

或者：

~~~text
BEGIN
↓
Project
↓
Member
↓
Key 失败
↓
ROLLBACK
~~~

最终不会把前两步保留下来。

**1. replaceOrigins() 说明 Atomicity 不是只用于“创建”**
当前 replaceOrigins()：

~~~text
BEGIN
↓
DELETE 当前 Project 的旧 Origins
↓
逐个 INSERT 新 Origins
↓
INSERT Audit Log
↓
COMMIT
~~~

如果没有 Transaction：

~~~text
DELETE 成功
↓
旧 Origins 已经全部删除
↓
第二个 INSERT 失败
~~~

Project 可能突然失去全部合法 Origin 配置。

所以业务上真正的原子操作是：

~~~text
把旧 Origin 集合
整体替换成新 Origin 集合
~~~

而不是：

~~~text
DELETE 是一个操作
INSERT 1 是一个操作
INSERT 2 是一个操作
~~~

**2. rotateKey() 说明状态迁移也需要 Atomicity**
当前 rotateKey()：

~~~text
BEGIN
↓
现有 active Key
设置 expires_at = now() + 24 hours
↓
INSERT 新 Key
↓
INSERT Audit Log
↓
COMMIT
~~~

业务想表达：

~~~text
开始从旧 Key 向新 Key 过渡
~~~

如果只完成：

~~~text
旧 Key 开始过期
~~~

而：

~~~text
新 Key 创建失败
~~~

就可能让系统进入错误过渡状态。

所以 Atomicity 保护的是：

~~~text
一个完整状态迁移
~~~

而不仅仅是“几条 INSERT”。

**3. retryDeadLetter() 说明不同 Table 之间也可以是一个原子状态变化**
当前 retryDeadLetter()：

~~~text
BEGIN
↓
DELETE dead_letter_tasks
↓
UPDATE outbox_tasks
status = pending
attempts = 0
available_at = now()
↓
COMMIT
~~~

业务语义：

~~~text
这个 Task 从 Dead Letter
重新回到可执行 Outbox
~~~

如果只 DELETE Dead Letter，却没有恢复 Outbox：

~~~text
失败任务记录消失
任务又没有回到正常队列
~~~

所以这两个 Table 的变化必须共同提交。

#### <u>3. Consistency（一致性）不是 Transaction 自动理解业务，而是多种机制共同维护合法状态</u>

Consistency 可以理解成：

> 数据库从一个合法状态变化到另一个合法状态，最终仍满足数据库约束和业务规则。

这里最容易出现一个误区：

~~~text
有 Transaction
↓
数据库一定 Consistent
~~~

这并不完整。

例如：

~~~text
project_members.project_id
必须引用真实 Project
~~~

依赖的是：

~~~text
Foreign Key Constraint
~~~

再例如：

~~~text
同一个 Project + Version
不能重复
~~~

依赖：

~~~text
UNIQUE Constraint / Unique Index
~~~

再例如：

~~~text
一个 Project 创建完成时
必须具有 Owner、Default Key、Default Origin
~~~

这部分规则属于：

~~~text
Application Business Logic
~~~

PostgreSQL 并不知道：

~~~text
“没有 Default Origin 的 Project 在业务上不能算创建完成”
~~~

除非应用或数据库结构专门把这条业务规则表达出来。

因此完整关系是：

~~~text
Business Logic
+
Schema
+
Constraint
+
Transaction
+
Concurrency Control
↓
共同维持 Consistency
~~~

Transaction 的作用是：

~~~text
如果应用决定 A、B、C 必须共同变化
↓
数据库提供机制让 A、B、C 一起提交或回滚
~~~

但 Transaction 不会自动判断：

~~~text
你的业务规则是不是写对了
金额是不是算错了
权限是不是判断错了
状态机是不是设计错了
~~~

这也是 ACID 中 Consistency 最容易被过度简化的地方。

#### <u>4. Isolation（隔离性）解决多个 Transaction 同时执行时的数据可见性和冲突</u>

到目前为止，所有例子都像：

~~~text
一个 Request
↓
一个 Transaction
↓
数据库
~~~

但真实服务端是：

~~~text
Request A → Transaction A
Request B → Transaction B
Request C → Transaction C
Worker 1  → Transaction D
Worker 2  → Transaction E
~~~

这些 Transaction 可能同时访问相同 Table，甚至相同 Row。

Isolation（隔离性）关注：

> 多个 Transaction 并发执行时，一个 Transaction 能看到另外一个 Transaction 的哪些数据变化，以及发生冲突时应该等待、失败还是继续读取其他版本。

这里开始进入数据库 Concurrency Control（并发控制）。

#### <u>5. Durability（持久性）解决 COMMIT 成功以后数据库崩溃怎么办</u>

ACID 最后一项是 Durability（持久性）。

它回答：

~~~text
PostgreSQL 已经向 Application 返回
COMMIT 成功

下一秒数据库进程崩溃
甚至服务器发生故障

已经确认成功的 Transaction
还能不能恢复？
~~~

如果 COMMIT 成功的数据一崩溃就消失，那么：

~~~text
Application 已经收到成功
↓
用户认为操作完成
↓
数据库恢复后数据不存在
~~~

系统就不能称为可靠提交。

因此 PostgreSQL 还需要：

WAL（Write-Ahead Logging，预写日志）。

当前阶段只建立它的位置：

~~~text
Transaction 修改数据
↓
COMMIT
↓
PostgreSQL 需要保证足够的恢复信息
已经进入可靠存储路径
↓
后续即使发生 Crash
也能根据 WAL 等机制恢复已提交状态
~~~

更底层的：

~~~text
WAL Record
LSN
Checkpoint
fsync
Crash Recovery
~~~

应该放到后面的数据库可靠性章节，不在 Transaction 章节一次深入。

所以 ACID 的四个问题可以重新放回整体：

~~~text
Atomicity
一次事务不能只完成一部分

Consistency
事务结束后数据仍满足系统规则

Isolation
并发事务之间怎样观察和协调

Durability
已经 COMMIT 的状态怎样面对故障继续存在
~~~

---

### 【第四层：Transaction 遇到并发以后进入独立的 Concurrency Control 问题】

前三层解决的是一个业务操作如何形成可靠的 Transaction Boundary。到了并发环境，还会出现另一个独立问题：

~~~text
Transaction A
+
Transaction B
↓
同时访问同一份业务状态
↓
即使两个 Transaction 各自都满足 Atomicity
仍然可能发生 Race Condition
~~~

因此需要先建立边界：

~~~text
Transaction
↓
保证一次业务状态变化作为完整执行单元

Concurrency Control
↓
保证多个 Transaction 同时运行时仍然满足业务不变量
~~~

ACID 中的 Isolation 仍然属于 Transaction 的可靠性目标，它回答：

~~~text
多个并发 Transaction
彼此允许看到什么状态
彼此的执行结果允许怎样相互影响
~~~

但 Isolation 的具体实现和工程控制机制不在本章重复展开。PostgreSQL 中的 MVCC、Snapshot、Isolation Level、Row Lock、Advisory Lock、Deadlock、Retry，以及项目中的 Critical Section，统一进入第 8 章 **Concurrency Control**。

因此这里不应形成：

~~~text
Transaction
= MVCC
= Lock
~~~

而应该形成前置关系：

~~~text
Transaction Boundary
↓
ACID
↓
Isolation 提出并发可靠性目标
↓
多个 Transaction 真正发生交叉
↓
进入 Concurrency Control
├── MVCC / Snapshot
├── Isolation Level
├── Explicit Lock
├── Constraint
├── Deadlock / Retry
└── Idempotency
~~~

这也意味着：

- Transaction 不等于 Lock；
- Isolation 不等于 Explicit Lock；
- 一个 Transaction 自身原子，并不代表多个 Transaction 并发执行后业务结果一定正确。

详细机制与 Browser Monitor 中 Invitation、Ingestion、Performance Sample、Threshold、Outbox Worker 等并发案例统一见第 8 章，避免在 Transaction 章节和 Concurrency Control 章节重复维护两套解释。

### 【第五层：System Boundary 说明 Local Transaction 的边界，并用 Transactional Outbox 保证 Producer 侧原子性】

数据库内部正确以后，边界继续向外扩展到 Redis、Mailer 和 Worker。此时一个 PostgreSQL Transaction 已经不能覆盖整个系统，需要把局部事务与异步可靠性、重复执行和跨系统一致性组合起来理解。

~~~text
PostgreSQL Local Transaction
↓
保证本地核心数据完整
↓
Outbox
↓
Worker
↓
Retry + Idempotency
↓
Redis / External System
↓
Eventual Consistency
~~~

#### <u>1. Transactional Outbox 解决“业务数据成功，但异步任务没有产生”的双写问题</u>

当前 Browser Monitor Ingestion 是理解 Transaction 最重要的项目案例。

SDK 上报 Event 后，API 需要同时产生：

~~~text
telemetry_events
+
outbox_tasks
~~~

两张表承担不同职责：

~~~text
telemetry_events
↓
这个原始 Event 已经被服务端可靠接收

outbox_tasks
↓
这个 Event 后续还有后台处理任务
~~~

如果分开：

~~~text
INSERT telemetry_events
↓
COMMIT
↓
服务进程崩溃
↓
INSERT outbox_tasks 没有执行
~~~

系统会变成：

~~~text
Raw Event 已经存在
↓
但没有 Worker Task
↓
Projection 永远不会产生
~~~

这就是典型 Dual Write Problem（双写问题）的一种表现。

当前源码使用一条 CTE：

~~~sql
WITH input AS (...),
inserted_events AS (
  INSERT INTO telemetry_events(...)
  SELECT ...
  FROM input
  ON CONFLICT DO NOTHING
  RETURNING event_id, occurred_at, event
)
INSERT INTO outbox_tasks(project_id, event_id, occurred_at, event)
SELECT $1, event_id, occurred_at, event
FROM inserted_events
RETURNING event_id;
~~~

这条 SQL 本身已经把：

~~~text
真正插入 telemetry_events 的 Event
↓
继续生成 outbox_tasks
~~~

连起来。

而整条 SQL 又处于：

~~~text
BEGIN
...
COMMIT
~~~

中。

所以：

~~~text
telemetry_events
+
outbox_tasks
~~~

共享一个 PostgreSQL Transaction。

这就是 Transactional Outbox（事务型 Outbox）的核心：

> 把核心业务事实和“后续需要异步处理”的任务记录写入同一个本地数据库 Transaction，从而避免数据库状态已经提交但任务消息没有产生。

当前链路：

~~~text
SDK Event
↓
Protocol / Schema Validation
↓
业务校验
↓
BEGIN
↓
Advisory Lock
↓
数据库 Duplicate Check
↓
INSERT telemetry_events
↓
INSERT outbox_tasks
↓
UPDATE ingestion_keys.last_used_at
↓
COMMIT
↓
Worker 后续消费 Outbox
~~~

这里 Transaction 解决的是：

~~~text
Event
和
Task
不能只存在一个
~~~

后面的 Worker Retry、Dead Letter、幂等则解决：

~~~text
Task 创建以后
如何可靠地被执行
~~~

#### <u>2. PostgreSQL Transaction 只能直接保护 PostgreSQL 内的数据，不能自动跨越 Redis</u>

当前 Ingestion 在 PostgreSQL：

~~~text
COMMIT
~~~

之后，才执行 Redis：

~~~ts
await this.redis
  .multi()
  .hincrby(...)
  .zadd(...)
  .exec()
  .catch(() => undefined);
~~~

这段设计非常重要，因为它展示了 Transaction 的边界。

PostgreSQL Transaction 可以直接保证：

~~~text
telemetry_events
outbox_tasks
ingestion_keys
~~~

这些 PostgreSQL 内部数据。

但它不能自动把：

~~~text
PostgreSQL
+
Redis
~~~

变成一个 Transaction。

例如：

~~~text
PostgreSQL COMMIT 成功
↓
Redis HINCRBY 失败
~~~

这时候不能简单：

~~~text
ROLLBACK PostgreSQL
~~~

原因有两个：

~~~text
1. PostgreSQL Transaction 已经 COMMIT 结束

2. Redis 本来也不属于这个 PostgreSQL Transaction
~~~

因此服务端需要区分：

~~~text
Local Transaction（本地事务）
↓
一个数据库系统内部的原子操作

Cross-System Consistency（跨系统一致性）
↓
多个独立系统之间如何协调状态
~~~

当前项目的设计是：

~~~text
PostgreSQL
↓
核心事实
↓
必须可靠

Redis
↓
Dashboard Counter
Recent Receive Rate
Analytics Cache Version
↓
属于派生 / 辅助状态
↓
允许短时间不同步
~~~

源码甚至明确：

~~~text
Redis statistics failure
不能把一个已经成功 COMMIT 的 Ingestion
重新变成 SDK 应该 Retry 的错误
~~~

这说明项目把：

~~~text
核心事实正确
~~~

和：

~~~text
辅助统计立即更新
~~~

设置成了不同可靠性等级。

这就是 Eventual Consistency（最终一致性）进入系统设计的位置。

#### <u>3. 外部网络调用通常不应该被长时间包在数据库 Transaction 内</u>

AuthService.register() 当前流程：

~~~text
准备 Password Hash
↓
BEGIN
↓
INSERT / UPDATE User
↓
让旧 Verification Token 失效
↓
创建新 Verification Token
↓
COMMIT
↓
release Connection
↓
Mailer.sendVerification()
~~~

Mailer 位于 COMMIT 后。

如果改成：

~~~text
BEGIN
↓
数据库修改
↓
请求 Mail Provider
↓
等待外部网络响应
↓
COMMIT
~~~

会出现：

~~~text
Transaction 一直打开
+
Connection 一直占用
+
Transaction 中已经拿到的 Lock 一直不释放
~~~

而网络调用具有：

~~~text
延迟不可控
超时
第三方故障
Retry
~~~

等特点。

所以 Transaction Boundary 的一个核心设计原则是：

> 事务只应该覆盖必须共同保证的数据操作，不应该因为“这些代码都在一个 Service 方法里”就把所有操作一起包进去。

#### <u>4. Long Transaction（长事务）会扩大 Lock、Connection 和 MVCC 成本</u>

假设：

~~~text
BEGIN
↓
SELECT Invitation FOR UPDATE
↓
执行复杂 CPU 计算 5 秒
↓
请求第三方 HTTP API 3 秒
↓
再 UPDATE
↓
COMMIT
~~~

这 8 秒期间：

~~~text
Connection 被当前 Request 占用
Row Lock 可能持续存在
Transaction Snapshot / State 持续存在
其他冲突 Transaction 持续等待
~~~

高并发下可能演变：

~~~text
Long Transaction 增加
↓
Lock Wait 增加
↓
Connection 被长期占用
↓
Pool 可用 Connection 减少
↓
更多 Request 等待 Connection
↓
整体数据库延迟进一步增加
~~~

长事务还会进一步影响 PostgreSQL 的旧版本清理等内部过程，但这部分放到 MVCC / Vacuum 章节继续展开。

当前阶段建立原则：

~~~text
Transaction
应该足够大
保证业务正确

同时应该足够小
尽快释放 Connection 和 Lock
~~~

当前 ProjectsService.create() 在 BEGIN 前先完成：

~~~ts
const publicKey = createOpaqueToken('bm_pk_');
const userHashSalt = createOpaqueToken();
const defaultOrigin = new URL(this.config.PUBLIC_BASE_URL).origin;
~~~

这些普通计算不需要占用 Database Transaction。

之后才：

~~~text
pool.connect()
↓
BEGIN
~~~

这是合理缩短事务范围的体现。

#### <u>5. EventProcessor 用一个 Transaction 同时保护 Projection 写入和 processed_at 状态</u>

当前 Worker 真正处理一条 Outbox Task 时，会进入：

~~~text
OutboxWorker.handle()
↓
EventProcessor.process()
↓
根据 Event 类型生成 Projection
↓
更新 telemetry_events.processed_at
~~~

这里首先要看真实代码，而不是只看事务流程图。

源码位置：

~~~text
browser-monitor/platform/apps/worker/src/processor.ts
~~~

关键代码：

~~~ts
async process(projectId: string, event: TelemetryEventV3): Promise<void> {
  const client = await this.database.pool.connect();
  try {
    await client.query('BEGIN');
    if (event.payload.type === 'performance') {
      await this.processPerformance(client, projectId, event, event.payload);
    } else if (event.payload.type === 'view') {
      await this.processView(client, projectId, event, event.payload);
    } else {
      await this.processCustomSignal(client, projectId, event, event.payload);
    }
    await client.query(
      'UPDATE telemetry_events SET processed_at = now() WHERE project_id = $1 AND event_id = $2 AND occurred_at = $3',
      [projectId, event.eventId, new Date(event.occurredAt)],
    );
    await client.query('COMMIT');
  } catch (error) {
    await client.query('ROLLBACK');
    throw error;
  } finally {
    client.release();
  }
}
~~~

这段代码里真正属于同一个 Transaction 的不是只有最后一条 UPDATE，而是：

~~~text
BEGIN
↓
processPerformance()
或 processView()
或 processCustomSignal()
↓
写 Projection Table
↓
UPDATE telemetry_events.processed_at
↓
COMMIT
~~~

这里的 Projection（投影）可以理解为：

> 把原始 telemetry_events 中的 Event，转换成后续查询更方便的结构化数据。

例如：

~~~text
performance Event
↓
performance_samples

view Event
↓
view_records

event / trace / span
↓
custom_signal_samples
+
custom_metric_samples
~~~

所以一条原始 Event 在 Worker 中存在两个相关状态：

~~~text
状态一：
Projection 数据已经写入

状态二：
telemetry_events.processed_at 已经更新
~~~

这两个状态共同表达：

~~~text
这条原始 Event 已经完成后台处理
~~~

如果没有共同 Transaction，可能出现：

~~~text
INSERT performance_samples
↓
成功并提交

UPDATE telemetry_events.processed_at
↓
失败
~~~

此时数据库会变成：

~~~text
performance_samples
已经有 Projection

但是

telemetry_events.processed_at
仍然是 NULL
~~~

系统后续再根据原始 Event 状态判断时，会把它看成：

~~~text
还没有处理
~~~

所以这里需要的 Atomicity（原子性）不是抽象的“多条 SQL 一起成功”，而是非常具体的业务不变量：

~~~text
Projection 已产生
⇔
Raw Event 已标记 processed
~~~

当前代码通过：

~~~text
同一个 Client
+
BEGIN
+
Projection SQL
+
UPDATE processed_at
+
COMMIT
~~~

保证这一点。

如果 processPerformance()、processView()、processCustomSignal() 或 UPDATE processed_at 中任意一步抛错：

~~~ts
catch (error) {
  await client.query('ROLLBACK');
  throw error;
}
~~~

整个 Transaction 会回滚。

因此不是：

~~~text
Projection 成功
processed_at 失败
只撤销 processed_at
~~~

而是：

~~~text
这一轮 Worker 对 PostgreSQL 产生的事务内修改
整体撤销
~~~

这里还要注意一个细节：processPerformance() 中如果判断当前 Event 的 sequence 已经过期，会直接 return：

~~~ts
const current = existing.rows[0];
if (!shouldApplySequence(current?.sequence ?? null, payload.sequence)) return;
~~~

这个 return 只是结束 processPerformance()，不会结束外层 process()。

外层仍然继续：

~~~text
UPDATE telemetry_events.processed_at
↓
COMMIT
~~~

也就是说：

~~~text
旧 sequence Event
不再修改 performance_samples

但是
这条 Event 仍然被认为已经处理完成
~~~

这是当前源码明确表达的处理语义。

#### <u>6. Outbox 的消费可靠性属于 Concurrency Control，而不是继续扩大 Local Transaction</u>

到这里，Transaction 章节只需要确认 Producer 侧的可靠性边界：

~~~text
Business Data
+
Outbox Record
↓
同一个 PostgreSQL Local Transaction
↓
共同 COMMIT / ROLLBACK
~~~

这解决的是 Dual Write：不能出现“业务事实已经提交，但对应的异步任务没有可靠地产生”，也不能在业务事务回滚后仍把对应事件当成成功结果发送出去。AWS Transactional Outbox Pattern 同样把业务数据与 Outbox Record 放在同一个本地事务中，并明确提醒后续消息处理可能重复，因此 Consumer 需要具备幂等能力。[[16]](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html)

Outbox Record 一旦提交，问题就从：

~~~text
Producer 怎样可靠地产生任务？
~~~

切换为：

~~~text
多个 Worker 怎样 Claim？
Worker 崩溃后怎样恢复？
Task 重复执行怎样避免重复副作用？
~~~

这些属于第 8 章 Concurrency Control 的 Consumer Reliability：

~~~text
Producer Reliability（本章）
Business Data + Outbox Record
↓
same Local Transaction

Consumer Reliability（第 8 章）
Claim
↓
Process
↓
Retry / Crash Recovery
↓
Idempotent Processing
~~~

因此本章不再重复展开 `FOR UPDATE SKIP LOCKED`、Stale Claim、Worker Retry 和 Idempotency 的实现细节，也不把当前项目描述为 Exactly Once Processing。

### 【第六层：工程层把 Transaction 抽象成可复用的实现、分类和设计方法】

最后一层不再增加新的数据库语义，而是把前面的事务能力映射回工程实现：ORM 如何封装事务、Migration 为什么也需要事务、项目中的事务有哪些类型，以及以后怎样从业务不变量反推 Transaction Boundary。

~~~text
Transaction Mechanism
↓
ORM / Raw SQL 实现
↓
Migration / Service / Worker 场景
↓
事务类型归纳
↓
从业务不变量设计 Transaction Boundary
↓
形成项目统一的数据可靠性方法
~~~

#### <u>1. Drizzle Transaction 只是更高层 API，底层仍然是 PostgreSQL Transaction</u>

当前 DatabaseHandle：

~~~ts
export interface DatabaseHandle {
  pool: Pool;
  db: NodePgDatabase<typeof schema>;
  close(): Promise<void>;
}
~~~

同一个 Pool 上同时创建：

~~~text
database.pool
↓
node-postgres
↓
Raw SQL

database.db
↓
Drizzle
↓
类型安全 Query API
~~~

Drizzle 可以：

~~~ts
await this.database.db.transaction(async (tx) => {
  await tx.insert(projects).values(...);
  await tx.insert(projectMembers).values(...);
});
~~~

它帮助 Application 管理：

~~~text
BEGIN
↓
tx 中执行 Query
↓
Callback 正常完成
↓
COMMIT
~~~

如果 callback 抛错：

~~~text
ROLLBACK
~~~

所以：

~~~text
pg Transaction
和
Drizzle Transaction
~~~

不是两种不同的数据库事务机制。

更准确关系：

~~~text
Application
├── node-postgres
│   ├── pool.connect()
│   ├── BEGIN
│   ├── query
│   └── COMMIT / ROLLBACK
│
└── Drizzle
    └── db.transaction(tx => ...)
        ↓
        封装 Connection / Transaction 生命周期
↓
PostgreSQL Transaction
~~~

当前项目之所以大量直接使用 pg Client，不是因为 Drizzle 不能做 Transaction，而是因为这些场景使用了较多 PostgreSQL 具体能力：

~~~text
FOR UPDATE
SKIP LOCKED
CTE
pg_advisory_xact_lock
jsonb_to_recordset
RETURNING
~~~

Raw SQL 在这些场景下表达更加直接。

#### <u>2. Migration Transaction 保证“结构已经修改”和“迁移已经记录”共同成立</u>

当前：

~~~text
browser-monitor/platform/packages/database/src/migrate.ts
~~~

每个 Migration：

~~~ts
const client = await pool.connect();
try {
  await client.query('BEGIN');
  await client.query(sql);
  await client.query(
    'INSERT INTO monitor_schema_migrations(name) VALUES ($1)',
    [name],
  );
  await client.query('COMMIT');
} catch (error) {
  await client.query('ROLLBACK');
  throw error;
} finally {
  client.release();
}
~~~

这里存在两个数据库事实：

~~~text
Migration SQL 已经执行
+
monitor_schema_migrations 已经记录这个文件
~~~

它们必须共同成立。

如果：

~~~text
Migration SQL 只执行了一部分
↓
但是 monitor_schema_migrations 已经写入
~~~

下一次运行：

~~~text
Migration Runner 看到它已经 applied
↓
直接跳过
~~~

数据库结构可能永远停留在不完整状态。

反过来：

~~~text
Migration SQL 已经成功
↓
但是 applied record 没有写入
~~~

下一次：

~~~text
Runner 又会尝试重复执行同一个 Migration
~~~

所以：

~~~text
Schema Change
+
Migration Record
~~~

也属于一个 Transaction Boundary。

这说明 Transaction 不只是业务 CRUD 技巧。

它是所有：

~~~text
多个数据库事实
必须共同描述一个状态变化
~~~

的通用数据管理机制。

#### <u>3. 当前项目中的 Transaction 可以按业务目的进一步分类</u>

当前源码中的事务并不是同一种用途，可以分成几类。

**1. 创建型 Transaction**
例如：

~~~text
ProjectsService.create()
AuthService.register()
~~~

特点：

~~~text
一次业务创建
需要同时产生多条关联数据
~~~

目标：

~~~text
防止只创建出半套对象
~~~

**2. 状态迁移型 Transaction**
例如：

~~~text
rotateKey()
updateThresholds()
verifyEmail()
resetPassword()
retryDeadLetter()
OutboxWorker.fail()
~~~

特点：

~~~text
原来的状态
↓
需要经过多次数据修改
↓
迁移到新状态
~~~

目标：

~~~text
防止状态迁移到一半
~~~

**3. 数据 + 任务型 Transaction**
例如：

~~~text
IngestionService.ingest()
~~~

特点：

~~~text
核心业务事实
+
后续异步任务
~~~

共同提交。

目标：

~~~text
防止数据已经存在
但异步任务丢失
~~~

**4. Projection 型 Transaction**
例如：

~~~text
EventProcessor.process()
~~~

特点：

~~~text
Raw Event
↓
生成派生数据
↓
同时标记 processed
~~~

目标：

~~~text
派生状态和处理状态保持一致
~~~

**5. Migration 型 Transaction**
例如：

~~~text
migrate.ts
~~~

特点：

~~~text
数据库结构修改
+
迁移元数据修改
~~~

目标：

~~~text
Schema State 和 Migration State 一致
~~~

#### <u>4. Transaction 的设计流程应该从业务不变量出发，而不是从代码模板出发</u>

以后看到一个 Service，不应该先问：

~~~text
这里是不是有三条 SQL？
如果有就套 BEGIN？
~~~

而应该按下面顺序分析。

第一步：

~~~text
这个 Service 方法最终想完成什么业务状态变化？
~~~

第二步：

~~~text
为了完成这个状态变化
哪些 Table / Row 必须修改？
~~~

第三步：

~~~text
如果只成功其中一部分
数据库状态还能不能接受？
~~~

如果不能：

~~~text
建立 Transaction Boundary
~~~

第四步：

~~~text
是否存在多个 Request / Worker
同时操作相同数据？
~~~

如果存在：

~~~text
检查 Constraint
Isolation Level
FOR UPDATE
Advisory Lock
ON CONFLICT
~~~

第五步：

~~~text
这个 Transaction 是否会调用 Redis、Mailer、HTTP API？
~~~

如果会：

~~~text
判断这些外部操作是否真的应该进入 Transaction
通常尽量放在 COMMIT 之后
~~~

第六步：

~~~text
Transaction 是否可能因为 Deadlock / Serialization Failure 重试？
~~~

如果可能：

~~~text
保证整个 Transaction 可以重新执行
~~~

第七步：

~~~text
Transaction 是否过长？
是否长时间占用 Connection / Lock？
~~~

必要时继续拆分。

#### <u>5. Transaction 在整个数据管理知识体系中连接“单条数据正确”与“多步骤业务正确”</u>

前面已经有：

~~~text
Schema
↓
定义数据结构

Constraint
↓
保证单条数据和关系合法

Index
↓
优化访问路径
~~~

~~~

Isolation

~~~

继续向异步可靠性：

~~~text

Dead Letter
~~~

继续向持久化可靠性：

~~~text
WAL

Backup
~~~

因此数据管理体系可以逐渐形成：

~~~text
业务规则
↓
SQL
↓
Table / Row
↓
Constraint
↓
Index
↓
Transaction
↓
Concurrency Control
├── Isolation Level
├── MVCC

↓
Async Reliability

↓

~~~

到 Transaction 这一层以后，数据库学习开始从：

~~~text
“数据怎么存”
~~~

进入：

~~~text
“多个请求、多个 Worker、多个数据修改同时存在时
系统怎样仍然保持可靠”
~~~

这也是后续继续进入 MVCC 和并发控制的基础。

## 8. Concurrency Control（并发控制）解决多个 Transaction 同时访问同一份数据时的正确性问题

上一节 Transaction（事务）解决的是：

~~~text
一次业务操作需要多次数据库修改
↓
这些修改不能只成功一部分
↓
需要共同 COMMIT 或共同 ROLLBACK
~~~

但是 Transaction 并不会自动让所有请求变成：

~~~text
Transaction A 完成
↓
Transaction B 才开始
↓
Transaction C 再开始
~~~

真实服务端中，大量请求和 Worker 会同时运行：

~~~text
HTTP Request A → Transaction A
HTTP Request B → Transaction B
Worker 1       → Transaction C
Worker 2       → Transaction D
Worker 3       → Transaction E
~~~

这些 Transaction 可能访问不同的数据，也可能同时读取和修改同一个 Row（行）、同一个业务资源，甚至同一个条件范围。

因此 Transaction 之后必须继续解决新的问题：

~~~text
两个 Request 同时接受同一个 Invitation 怎么办？
两个 Ingestion Request 同时上传相同 eventId 怎么办？
两个 Worker 同时更新同一个 performance sample 怎么办？
多个 Worker 同时领取 outbox_tasks 怎么保证不会拿到同一条 Task？
一个 Transaction 正在修改 Row 时，另一个 Transaction SELECT 到底应该看到什么？
~~~

这些问题统一属于 Concurrency Control（并发控制）。

Concurrency Control 的目标不是取消并发，而是：

> 在多个 Transaction 同时运行的情况下，尽可能保留并发能力，同时保证数据可见性、状态变化和最终结果仍然满足系统规则。

PostgreSQL 的并发控制体系可以先建立成：

~~~text
MVCC（多版本并发控制）
↓
Snapshot（快照）
↓
Visibility（可见性）
↓
Isolation Level（事务隔离级别）
↓
Row Lock（行锁）
↓
Advisory Lock（建议锁）
↓
Deadlock（死锁）
↓
Retry（重试）
~~~

当前 Browser Monitor 项目已经实际使用其中多种能力，因此这一节继续从真实源码出发建立完整框架。

---

这一章承接 Transaction，但不再讨论“单次业务操作是否完整”，而是专门讨论“多个完整 Transaction 同时运行时为什么仍可能出错，以及数据库怎样控制这种冲突”。

~~~text
Concurrency Control
├── 第一层：Concurrency Problem
│   └── 识别 Lost Update、Write Skew 等并发错误
├── 第二层：MVCC
│   └── Row Version + Snapshot + Visibility 解决并发读取
├── 第三层：Isolation
│   └── Read Committed / Repeatable Read / Serializable 定义 Snapshot 稳定范围
├── 第四层：Locking
│   └── FOR UPDATE / Pessimistic / Optimistic / Advisory Lock 主动协调冲突
├── 第五层：Critical Section
│   └── Ingestion、Processor、Outbox 把并发机制落到真实业务资源
├── 第六层：Failure Control
│   └── Deadlock、Constraint、Lock Scope、Long Transaction 控制失败和成本
└── 第七层：Design Method
    └── 从 Race Condition 和业务不变量反推并发控制方案
~~~

因此本章的主线是：

~~~text
并发为什么会错
↓
读取时看见什么
↓
什么时候必须加锁
↓
锁住什么资源
↓
冲突和失败怎样处理
↓
最终形成怎样的并发设计方法
~~~

### 【第一层：Concurrency Problem 先解释多个正确 Transaction 为什么仍可能得到错误结果】

并发控制不能从 API 开始学，而要先看 Race Condition 到底破坏了什么。只有先理解并发错误模型，后面的 MVCC、Lock 和 Isolation 才有明确目标。

~~~text
Transaction A
+
Transaction B
↓
同时读取 / 判断 / 修改共享状态
↓
Race Condition
├── Lost Update
└── Write Skew
↓
需要 Concurrency Control
~~~

#### <u>1. Transaction 保证单次操作完整，Concurrency Control 保证多个完整操作同时运行时仍然正确</u>

**1. Atomicity 正确不代表并发结果一定正确**
假设数据库中：

~~~text
balance = 100
~~~

Request A 希望扣除 30：

~~~text
BEGIN
↓
读取 balance
↓
计算新值
↓
UPDATE
↓
COMMIT
~~~

Request B 希望扣除 20，也使用完整 Transaction：

~~~text
BEGIN
↓
读取 balance
↓
计算新值
↓
UPDATE
↓
COMMIT
~~~

单独看两个 Transaction：

~~~text
A 要么全部成功，要么全部失败
B 要么全部成功，要么全部失败
~~~

Atomicity（原子性）没有问题。

但是两个 Transaction 并发时可能出现：

~~~text
Transaction A
SELECT balance
→ 100

Transaction B
SELECT balance
→ 100

A 计算
100 - 30 = 70

B 计算
100 - 20 = 80

A UPDATE balance = 70
B UPDATE balance = 80
~~~

最终：

~~~text
balance = 80
~~~

理论上两次扣款都成功时应该得到：

~~~text
50
~~~

但 A 的结果被 B 后续写入覆盖。

这说明：

~~~text
Transaction
解决一个业务操作内部的完整性

Concurrency Control
解决多个业务操作之间的相互影响
~~~

所以必须记住：

~~~text
有 Transaction
≠
并发一定正确
~~~

上一节 updateThresholds() 的 Version 竞争、本项目 Invitation 并发接受、Performance Sample sequence 更新，本质都属于这一层问题。

#### <u>2. Lost Update（丢失更新）说明“没有 Dirty Read”仍然可能产生错误最终结果</u>

即使 Read Committed 已经避免 Dirty Read：

~~~text
并发逻辑
仍然可能错误
~~~

典型例子：

~~~text
A READ count = 10
B READ count = 10

A
count = 11
UPDATE count = 11

B
count = 11
UPDATE count = 11
~~~

理论正确值：

~~~text
12
~~~

最终：

~~~text
11
~~~

A 的更新效果被 B 覆盖。

这就是 Lost Update（丢失更新）。

常见解决方式不是只有一种。

如果逻辑只是计数：

~~~sql
UPDATE counters
SET value = value + 1
WHERE id = $1;
~~~

让数据库直接完成原子运算，通常比：

~~~text
SELECT value
↓
Application + 1
↓
UPDATE value
~~~

更安全。

如果必须读取完整 Row 再做复杂判断：

~~~text
SELECT ... FOR UPDATE
~~~

可能更合适。

也可以使用：

~~~text
Version Column
+
Optimistic Concurrency Control
~~~

冲突后 Retry。

因此并发控制应该优先寻找：

~~~text
最小、最直接的原子数据库操作
~~~

而不是一遇到并发就使用最重的 Lock。

#### <u>3. Write Skew（写偏差）说明多个 Transaction 即使修改不同 Row，也可能共同破坏业务规则</u>

有些并发异常甚至不是：

~~~text
两个 Transaction
同时 UPDATE 同一个 Row
~~~

例如业务规则：

~~~text
至少有一个管理员保持在线
~~~

当前：

~~~text
Admin A = online
Admin B = online
~~~

Transaction A：

~~~text
读取 B
发现 B online
↓
把 A 设置 offline
~~~

Transaction B：

~~~text
读取 A
发现 A online
↓
把 B 设置 offline
~~~

两边修改的是：

~~~text
不同 Row
~~~

最终却可能：

~~~text
A offline
B offline
~~~

违反：

~~~text
至少一个管理员在线
~~~

这类现象称为 Write Skew（写偏差）。

它说明：

~~~text
并发冲突
不一定只发生在“同一个 Row”
~~~

有些业务不变量是：

~~~text
跨多个 Row
跨一个 Predicate
跨一个数据集合
~~~

这时可能需要：

~~~text
更合理的 Constraint
显式锁定相关资源
重新设计数据模型
或者更高 Isolation Level
~~~

当前 Browser Monitor 没有直接展示这个业务场景，因此这一部分属于并发控制的通用知识扩展。

### 【第二层：MVCC 通过 Row Version、Snapshot 和 Visibility 建立并发读取模型】

明确并发问题以后，先解决“读取”这一侧：PostgreSQL 不让所有读写互相阻塞，而是通过多个 Row Version 和 Snapshot 判断当前执行应该看到什么。

~~~text
Logical Row
↓
多个 Row Version
↓
Snapshot
↓
Visibility Rule
↓
当前 Statement 看见某个 Version
↓
普通 Read 与 Write 可以大量并发
~~~

#### <u>1. MVCC 让 PostgreSQL 可以在存在并发写入时继续提供大量非阻塞读取</u>

**1. 如果所有 Read 和 Write 都简单互斥，并发能力会非常差**
最直接的并发控制想法是：

~~~text
有人读取 Row
↓
锁住 Row

有人修改 Row
↓
锁住 Row
~~~

如果数据库所有操作都这样实现：

~~~text
Transaction A
SELECT Row A
↓
锁住

Transaction B
UPDATE Row A
↓
等待

Transaction C
SELECT Row A
↓
继续等待
~~~

大量普通读取都会互相阻塞。

PostgreSQL 的核心并发控制基础之一是：

MVCC（Multi-Version Concurrency Control，多版本并发控制）。

当前阶段先不要直接进入 xmin、xmax、Tuple Header 等内部字段，而是先建立宏观模型：

~~~text
一个逻辑 Row
↓
随着 INSERT / UPDATE / DELETE 和 Transaction 变化
可能存在不同 Row Version
↓
不同 Transaction
根据自己的 Snapshot
判断哪个 Version 对自己可见
~~~

MVCC 的重要意义是：

~~~text
普通 Read
和
并发 Write
不需要全部简单互斥
~~~

因此数据库能够在保持数据正确性的同时继续提供较高的并发能力。

**2. UPDATE 可以先理解成产生新的 Row Version，而不是让所有 Transaction 立即看到新值**
假设当前：

~~~text
Project A
enabled = true
~~~

Transaction A：

~~~sql
BEGIN;
UPDATE projects
SET enabled = false
WHERE id = 'A';
~~~

不要简单理解成：

~~~text
enabled = true
被立即物理覆盖
↓
所有 Transaction 从此只能看到 false
~~~

MVCC 的逻辑更接近：

~~~text
旧 Row Version
enabled = true

新 Row Version
enabled = false
~~~

之后 PostgreSQL 根据：

~~~text
当前 Transaction
+
Snapshot
+
其他 Transaction 的提交状态
~~~

决定某个 Query 应该看到哪个 Version。

Transaction A 自己已经执行 UPDATE，因此后续 Query 可以看到：

~~~text
enabled = false
~~~

另一个普通 Read Committed Transaction 在 A COMMIT 以前，不能把 A 未提交的新 Version 当作已提交数据使用，因此仍可能读取：

~~~text
enabled = true
~~~

这就是 Multi-Version（多版本）的核心直觉：

~~~text
同一个逻辑 Row
↓
在并发 Transaction 中
可能暂时存在多个 Version
↓
不同 Transaction
根据可见性规则看到不同 Version
~~~

#### <u>2. Snapshot 决定当前 Statement 或 Transaction 能看到哪些 Row Version</u>

Snapshot（快照）容易被误解成：

~~~text
数据库执行 SELECT 时
把整个 Database 复制一份
~~~

实际上不是。

可以先把 Snapshot 理解为：

> PostgreSQL 用于判断当前查询应该看到哪些 Transaction 结果、哪些 Row Version 的一组可见性信息。

因此：

~~~text
Snapshot
≠
Database Backup

Snapshot
≠
复制整张 Table
~~~

更接近：

~~~text
Query 开始
↓
确定当前可见范围
↓
扫描 Table / Index
↓
遇到不同 Row Version
↓
根据 Snapshot 判断这个 Version 是否可见
~~~

这也解释了为什么：

~~~text
数据库中物理存在某个 Row Version
≠
当前 Transaction 一定能看到它
~~~

数据是否可见取决于：

~~~text
是谁创建 / 修改了它
对应 Transaction 是否提交
当前 Snapshot 的边界
当前 Isolation Level
~~~

更底层的 Transaction ID、xmin、xmax、Tuple Visibility 会在后续 MVCC 深入部分继续展开。

#### <u>3. Read Committed 下同一个 Transaction 的两条 Statement 可以看到不同的已提交状态</u>

当前 Browser Monitor 源码没有显式设置：

~~~text
SET TRANSACTION ISOLATION LEVEL ...
~~~

因此在 PostgreSQL 默认配置下使用：

~~~text
Read Committed（读已提交）
~~~

Read Committed 的一个重要特点是：

> 普通 Statement 使用该 Statement 开始时可以看到的已提交数据，而不是从 BEGIN 开始到 COMMIT 永远固定一个 Snapshot。

例如 Transaction A：

~~~sql
BEGIN;
SELECT display_name
FROM projects
WHERE id = 'A';
~~~

第一次读取：

~~~text
display_name = Old Name
~~~

此时 Transaction B：

~~~sql
UPDATE projects
SET display_name = 'New Name'
WHERE id = 'A';
COMMIT;
~~~

Transaction A 再执行：

~~~sql
SELECT display_name
FROM projects
WHERE id = 'A';
~~~

第二次可能读取：

~~~text
display_name = New Name
~~~

虽然 A 自己还没有 COMMIT。

因此 Read Committed 更接近：

~~~text
Transaction A
BEGIN
↓
Statement 1
Snapshot 1
↓
其他 Transaction COMMIT
↓
Statement 2
Snapshot 2
↓
COMMIT
~~~

这也是 Nonrepeatable Read（不可重复读）在 Read Committed 中可能发生的原因。

#### <u>4. Dirty Read、Nonrepeatable Read、Phantom Read 描述的是不同类型的数据可见性异常</u>

**1. Dirty Read（脏读）是读取其他 Transaction 尚未提交的数据**
假设：

~~~text
Transaction A
BEGIN
UPDATE account
SET balance = 0
还没有 COMMIT
~~~

如果 Transaction B 此时读取：

~~~text
balance = 0
~~~

随后 A：

~~~text
ROLLBACK
~~~

那么 B 曾经读取到：

~~~text
一个最终根本没有成立的数据状态
~~~

这就是 Dirty Read（脏读）。

PostgreSQL 的 Read Committed 不允许 Dirty Read。

PostgreSQL 即使接受 Read Uncommitted（读未提交）这个隔离级别名称，实际也按照 Read Committed 处理，因此 PostgreSQL 不提供真正的 Dirty Read 行为。

**2. Nonrepeatable Read（不可重复读）是同一个 Transaction 两次读取同一 Row 得到不同结果**
~~~text
Transaction A
BEGIN
SELECT balance
→ 100

Transaction B
UPDATE balance = 50
COMMIT

Transaction A
再次 SELECT balance
→ 50
~~~

同一个 Transaction：

~~~text
第一次读取 100
第二次读取 50
~~~

就是 Nonrepeatable Read。

这在 Read Committed 中允许出现。

**3. Phantom Read（幻读）是相同查询条件对应的 Row 集合发生变化**
Transaction A：

~~~sql
SELECT *
FROM orders
WHERE status = 'pending';
~~~

第一次：

~~~text
10 Rows
~~~

Transaction B：

~~~text
INSERT 一条 status = pending 的 Row
↓
COMMIT
~~~

A 再执行相同 Query：

~~~text
11 Rows
~~~

这里变化的不是同一个 Row 的某个字段，而是：

~~~text
满足 Predicate（查询条件）的 Row 集合
~~~

这就是 Phantom Read（幻读）。

---

### 【第三层：Isolation Level 决定 Snapshot 在一个 Transaction 中稳定到什么程度】

MVCC 提供多版本和可见性基础，Isolation Level 再决定这些可见性规则在一个 Transaction 中有多稳定，以及发生冲突时数据库允许继续还是要求失败重试。

~~~text
MVCC + Snapshot
↓
Isolation Level
├── Read Committed：Statement 级可见性变化
├── Repeatable Read：更稳定的 Transaction Snapshot
└── Serializable：结果必须可解释为串行顺序
↓
必要时 Serialization Failure + Retry
~~~

#### <u>1. Repeatable Read 让一个 Transaction 在更稳定的 Snapshot 上工作</u>

PostgreSQL 的 Repeatable Read（可重复读）比 Read Committed 提供更稳定的数据视图。

可以先对比：

~~~text
Read Committed
↓
不同 Statement
可能看到其他 Transaction 新提交的数据

Repeatable Read
↓
同一个 Transaction
基于更稳定的 Transaction Snapshot 工作
~~~

因此：

~~~text
Transaction A
第一次 SELECT → 100

Transaction B
UPDATE → 50
COMMIT

Transaction A
第二次普通 SELECT
~~~

在 Repeatable Read 中不会简单像 Read Committed 那样切换到新提交的 50。

PostgreSQL 的 Repeatable Read 还能避免 PostgreSQL 实现中的 Phantom Read。

但这并不意味着：

~~~text
Repeatable Read
↓
所有并发 Transaction 都一定成功
~~~

如果当前 Transaction 尝试修改一条已经被其他并发 Transaction 改变的数据，PostgreSQL 可能无法继续维持它当前 Snapshot 的一致性，从而让 Transaction 失败。

此时 Application 需要：

~~~text
ROLLBACK
↓
重新 BEGIN
↓
基于新的数据库状态
重新执行整个 Transaction
~~~

#### <u>2. Serializable 允许并发执行，但要求最终结果可以解释成某种串行顺序</u>

Serializable（串行化）是 PostgreSQL 常用隔离级别中最严格的一层。

它不能简单理解成：

~~~text
Transaction A 完全执行完
↓
Transaction B 才允许执行
↓
Transaction C 再执行
~~~

实际上 PostgreSQL 仍然可以并发执行多个 Serializable Transaction。

目标是：

> 成功 COMMIT 的结果必须能够等价解释为这些 Transaction 按照某一种串行顺序一个接一个执行。

例如：

~~~text
A 与 B
物理上并发执行
~~~

但最终结果至少应该能够解释成：

~~~text
A → B
~~~

或者：

~~~text
B → A
~~~

如果 PostgreSQL 检测到当前并发结果无法满足任何合理串行顺序：

~~~text
Serialization Failure
↓
某个 Transaction 失败
↓
Application Retry
~~~

因此：

~~~text
Serializable
不是“不发生并发冲突”

而是
“发现不能安全串行化时
宁可让某个 Transaction 失败”
~~~

这也是为什么更强 Isolation Level 需要 Application 具备 Retry 能力。

### 【第四层：Locking 在仅靠 Snapshot 不够时主动协调冲突资源】

MVCC 和 Isolation 主要控制“看见什么”，但很多业务还需要保证“从读取状态到完成修改期间，别人不能同时改变关键资源”。这时才进入显式 Lock。

~~~text
Read Current State
↓
业务判断依赖这个状态
↓
是否允许其他 Transaction 同时修改？
├── 不允许 → Pessimistic Lock / FOR UPDATE
├── 允许先并发 → Optimistic Concurrency
└── 没有实体 Row → Advisory Lock
~~~

#### <u>1. 普通 SELECT 不足以保护“读取当前状态后继续修改”的业务流程</u>

当前项目最直观的例子是：

~~~text
ProjectsService.acceptInvitation()
~~~

源码位置：

~~~text
browser-monitor/platform/apps/api/src/projects/projects.service.ts
~~~

关键代码：

~~~ts
const client = await this.database.pool.connect();
try {
  await client.query('BEGIN');
  const invitation = await client.query<{
    id: string;
    project_id: string;
    email: string;
    role: ProjectRole;
  }>(
    'SELECT id, project_id, email, role FROM project_invitations WHERE token_hash = $1 AND accepted_at IS NULL AND expires_at > now() FOR UPDATE',
    [hashToken(token)],
  );
  const row = invitation.rows[0];
  if (!row) throw new NotFoundException('Invitation not found or expired.');
  if (row.email.toLowerCase() !== userEmail.toLowerCase()) {
    throw new ForbiddenException('Invitation email does not match the current account.');
  }
  await client.query(
    'INSERT INTO project_members(project_id, user_id, role) VALUES ($1,$2,$3) ON CONFLICT (project_id, user_id) DO UPDATE SET role = EXCLUDED.role',
    [row.project_id, userId, row.role],
  );
  await client.query(
    'UPDATE project_invitations SET accepted_at = now() WHERE id = $1',
    [row.id],
  );
  await client.query('COMMIT');
} catch (error) {
  await client.query('ROLLBACK');
  throw error;
} finally {
  client.release();
}
~~~

这里真正依赖的业务状态是：

~~~text
accepted_at IS NULL
~~~

也就是：

~~~text
Invitation 现在仍然没有被使用
~~~

后续 Application 会基于这个判断执行：

~~~text
创建 / 更新 Project Member
+
把 Invitation 标记 accepted
~~~

如果只是普通 SELECT：

~~~sql
SELECT ...
FROM project_invitations
WHERE accepted_at IS NULL;
~~~

两个 Request 可能同时得到：

~~~text
Request A
Invitation 未使用

Request B
Invitation 也未使用
~~~

然后两边都继续后续业务。

问题不是：

~~~text
SELECT 查询错误
~~~

而是：

~~~text
两个 Transaction
同时基于同一个旧状态
作出了后续业务决定
~~~

这种流程可以抽象成：

~~~text
Read
↓
Check
↓
Act
~~~

也叫典型的 Check-Then-Act（先检查再操作）模式。

只要业务要求：

~~~text
从读取状态
到完成修改
这段期间
不能被另一个 Transaction 改变关键状态
~~~

就必须继续设计并发控制。

#### <u>2. SELECT FOR UPDATE 为“读取后修改”的 Row 建立悲观并发保护</u>

acceptInvitation() 使用：

~~~sql
SELECT ...
FROM project_invitations
...
FOR UPDATE
~~~

FOR UPDATE 属于 Row-Level Lock（行级锁）的使用方式。

可以理解成：

> 当前 Transaction 不只是读取这个 Row，而是准备基于它当前的状态继续执行修改，因此需要锁住对应 Row，阻止其他冲突 Transaction 同时完成相同修改。

两个 Request 同时执行：

~~~text
Request A
BEGIN
↓
SELECT Invitation FOR UPDATE
↓
获得 Row Lock
~~~

Request B：

~~~text
BEGIN
↓
SELECT 同一个 Invitation FOR UPDATE
↓
发现冲突
↓
等待 A
~~~

A：

~~~text
检查 Email
↓
INSERT / UPDATE project_members
↓
UPDATE invitation.accepted_at
↓
COMMIT
↓
释放 Row Lock
~~~

B 才继续。

此时 B 不能继续假设：

~~~text
accepted_at 仍然是 NULL
~~~

因为 A 已经修改并 COMMIT。

所以：

~~~text
普通 SELECT
主要解决“读取”

SELECT FOR UPDATE
解决“读取当前状态后
我要基于它继续完成冲突修改”
~~~

#### <u>3. FOR UPDATE 属于 Pessimistic Locking（悲观并发控制）</u>

Pessimistic Locking（悲观锁 / 悲观并发控制）的核心思想是：

~~~text
认为并发冲突可能发生
↓
在执行关键修改以前
先取得 Lock
↓
其他冲突 Transaction 等待
↓
当前 Transaction 完成
↓
释放 Lock
~~~

当前 Invitation 场景：

~~~text
BEGIN
↓
SELECT Invitation FOR UPDATE
↓
获得 Row Lock
↓
检查状态
↓
修改 Member
↓
修改 Invitation
↓
COMMIT
~~~

优点是：

~~~text
关键状态读取以后
不会被另一个冲突 Transaction
无保护地同时修改
~~~

代价是：

~~~text
冲突 Transaction 会等待
↓
Lock Wait 增加

Transaction 越长
↓
Lock 持有时间越长
~~~

所以悲观锁不是：

~~~text
所有 SELECT 都加 FOR UPDATE
~~~

而应该用于：

~~~text
后续修改明显依赖当前 Row 状态
+
这个状态存在真实并发竞争
~~~

的场景。

#### <u>4. Optimistic Concurrency Control 不提前阻塞，而是在真正写入时检查状态是否已经变化</u>

和 Pessimistic Locking 对应，还有：

Optimistic Concurrency Control（乐观并发控制）。

核心思想是：

~~~text
先允许多个 Request 并发读取
↓
真正 UPDATE 时
检查自己读取的版本是否仍然有效
↓
有效
→ 修改成功

已经被别人修改
→ 当前操作失败 / Retry
~~~

例如 Table 存在：

~~~text
id = account-1
balance = 100
version = 3
~~~

Application 读取：

~~~text
balance = 100
version = 3
~~~

更新时：

~~~sql
UPDATE accounts
SET balance = 70,
    version = 4
WHERE id = $1
AND version = 3;
~~~

如果另一个 Transaction 已经先完成修改：

~~~text
version = 4
~~~

那么：

~~~text
WHERE version = 3
~~~

不会再匹配。

Application 得到：

~~~text
rowCount = 0
~~~

就知道：

~~~text
自己读取以后
这份数据已经被另一个 Transaction 修改
~~~

然后可以：

~~~text
返回并发冲突
或者
重新读取最新状态后 Retry
~~~

因此：

~~~text
Pessimistic Locking
↓
先锁再改

Optimistic Concurrency Control
↓
先并发执行
真正写入时检测冲突
~~~

当前 Browser Monitor 没有统一使用一个 version Column 实现通用 Optimistic Lock，因此这一部分属于通用并发控制知识扩展，不是当前项目已经统一采用的模式。

但项目中的：

~~~text
sequence 检查
Unique Constraint
ON CONFLICT
~~~

也体现了“允许执行到冲突检测点，再决定是否应用”的类似思想。

#### <u>5. Advisory Lock 保护 Application 定义的逻辑资源，即使数据库中还没有对应 Row</u>

Row Lock 有一个重要前提：

~~~text
目标 Row 已经存在
~~~

但当前 Ingestion 的幂等问题是：

~~~text
projectId + eventId
~~~

当 Event 第一次到达时：

~~~text
telemetry_events
里面可能根本还没有这个 Row
~~~

所以无法：

~~~text
SELECT 目标 Event Row
FOR UPDATE
~~~

当前源码使用：

~~~text
browser-monitor/platform/apps/api/src/ingestion/ingestion.service.ts
~~~

关键代码：

~~~ts
const eventIds = uniqueValid.map((event) => event.eventId).sort();
await client.query(
  'SELECT pg_advisory_xact_lock(hashtextextended($1 || ':' || ids.event_id, 0)) FROM unnest($2::text[]) AS ids(event_id) ORDER BY ids.event_id',
  [`ingest:${project.project_id}`, eventIds],
);
~~~

这里使用：

~~~text
pg_advisory_xact_lock
~~~

即 Transaction-Level Advisory Lock（事务级建议锁）。

Advisory Lock 可以理解成：

> Lock 的业务含义由 Application 自己定义，PostgreSQL 负责根据给出的 Lock Key 实现互斥与等待。

当前 Application 定义：

~~~text
ingest:{projectId}:{eventId}
~~~

代表：

~~~text
“当前 Project 下这个 eventId”
是一个需要互斥处理的业务资源
~~~

即使数据库中还没有对应 telemetry_events Row，也能先：

~~~text
获得逻辑资源 Lock
↓
检查是否已经存在
↓
决定是否写入
~~~

所以：

~~~text
Row Lock
保护真实 Row

Advisory Lock
保护 Application 自己定义的业务资源
~~~

### 【第五层：项目中的 Critical Section 把 Lock 精确落到 eventId、sampleId 和 Task Row】

理解 Lock 类型以后，需要回到源码确认真正的临界区。项目不是“给整个 Table 加锁”，而是围绕具体业务资源定义尽量小的互斥范围。

~~~text
业务资源
├── projectId + eventId → Ingestion Advisory Lock
├── projectId + sampleId → Advisory Lock + FOR UPDATE + sequence
└── Outbox Task Row → FOR UPDATE SKIP LOCKED
↓
形成最小 Critical Section
↓
保证并发正确同时保留吞吐量
~~~

#### <u>1. Ingestion 用 Advisory Lock 把 Duplicate Check 和真正写入放进同一个 Critical Section</u>

IngestionService 在进入数据库以前先做 Request 内部去重：

~~~ts
const seenEventIds = new Set<string>();
const uniqueValid = valid.filter((event) => {
  if (seenEventIds.has(event.eventId)) return false;
  seenEventIds.add(event.eventId);
  return true;
});
~~~

它只能解决：

~~~text
同一个 HTTP Request
内部重复 eventId
~~~

无法解决：

~~~text
Request A
eventId = e-001

Request B
eventId = e-001

两者同时到达
~~~

进入数据库 Transaction 后，源码：

~~~ts
await client.query('BEGIN');
const eventIds = uniqueValid.map((event) => event.eventId).sort();
await client.query(
  'SELECT pg_advisory_xact_lock(hashtextextended($1 || ':' || ids.event_id, 0)) FROM unnest($2::text[]) AS ids(event_id) ORDER BY ids.event_id',
  [`ingest:${project.project_id}`, eventIds],
);
const existing = await client.query<{ event_id: string }>(
  'SELECT event_id FROM telemetry_events WHERE project_id = $1 AND event_id = ANY($2::text[]) GROUP BY event_id',
  [project.project_id, eventIds],
);
~~~

完整并发保护链路：

~~~text
BEGIN
↓
按照 projectId + eventId
取得 Advisory Lock
↓
查询 telemetry_events
判断 Event 是否已经存在
↓
构造 existingIds
↓
过滤真正 pending Event
↓
INSERT telemetry_events
↓
INSERT outbox_tasks
↓
UPDATE ingestion_keys.last_used_at
↓
COMMIT
↓
Transaction-Level Advisory Lock 自动释放
~~~

如果没有这个 Lock，只做：

~~~text
SELECT 是否存在
↓
不存在
↓
INSERT
~~~

可能发生：

~~~text
Request A
SELECT e-001
不存在

Request B
SELECT e-001
也不存在

A 决定 INSERT

B 也决定 INSERT
~~~

两个 Request 的判断都正确地反映了：

~~~text
检查时刻的数据库状态
~~~

但它们都在：

~~~text
真正写入之前
~~~

完成检查。

这就是 Check-Then-Act Race（先检查再操作竞态）。

真正需要保护的不是一条 SELECT，而是整个：

~~~text
Check
↓
Decision
↓
Write
~~~

区间。

这个区间就是 Critical Section（临界区）。

当前项目通过：

~~~text
Transaction
+
Transaction-Level Advisory Lock
~~~

把同一个 eventId 的 Check + Write 串行化。

#### <u>2. 确定性的 Lock Order 用于降低多个资源加锁时的 Deadlock 风险</u>

当前 Ingestion 中：

~~~ts
const eventIds = uniqueValid.map((event) => event.eventId).sort();
~~~

数据库 SQL 又明确：

~~~sql
ORDER BY ids.event_id
~~~

这不是为了让返回结果更整齐。

它的核心目的是：

~~~text
多个 Transaction
按照同一个顺序
取得多个 Advisory Lock
~~~

假设 Transaction A：

~~~text
先拿 Lock 1
↓
再请求 Lock 2
~~~

Transaction B：

~~~text
先拿 Lock 2
↓
再请求 Lock 1
~~~

此时可能形成：

~~~text
A 已持有 Lock 1
等待 Lock 2

B 已持有 Lock 2
等待 Lock 1
~~~

也就是：

~~~text
A 等 B
↑   ↓
B 等 A
~~~

这就是 Deadlock（死锁）。

PostgreSQL 能检测 Deadlock，并主动让其中一个 Transaction 失败，从而打破循环等待。

但工程设计不能只依赖：

~~~text
发生 Deadlock
↓
数据库帮我杀一个
~~~

更好的方式是减少形成循环等待的机会。

假设两个 Batch：

~~~text
Batch A
event-3,event-1,event-2

Batch B
event-2,event-3,event-1
~~~

如果按照原始顺序取 Lock：

~~~text
A
3 → 1 → 2

B
2 → 3 → 1
~~~

更容易形成互相等待。

排序以后：

~~~text
A
1 → 2 → 3

B
1 → 2 → 3
~~~

所有 Transaction 使用同一个 Lock Order（加锁顺序）。

因此：

~~~text
一个 Transaction 需要同时获得多个 Lock
↓
尽量定义统一、确定性的资源排序
↓
所有 Transaction 按同样顺序获取 Lock
~~~

是降低 Deadlock 风险的重要工程原则。

#### <u>3. Processor 同时使用 Advisory Lock 和 FOR UPDATE，因为它既要保护逻辑 Sample，也要保护已经存在的 Row</u>

当前 Performance Worker：

~~~text
browser-monitor/platform/apps/worker/src/processor.ts
~~~

关键代码：

~~~ts
await client.query(
  'SELECT pg_advisory_xact_lock(hashtextextended($1, 0))',
  [`performance:${projectId}:${payload.sampleId}`],
);
const existing = await client.query<{
  observed_at: Date;
  sequence: number;
  state: string;
}>(
  'SELECT observed_at, sequence, state FROM performance_samples WHERE project_id = $1 AND sample_id = $2 ORDER BY observed_at DESC LIMIT 1 FOR UPDATE',
  [projectId, payload.sampleId],
);
const current = existing.rows[0];
if (!shouldApplySequence(current?.sequence ?? null, payload.sequence)) return;
~~~

这里的并发场景是：

~~~text
Worker A
拿到同一个 Sample
sequence = 3

Worker B
拿到同一个 Sample
sequence = 4
~~~

如果没有并发保护：

~~~text
A 读取 current.sequence = 2
B 也读取 current.sequence = 2
↓
A 判断 3 可以应用
B 判断 4 也可以应用
↓
B 先 UPDATE sequence = 4
↓
A 后 UPDATE sequence = 3
~~~

最终：

~~~text
新状态 sequence = 4
被旧状态 sequence = 3 覆盖
~~~

因此源码先：

~~~text
Advisory Lock
performance:{projectId}:{sampleId}
~~~

保护：

~~~text
这个逻辑 Sample
~~~

即使数据库中还没有 performance_samples Row，也能先互斥。

如果 Row 已存在：

~~~sql
SELECT ...
FOR UPDATE
~~~

再对实际 Row 建立行级锁。

因此两个 Lock 的作用层次不同：

~~~text
Advisory Lock
↓
保护 sampleId 这个逻辑业务资源
↓
它是一套 Application-defined cooperative protocol：只有同样按照约定计算并获取相同 Advisory Lock Key 的并发路径才会互斥；如果另一条代码路径完全不获取这把 Advisory Lock，PostgreSQL 不会因为业务上使用了同一个 sampleId 就自动阻止它

FOR UPDATE
↓
保护已经存在的 performance_samples Row
~~~

它们共同保护：

~~~text
读取 current.sequence
↓
shouldApplySequence()
↓
计算新 state / rating
↓
INSERT 或 UPDATE
~~~

这一整个 Critical Section。

#### <u>4. Sequence Check 是并发控制和幂等处理的一部分，不是 Transaction 的替代品</u>

当前代码：

~~~ts
const current = existing.rows[0];
if (!shouldApplySequence(current?.sequence ?? null, payload.sequence)) return;
~~~

说明系统不只是考虑：

~~~text
两个 Worker 会不会同时写
~~~

还考虑：

~~~text
旧 Event
是否应该覆盖新 Event
~~~

例如：

~~~text
数据库当前 sequence = 4

后来又收到 sequence = 3
~~~

即使不存在真正同时执行：

~~~text
sequence = 3
~~~

也已经是过期 Observation（观测）。

因此：

~~~text
Transaction
保证一次处理过程完整

Lock
保证同一时间对同一个 Sample 的并发修改受控

Sequence Check
保证旧 Event 不覆盖新 Event
~~~

这三者分别解决不同层的问题。

#### <u>5. Queue Consumer 使用 FOR UPDATE SKIP LOCKED，让多个 Worker 并发领取不同 Task</u>

当前源码：

~~~text
browser-monitor/platform/apps/worker/src/outbox-worker.ts
~~~

claim()：

~~~ts
private async claim(): Promise<OutboxTask[]> {
  const result = await this.database.pool.query<OutboxTask>(
    `WITH candidates AS (
       SELECT id FROM outbox_tasks
       WHERE (
         status = 'pending' AND available_at <= now()
       ) OR (
         status = 'processing' AND locked_at < now() - INTERVAL '5 minutes'
       )
       ORDER BY available_at, created_at
       LIMIT $1
       FOR UPDATE SKIP LOCKED
     )
     UPDATE outbox_tasks o SET
       status = 'processing', locked_at = now(), locked_by = $2, attempts = attempts + 1
     FROM candidates c WHERE o.id = c.id
     RETURNING o.id, o.project_id, o.event_id, o.event, o.attempts`,
    [this.config.WORKER_BATCH_SIZE, this.workerId],
  );
  return result.rows;
}
~~~

这里首先通过：

~~~sql
FOR UPDATE
~~~

说明：

~~~text
当前 Worker
不仅要查询 Task
还准备马上修改这些 Task 的状态
~~~

所以先锁住候选 Row。

但如果只有 FOR UPDATE，多个 Worker 同时领取时可能：

~~~text
Worker A
锁住最前面的 Task

Worker B
也查询同一批最前面的 Task
↓
等待 A
~~~

对于任务队列来说，这种等待没有必要，因为：

~~~text
Task 1 被 A 处理
~~~

并不代表：

~~~text
B 不能去处理 Task 2、Task 3
~~~

所以当前源码使用：

~~~sql
FOR UPDATE SKIP LOCKED
~~~

SKIP LOCKED 表示：

~~~text
如果候选 Row
已经被其他 Transaction Lock
↓
不要等待
↓
直接跳过
↓
继续寻找其他可领取 Row
~~~

例如：

~~~text
Worker A
已经锁住
Task 1
Task 2
Task 3

Worker B
执行 Claim
↓
跳过 1、2、3
↓
继续找到
Task 4
Task 5
Task 6
~~~

这样多个 Worker 可以真正并行消费不同 Task。

#### <u>6. SKIP LOCKED 适合 Queue Consumer，不适合普通要求完整结果集的业务查询</u>

SKIP LOCKED 有一个非常重要的语义：

~~~text
被其他 Transaction Lock 的 Row
当前 Query 会主动跳过
~~~

所以当前 Query 得到的结果不一定是：

~~~text
完整满足 WHERE 条件的 Row 集合
~~~

而是：

~~~text
满足条件
并且当前没有被其他 Transaction Lock 的 Row
~~~

因此它非常适合：

~~~text
任务队列
Job Queue
多个 Consumer
每个 Consumer 只需要拿一批当前可处理任务
~~~

但不适合普通业务查询，例如：

~~~text
查询用户所有订单
查询 Project 所有 Member
统计所有满足条件的数据
~~~

因为这些场景通常要求完整结果，而不是：

~~~text
别人锁住的 Row
我就当它不存在
~~~

所以 SKIP LOCKED 是非常有场景限制的并发工具。

#### <u>7. Outbox Claim 用一条 Statement 同时完成 SELECT + Lock + UPDATE，消除应用层时间窗口</u>

如果 Worker 写成：

~~~text
SQL 1
SELECT pending Task
↓
返回 Node.js

SQL 2
UPDATE Task
SET status = processing
~~~

两条 SQL 中间存在：

~~~text
Application 执行间隔
~~~

另一个 Worker 可能在这个间隔里读取同一个 pending Task。

当前源码使用：

~~~sql
WITH candidates AS (...)
UPDATE outbox_tasks ...
FROM candidates ...
RETURNING ...
~~~

把：

~~~text
选择候选 Task
↓
锁定候选 Row
↓
更新 processing
↓
RETURNING 真正领取的 Task
~~~

放在同一个 SQL Statement 中。

这一整条 Statement 本身就在 PostgreSQL 隐式 Transaction 内执行。

因此：

~~~text
Claim Task
~~~

不需要人为再拆成一个更长的显式 Transaction。

这里体现：

~~~text
能用一条原子 SQL 完成
↓
优先减少应用与数据库之间的竞态窗口
~~~

而不是：

~~~text
为了“看起来安全”
所有逻辑都套一个超长 BEGIN / COMMIT
~~~

#### <u>8. Outbox Claim 还通过 stale processing 状态实现 Worker Crash Recovery</u>

Claim 的 WHERE 不只是：

~~~sql
status = 'pending'
AND available_at <= now()
~~~

还包括：

~~~sql
status = 'processing'
AND locked_at < now() - INTERVAL '5 minutes'
~~~

这说明：

~~~text
Worker A
领取 Task
↓
status = processing
locked_at = T1
↓
Worker A 进程崩溃
↓
没有机会写 completed
~~~

如果永远只查询 pending：

~~~text
这条 Task
会永远停在 processing
~~~

当前设计：

~~~text
processing
+
locked_at 超过 5 分钟
↓
认为 Lock 已 stale
↓
允许其他 Worker 再次 Claim
~~~

所以系统明确允许：

~~~text
同一个 Task
在故障情况下再次被处理
~~~

这就是为什么上一节中的 Idempotency（幂等）不是额外优化，而是 Worker 模型正常工作的必要能力。

### 【第六层：Failure Control 处理 Constraint Conflict、Deadlock 和 Lock 成本】

Lock 解决冲突，但也会引入等待、死锁和吞吐量成本；Constraint 又负责阻止非法最终状态。因此完整并发设计必须同时考虑失败路径和资源成本。

~~~text
Concurrent Operation
↓
Lock / Constraint
├── 等待 → Lock Wait
├── 循环等待 → Deadlock
├── 最终状态非法 → Constraint Conflict
└── Transaction 过长 → Lock Duration 增长
↓
Rollback / Retry / 缩小 Lock Scope
~~~

#### <u>1. Unique Constraint 是并发控制中的最后数据库防线，而不是 Lock 的替代品</u>

当前 updateThresholds()：

~~~text
Transaction A
读取 max(version) = 3

Transaction B
也读取 max(version) = 3
~~~

两个 Transaction 都可能尝试：

~~~text
INSERT version = 4
~~~

当前数据库存在：

~~~text
UNIQUE(project_id, version)
~~~

因此最终：

~~~text
不允许两个 version = 4
同时成功提交
~~~

这里可以明确区分：

~~~text
Lock
↓
协调并发执行过程
控制谁先执行、谁等待

Constraint
↓
限制最终数据库状态
不允许非法结果真正提交
~~~

对于重要数据不变量，不应该只依赖：

~~~text
Application 理论上不会同时写
~~~

而应该尽可能在数据库层表达：

~~~text
这个非法状态
无论 Application 怎样并发
都不能最终 COMMIT
~~~

例如：

~~~text
UNIQUE
PRIMARY KEY
FOREIGN KEY
CHECK
Partial Unique Index
~~~

都是这种最后防线。

#### <u>2. Deadlock 不等于数据库永久卡死，PostgreSQL 会检测并终止其中一个 Transaction</u>

有 Lock 就可能出现 Deadlock。

典型结构：

~~~text
Transaction A
已经持有 Lock 1
↓
等待 Lock 2

Transaction B
已经持有 Lock 2
↓
等待 Lock 1
~~~

双方都无法继续。

PostgreSQL 会进行 Deadlock Detection（死锁检测）。

发现循环等待以后：

~~~text
PostgreSQL
终止其中一个 Transaction
↓
释放它持有的 Lock
↓
另一个 Transaction 可以继续
~~~

因此 Application 可能收到：

~~~text
Deadlock Detected
~~~

错误。

这时：

~~~text
数据库没有“坏掉”
~~~

而是：

~~~text
PostgreSQL 主动牺牲一个 Transaction
恢复系统继续执行
~~~

如果业务允许 Retry，应重新执行整个 Transaction，而不是只重放最后一条 SQL，因为之前读取的状态和取得的 Lock 都已经失效。

#### <u>3. Lock Scope 和 Lock Duration 决定并发控制对吞吐量的影响</u>

并发控制不是：

~~~text
Lock 越多越安全
~~~

而是需要考虑两个重要维度：

~~~text
Lock Scope（锁范围）
Lock Duration（锁持续时间）
~~~

当前项目中的 Lock Scope 很具体：

~~~text
Invitation
↓
一条 Invitation Row

Ingestion
↓
一个 projectId + eventId

Performance
↓
一个 projectId + sampleId

Outbox
↓
当前 Worker 领取的一批 Task Row
~~~

而不是：

~~~text
锁整张 Table
~~~

Lock Scope 越大：

~~~text
越容易覆盖所有冲突
但无关 Request 也更容易被阻塞
~~~

Lock Scope 越小：

~~~text
并发能力更高
但如果遗漏真正相关资源
可能仍然产生 Race Condition
~~~

所以正确粒度来自：

~~~text
业务不变量
~~~

而不是“锁越大越安全”。

#### <u>4. Long Transaction 会把 Connection 占用问题进一步放大成 Lock Wait 问题</u>

上一节已经分析：

~~~text
Long Transaction
↓
Connection 长时间不 release
~~~

在并发控制层还要继续看到：

~~~text
Long Transaction
↓
已经取得的 Row Lock
Advisory Lock
也会持续更久
~~~

例如：

~~~text
BEGIN
↓
SELECT Invitation FOR UPDATE
↓
调用外部 HTTP API 8 秒
↓
UPDATE
↓
COMMIT
~~~

这 8 秒内：

~~~text
Connection 被占用
+
Invitation Row Lock 被持有
+
其他冲突 Transaction 持续等待
~~~

如果大量请求同时发生：

~~~text
Lock Wait 增加
↓
等待中的 Request 继续占用 Application 资源
↓
Connection Pool 压力增加
↓
数据库延迟进一步上升
~~~

所以：

~~~text
缩短 Transaction
~~~

同时也是：

~~~text
缩短 Lock Duration
~~~

的重要手段。

### 【第七层：Concurrency Design 从 Race Condition 和业务不变量反推机制组合】

最后把所有机制收束成一套设计方法：先定位并发入口和共享业务资源，再识别竞态窗口，最后决定 Atomic SQL、Lock、Constraint、Retry 和 Idempotency 应该怎样组合。

~~~text
识别并发入口
↓
识别共享业务资源
↓
定位 Read → Check → Write 时间窗口
↓
优先 Atomic SQL
↓
选择 Row Lock / Advisory Lock / Optimistic Control
↓
Constraint 兜底
↓
设计 Retry / Idempotency
↓
形成完整 Concurrency Strategy
~~~

#### <u>1. Isolation Level、Lock、Constraint、Idempotency 和 Retry 分别处理不同阶段的问题</u>

这些能力经常一起出现，所以需要明确边界。

| 能力 | 主要解决的问题 |
| --- | --- |
| MVCC | 如何维护多个数据版本，让普通 Read / Write 尽量不完全互斥 |
| Snapshot | 当前 Query / Transaction 可以看到哪些 Row Version |
| Isolation Level | 不同 Transaction 之间允许怎样的数据可见性 |
| FOR UPDATE | 已存在 Row 的读取后修改并发冲突 |
| Advisory Lock | Application 定义的逻辑资源并发冲突 |
| Constraint | 阻止非法最终状态 COMMIT |
| ON CONFLICT | 对已知冲突结果定义 INSERT 行为 |
| Idempotency | 同一个操作重复执行时避免重复副作用 |
| Retry | Transaction 因并发冲突失败后重新基于最新状态执行 |
| Lock Order | 降低多个 Lock 之间形成 Deadlock 的风险 |

因此不能把它们理解成：

~~~text
选其中一个最强的
其他都不要
~~~

真正的服务端数据正确性通常来自组合。

#### <u>2. 当前 Browser Monitor 已经形成多种并发控制策略</u>

当前源码中的真实场景可以放回同一个框架。

| 场景 | 冲突资源 | 当前实现 |
| --- | --- | --- |
| Invitation 同时接受 | project_invitations Row | Transaction + FOR UPDATE |
| 相同 eventId 并发 Ingest | projectId + eventId | Transaction-Level Advisory Lock |
| 多个 eventId 批量 Ingest | 多个 Advisory Lock | eventId sort + ORDER BY，统一 Lock Order |
| 同一 Performance Sample 并发更新 | projectId + sampleId | Advisory Lock + FOR UPDATE + sequence |
| View start / end 并发处理 | projectId + viewId | Advisory Lock + FOR UPDATE |
| 多 Worker 领取 Outbox | outbox_tasks Row | FOR UPDATE SKIP LOCKED |
| Worker 崩溃后的 Task 恢复 | stale processing Task | locked_at 超时后重新 Claim |
| Threshold Version 并发创建 | projectId + version / active state | Transaction + Unique Constraint |
| Custom Signal 重复处理 | Unique Key | ON CONFLICT DO NOTHING |

这个表背后的共同判断方法不是：

~~~text
看到并发
↓
直接加 FOR UPDATE
~~~

而是：

~~~text
先确定真正的冲突资源
↓
判断冲突资源是否已有 Row
↓
判断应该等待还是允许 Retry
↓
判断最终状态是否可以用 Constraint 保护
↓
选择合适的 Lock / Constraint / Idempotency 方案
~~~

#### <u>3. 并发控制应该从 Race Condition 开始分析，而不是从数据库 API 开始选</u>

以后分析一个新业务时，可以按照下面的顺序。

**1. 先确定是否真的存在并发入口**
例如：

~~~text
多个 HTTP Request
多个 Worker
多个 Node.js Instance
多个定时任务
~~~

是否可能同时执行相同业务？

如果：

~~~text
永远只有一个执行者
~~~

就不一定需要复杂 Lock。

**2. 找到真正共享的业务资源**
例如：

~~~text
Invitation
↓
invitation Row

Ingestion
↓
projectId + eventId

Performance
↓
projectId + sampleId

Outbox
↓
Task Row
~~~

不能只说：

~~~text
它们都访问同一个 Table
~~~

Table 往往太大。

真正需要找到：

~~~text
哪些 Transaction
会竞争同一个业务状态
~~~

**3. 找出读取和修改之间是否存在时间窗口**
重点检查：

~~~text
SELECT
↓
Application 判断
↓
UPDATE / INSERT
~~~

这种结构。

如果：

~~~text
判断依赖 SELECT 时看到的旧状态
~~~

就可能存在 Check-Then-Act Race。

**4. 优先判断能否改成单条原子 SQL**
例如计数：

~~~sql
UPDATE counters
SET value = value + 1
WHERE id = $1;
~~~

通常比：

~~~text
SELECT value
↓
Application + 1
↓
UPDATE value
~~~

更容易保证并发正确。

**5. Row 已存在时再考虑 FOR UPDATE**
适合：

~~~text
读取已有 Row
↓
根据它当前状态做判断
↓
继续修改同一个或关联状态
~~~

例如 Invitation。

**6. 没有 Row 可以锁时考虑 Advisory Lock 或重新设计数据约束**
例如：

~~~text
第一次插入 eventId
~~~

目标 Row 还不存在。

当前项目使用：

~~~text
projectId + eventId
↓
Advisory Lock Key
~~~

**7. 最终不变量尽量通过 Constraint 再兜底**
即使 Application 已经做并发控制，也应该判断数据库是否可以表达：

~~~text
这个最终状态永远不允许出现
~~~

例如：

~~~text
UNIQUE(project_id, version)
~~~

**8. 明确冲突发生后的行为**
冲突后可能：

~~~text
等待
返回 Conflict
忽略重复
Retry
进入 Dead Letter
~~~

不能只考虑：

~~~text
如何不冲突
~~~

还需要设计：

~~~text
冲突以后系统如何恢复
~~~

#### <u>4. Concurrency Control 把 Transaction 扩展成完整的多请求数据正确性体系</u>

学习到这里，前面的数据管理能力可以继续连接：

~~~text
Business Operation
↓
Transaction
保证单次业务修改完整
↓
MVCC
维护并发环境中的多个 Row Version
↓
Snapshot
决定当前执行能看到哪些 Version
↓
Isolation Level
定义 Transaction 之间的数据可见范围
↓
Constraint
阻止非法最终状态
↓
FOR UPDATE
保护已有 Row 的读取后修改
↓
Advisory Lock
保护 Application 定义的逻辑资源
↓
Lock Order
降低 Deadlock
↓
SKIP LOCKED
让多个 Worker 跳过其他 Worker 已领取的 Task
↓
Retry
处理必须失败的并发 Transaction
↓
Idempotency
让重复执行最终仍然收敛
~~~

放回 Browser Monitor：

~~~text
Invitation
↓
FOR UPDATE

Ingestion eventId
↓
Advisory Lock

Performance sampleId
↓
Advisory Lock
+
FOR UPDATE
+
sequence

Outbox Worker
↓
FOR UPDATE SKIP LOCKED

Threshold Version
↓
Transaction
+
Unique Constraint

Repeated Worker Execution
↓
ON CONFLICT
+
Idempotency
~~~

到这里已经能够建立：

~~~text
Transaction
解决一个业务操作内部的完整性

Concurrency Control
解决多个 Transaction 同时运行时的正确性
~~~

下一层如果继续深入 PostgreSQL 内部实现，就会进入：

~~~text
MVCC Internal
↓
Transaction ID
↓
Tuple / Row Version
↓
xmin / xmax
↓
Snapshot
↓
Visibility Rule
↓
UPDATE / DELETE 为什么产生旧 Version
↓
Dead Tuple
↓
VACUUM
~~~

这会把当前已经建立的：

~~~text
“不同 Transaction 为什么能看到不同 Row Version”
~~~

继续落实到 PostgreSQL 真正的数据结构和可见性判断机制中。
