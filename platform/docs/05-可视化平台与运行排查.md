# 可视化平台与运行排查

可视化平台不是把数据库字段直接绘制成图表，而是把接入、权限、指标判断和故障定位组织成可执行流程。用户先建立账号和项目，获得 DSN 并配置 Origin；数据进入系统后，再从总览发现异常、从页面和指标视图缩小范围，最后用原始事件与服务状态确认原因。

## 1. 登录与项目边界

### 【账号生命周期】

开放注册会发送邮箱验证链接。未验证账号不能正常登录和创建项目；如果再次提交同一个未验证邮箱，服务端会更新注册信息、作废旧验证令牌并重新发送验证邮件，始终只保留一个有效链接。已验证邮箱重复注册仍返回冲突，前端会提示用户登录或找回密码。验证后可登录、退出、发起忘记密码和完成密码重置。登录 Session 保存在 Redis，浏览器只持有 HttpOnly Cookie，管理写请求还需要 CSRF Token。

前端的 `Protected` 路由用于改善导航体验，真正的权限判断仍在 API。即使用户手工访问项目 URL，服务端也会检查项目成员关系。

### 【owner 和 member】

owner 可以查看数据，并管理成员、写入键、Origin、阈值和死信重试；member 只查看项目与监控数据。公开 DSN 只能写入遥测，不能调用管理 API。角色、登录 Session 和 ingestion key 是三种不同目的的身份，不能相互替代。

## 2. 项目接入流程

### 【从创建项目到第一条数据】

1. 用户创建项目，并填写与 SDK `app.name` 一致的应用标识；
2. 平台在同一事务中创建 owner 成员关系、默认 ingestion key、默认阈值版本和项目盐值；
3. owner 把业务页面的完整 Origin 加入允许列表；
4. 设置页根据 `PUBLIC_BASE_URL` 和 public key 生成完整 DSN；
5. 业务代码把 DSN 配置到 `transport.dsn`，启动 SDK；
6. 浏览器请求采集 API，服务状态页出现 accepted；
7. Worker 投影完成后，总览和性能页出现数据。

设置页展示的是可复制接入信息，不要求业务项目再实现 endpoint。写入键泄露或需要切换时，owner 执行轮换：平台创建新 key，并让旧 key 在 24 小时后过期，为业务发布留出平滑迁移时间。

### 【routeName 为什么需要业务参与】

URL pathname 可能包含订单 ID、用户 ID 等高基数动态片段。SDK 默认清除 query 和 fragment，但无法可靠猜测 `/users/123` 与 `/users/456` 是否属于同一业务页面。业务可以提供 `resolveRouteName` 或调用 `setViewName()`，将它们稳定映射为 `user-detail`，平台再按该名称进行页面排名。

## 3. 页面与问题定位顺序

### 【总览】

总览展示 View、Session、采集事件量和主要性能指标健康度。它适合回答“系统最近是否有明显变化”，但不直接承担根因定位。发现 p75、poor 比例或覆盖率异常后，应继续进入 Performance 或 Routes。

总览同时读取服务状态摘要。如果业务指标突然归零而采集 rejected 或 Outbox pending 上升，首先要处理数据链路问题，不能把“没有数据”解释成性能改善。

### 【性能看板】

Performance 页面按时间展示 LCP、FCP、INP、CLS、FPS 和 LoAF。分位数反映群体分布，评级分布反映服务端阈值口径，覆盖率反映实际产生该指标的 View 占比。样本量很低时，即使 p75 较差也应结合原始事件判断，不能忽略统计基础。

环境、版本、routeName、指标和时间范围共同构成查询维度。对比发布前后时，应固定其他过滤条件，只改变 version 或时间段，避免把页面流量结构变化误判为版本回归。

### 【页面排名】

Routes 页面把 routeName 与指标组合起来，展示 p75、样本量、异常率、页面访问量，以及 LoAF 每千次访问数量。它适合从全站异常缩小到具体页面。动态 URL 没有稳定 routeName 时，页面会被拆成大量低样本条目，因此接入阶段的页面命名直接影响可读性。

### 【自定义事件】

Events 页面展示业务主动调用 `monitor.track()` 产生的事件趋势和页面分布。它不等同于自动 DOM 点击记录，而是业务明确表达的关键动作，例如 `order_submit`。属性已经过 SDK 和服务端双重限制与脱敏，仍不应传入密码、Token 或大对象。

### 【原始事件】

Raw Events 支持 eventId、sessionId、viewId、类型和名称检索，并使用 cursor 翻页。它承担两类工作：确认某一条客户端事实是否进入平台，以及在聚合异常时查看实际 Envelope、sequence、state、routeName 和处理时间。

原始页不是长期日志仓库，明细默认保留 30 天。需要复盘更早趋势时使用聚合看板，而不是依赖已经执行保留策略的原始事件。

### 【服务状态】

Service Status 展示最近一分钟 accepted、最近一分钟 processed、累计 accepted/duplicate/rejected、Outbox pending/processing/failed 和最近死信。它把链路分成三个判断点：

```text
accepted 不增长
  → 检查 SDK、DSN、Origin、协议和限流

accepted 增长，pending 持续上升
  → 检查 Worker 存活、数据库负载和消费容量

failed / dead letter 增长
  → 查看具体 eventId 和错误，修复后由 owner 重试
```

## 4. 前端请求与刷新

### 【统一 API 客户端】

Web 的 API 客户端统一携带 Session Cookie，并在写请求中加入 CSRF Token。遇到未登录响应时，认证上下文清理当前用户并引导回登录页。页面组件不直接拼装鉴权逻辑，以免部分设置请求遗漏 CSRF。

Analytics 默认查看最近 24 小时，查询参数使用 ISO 时间。主要页面通过 TanStack Query 管理加载、错误、缓存和刷新；看板默认每 15 秒重新请求，不在第一版引入 WebSocket。这个频率与 Worker 的异步处理、服务端 15 秒缓存共同形成近实时体验。

### 【图表与表格如何分工】

趋势图用于观察随时间变化，指标卡用于当前范围的总体结论，表格用于比较页面、事件或原始记录。不能只展示一条平均值曲线：平均值会隐藏长尾，因此 Performance 同时呈现 p50、p75、p90、p95 和评级分布。

## 5. 本地运行

### 【启动命令】

从 `browser-monitor/` 根目录执行：

```powershell
pnpm install
Copy-Item platform/.env.example platform/.env
docker compose --env-file platform/.env --profile dev -f platform/infra/docker-compose.yml up --build
```

迁移容器先创建普通关系表、TimescaleDB 扩展、Hypertable、连续聚合、压缩和保留策略。API 就绪后，Caddy 默认在 `http://localhost:8080` 提供 Web 与 API；Mailpit 默认在 `http://localhost:8025` 展示开发邮件。通过 Compose 运行时，`SMTP_HOST` 必须使用容器服务名 `mailpit`，不能使用只指向 API 容器自身的 `localhost`；只有直接在宿主机运行 API 时才改为 `localhost:1025`。

### 【生产必须修改的配置】

`.env.example` 只提供本地模板。生产环境至少要替换数据库凭据、`COOKIE_SECRET`、`USER_HASH_SECRET`、公开域名和 SMTP 配置，并启用 HTTPS。Caddy 的 `/internal/metrics` 只应对受信网络开放，不能与公开采集路由使用相同暴露策略。

## 6. 端到端排查手册

### 【第一步：确认 SDK 配置】

检查业务构建中是否只使用 `transport.dsn`，没有旧 `endpoint`；确认 `app.name` 与平台项目标识完全一致；确认页面实际 Origin 包含协议、域名和端口，且与白名单一致；确认 SDK 已调用 start，Performance 或 Custom Event 功能没有被配置关闭。

### 【第二步：确认 HTTP 结果】

浏览器 Network 中查看 `/api/v2/ingest/.../envelopes`。202 还要继续阅读 accepted、duplicate 和 rejected；429 表示项目或 IP 配额不足；403 通常对应 Origin；404 的 `invalid_ingestion_key` 表示 key 无效、禁用或过期；422 的 `unsupported_protocol` 或 `invalid_batch` 表示客户端数据契约不正确。

### 【第三步：确认持久化与消费】

服务状态 accepted 增长说明事务接收完成。pending 短暂增长属于正常异步过程；持续增长且 processed 不变时检查 Worker 容器和数据库连接。processing 长期存在可能来自中断实例，超过五分钟应被重新领取。failed 和死信需要查看错误详情，不能只重复重启进程。

### 【第四步：确认查询条件】

原始事件可以找到而看板为空时，检查 occurredAt 是否位于当前时间范围、环境和版本是否匹配、routeName 是否为空或不同、metric 过滤是否正确。Performance 还要检查 payload 的 sampleId、sequence、state，以及 Worker 是否已经设置 processed_at。

### 【第五步：确认聚合】

只有长时间范围缺数据时，检查 TimescaleDB Toolkit、连续聚合和迁移执行情况。最近 29 天主要查询明细，更早范围切换到小时 Rollup；因此聚合故障可能不会立刻影响默认 24 小时看板。

## 7. 运行监控

### 【健康检查】

`GET /health/live` 判断 API 进程是否运行，`GET /health/ready` 判断数据库和 Redis 是否就绪。容器编排应该使用 ready 决定是否接流量，而不是把进程启动等同于服务可用。

### 【Prometheus 指标】

`GET /internal/metrics` 暴露采集事件结果、采集延迟、Outbox 各状态和死信数量。生产监控至少应观察采集接口 p95、429 和 5xx、pending 增长率、最老任务等待时间、dead letter 增量和数据库空间。单看 API HTTP 成功率无法证明 Worker 没有积压。

### 【容量验证】

`load/k6-ingestion.js` 可以模拟持续和峰值采集。压测使用 `infra/docker-compose.load.yml` 提高测试配额，不能把压测限流覆盖带入生产默认值。验收时需要同时观察客户端发送数、API accepted、原始事件数量、Worker 完成数和最终聚合样本数，才能确认链路没有静默丢失。

## 8. 对应代码

### 【前端和管理入口】

- `apps/web/src/App.tsx`：公开、受保护和项目级路由；
- `apps/web/src/auth/AuthContext.tsx`：登录状态；
- `apps/web/src/api/client.ts`：Cookie、CSRF 与错误处理；
- `apps/web/src/pages/`：总览、性能、页面、事件、原始数据、服务状态和设置；
- `apps/api/src/auth/`：注册、验证、Session 和邮件；
- `apps/api/src/projects/`：项目、成员、key、Origin、阈值和死信重试；
- `apps/api/src/analytics/`：看板查询；
- `apps/api/src/health/`、`apps/api/src/observability/`：健康检查与运行指标。

这组页面的价值不只是“有图表”，而是把平台的每个可靠性边界暴露为可判断的状态：接入是否正确、数据是否接收、任务是否处理、指标是否形成，以及异常是否可以追溯。
