## 1. 系统边界：三个包，一条链路

完整系统位于同一个 `browser-monitor/` workspace，由三个有明确边界的项目构成：

| 包         | 目录                        | 主要输入                       | 主要输出                             | 不承担的责任                   |
| ---------- | --------------------------- | ------------------------------ | ------------------------------------ | ------------------------------ |
| `protocol` | `browser-monitor/protocol/` | 双方共同认可的数据约束         | Zod Schema、类型、常量、fixture      | 采集逻辑、业务处理、网络请求   |
| `sdk`      | `browser-monitor/sdk/`      | 浏览器 API、业务埋点、接入配置 | 协议 3.0 事件批次                    | 数据库存储、指标看板、账号权限 |
| `platform` | `browser-monitor/platform/` | 协议批次与管理操作             | 原始数据、指标、查询接口、可视化页面 | 页面 Hook 与浏览器运行时采集   |

**一句话**：SDK 只生产协议事件，平台只消费协议事件，协议由 `protocol` 包定死。

`protocol` 不是「复制到 SDK 和服务端的类型文件」，而是二者直接依赖的同一个包：SDK、API、Worker 都 import `@browser-monitor/protocol`。因此字段、枚举或版本号一旦变化，会在同一个 workspace 的类型检查与协议测试里立刻暴露，不会出现「SDK 按旧协议发、平台按新协议收」的静默错配。

当前协议常量（`../../protocol/src/constants.ts`）：

```ts
export const PROTOCOL_VERSION = "3.0" as const;
export const MAX_BATCH_EVENTS = 100;
export const PERFORMANCE_METRICS = [
  "LCP",
  "FCP",
  "INP",
  "CLS",
  "FPS",
  "LoAF",
] as const;
export const WEB_VITAL_METRICS = ["LCP", "FCP", "INP", "CLS"] as const;
```

## 2. 平台由哪些运行单元组成

新手最容易产生的误解是「一个后端项目 = 一个进程」。Platform 是一个 pnpm workspace，同时产出多个可独立部署的运行单元。

### 2.1 五个进程 + 一批共享包

| 单元             | 位置                                     | 技术                                | 职责                                                  | 启动入口                           |
| ---------------- | ---------------------------------------- | ----------------------------------- | ----------------------------------------------------- | ---------------------------------- |
| **API**          | `apps/api`                               | NestJS + Fastify                    | HTTP 接口：采集、认证、项目管理、分析查询、实验室任务 | `apps/api/src/main.ts`             |
| **Worker**       | `apps/worker`                            | 纯 Node.js                          | 消费 Outbox，投影明细、计算评级                       | `apps/worker/src/main.ts`          |
| **Audit Worker** | `apps/audit-worker`                      | Node.js + Chrome + Lighthouse       | 跑主动实验室测试（不碰 RUM 数据）                     | `apps/audit-worker/src/main.ts`    |
| **Web**          | `apps/web`                               | React + Vite + Ant Design + ECharts | 管理后台与看板                                        | `apps/web/src/main.tsx`            |
| **Migrate**      | `packages/database`                      | Node.js 脚本                        | 建表、Hypertable、连续聚合、保留策略                  | `packages/database/src/migrate.ts` |
| 共享包           | `packages/{shared,database}`、`protocol` | TypeScript                          | 被上面多个单元复用                                    | —                                  |

两处关键取舍：

- **API 用框架，Worker 不用框架。** API 要处理路由、鉴权、校验、依赖注入，框架能省事；Worker 只是「取任务 → 处理 → 写回」的循环，裸 Node 更直接。
- **Worker 与 Audit Worker 必须是两个进程。** 前者是数据管道的核心，必须稳定、轻量；后者要跑 Chrome，吃内存、可能崩，还带安全风险，因此在容器里用 `read_only: true`、`cap_drop: ALL` 之类的限制隔离。

### 2.2 目录结构

```text
platform/
├─ apps/
│  ├─ api/                 # 公开采集、认证、项目管理、分析查询、实验室任务
│  ├─ worker/              # Outbox 消费、数据投影、评级和失败恢复
│  ├─ audit-worker/        # 主动实验室测试（Chrome + Lighthouse）
│  └─ web/                 # 账号、项目设置和数据看板
├─ packages/
│  ├─ database/            # 关系模型、时序表、连续聚合和迁移（0001~0006）
│  └─ shared/              # 配置、安全、隐私和阈值规则
├─ infra/                  # Caddy、Compose、镜像 Dockerfile
├─ load/                   # 采集容量脚本（k6-ingestion.js）
└─ docs/                   # 本文档
```

### 2.3 API 与 Worker 为什么必须拆开

这是全项目最重要的一个架构决策：

> **API 只需回答「这批数据平台收不收」，必须快且确定；投影和聚合要访问更多表、可能因单条脏数据失败，绝不能拖慢采集。**

因此 API 只在一个数据库事务里写「原始事件 + 待处理任务（Outbox）」，真正的计算交给独立 Worker。由此推出两条硬规则：

- 接口返回成功 ≠ 指标已经算好，中间存在异步延迟；
- Worker 崩了不影响采集，但任务会积压，需要「服务状态」页去发现。

### 2.4 基础设施职责

| 组件            | 承担                                                    |
| --------------- | ------------------------------------------------------- |
| Caddy           | 同一站点下同时暴露 Web 和 API，减少业务接入时的域名组合 |
| TimescaleDB     | 同时承载账号、项目等关系数据与遥测时序数据              |
| Redis           | 登录 Session、采集限流、短期查询缓存、运行统计          |
| Mailpit（开发） | 接收验证、密码重置和邀请邮件                            |

## 3. 端到端全景：一条事件的完整路径

### 3.1 十步链路

```text
① 注册 / 登录          POST /api/v1/auth/register → /login → 拿到会话 Cookie
        ↓
② 创建项目             POST /api/v1/projects { displayName, appName }
        ↓              同一事务写入 projects / project_members / ingestion_keys /
                       allowed_origins / audit_logs，并生成 publicKey
③ 拿到 DSN             设置页展示 /api/v3/ingest/<publicKey>/envelopes
        ↓
④ 业务侧接入 SDK       createMonitor({ app, view, transport: { dsn } })
        ↓
⑤ 用户访问页面          SDK Instrumentation → Collector → Processing → Transport
        ↓
⑥ HTTP 上报            POST /api/v3/ingest/<publicKey>/envelopes
        ↓
⑦ 平台接收并落库       校验版本/批次/项目/Origin/限流 → 逐条校验 → 脱敏 → 幂等
                       → telemetry_events + outbox_tasks（同一事务）→ 202
        ↓
⑧ Worker 异步投影      outbox_tasks → performance_samples / view_records /
                       custom_event_samples / custom_signal_samples /
                       custom_metric_samples
        ↓
⑨ 连续聚合             TimescaleDB 物化视图 *_rollup_1m → *_rollup_1h
        ↓
⑩ 看板查询             GET /api/v1/projects/:projectId/analytics/*
```

| 阶段                         | 代码位置                                                                   |
| ---------------------------- | -------------------------------------------------------------------------- |
| HTTP 采集入口                | `apps/api/src/ingestion/ingestion.controller.ts`                           |
| 校验、脱敏和事务写入         | `apps/api/src/ingestion/ingestion.service.ts`                              |
| Redis 令牌桶                 | `apps/api/src/ingestion/rate-limiter.service.ts`                           |
| Outbox 领取与恢复            | `apps/worker/src/outbox-worker.ts`                                         |
| 领域投影与服务端评级         | `apps/worker/src/processor.ts`、`sequence.ts`                              |
| 表、Hypertable 和分钟 Rollup | `packages/database/migrations/0001_platform.sql`                           |
| 小时级分层 Rollup            | `packages/database/migrations/0002_hourly_aggregates.sql`                  |
| 实时聚合修正                 | `packages/database/migrations/0003_realtime_aggregates.sql`                |
| 实验室测试表                 | `packages/database/migrations/0004_lab_audits.sql`                         |

## 4. 身份与项目接入

### 4.1 三种身份不能互换

| 身份         | 凭证                                                      | 能做什么                                                  | 不能做什么                   |
| ------------ | --------------------------------------------------------- | --------------------------------------------------------- | ---------------------------- |
| 登录 Session | Redis 中的会话 + HttpOnly Cookie（写请求另需 CSRF Token） | 读数据、改项目设置                                        | 不能替代采集身份             |
| 项目角色     | `project_members.role`：`owner` / `member`                | owner 管成员、写入键、Origin、阈值、死信重试；member 只读 | 角色本身不是凭证             |
| 采集写入键   | DSN 里的 `publicKey`                                      | 只能写入遥测                                              | 不能读数据、改配置、重试死信 |

公开 DSN 会出现在浏览器代码里，**它不是秘密管理凭据**。它的安全边界由「写入键状态 + 有效期 + Origin 白名单 + 项目/IP 限流 + 轮换」共同组成。

### 4.2 账号生命周期

开放注册会发送邮箱验证链接。未验证账号不能正常登录和创建项目；若再次提交同一个未验证邮箱，服务端会更新注册信息、作废旧验证令牌并重新发送验证邮件，始终只保留一个有效链接。已验证邮箱重复注册仍返回冲突，前端提示登录或找回密码。验证后可登录、退出、发起忘记密码并完成密码重置。

登录 Session 保存在 Redis，浏览器只持有 HttpOnly Cookie。前端 `Protected` 路由只是导航体验，真正的权限判断始终在 API：即使用户手工拼出项目 URL，服务端也会检查项目成员关系。

### 4.3 从创建项目到第一条数据

```text
① 用户创建项目，填写与 SDK app.name 一致的应用标识
② 平台在同一事务中创建 owner 成员关系、默认 ingestion key、默认阈值版本、项目盐值
③ owner 把业务页面的完整 Origin 加入允许列表
④ 设置页根据 PUBLIC_BASE_URL + publicKey 生成完整 DSN
⑤ 业务代码把 DSN 配置到 transport.dsn，启动 SDK
⑥ 浏览器请求采集 API，服务状态页出现 accepted
⑦ Worker 投影完成后，总览和性能页出现数据
```

创建项目时会写入五张表（`apps/api/src/projects/projects.service.ts`）：

```text
projects          { display_name, app_name, user_hash_salt, enabled }
project_members   { project_id, user_id, role: 'owner' }
ingestion_keys    { project_id, public_key: 'bm_pk_…', label: 'default', active, expires_at }
allowed_origins   { project_id, origin }     ← 默认只有平台自己的域名
audit_logs        { project_id, action: 'project.created', detail }
```

DSN 由同一份配置拼出：

```ts
// apps/api/src/projects/projects.service.ts
private toDsn(publicKey: string): string {
  return new URL(`/api/v3/ingest/${publicKey}/envelopes`, this.config.PUBLIC_BASE_URL).toString();
}
```

**⚠️ 最容易踩的坑**：`allowed_origins` 默认只包含 `PUBLIC_BASE_URL` 的 origin，**业务域名必须手动加入**，否则浏览器上报会被 `403 origin_not_allowed` 拒绝。

### 4.4 `displayName` 和 `appName` 是两个东西

| 字段                      | 作用                                   | 约束                  | 谁在用                                       |
| ------------------------- | -------------------------------------- | --------------------- | -------------------------------------------- |
| `displayName`（项目名称） | 给人看的展示名                         | 1–120 字符            | 控制台列表、邮件                             |
| `appName`（SDK app.name） | 业务代码里 `app.name` 必须与它完全一致 | 只允许 `a-zA-Z0-9._-` | 服务端逐条校验，不一致报 `app_name_mismatch` |

设置页会把 `appName` 直接拼进代码片段，目的就是保证业务侧的 `app.name` 与项目登记的 `app_name` 天然一致。

### 4.5 写入键轮换

写入键泄露或需要切换时，owner 执行轮换：平台创建新 key，并让旧 key 在 24 小时后过期，为业务发布留出平滑迁移时间。轮换期间两把 key 都能写入，不会造成发布窗口内的数据真空。

### 4.6 routeName 为什么需要业务参与

URL pathname 可能包含订单 ID、用户 ID 等高基数动态片段。SDK 默认清除 query 和 fragment，但无法可靠猜测 `/users/123` 与 `/users/456` 是否属于同一业务页面。业务可以提供 `resolveRouteName` 或调用 `setViewName()`，把它们稳定映射为 `user-detail`：

```ts
createMonitor({
  app: { name: "customer-center", version: "1.4.0", environment: "production" },
  view: {
    resolveRouteName: ({ pathname }) => pathname.replace(/\/\d+/g, "/:id"),
  },
  transport: {
    dsn: "https://monitor.example.com/api/v3/ingest/bm_pk_xxx/envelopes",
  },
});
```

不做归并的后果很直接：页面排名会被打散成大量低样本条目，可读性急剧下降。

## 5. 协议 3.0：上报的数据长什么样

### 5.1 批次与事件

请求体是一个 `TelemetryBatchV3`，由批次头 + 事件数组组成（`protocol/src/schemas.ts`）：

```ts
interface TelemetryBatchV3 {
  protocolVersion: "3.0";
  sentAt: number;
  sdk: { name: string; version: string };
  events: TelemetryEventV3[];
}
```

批次头只校验 `events` 是数组、数量在 1–100 之间，**不逐条校验**。这是 Partial Acceptance 设计：单条坏事件不会让整批失败。事件级一致性由 `telemetryEventV3Schema` 负责，它包含几类交叉校验：

- `event.type` 必须等于 `payload.type`；
- `event.name` 必须等于 `payload.name`；
- View 事件里 `context.viewId` 必须等于 `payload.viewId`。

Schema 使用 `.strict()`：多一个未声明字段就会被判为非法。

### 5.2 事件类型总览

| payload 类型                           | 语义                                | 落表                    |
| -------------------------------------- | ----------------------------------- | ----------------------- |
| `performance`（LCP / FCP / INP / CLS） | 修订型 Web Vitals 样本              | `performance_samples`   |
| `performance`（FPS / LoAF）            | 一次性终态样本                      | `performance_samples`   |
| `view`（`view.start` / `view.end`）    | 页面访问的起止                      | `view_records`          |
| `event`                                | 业务自定义事件                      | `custom_event_samples`  |
| 自定义 Trace / Span                    | 链路追踪信号（`kind = trace/span`） | `custom_signal_samples` |
| 自定义指标                             | 业务自定义数值指标                  | `custom_metric_samples` |

### 5.3 性能样本的两种语义

所有性能指标共享四个字段，但用法分两类（`protocol/src/schemas.ts`）：

```ts
const performanceSampleSchema = z.object({
  type: z.literal("performance"),
  sampleId: identifier, // 样本身份
  sequence: z.number().int().nonnegative(), // 同一样本内的修订序号
  state: performanceSampleStateSchema, // 'provisional' | 'final'
  value: finiteNonNegative,
});
```

- **修订型（LCP / FCP / INP / CLS）**：一次页面访问中指标值会不断变化，SDK 用同一个 `sampleId` 反复上报修订，`sequence` 从 0 递增，`state` 标记是否已定稿，另外带 `delta`、`clientRating`、`navigationType`、`navigationId`。
- **一次性终态（FPS / LoAF）**：每次观测本身就是独立样本，`sampleId` 每次新建，`sequence` 恒为 0，`state` 直接是 `final`。

这个区别是整个聚合逻辑分叉的根源，第 8、9 节会反复用到。

### 5.4 一次上报报文的形状

```http
POST /api/v3/ingest/bm_pk_9Kd2Lm/envelopes HTTP/1.1
Content-Type: application/json
Origin: https://shop.example.com

{
  "protocolVersion": "3.0",
  "sentAt": 1758508800000,
  "sdk": { "name": "cx-browser-monitor-sdk", "version": "0.2.0" },
  "events": [
    {
      "protocolVersion": "3.0",
      "eventId": "event_7f3a91",
      "type": "performance",
      "name": "LCP",
      "occurredAt": 1758508799123,
      "app": { "name": "customer-center", "version": "2.3.1", "environment": "production" },
      "context": {
        "sessionId": "session_5c2e",
        "viewId": "view_07",
        "routeName": "/checkout",
        "url": "https://shop.example.com/checkout?step=2",
        "runtime": { "userAgent": "...", "language": "zh-CN", "online": true },
        "user": { "id": "u-10086", "properties": { "vip": "gold" } }
      },
      "payload": { "type": "performance", "name": "LCP", "sampleId": "s-1", "sequence": 0,

```

SDK 正常运行时使用 Fetch；页面退出时可以用 Beacon 发送**相同的 JSON 文档**。采集 API 对 Beacon 的 `text/plain` 字符串和普通 `application/json` 走同一套解析与校验，不因发送方式不同而形成第二条接收逻辑，也不会为 Beacon 维护字段更宽松的协议。

## 6. 采集 API：公开流量进入平台的第一道边界

采集 API 既不能信任浏览器提交的身份和属性，也不能为了低延迟只把数据放进内存队列。项目把「**已接收**」定义为「原始事件与 Outbox 任务已在数据库事务中持久化」：后续计算可以异步，但不能失去恢复入口。

### 6.1 端点与请求模型

```text
POST /api/v3/ingest/:publicKey/envelopes   → HTTP 202
```

`publicKey` 把公开请求映射到一个启用中的项目和 `app.name`。路由实现在 `../apps/api/src/ingestion/ingestion.controller.ts`。

### 6.2 校验顺序（每一步失败都不写库）

```text
① 协议版本         ≠ 3.0                → 422 unsupported_protocol
② 批次头结构       zod 失败             → 422 invalid_batch
③ publicKey → 项目 查不到 / 停用 / 禁用 / 过期 → 404 invalid_ingestion_key
④ Origin 白名单    不在列表 / 缺失       → 403 origin_not_allowed / origin_required
⑤ 限流            项目 + IP 超额        → 429 ingestion_rate_limited
⑥ 逐条事件        schema 失败           → invalid_event
                  app.name ≠ 项目       → app_name_mismatch
                  occurredAt 超窗口     → event_time_out_of_range
```

为什么是这个顺序：

- **协议版本最先检查**，可以对 1.0/2.0 等旧格式明确返回 `unsupported_protocol`，而不是让旧请求在深层字段校验中得到难以理解的错误。
- **批次头通过后才扣限流令牌**，避免完全无法解析的请求消耗数据库事务。
- **项目解析同时检查写入键是否启用、是否过期，以及项目是否启用**。所以「项目没创建 → 没有 key → 404 → 一条数据都不会落库」，事务根本没开始。
- **Origin 会先标准化为 URL 的 origin，再与 `allowed_origins` 精确匹配**。无 Origin 请求默认拒绝，只有明确开启 `ALLOW_ORIGINLESS_INGEST` 的环境才允许这类流量。

### 6.3 批次错误与事件错误不是一回事

| 层级   | 失败项                                      | 结果                                              |
| ------ | ------------------------------------------- | ------------------------------------------------- |
| 批次级 | 协议版本、批次形状、publicKey、Origin、限流 | **整批拒绝**，没有可信处理上下文                  |
| 事件级 | 单条 Schema、`app.name`、`occurredAt` 越界  | 只把该下标放进 `rejections`，其余合法事件照常提交 |

事件时间允许最多领先服务器 5 分钟，并且不能早于 30 天。这个窗口既容忍终端时钟的小幅偏差，又避免极端时间戳污染时序分区和保留策略。

### 6.4 服务端脱敏：为什么客户端清过还要再清一遍

SDK 已经移除 URL query、fragment 和常见敏感属性，但公开采集边界不能假设所有客户端都来自最新 SDK，也不能信任调用方没有手工构造请求。因此服务端在写入前再次执行：

- URL 清理；
- 自定义事件 / Trace / Span 的 `attributes` 属性脱敏；
- 用户属性脱敏。

用户原始 ID 不直接落库：平台把**项目盐值 + 原始 ID + 服务端 `USER_HASH_SECRET`** 组合成项目范围内的稳定散列。结果是同一个用户在同一项目内可以关联，但不会天然跨项目共享标识。

清理发生在幂等判定之前，事件合法 → 生成清理后的对象 → 再去重与写入。`eventId` 本身不变，所以客户端重试原事件仍然命中同一个幂等键，而落入 `telemetry_events.event` 的始终是服务端处理后的版本。

### 6.5 eventId 幂等：三层防护

| 层级          | 手段                                       | 解决什么                                             |
| ------------- | ------------------------------------------ | ---------------------------------------------------- |
| 请求内        | 内存 Set 去重                              | 同一批次里的重复 `eventId`，不产生无意义的锁与写操作 |
| 跨请求 / 并发 | `pg_advisory_xact_lock(projectId:eventId)` | 同一 ID 携带不同 `occurredAt` 的并发请求             |
| 数据库        | 唯一约束 + `ON CONFLICT DO NOTHING`        | 最后一道兜底                                         |

TimescaleDB 的唯一索引通常需要包含分区时间，而平台的幂等语义要求仅由「项目 + `eventId`」决定，这就是必须额外加 advisory lock 的原因。

事件 ID 会**先排序再按确定顺序取锁**，因此两个重叠批次不会因为锁顺序相反产生循环等待。拿到锁后查询项目下已存在的 ID，只对不存在的事件执行插入。

### 6.6 原始事件与 Outbox 的原子提交

两张表分别负责两件事：

- `telemetry_events`：**事实留存**，保存事件 Envelope、查询常用维度、接收时间和处理时间；
- `outbox_tasks`：**处理状态**，保存 Worker 需要的副本、可执行时间、尝试次数、锁持有者和任务状态。

如果先写事件再单独发消息，服务在两步之间退出就会留下无法处理的原始数据；如果先创建任务再写事件，Worker 可能看见尚不存在的事实。因此两者必须共享数据库事务，写入使用一个带 CTE 的 SQL：先插入 `telemetry_events`，再只对 `RETURNING` 的新行插入 `outbox_tasks`。

```text
BEGIN
  ① 对当前批次 eventId 取 advisory transaction lock（按 ID 排序）
  ② 查询已存在的 eventId
  ③ INSERT telemetry_events ... ON CONFLICT DO NOTHING RETURNING
     → 为真正插入的行 INSERT outbox_tasks
  ④ UPDATE ingestion_keys SET last_used_at = now()
COMMIT
```

任何 SQL 失败都 `ROLLBACK`。**只有 COMMIT 成功后，响应里的 accepted 才表示可靠接收。** Redis 里的运行统计在提交后更新，而且统计写失败不会把已经提交的数据伪装成 SDK 可重试错误。

### 6.7 响应语义与 SDK 重试

```json
{
  "accepted": 18,
  "duplicate": 1,
  "rejected": 1,
  "requestId": "request-uuid",
  "rejections": [{ "index": 7, "code": "invalid_event" }]
}
```

| 字段        | 含义                                                             |
| ----------- | ---------------------------------------------------------------- |
| `accepted`  | 本次真正创建原始记录和任务的数量                                 |
| `duplicate` | 请求内重复 + 历史重复 + 最终数据库冲突                           |
| `rejected`  | 逐事件校验失败数量                                               |
| `requestId` | 同时进入日志和最近一分钟接收统计，可把客户端现象与服务端请求关联 |

**哪些错误值得重试**：`408`、`429` 和 `5xx` 可能随时间恢复，SDK 可以有限次数退避重试。协议版本不支持、public key 无效、Origin 不允许、`app.name` 不匹配和单条字段非法都不会因原样重发而改变，因此不应进入无限重试队列。

即使客户端在收到响应前断线，只要数据库已经提交，下次重发也会由 `eventId` 识别为 duplicate。这个性质让「网络超时」不再等价于「重复计算」。

### 6.8 限流与硬限制

Redis Lua 脚本分别维护**项目级**和**项目内 IP 级**令牌桶，一次批次按**事件数量**消费令牌，而不是只按 HTTP 请求数计算，防止调用方通过放大批次绕过配额。项目桶保护租户整体容量，IP 桶限制单一来源对项目额度的挤占。生产默认配额是每项目 100 events/s、突发 500。

硬限制集中在入口，越靠近入口越能避免异常请求在 JSON 解析、数据库事务或 Worker 阶段放大资源消耗：

| 限制           | 值      | 来源        |
| -------------- | ------- | ----------- |
| 请求体大小     | 256 KiB | Fastify     |
| 单批事件数     | 100     | 协议 Schema |
| 事件名长度     | 128     | 协议常量    |
| routeName 长度 | 160     | 协议常量    |
| URL 长度       | 2048    | 协议常量    |

## 7. Worker 与 Outbox

Worker 把已经可靠接收的协议事件转换成适合查询和聚合的领域数据。原始事件保留「客户端实际发送了什么」，投影表回答「平台需要怎样统计它」。**这两个层次不能合并**：原始事实用于审计和追溯，投影模型可以随查询需求独立演进。

### 7.1 输入不是消息中间件

API 把每条首次接收的事件写进 `outbox_tasks`，Worker 直接从 PostgreSQL 领取任务，不依赖额外的消息系统。

```text
outbox_tasks.pending
  → claim
outbox_tasks.processing
  → EventProcessor 事务
领域投影 + telemetry_events.processed_at
  → completed
analytics:version:<projectId> + 1
```

### 7.2 多实例领取：SKIP LOCKED

领取 SQL 先找出到期的 pending 任务，以及锁定超过 5 分钟的 processing 任务，再用 `FOR UPDATE SKIP LOCKED` 取一个批次：

```sql
WITH candidates AS (
  SELECT id FROM outbox_tasks
  WHERE (status = 'pending' AND available_at <= now())
     OR (status = 'processing' AND locked_at < now() - INTERVAL '5 minutes')
  ORDER BY available_at, created_at
  LIMIT $1
  FOR UPDATE SKIP LOCKED
)
UPDATE outbox_tasks o SET
  status = 'processing', locked_at = now(), locked_by = $2, attempts = attempts + 1
FROM candidates c WHERE o.id = c.id
RETURNING o.id, o.project_id, o.event_id, o.event, o.attempts
```

不同 Worker 实例遇到已被另一个事务锁定的行会跳过，而不是彼此等待，因此可以横向扩容。领取动作与状态变化在**同一条 SQL 里原子完成**，不会出现两个实例都先查到 pending、随后同时处理的时间窗口。

**进程退出如何恢复**：`processing` 不是永久状态。锁定超过 5 分钟后任务重新满足领取条件，后续实例会再次处理它——因此领域投影必须幂等，不能假设每个任务只执行一次。

### 7.3 事件类型 → 投影表

| payload 类型        | 目标表                  | 主要用途                                    |
| ------------------- | ----------------------- | ------------------------------------------- |
| `performance`       | `performance_samples`   | 指标趋势、评级分布、分位数和页面排名        |
| `view`              | `view_records`          | PV、会话数、页面覆盖率和 View 结束状态      |
| `event`             | `custom_event_samples`  | 业务事件趋势和页面分布                      |
| 自定义 Trace / Span | `custom_signal_samples` | 链路追踪：起止、耗时、状态、trace/span 关联 |
| 自定义指标          | `custom_metric_samples` | 业务自定义数值指标                          |

投影完成后 Worker 更新对应的 `telemetry_events.processed_at`，因此原始事件页可以区分「已接收但尚未处理」和「已经进入查询模型」。

### 7.4 事务范围与至少一次投递

`processor` 为每条事件打开事务，在事务中完成领域写入和 `processed_at` 更新。任何一步失败都会回滚，这样不会出现「领域表已有数据、原始表仍显示未处理」的半完成状态。

但 Worker 在领域事务提交后，还要**单独**把 Outbox 标记为 completed。如果进程恰好在两者之间退出，任务会被重新领取。系统的选择是：

```text
At-least-once 投递
+
幂等投影
```

即允许任务重新执行，但重复执行不能改变最终结果。这就是各种唯一约束、`ON CONFLICT DO NOTHING` 和 sequence 规则存在的原因。

### 7.5 Performance 样本修订

Web Vitals 的值会在页面生命周期中更新，SDK 为同一次观测保持稳定 `sampleId`，每次修订递增 `sequence`：

```text
LCP sampleId = lcp-view-1
sequence 0, value 1800, provisional
sequence 1, value 2300, provisional
sequence 2, value 2600, final
```

`performance_samples` 的主键决定了「修订」的语义：

```sql
PRIMARY KEY (project_id, sample_id, observed_at)
```

`observed_at` 用首次插入时的 `occurredAt` 冻结，后续所有修订都是**原位 UPDATE**，不会插成多行。因此分位数看到的是「一次观测 = 一个样本」。

准入规则只有一行（`apps/worker/src/sequence.ts`）：

```ts
export function shouldApplySequence(
  current: number | null,
  incoming: number,
): boolean {
  return current === null || incoming > current;
}
```

**只有更高序号才接受**，重复投递与乱序到达被静默丢弃。这正是 Outbox 至少一次投递下数据仍然准确的原因。

**为什么不能把每次变化都当新样本**：如果 LCP 从 1800 更新到 2600 时插入两行，分位数和样本量会把同一页面体验计算两次，较活跃的页面还会获得更高权重。按 `sampleId` 保留最高 sequence 后，一个指标观测在聚合中始终只占一个样本。

### 7.6 state：final 是单向的

```ts
const state =
  payload.state === "final" ||
  current?.state === "final" ||
  viewEnded.rowCount === 1
    ? "final"
    : "provisional";
```

三种情况都会置为 `final`：SDK 已定稿、库里已经是 final、或该 View 已结束。**final 永不回退为 provisional**，但更高 sequence 的迟到事件仍可修正 final 的数值。

### 7.7 样本终结的三条路径

| 路径          | 触发                                                      | 适用情况                                           |
| ------------- | --------------------------------------------------------- | -------------------------------------------------- |
| SDK 主动      | `pagehide`（刷新/关页）或 `view.route-change`（SPA 跳转） | 最正常，值最准确                                   |
| View 结束兜底 | `view.end` 到达                                           | Collector 来不及逐项发 final，但 View 结束事件已到 |
| 超时兜底      | Worker 每 60 秒扫描一次                                   | 浏览器被强杀、Beacon 丢失、网络断开                |

`view.end` 处理时会顺带把该 View 下残留的 provisional 样本一并置为 final 并补齐 `routeName`：

```sql
UPDATE performance_samples SET state = 'final', route_name = $3
WHERE project_id = $1 AND view_id = $2 AND state = 'provisional'
```

超时兜底用的是 `last_updated_at`（平台侧最后更新时间），而不是 `observed_at`：

```sql
UPDATE performance_samples SET state = 'final'
WHERE state = 'provisional' AND last_updated_at < now() - INTERVAL '5 minutes'
RETURNING project_id
```

超时终结**不是拒绝迟到数据**：后续更高 sequence 仍可修正数值，只是状态保持 final。这样看板不会永久遗漏样本，同时仍接受网络延迟造成的合法更新。

### 7.8 服务端评级是唯一口径

SDK 上报的 rating 存为 `clientRating`，便于定位客户端版本或阈值差异；**看板一律使用 Worker 计算的 `serverRating`**。原因是项目可能覆盖默认阈值，而阈值版本属于服务端项目配置，旧 SDK 不可能提前知道。

默认阈值（`packages/shared/src/thresholds.ts`）：

| 指标 | 方向     | Good      | Needs improvement | Poor      |
| ---- | -------- | --------- | ----------------- | --------- |
| LCP  | 越小越好 | ≤ 2500 ms | ≤ 4000 ms         | > 4000 ms |
| INP  | 越小越好 | ≤ 200 ms  | ≤ 500 ms          | > 500 ms  |
| CLS  | 越小越好 | ≤ 0.1     | ≤ 0.25            | > 0.25    |
| FCP  | 越小越好 | ≤ 1800 ms | ≤ 3000 ms         | > 3000 ms |
| FPS  | 越大越好 | ≥ 50      | ≥ 30              | < 30      |

LoAF 不被强制套入 good/poor 阈值，而是保留 duration、blocking duration 和 script count，用密度与分位数表达影响。

**阈值版本化**：Worker 读取项目当前有效的阈值版本，把项目覆盖项合并到默认集合后计算，并把 `threshold_version_id` 与样本一起保存。项目修改阈值**只影响之后处理的样本**，不会静默重写已有数据的历史口径。若产品未来需要「按新阈值重算历史」，应当显式创建重算任务和新口径版本。

### 7.9 失败、退避与死信

| 失败类型                    | 处理                                                                                      |
| --------------------------- | ----------------------------------------------------------------------------------------- |
| 可恢复（attempts < 8）      | 状态恢复为 pending、清除锁、设置新的 `available_at`；等待秒数为 `min(300, 2 ** attempts)` |
| 不可自动恢复（第 8 次失败） | 同一事务写入 `dead_letter_tasks`，再把 Outbox 置为 failed                                 |

死信保存事件、错误堆栈截断结果、尝试次数和失败时间。Owner 从服务状态页触发重试后，平台删除对应死信记录并把 Outbox 恢复为 pending、attempts 归零。

**死信不是被忽略的数据**，它是「原始事实已接收，但投影需要人工介入」的明确状态。修复代码后重放任务，会继续利用领域幂等规则避免重复。

### 7.10 缓存失效与可见时间

Analytics 缓存键包含 `analytics:version:${projectId}`。每条任务成功后 Worker 递增项目版本，新查询自然落到新的 key，**不需要枚举和删除该项目的所有过滤组合**；旧 key 只保留 15 秒，到期自动清理。超时终结样本的维护任务同样会递增版本。

正常链路的可见延迟由 Worker 轮询、任务处理、连续聚合刷新和 Web 定时请求共同决定，新数据通常在约 10～15 秒内可见。服务状态页可以判断等待来自正常异步处理还是 Worker 故障：

```text
accepted 增长而 processedLastMinute 不增长  → 问题在 API 之后
pending 长期增大                            → 消费能力不足
failed / deadLetters 增长                   → 存在确定性处理错误
```

## 8. 数据模型：从事实到统计的五层

监控数据既要能逐条追溯，也要能按时间、页面和版本快速统计。只保存聚合会失去审计能力，只查询原始 JSON 又无法稳定支撑分位数和长时间趋势，因此平台保留多个层次，并由 Analytics API 根据查询跨度选择数据源。

### 8.1 层次总览

| 层次       | 表                                                                                                     | 回答的问题                   |
| ---------- | ------------------------------------------------------------------------------------------------------ | ---------------------------- |
| 原始事实   | `telemetry_events`                                                                                     | 浏览器到底上传过什么         |
| 处理状态   | `outbox_tasks` / `dead_letter_tasks`                                                                   | 这条数据被处理了吗，卡在哪   |
| 领域明细   | `performance_samples` / `view_records` / `custom_event_samples`                                        | 平台应该怎么理解这些数据     |
| 自定义观测 | `custom_signal_samples` / `custom_metric_samples`                                                      | 业务自定义的事件、链路与指标 |
| 时间聚合   | `*_rollup_1m` / `*_rollup_1h`                                                                          | 大量样本的整体分布长什么样   |
| 业务配置   | `projects` / `project_members` / `ingestion_keys` / `allowed_origins` / `threshold_versions` / `lab_*` | 身份、权限、口径             |

### 8.2 原始事实层

`telemetry_events` 保存协议事件和常用检索维度：`eventId`、发生与接收时间、类型、名称、环境、版本、Session、View、routeName 和服务端清理后的完整事件。它用于原始事件检索、处理状态确认和问题追溯，**不直接承担指标查询**。

环境、应用版本和 routeName 不只存在 JSON 中，也投影为普通列。Analytics 如果每次都从 JSON 读这些维度，将难以建立有效索引，也会让 SQL 和类型转换复杂化。常用稳定维度列化、完整事件仍保留在 JSON 中，兼顾查询性能与追溯信息。

### 8.3 领域明细层

| 表                      | 关键内容                                                                             | 查询作用               |
| ----------------------- | ------------------------------------------------------------------------------------ | ---------------------- |
| `performance_samples`   | 当前最高 sequence、数值、state、服务端评级、阈值版本、LoAF 扩展值                    | 性能统计和页面性能排名 |
| `view_records`          | View 开始、结束、页面、Session、环境和版本                                           | PV、会话数、覆盖率     |
| `custom_event_samples`  | 事件名、页面和清理后属性                                                             | 业务事件趋势与分布     |
| `custom_signal_samples` | `kind`（event/trace/span）、状态、起止时间、耗时、trace/span/parent 关联、attributes | 链路追踪查询           |
| `custom_metric_samples` | 自定义指标名、单位、值                                                               | 自定义指标趋势与聚合   |

`performance_samples` 表示「当前样本」，不是「每次协议更新」——这是第 7.5 节 sequence 规则的直接结果。

### 8.4 时间维度与 Hypertable

遥测查询通常围绕「事件什么时候发生」，因此原始表和领域明细按 `occurred_at` / `observed_at` 建立 Hypertable。接收时间仍然保留，用来分析客户端到平台的延迟，但看板时间范围以用户体验实际发生时间为主。

每个查询都要求项目 ID 和半开时间区间 `[from, to)`。半开区间让相邻窗口首尾相接而不重复计算边界记录，也能帮助 TimescaleDB 裁剪不相关时间分区。

### 8.5 聚合层：为什么不能只存 p75

假设一分钟有 5 个 LCP：`1000 1500 2000 2500 3000`。如果只保存这一分钟的 `p75 = 2500`，那么想算两分钟的整体 p75 时就只能：

```text
(2500 + 3000) / 2   ← 错的
```

原因有两个：两分钟流量权重可能悬殊（100 个样本 vs 10000 个样本），而且**分位数本身不可直接平均**。正确做法是把两份完整分布合起来，再重新取分位点。因此聚合表保存的是**可继续合并的中间状态**，而不是提前算死的数字。

一分钟聚合（`0001_platform.sql`）大致是：

```sql
SELECT
  time_bucket(INTERVAL '1 minute', observed_at) AS bucket,
  project_id, name, environment, app_version, route_name, threshold_version_id,
  count(*)::bigint                                             AS sample_count,
  min(value)                                                   AS minimum,
  max(value)                                                   AS maximum,
  avg(value)                                                   AS average,
  percentile_agg(value)                                        AS value_percentiles,
  count(*) FILTER (WHERE server_rating = 'good')                AS good_count,
  count(*) FILTER (WHERE server_rating = 'needs-improvement')   AS needs_improvement_count,
  count(*) FILTER (WHERE server_rating = 'poor')                AS poor_count,
  hyperloglog(8192, session_id)                                AS session_hll,
  hyperloglog(8192, view_id)                                   AS view_hll
FROM performance_samples
GROUP BY bucket, project_id, name, environment, app_version, route_name, threshold_version_id
```

小时聚合（`0002_hourly_aggregates.sql`）基于分钟聚合再分层：

```sql
SELECT time_bucket(INTERVAL '1 hour', bucket) AS bucket, ...
  sum(average * sample_count) / NULLIF(sum(sample_count), 0) AS average,
  rollup(value_percentiles) AS value_percentiles,
  rollup(session_hll)       AS session_hll,
  rollup(view_hll)          AS view_hll
FROM performance_rollup_1m
GROUP BY 1, 2, 3, 4, 5, 6, 7
```

两个关键点：

1. **分位数用 `rollup()` 合并中间态**，而不是对已算出的 p75 再求平均；
2. **均值按样本数加权**：`sum(average * sample_count) / sum(sample_count)`，等价于全局平均。

> 注意小时聚合里 `time_bucket(...) AS bucket` 与输入列同名，SQL 因此使用位置序号 `GROUP BY 1,2,…` 分组，确保分的是新算出的小时桶，而不是输入的一分钟桶。

### 8.6 聚合策略一览

| 对象                                                                                                                                | 刷新策略                                                  | 保留                             |
| ----------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------- | -------------------------------- |
| `*_rollup_1m`（performance / view / custom_event / telemetry / custom_signal / custom_metric）                                      | 每 10 秒，`end_offset = 10 秒`，`start_offset = 29 天`    | 180 天                           |
| `*_rollup_1h`                                                                                                                       | 每 5 分钟，`end_offset = 1 小时`，`start_offset = 179 天` | 180 天                           |
| `telemetry_events`、`performance_samples`、`view_records`、`custom_event_samples`、`custom_signal_samples`、`custom_metric_samples` | —                                                         | 30 天，超过 24 小时的 chunk 压缩 |

第三份迁移把全部聚合设置为 realtime（`materialized_only = false`），使已物化范围之外的近期明细可以与聚合结果共同参与查询，而不必等下一次物化才可见。样本行被 UPDATE 时（值从 provisional 改成 final），TimescaleDB 会记录时间段的失效并在下次刷新重算该桶，realtime 模式下失效区间由明细实时计算。因此**一次观测始终只贡献一个样本**，不会因为修订被重复计数。

### 8.7 数据生命周期小结

```text
原始事件与领域明细      保留 30 天，> 24h 压缩
分钟 / 小时聚合         保留 180 天
Outbox                  completed 任务由 housekeeping 在 7 天后删除；
                        pending / processing / failed 不会被普通清理丢掉
死信                    保留到 Owner 处理或后续制定单独策略
```

## 9. 查询层：Analytics API

### 9.1 为什么不直接给看板开数据库

浏览器看板不直接访问数据库，而是调用：

```text
GET /api/v1/projects/:projectId/analytics/*
```

Controller 把输入转换为受限的日期、字符串和分页参数，Service 以**参数化 SQL** 构建条件。所有路径在执行 SQL 前先调用项目访问校验，不能仅靠前端隐藏菜单实现隔离。统一过滤维度（`analytics.controller.ts`）：

```ts
const querySchema = z.object({
  from: z.string().datetime().optional(),
  to: z.string().datetime().optional(),
  environment: z.string().max(64).optional(),
  version: z.string().max(64).optional(),
  routeName: z.string().max(160).optional(),
  metric: z.enum(["LCP", "FCP", "INP", "CLS", "FPS", "LoAF"]).optional(),
});
```

默认查询最近 24 小时，最多回溯 180 天（超出会被夹到边界，避免查询已经过了保留期的分区）：

```ts
const to = parsed.to ? new Date(parsed.to) : new Date();
const from = parsed.from
  ? new Date(parsed.from)
  : new Date(to.getTime() - 24 * 60 * 60_000);
const minimum = new Date(to.getTime() - 180 * 24 * 60 * 60_000);
```

### 9.2 接口清单

| 接口                     | 输出重点                                           |
| ------------------------ | -------------------------------------------------- |
| `overview`               | View、Session、事件总量和各指标总体健康度          |
| `performance`            | 时间点、分位数、评级分布、覆盖率和 LoAF 扩展值     |
| `routes`                 | routeName + 指标的 p75、样本量、异常率和页面访问量 |
| `custom-signals`         | 自定义事件 / 链路 / 指标的列表（按名称与 kind）    |
| `custom-signals/detail`  | 单个自定义信号或指标的时间序列与聚合               |
| `custom-signals/records` | 自定义信号明细记录                                 |
| `traces/:traceId`        | 一个 trace 下的全部 span                           |
| `raw-events`             | 原始协议事件和处理上下文，游标分页                 |
| `service-status`         | 采集、消费、积压、失败和死信                       |

自定义信号的参数单独校验（`analytics.controller.ts`）：列表用 `kind`（`event` / `trace` / `span`）+ `name`；详情在此基础上增加可选的 `metric`、`unit` 和 `aggregation`（`count` / `sum` / `avg` / `min` / `max` / `p50` / `p75` / `p90` / `p95` / `p99`），并强制「选指标必须带单位、不带指标时只能用 count」的一致性。

页面排名的查询故意移除传入的 `routeName` 过滤，因为它要在其他过滤条件下比较多个页面；性能详情则可以用 routeName 聚焦单个页面。

### 9.3 近 29 天查明细，更早查 Rollup

```ts
private useRollups(filters: AnalyticsFilters): boolean {
  return filters.from.getTime() < Date.now() - 29 * 24 * 60 * 60_000;
}
```

| 查询跨度     | 数据源                               | 分位数算法                                                | 分桶   |
| ------------ | ------------------------------------ | --------------------------------------------------------- | ------ |
| 最近 29 天内 | 领域明细（`performance_samples` 等） | `percentile_cont()`，精确                                 | 1 分钟 |
| 早于 29 天   | `*_rollup_1h`                        | `approx_percentile(..., rollup(value_percentiles))`，近似 | 1 小时 |

明细保留 30 天，切换点定在 29 天，预留一天边界避免查询刚好跨越即将被清理的分区。这种切换**不是把两种结果拼在前端**，而是在服务端选择一个能完整覆盖查询区间的数据源。若未来需要同时返回近期分钟点和历史小时点，应明确设计多粒度响应，不能让同一时间段由明细与 Rollup 重复贡献。

近期精确查询的核心写法：

```sql
SELECT time_bucket(INTERVAL '1 minute', observed_at) AS bucket, name,
  count(*)::bigint AS count,
  count(DISTINCT session_id)::bigint AS session_count,
  count(DISTINCT view_id)::bigint    AS view_count,
  avg(value) AS average,
  percentile_cont(0.50) WITHIN GROUP (ORDER BY value) AS p50,
  percentile_cont(0.75) WITHIN GROUP (ORDER BY value) AS p75,
  percentile_cont(0.90) WITHIN GROUP (ORDER BY value) AS p90,
  percentile_cont(0.95) WITHIN GROUP (ORDER BY value) AS p95,
  count(*) FILTER (WHERE server_rating = 'good')::bigint AS good_count
FROM performance_samples p WHERE <filters> GROUP BY bucket, name
```

### 9.4 派生指标公式

```text
样本覆盖率 sampleCoverage = 有该指标的 DISTINCT view_id 数 / view_records 的 PV 数
异常率（routes）          = (needs_improvement + poor) / 有效评级样本数
会话 / 页面去重数         = distinct_count(rollup(session_hll)) / distinct_count(rollup(view_hll))
LoAF 每千次访问           = LoAF 样本数 × 1000 / 页面访问数
良好率                    = good_count / sample_count
```

LoAF 的「每千次访问」比单纯次数更能区分「页面访问量大所以事件多」和「单次访问更容易发生长动画帧」。会话与 View 去重通过 HyperLogLog 中间状态计算，因此可以跨桶合并。

### 9.5 原始事件游标分页

时序表持续写入，较大的 `offset` 需要数据库扫描并丢弃越来越多行，而且新事件插入会让页面位置漂移。平台改用游标：按 `(occurred_at, event_id)` 倒序，把最后一行的两个值编码为 Base64URL cursor，下一页条件为：

```sql
(occurred_at, event_id) < (:cursorOccurredAt, :cursorEventId)
```

`eventId` 是同一时间戳下的稳定次级排序键。API 每次多取一行判断是否还有下一页，只返回 `limit` 条及 `nextCursor`；无效 cursor 不会拼进 SQL，而是退回第一页。

### 9.6 Redis 查询缓存

```text
analytics:{projectId}:{version}:{namespace}:{filters}
```

结果只缓存 15 秒。Worker 每次成功处理事件、终结超时样本后都会递增版本，新数据到达即切换到新命名空间，旧结果无需遍历删除，TTL 到期自动释放。

**缓存不是权限层**：API 每次都先检查项目成员关系，再进入 cached loader；知道缓存 key 不等于获得读取授权。

## 10. 指标口径：看板上的数字到底怎么来的

### 10.1 没有单一「综合分」

平台**没有 0–100 的综合评分**，指标质量由三层共同表达：

| 层次         | 表达方式                                   | 用途                              |
| ------------ | ------------------------------------------ | --------------------------------- |
| 分位数       | `p50 / p75 / p90 / p95`                    | 体验分布，默认以 **p75** 为主口径 |
| 等级分布     | `good / needs-improvement / poor` 三档计数 | 来自 `serverRating`               |
| 健康度百分比 | `good_count / sample_count × 100%`         | 卡片进度条与「良好率」列          |

以 p75 为主口径，是因为它代表「四分之一的用户比这更差」，比平均值更能反映长尾（Web Vitals 官方也以 p75 为达标判定口径）。而「良好率」只是**样本中被评为 good 的比例**，不是加权分数，也不含 needs-improvement 的部分得分——所以「良好率很高但用户投诉慢」是可能的，此时要同时看 p95 和 poor 计数。

各界面用的口径：

| 界面       | 主口径                                    | 辅助                                |
| ---------- | ----------------------------------------- | ----------------------------------- |
| 运行总览   | LCP p75 趋势 + 各指标良好率               | 样本数、覆盖页面、覆盖率、p50/p95   |
| 性能详情   | 选定指标的 p50/p75/p90/p95 + 三档评级计数 | 样本覆盖率、LoAF 阻塞总时长与脚本数 |
| 页面排名   | 每路由 p75 + 异常率                       | 样本量、PV、LoAF 每千次访问         |
| 自定义信号 | 事件/链路计数、自定义指标聚合             | 时间序列、路由分布                  |

### 10.2 各指标口径速查

| 指标 | 单位  | 方向     | good ≤ / ≥ | poor > / < | 样本语义                                   | 备注                                           |
| ---- | ----- | -------- | ---------- | ---------- | ------------------------------------------ | ---------------------------------------------- |
| LCP  | ms    | 越小越好 | 2500       | 4000       | 每硬导航 1 个；开启软导航后每次软导航 1 个 | 软导航值是「相对软导航起点」，与硬导航不同量纲 |
| FCP  | ms    | 越小越好 | 1800       | 3000       | 每硬导航 1 个                              | 诊断型指标                                     |
| INP  | ms    | 越小越好 | 200        | 500        | 每页面持续修订                             | 需浏览器支持 interactionId                     |
| CLS  | score | 越小越好 | 0.1        | 0.25       | 每导航持续修订                             | 无单位                                         |
| FPS  | fps   | 越大越好 | ≥ 50       | < 30       | 每次采样窗口 1 个独立样本                  | 默认采样窗口 5s、间隔 30s                      |
| LoAF | ms    | 不评级   | —          | —          | 每条长任务 1 个独立样本                    | 最短 50ms、每 View 上限 20 条                  |

### 10.3 端到端算例：一次 LCP 如何变成看板数字

假设某生产页面一分钟内有 5 次访问，其中一次的过程如下。

**第 1 步 · SDK 上报（同一 `sampleId` 三次修订）**

```text
seq 0  value 1820  provisional   occurredAt T+1820
seq 1  value 2300  provisional   occurredAt T+2300
seq 2  value 2600  final         occurredAt T+34s（pagehide）
```

注意这是 **3 个原始事件 = 1 个 LCP 样本**。

**第 2 步 · Worker 投影**

- seq 0：无当前行 → INSERT，`observed_at = T+1820`（此后冻结）
- seq 1：2 > 1 → 同一行 UPDATE
- seq 2：3 > 2 → 同一行 UPDATE，`state = final`，`server_rating = needs-improvement`（2600 > 2500）

**第 3 步 · 落库结果**

`performance_samples` 该分钟新增 5 行（每次访问 1 行），值分别为 `2600 / 1900 / 4200 / 2400 / 3100`。原始层则保留全部 3 条事件用于追溯。

**第 4 步 · 评分**

```text
1900 → good
2400 → good
2600 → needs-improvement
3100 → needs-improvement
4200 → poor
```

**第 5 步 · 聚合（该分钟桶）**

```text
sample_count = 5
minimum = 1900, maximum = 4200
average = (2600+1900+4200+2400+3100)/5 = 2840
p50 = 2600, p75 = 3100（percentile_cont 线性插值）
good_count = 2, needs_improvement_count = 2, poor_count = 1
view_hll / session_hll = 去重基数中间态
```

**第 6 步 · 展示（29 天内查明细）**

```text
LCP  p75 = 3100 ms
良好率 = 2 / 5 = 40%
覆盖率 = 5 个有 LCP 的 View / 该分钟 PV
```

若查询跨度超过 29 天，同样的数据改为从小时 Rollup 用 `approx_percentile(0.75, rollup(value_percentiles))` 取近似 p75，可能与明细查询有细微差异。

### 10.4 关于 `sequence` 和 `clientRating` 的常见误解

- **「web-vitals 算出来的 LCP 不是最终值吗？」** 指标计算与候选筛选由 `web-vitals` 完成，SDK 不重新判断哪个元素是 LCP。但项目在协议上又加了一层生命周期：`web-vitals` 每次回调进来先统一标记为 `provisional`，SDK 在 `view.route-change` 或 `pagehide` 时再把缓存的最新值发一次 `final`。两层「最终」不是一个概念。
- **「默认配置下值都不变，那 sequence 有什么意义？」** 默认 `reportAllChanges = false` 时值的修订确实很少，但协议要同时支撑开启 `reportAllChanges`、final 快照、网络乱序和重试，`sequence` 是这些场景的公共解。
- **「clientRating 是不是在最终阶段额外算的？」** 不是。`web-vitals` 返回的 metric 本身就带 `rating`，SDK 只是把它翻译成协议字段 `clientRating`，`value` 与 `rating` 来自同一个 metric。服务端重算 `serverRating` 是为了统一口径（项目阈值可能不同、旧 SDK 规则可能不同），而不是因为客户端算得不对。

## 11. 实验室测试（Lab Audits）

RUM 数据回答「真实用户遇到了什么」，实验室测试回答「在受控条件下这个页面有多快」。两者互补，因此平台把它们分开实现：**主动测试不写入遥测表，也不会污染 RUM 指标。**

### 11.1 三个角色

```text
Web（LabAuditsPage）
  → API（apps/api/src/lab-audits）
  → lab_audits 表（queued）
  → Audit Worker（apps/audit-worker，Chrome + Lighthouse）
  → lab_audit_runs 表（每轮结果）
  → API 读取结果返回 Web
```

Audit Worker 是一个**独立进程**：它要启动 headless Chrome，内存占用高、可能崩溃，还带安全风险，因此在容器里以 `read_only: true`、`cap_drop: ALL` 之类的限制运行，与必须稳定轻量的 Outbox Worker 完全隔离。

### 11.2 接口与权限

| 接口                                                  | 作用                   |
| ----------------------------------------------------- | ---------------------- |
| `GET /api/v1/projects/:projectId/lab-settings`        | 读取实验室测试设置     |
| `PUT /api/v1/projects/:projectId/lab-settings`        | 更新设置               |
| `POST /api/v1/projects/:projectId/lab-audits`         | 创建一次测试任务       |
| `GET /api/v1/projects/:projectId/lab-audits`          | 列出历史任务           |
| `GET /api/v1/projects/:projectId/lab-audits/:auditId` | 查看单次任务与各轮结果 |

全部受 `SessionGuard + CsrfGuard` 保护，且只有 owner 能发起测试。

### 11.3 任务执行要点

- **创建时**：校验项目权限、校验目标 URL 的 Origin 在白名单内、处理「同一项目只能有一个进行中任务」的唯一约束冲突；请求里携带的自定义请求头（如需登录态）用 `encryptValue` **加密后存储**，读取时再解密。
- **执行时**：Audit Worker 认领 `queued/running` 任务并对其加锁，先删除该任务的旧 `lab_audit_runs`（保证重跑不残留），然后**循环执行 5 轮** Lighthouse，每轮结果写入 `lab_audit_runs`；单轮失败写入该轮的 error，全部结束后汇总更新 `lab_audits` 状态。
- **容器**：`infra/Dockerfile.audit-worker` 提供自带 Chrome 的镜像。

### 11.4 相关表

`0004_lab_audits.sql` 建三张表：

| 表                   | 作用                                                                    |
| -------------------- | ----------------------------------------------------------------------- |
| `lab_audit_settings` | 项目级实验室测试配置（如设备、默认 URL、自定义请求头密文）              |
| `lab_audits`         | 一次测试任务：目标 URL、设备、状态、轮次汇总                            |
| `lab_audit_runs`     | 单轮结果：Lighthouse 分数、指标、诊断、Chrome/Lighthouse 版本、错误信息 |

### 12.2 统一 API 客户端与刷新

Web 的 API 客户端统一携带 Session Cookie，并在写请求中加入 CSRF Token；遇到未登录响应时清理当前用户并引导回登录页。页面组件不直接拼装鉴权逻辑，以免某些设置请求遗漏 CSRF。

看板通过 TanStack Query 管理加载、错误、缓存和刷新，默认每 **15 秒**重新请求，不引入 WebSocket。这个频率与 Worker 的异步处理、服务端 15 秒缓存共同形成近实时体验。

### 12.3 图表与表格的分工

趋势图看随时间变化，指标卡给当前范围的总体结论，表格用于比较页面、事件或原始记录。**不能只展示一条平均值曲线**：平均值会隐藏长尾，因此 Performance 同时给出 p50、p75、p90、p95 和评级分布。

### 12.4 使用路径

```text
总览发现异常（p75 变差、poor 比例上升、覆盖率下降）
        ↓
性能看板确认是哪类指标、哪个时间点
        ↓
页面排名缩小到具体 routeName
        ↓
原始事件确认单条事实与处理状态
        ↓
服务状态判断是链路问题还是业务问题
```

总览同时读取服务状态摘要：**如果业务指标突然归零而 rejected 或 Outbox pending 上升，首先要处理数据链路问题，不能把「没有数据」解释成性能改善。**

对比发布前后时，应固定其他过滤条件，只改变 version 或时间段，避免把页面流量结构变化误判为版本回归。

## 13. 本地运行与运维

### 13.1 启动

从 `browser-monitor/` 根目录执行：

```powershell
pnpm install
Copy-Item platform/.env.example platform/.env
docker compose --env-file platform/.env --profile dev -f platform/infra/docker-compose.yml up --build
```

迁移容器先创建普通关系表、TimescaleDB 扩展、Hypertable、连续聚合、压缩和保留策略。API 就绪后，Caddy 默认在 `http://localhost:8080` 提供 Web 与 API；Mailpit 默认在 `http://localhost:8025` 展示开发邮件。

**一个常见坑**：通过 Compose 运行时，`SMTP_HOST` 必须使用容器服务名 `mailpit`，不能使用只指向 API 容器自身的 `localhost`；只有直接在宿主机运行 API 时才改为 `localhost:1025`。

### 13.2 生产必须修改的配置

`.env.example` 只是本地模板。生产环境至少要替换：

- 数据库凭据；
- `COOKIE_SECRET`、`USER_HASH_SECRET`；
- 公开域名（`PUBLIC_BASE_URL`）并启用 HTTPS；
- SMTP 配置。

Caddy 的 `/internal/metrics` 只应对受信网络开放，不能与公开采集路由使用相同的暴露策略。

### 13.3 健康检查

| 接口                | 含义                          |
| ------------------- | ----------------------------- |
| `GET /health/live`  | API 进程是否存活              |
| `GET /health/ready` | 数据库和 Redis 是否可服务请求 |

容器编排应该用 `ready` 决定是否接流量，而不是把「进程启动」等同于「服务可用」。

### 13.4 运行指标

`GET /internal/metrics` 暴露采集事件结果、采集延迟、Outbox 各状态和死信数量。生产监控至少应观察：采集接口 p95、429 与 5xx、pending 增长率、最老任务等待时间、死信增量和数据库空间。**单看 API HTTP 成功率无法证明 Worker 没有积压。**

### 13.5 容量验证

`load/k6-ingestion.js` 模拟持续和峰值采集，压测时用 `infra/docker-compose.load.yml` 提高测试配额——**不能把压测限流覆盖带进生产默认值**。

验收时需要同时观察客户端发送数、API accepted、原始事件数量、Worker 完成数和最终聚合样本数，才能确认链路没有静默丢失。

## 14. 端到端排查手册

### 14.1 分阶段定位

**第一步 · 确认 SDK 配置**

- 业务构建中是否只使用 `transport.dsn`，没有旧 `endpoint`；
- `app.name` 是否与平台项目标识完全一致；
- 页面实际 Origin 是否包含协议、域名和端口，且与白名单一致；
- SDK 是否已调用 start，Performance 或自定义埋点功能是否被配置关闭。

**第二步 · 确认 HTTP 结果**

浏览器 Network 中查看 `/api/v3/ingest/.../envelopes`：

| 状态                                         | 含义                                             |
| -------------------------------------------- | ------------------------------------------------ |
| 202                                          | 已接收，继续阅读 accepted / duplicate / rejected |
| 403                                          | Origin 不在白名单，或缺失且未开启 originless     |
| 404 `invalid_ingestion_key`                  | key 无效、禁用、过期，或项目被禁用               |
| 422 `unsupported_protocol` / `invalid_batch` | 客户端数据契约不正确                             |
| 429                                          | 项目或 IP 配额不足                               |

**第三步 · 确认持久化与消费**

服务状态 accepted 增长说明事务接收完成。pending 短暂增长属正常异步过程；持续增长且 processed 不变时检查 Worker 容器与数据库连接；processing 长期存在可能来自中断实例，超过 5 分钟应被重新领取；failed 和死信需要查看错误详情，**不能只重复重启进程**。

**第四步 · 确认查询条件**

原始事件能找到而看板为空时，检查 `occurredAt` 是否位于当前时间范围（注意不是 receivedAt）、环境和版本是否匹配、routeName 是否为空或不同、metric 过滤是否正确。Performance 还要检查 `sampleId`、`sequence`、`state`，以及 Worker 是否已经写入 `processed_at`。

**第五步 · 确认聚合**

只有长时间范围缺数据时，才需要检查 TimescaleDB Toolkit、连续聚合与迁移执行情况。最近 29 天主要查明细，更早范围切到小时 Rollup，因此聚合故障不一定会立刻影响默认 24 小时看板。

### 14.2 现象速查表

| 现象                              | HTTP / 位置                     | 原因                                               | 处理                                 |
| --------------------------------- | ------------------------------- | -------------------------------------------------- | ------------------------------------ |
| 一条数据都没有                    | 404 `invalid_ingestion_key`     | 项目未创建 / key 停用 / 项目禁用 / key 过期        | 创建项目或重新复制 DSN               |
| 一条数据都没有                    | 403 `origin_not_allowed`        | 业务域名不在 `allowed_origins`                     | 设置页添加完整 Origin                |
| 整批失败                          | 422 `unsupported_protocol`      | SDK 与平台协议版本不一致                           | 升级 SDK 或平台到同一版本            |
| 整批失败                          | 422 `invalid_batch`             | 批次头缺字段 / 多字段（`.strict()`）               | 检查是否自定义了上报体               |
| 部分被拒                          | `app_name_mismatch`             | 业务 `app.name` ≠ 项目 `app_name`                  | 改成一致                             |
| 部分被拒                          | `event_time_out_of_range`       | 客户端时间偏差过大                                 | 校准用户机器时间                     |
| 部分被拒                          | `invalid_event`                 | 单条事件不合 schema                                | 看 `rejections[].index` 定位         |
| 间歇失败                          | 429                             | 项目 + IP 维度限流                                 | 降低上报量或调整限流                 |
| 已 accepted 但看板没有            | `outbox_tasks`                  | Worker 未运行 / 任务进死信                         | 查 outbox 与 `dead_letter_tasks`     |
| 原始事件有数据、性能看板为空      | `telemetry_events.processed_at` | 尚未处理，或 payload 不是 performance              | 检查处理时间与过滤条件               |
| 近期与历史数据不一致              | 29 天切换点                     | 近期精确分位数、历史近似分位数；或 Rollup 未刷新   | 确认查询跨度与聚合策略               |
| 改了阈值历史看板没变              | 设计如此                        | 阈值只作用于之后处理的样本                         | 需要重算就显式建重算任务             |
| 页面 LCP 一直是空的               | —                               | 只能靠 SPA 跳转到达，默认 `reportSoftNavs = false` | 开启软导航或改造成硬导航可覆盖的路径 |
| 开启软导航后 LCP 变好、上报量暴涨 | —                               | 软导航小值与硬导航值混在同一分布                   | 单独评估，必要时分开看               |
| 良好率很高但用户投诉慢            | —                               | 良好率只看 good 占比，不看长尾                     | 同时看 p95 与 poor 计数              |
| 样本数远大于 PV                   | —                               | FPS / LoAF 本就是多样本指标                        | 若 LCP 也如此，检查是否开启软导航    |

> **SDK 侧特别注意**：非 2xx/408/429/5xx 的响应（如 404/403）会被判定为不可重试，不会重试。所以务必**先建项目、配好白名单，再上线 SDK**。

## 附：一句话总结

先把 `displayName + appName` 建成一个项目，平台在同一事务里生成 `publicKey` 并拼成 DSN；业务侧把 DSN 和**完全相同的 `app.name`** 配进 SDK；SDK 按协议 3.0 把数据批量 POST 到 `/api/v3/ingest/<key>/envelopes`；平台校验版本 → 批次 → 项目 → Origin → 限流 → 逐条事件后，在同一事务写入 `telemetry_events` 与 `outbox_tasks` 并返回 202；Worker 异步把事件投影成样本表、算出服务端评级；TimescaleDB 连续聚合把海量样本压缩成可继续合并的统计摘要；Analytics API 再按时间跨度选择明细或 Rollup，把分布翻译成 p75、良好率、覆盖率和页面排名。**任何一环没对齐（key 不存在、Origin 不在白名单、app.name 不一致、协议版本不匹配），数据都会在写库之前被拒，且 SDK 不会重试。**
