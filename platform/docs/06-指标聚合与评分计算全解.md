# 06 · 指标聚合与评分计算全解

> 目标读者：需要看懂「一条 SDK 上报数据，最后是如何变成看板上的 p75、良好率、覆盖率」的人。
> 本文把所有指标（LCP / FCP / INP / CLS / FPS / LoAF / View / 自定义事件）从**上报 → 落库 → 投影 → 评分 → 聚合 → 查询**串成一条线，并给出每一步的公式与代码位置。

---

## 0. 先记住这张图

```text

│ Instrumentation 产生 Raw Signal        │
│ Collector 翻译成 Payload + 上下文      │
```

一句话概括每一层在做什么：

| 层 | 回答的问题 | 关键机制 |
| --- | --- | --- |
| SDK | 这条数据该不该发、属于哪个页面 | 七道加工关卡、按事件时间解析 View |
| 写入层 | 这条数据是不是合法、是不是重复 | schema 校验、`eventId` 幂等、Outbox 事务 |
| 投影层 | 这条数据对应**哪个样本**、值是多少、评级是什么 | `sampleId` + `sequence` 修订、`serverRating` |
| 聚合层 | 一段时间/一个页面的**分布**长什么样 | 1m/1h 连续聚合、分位数中间态、HLL |
| 展示层 | 用哪个口径看 | 29 天内查明细，更久查 Rollup |

## 1. 上报前：不同指标的形态差异

聚合逻辑之所以分叉，根源是 SDK 上报时**样本语义不同**。协议里所有性能指标共享四个字段，但用法不同：

```ts
// protocol/src/schemas.ts:100-106
const performanceSampleSchema = z.object({
  type: z.literal('performance'),
  sampleId: identifier,     // 样本身份：修订型 vs 一次性
  sequence: z.number().int().nonnegative(),  // 同一样本内的修订序号
  state: performanceSampleStateSchema,       // 'provisional' | 'final'
  value: finiteNonNegative,
});
```

### 1.1 修订型样本：LCP / FCP / INP / CLS

一次页面访问中，指标值会不断变化，SDK 用**同一个 `sampleId` 反复上报修订**：

- `sampleId` = web-vitals 的 `metric.id`（形如 `v6-1770000000123-4567890123456`）；
- `sequence` 从 0 开始递增，`sequence` 越大越新；
- `state` 为 `provisional` 表示还可能变，`final` 表示已定稿；
- 额外带 `delta`（本次增量）、`clientRating`（客户端评级）、`navigationType`、`navigationId`。

```ts
// sdk/src/collectors/performance/web-vitals.ts:86-99
private emit(signal: WebVitalSignal, state: 'provisional' | 'final', timestamp: number): void {
  const sequence = this.sequenceBySample.get(signal.metricId) ?? 0;
  this.sequenceBySample.set(signal.metricId, sequence + 1);
  this.emitter.emit({ name: signal.name, timestamp, payload: toPayload(signal, sequence, state) });
}

private finalize(timestamp: number): void {
  for (const signal of this.latestBySample.values()) this.emit(signal, 'final', timestamp);
  this.latestBySample.clear();
}
```

结算（finalize）的两个时机：

```ts
// sdk/src/collectors/performance/web-vitals.ts:58-67
// This subscriber is installed before ViewCollector. Final snapshots are
// therefore still bound to the view that is about to end.
this.signals.subscribe('view.route-change', (signal) => {
  if (this.active) this.finalize(signal.timestamp);
}),
this.signals.subscribe('page.lifecycle', (signal) => {
  if (this.active && signal.type === 'pagehide' && !signal.persisted) {
    this.finalize(signal.timestamp);
  }
}),
```

### 1.2 一次性终态样本：FPS / LoAF

每次观测本身就是独立样本，**不需要修订**：

```ts
// sdk/src/collectors/performance/fps.ts:25-38
sampleId: createId('sample'),   // 每次都是新 ID
sequence: 0,
state: 'final',                 // 直接是终态
value: (signal.frameCount * 1_000) / signal.sampleDurationMs,
```

LoAF 同理，且带 minDuration 阈值与「每 View 上限」：

```ts
// sdk/src/collectors/performance/loaf.ts:30-40
this.signals.subscribe('performance.loaf', (signal) => {
  if (!this.active ||
      signal.duration < this.options.minDurationMs ||
      this.emittedEntries >= this.options.maxEntriesPerView) {
    return;
  }
  this.emittedEntries += 1;
  ...
```

额度在每次 `view.route-change` 时归零（默认每 View 最多 20 条，最短 50ms）。

### 1.3 三类数据对照

| 类别 | 指标 | 样本身份 | sequence | 是否修订 | 落表 |
| --- | --- | --- | --- | --- | --- |
| 修订型 | LCP / FCP / INP / CLS | `metric.id` | 0,1,2… | 是 | `performance_samples` |
| 一次性 | FPS / LoAF | 新建 `sample-*` | 恒为 0 | 否 | `performance_samples` |
| 成对事件 | `view.start` / `view.end` | `viewId` | — | 结束事件回填 | `view_records` |
| 自定义 | 业务事件 | `eventId` | — | 否 | `custom_event_samples` |

### 1.4 SDK 侧七道关卡（决定"哪些数据根本不会到平台"）

```ts
// sdk/src/processing/index.ts:33-41
return new ProcessingPipeline([
  new NormalizeStage(),                 // 1 格式修正
  new ValidateStage(),                  // 2 结构校验
  new RedactStage(options.sensitiveKeys), // 3 脱敏
  new FilterStage(options.excludeUrls),   // 4 排除 URL
  new DedupeStage(options.dedupeWindowMs),// 5 窗口去重（默认 1000ms）
  new SamplingStage(options.samplingRate),// 6 稳定抽样（默认 1，全采）
  new RateLimitStage(...),                // 7 限流（默认 120 条 / 60 秒）
]);
```

采样是**稳定采样**，按键 `sessionId + type + name` 做 FNV-1a 哈希，同一次会话的同类事件要么全采要么全不采，避免"有 start 没 end"的碎片数据（`sdk/src/processing/sampling/index.ts:37-39`）。

> 看板上的样本量天然受这些关卡影响。若 `samplingRate < 1`，p75 是在**被采样的会话**上算的，不是全量；同一会话内部是完整的，跨会话是按比例的。

## 2. 写入层：从 HTTP 请求到 Outbox

代码位置：`platform/apps/api/src/ingestion/ingestion.service.ts`

处理顺序与每步的丢弃原因：

| 步骤 | 失败结果 | 说明 |
| --- | --- | --- |
| `protocolVersion !== "2.0"` | `unsupported_protocol` | 整批拒绝 |
| batch 头校验失败 | `invalid_batch` | 整批拒绝 |
| publicKey 无效 / 项目停用 | `invalid_ingestion_key` | 整批拒绝 |
| Origin 不在白名单 | `origin_not_allowed` | 整批拒绝 |
| 限流 | `ingestion_rate_limited` (429) | 整批拒绝 |
| 单条 schema 失败 | `invalid_event` | 仅该条 |
| `app.name` 与项目不一致 | `app_name_mismatch` | 仅该条 |
| `occurredAt` 超出 `now+5min` ~ `now-30d` | `event_time_out_of_range` | 仅该条 |
| `eventId` 重复 | 计入 `duplicate` | 仅该条 |

幂等与原子写入的关键实现：

```ts
// ingestion.service.ts:153-166
const eventIds = uniqueValid.map((event) => event.eventId).sort();
await client.query(
  `SELECT pg_advisory_xact_lock(hashtextextended($1 || ':' || ids.event_id, 0))
   FROM unnest($2::text[]) AS ids(event_id) ORDER BY ids.event_id`,
  [`ingest:${project.project_id}`, eventIds],
);
const existing = await client.query<{ event_id: string }>(
  `SELECT event_id FROM telemetry_events
   WHERE project_id = $1 AND event_id = ANY($2::text[]) GROUP BY event_id`,
  [project.project_id, eventIds],
);
```

先按 `eventId` 排序取 advisory lock（避免并发批次死锁），再查重；随后用一个 CTE 完成「插入事件 + 插入 Outbox 任务」，保证**事件与任务同生同死**：

```sql
-- ingestion.service.ts:186-205（节选）
WITH input AS (SELECT * FROM jsonb_to_recordset($2::jsonb) AS row(...)),
inserted_events AS (
  INSERT INTO telemetry_events(...) SELECT ... FROM input
  ON CONFLICT DO NOTHING RETURNING event_id, occurred_at, event
)
INSERT INTO outbox_tasks(project_id, event_id, occurred_at, event)
SELECT $1, event_id, occurred_at, event FROM inserted_events
RETURNING event_id
```

写入前还会做服务端脱敏：用户 id 用项目盐 + 服务端密钥哈希（`hashUserId`）、URL 再次清洗、自定义属性按规则脱敏（`sanitizeEvent`）。

统计落在 Redis（`ingestion:stats:*` 与滚动 60 秒的 `ingestion:rate:*`），因此**被拒绝的事件不会出现在遥测表里**，排查时要看 `service-status` 的 `rejected`。

## 3. 投影层：事件 → 领域样本

代码位置：`platform/apps/worker/src/processor.ts`、`outbox-worker.ts`

Outbox 保证「至少一次投递 + 幂等投影」：任务被领取后处理，失败按 `min(300, 2^attempts)` 秒退避重试，达到 8 次进死信表。

### 3.1 性能指标：一个样本只占一行

主键决定了"修订"的语义：

```sql
-- migrations/0001_platform.sql:203
PRIMARY KEY (project_id, sample_id, observed_at)
```

`observed_at` 用首次插入时的 `occurredAt` 冻结，后续所有修订都是**原位 UPDATE**，不会插成多行。因此分位数看到的是「一次观测 = 一个样本」。

修订的准入与并发控制：

```ts
// processor.ts:80-91
await client.query(
  `SELECT pg_advisory_xact_lock(hashtextextended($1, 0))`,
  [`performance:${projectId}:${payload.sampleId}`],
);
const existing = await client.query(
  `SELECT observed_at, sequence, state FROM performance_samples
   WHERE project_id = $1 AND sample_id = $2
   ORDER BY observed_at DESC LIMIT 1 FOR UPDATE`,
  [projectId, payload.sampleId],
);
if (!shouldApplySequence(current?.sequence ?? null, payload.sequence)) return;
```

```ts
// sequence.ts:1-3
export function shouldApplySequence(current: number | null, incoming: number): boolean {
  return current === null || incoming > current;
}
```

即：**只有更高序号才接受**，重复投递与乱序到达被静默丢弃，这正是 Outbox 至少一次投递下数据仍然准确的原因。

### 3.2 state：final 是单向的

```ts
// processor.ts:97-106
const viewEnded = await client.query(
  `SELECT 1 FROM view_records WHERE project_id = $1 AND view_id = $2 AND ended_at IS NOT NULL LIMIT 1`,
  [projectId, event.context.viewId],
);
const state =
  payload.state === 'final' || current?.state === 'final' || viewEnded.rowCount === 1
    ? 'final'
    : 'provisional';
```

三种情况都会置 final：SDK 已定稿、库里已经是 final、或该 View 已结束。**final 永不回退为 provisional**，但更高 sequence 的迟到事件仍可修正 final 的数值。

### 3.3 View：start/end 合并成一行

```ts
// processor.ts:184-192（插入）
INSERT INTO view_records(project_id, view_id, started_at, ended_at, route_name, url, source, ...)
-- processor.ts:204-216（结束回填）
UPDATE view_records SET ended_at = $4, route_name = $5, url = $6
WHERE project_id = $1 AND view_id = $2 AND started_at = $3
```

同时，`view.end` 会把该 View 里残留的 provisional 样本一并终结：

```sql
-- processor.ts:220-224
UPDATE performance_samples SET state = 'final', route_name = $3
WHERE project_id = $1 AND view_id = $2 AND state = 'provisional'
```

## 4. 评分：serverRating 是怎么算出来的

平台**不采信客户端评级**。SDK 的 `clientRating` 只存为 `client_rating` 列用于排查版本差异，看板一律用服务端算的 `server_rating`。

### 4.1 阈值集合

```ts
// packages/shared/src/thresholds.ts:12-18
export const DEFAULT_THRESHOLDS: ThresholdSet = Object.freeze({
  LCP: { direction: 'lower-is-better', good: 2_500, poor: 4_000 },
  INP: { direction: 'lower-is-better', good: 200,   poor: 500 },
  CLS: { direction: 'lower-is-better', good: 0.1,   poor: 0.25 },
  FCP: { direction: 'lower-is-better', good: 1_800, poor: 3_000 },
  FPS: { direction: 'higher-is-better', good: 50,   poor: 30 },
});
```

### 4.2 评级函数

```ts
// packages/shared/src/thresholds.ts:20-35
if (threshold.direction === 'lower-is-better') {
  if (value <= threshold.good) return 'good';
  if (value <= threshold.poor) return 'needs-improvement';
  return 'poor';
}
if (value >= threshold.good) return 'good';
if (value >= threshold.poor) return 'needs-improvement';
return 'poor';
```

写成公式：

```text
越小越好（LCP/INP/CLS/FCP）：
  value ≤ good            → good
  good < value ≤ poor     → needs-improvement
  value > poor            → poor

越大越好（FPS）：
  value ≥ good            → good
  poor ≤ value < good     → needs-improvement
  value < poor            → poor

LoAF：不评级，rateMetric 返回 null
```

### 4.3 阈值版本化

Worker 读取项目当前有效的阈值版本，项目覆盖项与默认集合合并后计算，并把 `threshold_version_id` 与样本一起保存：

```ts
// processor.ts:228-241
const result = await client.query(
  `SELECT id, config FROM threshold_versions
   WHERE (project_id = $1 AND active)
      OR (project_id IS NULL AND active AND NOT EXISTS (...))
   ORDER BY project_id NULLS LAST LIMIT 1`, ...);
```

**修改阈值只影响之后处理的样本，不会回写历史桶**。所以长期趋势上不同日期可能对应不同阈值版本，看板上出现"评级跳变"时要先确认是否改过阈值。

## 5. 样本终结的三条路径

| 路径 | 触发 | 说明 |
| --- | --- | --- |
| SDK 主动 | `pagehide`（刷新/关页）或 `view.route-change`（SPA 跳转） | 最正常，值最准确 |
| View 结束兜底 | `view.end` 到达 | 处理"Collector 来不及逐项发 final"的情况 |
| 超时兜底 | 每 60 秒扫描一次 | 浏览器被强杀、Beacon 丢失、网络断开 |

```ts
// outbox-worker.ts:48-58
const result = await this.database.pool.query(
  `UPDATE performance_samples SET state = 'final'
   WHERE state = 'provisional' AND last_updated_at < now() - INTERVAL '5 minutes'
   RETURNING project_id`,
);
for (const projectId of new Set(result.rows.map((row) => row.project_id))) {
  await this.redis.incr(`analytics:version:${projectId}`);
}
```

> 这里用的是 `last_updated_at`（平台侧最后更新时间），而**不是** `observed_at`。
> 注意：SPA 场景下路由一切换就 finalize，LCP 可能被"截断"成偏小值——这是口径，不是 bug。

## 6. 聚合层：分位数是怎么合出来的

### 6.1 分钟级连续聚合

```sql
-- migrations/0001_platform.sql:246-267（节选）
SELECT
  time_bucket(INTERVAL '1 minute', observed_at) AS bucket,
  project_id, name, environment, app_version, route_name, threshold_version_id,
  count(*)::bigint                                          AS sample_count,
  min(value)                                                AS minimum,
  max(value)                                                AS maximum,
  avg(value)                                                AS average,
  percentile_agg(value)                                     AS value_percentiles,
  count(*) FILTER (WHERE server_rating = 'good')             AS good_count,
  count(*) FILTER (WHERE server_rating = 'needs-improvement') AS needs_improvement_count,
  count(*) FILTER (WHERE server_rating = 'poor')             AS poor_count,
  hyperloglog(8192, session_id)                             AS session_hll,
  hyperloglog(8192, view_id)                                AS view_hll,
  sum(CASE WHEN name = 'LoAF' THEN COALESCE((detail->>'blockingDuration')::double precision, 0) ELSE 0 END) AS blocking_duration_total,
  sum(CASE WHEN name = 'LoAF' THEN COALESCE((detail->>'scriptCount')::integer, 0) ELSE 0 END)::bigint       AS script_count
FROM performance_samples
GROUP BY bucket, project_id, name, environment, app_version, route_name, threshold_version_id
```

七个分组维度：**时间桶 + 项目 + 指标名 + 环境 + 版本 + 路由 + 阈值版本**。
注意 `percentile_agg(value)` 存的是**可再合并的中间状态**（不是已经算好的数字），这样才能把分钟桶再合成小时桶。

### 6.2 小时级分层聚合

```sql
-- migrations/0002_hourly_aggregates.sql:5-29（节选）
SELECT time_bucket(INTERVAL '1 hour', bucket) AS bucket, ...
  sum(average * sample_count) / NULLIF(sum(sample_count), 0) AS average,
  rollup(value_percentiles) AS value_percentiles,
  rollup(session_hll) AS session_hll,
  rollup(view_hll)    AS view_hll,
FROM performance_rollup_1m
GROUP BY 1, 2, 3, 4, 5, 6, 7
```

两个关键点：

1. **分位数用 `rollup()` 合并中间态**，而不是对已算出的 p75 再求平均——后者会让小流量桶和大流量桶等权。
2. **均值按样本数加权**：`sum(average * sample_count) / sum(sample_count)`，等价于全局平均。

### 6.3 刷新、实时、保留与压缩

| 配置 | 值 |
| --- | --- |
| 分钟聚合刷新 | 每 10 秒，`end_offset = 10 秒` |
| 小时聚合刷新 | 每 5 分钟，`end_offset = 1 小时` |
| 实时聚合 | `materialized_only = false`（0003 迁移），未物化区间由明细实时补 |
| 明细保留 | `telemetry_events` / `performance_samples` / `view_records` / `custom_event_samples`：30 天 |
| 聚合保留 | 1m / 1h 均为 180 天 |
| 压缩 | 超过 24 小时的 chunk 压缩，`segmentby = project_id,name` |

### 6.4 关于修订与聚合的一致性

样本行会被 UPDATE（值从 provisional 改成 final）。TimescaleDB 会为受影响的时间段记录失效并在下次刷新时重算该桶，realtime 模式下失效区间由明细实时计算。因此**一次观测始终只贡献一个样本**，不会因为修订而被重复计数——这是"同 `sampleId` 原位 UPDATE"设计的核心收益。

## 7. 查询层：什么时候查明细，什么时候查 Rollup

```ts
// analytics.service.ts:382-384
private useRollups(filters: AnalyticsFilters): boolean {
  return filters.from.getTime() < Date.now() - 29 * 24 * 60 * 60_000;
}
```

| 查询跨度 | 数据源 | 分位数算法 | 分桶 |
| --- | --- | --- | --- |
| 最近 29 天内 | `performance_samples` 明细 | `percentile_cont()`（精确） | 1 分钟 |
| 早于 29 天 | `performance_rollup_1h` | `approx_percentile(0.75, rollup(value_percentiles))`（近似） | 1 小时 |

近 29 天的精确查询（以 performance 接口为例）：

```sql
-- analytics.service.ts:92-108（节选）
SELECT time_bucket(INTERVAL '1 minute', observed_at) AS bucket, name,
  count(*)::bigint AS count,
  count(DISTINCT session_id)::bigint AS session_count,
  count(DISTINCT view_id)::bigint    AS view_count,
  avg(value) AS average,
  percentile_cont(0.50) WITHIN GROUP (ORDER BY value) AS p50,
  percentile_cont(0.75) WITHIN GROUP (ORDER BY value) AS p75,
  percentile_cont(0.90) WITHIN GROUP (ORDER BY value) AS p90,
  percentile_cont(0.95) WITHIN GROUP (ORDER BY value) AS p95,
  count(*) FILTER (WHERE server_rating = 'good')::bigint AS good_count,
  ...
FROM performance_samples p WHERE <filters> GROUP BY bucket, name
```

支持的所有过滤维度（`analytics.controller.ts:10-17`）：`from / to / environment / version / routeName / metric`。
**没有 navigationType、没有 device、没有自定义维度**——这就是为什么软导航 LCP 无法在平台侧与硬导航 LCP 分开看。

### 7.1 派生指标公式

```text
样本覆盖率 sampleCoverage = 有该指标的 DISTINCT view_id 数 / view_records 的 PV 数
异常率（routes）          = (needs_improvement + poor) / 有效评级样本数
会话 / 页面去重数         = distinct_count(rollup(session_hll)) / distinct_count(rollup(view_hll))
LoAF 每千次访问           = LoAF 样本数 × 1000 / 页面访问数
```

### 7.2 缓存

```ts
// analytics.service.ts:563-569
const version = (await this.redis.get(`analytics:version:${projectId}`)) ?? "0";
const key = `analytics:${projectId}:${version}:${namespace}:${JSON.stringify(filters)}`;
...
await this.redis.set(key, JSON.stringify(value), "EX", 15);
```

结果只缓存 15 秒；Worker 每成功处理一个事件、或每终结一批超时样本都会 `INCR` 版本号，前端因此切到新命名空间，无需主动清理旧键。

## 8. "最终分数"到底是什么

平台**没有单一的 0-100 综合分**，指标质量由三层共同表达：

### 第一层：分位数（体验分布）

`p50 / p75 / p90 / p95`。看板默认以 **p75** 为主口径——它代表"四分之一的用户比这更差"，比平均值更能反映长尾。
（Web Vitals 官方也以 p75 为达标判定口径。）

### 第二层：等级分布（评级计数）

`good / needs-improvement / poor` 三档计数，来自第 4 节的 `serverRating`。

### 第三层：健康度百分比（界面上最接近"分数"的那个数）

```ts
// apps/web/src/pages/OverviewPage.tsx:13-15
function quality(metric: MetricSummary): number {
  return metric.count ? Math.round((metric.goodCount / metric.count) * 100) : 0;
}
```

```text
良好率 = good_count / sample_count × 100%
```

卡片上的 `指标健康度` 进度条就是它，`核心指标` 表里的 `良好率` 列也是它。
**它是"样本中被评为 good 的比例"，不是加权分数，也不含 needs-improvement 的部分得分。**

### 各页面用的口径

| 界面 | 主口径 | 辅助 |
| --- | --- | --- |
| 运行总览 | LCP p75 趋势 + 各指标良好率 | 样本数、覆盖页面、覆盖率、p50/p95 |
| 性能详情 | 选定指标的 p50/p75/p90/p95 + 等级分布三档计数 | 样本覆盖率、LoAF 阻塞总时长/脚本数 |
| 页面排名 | 每路由 p75 + 异常率 | 样本量、PV、LoAF 每千次访问 |

## 9. 各指标口径速查表

| 指标 | 单位 | 方向 | good ≤ / ≥ | poor > / < | 样本语义 | 备注 |
| --- | --- | --- | --- | --- | --- | --- |
| LCP | ms | 越小越好 | 2500 | 4000 | 每硬导航 1 个；开启软导航后每次软导航 1 个 | 软导航值为"相对软导航起点"，与硬导航不同量纲 |
| FCP | ms | 越小越好 | 1800 | 3000 | 每硬导航 1 个 | 诊断型指标 |
| INP | ms | 越小越好 | 200 | 500 | 每页面持续修订 | 需浏览器支持 `interactionId` |
| CLS | score | 越小越好 | 0.1 | 0.25 | 每导航持续修订 | 无单位 |
| FPS | fps | 越大越好 | ≥ 50 | < 30 | 每次采样窗口 1 个独立样本 | 默认采样窗口 5s、间隔 30s |
| LoAF | ms | 不评级 | — | — | 每条长任务 1 个独立样本 | 最短 50ms、每 View 上限 20 条 |

## 10. 端到端示例：一次访问的 LCP 如何变成看板数字

假设一个生产环境页面，某分钟内有 5 次访问：

**第 1 步 · SDK 上报（同一 `sampleId` 三次修订）**

```text
seq 0  value 1820  provisional   occurredAt T+1820
seq 1  value 2300  provisional   occurredAt T+2300
seq 2  value 2600  final         occurredAt T+34s（pagehide）
```

**第 2 步 · Worker 投影**

- seq 0：无当前行 → INSERT，`observed_at = T+1820`（**此后冻结**）
- seq 1：2 > 1 → UPDATE 同一行
- seq 2：3 > 2 → UPDATE 同一行，`state = final`，`server_rating = needs-improvement`（2600 > 2500）

**第 3 步 · 落库结果**

`performance_samples` 里该项目该分钟新增 5 行（每次访问 1 行），值分别为 `2600 / 1900 / 4200 / 2400 / 3100`。

**第 4 步 · 评分**

```text
1900 → good
2400 → good
2600 → needs-improvement
3100 → needs-improvement
4200 → poor
```

**第 5 步 · 聚合（该分钟桶）**

```text
sample_count = 5
minimum = 1900, maximum = 4200
average = (2600+1900+4200+2400+3100)/5 = 2840
p50 = 2600, p75 = 3100（percentile_cont 线性插值）
good_count = 2, needs_improvement_count = 2, poor_count = 1
view_hll / session_hll = 去重基数中间态
```

**第 6 步 · 展示（29 天内查明细）**

```text
LCP  p75 = 3100 ms
良好率 = 2 / 5 = 40%
覆盖率 = 5 个有 LCP 的 View / 该分钟 PV
```

如果查询跨度超过 29 天，同样的数据改为从 `performance_rollup_1h` 用 `approx_percentile(0.75, rollup(value_percentiles))` 取近似 p75，可能与明细查询有细微差异。

## 11. 常见误解与排查

| 现象 | 真实原因 |
| --- | --- |
| 看板无数据，但原始事件里查得到 | 先查 `telemetry_events.processed_at` 是否为空，再看 Outbox 的 pending/processing/failed 与死信；也要确认时间范围是否覆盖 `occurredAt`（不是 receivedAt） |
| 近期与历史数据不一致 | 查询跨过 29 天切换点：近期用精确分位数，历史用近似分位数；也可能是 Rollup 策略未运行 |
| 改了阈值，历史看板没变 | 设计如此，阈值只作用于之后处理的样本，旧桶保存着当时的 `threshold_version_id` |
| 页面 A 的 LCP 一直是空的 | 若 A 只能靠 SPA 跳转到达，默认 `reportSoftNavs = false` 时根本不产生 LCP |
| 开启软导航后 LCP 突然变好 | 相对软导航起点的小值与硬导航值混在同一分布里，p75 与良好率被稀释 |
| 开启软导航后上报量暴涨 | web-vitals 在 `softNavsEnabled` 时不再取最后一条 entry，等效于打开了 `reportAllChanges` |
| 良好率很高但用户投诉慢 | 良好率只看 good 占比，不看长尾；应同时看 p95 与 poor 计数 |
| 样本数远大于 PV | FPS/LoAF 本就是多样本指标；若 LCP 也如此，检查是否开启了软导航 |
